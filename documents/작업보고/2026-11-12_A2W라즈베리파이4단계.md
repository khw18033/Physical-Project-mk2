## 5. ⚠ netplan yaml 손상: 연구실 Wi-Fi 프로필 사라짐 (연구실 프로필만 복구함)

> **추가 (같은 날, 사람 승인 후)**: 연구실 Wi-Fi 프로필만 다시 등록했다. 재부팅 확인은 아직 하지 않았다.
>
> 한 일:
> 1. 백업의 `90-NM-16ace436-….yaml`을 `/etc/netplan/`에 되살렸다(616 B, root, 600). 내용은 출력하지 않았다.
> 2. `sudo sync` → `netplan generate` → `nmcli con reload`
> 3. `nmcli con mod netplan-wlan0-SysAILAB_5GHz connection.autoconnect-priority 12` → `sudo sync`
>
> 지금 상태:
> - `netplan-wlan0-SysAILAB_5GHz`가 자동 연결 yes, 우선순위 12로 다시 보인다. yaml은 668 B이고 `autoconnect-priority: "12"`가 들어 있다.
> - 연결 중인 `!!`(wlan0)와 Tailscale은 끊기지 않았다.
>
> 하지 않은 것:
> - `netplan-eth0`(유선 DHCP, 원래 자동 연결 끔)은 되살리지 않았다.
> - 0바이트로 남은 `90-NM-75a1216a-….yaml`은 `con reload` 때 NM이 지웠다.
> - 이 프로필이 필요하면 백업의 같은 파일을 되살리면 된다.
>
> 아래 「복구안」 가운데 연구실 부분은 위 내용으로 끝났다.

**증상**
- 재부팅 뒤 `nmcli con show`에 `netplan-wlan0-SysAILAB_5GHz`와 `netplan-eth0`이 없다.
- `/etc/netplan/90-NM-*.yaml` 두 개가 모두 0바이트다.
- 지금 wlan0은 우선순위가 가장 높은 `!!`(10.47.149.200)로 붙어 있다. 기본 경로와 Tailscale은 정상이다.
- 핫스팟이 없는 곳에서는 연구실 Wi-Fi에 붙지 못한다. **연구실에서 핫스팟을 끄면 pi10에 원격으로 닿을 수 없다.**
- `netplan-eth0`(유선 DHCP)은 원래 자동 연결을 꺼 둔 프로필이라 사라져도 동작에는 영향이 없다.

**원인**

이번 부팅 기록에 비정상 종료 흔적이 있다.
- `EXT4-fs (mmcblk0p2): orphan cleanup on readonly fs`
- `/boot/firmware`: `Dirty bit is set. Fs was not properly unmounted`

일어난 순서는 다음과 같다.
1. `nmcli con mod netplan-wlan0-SysAILAB_5GHz …`를 실행하면 NetworkManager의 netplan 연동이 `90-NM-*.yaml`을 다시 쓴다. 두 파일 모두다.
   - 바꾼 직후에는 파일이 정상이었다. `connection.autoconnect-priority: "12"`를 확인했다.
2. 몇 분 뒤 전원이 정리 없이 끊겼다. 다시 쓴 내용이 SD 카드에 완전히 기록되기 전이었다.
3. 부팅 때 파일 시스템 복구에서 두 파일이 0바이트로 남았다.
   - 파일 시각이 이번 부팅 1~2초 시점이다. 이 시점 시계는 저장된 값(14:53)에서 출발했다.

같은 방식으로 다시 쓴 NM 키 파일 셋(`!!`, `AndroidAP1991`, `dshs`)은 멀쩡했다.

작업 전부터 0바이트였던 `/etc/NetworkManager/system-connections/SysAILAB_5GHz.nmconnection`(2026-11-11)도 같은 원인으로 보인다. NM은 부팅 때마다 이 파일을 읽다가 `connection.type: property is missing` 경고를 낸다.

**복구안 (실행하지 않음)**

자동 모드 권한 검사에서 막혀 실행하지 않았다. 사람 승인이 필요하다.

```
B=~/pi-a2-backup/20261112-145350-wifiprio/netplan
sudo cp --preserve=mode,ownership $B/90-NM-16ace436-6c3d-3bad-8cee-4204382a59cc.yaml /etc/netplan/
sudo cp --preserve=mode,ownership $B/90-NM-75a1216a-9d1a-30cd-8aca-ace5526ec021.yaml /etc/netplan/
sudo sync
sudo netplan generate
sudo nmcli con reload
sudo nmcli con mod netplan-wlan0-SysAILAB_5GHz connection.autoconnect-priority 12
sudo sync
nmcli -f NAME,AUTOCONNECT,AUTOCONNECT-PRIORITY,ACTIVE con show
```

- 백업은 우선순위를 바꾸기 직전 상태다. 두 파일 모두 정상 크기(616 B, 317 B)이고, `netplan-eth0` 자동 연결 끄기도 들어 있다.
- `con reload`는 지금 연결 중인 `!!`를 끊지 않는다.

## 6. 주의 (현장 운용)

- **pi10은 보조배터리를 뽑아서 끈다. 설정을 바꾼 뒤에는 반드시 `sudo sync`를 하거나, `sudo poweroff`로 끈다.** 이번 손상이 바로 이것 때문이다.
- 특히 netplan으로 저장된 프로필(`netplan-*`)은 nmcli로 바꿀 때마다 yaml을 통째로 다시 쓴다.
  - 복구 뒤 연구실 프로필을 NM 키 파일로 옮기는 것도 생각해 볼 만하다.
  - 0바이트 `SysAILAB_5GHz.nmconnection`은 그때 같이 정리하면 된다. 사람 판단이 필요하다.
- `autostart.sh` 주석의 끄는 법 `pkill -f viz_a2/autostart.sh`는 cron으로 뜬 것(절대경로)에는 맞는다. 손으로 `./autostart.sh`처럼 띄운 것에는 맞지 않는다.
- PC2 브리지는 부팅 직후 20~30초 동안 `ClientStub` 오류와 `unreachable` 경고를 내다가 스스로 붙는다. 정상이다.
- 재부팅하면 브리지는 늘 모의 실행(`dry_run: true`)으로 뜬다. 실제 제어는 사람이 웹에서 고를 때만 켜진다.
