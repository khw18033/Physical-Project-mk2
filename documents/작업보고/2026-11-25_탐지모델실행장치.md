## 1절 — 무엇을 정했나 (사용자 결정)

| 항목 | 결정 |
|---|---|
| 표시 | 판 목록은 모델명처럼 간단히(칩 끝 한 낱말), 상세는 정확히 어떤 장치인지 |
| data_stream 협의 ① `running` 에 `node` 적기 | data_stream: 오히려 요동칠 수 있다 → **가시화가 배치표를 받아 저장하고 그대로 쓴다.** 배치가 바뀌면 `planned` 가 처음부터 다시 오므로 새 배치표로 갈아 끼운다 |
| data_stream 협의 ② 자원 배분 없이 띄운 비전의 위치 | data_stream: 필요 없는 정보를 더하면 성능 문제 → **배치표에 없으면 추정이 아니라 data_stream 기기로 확정** |
| 지금 보이는 값 | 지금은 노트북만 뜨는 게 맞다(placement/1 은 GPU 모델을 파이로 옮기지 않는다 — 사용자 확인) |
| data_stream 답 ① (정리본) | 「배치가 달라질 때마다 스트림 갱신 — 가시화도 동기화 갱신으로 해결되는지 확인」 → 코드로 확인하고 **끝남(`stopped`)까지 따라가게** 고침(3절) |
| data_stream 답 ② (정리본) | 「자원 배분이 없으면 data_stream 서버에서 모든 비전」 → 런처 코드로 확인, 서버 고정과 host 키 비교 뒤 **서버 고정 유지**(사용자 결정) |

### data_stream 답 검토

**① 배치가 바뀌는 길** (`ds_resources/controller.py` · `cli.py`)

| 바뀌는 길 | 스트림 | 반영 |
|---|---|---|
| 새 실행(런처 → `cli run` → `submit`) | 새 `planned` | 저장본 교체 |
| GPU 메모리 부족으로 다시 요청(`RETRY_GPU`) | `planned` 연달아 | 가장 새 것 |
| 실행 끝(✕ · 끝남 · 돌 것 없음) — `cli` 는 끝낼 때 늘 `k.stop` | `stopped` (새 `planned` 없음) | **처음 구현은 놓쳤다** → 고침: 그 배치표는 「지난 배치표」, 칩은 data_stream 기기 |
| CPU 작업 노드 이동 | `replanned` (새 `planned` 없음) | 반영 안 함 — CPU 작업은 탐지 모델 칩이 아니다 |

GPU 작업은 실행 중 노드를 옮기지 않는다(죽으면 WSL 안에서 다시 띄우고 `degraded`). 그래서 칩에 닿는 변화는 새 `planned` 와 `stopped` 둘이다.

**② 자원 배분이 없을 때** — 런처 `launcher.ps1:707` 은 같은 기기 WSL 창에서 `vision/vision_infer.py` 를 바로 띄운다(켜면 `:686` `ds_resources.cli run`).
다른 기기에서 비전을 띄우는 길은 없다.

| | 서버 고정 (채택) | host 키 추가 |
|---|---|---|
| data_stream 수정 · 성능 | 없음 | 결과 · `/health` 에 칸 추가(그쪽 성능 우려), telemetry 는 SCAN + GET |
| 정확도 | 런처 규칙 안에서는 정확, 손으로 다른 기기에서 띄우면 틀림 | 늘 정확 |
| 장치 이름 · 하드웨어 | `node_resource_stream` 의 `source: local` 노드 | 호스트 이름뿐 — 결국 노드 스트림과 맞춰야 함 |
| 계약 | 있는 스트림 둘 | 새 계약 필요 |

## 2절 — 읽는 창구 (data_stream 무수정)

`/health` 에는 실행 장치가 없다(그쪽 `host` 는 영상을 받는 서버 이름). 그래서 data_stream 이 「가시화가 읽는 계약」으로 만든 스트림 두 개를 읽는다.

| 스트림 | 쓰는 것 |
|---|---|
| `orchestration_stream` (orch/1) | **가장 최근 `planned`** 의 `plan.gpu_units[] = {node, models, sources, fps_cap, need_mb, need_basis}` · `cpu_units` · `refused`, 그 요청의 마지막 기록(applied · running · stopped …) |
| `node_resource_stream` (node/1) | 노드마다 마지막 기록(role · source(local/k3s) · CPU · 메모리 · GPU 사용량), 가장 최근 `baseline`(arch · 스레드 · RAM · GPU 이름) |

개발 서버 중계에 넷째 경로를 더했다.

```
GET /vision-stream/placement?redis=redis://<host>:6380
  → XREVRANGE orchestration_stream + - COUNT 200
  → XREVRANGE node_resource_stream + - COUNT 300     (이 둘만 보낸다 · 키는 쿼리로 안 받는다)
  → { plan: {...} | null, nodes: { <노드>: {...} } }
```

## 3절 — 판단 규칙

1. **배치표 저장 · 교체** — 받은 배치표는 이 브라우저 `localStorage`(`vz.detect.placement.v1:<redis 주소>` — **Redis 주소마다 따로**)에 둔다.
   창구가 배치표를 못 주면(스트림에서 밀려남 · Redis 꺼짐) 저장본을 그대로 쓰고 상세에 「저장해 둔 배치표(시각)를 씁니다」를 적는다.
   **더 새 `planned`** 가 오면 통째로 바꾼다. 신구는 **기록 시각 `ts`** 로 가린다 — Redis 가 꺼져 있던 동안의 기록은 data_stream 이 나중에
   몰아 쓰므로(outbox) 스트림 ID 로 가리면 옛 `planned` 가 새것처럼 보인다. 노드 baseline 도 이번 답에 없으면 저장본을 이어 쓴다.
2. **끝남 따라가기** — 창구가 읽은 범위 안 요청마다 마지막 기록(`requests`)을 같이 준다. 저장본의 요청이 거기 있으면 `last` 를 갈아 끼운다
   (배치표가 밀려난 뒤에 온 `stopped` 도). `last` 가 `stopped` 면 그 배치표는 **저장은 그대로, 칩 판단에는 안 쓴다** — 상세에 「지난 배치표 · 끝남」.
3. **(소스, 모델) → 장치** — 돌고 있는 배치표 `gpu_units` 에 그 소스 · 모델이 있으면 그 노드. 없으면 **data_stream 기기로 확정**하고, 노드 이름은
   `source: local` 로 기록된 노드(자원 기록기)에서 가져온다. 기록기가 꺼져 있으면 이름 대신 「이름 모름 · 서버 host」.
4. **장치 종류** — 노드 이름으로 가르지 않는다(아래 4절: 이름이 문서마다 다르다). `source: local` 이나 `role=gpu` 면 「노트북」,
   `role` 이 robot · sensor · small 이거나 arch 가 aarch64 면 파이(노드 이름을 보라색으로), 그 밖은 노드 이름.

## 7절 — 쓰는 법과 한계

- 판: 살아 있는 모델 칩 끝에 「노트북」. 머리 안내 줄에 「장치 N곳」. 칩에 마우스를 올리면 노드 이름.
- 상세(카드 더블클릭): 오른쪽 맨 위 「실행 장치」. 배지가 「배치표」면 돌고 있는 오케스트레이터 배치가 둔 곳, 「data_stream 기기」면 돌고 있는 배치표에
  없어 확정한 것. 배치표가 끝났으면 「지난 배치표 · 끝남 시각」 한 줄이 같이 나온다.
- 끝남은 그 요청의 **마지막** 기록이 `stopped` 일 때다. 한 요청 안 여러 단위 중 일부만 멈추는 경우는 따로 가르지 않는다(지금 런처 실행은 GPU 단위 하나).
- CPU 작업의 `replanned`(노드 이동)는 반영하지 않는다 — CPU 작업을 판에 보일 때 같이 붙인다.
- 저장본은 브라우저마다 따로다. 다른 기기에서 처음 열면, 스트림에 `planned` 가 남아 있어야 배치표가 선다. 없으면 모두 data_stream 기기로 나온다.
- data_stream Docker 계획(`ba59516`)의 감독자도 `orchestration_stream` 에 쓴다고 한다. 모르는 기록 종류는 무시하므로 깨지지 않지만, 계약이 정해지면 다시 본다.
- 정적 빌드(중계 없음)에서는 배치표를 못 읽는다. 그때도 칩은 「노트북」(data_stream 기기 확정)으로 나온다.
