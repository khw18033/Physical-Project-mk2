## 요약

- **지금 모습:** 가시화 웹이 Tailscale을 거쳐 로봇 위 라즈베리파이(`pi10`)에 붙는다. 그 하나의 주소로 다음이 모두 된다.
  - A2-W 상태 보기
  - 전방 카메라 보기
  - 키보드 수동 제어
- 노트북을 로봇에 꽂을 필요가 없어졌다. Go1(pi7)과 같은 방식이다.
- **거쳐 온 길:**
  1. 노트북을 PC2에 유선으로 직접 꽂아 접속했다.
  2. PC2에 브리지를 올려 웹에 띄우고, 카메라와 수동 제어를 붙였다.
  3. Pi 전환 인계 폴더를 만들었다.
  4. pi10에 브로커, 카메라 중계, 방화벽을 설정했다.
  5. 브리지를 pi10 브로커로 옮겼다.
  6. 자동 시작을 걸었다. 로봇과 pi10의 전원을 껐다 켜기만 하면, 사람이 손대지 않아도 웹에 다시 뜬다.
- **사용자 확인(3단계 끝):** 웹 연결, 카메라 송출, 키보드 제어(모의 실행, 실제 제어)가 모두 정상이다.
- **4단계 확인:** 재부팅 뒤 `check-pi.sh robot`이 모두 OK다. 브리지는 다시 모의 실행으로 뜬다. Tailscale 규칙도 살아 있다.
- **사고 1건:** pi10 Wi-Fi 설정을 바꾼 직후 배터리를 뽑아 껐다. 그 바람에 연구실 Wi-Fi 프로필 파일이 0바이트가 되었다. 연구실 프로필은 백업에서 되살렸고, 재부팅 확인은 아직이다(§2.7).
- **남은 것:**
  - 5단계: 실외와 무선 점검
  - 연구실 Wi-Fi 복구를 재부팅으로 확인
  - A/D(옆 이동) 무반응
  - 조종기 명령 실동작 확인

### 2.4 pi10 1단계: 책상에서 설정 (pi10 에이전트)

- 새 Pi 대신 기존 **pi10**(Raspberry Pi 5, Debian 13 trixie)을 썼다. 호스트 이름과 Tailscale 이름은 그대로 두었다.
- 작업 전에 확인했다: pi10에 다른 브로커가 없다. Go1 브로커와 겹치지 않는 A2 전용 브로커다.

| 항목 | 결과 |
|---|---|
| eth0 | NM 프로필 `a2-pc2`: `192.168.124.50/24`, 게이트웨이 없음. 기존 `netplan-eth0`(DHCP)는 자동 연결만 껐다. 기본 경로는 wlan0 그대로 |
| mosquitto 2.0.21 | `/etc/mosquitto/conf.d/a2.conf`: 1883, 9001(ws) |
| 카메라 중계 | `a2-camrelay.service`(socat) |
| 방화벽 | `/etc/nftables.d/a2.nft`, `nftables.conf`에 include만 추가 |
| 백업 | 작업 전 상태를 `~/pi-a2-backup/20261112-140559/`에 남겼다 |

`nftables` 주의: 서비스를 `restart`나 `start`하지 않는다. `nftables.conf` 첫 줄의 `flush ruleset`이 Tailscale 규칙까지 지운다. a2viz 표만 다시 올릴 때는 `sudo nft -f /etc/nftables.d/a2.nft`를 쓴다.

노트북에서 따로 확인했다(노트북이 pi10과 같은 Wi-Fi 192.168.50.x에 있었다).

| 경로 | 1883 | 9001 | 8090 | 22 |
|---|---|---|---|---|
| Tailscale `pi10.tailcb6bfb.ts.net` | 열림 | 열림 (ws MQTT 접속 성공, mosquitto 2.0.21) | 열림 | — |
| Wi-Fi 직접 `192.168.50.73` | **막힘** | **막힘** | **막힘** | 열림 (경로 대조군) |

→ 인증 없는 브로커가 Tailscale과 로봇 쪽에만 열려 있다.

브로커에서 본 값:
- 1883에 붙은 클라이언트는 PC2 하나뿐이다.
- 3초 동안 state 30건(10 Hz), status 2건, heartbeat 1건, capability 1건이 오갔다.
- status: `online`, `dry_run: true`, `sdk.ready: true`, 배터리 63 %, `robot_mode: ai_free_walk`
- `registration.ip`는 `192.168.124.162`로 자동으로 잡혔다(0.3 변경).

카메라:
- Pi 중계 snapshot: 1920×1080 JPEG 189 KB
- PC2 직접 snapshot: 200

**사용자 확인 결과:** 웹에서 「Tailscale (A2-W)」로 붙어 다음을 확인했다.
- 가시화 연결: 카드 `a2-001`과 상태판
- 카메라 송출
- 키보드 제어: 모의 실행과 실제 제어 모두

**노트북 쪽 기록(Tailscale):** 시험 동안 pi10에서 약 1.3 GB를 받았다. 같은 Wi-Fi인데도 연결이 **직접이 아니라 중계 서버(DERP, `tok`)를 거쳤다.** 오늘은 문제가 없었지만 지연과 대역폭에 불리하다. 5단계에서 잰다.

**2·3단계에서 나온 것과 처리:**

| 발견 | 처리 |
|---|---|
| 첫 접속에도 `[mqtt] reconnected after 0s`가 찍힌다 | 저장소 `a2-bridge/`에서 고쳤다(한 번이라도 붙었는지 따로 기억). **PC2에는 아직 올리지 않았다.** 표시만 틀린 문제라 급하지 않다 |
| ssh로 `nohup … &`를 실행하면 ssh가 돌아오지 않는다 | 4단계에서 `ssh -f` + `setsid`로 피했다. `autostart.sh` 주석에 이 방법을 적었다 |

### 2.6 pi10 4단계: 자동 시작

| 위치 | 한 일 |
|---|---|
| pi10 | mosquitto, a2-camrelay, tailscaled, nftables가 모두 enabled인지 확인했다. nftables는 start하지 않았다 |
| PC2 | 사용자 crontab에 `@reboot /home/unitree/viz_a2/autostart.sh` 한 줄만 넣었다. sudo는 쓰지 않았다 |
| pi10 (사람 요청) | Wi-Fi 자동 연결 우선순위: 핫스팟 `!!` 20, `AndroidAP1991` 15, 연구실 `SysAILAB_5GHz` 12, `dshs` 10 |

**재부팅 확인:** 사람이 로봇과 pi10 전원을 껐다 켠 뒤, 아무것도 손대지 않고 확인했다(두 장비 모두 uptime 1분).

| 항목 | 결과 |
|---|---|
| `check-pi.sh robot` | 모두 OK. nft 항목까지 포함 |
| 브리지 | cron → `autostart.sh` → `a2_bridge.py --broker 192.168.124.50`. `dry_run: true`, 배터리 53 % |
| Tailscale 규칙 | tailscaled 표 6개와 `ts-*` 체인이 그대로 있다. 부팅 순서: nftables 3.5초 → tailscaled 6.4초. 그래서 `flush ruleset`이 Tailscale 규칙을 지우지 않는다 |
| 부팅 직후 브리지 로그 | 약 20초 동안 `[ClientStub] send request error`가 나온다(PC1 서비스가 아직 안 뜸). pi10 부팅 중에는 `unreachable` 경고가 나오고, 31초 뒤 스스로 붙는다. 브리지가 죽었다 다시 뜬 일(`exited`)은 없다 |

**재부팅하면 브리지는 늘 모의 실행으로 돌아간다.** 실제 제어는 사람이 웹에서 고를 때만 켜진다.

### 2.7 사고: pi10 netplan 파일 손상 → 연구실 Wi-Fi 프로필 사라짐

| 항목 | 내용 |
|---|---|
| 일어난 일 | Wi-Fi 우선순위를 바꾸려고 `nmcli con mod`를 실행하면 NM이 `/etc/netplan/90-NM-*.yaml` 두 개를 다시 쓴다. 몇 분 뒤 보조배터리를 뽑아 전원을 끊었다. 디스크에 다 써지기 전이었다 |
| 근거 | 부팅 기록에 `EXT4-fs … orphan cleanup`과 `/boot/firmware` `Dirty bit is set`이 남았다 |
| 결과 | yaml 두 개가 0바이트가 되었다. 연구실 Wi-Fi(`netplan-wlan0-SysAILAB_5GHz`)와 `netplan-eth0`(원래 자동 연결 끔) 프로필이 사라졌다. pi10은 핫스팟 `!!`로만 붙었다 |
| 복구 (사람 승인 후) | 백업(`~/pi-a2-backup/20261112-145350-wifiprio/`)에서 연구실 yaml을 되살리고 우선순위 12를 다시 넣었다. `netplan-eth0`은 쓰지 않는 프로필이라 되살리지 않았다 |
| 아직 안 한 것 | **복구한 연구실 프로필이 재부팅 뒤에도 남는지 확인.** 핫스팟을 끄고 재부팅하면 연구실 Wi-Fi로 붙는지까지 한 번에 확인된다 |
| 교훈 | pi10을 끌 때는 `sudo poweroff`를 쓴다. 설정을 바꾼 뒤에는 최소한 `sudo sync`를 한다. 배터리를 그냥 뽑지 않는다 |

작업 전부터 0바이트였던 `SysAILAB_5GHz.nmconnection`(11-11)도 같은 원인으로 보인다. 연구실 프로필을 NM 키 파일로 옮기면서 같이 정리할지는 사람이 정한다.
