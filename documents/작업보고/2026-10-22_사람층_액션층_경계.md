## 1절 — 긴급정지를 기록 열에 남긴다

### 어디에 넣었나

`src/physical/robotCommands.ts` 의 `emergencyStop()` 은 **잠금이 끝난 뒤에 기록만 붙인다.**

```
1. abort 발행            ← 그대로
   (예외를 받아도 이어 감) ← 그대로
   못 보낸 정지 알림       ← 그대로
2·3·4. lockStopped(...)   ← 그대로. 발행 결과를 넘기기만 한다
+ recordStop(...)         ← 새로 붙인 것. 보낸 정지만 적는다
  return                  ← 그대로
```

- 일시정지(`pauseMission`)와 같은 모양: `commanded`(주체 `human`, action `abort`, 값 `{reason:1}`, 돌던 태스크)를 적고, 로봇의 첫 답(또는 4초 기한)을 같은 행에 붙인다.
- 정지 기록을 위해 바꾼 것은 두 가지다. 함수 첫 줄에 `runningTaskId()` 를 **읽기만** 하는 줄을 더했고, 발행 결과에서 `commandId` 를 받아 두는 줄을 하나 더했다. 화면 문구는 하나도 안 바꿨다.
- 기록 쪽에서 무엇이 던져도 삼킨다. 듣기가 비동기라 그 실패가 정지 경로로 새어 나오지 않게 한 것이다.
- **못 보낸 정지는 안 적는다.** 나가지 않은 명령이다. 그 사실은 지금처럼 알림과 `stopped.failure` 에 남는다.

### 동작 순서를 안 바꿨다는 것을 무엇으로 확인했나

1. **`verify:emergency-stop` 초록** — 고치기 전과 같은 판정이다. 이 검사 파일은 한 줄도 안 고쳤다.
2. **`verify:stop-recorded`(신설)가 순서를 실행 중에 본다.** 가짜 로봇이 발행되는 순간의 상태를 적어 두고, 잠금이 걸리는 순간에는 `subscribeRobot` 으로 기록 열을 들여다본다.
   - 발행하는 순간 — 아직 안 잠김 · 기록 없음
   - 잠그는 순간 — 기록 아직 없음
   - 반환 뒤 — 기록 있음
3. 같은 검사가 **소스의 뼈대 순서**도 본다: 발행 → catch → 알림 → `const stopped = lockStopped(published, failure)` → `recordStop` → `return stopped`. 잠금이 조건 안에 들어가지 않았는지, 본문이 잠금 앞에서 직접 기록하지 않는지도 함께 본다.
4. 발행 실패 · 발행 예외 · 클라이언트 없음, 이 세 경우 모두 잠긴다(같은 검사 ④).

### 함께 고친 잠복 버그 하나

`firstAnswer()`(일시정지가 답을 듣는 함수)는 기한 타이머를 **먼저** 건 다음에 귀를 열었다. 그래서 귀를 여는 데서 예외가 나면 타이머만 살아남았고, 4초 뒤 아직 없는 `off` 를 부르며 프로세스가 죽었다. 정지가 같은 함수를 쓰게 되면서 `verify:stop-unsupported` 에서 드러났다(그 검사는 4초 넘게 살아 있다). 귀를 먼저 열고 그 뒤에 타이머를 걸게 바꿨다. 실제 클라이언트에서는 동작이 같다.

## 2절 — 사람 층에서 옮긴 것과 남긴 것

### 뿌리

출구 본체 `CommandTracker.issue()`(`src/shared/commandCenter.ts`)는 지나가는 명령을 **모두** `recordHuman` 으로 적었다. 260920 에 액션 층이 생긴 뒤로는 로봇 명령이 두 번 적혔다.

### 고친 것

| 무엇 | 전 | 지금 |
|---|---|---|
| 태스크가 있는 자동 명령(`scan_mission` · `turn` · `move_forward` · 도착 `abort`) | 사람 층 + 액션 층 | **액션 층만** (주체 `backend`) |
| `NO_NODE` 자동 명령(`scan_continue` · `sdk_*`) | 사람 층만 (주체 `human` — 틀림) | **액션 층** (주체 `backend`) · 응답도 그 행에 · 노드에는 안 붙음 |
| `mission_restarted` 등 사람이 누른 것 | 사람 층 | 사람 층 그대로 |
| 제어 패널 · 수동 제어 · SAR · 비행 제어 명령 | 사람 층 | 사람 층 그대로 (사람이 누른 명령) |

방법: `IssueOptions.actionLayer` 를 더했다. 이 값을 준 명령은 출구 본체가 사람 층에 적지 않는다. 주는 곳은 `issueThroughTracker()` 하나뿐이고, 그 명령은 발행한 쪽이 액션 층에 적는다. `robotBridge.ts` 는 `NO_NODE` 명령의 응답도 액션 층에 적되, 태스크 사건(노드 칠하기)은 지금처럼 만들지 않는다.

### 사람 층에 새로 적는 것 (지시서에 없던 것 — 아래 「다르게 한 곳」)

복사본을 걷어 내자 **pi7 경로의 「임무 시작」·「접근 시작」·「재시작」 누름이 기록 어디에도 안 남았다.** 지금까지는 뒤따라 나가는 명령의 복사본이 그 흔적 노릇을 해 왔다. 그래서 버튼(`StopButton.tsx`)이 사람 층에 직접 적게 했다: `mission_started` · `approach_started` · `mission_resumed`. 다른 편(화면이 모는 편)에서 이미 쓰는 이름과 맞췄다.

### `NO_NODE` 를 들이면서 `verify:sdk-bridge` 를 어떻게 좁혔나

정의 자리부터 옮겼다. `NO_NODE` 와 「노드에 붙는가」(`attachedToNode()`)를 `src/data/actionTrace.ts` 에 두고, `missionLink.ts` 는 다시 내보내기만 한다. 화면(`ActionModal` 의 각도 칸)과 측정이 **같은 함수로** 가른다.

`verify:sdk-bridge` ④ 를 이렇게 바꿨다.

| 전 | 지금 |
|---|---|
| 브리지 명령의 응답이 **열에 사건을 하나라도** 만들면 실패 | ① 명령 1줄 + 응답 2줄이 **열에 없으면** 실패 · ② 태스크 층 사건을 만들거나 행이 노드에 붙거나 **어느 태스크를 열어도 보이면** 실패 · ③ 주체가 `backend` 가 아니면 실패 · ④ 각도 칸이 `attachedToNode` 로 거르지 않으면 실패 |

명령은 실제 길(`issueSdkStart` → 추적기 → `receiveUplink`)로 낸다. 전에 있던 대조군 「`NO_NODE !== 'T-A3'`」는 아무것도 재지 않는 상수 비교였다. 그 자리를 실제 열을 변조하는 대조군 다섯으로 바꿨다: T-A3 에 붙인 사본 · 태스크 사건을 만든 사본 · 열에서 뺀 사본(9/20 모양) · 주체를 human 으로 적은 사본 · 각도 칸 필터를 뺀 화면 사본. 다섯 다 잡힌다. 9/20 모양인 「열에서 뺀 사본」이 **이제는 실패로 잡힌다**는 것이, 검사를 무르게 한 것이 아니라 보는 자리를 옮긴 것이라는 근거다.

`verify:action-trace` ④ 도 같은 선으로 고쳤다(전에는 「NO_NODE 는 열에 안 들어간다」를 지켰다). 그 검사의 소스 대조군 정규식은 `recordCommanded` 블록의 들여쓰기가 바뀐 데 맞췄다.

## 3절 — 분모가 움직였나

**안 움직였다.** 고친 측정으로 같은 79판을 다시 세면 이렇다.

```
분모 (노드에 붙은 액션)        중앙 75   (태스크층 28 + 액션 48)
노드에 안 붙은 명령            중앙 32   (명령 8 + 응답·기한 24)
합계 (기록 열 전체)            중앙 107
사람 층                        중앙 12   (그중 자동 명령 복사본 중앙 12)
```

- 표의 다른 숫자도 기준선 파일과 한 줄도 다르지 않다(diff 로 확인). 바뀐 줄은 「열 밖」 두 줄이 위 넉 줄로 바뀐 것뿐이다.
- 세는 자리는 여전히 `tally()` 하나다. 셋째 인자로 「노드에 안 붙은 재료」를 받고, `total`(분모)과 `whole`(합계)을 같은 함수가 낸다.
- 노드에 안 붙은 명령은 이렇게 센다. 새 코드 판은 열에서 직접 센다. 옛 코드 판은 그 명령을 열에 안 적었으므로 작업대에서 복원한다. 9/21 이 「열 밖」으로 세던 것과 같은 재료다.
- 판이 어느 코드로 기록됐는지는 **증거로** 가른다. 액션 층이 열에 있고, 사람 층에 옛 명령 줄이 없고, `NO_NODE` 가 열에 있으면 새 코드다. 측정은 「■ 코드 시대별」에서 두 시대를 나란히 내고, 새 코드 판은 판마다 한 줄씩(분모 · 노드 밖 · 사람 층 · 정지 · 중복) 찍는다.
- 새 코드 분기는 실물이 아니라 **검사용으로 몬 한 판**을 임시 폴더에 넣고 측정 사본으로 확인했다. 그 판은 새 코드로 갈리고, 정지 2 · 중복 0 · 사람 층 자동 0 으로 나왔다.

`measure:representation` — HEAD 사본과 지금의 출력이 **바이트까지 같다**(`assets/2026-10-22_representation_고친뒤.txt`).

## 4절 — 실물 재주행: **아직 0판**

| | 목표 | 지금 |
|---|---|---|
| 새 코드 판 (MSN-260909-01) | 완주 13 | **0** |
| 정지를 누른 판 | 2 이상 | **0** |
| 미완주 판 | 버리지 않고 쌓기 | 0 |

**이유** — 판을 태우려면 앱 화면에서 사람이 승인·시작·접근을 누르고, 로봇(pi7)이 실제로 돌고, 판마다 로봇을 제자리로 옮겨야 한다. 이 세션에는 화면을 누를 도구도, 로봇에 손댈 방법도 없다. 지어낸 판을 `mission-history/` 에 넣는 일은 하지 않았다.

**돌리실 때**

1. 이 커밋으로 앱을 띄운다(`npm run dev`). 예전 탭은 새로고침한다 — 옛 번들로 탄 판은 옛 코드로 기록된다
2. MSN-260909-01 을 완주 13판 이상, 그중 두 판 이상은 도중에 **■ 정지**(그중 하나는 스캔 중, 하나는 스캔과 접근 사이에 누르면 `NO_NODE` 정지까지 확인된다)
3. `npm run measure:trace-scale` — 「■ 코드 시대별 → 새 코드」 칸에 아래 네 가지가 그대로 나온다

| 확인 | 측정에서 보는 자리 | 기대 |
|---|---|---|
| 정지한 판 | `정지 기록 … 그런 판` | 2판 이상 · 판별 줄의 `정지 ≥1` |
| 사람 층 | 판별 줄의 `사람 층 n(자동 0)` | 자동 0 · 남은 것은 `mission_started`·`approach_started`·`mission_restarted` 류 |
| 액션 층 | `NO_NODE 명령이 액션 층에 … 주체 backend` | `scan_continue` 수만큼 backend · human 은 정지·일시정지만 |
| 중복 | `두 층 중복(옛 명령 줄) — 합` | 0 |

판별 줄에 새 판이 안 뜨고 「옛 코드」 판 수가 늘었다면 옛 번들로 탄 것이다. 되감기로 명령 표에 정지가 뜨는지는 화면에서 손으로 본다(측정이 못 보는 자리다).

## 6절 — 신설 셋과 대조군

| 검사 | 보는 것 | 대조군 (전부 검출) |
|---|---|---|
| `verify:stop-recorded` | 정지가 `commanded`(human · abort · 돌던 태스크)로 열에 들어간다 · 답이 붙는다 · 태스크가 없으면 `NO_NODE` · 못 보낸 정지는 안 적는다 · **발행 → 잠금 → 기록 순서를 실행 중에, 그리고 소스에서** | ① **기록을 지운 사본** — 실행 3건 · 소스 1건으로 잡힘 ② **기록을 잠금 앞으로 옮긴 사본(순서를 바꾼 사본)** — 실행 1건(「잠그기 전에 기록이 먼저」) · 소스 2건으로 잡힘 |
| `verify:human-layer-pure` | 문 찾기 편 한 판(명령 7건)을 실제 길로 몰았을 때 사람 층의 자동 명령 0 · 출구 본체가 `actionLayer` 명령만 건너뛰고 사람의 명령은 적는다 · 버튼이 시작·재시작·접근을 적는다 | ① **`scan_mission` 을 사람 층에 도로 넣은 사본**(`actionLayer` 를 뺀 robotCommands) — 같은 판을 몰면 scan_mission·scan_continue·turn·move_forward·abort 가 사람 층에 나타나 잡힘(9/21 실물 판과 같은 모양) ② 출구 본체가 `actionLayer` 를 무시하는 commandCenter 사본 ③ 버튼에서 `approach_started` 를 지운 사본 |
| `verify:no-command-dup` | 액션 층의 명령마다 사람 층에 같은 명령(이름·태스크·실린 값) 0 · 나간 명령은 정확히 한 층에 한 번 | ① 열에 `scan_mission` 옛 줄을 되살린 사본 ② 액션 층에서 명령을 지운 사본(빠진 것도 실패) ③ **복사본을 되살린 robotCommands 사본** — 6건으로 잡힘 |

- 코드 대조군은 모두 `readSource()` 로 LF 정규화한 원본에서 만든다. 사본은 `src/…/.verify-*` 임시 폴더에 두고, 상대 import 를 한 칸 깊게 고쳐 **같은 모듈 인스턴스**를 쓰게 했다. 원본과 사본이 **같은 판정 함수**를 돈다.
- 두 검사가 같은 판을 보도록 판 몰기는 `scripts/lib/pi7Run.mjs` 하나에 뒀다.
- 고친 기존 검사는 `verify:sdk-bridge`(2절) · `verify:action-trace`(2절) · `verify:human-trace` 다. `verify:human-trace` 는 머리말을 「사람이 낸 명령」으로 바꿨고, 기록 줄에 `actionLayer` 말고 다른 조건이 붙으면 실패하게 했다. 대조군도 하나 더했다(엉뚱한 조건을 단 사본).
- 마지막 전종 실행: **111종 초록**(108 + 3), 잔여물 0, `tsc --noEmit` 통과.

**흔들리는 검사 하나 — 이번 작업과 무관.** `verify:fake-device` 가 가끔 「착륙 뒤에도 arm 상태다」로 빨개진다. 이 검사는 고친 모듈을 하나도 안 쓴다. HEAD 사본(고치기 전 코드)에서 5번 돌려도 1번 같은 줄로 빨갰다. 가짜 드론의 시간 의존 문제로 보인다. 손대지 않았다.

## 지시서와 다르게 한 곳

1. **4·5절을 끝내지 못했다** — 위 4절. 코드와 측정은 준비해 뒀고 판만 타면 된다.
2. **사람 층에 `mission_started` · `approach_started` · `mission_resumed` 를 새로 적는다.** 지시서는 「사람이 누른 것은 사람 층에 그대로」라고 했는데, pi7 경로의 이 셋은 **원래 적히는 줄이 없었다**. 복사본이 대신하고 있었으므로, 걷어 내기만 하면 사람이 누른 사실이 사라진다. 그래서 새 판의 사람 층은 `mission_restarted` 하나만이 아니라 이 줄들도 함께 담는다.
3. **일시정지도 태스크가 없으면 `NO_NODE` 로 적는다.** 전에는 돌던 태스크가 없으면 아예 안 적었다(「외톨이 행」 이유). 2절의 규칙(명령은 종류를 가리지 않고 액션 층)과 1절의 「일시정지와 같은 모양」을 함께 지키려면 정지와 일시정지가 같아야 한다. 동작은 안 바뀌고 기록만 늘었다.
4. **`firstAnswer()` 의 타이머 순서를 고쳤다**(1절). 정지 경로가 아니라 답을 듣는 도우미다. 고치지 않으면 정지 기록을 더한 것만으로 다른 검사의 프로세스가 죽는다.
5. **수동 제어 · SAR · 비행 제어 명령은 사람 층에 남겼다.** 사람이 누른 명령이라 주체 `human` 이 맞다. 이 명령들은 문 찾기 편에 안 나온다. 액션 층으로 옮기려면 태스크를 정하고 응답을 잇는 일이 따로 필요해 이번 범위 밖으로 뒀다. 「명령은 액션 층」이라는 문장을 엄밀하게 읽으면 이 셋이 남은 예외다.
