# 작업 보고: 임무 이력 서버가 판 하나를 거절했다 — NUL 문자

**날짜**: 2026-11-19
**선행**: 임무 이력 서버 연동 2차(`99a7a91`) · 서버 기본 주소(`21f2d44`)
**상태**: 원인을 찾고 고쳤다. 가져오기와 서버로 올리는 길 셋 모두 NUL 문자를 뺀다. 실패한 판은 다시 들였다. **서버로 다시 올리는 일은 아직 하지 않았다.**

> 한 줄 요약 — `history:push` 로 123판을 올렸는데 122판만 올라갔다. 남은 한 판의 `progress.json` 에
> NUL 문자(`\u0000`) 728개짜리 줄이 있었고, 서버 DB(PostgreSQL jsonb)가 그 문자를 받지 못해 HTTP 400 을 냈다.
> NUL 은 Pi 쪽 실행기 출력(`.out`)의 끝에 붙어 있었고, 가져오기 스크립트가 그 줄을 걸러내지 않았다.

---

## 1절 — 증상

```
올림 122/123판 · 56.6MB
실패:
  261109/161947_FLT-x500-001: PUT /runs/261109/161947_FLT-x500-001/progress.json → HTTP 400
  {"error": "DB 가 이 값을 받지 않습니다: unsupported Unicode escape sequence"}
```

`unsupported Unicode escape sequence` 는 PostgreSQL 의 `jsonb` 가 문자열 속 `\u0000` 을 받을 때 내는 오류와 문구가 같다. PostgreSQL 텍스트형은 NUL 문자를 담을 수 없다. JSON 문법으로는 올바른 값이라 우리 쪽 검사(`check-history-server`)는 통과하고, DB 에 넣는 단계에서만 막힌다.

## 2절 — 원인

### 어디에 있었나

| 항목 | 값 |
|---|---|
| 판 | `mission-history/261109/161947_FLT-x500-001` |
| 자리 | `progress.json` → `flight.runs[1].lines[120].text` |
| 실행 | `20261109_162004` · `test_sar_rtk.py` · 실제 비행 |
| 내용 | NUL 문자 728개뿐, 글자 없음 |
| 바로 앞 줄 | `#12 진행 -0.1m 속도 0.0m/s 고도 -0.3m 헤딩 295.1°` — 착륙 직후 |

`mission-history` 전체에서 `\u0000` 이 든 판은 이 하나뿐이었다.

### 왜 들어왔나 — 두 단계

**① Pi 원본 로그가 깨져 있었다.** `flight_20261109/script_logs/20261109_162004.out` 은 마지막 정상 줄의 `\n` 뒤가 NUL 바이트 728개로 끝난다. 이 폴더의 `.out` 30개 중 이 파일만 그렇다.

착륙 직후 기체 전원이 끊긴 것으로 추정한다(확인은 못 했다). 그러면 파일 길이는 디스크에 기록됐는데 내용 블록은 아직 쓰이지 않아서, 그 자리가 0으로 채워진 채 남는다. 근거는 둘이다.

- 마지막 기록이 착륙 고도(-0.3m)다.
- `flight_20261109/README.md` 에도 `mav.csv` 에 「NULL 바이트로 깨진 줄이 있을 수 있다」고 적혀 있다. 같은 현상으로 본다.

**② 가져오기 스크립트가 `.out` 에서는 NUL 을 거르지 않았다.** `scripts/import-flight-logs.mjs` 의 머리 주석은 「NULL 바이트로 깨진 줄은 건너뛴다」고 했지만, 실제로 건너뛰는 곳은 `readMav`(mav.csv)뿐이었다. `.out` 을 읽는 `readRun` 은 그 줄을 그대로 `lines` 에 넣었고, JSON 에 `\u0000…` 으로 저장됐다.

## 3절 — 고친 것

### 가져오기 — `viz-debugger/scripts/import-flight-logs.mjs`

`readRun` 에서 `.out` 을 읽을 때 NUL 문자를 지운다. 끝에 붙어 있던 NUL 줄은 빈 줄이 되어, 원래 있던 「끝의 빈 줄 버리기」에서 빠진다. 머리 주석도 실제 동작(mav.csv 는 줄을 버리고, `.out` 은 NUL 만 지운다)에 맞게 고쳤다.

### 올리기 쪽 방어 — `viz-debugger/src/record/jsonText.ts` (신설)

`stripJsonNul(text)` 는 JSON 글에서 `\u0000` 이스케이프만 지운다. 글을 다시 짜지 않으므로 들여쓰기와 순서는 그대로다. 역슬래시 글자 뒤에 `u0000` 이 오는 경우(`\\u0000`)는 NUL 이 아니므로 남긴다. 앞의 역슬래시 개수가 짝수일 때만 이스케이프로 본다.

서버로 보내는 길 세 곳이 모두 이 함수를 지난다.

| 길 | 자리 |
|---|---|
| 기록기가 서버에 바로 쓸 때 | `historyServer.ts` 의 `writeToHistoryServer` — JSON 본문(문자열 · Blob · 바이트)을 여기서 거른다 |
| 대피 판 자동 올리기(`historyUpload.ts`) | 같은 함수(`uploadRecordFile` → `writeToHistoryServer`)를 지난다 |
| `npm run history:push` | `push-history-to-server.mjs` 가 같은 함수로 `progress.json` · `mission.json` 을 거른다 |

웹 기록기도 Pi 의 `.out` 을 실시간으로 받는다. 그래서 가져오기만 고치면 같은 일이 다시 생길 수 있어, 올리기 쪽에도 걸었다. 이 PC 에 쓰는 판(로컬 기록)은 그대로 두었다. NUL 이 남아도 파일로는 문제가 없고, 서버로 갈 때 걸러진다.

## 4절 — 확인

- `tsc --noEmit` 이 통과했다.
- `stripJsonNul` 경계 사례 4개가 모두 맞았다.

  | 입력(문자열 값) | 결과 |
  |---|---|
  | `x` + NUL + `y` | `xy` |
  | 역슬래시 글자 + `u0000` | 그대로 |
  | 역슬래시 글자 + NUL + `z` | 역슬래시 글자 + `z` |
  | NUL 두 개 | 빈 문자열 |

- 실패했던 실제 `progress.json`(25,732자)을 걸렀더니 21,364자가 됐다. 남은 NUL 은 없고, JSON 으로 정상 읽힌다.
- `flight_20261109` 를 다시 들여 기존 판과 비교했다.
  - 판 나누기는 그대로 14판이다(`--dry` 로 먼저 봤다).
  - `161947_FLT-x500-001/progress.json` 은 NUL 줄 하나만 빠졌다(121줄 → 120줄). 나머지는 같다.
  - 14판의 `mission.json` 은 `importedAtIso`(들인 시각)만 바뀌었다.
  - `mission-history` 전체에 `\u0000` 이 남은 곳이 없다.

## 5절 — 남은 일

- **서버에 다시 올리기**: `npm run history:push -- http://100.102.8.102:8850` 을 돌리면 서버에 아직 없는 이 판만 올라간다. 나머지 들인 판들은 바뀐 것이 `importedAtIso` 뿐이라 `--force` 로 다시 덮을 필요는 없다.
- **서버 쪽(선택)**: 받을 때 `\u0000` 을 지우거나, 오류 문구를 「NUL 문자 포함」처럼 더 분명하게 바꾸면 다른 클라이언트도 같은 일을 덜 겪는다. 서버 담당과 상의할 일이다.
- **Pi 쪽(선택)**: 착륙 뒤 전원을 끄기 전에 실행기 출력을 `fsync` 하거나 종료를 기다리면 원본 로그 자체가 덜 깨진다.
