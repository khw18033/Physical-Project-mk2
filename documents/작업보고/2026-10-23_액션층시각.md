## 1절 — 보고 셋

### 1. 자름은 누구를 위한 것인가 · 없으면 무엇이 깨지는가

**출처.** 자름은 두 군데다.

| 자리 | 들어온 때 | 무엇 |
|---|---|---|
| `recordHuman` — `Math.min(state.headSec, durationSec)` | `d7e64b3` 260904 | 사람 층. **대본만 있던 때** |
| `actionAtSec` — `Math.min(at, durationSec)` | `84ce2e2` 260921 | 액션 층. 주석이 「`appendHuman` 주석과 같은 이유」라고 적는다 — 위 줄을 옮긴 것이다 |

대본 재생에서는 머리가 `durationSec` 을 넘지 않는다(타이머가 거기서 선다). 그래서 260904 의 자름은 **언제나 아무 일도 안 하는 축 안 지킴이**였다. 슬라이더의 `max` 가 `durationSec` 이라, 사건이 그 밖에 놓이지 않게 막는 줄이다.

**대본 재생은 이 함수를 거치지 않는다.** 대본의 액션 아이템은 `feedLocalTrace()` 가 `actionItemEvents()` 로 펴서 **`appendTrace()` 로 제 시각 그대로** 넣는다. `actionAtSec` 을 부르는 것은 `recordCommanded`·`recordAnswered`·`recordExpired`·`recordAdjusted` 넷뿐이다. 그 넷을 부르는 곳은 전부 라이브 경로다 — `robotCommands.ts`·`robotBridge.ts`·`humanCommands.ts`·`ActionModal.tsx`(값 바꿈).

**없으면 무엇이 깨지나.**

| 자리 | 자름 없이 | 판정 |
|---|---|---|
| 대본 재생 | 안 거친다 | **안 깨진다** |
| 라이브 중 슬라이더 | 사건이 축 밖(`> durationSec`)에 놓인다. 축이 늘기 전에는 슬라이더로 그 시각에 못 간다 | **태스크 층이 이미 그렇다** — 로봇이 모는 판은 머리가 `durationSec` 을 넘는다(보관 판 머리 5944초 등). 액션 층이 같은 처지가 될 뿐이다 |
| 저장 뒤 다시보기 | `loadRecordedMission` 이 축을 `max(durationSec, 사건 최대 시각)` 으로 늘린다 | **안 깨진다** |
| 음수 | `Math.max(0, …)` 이 막는다 | 이건 **남긴다** |

**자름이 실제로 한 일은 지킴이가 아니라 손상이다.** 0으로 깎인 82건(생성 임무)과, 48초로 깎인 232건(시연 대본). 둘 다 같은 줄이다.

### 2. `durationSec` 이 0인 임무에서 재생 머리는 어떻게 움직이나 · 라이브만 끄면 어긋나나 · `LIVE_STRETCH_SEC` 와는

**머리.** 생성 임무(모델 제안 · 정량 명령 `MSN-Q-*`)는 `activateGenerated()` 로 열린다 — `headSec: 0 · playing: false`, **타이머를 안 세운다**(흘릴 사건이 없다). 머리는 로봇 쪽이 민다.

```
receiveRobotProgress · advanceRobotHead · pushAction  →  headSec = max(headSec, atSec)
```

그래서 라이브 중 **머리는 `durationSec` 0 을 넘어 간다**(보관 `MSN-Q-*` 머리 1.7~22.8초). 축은 안 늘어난다. 화면은 `shown = min(durationSec, second) = 0` · 슬라이더 `max = 0` · 「0s / 0s」다. **생성 임무는 라이브 중에 아예 되감을 수 없다.** 저장했다가 다시 열면 축이 사건 최대 시각까지 늘어 슬라이더가 산다. 그런데 액션 층은 전부 0초라 머리를 어디 두든 다 보인다 — 이것이 증상이다.

**`LIVE_STRETCH_SEC` 와 어떻게 맞물리나.** 그 장치는 `runLocalTimer()` 안에 있고, **실제 장치가 태스크를 맡은 판(`liveClaims > 0`)** 에서만 돈다. 화면이 모는 편이 그렇다(`MSN-260929-02` 장치 두 대). 머리가 `durationSec − 1` 에 닿으면 축을 `ceil(머리) + 30` 으로 늘린다. 다 끝나면 `finishLiveRun()` 이 축을 `ceil(머리)` 로 줄인다. **생성 임무에는 타이머가 없어서 이 장치가 안 돈다.**

| 판 | 머리를 미는 것 | 축 | 자름을 라이브에서 끄면 |
|---|---|---|---|
| 대본 재생 | 타이머 | 고정 | 해당 없음(안 거친다) |
| 로봇이 모는 대본 판 `MSN-260909-01` | 로봇 사건(`elapsedSec`) | 48 고정 · 머리는 넘어 간다 | 48초 넘는 명령이 **태스크 층과 같은 시각**에 놓인다 — 지금 어긋난 것이 맞춰진다 |
| 화면이 모는 판 `MSN-260929-02` | 타이머(1배속) + `LIVE_STRETCH` | 머리보다 늘 앞서 늘어난다 | 자름이 애초에 안 걸린다(축이 앞서 있다). 이 판의 0은 자름이 아니라 **시계**(3번)다 |
| 생성 임무 `MSN-Q-*` | 로봇 사건 | 0 고정 | 시각이 퍼진다. 라이브 중 슬라이더가 0 인 것은 그대로다(태스크 층과 같은 처지). 다시 열면 축이 산다 |

**재생이 어긋나는 자리는 없다.** 재생 쪽은 자름을 쓰지 않기 때문이다. 대본과 라이브를 무엇으로 가를지는 따로 정할 필요가 없다 — `actionAtSec` 을 부르는 넷이 전부 라이브다. 그래서 **위쪽 자름을 그 함수에서 걷는 것으로 충분하다**(아래 결정 ①). 굳이 판별식을 둔다면 `state.activatedBy`(`'approval'`·`'record'`) 나 `robotDrives()` 가 후보다. 하지만 그러면 같은 함수가 판마다 다른 시각을 주게 된다.

### 3. `elapsedSec()` 가 0 대신 무엇을 줄 수 있나 · 후보 둘 · 탐지·뷰포인트에 미치는 영향

**`MSN-260929-02` 가 왜 0인가.** 13판 전부 `started: false · startedAtMs: null` 이다. 이 편은 로봇 관문을 안 연다(`opensRobotGate` 가 문 찾기 편에 묶여 있다). 그래서 `markStarted()` 가 첫 줄(「승인 없이는 시작도 없다」)에서 돌아간다. 시계는 끝내 서지 않고, 명령은 `elapsedSec()` 의 0을 받는다. 같은 판의 **사람 층(37.8)과 태스크 층(37.8)은 맞다** — 둘 다 그 판의 축(`state.headSec`, 1배속 타이머)을 쓴다.

**같은 시계를 읽는 쪽**(바꾸면 함께 움직인다).

| 읽는 곳 | 무엇에 쓰나 |
|---|---|
| `detect/useDetect.tsx` | 탐지 결과를 여덟 칸에 얹고 노드를 민다 |
| `physical/robotBridge.ts` `receiveUplink(…, elapsedSec())` | 응답 줄 · 뷰포인트 프레임 · 태스크 진행의 시각 |
| `physical/robotClient.ts` · `scanGate.ts` | 촬영 칸을 여는 시각 |
| `physical/prepStage.ts` · `scanElapsedSec()` | 준비 단계 · 각도별 결과의 박자 |
| `physical/robotCommands.ts` | 명령 · 기한 · 응답 기록(이번 대상) |

이 쪽들은 「시작 전에는 0」을 **의도대로** 쓴다(260912 주석 — 승인하고 설명하는 동안 시계가 흐르면 처음부터 270도가 켜져 있었다).

| 후보 | 무엇 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **가** 임무 시작 기준 | 기록의 `startedAtIso`(판이 열린 시각)부터 잰다 | 세션이 안 서도 값이 있다 | **기록 하나에 벽시계가 둘 생긴다.** 문 찾기 편은 승인~시작 사이 설명 시간만큼 액션 층이 태스크 층보다 앞선다. `elapsedSec()` 자체를 바꾸면 위 표의 탐지·뷰포인트가 같이 움직인다 — 지시서 §5 위반 |
| **나** 「모른다」를 올린다 | 명령 기록용 함수를 따로 둔다. 세션이 섰으면 `elapsedSec()`, 안 섰으면 `null`. `null` 은 받는 자리 하나(`actionAtSec`)가 **그 판의 축(`state.headSec`)** 으로 푼다 | `elapsedSec()` 는 **한 글자도 안 바뀐다** — 탐지·뷰포인트 영향 0. `MSN-260929-02` 에서 사람 층·태스크 층과 **같은 축**이 된다. 세션이 선 판(문 찾기 · 생성 임무)은 지금과 같은 값이다 | 함수가 하나 는다. 축 자체가 0에 서 있는 판(아무것도 머리를 안 미는 판)이면 여전히 0이다 — 그때도 그것은 거짓 0이 아니라 축의 자리다 |

**고른 것 — 나.** 이유 셋.
1. 시계를 바꾸지 않고 **기록 쪽에서 고른다.** 탐지·뷰포인트가 읽는 `elapsedSec()` 는 그대로 둔다(§5).
2. 고른 값이 **이미 다른 두 층이 쓰는 축**이다. 새 시계를 들이지 않는다 — 가는 셋째 시계를 들인다.
3. 「모른다」가 경계에서 `null` 로 드러난다. 그것을 무엇으로 풀지는 `scenario.ts` 한 곳이 정하고, 검사가 그 자리를 본다.

원인 다(사람 명령 경로가 `atSec` 을 안 준다)도 같은 함수로 막는다. 사람 명령도 그 함수 값을 넘긴다.

> **원인 다의 전제 하나는 코드와 다르다.** 「되감아 둔 상태에서 명령을 내면 과거 시각에 적힌다」 —
> 슬라이더의 되감기는 화면 값(`main.tsx` 의 `override`)만 바꾸고 **`state.headSec` 은 안 옮긴다.**
> 그래서 과거 시각에 적히지는 않는다. 실제 위험은 다른 데 있다. 세션이 선 판에서 `headSec` 은 로봇
> 사건이 올 때만 앞으로 가서 **실제 시각보다 뒤처진다.** 사건 사이에 낸 사람 명령이 조금 이른 시각에
> 적힌다. 고칠 이유는 그대로다.

## 왜 검사 108종이 이걸 못 잡았나

**센 것** — 검사 파일 113개(`verify:*` 114항목).

| 묶음 | 수 |
|---|---:|
| 시연 대본을 전제로 쓴 검사 — `MSN-260909-01` 을 쓰거나 그 편을 모는 시험 도구(`lib/pi7Run.mjs`·`lib/humanCommandRig.mjs`)를 쓰거나 그 편의 태스크 id(`T-A3`·`T-B2`·`T-B3`)를 박은 것 | **38 / 113** |
| 액션 층을 보는 검사 | 12 |
| — 그중 시연 대본 전제 | 8 |
| — 나머지 넷 | 손으로 적은 기록 열을 접거나(`fold-actions`·`no-answer` 류 — `atSec` 을 손으로 넣는다) 옛 대본 재생(`replay`) |
| 생성 임무를 실제로 돌리는 검사 | **1**(`verify:step-script`) — 액션 층을 안 본다 |
| **액션 층 × 생성 임무** | **0** |

**구조적 이유 셋.** 셋 다 「없는 검사」가 아니라 「잘못 고른 재료」다.

1. **결함이 검사 안에서 매번 재현되고 있었다.** 시험 도구(`pi7Run`)는 `markApproved()` 만 부르고 `markStarted()` 는 안 부른다. 그래서 그 판의 명령은 전부 `elapsedSec()` 의 0을 받는다. 직접 몰아 찍어 보면 `commanded ×7` 이 **0초**이고, 같은 명령의 응답과 태스크 사건은 도구가 넣은 **3초**다. 어느 검사도 「같은 명령의 층별 시각이 맞는가」를 묻지 않아 통과했다
2. **시험 판이 짧아서 위쪽 자름이 안 걸린다.** 도구가 모는 판은 200 ms 안팎에 끝나고 시각이 3초를 안 넘는다. `durationSec` 48 에 닿는 판이 없다. 시각이 축을 넘는 경우를 만든 검사가 없다
3. **접기 검사는 읽기만 시험한다.** `fold-actions`·`no-answer`·`manual-replay` 는 `atSec` 을 손으로 넣은 열을 접는다. 그 열을 **쓰는 쪽**(`actionAtSec`·`elapsedSec`)은 거치지 않는다. 그래서 「과거 시점에는 그때까지 온 것만」은 맞게 검사되는데, 들어오는 시각이 틀리면 그 검사는 아무것도 못 본다

정리하면 이렇다. **검사들은 「있는가 · 어느 층인가 · 몇 건인가 · 순서」를 봤고 「언제인가」를 보지 않았다.** 그리고 「언제」를 볼 수 있는 유일한 재료(실물 판 · 긴 판 · 생성 임무)를 검사가 쓰지 않았다. 이 결함을 찾은 것은 우리 검사가 아니라 Foxglove 였다 — 응답 네 줄이 한 점에 겹쳐 「Zoom for more」가 떴다.

## 하나 더 — 화면의 명령 표는 슬라이더를 안 따라간다 (범위 밖 · 보고만)

## 대본과 라이브를 무엇으로 가르나 — **가르지 않는다**

①의 근거 그대로다. 대본의 액션 아이템은 `feedLocalTrace()` 가 `appendTrace()` 로 제 시각에 넣고, `actionAtSec` 을 부르는 넷은 전부 라이브 경로다. 판별식을 두면 같은 함수가 판마다 다른 시각을 준다.

## `elapsedSec` 을 어떻게 고쳤나 — **안 고쳤다. 옆에 둘을 더했다**

```ts
// robotSession.ts — 명령을 기록할 시각. 모르면 null (0이 아니다)
export function commandClockSec(): number | null {
  if (!robotDrives() || session.startedAtMs === null) return null;
  return elapsedSec();
}
// scenario.ts — 지금 라이브 판의 몇 초인가. 사람 층 · 액션 층이 같은 자리에서 얻는다
function liveNowSec(): number {
  return Math.max(0, commandClockSec() ?? state.headSec);
}
```

**왜 이 쪽인가.** 로봇이 모는 판(문 찾기 · 정량 명령)은 축 자체가 로봇 시계다 — `receiveRobotProgress` 가 그 값으로 머리를 민다. 그 밖(관문을 안 여는 장치 두 대 편 · 로봇 없이 도는 대본)은 축을 화면의 진행기가 민다. 그때 로봇 시계를 쓰면 기록 하나에 시계가 둘이 된다. `null` 을 축으로 푸는 것은 **이미 다른 두 층이 쓰는 그 값**을 쓰는 것이다. 탐지·뷰포인트가 읽는 `elapsedSec()` 는 그대로다.

`robotDrives()` 를 조건에 넣은 이유 — 문 찾기 편을 로봇 없이 대본으로 돌리면 시작은 눌리지만 축은 20배속 진행기다. 거기서 벽시계를 쓰면 사람 층 누름이 대본 시각에서 벗어난다.

| `MSN-260909-01` 13판이 「지금과 같아야 한다」 | 「48초 안은 그대로 · 48초 너머는 태스크 층 시각」으로 봤다 | ② 결정 ④ — 지금 값이 깎인 값이다 |
| 신설 둘 | 셋 | ② 「같은 명령의 층별 시각」을 더했다 |
| 대조군 「`atSec` 을 안 넘기는 사본」 | 「기록이 명령 시계를 안 받는 사본」 | 고친 뒤에는 **아무도 `atSec` 을 안 넘긴다** — 시각은 `liveNowSec()` 한 곳이 푼다. 같은 결함의 모양은 「그 한 곳이 재생 머리로만 떨어진다」가 된다 |

## 옛 판 — 못 고친다

**35판**(0으로 적힌 24 + 48초에 깎인 시연 대본 11)의 액션 층 시각을 믿을 수 없다. 사람 층도 같은 11판에서 48초에 깎인 줄이 있다. 다시 만들 수 없는 기록이라 손대지 않았다.
