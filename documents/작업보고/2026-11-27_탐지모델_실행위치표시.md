## 1절 — 무엇이 틀렸나

자동 자원 배분을 켠 상태에서 「이 모델이 진짜 노트북에서 도는가」를 확인했다(2026-11-27 11:04 요청 `req-32228602c6`).

| 근거 | 값 |
|---|---|
| 배치표 `planned` | GPU 단위 `targeted` · pi12, robot1 → `book-4vg1edpvi5` |
| 실행 기록 `applied` | 「`book-4vg1edpvi5` GPU (RTX 4050 Laptop) — 이 기기 · WSL (pid 946126)」 · `detail.where` 같은 문장 |
| 결과 한 건의 `node_id` | `BOOK-4VG1EDPVI5` (`producer.tier = server`) |

노트북이 맞다. 그런데 상세는 「실행 방식: k3s · 자원 근거 live」였다. 이 값은 기록의 `mode` 칸이고, data_stream 은 이것을 「클러스터 조회가 됐으면 k3s, 아니면 local」
(`controller.py:454`)로 쓴다 — 배치를 **어떻게 계산했나**다. 같은 요청의 `running` 기록은 `mode: local` 이기도 하다. 「실행 방식」이라는 이름표 때문에
k3s 파드에서 도는 것으로 읽혔다.

## 2절 — 무엇을 고쳤나

| 파일 | 바뀐 것 |
|---|---|
| `scripts/vision-redis-placement.mjs` | `summarizePlacement` — 배치표와 **같은 요청**의 `applied` 기록에서 `detail.where` 를 노드별로 모아 `plan.where` 에. `where` 가 없는 기록(CPU 작업)은 건너뛴다 |
| `src/detect/status/placement.ts` | `PlanSummary.where?` (옛 저장본에는 없다) |
| `src/detect/status/views/DetectStatusParts.tsx` | 「실행 장치」 칸에 「실행 위치」 줄 — 배치표에서 온 장치이고 그 노드의 문장이 있을 때만 |
| `src/i18n/ko.ts` · `en.ts` | `dms.pl.runsAt` 「실행 위치」 · `dms.pl.mode` 「실행 방식」 → 「배치 방식」 · 값 「{mode} 로 계산 · 자원 근거 {basis}」 |

- `where` 는 data_stream `gpu_where(node)` 가 노드만으로 정하므로 노드 → 문장 하나면 된다.
- 실행 기록이 오기 전(배치만 된 순간)이나, 저장본에서 연 배치표는 「실행 위치」 줄이 없다. 지어내지 않는다.

## 3절 — 검사

`npm run verify:detect-placement` 통과. 더한 것:

- 실행 위치 — 같은 요청 GPU `applied` 의 `where` (기록 `mode` 는 k3s 그대로)
- 대조군 — 다른 요청의 `applied` · `where` 없는 `applied` 는 안 섞인다
- `applied` 전이면 실행 위치 없음

그 밖에 `verify:detect-status` · `tsc -b` · `verify:dict-shape` · `verify:i18n-data` · `verify:i18n-no-frozen` 통과.
실제 Redis(`100.125.104.23:6380`)에 고친 `readPlacement` 를 돌려 `where = book-4vg1edpvi5 GPU (NVIDIA GeForce RTX 4050 Laptop GPU) — 이 기기 · WSL` 을 확인했다.
