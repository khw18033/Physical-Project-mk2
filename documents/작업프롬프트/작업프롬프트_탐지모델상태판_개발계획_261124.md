## 1. 지금 구조

- 오른쪽 기둥(`src/main.tsx` 의 `right-column`) = `ServerCard` · 하드웨어 판 · `CapabilityPanel`(「기능」). 하드웨어와 기능이 세로 1:1.
- 객체 탐지는 이미 `src/vision/` 에 있다.
  - `visionClient.ts` — 연결 관리 「객체 탐지 추론 스트림」의 IP 한 칸 + 포트 줄(`visionBases()`), `/health` 해석(`parseStreamHealth` → 모델별 `results · n · run · lagMs · inferMs · detections · ageS`), `modelLive`(30초) · `modelStale`(5초).
  - `store.ts` — 포트마다 `/health` 를 1초마다 읽는 저장소. `holdAllVisionSources()` 로 전부 붙든다(전체 장치 확인이 쓴다). 모델별 처리 속도도 여기서 잰다.
  - `binding.ts` — 장비 ↔ 포트 묶음(브로커 주소로 자동 맞춤 · 사람이 고름).
  - `views/VisionViews.tsx` — `VisionCell`(크게 보기 · 녹화 `RecordFrame` · 근거 카드 `VisionCards` · 영역 지정 `VisionRoi` · 재식별 `VisionReid` · 버튼 묶음 `VisionToolStack`), `VisionCam`, `VisionDeviceSection`(하드웨어 상세의 탐지 칸).
  - 중계 `scripts/vision-stream-relay.mjs` — `/health`(CORS 없음)와 한 장 그림을 옮긴다.
- 스캔 탐지 판(`src/detect/scan/scanStore.ts`)은 이 가시화가 보낸 `prepare` 의 대상 · `query_used` · `profile_version` 을 들고 있다.
- 기억해 둘 것: 261123 에 jny_AI 런타임을 이 자리에 붙이는 일은 **동결**했다. 이번 것은 그것과 다른 판(data_stream 탐지 상태)이고, 자리를 바꾸는 것은 사용자 지시다. `src/capability/` 코드는 지우지 않는다(§6 결정 1).

### 3-4. 지정 탐지 — 무엇을 찾고 있나

출처마다 확실함이 다르므로 **출처를 같이 적는다.**

| 갈래 | 언제 | 보이는 것 | 출처 표시 |
|---|---|---|---|
| A. 이 가시화의 스캔 판 | `scanStore` 에 판이 있고 그 포트 | 대상 · `query_used` · 각도 n/8 · `profile_version` · 판 전 대상 | 「임무 MSN-… 의 스캔 판」 |
| B. 남이 연 스캔 판 | `/health` 의 `busy_scan_id` 가 있고 A 가 아님 | 판 번호 · `/scan/status` 의 상태 · 수집한 각도 | 「다른 화면이 연 스캔 판」 |
| C. 런처 설정(평소) | Redis 를 읽을 수 있을 때 | `targets` · 프로필 이름 · 판 · `provisional` | 「런처 설정 (profile vN)」 |
| D. 보이는 것만 | C 가 안 될 때 | 마지막 장 검출 라벨 · `counts` | 「대상 목록 못 읽음 — 마지막 장에 보인 것」 |

- C 는 **개발 서버 중계에 읽기 창구 하나를 더한다**: `GET /vision-stream/latest?redis=<redis://host:6380>&source=<소스>&model=targeted` → `XREVRANGE … COUNT 1` 의 `result` 에서 `targets · cues 이름 · provisional · distance · profile` 만 돌려준다(그림 · 검출은 빼서 작게). 쓰기 명령은 열지 않는다. Redis 주소는 연결 관리 「객체 탐지 추론 스트림」에 칸 하나(기본 비움 = C 끔).
- 지정 탐지 줄은 `targeted` 모델이 살아 있는 포트에만 붙는다. `yoloe` · `river` 는 고정 클래스라 대상 줄 대신 모델 이름만.

### 3-5. 변경 기록

data_stream 은 바뀐 기록을 따로 남기지 않는다. 그래서 **가시화가 조회마다 앞 값과 비교해 사건을 만든다**(순수 함수 `diffDetectSnapshot(prev, next) → DetectEvent[]`).

| 사건 | 판정 |
|---|---|
| 모델 + | 앞에 없던 (소스, 모델)이 `modelLive` |
| 모델 − | 살아 있던 것이 `MODEL_GONE_S`(30초) 넘게 결과 없음 |
| 모델 다시 시작 | 같은 모델의 `run` 이 바뀜 · `results` 누계가 줄어듦 |
| 대상 바뀜 | 갈래 A/C 의 대상 목록 · `profile.version` 이 바뀜 |
| 스캔 판 시작 · 끝 | `busy_scan_id` 가 생김 · 사라짐 |
| 소스 끊김 · 다시 연결 | `/health` 실패 시작 · 회복 (끊긴 길이 같이) |

- **임무 판이 돌 때만 적는다** (§6 결정 4). 판이 시작되면 첫 줄에 「기록 시작 — 지금 모델 · 대상」을 적고, 판이 끝나면 멈춘다. 보관은 브라우저 메모리 + `localStorage` 최근 200건(실패해도 화면은 돈다)과 그 판의 임무 이력 `progress`(이력에서 다시 볼 수 있게).
- 임무가 없을 때는 비교만 하고 적지 않는다 — 「변경 기록」 자리에 「임무가 돌 때만 적습니다」.
- 선택(D7): Redis 가 열리면 `XRANGE` 로 남아 있는 범위 안의 `profile.version` 변화를 거슬러 채운다. 스트림 길이가 data_stream 설정에 달려 있어 얼마나 거슬러 가는지 보장이 없다 — 「Redis 에 남은 범위」로 표시.

## 6. 정한 것 (사용자 2026-11-24)

1. **「기능」 판** — 화면에서는 뺀다(`main.tsx` 의 `<CapabilityPanel />` 자리만 바꿈). `src/capability/` 코드는 그대로 둔다(동결 결정과 맞음).
2. **조회 부담** — 판은 2초, 상세가 열린 포트만 1초. (판이 늘 떠 있으면 모든 포트 `/health` 를 읽게 되므로.)
3. **Redis 갈래 C 를 넣는다** — 사용자 확인: Redis 6380 이 테일넷 쪽으로 열려 있다. D6 을 단계에 넣고, D0 에서는 `XREVRANGE` 1건의 크기 · 칸만 실측한다. Redis 주소 칸의 기본값은 추론 스트림 IP 칸과 같은 호스트의 `:6380` 으로 둔다.
4. **변경 기록** — **임무 판이 돌 때만** 남긴다(브라우저 보관 · 임무 이력 `progress` 모두). 임무가 없을 때 판의 「변경 기록」은 「임무가 돌 때만 적습니다」를 보이고 지금 상태만 보여 준다. §3-5 · D5 를 이에 맞춘다.
5. **추론 스트림 서버 IP 선택지 변경 (바로 반영함)** — 연결 관리 「객체 탐지 추론 스트림」 IP 칸의 「스트림 서버 (테일넷)」 값을 `100.102.8.102` → `100.125.104.23`(data_stream 노트북 WSL)으로 바꿨다. `src/vision/presets.ts` 의 `VISION_STREAM_HOST`, 설명 문구 `preset.vision.why`(한 · 영), `scripts/verify-vision-stream.mjs` 기본 주소 검사. 결과로 서버 칸의 「같은 호스트의 추론 서버 이름」(`serverStatus.ts` 2번 갈래)은 게이트웨이(`100.102.8.102`)와 호스트가 달라져 기본값에서는 더 서지 않는다 — 맞는 동작이다.
