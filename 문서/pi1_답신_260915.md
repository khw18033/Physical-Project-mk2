`pi1_조사결과.md`(§0 조사 · 결정 3건)에 대한 답이다. 아래 「붙여 넣을 답신」을 pi1 쪽 AI 에 그대로 붙여 넣는다.

## 붙여 넣을 답신

조사 보고 잘 받았다. 코드 줄 근거까지 확인했고, 저장소 `HW` 브랜치의 `pi/robot/go1_sdk_pc.cpp` 를 가시화 쪽에서도 읽어 대조했다.
결정 3건의 답과, 내가 보낸 계약에서 **틀렸던 곳**, 그리고 **사건을 얻는 곳을 하나 바꿔 달라는 요청**이 있다. 이것을 반영해 구현하고
처음 프롬프트의 §4 시험 · §5 보고 형식대로 보고해 달라.

### 1. 결정 3건

**2.1 브로커 설치 — 승인한다.**
- `sudo apt install mosquitto` 후 `/etc/mosquitto/conf.d/hw-viz.conf` 에 제안한 내용(`listener 1883 0.0.0.0` · `listener 9001 0.0.0.0` + `protocol websockets` · `allow_anonymous true` · `max_keepalive 300`)을 새 파일로 둔다.
- 설치 전에 `/etc/mosquitto/mosquitto.conf` 에 `include_dir /etc/mosquitto/conf.d` 가 있는지, conf.d 파일이 기본 설정과 겹치는 항목(persistence 등)을 안 적었는지 확인한다.
- 부팅 자동 시작해도 된다(로봇을 움직이지 않는다). **로봇 실기 시험 중이 아닐 때** 설치하고 시각을 보고서에 적는다.
- robot-node 가 엣지 브로커(`192.168.50.244:1883`)로 발행하는 설정은 **건드리지 않는다.** 새 브로커는 중계 전용이다.

**2.2 배터리·yaw 원천 — 제안대로.** 고정 client id `viz-nav-feed-pi1` 로 Go1 내부 MQTT(`192.168.123.161:1883`) `bms/state`·`robot/state` 를 **구독만** 하고,
`go1_link` 의 상수·`_bms_soc` 규칙은 읽기 전용으로 가져다 쓴다. `Go1Link` 인스턴스를 만들지 않는 판단이 맞다.
- `yaw_deg` 는 계약대로 15101 브리지 값(`yaw_source: "bridge_state"`), 없을 때만 IMU(`"go1_odometry"`).
- **추가 요청:** `nav_state` 에 선택 키 **`yaw_odometry_deg`** 를 더해 IMU 값(`robot/state`, 원래 부호 그대로, 도, -180~180)을 **늘** 나란히 실어 달라. 못 읽으면 `null`.
  브리지 yaw 의 offset 이 경로마다 다시 맞춰진다는 보고를 받고 가시화가 두 값을 함께 보이기로 했다. 가시화는 이미 이 키를 읽는다. `schema` 는 `viz-nav/1` 그대로 둔다(키를 더한 것뿐이다).

**2.3 사건 두 가지 — 둘 다 제안대로.**
- `estop` 은 **15100 텔레옵 4번째 필드의 0→1 로만** 센다. `source: "udp15100_estop"`. 15101 의 estop 필드(= 서 있음)는 쓰지 않는다.
- `cancel_ack` 는 로직만 두고 지어내지 않는다. 가시화는 `path_cancel` 로 재탐색을 시작하고 다음 `path_received` 로 끝내므로 없어도 된다.

### 2. 내 계약이 틀렸던 곳

프롬프트 §2 에 「15101 의 mode 98/99 는 브리지가 여러 주기 연달아 싣는다 — 0 이 아닌 값이 처음 보인 주기만」이라고 썼다.
그건 `unity_bridge.py` 의 동작이고 **pi1 의 `go1_sdk_pc` 와 다르다.** 보고대로 평소 mode 는 1/2 이고, 99 는 `path_done_notify` 로 **한 번만** 나간다.
**mode 가 정확히 99 인 줄**만 `path_done` 으로 친다(98 도 정확히 98). 「0 이 아닌 값」 규칙은 버린다.

### 3. 요청 — 경로 사건은 브리지 로그에서 먼저 얻어 달라

`go1_sdk_pc.cpp` 를 읽어 보니 사건을 **패킷 캡처로 세면 브리지가 실제로 한 일과 어긋나는 자리가 둘** 있다.

1. **브리지는 한 루프에 여러 경로가 오면 마지막 것만 쓴다** (`latest_path_json`, `:1474-1495`). 파싱이 실패하면 활성화하지도 않는다(`:1498`).
   캡처는 받은 패킷마다 `path_received` 를 내므로, 브리지가 버린 경로까지 「이동 시작」으로 칠해진다.
2. **mode 99 는 500 Hz 상태 흐름 속의 UDP 한 개다.** 캡처가 그 한 개를 놓치면(`AF_PACKET` 수신 버퍼 넘침·파이썬 멈칫) 그 경로는 가시화에서 **영영 안 끝난다.**

그런데 브리지는 세 사건마다 **`fflush` 한 로그 줄**을 남긴다 — 이것이 브리지가 실제로 한 일이다.

| 사건 | 로그 줄 (`go1-sdk.service` stdout → journald) | 코드 |
|---|---|---|
| `path_received` | `[PATH] activated id=<N> waypoints=<M> anchor_yaw=<deg>deg` — `path_id=N`, `point_count=M` | `:708` |
| `path_cancel` | `[PATH] PATH_CANCEL received from Unity dynamic obstacle replan` | `:605` |
| `path_done` | `[PATH] done notify sent (mode=99)` — `path_id` 는 직전 activated 의 id | `:1748` |

그래서 이렇게 해 달라.

- **경로 사건 셋은 `journalctl -u go1-sdk -f -o short-unix` (읽기 전용)에서 먼저 얻는다.** `source: "journal"`.
  `ts_ms` 는 로그의 시각을 쓴다. 중계가 다시 뜨면 **지난 줄을 다시 사건으로 내지 않는다**(`-n 0` 또는 시작 시각 이후만).
- `physical` 사용자가 journal 을 못 읽으면(`systemd-journal`·`adm` 그룹이 아니면) **그룹을 더하지 말고 먼저 보고**한다 — 시스템 설정 변경이다.
  그동안은 원래 계획한 패킷 캡처로 세고 `source` 를 `udp15110` · `udp15101_mode99` 로 둔다. 캡처 소켓은 `SO_RCVBUF` 를 넉넉히 준다.
- **한 판에 두 원천을 섞지 않는다** — 같은 경로가 두 번 `path_received` 로 나가면 가시화가 이동 회차를 하나 더 센다. 어느 원천을 썼는지 보고한다.
- yaw(15101)·`moving`(5009, 두 키가 다 있는 JSON 만)·`estop`(15100)은 로그에 없으니 **캡처 그대로** 간다.

### 4. 참고 — 가시화 쪽에서 바꾼 것

- pi1 브로커 기본 주소를 `ws://pi1.tailcb6bfb.ts.net:9001/mqtt` 로 넣었다.
- `yaw_odometry_deg` 를 받아 「로봇 위치 확인」 노드에 브리지 yaw 와 나란히 보인다.
- `cancel_ack` 가 안 와도 재탐색 노드는 `path_cancel` → 다음 `path_received` 로 진행한다.
- 5009 로 함께 나가는 `go1_detect_forward` 탐지 JSON 은 가시화가 AI 서버(`210.110.250.33:7864`)에서 따로 받으므로 중계에 싣지 않아도 된다.

구현이 끝나면 §5 형식으로 보고하되, **2번(원천)에 journal 을 읽을 수 있었는지**와 **yaw 두 값(브리지 · IMU)을 같은 순간 나란히** 꼭 넣어 달라.
