# 탐지 산출물 분석과 화면 적용 계획 (2026-09-11)

`door_example/` 를 읽고, **지금 화면의 빈자리에 무엇이 들어가는지**와 **실제 연결에서 어떻게
돌아야 하는지**를 적는다. 코드는 아직 안 건드렸다.

앞선 두 문서를 대체하지 않는다. [`탐지_명령규약_260910.md`](탐지_명령규약_260910.md) 가
주고받을 모양을 정했고, [`작업프롬프트_탐지연동_260910.md`](작업프롬프트_탐지연동_260910.md)
가 붙이는 순서를 정했다. 이 문서는 그 둘을 **실제 산출물과 대조한 결과**다.

## 2. 여덟 프레임이 곧 여덟 칸이다

이것이 이 자료의 핵심이고, 우리 화면과 맞물리는 자리다.

```json
"rotation_sequence": {
  "rotation_direction": "clockwise (오른쪽)",
  "nominal_step_deg": 45.0,
  "frames": [ {"frame":"frame_000001.jpg","rotation_deg":0.0}, … 315.0 ]
}
```

로봇이 **오른쪽으로 45도씩 여덟 번** 돌며 찍은 여덟 장이다. 우리 화면의 `T-A4-0` ~ `T-A4-7`
여덟 칸과 개수도 간격도 방향도 같다.

```
index = rotation_deg / step_deg          (0°→0 … 315°→7)
```

**이 한 줄이 이번 연동에서 가장 흔하게 틀릴 자리다.** 로봇의 `step` 은 1부터이고
탐지의 `rotation_deg` 는 0부터다. 한 칸 밀려도 화면은 그럴싸하게 돌아간다 — 여덟이 차례로
켜지고 초록도 하나 뜬다. 눈으로는 못 잡는다. 하드웨어 연동 때 `verify:status-index` 를
만든 이유가 그것이고, 탐지에도 같은 검사가 하나 더 필요하다.

### 문이 두 방향에서 잡혔다 — 실제로

```
frame_000113  rotation 270°  found ✓  absolute_bearing 16.3°  clip 0.2696
frame_000132  rotation 315°  found ✓  absolute_bearing 61.3°  clip 0.2680
```

지시서 §11 이 「라이브에서는 둘 이상이 뜬다」고 예상한 그대로다. **가정이 아니라
측정값이다.** 정해 둔 규칙(최고 점수 하나만 초록, 나머지는 더블클릭에 남긴다)이 첫 판부터
쓰인다. 두 점수 차이가 `0.2696` 대 `0.2680` 으로 **0.0016** 밖에 안 난다는 것도 같이 봐야
한다 — 흔들리면 초록이 옮겨 다닌다.

## 3. 빈자리와 자료의 1:1 대응

지금 화면에서 비어 있거나 임시로 채운 자리를, 이 자료의 어느 값이 메우는지다.

| 태스크 노드 | 지금 | 들어올 값 |
|---|---|---|
| `T-A1` 2D 맵에서 문 위치 확인 | 대기만 | `evidence.target_resolution` — 도면상 고정 위치 `(922.8, 327.8)cm`, 출처 `gt_fixed` |
| `T-A2` 로봇 현재 위치와 각도 파악 | 대기만 | `robot_position_cm (236.2,126.9)` · `current_heading_map_deg 106.3` |
| `T-A3` 로봇이 1바퀴 돈다 | **로봇이 채운다** (이미 동작) | 그대로 |
| `T-A4-n` N도 방향 탐색 | 회전만 표시 · 판정은 임시 무작위 | `frames[n].found` + 점수 + 상자 |
| `T-A5` 문이 있는 방향으로 판단 | **여덟 중 하나를 무작위로 뽑는다** | 최고 점수 프레임 하나 |
| `T-A6` 근거 가시화 | 대기만 | `features_sent` + `mandatory_gates` + `target_crop.jpg` |
| `T-B1` 2D 맵 기반 경로 산출 | 대기만 | `path_calculation` 5단계 (식과 대입값이 그대로 있다) |
| `T-B2` 전방으로 직진 | 대본의 `forward_distance_m: 4.2` | `forward_distance_cm: 635.4` |
| `T-B3` 문과 가까워지면 정지 | 대본의 `stop_distance_max_m: 0.9` | `standoff_cm: 80.0` |
| `T-C1` 임무 종료 확인 | 대기만 | `goal_cm (846.1, 305.3)` 도달 여부 |

| 자리표시 (`pendingSources`) | 들어올 값 |
|---|---|
| `detections` 탐지 결과 연결 예정 | 프레임별 `box_xyxy` · 점수 · 관문 |
| `video-stream` 영상 스트림 연결 예정 | `original.jpg` / `target_overlay.jpg` |
| `zone-map` 2D 맵 | `path_overlay.jpg` (도면 + 경로) |

**대본이 지어 두었던 숫자가 전부 탐지 산출물로 바뀐다.** `door_viewpoint_index: 2`,
`forward_distance_m: 4.2`, `stop_distance_max_m: 0.9` 셋은 값을 줄 데가 없어서 대본에 박아
둔 것이었다. 이제 줄 데가 생겼다.

### `path_overlay.jpg` 는 그대로 쓸 수 있다

도면 위에 로봇 위치, 90도 회전, 635.4cm 직진선, 목표점 ×가 이미 그려져 있다.
`VIEW-MAP` 을 「자리만 만들고 더미를 그리지 마라」로 둔 이유가 형식이 없어서였는데,
**형식이 왔다.** 다만 이 그림은 **한 판의 결과물**이지 실시간 맵이 아니다 — 스캔이 끝나고
경로가 정해진 뒤에 한 장 온다.

## 4. 좌표축이 셋이다 — 가장 위험한 자리

같은 「각도」라는 말이 세 가지를 가리킨다. 섞으면 화면이 엉뚱한 방향을 가리키고,
**틀렸다는 것이 눈에 안 보인다.**

| 축 | 값의 예 | 0도가 어디인가 |
|---|---|---|
| `rotation_deg` (탐지) | 0·45·…·315 | **스캔 시작 자세.** 오른쪽이 + |
| `yaw_deg` (로봇 ACK) | −9.98 · 35.09 · … | 로봇 내부 기준. **판마다 출발점이 다르다** |
| `absolute_bearing_deg` / 도면각 | 16.3 · 61.3 · 106.3 | **도면 북쪽.** cm 좌표계와 같은 축 |

이어 주는 식이 자료에 적혀 있다.

```
absolute_bearing_deg = (rotation_deg + current_heading_map_deg) mod 360
```

그런데 `current_heading_map_deg` 자체가 **관측에서 역산된 값**이다.

```
step1  map_bearing_to_pedestal = atan2(118.3-126.9, 207.0-236.2) mod 360 = 196.3
step2  pedestal_bearing_rotation_frame = mean(rotation_deg) = 90.0
step3  current_heading_map = (196.3 - 90.0) mod 360 = 106.3
```

즉 **받침대를 90도 프레임에서 본 것**으로 로봇의 도면상 방위를 정한다. 로봇의 `yaw_deg` 는
여기에 안 쓰인다. 이것이 뜻하는 바 셋.

- **받침대를 못 찾으면 절대 방위가 없다.** 그러면 `T-B1` 경로 산출이 통째로 안 선다.
  화면은 그 사실을 말해야 한다 — 「문은 찾았는데 어디로 갈지는 모른다」가 실제 상태다.
- 로봇 ACK 의 `yaw_deg` 와 탐지의 방위는 **서로 검산에 쓸 수 있지만 대체할 수 없다.**
  둘이 어긋나면 그것 자체가 정보다. 어느 한쪽으로 덮어쓰면 안 된다.
- 우리가 이미 `door_turn` 을 방위로 견주고 있는데(같은 판의 yaw 끼리), 그 축과 탐지의 축은
  **다르다.** 칸을 고르는 열쇠는 계속 `index` 하나여야 한다.

## 5. 규약 초안과 실제 산출물의 차이

[`탐지_명령규약_260910.md`](탐지_명령규약_260910.md) §2 에서 우리가 그려 보낸 모양과 실제
파일이 다르다. **고칠 쪽이 어디인지 정해야 한다.**

| 규약 초안 | 실제 산출물 | 어떻게 |
|---|---|---|
| `index` 0~7 | 없음 · `rotation_deg` | 우리가 `rotation_deg / step_deg` 로 유도 |
| `door: true/false` | `found: true/false` | 이름만 다르다 |
| `confidence` 0~1 | `final_score` **0.2696** | **아래 따로** |
| `bbox [x,y,w,h]` | `box_xyxy [x1,y1,x2,y2]` | 변환 한 줄. 어느 쪽으로 맞출지 정할 것 |
| `reason` 한국어 한 문장 | 없음 | **우리가 만들어야 한다** — 관문과 점수에서 조립 |
| `ts` 탐지 시각 | 없음 | 있으면 좋다 |
| — | `absolute_bearing_deg` | **규약에 없다.** 이게 있어야 `T-B1` 이 산다 |
| — | `distance_cm` · `in_valid_calibration_range` | 아래 따로 |
| — | `mandatory_gates` 넷 | 근거 가시화의 알맹이 |

### `confidence` 를 퍼센트로 그리면 안 된다

찾은 프레임의 `final_score` 가 **0.2696** 이다. 그대로 「신뢰도 27%」로 그리면 보는 사람은
「거의 못 찾았다」로 읽는다. **찾았다는 판정은 점수가 아니라 관문 넷이 정한다.**

```
color_gate            light blue 0.2698 이 여덟 색 중 1등        통과
shape_gate            rectangular 0.2399 이 네 모양 중 1등       통과
reference_image_gate  유사도 0.7903 ≥ 임계 0.75                  통과
saturation_gate       중앙값 채도 108 ≥ 최소 85                  통과
```

`final_score` 는 특징 여덟 중 **최고값**(= 색 점수)이지 확률이 아니다. 화면에는
**관문 넷을 그대로** 보이고, 점수는 「특징 최고값」이라고 이름을 붙여 옆에 둔다.
지금 여덟 칸에 「문 있음 · 100%」라고 적고 있는 자리가 이것으로 바뀐다.

### `distance_cm` 은 문에서 못 쓴다

```json
"distance_cm": 0.0, "in_valid_calibration_range": false
"distance_note": "…도면상 고정 위치가 따로 있는 랜드마크는 실제 경로 계산에는
                  이 값 대신 고정 위치까지의 거리를 쓴다"
```

자료가 직접 못박았다. 문까지의 거리는 **깊이 추정이 아니라 도면 좌표로** 낸다
(`distance_to_target_cm: 715.4`). 화면이 `distance_cm` 을 「0.0m」로 그리면 거짓이다 —
**안 그리는 것이 맞다.**

## 6. 실제 연결에서 어떻게 돌아야 하는가

### 시간 순서

```
사람: "저기 문 쪽으로 가"  →  승인
  │
  ├─ 웹 → 탐지   스캔 시작 (command_id 를 같이 준다)
  ├─ 웹 → 로봇   scan_mission { steps: 8, step_deg: 45, forward_m: 0 }
  │
  │  ── 여기부터 두 줄기가 같이 흐른다 ──
  │
  │  로봇 ──▶ scan_turn step1..8      : 칸이 「탐색 중」→「탐색 완료」
  │  탐지 ──▶ frames[0..7] found      : 칸이 「문 없음」/「문 있음」
  │
  ├─ 로봇: door_turn                   (고정 기하값 — 탐지 결과가 아니다)
  ├─ 탐지: 최고 점수 프레임 확정        → T-A5 초록 하나
  ├─ 탐지: evidence + path_calculation → T-A6 근거 · T-B1 경로 · path_overlay
  │
  └─ 사람: 「접근 시작」                ← **여기서 한 박자 쉰다**
       웹 → 로봇  turn(회전량) → move_forward(forward_distance)
```

### 두 줄기가 만나는 자리

로봇과 탐지는 **다른 경로로 들어온다.** 로봇은 MQTT 로 밀어 주고, 탐지는 우리가 HTTP 로
받아 간다. 둘이 같은 칸을 채우므로 **누가 무엇을 채우는지 갈라 둬야 한다.**

| | 로봇이 채우는 것 | 탐지가 채우는 것 |
|---|---|---|
| 여덟 칸 | 「회전이 지나갔다」 (`scan_turn`) | 「거기 문이 있나」 (`found`) |
| 방향 판단 | **안 한다** (`door_turn` 은 고정 기하값) | 최고 점수 하나 |
| 거리·회전량 | **안 준다** | `turn_instruction` · `forward_distance_cm` |

지금 화면은 탐지가 없어서 **여덟 중 하나를 무작위로 뽑아** 초록을 켜고 있다. 그 자리가
그대로 `found` 로 바뀐다 — 화면 코드는 안 바뀐다. 뽑는 함수 하나를 갈아 끼우는 일이다.

### 프레임을 무엇으로 잇는가

탐지는 `frame_000113.jpg` 라고 부르고 로봇은 `step 7` 이라고 부른다. 지금은 둘 다 45도
간격이라 `index` 로 맞출 수 있지만, **한 프레임이라도 빠지거나 겹치면 그 순간 어긋난다.**

규약 §2 가 `index` 를 달라고 한 이유가 이것이고, 자리표시 `detections` 가 「그 박스가 어느
프레임의 것인지(프레임 참조값)」라고 적어 둔 것도 같은 자리다(`VZ-I-07` · `AI-C-03`).
**탐지 결과에 `index` 를 실어 달라고 다시 부탁하는 것이 가장 싸다.**

### 그림을 어떻게 가져오는가

자료의 이미지 경로가 **탐지 기계의 로컬 절대경로**다.

```
/home/jin24/Physical-Project-mk2-jny-backup/demo/test/door/frame_000113/original.jpg
```

브라우저는 이 경로를 못 연다. 규약 §2 의 `GET /detect/frame?index=N` 으로 받아야 하고,
그때 CORS 헤더가 필요하다(규약 §3). **경로 문자열을 화면에 그대로 넣으면 안 된다** —
지금 자리표시가 비어 있는 것이 그것보다 낫다.

### 못 찾았을 때

여덟이 다 `found: false` 면 초록이 없고 `MS-B` 로 갈 선도 없다. 지시서 §11 이 정한 대로
**「문을 찾지 못함」에서 멈춘다.** 임의로 한 방향을 고르지 않는다.

받침대를 못 찾은 경우는 **다른 실패**다. 문은 찾았는데 절대 방위가 없어 경로를 못 낸다.
화면이 둘을 갈라 말해야 한다.

## 7. 구현 계획

지금 화면이 이미 갖춘 것이 많아서, 새로 만드는 것보다 **갈아 끼우는 것**이 대부분이다.

### 1단계 — 판정의 출처만 바꾼다 (가장 작고 가장 크다)

여덟 칸을 채우는 길(`detection` 프레임 → `fill.ts`)은 이미 있고 로봇 연동에서 쓰고 있다.
지금 무작위로 뽑는 자리를 탐지 결과로 바꾼다.

```
pickDoorIndex(8)        →  탐지 results 에서 최고 점수 index
door: chosen            →  found
reason: '임시 판정…'     →  관문 넷에서 조립한 문장
confidence: 1           →  final_score (이름을 「특징 최고값」으로)
bbox: null              →  box_xyxy → [x,y,w,h] 변환
```

여기까지만 해도 화면의 거짓말 둘(무작위 초록, 100%)이 사라진다.

### 2단계 — 근거와 그림

- `T-A6` 근거 가시화 : 관문 넷 + 특징 여덟 점수 + `target_crop.jpg`
- `VIEW-CAM` 전역 노드 : 스캔 도는 동안 `original` / `target_overlay` 를 폴링
- 칸 더블클릭 : 그 각도의 `rpn_overlay` 와 점수 전부

근거 4층을 그리는 방식은 계획 승인 카드가 이미 쓰고 있다 — 같은 모양을 쓴다.

### 3단계 — 경로와 맵

- `T-A2` : `robot_position_cm` · `current_heading_map_deg` (역산 근거까지)
- `T-B1` : `path_calculation` 5단계를 식과 대입값 그대로
- `VIEW-MAP` : `path_overlay.jpg`
- `T-B2` · `T-B3` : 대본 숫자를 탐지 값으로 교체

`path_calculation` 은 식과 대입값이 이미 문자열로 들어 있어서 **우리가 계산을 다시 할 필요가
없다.** 그대로 네 줄로 그리면 「왜 90도를 돌았나」에 답이 된다.

### 4단계 — 어긋남을 보여 준다

로봇 ACK 의 `yaw_deg` 와 탐지의 `rotation_deg` 는 같은 회전을 다른 축으로 적은 것이다.
**둘을 나란히 두고 어긋나면 어긋났다고 적는다.** 한쪽으로 덮어쓰지 않는다.

### 검사

각 단계마다 대조군을 가진 `verify:*` 를 하나씩 만든다. 특히 셋.

- **한 칸 밀림** — `rotation_deg / step_deg` 가 `index` 와 같은가. 한 칸 민 사본이 잡히는가
- **점수를 확률로 그리지 않는가** — 0.2696 을 「27%」로 적은 사본이 잡히는가
- **`distance_cm: 0.0` 을 거리로 그리지 않는가**

## 8. 탐지 담당에게 물을 것

1. 결과에 **`index` 를 실어 줄 수 있나** (0~7). 없으면 `rotation_deg` 로 유도하는데, 프레임이
   빠지는 순간 어긋난다.
2. `final_score` 를 화면에 **뭐라고 적어야 하나.** 확률이 아닌 것은 알겠는데, 사람이 읽을
   이름이 필요하다. 「특징 최고값」으로 적어도 되나?
3. 결과를 **스캔 도중에 한 프레임씩** 받을 수 있나, 아니면 여덟이 다 끝나야 나오나.
   화면이 「탐색 중」을 언제 「문 없음」으로 바꿀지가 여기서 갈린다.
4. **받침대를 못 찾으면** 어떻게 오나. `localization_ok: false` 인가, 아니면 `evidence.json`
   자체가 안 오나. 문은 찾았는데 경로를 못 내는 상태를 화면이 그려야 한다.
5. `box_xyxy` 를 **`[x,y,w,h]` 로 맞춰 줄 수 있나.** 아니면 우리가 변환한다 — 어느 쪽이든
   한 곳에서만 바꾸면 되게 정해 두자.
6. 한국어 `reason` 한 문장을 **탐지 쪽이 만들 수 있나.** 못 만들면 우리가 관문에서
   조립하는데, 그러면 문장의 책임이 화면으로 넘어온다.
7. `path_overlay.jpg` 는 **언제 나오나.** 스캔 끝난 뒤 한 장인가, 갱신되나.

## 9. 이번에 하지 않을 것

- **실시간 2D 맵.** 받은 것은 한 판의 결과 그림이다. 실시간 맵은 다른 이야기다.
- **추적·궤적** (`tracking` 자리표시). 이 자료에 없다.
- **받침대를 화면의 목표로 올리는 것.** 받침대는 자세를 역산하는 기준점이지 시연의 목표가
   아니다. 근거에만 나온다.
- **깊이값으로 거리 그리기.** 자료가 쓰지 말라고 적어 뒀다.
- **탐지 결과로 로봇을 직접 움직이는 것.** 「접근 시작」은 계속 사람이 누른다.
