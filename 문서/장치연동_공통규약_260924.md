# 장치 연동 공통 규약 — 관제 웹의 명령을 알아듣는 장치를 만드는 법 (초안)

> 대상: 관제 웹에 새 장치를 붙이는 쪽의 개발자·AI (RoboMaster EP, 고정 카메라, 센서, 액추에이터)
> 작성 2026-09-24 · 가시화(김현우) · 상태 **초안 — 검토 전**
> 장치별 세부는 부록에 있다. 부록 A: [RoboMaster EP](장치연동_부록A_로보마스터EP_260924.md)

이 문서 하나와 해당 부록만 읽으면 장치 쪽 노드를 만들 수 있게 쓴다.
Go1(`go1-001`, pi7)이 이미 이 규약으로 움직이고 있다. **새 장치는 Go1과 똑같이 보이면 된다.**
관제 웹은 장치 종류마다 따로 짠 코드를 두지 않는다. 장치가 스스로 밝힌 것(§4, §6)을 보고 화면과 명령을 고른다.

---

## 0. 무엇이 확정이고 무엇이 제안인가

| 표시 | 뜻 |
|---|---|
| **[실측]** | Go1·드론에서 실제로 돌고 있거나 캡처한 것. 그대로 따른다 |
| **[제안]** | 이 문서에서 새로 정한 것. 웹도 아직 구현하지 않았다. 이견이 있으면 구현 전에 말해 달라 |

§1~§5(연결·토픽·봉투·응답 순서·정지)는 전부 **[실측]** 이다.
§6의 장치 종류별 상태 필드 중 `camera`·`sensor`·`actuator` 부분은 **[제안]** 이다.

## 1. 전체 모양

```
관제 웹(브라우저) ──MQTT over WebSocket──▶ 브로커(mosquitto) ◀──MQTT──  장치 노드 ──▶ 장치
                  명령: protobuf                                     (장치 SDK·드라이버를 부른다)
                  상태: JSON
```

- **장치 노드**는 이 문서가 구현을 요구하는 프로그램이다. MQTT로 명령을 받아 장치의 SDK나 드라이버 호출로 바꾸고, 결과와 상태를 MQTT로 올린다.
  - Go1은 pi7의 `robot-node`가 이 역할이다. 드론은 pi3의 노드가 맡는다.
- **장치를 대신해서 답하는 쪽**이 노드다. 장치에 직접 MQTT를 올릴 수 없으면(마이크로컨트롤러, 서버가 연결을 쥔 카메라) 그 앞의 파이나 서버가 노드가 된다. **규약은 누가 노드든 같다.**
- 영상은 이 경로로 흐르지 않는다(§8).

## 2. 브로커 [실측]

| 항목 | 값 |
|---|---|
| 브로커 | mosquitto. 장치 옆 파이에 하나씩 둔다(Go1 = pi7, 드론 = pi3). 웹은 브로커 여러 개에 동시에 붙는다 |
| TCP 리스너 | **1883** (노드·도구용) |
| WebSocket 리스너 | **9001**, 경로 `/`와 `/mqtt` 모두, 서브프로토콜 `mqtt` (브라우저용) |
| 프로토콜 | MQTT 5.0 권장, 3.1.1도 붙는다 |
| 인증 | 없음(`allow_anonymous true`). 폐쇄망 전제. 공개망에 두지 않는다 |

**clientId는 브로커에서 유일해야 한다.** 노드는 자기 장치 id(§3)를 clientId로 쓴다. 웹은 `web-<임의값>`을 쓴다. 같은 clientId가 둘이면 나중에 붙은 쪽이 먼저 붙은 쪽을 밀어낸다.

노드는 접속할 때 **LWT(유언)** 를 걸어 둔다. 노드가 급사하면 브로커가 §6-2의 `offline` 상태를 대신 발행한다.

## 3. 식별자 [실측]

| 항목 | 규칙 | 예 |
|---|---|---|
| `entity_id` (장치 id) | `<기종>-<3자리 번호>`. clientId, 토픽, `Command.target`, `Capability.device_id`에 모두 같은 값 | `go1-001`, `x500-001` |
| `entity_type` (장치 종류) | §5의 네 값 중 하나 | `robot` |
| `device_type` (기종) | 가장 구체적인 이름. 자유 문자열 | `unitree_go1`, `x500_drone` |
| `zone_id` | 구역 | `zoneA` |
| `node_id` | 노드가 도는 기계 | `pi7` |

**장치 id와 영상 소스 키는 다르다.** 장치는 `go1-001`, 그 장치의 카메라 영상은 `go1-001_front`다. 명령 대상에는 장치 id만 쓴다(§8).

## 4. 명령 평면 — protobuf [실측]

### 4-1. 토픽

| 방향 | 토픽 | QoS | 싣는 것 |
|---|---|---|---|
| 웹 → 노드 | `terminal/<entity_id>/downlink` | 1 | `command`, `cancel_request` |
| 노드 → 웹 | `terminal/<entity_id>/uplink` | 1 | `acceptance`, `status`, `result`, `cancel_response`, `capability` |

토픽에는 **방향만** 담긴다. 메시지 종류는 봉투의 `oneof body`가 정한다. 페이로드는 **protobuf 이진**이다. JSON이 아니다.

### 4-2. 스키마

원본은 저장소 `HW` 브랜치의 `schema/physical_command.proto` 한 파일이다. 사본이 [viz-debugger/schema/physical_command.proto](../viz-debugger/schema/physical_command.proto)에 있다. **고치지 말고 그대로 컴파일해 쓴다.** 고칠 일이 생기면 HW 브랜치에 요청한다.

```proto
message PhysicalCommandEnvelope {
  oneof body {
    Command                 command          = 1;  // 웹→장치
    CancelCommandRequest    cancel_request   = 2;  // 웹→장치
    CommandAcceptance       acceptance       = 3;  // 장치→웹
    CommandStatus           status           = 4;  // 장치→웹
    CommandResult           result           = 5;  // 장치→웹
    CancelCommandResponse   cancel_response  = 6;  // 장치→웹
    Capability              capability       = 7;  // 장치→웹
  }
}
enum TerminalStatus { TERMINAL_STATUS_UNSPECIFIED = 0; SUCCEEDED = 1; ABORTED = 2; CANCELED = 3; }
message Command {
  string command_id = 1;
  string target     = 2;
  string action     = 3;
  map<string, double> parameters = 4;
  int64  deadline_unix_ms = 5;
}
message CancelCommandRequest  { string command_id = 1; }
message Rejection             { string code = 1; string message = 2; }
message Failure               { string code = 1; string message = 2; }
message CommandAcceptance     { string command_id = 1; bool accepted = 2; Rejection rejection = 3; }
message CommandStatus         { string command_id = 1; string state = 2; string detail = 3; }
message CommandResult         { string command_id = 1; TerminalStatus status = 2; map<string, double> result = 3; Failure failure = 4; }
message CancelCommandResponse { string command_id = 1; bool accepted = 2; }
message Capability            { string device_id = 1; repeated string actions = 2; }
```

### 4-3. 명령 하나를 받았을 때 노드가 할 일

1. **대상 확인.** `target`이 자기 장치 id가 아니면 무시한다.
2. **중복 확인.** `command_id`는 멱등키다. 이미 받은 id면 **다시 실행하지 않고** 전에 보낸 응답을 되돌려 준다. 전 응답이 없으면 `ALREADY_EXISTS`로 거부한다.
3. **선언 확인.** `action`이 Capability에 없으면 `UNIMPLEMENTED`로 거부한다.
4. **파라미터 확인.** 빠졌거나 범위 밖이면 `INVALID_ARGUMENT`로 거부한다. **범위 밖 값을 조용히 잘라 쓰지 않는다.**
5. **상태 확인.** 지금 실행할 수 없으면(배터리 부족, 다른 명령 실행 중, 장치 링크 끊김) `FAILED_PRECONDITION` 또는 구체 코드(§4-5)로 거부한다.
6. **시한 확인.** `deadline_unix_ms`가 0이 아니고 지금이 그 시각을 넘었으면 시작하지 않고 `FAILED_PRECONDITION`으로 거부한다. 웹은 지금 이 값을 넣지 않는다. 서버 경유 명령(§9)이 넣을 예정이다.
7. 모두 통과하면 수락하고 실행한다.

**1~6은 실행 로직에 닿기 전에 끝나야 한다.** 거부된 명령으로 장치가 조금이라도 움직이면 안 된다. 웹은 "거부 = 아무것도 안 일어났다 = 재시도해도 안전하다"로 읽는다.

### 4-4. 응답 순서

```
수락 1건 → 진행 0~n건 → 종료 1건
acceptance{accepted:true} → status{state:"EXECUTING", detail} … → result{status: SUCCEEDED | ABORTED | CANCELED}
```

- **거부되면 `acceptance{accepted:false, rejection}` 한 건으로 끝난다. `result`를 보내지 않는다.**
- 수락된 명령은 **반드시** `result` 한 건으로 끝난다. 웹은 `result`가 올 때까지 다음 단계를 보내지 않는다(단계당 60초).
- `status.state`는 `ACCEPTED` / `EXECUTING` / `CANCELING` 중 하나다.
- `status.detail`은 빈 문자열, 짧은 단계 이름(`"executing"`), 또는 JSON 문자열이다. 웹은 셋 다 받는다.
- `result.result`는 **숫자만** 실린다(`map<string,double>`). 모르는 값은 0을 넣지 말고 **키를 빼라.** 웹은 "키 없음 = 모름", "0 = 쟀더니 0"으로 읽는다.
- `result.status`가 `ABORTED`면 `failure{code, message}`에 사유를 넣는다.

### 4-5. 거부·실패 코드

gRPC 상태 코드 관례를 따른다. 웹은 코드를 화면에 그대로 보여 준다.

| 코드 | 언제 |
|---|---|
| `INVALID_ARGUMENT` | 파라미터 누락·범위 밖 |
| `FAILED_PRECONDITION` | 지금 상태로는 실행 불가(일반) |
| `UNIMPLEMENTED` | 선언하지 않은 action |
| `ALREADY_EXISTS` | 이미 쓴 `command_id` |
| `PERMISSION_DENIED` · `RESOURCE_EXHAUSTED` | 권한 없음 · 자원 고갈 |
| 구체 코드(소문자) | 사람이 원인을 바로 알 수 있으면 더 좋다. Go1 예: `battery_too_low`, `mission_in_progress`, `robot_state_dead`. **새로 만들면 부록 어휘표에 적는다** |

`message`는 사람이 읽는 한 줄이다. 영어든 한국어든 상관없다.

### 4-6. 파라미터는 숫자만 들어간다

`parameters`와 `result`는 `map<string, double>`이다. **문자열을 실을 자리가 없다.**
- 모드·종류는 **action 이름으로** 가르거나, **숫자 코드**로 정하고 부록에 표를 둔다. 예: `abort{reason: 1}`.
- 참·거짓은 `1`/`0`이다. 예: `sdk_auto{on: 1}`.
- 백엔드가 문자열·열거형 파라미터를 위한 `.proto` 개정을 계획하고 있다(Phase 6). 그전까지는 위 방법으로 한다.

### 4-7. 취소(`cancel_request`) — 권장

`cancel_request{command_id}`를 받으면 `cancel_response{command_id, accepted}`로 답한다. 수락했으면 그 명령을 멈추고 원래 `command_id`로 `result{status: CANCELED}`를 보낸다. `cancel_response`는 "취소 절차에 들어갔다"는 뜻이지 "멈췄다"는 뜻이 아니다.
웹은 지금 취소를 쓰지 않고 정지(§7)를 쓴다. 구현 여부는 부록에 적는다.

### 4-8. Capability — 할 수 있는 것을 밝힌다

노드는 **브로커에 붙을 때마다** uplink로 `capability{device_id, actions[]}`를 한 번 발행한다. 할 수 있는 일이 바뀌면(예: 장치 링크가 끊겼다 붙음) 다시 발행한다.
- retained가 아니다. 늦게 붙은 웹은 못 받는다. 웹은 그 경우 `status.registration`(§6-2)으로 장치를 알아보고 `ping`으로 확인한다.
- **선언한 것만 받고 나머지는 전부 `UNIMPLEMENTED`로 거부한다.**
- 웹은 이 목록으로 버튼을 켜고 끈다. 예: `abort`가 없으면 정지 버튼 대신 "조종기로 멈추세요"를 띄운다.
- Capability에는 장치 종류를 실을 자리가 없다. 종류는 JSON 상태(§6)에서 읽는다.

## 5. 장치 종류 — 네 가지

토픽 둘째 칸과 `registration.entity_type`에 이 값을 쓴다. **웹은 이 값을 보고 화면을 고른다.** 로봇 화면이 센서에 뜨는 일은 이 값이 틀릴 때 생긴다.

| `entity_type` | 무엇 | 필수 action | 선택 action 예 | 필수 상태(§6-3) | 웹 화면 |
|---|---|---|---|---|---|
| `robot` | 스스로 움직이는 기체. Go1, RoboMaster EP | `ping`, **`abort`** | `diag`, `turn`, `move_forward` | 배터리, 위치, 모드 | 이동 명령, 정지 버튼 |
| `camera` | 고정 카메라 | `ping` | `diag`, `snapshot`, 설정 변경 | 영상 소스별 도달 여부 | 영상, 설정. 정지 버튼 없음 |
| `sensor` | 값을 재서 올리는 장치. 수위계 등 | `ping` | `diag`, `set_interval`, `calibrate` | **측정값** | 값·추이, 임계치. 정지 버튼 없음 |
| `actuator` | 제자리에서 움직이는 장치. 수문 등 | `ping`, **`abort`** | `set_position` | 위치(%), 동작 중 여부 | 열기·닫기, 정지 버튼 |

규칙:
- **물리적으로 움직이는 부분이 있으면 `abort`는 필수다.** 팬·틸트 카메라도 여기에 든다.
- `ping`은 모든 장치가 받는다. 결과에 `uptime_s`(노드 가동 시간, 초)를 싣는다. 장치와 노드 사이 링크가 따로 있으면 그 생존을 `<이름>_link`(1/0)로 싣는다. 예: 드론은 `fc_link`.
- 한 장치가 두 종류에 걸치면(예: 센서가 달린 로봇) **주된 종류 하나**를 고른다. 측정값은 §6-3의 `readings`로 같이 올릴 수 있다.
- 드론(`drone`)은 별도 계약([CONTRACT_x500.md](CONTRACT_x500.md))을 따른다. 이 문서의 대상이 아니다.

## 6. 상태 평면 — JSON

### 6-1. 토픽 [실측]

`{zone_id}/{entity_type}/{entity_id}/{channel}` — 예: `zoneA/robot/ep-001/state`, `zoneA/sensor/wl-001/state`

| 채널 | 주기 | QoS | retained | 담는 것 |
|---|---|---|---|---|
| `status` | 10초 + 등록·종료 때 | 1 | **예** | 자기소개(`registration`)와 요약 |
| `state` | 5초 이하. 움직이는 동안은 더 자주(Go1: 20Hz) | 1 | 아니오 | 현재 값 |
| `heartbeat` | 5초 | 0 | 아니오 | 살아 있다는 것만 |

`status`가 retained여야 한다. 웹은 구독하자마자 이것으로 첫 화면을 그리고 장치가 누구인지 안다.
웹은 마지막 수신 뒤 15초가 지나면 장치를 낡은 것으로 본다. **5초 주기를 지켜 달라.**

### 6-2. 모든 메시지에 붙는 머리 [실측]

```json
{
  "schema_version": "1.1",
  "source_id": "ep-001",
  "node_id": "pi8",
  "zone_id": "zoneA",
  "timestamp": "2026-09-24T14:03:11.512+09:00",
  "session_id": "3e276e814c9b",
  "sequence_id": 20,
  "channel": "state"
}
```

값은 예시다. `schema_version`은 노드 자기 판의 번호를 쓴다(드론 `1.1`, Go1 `1.3`).

| 키 | 뜻 |
|---|---|
| `timestamp` | 발행 시각. RFC3339, ms, `+09:00` |
| `session_id` | 노드 1회 기동 식별자. 재시작하면 바뀐다 |
| `sequence_id` | 발행 순번. `session_id`가 바뀌면 0부터 |

`status`에는 머리 외에 다음이 들어간다.

```json
{
  "channel": "status", "event": "summary", "status": "online",
  "device_status": "ok", "link": "ok",
  "registration": {
    "entity_id": "ep-001", "node_id": "pi8", "zone_id": "zoneA",
    "entity_type": "robot", "device_type": "robomaster_ep", "fw_version": "0.1.0"
  }
}
```

| 키 | 값 |
|---|---|
| `event` | `birth`(등록) / `summary`(10초) / `shutdown`(정상 종료) / `death`(LWT) |
| `status` | `online` / `offline` |
| `device_status` | 장치 자기 판단. `ok` / `degraded` / `fault` |
| `link` | 노드 ↔ 장치 링크. `ok` / `degraded` / `fault`. 노드가 곧 장치면 `ok` |
| `registration` | **웹이 장치를 알아보는 근거.** `entity_type`을 반드시 넣는다 |

LWT 페이로드는 `{…머리, "channel":"status", "event":"death", "status":"offline", "device_status":"fault", "reason":"lwt"}`이고 retained로 건다.

### 6-3. 종류별 필드

**공통 결측 규칙: 모르면 `null`이다. 0을 넣지 않는다.** 장치 링크가 끊겼으면 마지막 값을 다시 보내지 말고 `null`로 보낸다. 웹은 "끊긴 뒤에도 흘러나오는 마지막 값"을 가장 위험한 거짓말로 다룬다.

**`robot`** [실측 — Go1과 같다]

| 키 | 단위·값 | 채널 |
|---|---|---|
| `battery_pct` | 0~100 | `state`, `status` |
| `position` | `{x, y, heading_deg}`. 좌표계는 부록에 적는다 | `state` |
| `speed_mps` | m/s | `state` |
| `robot_mode` | 자유 문자열. 예 `idle`, `moving` | `state`, `status` |
| `in_mission` | `true`/`false`. 명령 실행 중이면 `true` | `status` |

**`camera`** [제안]

| 키 | 단위·값 | 채널 |
|---|---|---|
| `sources` | `[{ "source_id": "cam-002_main", "reachable": true, "fps": 15.0, "resolution": "1280x720" }]` | `status` |

`reachable`은 노드가 카메라에서 프레임을 받고 있는가다. 모르면 `null`이다. 영상 자체는 여기 싣지 않는다(§8).

**`sensor`** [제안]

| 키 | 단위·값 | 채널 |
|---|---|---|
| `readings` | 배열. 한 장치가 값을 여러 개 낼 수 있다 | `state` |
| `interval_s` | 측정 주기(초) | `status` |

```json
"readings": [
  { "name": "water_level", "value": 1.23, "unit": "m", "measured_at": "2026-09-24T14:03:11.000+09:00", "quality": "ok" }
]
```

| 키 | 뜻 |
|---|---|
| `name` | 측정량 이름. 소문자와 밑줄 |
| `value` | 숫자. 못 쟀으면 `null` |
| `unit` | SI 단위 문자열. `m`, `degC`, `%`, `Pa` 등 |
| `measured_at` | **잰 시각.** 발행 시각(`timestamp`)과 다를 수 있다 |
| `quality` | `ok` / `suspect` / `invalid` |

임계치를 넘으면 `state`를 주기와 상관없이 즉시 한 번 보내고 머리에 `"reason": "threshold"`를 넣는다.

**`actuator`** [제안]

| 키 | 단위·값 | 채널 |
|---|---|---|
| `position_pct` | 0(닫힘)~100(열림) | `state` |
| `target_pct` | 지금 가려는 값. 없으면 `null` | `state` |
| `moving` | `true`/`false` | `state` |

## 7. 정지(`abort`) [실측 — Go1에서 쓰는 규칙]

움직이는 장치(§5)는 반드시 구현한다.

```
action     = "abort"
parameters = { "reason": 1 }   // 1 사람이 정지 버튼을 누름 · 2 화면 판단 · 3 연결 이상. 기록용
```

1. **대상을 고르지 않는다.** 그 장치가 지금 하는 일을 전부 멈춘다.
2. **거부하지 않는다.** 아무것도 안 하고 있어도, 장치 링크가 끊겨 있어도 `accepted: true`로 받는다. 멈췄으면 `result{SUCCEEDED}`로 끝낸다.
3. **여러 번 와도 같다.** 두 번째 `abort`가 오류가 되면 안 된다. 사람은 급하면 여러 번 누른다.
4. **멈춰진 명령도 답한다.** 돌던 명령은 원래 `command_id`로 `result{status: ABORTED, failure{code, message}}`를 보낸다. 웹은 이것으로 어느 명령이 어디서 끊겼는지 그린다.
5. **빨라야 한다.** 다른 명령 처리에 줄 서지 말고 먼저 처리한다.
6. `reason` 값과 상관없이 동작은 같다.

**`abort`는 비상정지가 아니다.** 통신이 살아 있을 때만 닿는다. 그래서 움직이는 장치의 노드에는 **자체 안전장치**가 필요하다.
- 브로커 연결이 끊기면 진행 중인 동작을 멈춘다.
- 한 명령의 동작에는 상한(거리·시간)이 있어야 한다. 끝없이 도는 명령을 만들지 않는다.
- 하드웨어 E-stop(장치 본체 버튼, 조종기)은 이 규약과 별개로 살려 둔다.

## 8. 영상은 이 경로로 보내지 않는다

카메라 영상과 로봇에 달린 카메라 영상은 **MQTT에 싣지 않는다.** 백엔드의 미디어 경로(`/media`, 서버 8765)가 따로 있다.
- 이 규약에서 카메라에 대해 하는 일은 명령(촬영, 설정)과 상태(§6-3 `sources`)뿐이다.
- 영상 소스 키는 `<entity_id>_<위치>` 꼴이다. 예: `go1-001_front`, `cam-002_main`. `Command.target`에는 이 키가 아니라 장치 id를 쓴다.
- 영상 켜기·끄기를 MQTT action으로 만들지 않는다. 미디어 경로는 붙는 것이 켜기, 끊는 것이 끄기다.

---

## 9. 서버를 거치는 장치

고정 카메라처럼 서버가 장치 연결을 쥐는 경우가 있다. 그때도 **웹이 보내는 봉투는 같아야 한다.**

- 서버(또는 서버 옆 브리지)가 §4의 노드 노릇을 한다. `terminal/<entity_id>/downlink`를 구독하고 uplink로 답한다.
- 서버가 봉투를 받아 장치 고유 API로 바꾸는 것은 서버 안의 일이다. 웹은 몰라도 된다.
- 백엔드가 계획한 명령 경로(Phase 6: 서버 → Kafka → 브리지 → MQTT)도 장치 쪽 경계는 MQTT downlink 그대로다. 그 경로로 온 명령에는 `deadline_unix_ms`와(개정 후) `traceparent`가 붙을 수 있다. 모르는 필드는 proto3가 무시하므로 지금 노드가 깨지지 않는다.

## 10. 새 장치의 어휘표 양식

부록마다 이 표를 채운다. **웹은 이 표를 보고 명령 화면을 만든다.** 표에 없는 action은 웹에서 보내지 않는다.

| action | 움직이나 | 파라미터 (이름: 단위, 범위, 기본값) | 결과 키 (이름: 단위) | 거부 코드 | 걸리는 시간(최대) |
|---|---|---|---|---|---|
| `ping` | 아니오 | 없음 | `uptime_s`: 초 | — | 1초 |
| … | | | | | |

같은 뜻의 동작은 **이미 있는 이름·단위·부호를 그대로 쓴다.** 예: 회전은 `turn{deg}`, 직진은 `move_forward{distance_m, vx}`. 이름이 같으면 웹의 발화 명령("1m 앞으로")이 장치를 가리지 않고 통한다.

## 11. 적합성 점검 — 노드를 다 만들었으면 확인할 것

브로커에 붙인 상태에서 아래를 모두 확인하고 결과를 부록 끝에 적는다.

| # | 확인 | 방법 |
|---|---|---|
| 1 | 노드가 붙으면 `status`(`event: birth`, retained)가 온다 | `mosquitto_sub -h <브로커> -V 5 -t 'zoneA/+/+/#' -v` |
| 2 | `registration.entity_type`이 §5의 값이다 | 위와 같음 |
| 3 | `heartbeat`가 5초마다 온다 | 위와 같음 |
| 4 | 붙자마자 uplink에 `capability`가 온다 | `mosquitto_sub -h <브로커> -V 5 -t 'terminal/<id>/uplink' -F '%x'` |
| 5 | `ping` → 수락 → 종료(`SUCCEEDED`, `uptime_s`) | [mqtt-command.js](../mqtt-command.js) `createRobotControl({ broker, device }).ping()` |
| 6 | 같은 `command_id`를 다시 보내면 재실행하지 않는다 | 같은 hex를 두 번 발행 |
| 7 | 선언하지 않은 action → `UNIMPLEMENTED` 수락 한 건, `result` 없음 | `action: "no_such_action"` |
| 8 | 범위 밖 파라미터 → `INVALID_ARGUMENT`, 장치가 움직이지 않는다 | 부록 어휘표의 범위 밖 값 |
| 9 | (움직이는 장치) 동작 중 `abort` → `abort`는 `SUCCEEDED`, 돌던 명령은 `ABORTED` | 이동 명령 직후 `abort` |
| 10 | (움직이는 장치) 아무것도 안 할 때 `abort`를 두 번 → 둘 다 `SUCCEEDED` | |
| 11 | (움직이는 장치) 동작 중 브로커 연결을 끊으면 멈춘다 | 노드 쪽 네트워크를 끊는다 |
| 12 | 노드를 `kill -9` 하면 `status`에 `death`/`offline`이 온다 | |
| 13 | 장치 링크를 끊으면 `link: fault`, 값은 `null` | 장치 전원 또는 무선을 끊는다 |

바이트를 비교할 때 주의: `map` 필드는 인코더마다 순서가 다를 수 있다. **hex를 문자열로 비교하지 말고 디코딩해서 비교한다.**
