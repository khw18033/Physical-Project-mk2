# 작업 프롬프트 — 가시화: 로봇 칸에 드론(pi3) 연결 (2026-09-21)

> 가시화 저장소(`Physical-Project-mk2`) 작업 AI에게 붙여 넣는 용도. 같이 내릴 명령은 `작업명령_드론가시화연결_260921.md`.

---

## 배경

연결 관리의 **로봇(`physical`) 칸**은 지금 Go1(`pi7`)에 붙는다. 여기에 X500 v2 드론을 추가한다.

**칸을 새로 만들지 않는다.** 같은 로봇 칸에서 주소를 `pi7` 대신 `pi3`로 바꾸면 드론에 붙는다. 드론 라즈베리파이(`pi3`)도 Go1과 똑같이 자체 MQTT 브로커(9001 WebSocket)를 띄우고, 같은 protobuf 봉투와 토픽 규칙(`terminal/<device_id>/uplink|downlink`)을 쓴다. 드론의 device_id는 **`x500-001`**.

이번 목표는 **드론의 연결 상태, 배터리, 드론 상태를 화면에서 보는 것**이다. **드론 제어 명령은 이번 범위가 아니다.**

### 계약

드론 쪽 AI가 `CONTRACT_x500.md`를 만든다. 사용자가 전달해 준다. **그 문서의 값이 기준이다.** 아래는 초안이고, 계약 문서와 다르면 계약 문서를 따른다.

| 항목 | 초안 값 |
|---|---|
| 주소 | `ws://pi3.local:9001` · 연구실 `ws://192.168.50.254:9001` · Tailscale `ws://100.85.243.54:9001` |
| device_id | `x500-001` |
| 토픽 | `terminal/x500-001/downlink` · `terminal/x500-001/uplink` |
| Capability | 접속 시 발행. actions = `ping` 하나 |
| 상태 | 1~2Hz. FC 링크, 배터리(전압·전류·잔량), arm, 비행 모드, GPS fix·위성 수, 자세, 최근 경고 |

## 원칙

### 1. 장비 종류는 주소가 아니라 장비가 알려 준다

"`pi3`에 붙으면 드론"을 **주소 문자열로 판정하지 않는다.** 붙은 뒤 장비가 발행하는 **Capability(device_id, 종류)**로 판정한다.
- 주소는 IP로 바뀌거나 Tailscale로 바뀔 수 있다. 주소로 판정하면 그때마다 깨진다
- 사용자 입장에서는 똑같이 "pi3 프리셋을 고르면 드론"이다

### 2. 기종별 항목표를 화면 코드에 두지 않는다

요구사항에 이미 있다: *"대상별로 조회할 상세 항목은 어댑터 프로파일에서 제공하며 화면 코드에 기종별 항목표를 두지 않는다."*
- 드론 상태 칸을 `if (drone)`으로 하드코딩하지 말고, 장비가 보낸 상태 항목을 받아 그리는 구조로 만든다
- 계약상 불가능하면(항목 이름·단위가 페이로드에 없으면) 최소한 **항목표를 `src/physical/` 안 한 곳**에 두고, 보고서에 한계로 적는다

### 3. `target`이 `go1-001`로 고정된 곳을 없앤다

지금 `encode.ts` 등에 `robot-01 → go1-001` 매핑이 있다. 드론에 붙으면 `x500-001`이어야 한다.
- 발행 대상과 구독 토픽은 **붙은 장비의 Capability에서 받은 device_id**로 정한다
- Capability를 아직 못 받았으면 명령을 내보내지 않는다
- `verify:physical-port` 제약(주소·토픽을 아는 면은 `src/physical/` 하나)은 그대로 지킨다

### 4. 오래된 값을 현재 값처럼 보이지 않는다

- 상태 수신이 일정 시간(예: 3초) 끊기면 값을 흐리게 하고 "마지막 수신 n초 전"을 표시
- 드론이 "FC 링크 없음"을 보내면 배터리·자세 칸은 비운다

## 화면

### 연결 관리 (로봇 칸)

- 프리셋에 `pi3` 셋 추가: 이름 `ws://pi3.local:9001`, 연구실 `ws://192.168.50.254:9001`, Tailscale `ws://100.85.243.54:9001`. `pi7` 프리셋은 그대로 둔다
- 상태 표시를 **셋으로** 나눈다. 기존 브로커/로봇 두 줄에 드론일 때만 한 줄이 더 붙는 구조

| 줄 | 무엇 | 실패 뜻 |
|---|---|---|
| 브로커 | WebSocket 연결 | 주소·망 문제 |
| 장비 | `ping` 왕복 + 장비 종류·device_id 표시 | 라즈베리파이 노드 문제 |
| FC 링크 (드론만) | 드론이 보고한 FC 링크 | 라즈베리파이는 살았는데 FC와 끊김 |

셋째 줄이 있어야 "라즈베리파이는 켜졌는데 FC와 안 붙었다"를 무대 전에 가를 수 있다. 오늘 실제로 이 상황 때문에 반나절을 썼다.

### 시연 화면 표시등

- 기존 표시등을 그대로 쓰되, 붙은 장비 종류가 보이게 (예: "드론 x500-001 연결됨")
- 누르면 연결 관리가 열리는 동작 그대로

### 장비 상태 보기

- Go1 쪽에 상태 보기 자리가 이미 있으면 **같은 자리에 같은 방식으로** 드론 상태를 띄운다
- 없으면 연결 관리 로봇 칸 아래에 접을 수 있는 상태 영역을 둔다
- 배터리는 숫자와 함께 경고 구간 색 (구간 값은 계약 문서나 장비가 주는 값을 따르고, 없으면 상수 한 곳에)
- arm 상태는 눈에 잘 띄게. **ARMED는 경고색**

### 긴급 정지 버튼

드론은 이번에 정지 action을 선언하지 않는다. 드론에 붙은 상태에서 정지 버튼을 누르면:
- 명령을 보내지 않고, "이 장비는 화면 정지를 지원하지 않습니다 — 조종기로 정지하세요"를 크게 띄운다
- 판정 근거는 Capability의 actions 목록이다 (종류로 판정하지 않는다)

## 작업 순서

### 0단계. 조사 (바꾸지 않는다)
- 연결 관리 `physical` 칸의 현재 구조, 프리셋이 정의된 곳
- `go1-001`이 코드에 적힌 모든 곳 (`grep`)
- 웹이 지금 Capability를 받아 쓰는가. 받는다면 어느 토픽, 어디서
- Go1 상태(배터리 등)를 지금 화면에 보여 주는 자리가 있는가
- 기존 목 uplink 구조
- `verify:*` 현재 결과와 `verify:standalone` 수치

보고하고 멈춘다. 이때 **계약 문서가 이미 있으면** 계약 문서와 현재 코드의 차이도 같이 정리한다.

### 1단계. 구현
- 위 원칙과 화면대로
- 드론용 목 uplink 추가: Capability → 1Hz 상태 → 중간에 "FC 링크 없음" 5초 → 복구. 배터리가 경고 구간으로 떨어지는 경우 한 번, ARMED 한 번

### 2단계. 검증

| 검사 | 무엇을 |
|---|---|
| **`verify:device-by-capability`** (신설) | 장비 종류·device_id를 주소가 아니라 Capability로 정하는가. 코드에 `pi3`·`pi7` 문자열로 분기하는 곳이 없는가 |
| **`verify:no-hardcoded-target`** (신설) | 발행 대상이 `go1-001` 상수가 아니라 받은 device_id인가. Capability 전에는 명령이 안 나가는가 |
| **`verify:stale-state`** (신설) | 상태가 끊기면 흐려지는가, "FC 링크 없음"이면 배터리 칸이 비는가 |
| **`verify:stop-unsupported`** (신설) | actions에 정지가 없으면 정지 버튼이 명령을 안 보내고 안내를 띄우는가 |
| `verify:physical-port` · `verify:connection-panel` · `verify:no-physical` | 그대로 통과 |
| Go1 회귀 | Go1 목으로 기존 시험(ping, 스캔 노드 채움, 정지)이 그대로 도는가 |
| `verify:standalone` | 증가분 숫자 |

### 3단계. 실기
사용자와 함께: 로봇 칸에서 `pi3` 프리셋 → 브로커·장비·FC 링크 셋 다 초록 → 배터리 값이 실제와 맞는지 → 기체 기울이면 자세 변화 → TELEM 점퍼 뽑으면 FC 링크만 빨강.
