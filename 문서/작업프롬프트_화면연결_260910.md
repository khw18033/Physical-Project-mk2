# 작업 지시: 화면에서 명령 발행 · 긴급 정지 (2단계-A 마무리)

**날짜**: 2026-09-10
**선행**: `reports/2026-09-10_하드웨어연동.md` — 경계·매핑·목까지 서 있고 화면이 부르지 않는다
**범위**: 보고서 9절의 넷을 화면에 붙이는 것 + **긴급 정지**

> 시연은 **가시화 화면으로 로봇이 움직이는 것**을 보여 주는 자리다.
> 콘솔에서 함수를 부르는 것으로는 시연이 성립하지 않는다.

---

## 0. 착수 전에 확인할 것

| 확인 | 무엇을 |
|---|---|
| **지금 화면의 「정지」 버튼** | 어느 탭에 있고 지금 무엇에 묶여 있는가. `CommandTracker` 를 지나는가 |
| `PlanApproval` | 승인 버튼이 지금 무엇을 하는가. 여기에 실행을 매단다 |
| `commandForTask()` | 2단계-A가 만든 것. 화면이 이걸 부르면 된다 |
| `effectsOf()` | 응답을 화면 상태로 옮기는 함수. 무엇을 내놓는가 |
| `BROKER_PRESETS` | 프리셋 넷. 그리기만 하면 된다 |
| **「연결 관리」 탭** | `physical` 대상이 등록돼 있는가 · 주소를 바꾸면 실제로 반영되는가 · 로드 전에 무엇이 보이는가 |
| `CommandTracker` | 4단계 추적(`VZ-O-02`)과 감사(`VZ-O-03`)를 이미 하고 있다. **로봇 명령도 이걸 지나야 한다** |

마지막 줄이 중요하다. 탭 이식 때 `CommandTracker` 를 본체로 삼은 이유가 이것이다.
로봇 명령이 이걸 우회하면 추적과 감사가 그 명령만 못 본다.

## 1. 시연에서 사람이 누르는 것

발표 흐름 그대로다. **누르는 순서가 곧 시연 대본이다.**

| # | 버튼 | 하는 일 | 자리 |
|---|---|---|---|
| 0 | **연결 확인** | `ping` 왕복. 성공·실패·왕복 시간 | 화면 한구석. 발표 직전에만 쓴다 |
| 1 | 발화 / 텍스트 입력 | 이미 있다 | — |
| 2 | **승인** | 실행 시작 → `T-A3` 가 `scan_mission` 을 쏜다 | 기존 `PlanApproval` |
| 3 | **접근 시작** | `T-B2` 가 `move_forward` 를 쏜다 | `MS-B` 가 열린 뒤 |
| 4 | **긴급 정지** | 4절 | **항상 보이는 자리** |

### 왜 3번이 따로 있는가

`scan_mission` 을 `forward_m=0` 으로 쏘기로 한 결정(2단계-A 5절) 덕에 스캔과 접근이 갈렸다.
스캔이 끝나면 화면이 초록 노드를 보여 주고 **거기서 한 박자 쉰다.**
발표자가 "이 방향으로 갑니다"를 말하고 누르면 로봇이 간다.

**자동으로 이어지게 하지 마라.** 그 한 박자가 시연에서 가장 좋은 자리다.

### 주소 프리셋 UI — 값을 갖는 곳은 「연결 관리」 하나다

브로커 주소는 **「연결 관리」 탭의 `physical` 대상**이 갖는다. 런타임 변경과
`localStorage` 영속을 그쪽이 이미 한다. 2단계-A가 `connections.ts` 의 대비값을 비운 것은
**주소 문자열을 아는 면을 `src/physical/` 하나로 두기 위해서**이지, 연결 관리에서 빼려는
것이 아니었다.

시연 화면의 프리셋 넷은 **그 값을 읽고 쓰는 지름길**이다. 별도 상태를 만들지 마라.

- 프리셋을 고르면 연결 관리의 `physical` 주소가 바뀐다. 반대도 마찬가지로 보인다
- 「어느 쪽이 진짜냐」가 생기면 발표장에서 엉뚱한 주소로 붙는다
- 직접 입력 칸도 같은 값을 건드린다

**왜 시연 화면에도 두는가** — 발표 중에 탭을 옮기고 싶지 않다. 이름이 안 풀려서
IP로 바꾸는 일이 무대에서 일어날 수 있고, 그때 화면을 떠나면 흐름이 끊긴다.

### 연결 관리가 빈 주소를 보이는 문제

2단계-A 보고서 7절이 적어 둔 부작용이다. `PhysicalClient` 가 로드되기 전에는 연결 관리
화면에 주소가 비어 보인다. **발표 직전 확인할 때 헷갈리는 자리다.**

기본값이 실제로 무엇인지 화면에서 알 수 있어야 한다. 「아직 붙지 않음」과
「주소가 없음」을 구분해서 보여라. 대비값을 `connections.ts` 로 되돌리지는 마라 —
`verify:physical-port` 가 그걸 잡는다.

## 2. 승인 앞 정지는 그대로다

매칭 결과는 **제안**이고 사람이 승인하기 전에는 아무것도 나가지 않는다(`VZ-U-07`).
2번 버튼을 누르기 전에 MQTT로 나가는 바이트가 있으면 안 된다.

`verify` 로 확인할 것 — **승인 전 발행 0건.**

## 3. 응답을 화면에 옮긴다

`effectsOf()` 가 이미 내놓는 것을 화면 상태로 잇는다. 새로 계산하지 마라.

| 응답 | 화면 |
|---|---|
| `Acceptance{accepted:true}` | 태스크 노드 실행 중 |
| `Acceptance{accepted:false}` | 태스크 노드 실패. **`rejection.code` 와 `message` 를 그대로** |
| `CommandStatus` `scan_turn` | 뷰포인트 노드 채움 (`index = step - 1`) |
| `CommandStatus` `door_turn` | `MS-B` 로 넘어가는 선 활성화 |
| `CommandStatus` `note != ok` | 그 노드에 경고 |
| `CommandStatus` `ack/of` | 진행률 (`forward_m=0` 이면 `of` 는 9) |
| `CommandResult{SUCCEEDED}` | 태스크 노드 완료 |
| `CommandResult{그 외}` | 태스크 노드 실패 + 사유 |

**연결이 끊긴 것과 로봇이 안 움직이는 것은 다르다.** 둘을 같은 표시로 뭉치지 마라.
브로커 연결 상태를 따로 보여 주는 자리가 하나 있어야 한다.

## 4. 긴급 정지

**이 절이 이번 작업에서 가장 중요하다.** 로봇이 사람 쪽으로 걸어가는 상황이 실제로 생긴다.

### 버튼

- 지금 화면에 있는 **「정지」 버튼을 실제로 동작하게** 한다. 새로 만들지 마라
- **어느 화면에 있든 보여야 한다.** 마일스톤을 열었든 뷰 노드를 열었든
- **확인 대화상자를 띄우지 마라.** 한 번 누르면 멈춘다
- 크고, 색이 다르고, 다른 버튼과 멀리 떨어져 있어야 한다 — 잘못 누르는 것보다 못 누르는 게 나쁘다

### 누르면 일어나는 일 넷

1. **정지 명령 발행** — `abort` (5절)
2. 진행 중인 명령 추적 중단 — 뒤늦게 오는 `CommandStatus` 로 노드가 더 차지 않게
3. 화면 타이머·폴링 정지
4. 화면을 **「정지됨」으로 잠근다.** 승인·접근 시작 버튼이 눌리지 않는다

### 연결이 끊겨 있으면

**버튼을 비활성화하지 마라.** 누를 수 있어야 하고, 못 보냈으면 그렇게 말해야 한다.

```
정지 명령을 보내지 못했습니다 — 브로커 연결 없음
```

크게, 빨갛게. **조용히 성공한 척하는 것이 최악이다.**
누른 사람은 로봇이 멈춘 줄 알고 다가간다.

### 재개

자동으로 돌아가지 않는다. 사람이 다시 승인해야 한다.
「정지됨」에서 나오는 길을 명시적으로 하나 둔다.

### 이건 안전장치가 아니다

화면 버튼은 네트워크를 타고 나간다. 브로커가 죽었거나 Wi-Fi가 끊기면 안 나간다.
**보고서와 발표 자료에 이렇게 적어라.**

> 화면의 정지는 소프트웨어 정지다. 물리적 비상 정지는 로봇 본체와 조종기 쪽에 있다.

시험할 때도 발표할 때도 **로봇 조종기를 든 사람이 옆에 있어야 한다.**

## 5. 정지 명령 — 우리가 정의했다

확인된 action 셋에 멈추는 명령이 없어서 **우리가 안을 만들어 하드웨어 쪽에 넘겼다.**
규약은 `문서/정지명령_규약_260910.md` 다. 그대로 구현한다.

```
action     = "abort"
parameters = { "reason": 1 }        // 생략 가능. 1 = 사람이 눌렀다
```

- 토픽·QoS는 다른 명령과 같다
- **대상을 지정하지 않는다.** 그 로봇이 지금 하는 것 전부를 멈춘다
- `abort` 는 **자기 `command_id`** 를 새로 만든다. 돌던 임무의 id를 재사용하지 마라 —
  응답이 섞인다
- 돌던 임무 쪽에서는 원래 id로 `CommandStatus{event:"aborted"}` → `CommandResult{ABORTED}` 가 온다.
  그것으로 어느 임무가 몇 번째에서 끊겼는지 화면에 표시한다

### 규약 밖으로 나가지 마라

이름과 파라미터는 우리가 정했지만 **받는 쪽이 아직 합의하지 않았다.**
`reason` 말고 다른 파라미터를 더하지 마라. 하드웨어가 다른 이름을 쓰겠다고 하면
`src/physical/presets.ts` 의 상수 한 줄만 고치면 되게 둔다.

### 명령이 안 나가도 화면은 멈춘다

4절의 넷 중 1번이 실패해도 2·3·4는 그대로 일어난다. **이게 이 기능의 뼈대다.**
발행 성공 여부와 화면 잠금을 한 덩어리로 묶지 마라.

## 6. 목으로 먼저 시험한다

로봇 없이 4절의 넷 중 셋(2·3·4)을 확인할 수 있다.

- 목 uplink가 `step` 을 흘리는 중에 정지를 누른다
- 남은 `CommandStatus` 가 와도 **노드가 더 차지 않아야 한다**
- 화면이 「정지됨」으로 잠기고 승인 버튼이 안 눌려야 한다
- 브로커 주소를 일부러 틀리게 두고 눌러 「보내지 못했습니다」가 뜨는지 본다

## 7. 검증

| 검사 | 무엇을 |
|---|---|
| **`verify:no-publish-before-approval`** (신설) | 승인 전에 발행이 **0건**인가 |
| **`verify:emergency-stop`** (신설) | 정지 뒤 **늦게 온 `CommandStatus` 가 노드를 안 바꾸는가** · 타이머·폴링이 멈추는가 · 화면이 잠기는가 · 연결이 없을 때 버튼이 눌리고 실패를 표시하는가 |
| **`verify:command-through-tracker`** (신설) | 로봇 명령이 `CommandTracker` 를 지나는가 (`VZ-O-02`·`VZ-O-03` 이 보게) |
| **`verify:one-broker-address`** (신설) | 브로커 주소를 **갖는 상태가 하나뿐인가.** 시연 화면 프리셋이 별도 상태를 만들지 않았는가 |
| `verify:physical-port` | 정지 action 이름과 토픽이 `src/physical/` 밖에 없는가 |
| `verify:status-index` · `command-encode` | 2단계-A 그대로 통과 |
| `verify:viewpoint-fill` · `viewpoint-layout` | 1단계 그대로 통과 |
| `verify:standalone` | **통합 빌드 KB 를 다시 잰다.** 기준선은 520.21 kB (보고서 3절) |
| 기존 전종 | 통과 |

`verify:emergency-stop` 의 첫 줄이 핵심이다. **정지를 눌렀는데 화면이 계속 진행하는 것**이
이 기능의 가장 흔한 실패 모양이고, 그건 눈으로 보면 "어? 멈췄는데 왜 돌지"로 나타난다.

번들은 이번에 실제로 는다 — `protobufjs/minimal` 과 생성 모듈과 `mqtt` 가 이제 화면에 붙는다.
보고서 3절이 말한 대로다. **숫자를 재서 남겨라.**

## 8. 하지 않을 것

- 새 정지 버튼 신설 — 기존 것을 살린다
- 브로커 주소를 시연 화면이 따로 들고 있는 것 — 연결 관리의 값을 읽고 쓴다
- 규약 밖의 파라미터 추가 — `reason` 하나뿐이다
- 스캔 → 접근 자동 연결 — 사람이 누른다
- 승인 전 발행
- `CommandTracker` 우회
- 객체 탐지 연동 (2단계-B) · 2D 맵 · 뷰포인트 배치와 색
