# 작업 지시: 명령 기록을 기록 열에 합류시킨다

**날짜**: 2026-09-20
**선행**: `문서/논문Outline_초안_260904.md` §4-2·§4-3·§4-7 · `reports/2026-08-28_탭이식.md` 두 상태 모델 판단 · `문서/정지명령_규약_260910.md`
**범위**: 1부만 이번에 한다. 2부는 1부가 끝난 뒤 따로 연다
**목표**: **되감기가 세 층에 닿는다.** 그리고 로봇 없이 실험을 돌릴 수 있다

> 논문 §4-2 가 「임의 시점의 계층 상태를 복원한다」고 쓰는데 복원되는 계층이 셋 중 둘이다.
> 이 지시가 그 문장을 참으로 만든다.

---

## 왜 하나

지금 기록이 두 군데 산다.

| | 어디 | 무엇이 들어가나 | 되감기가 닿나 |
|---|---|---|---|
| **기록 열** | `src/data/trace.ts` | 마일스톤 · 태스크 | ✓ |
| **작업대** | `src/physical/robotSession.ts` | 명령과 로봇 응답 | ✗ |

`robotSession.ts` 는 `trace.ts` 를 import 하지 않는다. `recordCommand()` 를 부르는 곳은
`robotCommands.ts:107` 한 군데, **실제 로봇에 명령 낼 때뿐**이다.

그래서 셋이 무너진다.

- **되감기가 명령까지 안 간다.** `foldStatuses()` 가 돌려주는 것은 `{ tasks, milestones }` 둘뿐이다.
  재생 머리를 옮겨도 `ActionModal` 의 명령 표는 안 따라 움직인다 — 지금 작업대에 남아 있는
  마지막 명령을 그냥 읽는다. **논문 §4-4 의 「모든 노드가 같은 재생 머리를 쓴다」가 여기서 깨진다**
- **세션을 닫으면 사라진다.** 일지는 남고 작업대는 치워진다
- **대본 재생에는 아예 없다.** 실험 60건을 돌리려면 로봇을 매번 켜야 한다

그리고 논문 §4-3 이 「AI·백엔드·사람 셋 중 누가 만든 값인지 적는다」고 주장하는데,
**대본 6편의 실패 사건 4건이 전부 `producedBy: backend` 다.** 사람이 만든 값이 기록에 0건이다.
`trace.ts` 에 `HUMAN_SEQ_BASE = 1_000_000` 자리가 예약돼 있는데 안 쓰고 있다.

# 1부 — 로봇을 안 건드리는 것

## 1. 사건 네 종을 더한다

지금 대본에 있는 `kind` 는 `created · started · evaluated · failed · derived · progress` 여섯이다.
여기에 넷을 더한다.

| kind | 언제 | `producedBy` |
|---|---|---|
| `commanded` | 명령이 실제로 나갔다 | 그 명령을 낸 주체 |
| `answered` | 로봇 응답이 한 줄 도착했다 | `robot` |
| `expired` | 기다리는 기한이 끝났는데 안 왔다 | `robot` |
| `adjusted` | 사람이 값을 바꿨다 | `human` |

### `nodeId` 는 `commandId` 다

액션 아이템의 정체가 `TaskCommandRecord` 이고 그것을 가리키는 키가 `commandId` 다.
새 식별자를 만들지 마라.

어느 태스크의 것인지는 `payload` 에 싣는다. 대본이 이미 `events[].payload` 를 쓰고 있다
(`payload.criterion` ↔ `tasks[].evaluation.criteria[]`).

```
commanded  payload: { taskId, action, parameters, requestId }
answered   payload: { taskId, line, index }        // index 는 회전 걸음 번호. 없으면 null
expired    payload: { taskId, waitedMs, reason }
adjusted   payload: { taskId, field, before, after }
```

**`parameters` 는 실제로 실려 나간 값이다.** 화면에 적힌 계획값이 아니다 —
`robotSession.ts` 주석이 그렇게 못박아 뒀다. 그 원칙을 그대로 지켜라.

### ⚠ 현황판 값은 안 옮긴다

로봇 위치·배터리·연결 램프는 **기록 열에 넣지 않는다.** 260828 에 「두 상태 모델은 합치지
않았다」고 정한 판단은 그대로 유효하다. 그것들은 지금 값이지 사건이 아니다.

명령만 옮기는 이유는 명령에는 **낸 시각이 있고 상태가 전이하기 때문**이다
(`issued → running → done/failed`). 사건의 모양을 하고 있다.

---

## 2. 무응답을 어떻게 적는가 — 이 작업의 핵심

일지는 **일어난 일만** 덧붙인다. 그런데 안 온 응답은 일어나지 않은 일이다.

그래서 **기다림이 끝났다는 사실**을 적는다. 기다린 것은 일어난 일이다.

이미 재료가 있다. `reportPauseAnswer(client, commandId, timeoutMs = 4000)` 이 4초를 기다리고
안 오면 `notePauseFailure()` 를 부른다. 그 자리에서 `expired` 를 일지로도 보낸다.

### 「아직」과 「영영」을 반드시 가른다

접기만으로 판정하면 이 둘이 같아진다.

| 시각 t 에서 | 응답 사건 | 기한 사건 | 뜻 |
|---|---|---|---|
| 명령 났음 | 0건 | 없음 | **아직 기다리는 중** |
| 명령 났음 | 0건 | 있음 | **영영 안 왔다** |

**디버깅에서 제일 중요한 구분이 이것이다.** 느린 것과 죽은 것은 원인이 완전히 다르다.
기한 사건이 없으면 이 둘을 영원히 구분 못 한다.

이 구분이 논문에도 값을 한다. 로봇 침묵이 원인인 실패가 지금은 계측 범위 밖인데,
`expired` 를 남기면 기록 안으로 들어온다. §6-2 의 「도구가 원리적으로 못 찾는 경우」가 줄어든다.

---

## 3. `fold` 를 세 층으로

`src/data/fold.ts` 의 `FoldedStatuses` 에 층을 하나 더한다.

```ts
export type FoldedStatuses = {
  tasks: Record<string, { status: TaskStatus; attempt: number }>;
  milestones: Record<string, TaskStatus>;
  actions: Record<string, {                    // ← 더한다. 키는 commandId
    taskId: string;
    status: 'issued' | 'running' | 'done' | 'failed';
    answered: number;                          // 그 시점까지 온 응답 줄 수
    expired: boolean;                          // 기한이 끝났는가 — status 와 별개다
  }>;
};
```

`expired` 를 `status` 에 섞지 마라. 섞으면 §2 의 구분이 도로 사라진다.

### 순수 함수라는 성질을 지켜라

`fold.ts` 는 저장소도 대본 파일도 모른다. `verify:scenario-mode` 가 이 함수를 Node 에서
직접 불러 검사하기 때문이다. **`robotSession` 을 import 하면 그 검사가 죽는다.**
접기는 기록 열만 읽는다. 작업대를 보지 않는다.

---

## 4. 화면 — 명령 표가 재생 머리를 따라간다

`ActionModal` 이 지금 `commandsOfTask(task.id)` 로 작업대를 직접 읽는다.
이걸 **접은 결과를 읽는 쪽으로** 바꾼다.

- 되감아 놓은 시점에서는 그 시점까지의 명령과 응답만 보인다
- 기한이 끝난 명령은 「응답 없음」으로 뜬다. 아직 기다리는 것은 「대기 중」이다. **둘이 다르게 보여야 한다**
- 값이 바뀐 자리는 전후를 같이 보인다

### ⚠ 다 적는 것과 다 보여주는 것은 다르다

기록에는 전부 남긴다. 화면은 §4-5 의 표시 깊이로 가른다 — 접힌 상태에서는 판정과 숫자,
누르면 확대되면서 줄이 열린다.

**격리로 600줄을 40줄로 줄여 놓고 화면에서 다시 600줄을 보이면 줄인 의미가 없다.**
값을 감추는 것이 아니라 한 번 더 눌러야 나오게 두는 것이다.

---

## 5. 목 게이트웨이도 같은 사건을 흘린다

**이게 빠지면 실험 60건마다 로봇을 켜야 한다.** 1부에서 제일 값이 큰 항목이다.

`tasks[].actionItems` 는 스키마에 이미 있다. 대본이 액션 아이템을 정의하면
목 게이트웨이와 로컬 재생기가 그것을 읽어 `commanded` · `answered` 사건으로 흘린다.
fold.ts 260904 주석이 말하는 구조 그대로다 — 대본은 정의를 들고, 재생기가 기록으로 흘리고,
화면은 흘러온 것만 접는다.

### 대본은 한 편만 채운다

전편을 채우는 것은 별건이다. 이번에는 **`MSN-260909-01` 한 편만** 액션 아이템을 채워
경로가 도는 것을 증명한다. 나머지 다섯은 다음 작업이다.

`MSN-260909-01` 을 고른 이유 — 시연 대본이라 실제 로봇 실행과 대조할 수 있다.
같은 임무를 라이브로 한 번, 목으로 한 번 돌려 **두 기록이 같은 모양인지** 볼 수 있다.

### 응답 없는 명령을 한 건 넣어라

대본에 `expired` 가 한 건도 없으면 §2 를 검사할 방법이 없다. 일부러 한 건 심는다.

# 2부 — 로봇을 건드리는 것 (1부 뒤에 따로 연다)

지시서를 따로 쓴다. 여기서는 판단만 적어 둔다.

## 정지가 확인된 경우에만 조정과 재시작을 연다

지금 일시정지는 로봇에 쏘고 4초 기다린다. 답이 없으면 실패로 적는다.
즉 **멈췄는지 확신 못 하는 상태가 실제로 있다.**

그 상태에서 값 바꾸고 재시작을 누르면 두 가지가 겹친다. 로봇은 계속 가는 중인데 새 명령이
나가고, 재시작은 그 단계를 처음부터 다시 도는 방식이라 이미 절반 간 로봇이 처음 위치 기준
명령을 받는다.

`lockPaused(taskId, published, failure)` 에 발행 성공 여부와 실패 사유가 이미 있다.
그것을 관문으로 쓴다. 확인이 안 됐으면 버튼을 잠그고 **왜 잠겼는지 화면에 적는다.**
그것도 디버깅 정보다.

## 값 조정을 재시작에 잇는 자리는 한 군데다

`ActionModal` 의 입력칸은 `issueCommand({ ..., params: { speed, clearance } })` 로 게이트웨이에
직접 나간다. 그런데 `resumeMission` 은 `currentMission().params` 를 읽는다. **서로 다른 물통이다.**

`currentMission().params` 는 `scenario.ts:213` 에서 대본 불러올 때 한 번 채워지고
**아무도 바꾸지 않는다.** 읽는 데는 `robotClient` · `scanGate` · `navLink` · `StopButton` ·
`main.tsx` 여럿인데 쓰는 데가 없다. 입력칸이 이 params 를 덮어쓰게 하면 이어진다.

## 안 한다

- **긴급정지 경로 자체.** 260910 에 규약을 확정했고 시연이 그 위에 선다. **일지에 남기는 것만
  더하고 동작은 한 줄도 안 바꾼다.** `verify:emergency-stop` 이 그것을 지킨다
- **이어하기.** 로봇 규약에 없다. 우리가 못 고친다. 논문에 「그 단계를 처음부터 다시 돈다」고
  그대로 쓴다. 숨길 일이 아니다

- **영문화 남은 몫** — 새 사건의 화면 문구는 사전을 태운다. 그것만 한다
- **검사 기준 완화** — 키 대조로 바꾸는 것이지 빼는 것이 아니다

## 7. 검증

### 신설 4종

| 검사 | 보는 것 | 대조군 |
|---|---|---|
| `verify:action-trace` | 명령이 기록 열에 들어가는가. 작업대와 기록 열에 **같은 `commandId`** 가 있는가 | 기록 열에 안 넣은 사본이 잡혀야 |
| `verify:fold-actions` | `fold` 가 세 층을 돌려주는가. **Node 에서 직접 돌린다** — `verify:scenario-mode` 와 같은 방식 | 액션 층이 빈 사본이 잡혀야 |
| `verify:no-answer` | 「아직」과 「영영」이 갈리는가 | **응답이 온 명령이 무응답으로 잡히면 실패** |
| `verify:adjust-pair` | 값 변경이 전후 짝으로 남는가 | 후만 남긴 사본이 잡혀야 |

**대조군 없는 검사는 통과해도 아무것도 증명하지 않는다.** 네 종 전부 「일부러 틀린 사본이
반드시 잡히는지」를 같이 확인해라.

### 깨질 만한 것 — 이름으로 확인해라

`verify:scenario-mode` (fold 시그니처) · `verify:command-log` · `verify:mission-record` ·
`verify:emergency-stop` · `verify:no-publish-before-approval`.

**파일 하나를 고치면 그 파일을 보는 검사도 같은 커밋에서 고친다.** 한 번도 빨간 채로 넘어가지 않는다.

### 손 확인

- 라이브로 시연 한 바퀴 → 되감기 → **명령 표가 재생 머리를 따라가는가**
- 목으로 `MSN-260909-01` 한 바퀴 → 같은 확인
- 라이브 기록과 목 기록이 **같은 모양인가**
- `?lang=en` 에서 새 문구가 한국어로 안 새는가

## 8. 재측정 — 논문에 들어갈 숫자다

끝나고 사건 수를 다시 센다. 기준선은 **280건**이다.

```
npm run measure:representation     # 기존. 대본 노드 수
npm run measure:trace-scale        # 신설. 층별 사건 수 — 액션 층 포함
```

`measure:trace-scale` 이 내놓을 것 — 대본별로 마일스톤 · 태스크 · 액션 · 응답 줄 각각 몇 건인지,
그리고 합계. 이 숫자가 논문 §5-2 축 가의 **분모**가 된다.

> 지금 분모가 노드 24개라 「축소했다」는 말이 안 선다. 이 작업이 분모를 만든다.
> 얼마나 커지는지가 축 가를 쓸 수 있는지를 결정하므로, **이 측정이 이 작업의 마지막 관문이다.**
