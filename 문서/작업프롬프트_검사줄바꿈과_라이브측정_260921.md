# 1절 — 검사의 줄바꿈 의존을 끊는다

## 무엇이 일어났나

`.gitattributes` 가 `* text=auto` 다. **저장소는 LF, 윈도우 작업 트리는 CRLF.**
일부러 그렇게 못박아 둔 규칙이고 그 파일에 이유까지 적혀 있다.

그런데 260920 에 새로 쓴 검사들이 대조군을 이렇게 만든다.

```js
source.replace('    if (event.atSec > second) break;\n    if (!ACTION_KIND_SET.has(event.kind)) continue;', …)
```

찾는 문자열이 `\n` 인데 작업 트리는 `\r\n` 이다. **`replace` 가 아무것도 못 찾고 원본을
그대로 돌려준다.** 검사는 그것을 「대조군을 만들지 못했다」로 잡아냈다 — 검사가 제 일을 했다.

**WSL 에서는 초록, 윈도우에서는 빨강이다.** 260920 보고서의 80/80 은 거짓이 아니라
WSL 기준이었다.

## 고칠 것 — 다섯

`replace` 안에 `\n` 을 쓰는 검사가 다섯이고, 원본을 정규화하는 것은 **하나도 없다.**

```
verify-action-trace.mjs · verify-adjust-pair.mjs · verify-fold-actions.mjs
verify-human-trace.mjs  · verify-no-answer.mjs
```

`action-trace` 와 `fold-actions` 가 지금 통과하는 것은 **운이다.** 그 둘의 대조군이
마침 한 줄짜리였을 뿐, 같은 지뢰를 밟고 있다. **다섯 다 고친다.**

### 방법 — 원본을 LF 로 정규화하고 시작한다

```js
const source = readFileSync(path, 'utf8').replace(/\r\n/g, '\n');
```

`\r?\n` 정규식으로 찾는 쪽은 **쓰지 마라.** 대조군이 늘어날 때마다 사람이 기억해야 하는
규칙이 되고, 한 번 잊으면 조용히 통과한다. 입구에서 한 번 정규화하는 쪽이 잊을 자리가 없다.

### 사본을 쓸 때의 줄바꿈

사본은 임시 디렉터리에 쓰이고 Node 가 읽을 뿐이라 **LF 로 써도 된다.** 원본 파일은
한 글자도 안 건드린다 — 정규화는 메모리 안에서만 일어난다.

## 규칙으로 못박는다

**대조군은 LF 로 정규화한 원본에서 만든다.**

이 한 줄을 `scripts/README` 든 검사 공통 주석이든 **다음 사람이 반드시 보는 자리**에
적어라. 지금은 다섯이지만 여러 줄 대조군을 쓸 때마다 같은 일이 난다.

### 신설 — `verify:crlf-safe`

검사 스크립트 자신을 보는 검사다. **`replace(` 안에 `\n` 이 있는데 그 파일이 원본을
정규화하지 않으면 실패.**

- 대조군 — 정규화 줄을 지운 사본이 반드시 잡혀야 한다
- 소스만 본다. 돌릴 필요가 없어 빠르다

이것이 없으면 다음에 검사를 하나 더 쓸 때 다시 밟는다.

## 검증

```
npm run verify:clean
npm run verify:no-answer      # 대조군 5/5
npm run verify:adjust-pair    # 대조군 5/5
npm run verify:action-trace   # 대조군 3/3 — 여전히
npm run verify:fold-actions   # 대조군 4/4 — 여전히
npm run verify:human-trace
npm run verify:crlf-safe      # 신설
```

그리고 **전종**을 돌려 81/81 을 확인한다. 개수가 아니라 이름으로 본다.

> **되돌아가 확인할 것 하나** — 260920 보고서의 「80/80 초록」에 이 사실을 덧붙여라.
> 지운다는 뜻이 아니라 「WSL 기준이었고 윈도우에서 셋이 빨갰다」를 한 줄 더한다는 뜻이다.
> 보고서는 그때 무엇을 봤는지의 기록이므로 고쳐 쓰지 않는다.

# 2절 — 라이브 한 판을 잰다. **축 가의 판정 관문이다**

## 왜 이것이 먼저인가

260920 재측정이 사건 280 → 295, **×1.05** 였다. 한 편만 채웠으니 당연한 숫자다.
보고서가 「이 숫자로는 모른다」고 적은 것이 맞다.

그리고 보고서의 진단도 맞다. **600줄에 닿는 길은 대본이 아니라 라이브다.**
대본 다섯 편을 더 채워 봐야 편당 80건이고, 실험 한 건이 보는 것은 한 편이다.

반면 실제 한 판에서는 `scan_mission` 하나가 회전 8걸음마다 수락·진행·촬영대기·풀림·종료를
흘린다. **이 비율이 곧 600의 뼈대다.**

**그래서 격리보다 이것이 먼저다.** 이 숫자가 축 가를 쓸 수 있는지를 정하고,
못 쓰면 격리를 구현해도 논문에 못 싣는다. 순서를 바꾸면 헛수고할 위험이 있다.

## 무엇을 재나

실제 로봇을 붙여 시연 경로를 한 판 완주하고, 기록 열을 그대로 뜬다.

| 잴 것 | 왜 |
|---|---|
| 층별 사건 수 — 마일스톤 · 태스크 · `commanded` · `answered` · `expired` | 분모의 실측 |
| **명령 하나당 응답 줄 수의 분포** | 최소·중앙·최대. 600의 뼈대가 이 비율이다 |
| `scan_mission` 한 건이 흘리는 줄 수 | 가장 긴 명령이다. 이것 하나가 분모를 좌우한다 |
| 한 판의 총 소요 시간과 기록 열 바이트 | 축 라(계측 비용)에도 들어간다 |
| `expired` 가 실제로 났는지 | 났으면 그 상황을 적어 둔다. 실물에서 침묵이 얼마나 나는지가 §6-2 에 걸린다 |

`measure:trace-scale` 을 라이브 열에도 쓸 수 있게 넓힌다. **대본용과 라이브용 두 벌을
만들지 마라** — 세는 규칙이 갈리면 두 숫자를 견줄 수 없다.

## 판정 기준을 먼저 박는다

재고 나서 정하면 숫자에 맞춰 기준이 움직인다.

| 한 판 사건 수 | 판정 |
|---|---|
| **300 이상** | 축 가를 쓴다. 분모가 「사람이 다 훑기 어려운 양」이다 |
| **100 ~ 300** | 조건부. 격리 대상을 명령과 응답 줄까지로 잡으면 성립한다. 다만 베이스라인 셋(원시 로그·평면 타임라인·계층만)과의 차이가 작아지므로 **베이스라인 정의를 다시 본다** |
| **100 미만** | 축 가를 뺀다. 분모를 억지로 부풀리지 말고, 논문은 축 라·마와 사례연구로 세운다 |

**300 을 경계로 잡은 이유** — 축소율이 뜻을 가지려면 「다 보면 되지 않냐」는 반문이
안 나와야 한다. 한 화면에 안 들어오는 양이 그 선이고, 수백 줄이 거기다.
이 기준 자체에 이견이 있으면 **재기 전에** 말해라. 잰 뒤에 바꾸면 그건 결과에 맞춘 것이다.

## 로봇을 못 쓰면

실물 접근이 안 되면 **가짜 로봇으로 줄 비율만 재고 실판 수치는 보류한다.**
`scan_mission` 이 8걸음을 실제로 흘리게 해서 명령당 줄 수 분포를 얻는 것까지는 된다.

그때는 보고서에 **「실측이 아니라 가짜 로봇이다」를 제목 옆에 적어라.**
비율은 설계에서 나오므로 쓸 만하고, 총량은 실물이 아니면 못 믿는다. 둘을 섞지 않는다.

## 손 확인 하나 — 260920 이 못 한 것

**실제 로봇을 붙인 한 판에서 되감기를 해 본다.** 260920 은 가짜 로봇으로만 태웠고
보고서가 그 사실을 적어 뒀다. 이번에 실물이 붙으면 그 자리를 메운다.

재생 머리를 실패 시점 앞뒤로 옮기며 **명령 표가 따라가는지 눈으로 본다.**

# 3절 — 논문에 넘길 기록 넷 (코드 아님)

260920 검토에서 나온 것들이다. 전부 한두 줄이고, 지금 안 적으면 초고 쓸 때 잊는다.
`문서/논문Outline_초안_260904.md` 에 메모로 박아 둔다.

**① 액션 층의 상태 어휘는 넷이다.** 태스크는 8상태인데 `ActionStatus` 는
`issued·running·done·failed` 넷이다. §4-1 에서 8상태를 설명할 때 액션 층은 다르다는 것을
같이 적는다. 안 적으면 심사에서 「그래서 상태가 몇 개냐」가 나온다.

**② `seq` 대역이 넷이다.** AI 0.5M · 사람 1M · 대본 1.5M · 라이브 1.75M.
§4-2 에서 「덧붙이기 전용이라 순서가 보존된다」고 쓸 텐데, 순서는 `(atSec, seq)` 로 서고
`seq` 는 같은 시각 안의 결정적 순서라는 것을 한 줄 덧붙인다.

**③ `NO_NODE` 명령은 기록 열에 안 들어간다.** 브리지 기동처럼 순서도에 자리가 없는
명령이다. 판단은 옳지만 **그만큼이 계측 범위 밖**이다 — 브리지 기동 실패가 원인인 임무
실패는 도구가 원리적으로 못 찾는다. §6-2 의 「못 찾는 경우」에 한 줄 더한다.

**④ `adjusted` 는 `nodeId` 가 태스크일 수 있다.** 명령이 없는 태스크의 계획값을 바꾸면
가리킬 `commandId` 가 없어서다. 그래서 **kind 와 nodeId 의 층이 어긋나는 유일한 사건**이다.

판별 규칙을 여기 적어 둔다 — **`nodeId === payload.taskId` 이면 계획값 조정이다.**
격리가 역추적할 때 이 규칙을 안 쓰면 명령 층 그래프에서 그 사건이 붕 뜬다.
**다음 지시서(격리)에 반드시 넘길 항목이다.**
