# 피지컬팀 프로젝트 mk2 — 전체 기능 구현 현황

기준: 각 파트 브랜치의 원격 최신 상태 (2026-09-25 확인)
범위: 기능만 적었다. 성능 수치는 각 파트가 자기 문서에 적은 실측값이다.

| 파트 | 브랜치 | 한 줄 역할 |
|---|---|---|
| 가시화 + 임무 생성 | `khw_VZ` | 말로 임무를 내리고, 실행을 한 화면에서 보고, 되감는다 |
| 하드웨어 | `HW` | 로봇·센서·액추에이터를 라즈베리파이 말단 노드로 묶어 명령을 실행하고 상태·영상을 낸다 |
| 백엔드 (+ 360° 카메라) | `ldg_BE`, `360camera_work` | 데이터를 성격별로 모아 저장·중계·관측한다. 360° 카메라로 장애물을 트윈에 반영한다 |
| AI | `jny_AI` | 영상에서 대상을 탐지하고 위험을 판단해 로봇이 갈 경로 값을 낸다 |

## 1. 시스템 전체 구조

### 1.1 계층

```
[말단 장치]  Go1 4족 로봇 · X500 드론 · RoboMaster EP · 수위센서 · 수문 · 360° 카메라
     │
[말단 노드]  Raspberry Pi 5 (pi7 · pi1 · pi3)                           ── 하드웨어
     │  안전 루프(systemd 상주) + 증강 기능(K3s)
     │  MQTT 5 (Mosquitto, TCP 1883 / WebSocket 9001)
[구역 엣지]  Mosquitto · MQTT→Kafka 브리지 · OTel Agent · 엣지 Prometheus  ── 백엔드
     │  Tailscale 터널
[중앙 서버]  Kafka · TimescaleDB · MySQL · Prometheus/Loki/Tempo · Grafana · WS 게이트웨이
     │                                        │
[AI 인지]  탐지 · 위험 판단 ── AI           [360° 인지]  Pro2 → YOLO-World → 3D 위치 ── 백엔드
     │
[사용자]  가시화 웹(노드 캔버스 · 음성 → 임무 · 되감기) ── 가시화
          Unity 디지털 트윈
```

### 1.2 세 평면

데이터 성격에 따라 채널이 정해진다.

| 평면 | 싣는 것 | 수단 |
|---|---|---|
| 업무 | 명령, 상태, 하트비트 | MQTT 5 (말단↔엣지), Kafka (엣지↔서버) |
| 관측 | 지표, 트레이스, 로그 | OpenTelemetry → Prometheus / Tempo / Loki |
| 미디어 | 영상 | 백엔드 WebSocket `/media`. 영상 픽셀은 MQTT에 싣지 않는다 |

### 1.3 공통 규약

- **물리 명령**
  - 장비마다 토픽 두 개: `terminal/<device-id>/downlink`(명령), `terminal/<device-id>/uplink`(응답)
  - 형식: Protobuf `PhysicalCommandEnvelope`. 한 봉투에 명령 · 수락 · 상태 · 결과 · 취소 · Capability 중 하나를 담는다.
  - 상태 흐름: ACCEPTED → EXECUTING → (CANCELING) → 종료
  - 규칙
    - 같은 id로 다시 보내면 한 번만 실행된다(멱등).
    - deadline이 지난 명령은 거부한다.
    - 취소가 실행보다 우선한다.
    - 장비가 선언하지 않은 action은 `UNIMPLEMENTED`로 거부한다.
  - 장비는 자기가 할 수 있는 action을 Capability로 먼저 밝힌다.
- **상태**: JSON, 토픽 `{zone}/{entity_type}/{id}/{status|state|heartbeat}`
  - `status`는 retained이고, 연결이 끊기면 LWT로 알린다.
  - `state`는 Go1이 임무 중일 때 20Hz로 발행한다.
  - `heartbeat`는 5초 주기이고, 15초가 지나면 stale로 판정한다.
- **정지(`abort`)**: 거부하지 않고, 멱등이며, 다른 어떤 처리보다 먼저 한다.
- **공통 헤더**: 백엔드가 JSON Schema로 정의한다(`contracts/common/`). sequence_id, ms 단위 시각, session_id, frame_ref가 들어간다.

### 1.4 장비

| 장비 | id | 붙는 노드 | 기능 상태 |
|---|---|---|---|
| Unitree Go1 Edu | `go1-001` | pi7 | 구동, 임무 수행, 카메라 5대 영상 |
| 드론 X500 v2 (PX4) | `x500-001` | pi3 | 연결과 Capability 확인. 보기 전용 |
| DJI RoboMaster EP | `ep-001`(제안) | pi1 | HW 링크 구현. 가시화 연동 규약은 초안 |

| 수위 센서 / 수문 | `wl-001` / `gate-01` | — | 가짜 센서와 모의 액추에이터로만 동작 |

## 2. 가시화 + 임무 생성 (`khw_VZ`)

### 2.1 개요
배포된 장비·임무 상태가 화면에 저절로 맞춰진다. 화면은 노드를 이어 붙여 구성하거나, 음성 지시를 로컬 LLM이 분해해서 자동으로 만든다.
사용자는 세 층이다: 개발자, 운영자, 결심자. 더블클릭할 때마다 한 층씩 내려가며 근거를 볼 수 있다.

기술 스택
- 웹: React 19, TypeScript, Vite, mqtt.js, protobufjs
- 게이트웨이: Node
- 음성 인식: faster-whisper `large-v3-turbo`
- 임무 생성: llama.cpp + Qwen3 8B/4B · EXAONE 3.5 7.8B. GBNF 문법으로 출력 형식을 강제한다. 전부 로컬에서 돌린다.
- 디지털 트윈: Unity ↔ Pyjevsim

### 2.2 기능

| 기능 | 내용 |
|---|---|
| 노드 캔버스 | 임무를 마일스톤 → 태스크 → 액션 아이템의 3계층 그래프로 그린다. 노드 종류는 관측·판정·구동·검증·보고 다섯 가지다. 합류와 되돌아가는 흐름도 표현한다. |
| 뷰 노드 | 장치·위험, 제어, 지표, 영상 뷰를 태스크에 연결하면, 그 태스크의 장비·구역·시간이 곧 조회 범위가 된다. |
| 발화 → 임무 생성 | 음성 → 텍스트 → LLM이 장비 목록과 장소 정보를 보고 임무 그래프를 만든다 → 스키마로 검증한다 → **사람이 승인해야** 실행할 수 있다. 승인과 「시작」은 따로 누른다. "1m 앞으로" 같은 정량 명령도 해석한다. |
| 실물 장비 제어 | Protobuf로 명령을 인코딩해 보내고, 명령마다 진행 상태를 추적한다. 정지·일시정지 버튼이 있다. 대상 장비는 장비가 밝힌 Capability와 id로 고른다. 여러 브로커(여러 로봇)에 동시에 붙는다. |
| 문 찾기 | Go1이 8방향으로 회전하며 촬영하게 하고, AI 탐지 결과를 받아 영상·근거·2D 맵 뷰에 채운다. 산출된 경로로만 이동한다. |
| 자율주행 보기 | 노드의 주행 상태(nav_state)를 구독해 보여 준다. |
| 장비 카드 | Go1과 드론의 상태를 카드와 표로 보여 준다. |
| 영상 수신 | 백엔드 `/media`로 JPEG와 H.264를 받아 브라우저에서 디코드한다(WebCodecs). |
| 기록과 되감기 | 지우지 않는 실행 기록에서 임의 시점의 3계층 상태를 다시 실행하지 않고 복원한다. 로봇 명령과 응답도 같은 기록에 들어간다. 임무 이력은 파일로 저장한다. |
| 연결 관리 | 게이트웨이, 음성 인식, 브로커, 탐지, 미디어 주소를 실행 중에 바꾼다. |
| 자체 관측 | 화면 자신의 지표를 60초마다 집계한다. |
| 한/영 전환 | 화면 전체를 한국어·영어로 바꾼다. |
| 모의 모드 | 모의 게이트웨이와 대본 6편으로 장비 없이도 전체 흐름을 돌린다. |

데이터: 장소 54곳과 인접 관계 61개(Unity 맵에서 추출), 장비 10건, JSON Schema 14종(임무·마일스톤·태스크·액션 아이템·실행 기록 등)

### 2.3 성능

| 항목 | 결과 |
|---|---|
| 실물 Go1 임무 완주 | 13판. 한 판에 쌓이는 기록은 중앙값 75건 |
| 명령 인코딩 크기 | ping 31B, scan_mission 79B (HW 측정값과 일치) |
| 드론 추가 | 공통 코드 수정 0줄, HW 어댑터 2파일 |
| 임무 생성 (Qwen3 8B + 문법 강제) | 스키마 적합 100%, 중앙 7.5초. 문법 없이 돌리면 45%, 38.8초 |
| 없는 장비 지어내기 | 장비 목록을 넣어 주면 20건 → 0건 |
| GPU 메모리 | LLM 8B와 음성 인식을 함께 올려 8.1/12GB (RTX 3060) |
| 영상 표시 | 첫 그림까지 215ms, 900장 파싱에 11ms |

### 2.4 아직 안 된 기능
- 브라우저 OTel 지표 발행
- 백엔드 실서버 `/state`·`/media` 접속. 코드는 준비됐고, 서버 접속만 남았다.
- 영상이 끊겼다 이어질 때 「재개 대기」 표시
- 로봇 N대 임무 배정, 결함 주입, 격리 집합
- 장치 규약 미결 사항: 좌표계, 카메라·센서·액추에이터 필드, 문자열 파라미터, 인증·TLS

## 3. 하드웨어 (`HW`)

### 3.1 개요
- 라즈베리파이 5 말단 노드가 센서, 로봇, 액추에이터 세 종류를 맡는다.
- **2층 구조**다.
  - 안전 루프(계측, 임계 판정, 주기 전환, 두절 버퍼)는 systemd에 상주한다.
  - 증강 기능(AI·분석)은 K3s로 배포한다.
  - 그래서 제어평면이 끊겨도 안전 루프는 계속 돈다.
- pi7은 Go1 내부망과 외부망을 잇는 유일한 지점이고, MQTT 브로커도 겸한다.

기술 스택: Python, C++(Unitree SDK), MQTT 5, Protobuf, OpenTelemetry, K3s, Docker, systemd, ffmpeg/GStreamer

### 3.2 기능

| 기능 | 내용 |
|---|---|
| 공통 노드 | 연결 알림(Birth/LWT), 하트비트 5초, 공통 봉투, OTLP 지표, 명령 trace |
| 두절 버퍼 | 통신이 끊기면 버퍼에 쌓았다가 다시 보낸다. 이산 사건은 전부 보관하고, 연속값은 다운샘플한다. |
| 명령 서버 | 물리 명령 규약의 말단 서버다. 멱등, deadline, 취소 우선, 미선언 action 거부를 지킨다. |
| Go1 상태 읽기 | Go1 내부 상태 메시지를 역공학해 자세, 12관절, 높이, 위치·속도, 배터리를 읽는다. |
| Go1 구동 | C++로 HighCmd를 보낸다. 안전장치는 세 겹이다: 속도 상한, 입력이 0.4초 없으면 자동 정지, 비상정지. |
| 미션 | `scan_mission`(45°씩 8번 회전하며 촬영, 단계마다 ACK), `move_forward`, `abort`(실행 중인 것을 전부 멈춤) |
| 영상 | Go1 카메라 5대의 H.264를 변환 없이 중계한다. 카메라가 멈추면 워치독이 자동 복구한다. 정면 촬영 세션을 만들어 업로드한다. |
| Unity 트윈 연동 | 로봇 상태를 Unity에 중계하고, Unity에서 오는 조작·경로를 받는다. 여러 로봇을 `(노드, 기종, 로봇 id)`로 구분한다. |
| 기종 전환 | 환경변수 하나(`go1 \| ep \| sim`)로 Go1, RoboMaster EP, 시뮬레이터를 바꾼다. 붙어 있는 로봇만 자동으로 기동한다. |
| 센서 노드 | 평시 60초 주기로 보내고, 임계를 넘거나 급변하면 즉시 보낸다. 이벤트 모드에서는 1Hz로 보낸다. |
| 액추에이터 노드 | 상태 5종, ACK 전 명령 거부, 안전 잠금 (모의 장치) |
| 배포 | systemd 유닛 약 20개, udev 규칙, K3s 매니페스트, 프로비저닝 스크립트 |

### 3.3 성능

| 항목 | 결과 |
|---|---|
| 영상 glass-to-glass 지연 | 0.3~0.4초 |
| 파이 내부 영상 처리 지연 | 0.1ms (무변환 중계). CPU 0.05코어 |
| Go1 카메라 | 5대, 464×400 29fps, 대당 0.55Mbps |
| 로봇 상태 주기 | 임무 중 19.9Hz / 대기 0.2Hz |
| 시각 동기 오차 | 77µs |
| 두절 버퍼 | 63초 두절 시 1,257건을 64건으로 줄여 재전송(95% 감축). 이산 사건은 전량 재전송 |
| 8방향 회전 | 누적 359.2°, 오차 0.8° |
| 경로 추종 (시뮬) | 최종 오차 0.03m / 7° |
| 다중 로봇 트윈 중계 | 패킷 2,952개, 버림 0 |

### 3.4 아직 안 된 기능
- 실물 센서·액추에이터 (지금은 모의 장치)
- 고정 CCTV, 온디바이스 AI, TLS
- 문자열 파라미터 명령: 지금 규약의 파라미터는 숫자만 받는다.

## 4. 백엔드 (`ldg_BE`)

### 4.1 개요
엣지-클라우드 관측 백엔드다. 말단·엣지·AI에서 오는 데이터를 업무·관측·영상으로 나눠 저장하고 중계한다. 파트 경계는 JSON Schema로 정한다. MQTT, Kafka, OTel 같은 구현 기술은 바꿔 끼울 수 있게 두었다.

기술 스택: Python, Kafka, TimescaleDB, MySQL, OpenTelemetry(Prometheus/Loki/Tempo), Grafana, WebSocket, Tailscale, Docker Compose, systemd

### 4.2 기능

| 기능 | 내용 |
|---|---|
| 수집 | MQTT 상태·하트비트를 구독해 공통 헤더를 검증하고 Kafka 토픽 3개로 넘긴다. 검증에 실패한 메시지는 격리한다. |
| 계측 저장 | TimescaleDB에 저장한다. 시간축은 발행 시각이고, 재소비 중복은 흡수한다. 결측 구간을 찾는 SQL이 있다. |
| 관계형 저장 | MySQL에 장비 레지스트리(선언과 관측 두 축), 감사 로그, 임무 이벤트를 둔다. 감사 로그와 임무 이벤트는 DB 권한으로 추가만 허용한다. |
| 관측 | OTel Collector가 지표는 Prometheus로, 트레이스는 Tempo로, 로그는 Loki로 나눠 보낸다. 백엔드 자기 지표 9종, 업무 값 지표 12종을 낸다. 엣지와 서버의 2계층 페더레이션을 갖췄다. |
| 상태 중계 | WebSocket `/state`로 실시간 상태를 화면에 푸시한다. 가시화 계약 형식으로 바꿔 주는 어댑터가 있다. |
| 영상 중계 | WebSocket `/media`. 원래 코덱을 그대로 끝까지 보내고, 서버는 헤더만 읽는다. 대역이 부족하면 GOP 단위로 오래된 프레임부터 버리고, 다음 키프레임에서 다시 이어 준다. 토큰으로 인증한다. |
| 촬영본 저장 | HTTP PUT `/capture`. 매니페스트를 먼저 받고 아카이브를 받는다. 파일은 파일시스템에, 메타데이터는 MySQL에 둔다. 같은 촬영본을 다시 보내면 한 번만 저장한다. |
| 입력 방어 | 토큰 없음·불일치, 같은 소스 중복 접속, 8MB 초과 프레임, 느린 뷰어를 차단하거나 격리한다. |

### 4.3 성능

| 항목 | 결과 |
|---|---|
| 수집 → 저장 → 화면 푸시 | 전 구간 약 9ms |
| 엣지 ↔ 서버 터널 | 3ms (직접 연결) |
| 영상 중계 | 3,836장, 드롭 0 |
| 뷰어 지연 | p50 7ms, p90 9ms |
| 저대역(500kbit) | 끊긴 곳 19개가 전부 키프레임에서 다시 이어짐 |

### 4.4 아직 안 된 기능
- **가용성 판정기**: 하트비트·LWT와 Prometheus를 종합해 장비 상태를 판정하고 제어 잠금을 낸다.
- **명령 상관·감사·권한**: command_id, RBAC, WSS
- **디지털 트윈 통합**: 여러 구역의 트윈을 종합한다.
- 가시화용 OTel 수신 포트 개방

## 5. 360° 카메라 (`360camera_work`, 백엔드 파트 소속)

### 5.1 개요
고정된 360° 카메라(Insta360 Pro2)로 공간을 보고, 장애물의 3D 위치를 Unity 디지털 트윈에 큐브로 실시간 반영한다. 로봇 시야의 사각지대를 메우는 인프라 센서다.

### 5.2 처리 흐름
1. Pro2가 카메라 안에서 360° 영상을 스티칭해 RTMP로 내보낸다(3840×1920).
2. PC가 최신 프레임만 골라 JPEG로 서버에 보낸다.
3. 서버(RTX A6000)가 영상을 90° 슬라이스로 자른다.
4. YOLO-World(59개 클래스)로 물체를 검출한다.
5. 박스 아랫변을 지나는 광선이 바닥평면과 만나는 점으로 3D 위치를 계산한다. 깊이 모델은 쓰지 않는다.
6. PC가 UDP 5010으로 Unity에 보낸다. Unity는 장애물 큐브를 갱신한다.

### 5.3 성능

| 항목 | 결과 |
|---|---|
| 종단 지연 | 약 0.5초 (최악 1.3초). 이전 사진 방식보다 150배 이상 빠름 |
| Unity 갱신 주기 | 0.44초 (2.29Hz) |
| 유실률 | 0.2% |
| 좌표 오차 | 9.6cm (보정 후) |

### 5.4 아직 안 된 기능
- Go1 로봇 자체를 검출하는지 확인
- 스트림이 끊겼을 때 자동 재연결
- 세 슬라이스 통합, 방향(yaw) 자동 산출, 검출 스무딩

## 6. AI (`jny_AI`)

### 6.1 개요
Physical AI 실행 프레임워크다. 센서·모델·연산장치·전송기술이 바뀌어도 핵심 로직을 고치지 않고 기능을 확장·교체·축소한다. 탐지·추적·위험 판단을 맡고, 물리 명령 규약의 원안을 정의했다.

기술 스택: Python, OpenCV, PyTorch/ONNX Runtime, YOLO-World, GroundingDINO, FastSAM, CLIP, UniDepth, MQTT, Kafka, OTel, K3s

### 6.2 기능

| 기능 | 내용 |
|---|---|
| 기능 조립 | 기능을 Capability · Provider · Registry · Selector로 조립한다. 호환성과 최소 자원을 기준으로 모델과 장치를 고르고, 자원이 부족하면 단계적으로 축소 운용한다. |
| 인지 | 탐지, 추적, 여러 소스 연계, 미리 정하지 않은 대상 탐지(open-vocabulary), 미확인 객체 판정 |
| 위험·안전 | 위험 상태 FSM, 위험 점수, 경로 평가. 네트워크가 끊겨도 로컬에서 안전 판단을 하고, 입력이 사라지면 `SAFE_STOP`으로 전환한다. |
| 실행 관리 | 모델 배포, 수명주기와 롤백, 폐쇄망 배포, 물리 명령 게이트웨이 |
| 문 찾기 | Go1의 8방향 스캔 영상을 MQTT로 받는다. 멈춘 카메라가 보낸 중복 프레임을 걸러 내고 문을 탐지한다. 거리를 추정해 회전각(`turn_deg`)과 전진 거리(`forward_distance_m`)를 계산하는데, 문 앞 80cm에서 멈추도록 계산한다. 결과는 HTTP API로 제공한다. |
| 시뮬레이터 | DEVS 기반. 장비 핫플러그, 자원 축소, 장애 격리, 링크 지연, 문 탐지 융합 시나리오 |
| 상태 UI | 프레임워크 상태를 한/영으로 보여 준다. |

### 6.3 성능 (모델별 프레임당 지연)

| 모델 | 지연 |
|---|---|
| SSD (CPU) | 50~57ms |
| TinyYOLO | 60~67ms |
| OWL-ViT | 약 1초 |
| 조건부 escalation | 약 700ms |

### 6.4 아직 안 된 기능
- 실제 GPU 기기에서 탐지·깊이 모델을 끝까지 돌리는 검증. 지금까지는 입출력 계층만 확인했다.
- 실제 말단 장비에서의 성능·발열 측정

## 7. 네 파트 통합 동작

### 7.1 통합 구성도

```
                       ┌─────────────────────────── 가시화 웹 ───────────────────────────┐
  사용자 음성 ──▶ STT ──▶ LLM 임무 생성 ──▶ 검증 ──▶ [승인] ──▶ [시작]                     │
                       │   노드 캔버스 · 뷰 노드 · 장비 카드 · 영상 · 기록/되감기            │
                       └──┬───────────────▲──────────────▲───────────────▲───────────────┘
            ① 명령(Protobuf)│   ⑤ 응답·상태  │   ⑥ 상태·영상  │   ④ 탐지 결과    │
                          ▼               │  (/state,/media)│   (HTTP)        │
   ┌──────────── 하드웨어 말단 노드 (pi7) ────────────┐   ┌──── 백엔드 ────┐   ┌── AI ──┐
   │ MQTT 브로커 · 명령 서버 · 안전 루프              │   │ 엣지 브리지     │   │ 문 탐지 │
   │ Go1 구동 / 스캔 촬영 / 상태 20Hz / 영상 H.264    │─▶ │ Kafka · 저장    │   │ 거리 추정│
   └──────┬──────────────┬──────────────┬─────────┘   │ 관측 · 영상 중계 │   │ 경로 값 │
          │ ② 구동       │ ③ 스캔 프레임  │ 트윈 상태      │ 촬영본 저장     │   └───▲───┘
          ▼              └───────────────┼─────────────┼────────────────┼───────┘
       Go1 로봇                           ▼             └────────────────┘
                                  Unity 디지털 트윈 ◀── 360° 카메라 장애물 위치(백엔드)
```

### 7.2 대표 시나리오: 「문 쪽으로 가」

| 단계 | 담당 | 동작 |
|---|---|---|
| 1. 지시 | 가시화 | 운영자가 "문 쪽으로 가"라고 말한다. 음성 인식이 텍스트로 바꾼다. |
| 2. 임무 생성 | 가시화 | 로컬 LLM이 장비 목록·장소 정보를 보고 임무 그래프를 만든다: 둘러보기(8방향 촬영) → 문 탐지 → 이동 → 도착 확인. 스키마로 검증한 뒤 캔버스에 그린다. |
| 3. 승인·시작 | 가시화 | 운영자가 그래프를 확인하고 승인한 뒤, 「시작」을 따로 누른다. 그 전에는 아무것도 실행되지 않는다. |
| 4. 명령 전달 | 가시화 → HW | 가시화가 `scan_mission`을 Protobuf로 인코딩해 `terminal/go1-001/downlink`로 보낸다. 대상은 Go1이 밝힌 Capability를 보고 고른다. |
| 5. 명령 접수 | HW | 말단 노드가 멱등·deadline을 확인하고 ACCEPTED를 `uplink`로 돌려준다. |
| 6. 스캔 실행 | HW | Go1이 45°씩 8번 회전하며 정면 카메라로 촬영한다. 단계마다 진행 상태를 uplink로 보내고, 로봇 상태는 20Hz로 발행한다. 스캔 프레임은 AI로, 촬영 세션은 백엔드 저장소로 간다. |
| 7. 탐지 | AI | 8장의 프레임에서 문을 찾는다. 거리를 추정해 회전각과 전진 거리를 계산한다(문 앞 80cm 정지). |
| 8. 결과 표시 | AI → 가시화 | 가시화가 탐지 결과를 받아 영상·근거·2D 맵 뷰를 채운다. 운영자는 왜 그 문을 골랐는지 근거를 본다. |
| 9. 이동 | 가시화 → HW | 산출된 값으로 회전·전진 명령을 보낸다. HW가 Go1을 구동하고, 완료되면 결과(SUCCEEDED)를 보낸다. |
| 10. 동시 관찰 | 백엔드·360°·Unity | 상태·영상이 백엔드를 거쳐 저장·중계되고 관측 지표로 남는다. Unity 트윈에서는 로봇 위치와 360° 카메라가 본 장애물이 함께 움직인다. |
| 11. 기록·되감기 | 가시화 (+ 백엔드) | 발화부터 명령·응답까지 전 과정이 실행 기록에 남는다. 시간 슬라이더로 아무 시점이나 되돌려 볼 수 있다. 백엔드에는 감사 로그와 임무 이벤트로 남는다. |

### 7.3 이상 상황 처리

| 상황 | 동작 |
|---|---|
| 운영자가 정지를 누름 | 가시화가 `abort`를 보낸다. HW는 거부 없이 가장 먼저 처리해 실행 중인 모든 동작을 멈춘다. |
| 가시화와 로봇 사이 명령 입력이 끊김 | HW가 무입력 0.4초에 Go1을 자동 정지시킨다. |
| 말단과 엣지 사이 네트워크 두절 | HW의 안전 루프는 계속 돈다. 데이터는 버퍼에 쌓았다가 복구되면 다시 보낸다. AI는 로컬 안전 판단으로 넘어가고, 입력이 없으면 `SAFE_STOP`한다. |
| 노드가 죽음 | MQTT LWT로 `status`가 바뀐다. 하트비트가 15초 끊기면 stale로 표시된다. 가시화 장비 카드와 백엔드 레지스트리에 반영된다. |
| 영상 대역 부족 | 백엔드가 오래된 프레임을 GOP 단위로 버린다. 영상은 다음 키프레임에서 다시 이어진다. |
| 카메라 멈춤 | HW 워치독이 자동 복구한다. AI는 중복 프레임을 걸러 낸다. |
| 장비가 할 수 없는 명령 | HW가 `UNIMPLEMENTED`로 거부한다. 가시화는 Capability에 없는 명령은 애초에 만들지 않는다. |

### 7.4 새 장비를 붙일 때
HW가 새 장비용 어댑터만 추가하면 된다. 노드가 Capability를 밝히면 가시화는 연결 관리에 브로커 주소 하나를 넣는 것만으로 장비 카드와 명령 대상을 자동으로 만든다. 백엔드는 공통 헤더만 맞으면 그대로 수집·저장한다.
드론 X500이 이렇게 붙었다. 공통 코드 수정은 0줄이었다.

### 7.5 설계 목표와 현재 연결의 차이

설계상 모든 상태와 영상은 백엔드를 거쳐 화면으로 간다. 지금 실물로 돌아가는 연결은 다음과 같다.

| 구간 | 설계 목표 | 현재 |
|---|---|---|
| 가시화 ↔ HW (명령·상태) | 백엔드를 거친 명령 일원화 | 가시화가 pi7 브로커에 직접 붙어 실물 Go1을 제어한다(13판 완주). 드론도 직접 연결했다. |
| 가시화 ↔ AI (탐지) | 탐지 결과 규격으로 연동 | HTTP API로 연동했다. AI 모델 본체는 실기 검증 전이다. |
| HW → Unity 트윈 | 백엔드 트윈 통합 | HW가 Unity로 직접 중계한다(다중 로봇 포함). |
| 360° 카메라 → Unity | 백엔드 트윈 통합 | UDP로 Unity에 직접 반영한다. |
| HW → 백엔드 | 전체 상태·영상 수집 | 센서 노드 데이터로 파이프라인을 관통했다. 실물 로봇 영상은 아직 백엔드를 거치지 않았다. |
| 백엔드 → 가시화 | `/state`·`/media` | 양쪽 구현은 끝났고, 실서버 접속이 남았다. |
| AI ↔ 백엔드 | 탐지 결과 저장, 가용성 연동 | AI는 모의 백엔드로 동작한다. 백엔드 가용성 판정기가 들어오면 교체한다. |
| 센서 → 수문 | 수위 임계 → 위험 판단 → 수문 명령 | 센서와 수문 모두 모의 장치로만 동작한다. |
