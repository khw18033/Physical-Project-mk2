# 하드웨어 쪽에 묻는 것 (가시화 → pi7 · 2026-09-10)

아래를 그대로 하드웨어 담당 AI 에게 붙여 넣으면 된다.

---

## 붙여 넣을 프롬프트

나는 관제 웹(가시화) 쪽을 만들고 있다. `web-integration.md` 와 `mqtt-command.js` 를 받아
붙였고, **오늘 pi7 의 실물 `go1-001` 과 시뮬레이터 `go1-sim` 양쪽에 실제로 명령을 쏴서
재봤다.** 아래는 전부 추측이 아니라 측정값이다. 각 항목에 대해 (a) 의도한 동작이 무엇인지,
(b) 노드를 고칠 것인지 문서를 고칠 것인지, (c) 웹 쪽이 지금 무엇을 가정하고 있어야
하는지를 답해 달라.

측정 환경: `ws://pi7.local:9001/mqtt`, MQTT 5, `terminal/go1-001/{downlink,uplink}`.
장치 상태는 `zoneA/robot/go1-001/status` 기준 `schema_version 1.3`, `fw_version 0.3.0`.

### 1. 구동 브리지 명령이 노드에 없다

`web-integration.md` §4-2 · §4-3 과 `mqtt-command.js` 의 `sdkStart / sdkStop / sdkAuto` 를
그대로 썼는데 거절된다. **실물과 시뮬레이터 둘 다** 같다.

```
ping           수락
diag           수락
abort_mission  수락
abort          수락
scan_mission   수락 (실제로 돌았다)
move_forward   수락
sdk_stop       거절  UNIMPLEMENTED  action not supported
sdk_auto       거절  UNIMPLEMENTED  action not supported
```

`sdk_start` 는 **일부러 안 쏴 봤다** — 성공하면 로봇이 일어서기 때문이다. 위 둘과 같이
안 올라가 있다고 짐작만 하고 있다.

- 이 어휘가 아직 배포 전인가, 아니면 다른 이름으로 올라가 있나?
- 배포 예정이라면 언제쯤인가? 우리는 버튼을 이미 만들어 두고 거절이 오면 「이 노드에는
  구동 명령이 아직 없습니다」로 표시하고 있다. 배포되면 저절로 풀리게 해 뒀다.
- `sdk_start` 도 같은 상태로 보는 것이 맞나?

### 2. `status.sdk` 가 안 실려 온다

§4-3 이 `"sdk": { "ready": true, "autostart": true }` 를 상태 요약에서 읽으라고 했는데,
지금 오는 `status` 봉투에 그 키가 아예 없다. 실제로 받은 것(발췌):

```json
{"schema_version":"1.3","device_status":"fault","robot_mode":"unknown",
 "in_mission":false,"link":"fault","battery_pct":57,
 "registration":{"fw_version":"0.3.0", ...},"media":{...}}
```

- 이것도 1번과 같이 배포 전인가?
- 우리는 `ready` 가 없으면 **「모름」(회색)** 으로 두고 「꺼짐」으로 그리지 않는다.
  §4-3 이 그렇게 하라고 해서 그렇게 했다. 이 해석이 맞나?

### 3. **가장 궁금한 것** — 지금 노드도 이동 명령이 브리지를 자동으로 띄우나?

우리가 하려는 설계는 이렇다. 평시에는 「연결만 된 상태」로 두고, **해당 로봇에 임무가
할당되어 제어 명령이 들어오는 순간 SDK 를 띄워 실제 이동까지 간다.** §4-3 을 읽으면 이미
그것이 기본 동작으로 보인다.

그런데 1번처럼 브리지 명령이 없는 상태에서, **지금 배포된 노드도 그 자동 기동을 하나?**

- 한다면: `sdk_starting` → `sdk_ready` 진행 보고도 지금 나오나? 우리는 그 두 건을 받아
  「로봇이 일어서는 중입니다」를 화면에 띄우게 만들어 뒀다. 아직 실물에서 못 봤다.
- 안 한다면: 이동 명령을 쏘기 전에 사람이 pi7 에서 무엇을 해야 하나?
  (`systemctl start go1-sdk` 인가?)
- 오늘 낮에는 `scan_mission` 이 실제로 돌았고 그때 `link` 는 `ok` 였다. 지금은 `fault` 다.
  **누가 브리지를 올리고 내렸나?** 우리가 쏜 명령 때문인가, 사람이 한 것인가?

### 4. 브리지가 내려가 있을 때의 `link` 를 어떻게 그려야 하나

브리지가 없어 보이는 지금 상태가 이렇다.

```
link: "fault"   device_status: "fault"   robot_mode: "unknown"
```

§3-1 은 `link` 를 「로봇 ↔ 파이」 구간이라고만 적었다. 우리 화면은 지금 이걸 빨간
「로봇 ✕ — 내부 링크 fault」로 그린다.

- **브리지가 평시에 내려가 있는 것이 정상**이라면, 그때의 `fault` 는 고장이 아니라
  「평시」다. 그걸 빨갛게 그리면 발표장에서 멀쩡한 로봇을 고장으로 읽는다.
- 「브리지가 안 떠서 상태를 못 읽는 것」과 「진짜 링크 고장」을 웹이 구별할 방법이 있나?
  없다면 `link` 에 값을 하나 더 주거나 `sdk.ready` 를 먼저 배포해 주면 좋겠다.

### 5. `forward_m: 0` 을 안 지킨다 — **로봇이 스스로 1m 걷는다**

우리 시연은 이렇다. 스캔은 **돌기만** 하고, 로봇이 고른 문 방향에 초록 불이 켜지면
사람이 화면에서 「접근 시작」을 눌러야 그때 이동한다. 그래서 직진을 빼고 보낸다.

```
보낸 것   scan_mission { steps: 8, step_deg: 45, forward_m: 0 }
```

그런데 **오늘 실물에서 세 판 모두** 마지막에 직진이 붙었다.

```
19:31  … door_turn step=1 yaw=-5.20    ack=10/10
       forward   step=1 yaw=-8.50    ack=11/10  note="ok odo=1.00m cmd=0.94m"
       result {"steps":8,"turns_ok":9,"acks":10,"odo_m":1,"forward_m":1,"step_deg":45}

19:34  … forward step=1 yaw=-54.33  ack=21/10  note="ok odo=1.00m cmd=1.86m"
19:40  … forward step=1 yaw=-96.16  ack=31/10  note="ok odo=1.00m cmd=1.41m"
```

시뮬레이터도 같다 (`forward_m: 0` → 결과 `forward_m: 1, odo_m: 1`).

`0` 을 「안 준 값」으로 읽고 기본값 `1.0` 을 쓰는 것으로 보인다. 첫 진행 보고부터
`of: 10` 인 것도 근거다 — §5-2 의 식 `steps + 1 + (forward_m > 0 ? 1 : 0)` 로 10 이 되려면
노드가 **처음부터 직진을 계획에 넣었다**는 뜻이다.

- `forward_m` 이 0 이면 0 으로 읽어 줄 수 있나? (`if forward_m:` 이 아니라
  `if forward_m is not None:` 같은 판정)
- 안 된다면, **직진 없이 스캔만 도는 다른 방법**이 있나? 없으면 우리 시연에서 로봇이
  아무도 안 누른 상태로 1m 전진한다. 지금은 화면에 경고만 띄워 두고 있다.

### 6. `odo` 는 늘 1.00m 인데 `cmd` 는 판마다 다르다

위 세 판의 `note` 를 보면 `odo=1.00m` 는 세 번 다 정확히 같고, `cmd=` 는 0.94 → 1.86 →
1.41 로 다르다. 우리가 보낸 파라미터는 세 판 다 같았다.

- `cmd` 는 무엇인가? 우리가 안 보낸 값이 왜 판마다 달라지나?
- `odo=1.00m` 가 세 번 정확히 같은 것은 실측인가, 아니면 지령값을 그대로 적은 것인가?

### 7. `door_turn` 의 `step` 이 늘 1 이다

§5-3 은 「노드 선택도 탐지 정합도 `step` 에서 유도한다」고 했다. 그런데 `door_turn` 의
`step` 은 **고른 걸음이 아니라 늘 1** 이다.

```
scan_turn  step=8  yaw=-54.76   ← 여덟 걸음이 1~8 로 온다
door_turn  step=1  yaw=-94.16   ← 고른 것은 yaw -99.67 인 7번째 걸음이다
```

그래서 우리는 그 판의 회전 걸음들이 보고한 yaw 와 견주어 가장 가까운 걸음을 고르고 있다
(위 예에서 index 6). 절대 각도를 안 쓰고 같은 판의 값끼리만 견주므로 §5-3 의 기준점 이월
문제는 피한다.

- `door_turn.step` 에 **고른 걸음 번호**를 실어 줄 수 있나? 그러면 각도 견주기가 필요 없다.
- 아니면 `chosen_step` 같은 필드를 따로 하나 주면 좋겠다.

### 8. `ack` 는 명령을 넘어 누적된다 (확인만)

§6 의 알려진 문제와 같은 것으로 보이는데 확인하고 싶다. 한 판에서 `ack` 가 22→31 로 오고,
다음 판은 그 뒤 번호에서 이어진다. `of` 는 10 인데 `ack` 가 31 이라 그대로 띄우면
「31 / 10」이 된다.

우리는 우리가 채운 칸 수를 앞에 두고 로봇의 값을 그 옆에 그대로 붙여 두었다.
노드 쪽에서 임무별로 리셋할 계획이 있나? 있다면 언제 바뀌는지 알려 달라 —
바뀌는 순간 우리 화면 문구를 같이 고쳐야 한다.

### 9. `mqtt-command.js` 의 첫 명령이 응답을 놓친다

받은 클라이언트를 그대로 돌리면 **연결 후 첫 명령만** 응답을 못 받는다. 순서를 바꿔도
첫째가 실패한다.

```
ping 먼저 → ping  CommandTimeout,  diag 성공
diag 먼저 → diag  CommandTimeout,  (다음 것) 성공
```

`run()` 이 곧바로 publish 하는데, `client.on("connect")` 안의 `subscribe` 가 SUBACK 을
받기 전에 로봇의 응답이 지나가서 그런 것으로 보인다. 우리 쪽 클라이언트는 **명령 구독의
SUBACK 을 기다린 뒤에 「연결됨」을 말하도록** 고쳤고, 그 뒤로 연결 직후 곧바로 쏜 ping 이
9ms 에 돌아온다.

배포하는 `mqtt-command.js` 에도 같은 수정을 넣어 두면 다른 팀이 같은 데서 헤매지 않는다.

```js
client.on("connect", () => {
  client.subscribe(`terminal/${device}/uplink`, { qos: 1 }, () => onLink(true))
})
// 그리고 run() 은 onLink(true) 이후에만 publish 하도록
```

### 우리가 이미 처리한 것 (중복으로 고치지 않아도 되는 것)

- `ack` 누적 — 우리 카운트를 앞에 두고 로봇 값을 옆에 그대로 붙인다
- `battery_pct: null` — 0% 로 안 그리고 「모름」으로 둔다
- `link` 가 `ok` 가 아닐 때의 배터리·위치 — 「마지막 수신」을 붙인다
- `Capability` 가 retain 이 아니라 못 받는 것 — 거절 코드(`UNIMPLEMENTED`)를 기억하는
  방식으로 우회한다
- `command_id` 멱등키 — 시각을 섞어 만든다

### 답을 받으면 우리가 할 것

3번과 5번의 답에 따라 시연 순서가 달라진다. 특히 5번이 안 고쳐지면 「접근 시작」 버튼의
뜻이 바뀌므로(첫 걸음이 아니라 두 번째 걸음), 시연 대본을 다시 쓴다.
