# 1. 🔴 시각화 종점에 실시간 구독 경로가 없다

문서 **§7 표 7**이 시각화 소스를 이렇게 정리합니다.

| 데이터 | 저장소 | 시각화 |
|---|---|---|
| 업무 데이터(수위·로봇 상태) | TSDB | Grafana / **관제 화면이 백엔드를 거쳐 TSDB를 읽는다** |
| 관측 지표 | Prometheus | Grafana |
| 로그 · trace | Loki · Tempo | Grafana |
| 명령 책임 기록 | MySQL | 관제 화면이 백엔드를 거쳐 읽는다 |

그리고 본문이 이렇게 못 박습니다.

> **"시각화의 소스는 항상 조회 가능한 저장소이지 전송 층(Kafka, OpenTelemetry)이 아니다."**

## 무엇이 문제인가

**이 표는 전부 조회(pull) 모델입니다.** 그런데 내 화면의 뼈대는 **구독(push) 모델**입니다.

| 내 요구사항 | 전제 |
|---|---|
| `VZ-I-01` 실시간 상태 구독 | WS 게이트웨이가 **밀어준다**. 계약 축 `{entity, node, channel}` |
| `VZ-I-02` 구독 즉시 현재값 1회 | 백엔드 **캐시**가 푸시(`BE-T-06`) |
| `VZ-U-01` 상태 4종 | 상태 3층이 **도달 즉시** 갱신 |
| `VZ-U-02` 트윈 위치 | 임무 중 **50ms** 수신 → 보간 |

**로봇 상태 50ms를 TSDB 조회로 그릴 수는 없습니다.** 초당 20회 폴링은 저장소를 두드리는 짓이고, 그렇다고 폴링 주기를 늦추면 트윈이 끊깁니다. `VZ-I-01`의 100ms 병합은 *"데이터는 전량 받되 화면 반영만 묶는다"* 인데, 이건 **받는 것이 푸시일 때만** 성립합니다.

`BE-T-03`(가시화 클라이언트 실시간 채널 게이트웨이)이 시트에는 멀쩡히 있는데, **이 문서 어디에도 등장하지 않습니다.** §7이 "항상 저장소"라고 단정하면서 그 경로가 지워진 모양이 됐습니다.

## 어긋남이 아니라 누락일 가능성이 큽니다

시트의 `BE-T-03`·`BE-T-06`이 그대로 살아 있으니 **의도적으로 뺀 것이 아니라 이 문서가 전송 도구(MQTT·Kafka·OTLP) 관점으로 쓰여서 클라이언트 채널이 범위 밖으로 빠진 것**으로 보입니다.

다만 **문서에 안 적힌 것은 없는 것과 같아집니다.** 나중에 "화면은 TSDB 읽으면 되잖아"가 나오면 되돌리기 어렵습니다.

> **요청** — §7에 한 줄. *"실시간 상태·명령 결과·계획 진행은 저장소 조회가 아니라 WS 게이트웨이(`BE-T-03`) 구독으로 전달한다. 저장소 조회는 이력·지표·감사용이다."*

# 2. ⚠️ `availability` 판정이 두 평면에서 나온다

문서 **§6-5**가 장치 생사 감지를 넷으로 둡니다.

| 메커니즘 | 평면 | 무엇을 보나 |
|---|---|---|
| MQTT 유언 메시지(LWT) | 업무 | 급사 즉시 |
| 하트비트 타임아웃 | 업무 | 일정 시간 무소식 |
| Prometheus `up` | 관측 | 지표를 내고 있는가 |
| Alertmanager | 관측 | 임계 위반 즉시 경보 |

그리고 이렇게 설명합니다.

> 업무 평면(MQTT)은 **장치가 값과 명령을 주고받을 수 있는지(세션)** 를 보고, 관측 평면(Prometheus)은 **그 노드가 지표를 내고 있는지(응답)** 를 본다. 서로 다른 각도라 이중으로 두어 사각을 없앤다.

**이중으로 두는 것은 맞습니다.** 문제는 내가 받는 `availability`가 **어느 쪽 판정인가**입니다.

내 `VZ-U-01`은 **`availability` 하나**를 받아 상태 4종을 파생시킵니다. 그런데 두 평면의 답이 갈릴 수 있습니다.

| 상황 | 업무 평면 | 관측 평면 |
|---|---|---|
| MQTT 세션은 살아 있는데 지표 발신이 죽음 | online | `up=0` |
| 지표는 나오는데 MQTT 브로커 연결이 끊김 | offline(LWT) | `up=1` |

둘이 다를 때 화면에 뭐라고 표시해야 하는지가 정의되어 있지 않습니다.

> **요청** — `availability`가 **어느 평면의 판정인지**, 두 판정이 갈릴 때 **어느 쪽이 우선인지**. 아니면 두 값을 따로 주고 화면이 구분해 표시할지.
>
> 개인적으로는 **업무 평면 우선**이 맞다고 봅니다 — 관제사가 알아야 하는 건 "이 장치에 명령을 보낼 수 있나"이고, 지표가 안 나오는 것은 그 다음 문제입니다. 다만 **"명령은 가는데 지표가 없다"도 화면에 보여야** 하므로, 상태 3층에 이미 있는 자리(`device_status`)와 겹치지 않는 별도 표기가 필요할 수 있습니다.

# 3. ⚠️ 관제 화면이 관측 지표를 읽는 경로가 표에 없다

§7 표 7에서 **관측 지표(Prometheus)의 시각화가 "Grafana"뿐**입니다. 관제 화면이 없습니다.

그런데 내 요구사항 둘이 여기에 걸립니다.

- **`VZ-I-04` 지표 질의** — 질의 프록시(`BE-Q-01`)로 시계열을 받아 화면에 그린다. 실측 검증도 마쳤습니다(요약 12ms/60점 · 원본 975ms/900점)
- **`VZ-O-04` 자체 관측 지표 발행** — 가시화가 자기 성능 지표를 관측 스택에 **직접 발행**한다. 내가 발행한 걸 내가 못 본다는 게 됩니다

`BE-Q-01`(질의 프록시)이 시트에 있으므로 이것도 **누락으로 보이지만**, 표에 없으면 "관측은 Grafana로 보면 되지"가 됩니다.

> **요청** — 표 7의 관측 지표 행에 *"관제 화면이 질의 프록시(`BE-Q-01`)를 거쳐 읽는다"* 를 추가.

# 4. 🟡 영상 — 구현체 후보가 나왔고, 뷰어 종점은 여전히 공백

**새로 알게 된 것** — §5-9에 *"영상: **Redis 등** 미디어 경로"* 라고 구현체 후보가 등장했습니다.

**여전히 없는 것** — §7 시각화 종점 표에 **영상이 아예 없습니다.** 업무·관측·로그·trace·감사 다섯 줄인데 영상은 빠져 있습니다.

정리하면 영상 경로는 이렇게 조각나 있습니다.

| 구간 | 상태 |
|---|---|
| 카메라 → 엣지 | `HW-R-07`·`HW-S-06` — 있음 |
| 엣지 → 미디어 경로 | **Redis 등** (이 문서, 신규) |
| 원본 규격 흡수 | `AI-C-08` GStreamer 어댑터 — **경로가 AI 모듈까지** |
| 미디어가 별도 평면 | `AI-C-14` — 있음 |
| **미디어 경로 → 뷰어** | **없음** |

질문이 또 한 번 좁혀집니다 — 이제 *"미디어 경로가 뭐냐"* 도 답이 나왔으니, 남은 건 **"그 미디어 경로에서 뷰어가 재생 가능한 규격으로 나가는 분기를 누가 만드나"** 하나입니다.

# 5. ✅ 확인된 것 — 내 근거가 단단해졌다

## 5-1. 명령 경로 확정 (§6-6)

서버→엣지 **Kafka**, 엣지→말단 **MQTT**. A안 채택이고 근거가 셋입니다 — 채널을 늘리지 않음 · 사설 IP 엣지 접근 우회 · 순서 보장.

**내 `VZ-O-01`·`VZ-O-02`의 전제가 그대로 유효**합니다. 명령을 추상 action으로 백엔드에 넘기고, 백엔드가 번역해 내리는 구조가 문서에서 확인됩니다.

## 5-2. 상관키 발급 시점 (§5-6)

> 업무·책임 추적(`command_id`): **백엔드가 명령을 만들 때 발급**해 중앙 감사 저장소(MySQL)에 기록한다.

내 두 키 구조(`client_request_id` → `command_id`)와 일치합니다.

> ⚠️ 다만 **ACK에 `client_request_id`를 에코하는지는 이 문서에도 없습니다.** 기존 미결 그대로 유지.

## 5-3. 페더레이션 15초 · 요약만 (§6-4)

> 원본은 엣지에 남고 백엔드에는 구역 요약만 올라온다. 부하가 **장치 수가 아니라 구역 수에 비례**한다.

`VZ-I-04`·`VZ-C-03`의 근거가 그대로입니다. **다시 계산할 것 없습니다.**

## 5-4. 요약하지 않는 것 (§6-3, §6-5)

log·trace는 원본 전달(요약하면 의미가 깨짐), 장치 생사·치명 오류는 **요약 대상에서 빼고 개별 전송**. 내 `VZ-I-10`(AI 실패 이벤트를 지표 경로가 아닌 별도 푸시로)의 논리와 같은 방향입니다.

# 6. 📌 영향 재검토 — 명령 만료 시각

명령 왕복이 생각보다 깁니다.

```
화면 → 백엔드 → Kafka(10~50ms) → 엣지 → 브릿지 전환 → MQTT → 장치
                                                              ↓
화면 ← 백엔드 ← Kafka ← 엣지 ← MQTT ← ACK
```

문서가 Kafka 지연을 **10~50ms**로 밝히고 *"발신에서 디스크 기록·복제, 수신까지의 전체 파이프라인 시간"* 이라고 설명합니다. 여기에 브릿지 전환 한 겹이 더 붙고, 왕복이니 두 번 겪습니다.

**내 목 서버는 ACK를 즉시 주도록 되어 있습니다.** 실제 경로에서는 100ms 안팎이 정상일 수 있고, 그러면 내 `expires_at` 기본값과 "ACK 없이 만료" 판정 임계가 너무 빡빡할 수 있습니다.

→ 지금 고칠 것은 아니지만, **목 서버에 왕복 지연을 주입하는 옵션**을 넣어 두면 실제 백엔드를 붙이기 전에 확인할 수 있습니다. `ack-late` 시나리오를 확장하면 됩니다.

# 8. 대규에게 보낼 요약

> 전송 아키텍처 문서 잘 봤어. 전송 도구 결정은 내 쪽 전제랑 다 맞아. 세 가지만 확인해줘.
>
> **1. §7 시각화 종점에 실시간 구독 경로가 빠진 것 같아.** 표가 전부 "저장소를 조회해서 그린다"인데, 내 화면의 뼈대는 WS 게이트웨이(`BE-T-03`) **구독 푸시**야. 로봇 상태 50ms를 TSDB 조회로 그릴 수는 없어. 시트에는 `BE-T-03`·`BE-T-06`이 멀쩡히 있으니 이 문서가 전송 도구 관점이라 빠진 걸로 보이는데, **문서에 안 적히면 없는 것과 같아져서** 한 줄 넣어주면 좋겠어 — "실시간 상태·명령 결과·계획 진행은 WS 게이트웨이 구독으로 전달하고, 저장소 조회는 이력·지표·감사용이다."
>
> **2. `availability`가 어느 평면 판정이야?** §6-5에서 업무 평면(MQTT 세션)과 관측 평면(Prometheus `up`)이 서로 다른 각도로 본다고 했잖아. 근데 내 화면은 `availability` **하나**를 받아서 상태 4종을 파생시켜. 둘이 갈릴 때 — MQTT는 살아 있는데 지표가 죽었다든가 — 어느 쪽을 주는 거야? 내 생각엔 **업무 평면 우선**이 맞을 것 같아. 관제사가 알아야 하는 건 "명령을 보낼 수 있나"니까. 다만 "명령은 가는데 지표가 없다"도 화면에 보여야 해서, 그건 따로 표기가 필요할 수도 있어.
>
> **3. 표 7 관측 지표 행에 관제 화면이 없어.** Grafana만 있는데, 내 `VZ-I-04`가 질의 프록시(`BE-Q-01`)로 지표를 받아 그리고 있고 `VZ-O-04`로 내 성능 지표를 발행도 해. 한 줄 추가해주면 좋겠어.
>
> 그리고 영상은 §5-9에서 "Redis 등 미디어 경로"라고 구현체가 나왔던데, §7 시각화 종점 표에는 영상이 없더라. **미디어 경로에서 뷰어로 나가는 분기**가 여전히 비어 있어 — 이건 3자 회의 안건으로 남겨둘게.
