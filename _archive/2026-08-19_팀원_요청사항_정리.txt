가시화 파트가 팀원들에게 부탁하는 것들  (쉬운 말 정리본)
====================================================================
작성   : 김현우 (가시화 담당)
날짜   : 2026-08-19
근거   : 요구사항정의서 v0.2 / 가시화 담당 요구사항 정의서 v2 /
         AI 담당 요구사항 정의서 / 하드웨어 담당 요구사항 정의서 3 /
         260818 회의록

이 문서는 "가시화 담당 요구사항 정의서"에 있는 요청 항목(I·D·H·A 번호)을
전문 용어 없이 다시 쓴 것입니다. 정확한 필드 이름과 스키마는 원문 문서를
보시면 되고, 이 문서는 "왜 이게 필요한지"를 빠르게 이해하려고 만든 겁니다.

가시화 파트가 하는 일을 한 줄로 말하면 이렇습니다.
  여러분이 만든 데이터를 화면에 그리고, 사용자가 화면에서 누른 명령을
  다시 여러분 쪽으로 내보냅니다. 데이터를 모으거나 저장하지는 않습니다.

--------------------------------------------------------------------
0. 급한 순서만 먼저 (시간 없으면 이것만)
--------------------------------------------------------------------

[1순위 — 이게 없으면 아예 못 만듭니다]
  · 대규에게 : 제어 명령을 어느 길로 보낼지 정해주세요.        (D-1)
  · 대규에게 : 데이터에 붙는 이름표 규칙을 맞춰주세요.          (I-2)
  · 병현에게 : 로봇에도 "어디에 설치됐는지" 값을 넣어주세요.    (H-1)
  · 병현에게 : 좌표가 어디를 기준으로 한 값인지 알려주세요.     (H-2)

[2순위 — 없으면 화면 품질이 크게 떨어집니다]
  · 대규에게 : 브라우저가 실시간 데이터를 받는 길을 정해주세요. (D-2, I-9)
  · 나영에게 : 탐지 결과에 "어느 화면(프레임)을 본 건지" 넣어주세요. (A-1)
  · 병현에게 : 화면을 새로 켰을 때도 마지막 상태가 보이게 해주세요. (H-3)

[3순위 — 나중에 정해도 되지만 잊으면 곤란합니다]
  · 병현에게 : 영상 주소를 브라우저가 재생할 수 있는 형식으로. (H-4)
  · 나영에게 : 좌표 기준·수치 단위 같은 것들 (A-2)
  · 세 명 모두 : 식별자(ID) 체계 한자리에서 통일 (5장)


====================================================================
1. 이대규 — 관측 스택(OTel/Prometheus/Grafana) 담당
====================================================================

--------------------------------------------------------------------
1-1. 제일 급한 것 : 제어 명령을 어느 길로 보낼까요?  (D-1, O-1a, O-1b)
--------------------------------------------------------------------
무슨 말이냐면
  화면에서 사용자가 "게이트 열어" 버튼을 누르면, 그 명령이 실제 장비까지
  가야 합니다. 그런데 지금 그 길이 정해져 있지 않습니다.

제 제안
  (1) 명령 자체는 MQTT로 보냅니다. 실시간이고, 도착 보장이 필요하니까요.
  (2) "누가 언제 무슨 명령을 냈다"는 기록은 OTel에 따로 남깁니다.
      나중에 찾아봐야 하니까요.
  같은 사건을 두 군데 보내는 게 중복처럼 보이지만 역할이 다릅니다.
  MQTT는 전달용, OTel은 기록용입니다.
  (MQTT를 기록용으로 쓰면 나중에 조회가 안 되고, OTel을 전달용으로 쓰면
   전달 보장이 없습니다.)

부탁드리는 것
  이 방식으로 가도 되는지 예/아니오만 주시면 됩니다.
  다른 방식이 나으면 그 방식으로 맞추겠습니다.

없으면
  제어 기능 전체가 못 나갑니다. 우회 방법이 없습니다.

--------------------------------------------------------------------
1-2. 두 번째 : 데이터에 붙는 이름표 규칙을 맞춰주세요  (I-2)
--------------------------------------------------------------------
무슨 말이냐면
  화면은 "이 온도 값이 어느 로봇의, 어느 장소의 값인지" 알아야 올바른
  자리에 그립니다. 그 판단은 데이터에 붙어 있는 이름표(라벨)로 합니다.

지금 상황
  하드웨어 쪽은 이미 로봇에 agent_id, 센서에 sensor_id + site_id 를
  이름표로 붙이기로 했습니다.
  가시화 쪽은 Entity(개별 대상) / Node(설치 단위) 라는 구조를 씁니다.
  이 둘이 어떻게 대응되는지가 정해져 있지 않습니다.

부탁드리는 것
  "가시화의 Entity = 하드웨어의 agent_id/sensor_id,
   가시화의 Node = 하드웨어의 site_id" 이런 식의 대응표 한 장이면 됩니다.

없으면
  데이터가 와도 화면 어디에 그려야 할지 판정할 수 없습니다.

--------------------------------------------------------------------
1-3. 세 번째 : 브라우저가 실시간 데이터를 어떻게 받나요?  (D-2, I-9)
--------------------------------------------------------------------
무슨 말이냐면
  가시화 화면은 웹 브라우저에서 돕니다. 그런데 브라우저는 MQTT에 직접
  붙을 수 없습니다. 기술적 제약입니다.

제 제안
  백엔드에 중계 서버(WebSocket 게이트웨이)를 하나 두고, 브라우저는
  거기에만 붙습니다. 브라우저가 브로커에 직접 접근하지 않는 편이
  권한 관리도 감사 기록도 단순해집니다.

부탁드리는 것
  이 중계 서버를 백엔드에서 만들어 주실 수 있는지, 아니면 다른 방법이
  있는지 알려주세요.

없으면
  실시간 갱신이 안 되고, 화면이 몇 초마다 새로 물어보는(폴링) 방식으로
  떨어집니다. 부드럽지 않고 부하도 큽니다.

--------------------------------------------------------------------
1-4. 나머지 (급하진 않지만 필요합니다)
--------------------------------------------------------------------
  · Prometheus에 어떻게 질문하면 되는지 알려주세요.            (I-1)
    - 주소(개발용/운영용), 인증 방법, 한 번에 얼마나 물어봐도 되는지,
      데이터가 며칠치나 남아 있는지.
    - 비밀번호·토큰 값 자체는 안 주셔도 됩니다. 어디서 가져오는지만요.
      (가시화 설정 파일에 자격 증명을 적지 않는 게 원칙입니다.)

  · Grafana 조회 API와 인증 방법                                (I-3)
    - 이미 만들어 둔 Grafana 대시보드를 가시화가 그대로 재사용할 수
      있으면 작업량이 줄어듭니다.

  · 감사 로그를 "읽는" API                                      (I-5)
    - 가시화는 기록을 남기기만 하고 저장은 안 합니다. 그런데 화면에
      "이 게이트를 마지막으로 조작한 사람: 홍길동" 을 띄우려면 다시
      읽어와야 합니다. 쓰기만 있고 읽기가 없으면 이 표시가 안 됩니다.

  · 권한/역할 모델                                              (I-6)
    - 어떤 역할이 있고, 각 역할이 무슨 제어를 할 수 있는지.
      현재 사용자의 역할을 물어보는 API도 있으면 좋습니다.
    - 최종 권한 검사는 백엔드가 합니다. 화면에서는 버튼을 아예 안
      보여주는 1차 차단 용도로 씁니다.

  · MQTT ↔ OTel 다리(브리지)가 이미 있나요?                     (D-8)
    - ★ 이거 먼저 확인 부탁드립니다. 이미 있다면 가시화가 기록을
      따로 보낼 필요가 없어져서 작업이 줄어듭니다.
      하드웨어 쪽도 같은 질문을 올려뒀으니 한 번에 답해주시면 됩니다.

--------------------------------------------------------------------
1-5. 반대로, 제가 대규에게 보낼 것들
--------------------------------------------------------------------
  · 제어 명령 기록 (누가 / 언제 / 어디에 / 어떤 방법으로 결정했는지)
    - "어떤 방법으로"가 핵심입니다. 앞으로 명령을 내는 길이
      ① 손으로 클릭 ② 음성 지시 ③ LLM 제안 수락 ④ AI 자동제어
      네 가지로 늘어납니다. "누가 눌렀나"만 남기면 사고가 났을 때
      책임 구조를 알 수 없습니다.
    - LLM 제안을 "그대로 수락"했는지 "고쳐서 수락"했는지도 구분해서
      남깁니다. 이 둘은 책임이 다릅니다.
  · 가시화 자체 성능 지표 (viz.* 로 시작하는 이름을 쓰겠습니다)
    - 화면 반영 지연, 편집기 반응 속도, LLM 호출 지연·실패율 등
    - AI가 ai.*, 하드웨어가 robot.*/sensor.* 를 쓰니 겹치지 않습니다.
  · 가시화가 어떤 데이터를 얼마나 자주 조회하는지 목록
    - 백엔드 부하 예측에 쓰시면 됩니다.


====================================================================
2. 조병현 — 하드웨어(센서 · 로봇) 담당
====================================================================

먼저 말씀드릴 것
  하드웨어 요구사항 정의서에 토픽 규칙, QoS, retained, 시간 기준,
  traceparent까지 이미 잘 정리돼 있습니다. 가시화가 따로 스키마를
  만들면 충돌하니, 그 문서 규약을 그대로 쓰겠습니다.
  아래는 "그 문서에 없거나 다른 부분"만 추린 것입니다.

--------------------------------------------------------------------
2-1. 제일 급한 것 : 로봇에도 "어디에 설치됐는지" 값을 넣어주세요 (H-1)
--------------------------------------------------------------------
무슨 말이냐면
  센서에는 site_id(어느 관측소인지)가 붙어 있는데, 로봇에는 그에 해당하는
  값이 없습니다. agent_id(로봇 번호)와 domain(분야)만 있습니다.

왜 필요하냐면
  화면에 여러 대상을 같이 그리려면 "이 대상이 어느 설치 단위에 속하는지"를
  알아야 합니다. 그게 좌표를 맞추는 기준점이 되기 때문입니다.

부탁드리는 것
  로봇 이름표에도 센서의 site_id 같은 값을 하나 추가해주세요.
  이름은 그냥 site_id 그대로 써도 됩니다. 이미 센서에 있는 걸 로봇에
  맞추는 거라 새 체계를 만드는 일은 아닙니다.

덧붙임
  Zone(더 큰 구역)은 요청하지 않겠습니다. 캡스톤에서는 구역이 하나뿐이라
  domain으로 대체하면 됩니다. 하천 쪽에서 지점이 둘 이상 되면 그때
  다시 얘기하겠습니다.

없으면
  로봇을 화면 어디에 놓아야 할지 판정할 수 없습니다.

--------------------------------------------------------------------
2-2. 두 번째 : 좌표가 "어디를 기준으로" 한 값인가요?  (H-2)
--------------------------------------------------------------------
무슨 말이냐면
  로봇 상태에 position {x, z} 가 들어 있는데, 이 x가 0이면 그게 어디인지
  적혀 있지 않습니다. AI 쪽 position_world {x, y, z} 도 마찬가지입니다.

왜 필요하냐면
  기준점이 다르면 두 로봇의 좌표를 같은 화면에 겹칠 때 엉뚱한 자리에
  그려집니다. 지도 두 장을 기준점 없이 겹치는 것과 같습니다.

부탁드리는 것
  아래 네 가지만 정리해주시면 됩니다.
    (1) 어느 지점을 원점(0,0)으로 잡았는지, 그 물리적 위치
    (2) x축, z축이 각각 어느 방향이고 단위가 무엇인지 (미터? 센티미터?)
    (3) y(높이)를 뺀 이유 — 평면이라고 가정한 건지, 그냥 안 쓰는 건지
    (4) AI의 position_world 와 같은 기준인지, 변환이 필요한지

  이 항목은 AI 파트와도 걸리는데, 좌표를 처음 만드는 쪽이 하드웨어라
  여기서 기준을 정하고 AI가 따라오는 편이 어긋날 여지가 적습니다.

없으면
  로봇이 두 대 이상 있는 화면을 만들 수 없습니다.

--------------------------------------------------------------------
2-3. 화면을 새로 켜면 값이 안 보입니다  (H-3)
--------------------------------------------------------------------
무슨 말이냐면
  지금 상태 데이터는 "주기적으로 계속 보내는" 방식이고, 마지막 값을
  브로커가 들고 있지 않습니다(retained=false).
  그래서 관제 화면을 새로 열거나 새로고침하면 다음 발송 주기가 올 때까지
  화면이 비어 있습니다.

왜 문제냐면
  가시화 요구사항 중에 "일부러 안 켠 것 / 고장난 것 / 정상"을 구분해서
  보여주는 게 있습니다. 그런데 지금은 여기에 "접속은 됐는데 아직 값을
  못 받은 상태"라는 애매한 네 번째가 생깁니다. 이걸 고장으로 표시하면
  거짓 경보가 되고, 정상으로 표시하면 놓칩니다.

부탁드리는 것
  둘 중 아무거나 하나만 해주시면 됩니다.
    (가) 상태 토픽에 retained=true 를 켜서 마지막 값이 남게 하거나
    (나) 백엔드가 마지막 상태를 들고 있다가 새로 접속한 화면에 주거나
  어느 쪽이든 상관없습니다.

--------------------------------------------------------------------
2-4. 영상 주소가 브라우저에서 재생이 안 됩니다  (H-4)
--------------------------------------------------------------------
무슨 말이냐면
  문서에 영상을 RTSP 또는 WebRTC로 보낸다고 돼 있는데, RTSP는 웹
  브라우저에서 바로 재생이 안 됩니다. 브라우저 자체의 제약입니다.

부탁드리는 것
  RTSP를 WebRTC나 HLS로 바꿔주는 지점이 어디인지 정해야 합니다.
  그리고 영상 주소 형식(stream_url) 협의 대상에 가시화도 넣어주세요.
  하드웨어 문서 7장 협의 표에 가시화가 빠져 있는데, 영상을 실제로
  화면에 그리는 건 가시화라서요.

없으면
  화면에 영상이 안 나옵니다. 임시로 녹화 파일이나 가짜 데이터로
  대체할 수는 있습니다.

--------------------------------------------------------------------
2-5. 가시화가 명령을 보내는 게 규약에 없습니다  (H-5)
--------------------------------------------------------------------
무슨 말이냐면
  명령 토픽(cmd)의 발신자가 "백엔드·AI"로만 적혀 있고 가시화가 없습니다.
  그런데 가시화 요구사항에는 사용자가 화면에서 제어 명령을 내는 기능이
  들어 있습니다.

부탁드리는 것
  가시화 명령이 같은 토픽으로 들어가는지, 아니면 백엔드를 거쳐서
  백엔드 이름으로 나가는지 정해주세요.

제 제안
  백엔드를 거치는 쪽. 브라우저가 브로커에 직접 쓰지 않는 편이
  권한 관리와 기록 양쪽에서 단순합니다. (대규에게 드린 1-3과 같은 판단)

--------------------------------------------------------------------
2-6. 명령이 "성공했다"를 언제로 볼까요?  (H-6)
--------------------------------------------------------------------
무슨 말이냐면
  문서에 "명령 성공 여부는 응답(ack)이 아니라 실제 상태 값으로 최종
  확인한다"고 적혀 있는데, 이게 화면 동작에 그대로 영향을 줍니다.

  화면에는 두 가지 방식이 있습니다.
    (가) 버튼 누르자마자 바로 열린 것처럼 보여주기 (빠르지만 틀릴 수 있음)
    (나) 실제로 열렸다는 확인이 올 때까지 기다리기 (느리지만 정확)

부탁드리는 것
  명령 종류별로 어느 쪽인지 목록을 주세요.
  예: 게이트 개폐 → 상태 확인까지 기다림 / 로봇 이동 → 응답만으로 충분?
  로봇 이동 명령은 응답만 받으면 되는지, 실제로 움직이기 시작하는 것까지
  봐야 하는지가 같은 질문입니다.

--------------------------------------------------------------------
2-7. 그대로 따르겠다고 정한 것들 (확인만 해주세요)
--------------------------------------------------------------------
  · 토픽 규칙  {domain}/{type}/{id}/{channel}
  · QoS/retained  상태 0·false / 접속상태 1·true / 명령 1·false
  · 시간  ISO8601 UTC 밀리초, 장비 시각 동기 필수
  · 영상  MQTT에 원본을 싣지 않고 참조(frame_ref)만. 원본은 별도 스트림
  · 명령 응답  cmd/ack 하위 토픽, traceparent 그대로 복사
  · 유실 검출  seq 번호가 건너뛰면 빠진 것으로 판정
  · 스키마 버전  schema_version 필드


====================================================================
3. 진나영 — AI (인지 · 예측 · 의사결정) / 오케스트레이터 담당
====================================================================

--------------------------------------------------------------------
3-1. 제일 급한 것 : 탐지 결과에 "어느 화면을 본 건지" 넣어주세요 (A-1)
--------------------------------------------------------------------
무슨 말이냐면
  가시화는 영상 위에 탐지 박스를 겹쳐 그립니다. 그러려면 "이 박스가
  영상의 몇 번째 프레임에 대한 결과인지"를 알아야 합니다.
  지금 출력에는 시각(timestamp)만 있고 프레임 정보가 없습니다.

왜 시각만으로는 안 되냐면
  30fps면 프레임 간격이 33밀리초입니다. 시각이 조금만 어긋나도 한 프레임씩
  밀려서, 움직이는 물체의 박스가 몸에서 벗어난 자리에 그려집니다.

부탁드리는 것
  입력으로 받은 frame_ref 를 출력에 그대로 되돌려 주시면 됩니다.
  새로 만드는 게 아니라 있는 걸 복사해서 내보내는 거라 부담이 적습니다.

    {
      "agent_id": "...",
      "timestamp": "...",
      "frame_ref": { "stream_url": "...", "frame_ts": "..." },   ← 추가
      "detections": [ ... ],
      "model_version": "...",
      "processing_latency_ms": ...
    }

없으면
  영상 위 박스 겹치기를 포기하고 영상만 띄워야 합니다.

--------------------------------------------------------------------
3-2. bbox 좌표가 어떤 기준인가요?  (A-2)
--------------------------------------------------------------------
부탁드리는 것 — 세 가지만
  (1) 픽셀 숫자인가요, 0~1 사이 비율인가요?
  (2) 원점이 왼쪽 위인가요, 왼쪽 아래인가요?
  (3) 픽셀이라면 기준 해상도가 뭔가요? 스트림 해상도가 바뀌면 어떻게 되나요?

없으면
  해상도가 바뀌는 순간 박스 위치가 전부 깨집니다.

--------------------------------------------------------------------
3-3. 어떤 값이 "원본"이고 어떤 값이 "이미 판단이 들어간 값"인가요? (A-3)
--------------------------------------------------------------------
무슨 말이냐면
  예측 AI의 위험도, 의사결정의 priority 같은 값은 이미 여러 데이터를
  종합해서 나온 결론입니다. 반면 온도나 좌표는 날것의 측정값입니다.

왜 필요하냐면
  가시화에는 "여러 값을 묶어서 요약 지표를 만드는" 기능이 있습니다.
  이미 요약된 값을 원본으로 잘못 알고 또 요약하면, 두 번 요약한
  이상한 값이 화면에 나옵니다.

부탁드리는 것
  출력 필드 목록에 "이건 원본 / 이건 종합 판단" 표시를 붙여주세요.
  종합 판단이라면 어떤 입력으로부터 나온 건지도 알려주시면 좋습니다.

--------------------------------------------------------------------
3-4. 판단 근거를 구조로 주실 수 있나요?  (A-4)
--------------------------------------------------------------------
무슨 말이냐면
  지금 의사결정 출력에 reason 필드가 있는데 "로그·디버깅용" 문자열로
  돼 있습니다.

  가시화 요구사항에는 "이 판단이 왜 나왔는지, 어떤 데이터가 얼마나
  기여했는지"를 화면에 보여주는 게 있습니다(설명가능성).
  사람이 읽는 한 줄 문장으로는 이걸 화면에 구조적으로 못 그립니다.

부탁드리는 것
  reason 을 이런 식으로 확장할 수 있는지 협의하고 싶습니다.
    reason: [
      { "factor": "battery_pct", "value": 18, "contribution": 0.6 },
      { "factor": "distance_m",  "value": 42, "contribution": 0.3 }
    ]
  형식은 얼마든지 바뀌어도 됩니다. "무엇이 얼마나 기여했나"만 나오면 됩니다.

  부담이 크면 우선 상위 2~3개 기여 요인만이라도 괜찮습니다.

--------------------------------------------------------------------
3-5. 오케스트레이터 쪽 (컨테이너 배포 이벤트)
--------------------------------------------------------------------
  가시화는 "컨테이너가 하나 뜨면 대시보드가 자동으로 생긴다"가 핵심
  기능입니다. 그래서 등록·해제 이벤트를 받아야 합니다.

  필요한 것
    (1) 이벤트에 담기는 식별자 체계 (컨테이너를 뭐라고 부르는지)
    (2) 상태 값의 목록 (running / stopped / failed / ... 뭐가 있는지)
    (3) "일부러 배포 안 한 것"을 어떻게 표시할지
        - 이게 중요합니다. 가시화는 "일부러 안 켠 것"과 "고장난 것"을
          화면에서 다르게 보여줘야 하는데, 구분 표시가 없으면 둘 다
          똑같이 회색으로 나옵니다.

  급하지 않은 이유
    이벤트 소스가 없어도 설정 파일로 목록을 넣어 동작하게 만들어 뒀습니다.
    그래서 나영 파트 진척에 가시화가 막히지는 않습니다. 다만 나중에
    붙일 때 형식이 안 맞으면 다시 고쳐야 하니 미리 알려주시면 좋습니다.

--------------------------------------------------------------------
3-6. 반대로, 제가 나영에게 드릴 것
--------------------------------------------------------------------
  · 오브젝트 디텍션을 가시화 파이프라인의 한 단계(transform 노드)로
    부를 수 있게, 입출력 규격과 등록 방법을 정리해서 드리겠습니다.
  · AI 모듈이 내보내는 성능 지표를 가시화 대시보드에서 바로 쓸 수 있게
    라벨 이름 규칙을 맞추겠습니다.
  · 경계 정리 : 가시화의 로컬 LLM은 "화면 조작을 자연어로 푸는" 계층이고,
    예측 AI는 "도메인 판단을 내리는" 쪽입니다. 서로 침범하지 않습니다.
    LLM이 예측 결과를 가져다 쓰는 건 괜찮습니다.


====================================================================
4. 세 분 모두에게 (한자리에서 정하는 게 나은 것)
====================================================================

4-1. ID 체계를 한 번에 통일합시다
  지금 네 개의 이름 체계가 따로 굴러가고 있습니다.
    · 컨테이너 ID          (나영 / 오케스트레이터)
    · agent_id, sensor_id  (병현 / 하드웨어)
    · Entity ID, Node ID   (현우 / 가시화)
    · 메트릭 라벨          (대규 / 관측 스택)
  각자 정하면 반드시 어긋납니다. 30분만 같이 앉아서 대응표 한 장
  만들면 끝나는 일이라고 봅니다.

  참고로 가시화는 별도 ID를 새로 발급하지 않습니다.
  하드웨어의 agent_id / sensor_id 를 그대로 Entity ID로 쓰겠습니다.

4-2. MQTT와 OTel을 잇는 다리가 이미 있나요?
  있으면 가시화도 하드웨어도 같은 내용을 두 번 보낼 필요가 없어집니다.
  대규가 한 번만 확인해주시면 두 파트 작업이 같이 줄어듭니다.

4-3. 채널 고르는 기준 (제안)
  같은 사건이 두 채널에 나타나는 건 중복이 아니라 역할 분리입니다.

     판단 기준        MQTT (전달)              OTel (기록)
     ---------------- ------------------------ ------------------------
     누가 받나        기계가 즉시 반응         사람이 나중에 분석
     늦어도 되나      밀리초~수백 ms           초 단위도 괜찮음
     빠져도 되나      안 됨 (도착 보장 필요)   괜찮음 (샘플링 전제)
     시간 방향        지금부터 오는 것 구독    지난 구간을 조회
     저장             브로커는 저장소 아님     저장돼서 나중에 조회 가능

  헷갈리면 이렇게 생각하시면 됩니다.
    "지금 반응해야 하는가?"  → MQTT
    "나중에 찾아봐야 하는가?" → OTel
    둘 다면 둘 다 보냅니다.


====================================================================
5. 제가 지키겠다고 약속하는 것들
====================================================================

  · 데이터를 모으거나 저장하는 것을 만들지 않습니다. 물어보고 내보내기만.
  · 특정 관측 스택(OTel/Prometheus/Grafana)에 코드가 직접 묶이지 않게
    인터페이스 뒤에 숨겨 둡니다. 나중에 갈아끼울 수 있게요.
  · 비밀번호나 토큰 값을 설정 파일에 적지 않습니다. 어디서 가져오라는
    참조 키만 넣습니다.
  · 제어 명령을 실제로 실행하거나 검증하지 않습니다.
    화면에 버튼 만들고, 눌린 걸 내보내고, 결과를 표시하는 데까지입니다.
  · 하드웨어·AI가 이미 정한 규약을 다시 만들지 않습니다.
    그대로 쓰고, 다른 부분만 요청드립니다.
  · LLM이 만든 내용과 실제로 측정된 값을 화면과 로그 양쪽에서
    구분해 둡니다. 섞이면 시스템 전체를 못 믿게 되니까요.


====================================================================
6. 답을 못 받으면 어떻게 되는지 (참고)
====================================================================

  항목                          상대      답 없을 때
  ----------------------------- --------- ----------------------------
  제어 명령 채널 (D-1, O-1)     대규      우회 불가. 제어 기능 중단
  ID/라벨 통일 (I-2, H-1)       대규·병현 임시 규약으로 진행,
                                          나중에 갈아끼우는 비용 발생
  좌표계 기준 (H-2)             병현·나영 로봇 1대 화면까지만 가능
  브라우저 실시간 경로 (D-2)    대규      폴링으로 임시 동작, 품질 저하
  프레임 참조 (A-1)             나영      영상만 표시, 박스 겹치기 포기
  retained·영상 규격 (H-3, H-4) 병현      녹화 파일·가짜 데이터로 대체
  그 외                         전체      가정하고 진행, 어긋나면 보정

  1~3번 말고는 전부 우회 경로가 있습니다. 가시화는 다른 파트가 늦어도
  혼자 굴러가도록 요구사항에 넣어뒀으니, 막힐 걱정은 안 하셔도 됩니다.
  다만 늦게 맞출수록 고치는 범위가 넓어집니다.
