# A. 반드시 수정 (7건)

## A-1. REQ-907 — 감사 이벤트의 **작성 주체가 바뀜** 🔴 최우선

**현재 (§2.9)**
> 시스템은 발행하는 모든 제어 명령을 **관측 스택(OTel)에 이벤트로 내보내야** 하며, 이벤트는 누가 / 언제 / 어디서 / 어떤 방식으로 의사결정했는지를 포함해야 한다.

**v3에 따르면** — §2.3 송신·감사 필드 [변경 반영]
> 명령 요청에 origin.path·voice·llm **필드만 실어 보냄**. Log Record 작성은 **백엔드 audit-writer**(actor는 토큰에서 주입)

**수정안**
> 시스템은 발행하는 모든 제어 명령에 **책임소재 필드**(`origin.path`, `voice.*`, `llm.*`)를 실어 백엔드에 전달해야 한다. OTel Log Record의 **작성·저장은 백엔드 audit-writer**가 수행하며, `actor`는 토큰에서, 시각은 서버 시각으로 백엔드가 주입한다. **본 레이어는 감사를 OTel에 직접 발행하지 않는다.**

**이유**: 브라우저가 직접 쓰면 `actor`가 클라이언트 자기신고가 되고(위조), 시각이 사용자 PC 시계가 되며, 탭이 닫히면 유실됩니다. v1 → v3에서 제 지적으로 바뀐 부분입니다.

⚠️ **주의**: `viz.*` **자체 지표는 여전히 OTel 직접**입니다([확정] 유지). "감사는 백엔드 경유, 지표는 직접" — 이 구분을 문서에서 흐리지 마세요.

**파급 (같은 취지로 함께 수정)**: NFR-002 · REQ-1305 · §3 제외 항목 · §6.2 표

## A-2. NFR-002 — 감사 로그 기록 주체

**현재**
> 시스템은 모든 제어 명령의 발행자, 발행 시각, 대상, 파라미터, 발행 경로, 결과를 **감사 로그로 기록해야** 하며, 로그는 사후 조회 가능해야 한다.

**수정안**
> 시스템은 제어 명령의 대상·파라미터·**발행 경로**를 감사 필드로 백엔드에 전달해야 하며, **기록·보존·조회는 백엔드가 수행한다**(발행자·시각은 백엔드 주입). 본 레이어는 **감사 조회 API로 되읽어** 화면에 표시한다.

## A-4. REQ-203 — 2가지 표시 → **상태 3층 조합 4가지** 🔴

**현재 (§2.2)**
> 시스템은 특정 컴포넌트가 **의도적으로 배포되지 않은 상태와 장애로 인해 응답하지 않는 상태를 구분**해 화면에 다르게 표시해야 한다.

**v3에 따르면** — §2.3 수신·실시간 상태 [변경 반영]
> **상태 3층 필드**(`device_status` / `availability` / `deployment` + `last_seen`)를 WS 게이트웨이로 구독 · **lifecycle은 파생**

**수정안**
> 시스템은 상태 3층(`device.status` / `availability` / `deployment`)의 **조합**으로 **정상 · 장애 · 의도적 미배포 · 판단 불가(stale)** 를 구분 표시해야 한다. 단일 상태 필드로 뭉쳐 저장·표시해서는 안 되며, `lifecycle` 같은 단일 표시값은 3층에서 **파생**시킨다.
>
> **덧붙임**: `stale` 판정은 백엔드가 서버 시각과 `last_seen`으로 수행한다. **본 레이어는 클라이언트 시계로 판정하지 않는다.**

**이유**: 2가지만 구분하면 "연결은 됐는데 기기 fault"와 "값이 오래됨"을 표현할 수 없습니다. v3가 3층을 필드로 내려주기로 한 게 정확히 이 때문입니다.

즉 `deployment` 층은 백엔드가 오케스트레이터에서 파생해 **상태 3층에 합쳐서** 내려줍니다. 나영에게 직접 받는 구조가 아닙니다.

**수정안**
> 시스템은 오케스트레이터에서 파생된 **`deployment` 상태를 백엔드 WS 게이트웨이를 통해 상태 3층의 일부로** 수신해야 한다. 이벤트 소스(Docker / K3s)의 구현 차이는 백엔드 뒤에 은닉되며, **본 레이어는 오케스트레이터에 직접 접속하지 않는다.**

**파급**: §3 파트 경계표의 "나영" 행, §6.1 표의 REQ-201 행(대상 파트 나영 → 백엔드)

## A-7. REQ-903 — 낙관적 반영 vs 확인 후 반영, **기본값이 정해짐**

**현재**
> 개발자는 명령 발행 후 화면 상태를 **낙관적으로 즉시 반영할지, 백엔드 확인 후 반영할지를 액션별로 지정**할 수 있어야 한다.

**v3에 따르면** — §2.3 [확정] / §2.4 상관·감사
> 확인 후 반영(**state 기반 completed**) / 디바이스 ack → **공통 `command.result`로 승격(→completed)**

**수정안**
> …액션별로 지정할 수 있어야 하며, **기본은 확인 후 반영**이다. 확정 판정은 백엔드가 디바이스 ack를 공통 `command.result`로 승격해 내려주는 값을 따르며, 본 레이어는 **`accepted`(진행중) / `completed`(확정) / `rejected`·`timeout`·`failed`(실패)** 3상태로 표시한다.

**부수 효과**: 제가 원래 요청했던 **"액션별 ack/state 판정 목록"이 불필요해졌습니다.** 백엔드가 승격해주니까요. §7.1의 관련 미결 항목도 삭제 대상입니다(D 참조).

## B-1. REQ-304 (신설) — 구성 조회 🔴 F3의 입력이 통째로 빠져 있음

**v3** §2.3 수신·구성 조회 **[확정]**
> 레지스트리에서 **존재 목록 · Entity↔Node 소속 · Node 원점 · Zone 트리** 조회(미배포 표시·3D). 형태 Tier 2

**신설 문구**
> **REQ-304 | 기능 | 구성(레지스트리) 조회 | High**
> 시스템은 백엔드 레지스트리 조회로 **존재해야 할 Entity 목록, Entity↔Node 소속, Node 원점의 전역 배치, Zone 트리**를 수신해야 한다. **값을 발행하지 않는 대상(미배포)도 이 목록을 통해 화면에 표시한다.**

**왜 신설이 필요한가**: 현재 F3(REQ-301~303)에는 계층을 **어디서 받는지**가 없습니다. 그리고 **REQ-203의 미배포 표시가 이것 없이는 성립하지 않습니다** — 미배포 대상은 값을 안 보내므로 상태 메시지에 영원히 나타나지 않습니다.

## B-3. REQ-901 보강 + §6.1 신규 행 — **action 어휘집**

**v3** §2.4 번역·조립(G5) [확정]
> **가시화 추상 action+params를 디바이스 cmd로 번역**(예: `open_gate`→센서 `levee:open`, `goto`→로봇 path). **action 어휘는 도메인 어휘집**

**REQ-901에 덧붙일 문장**
> 본 레이어는 **추상 action + params까지** 선언·발행하며, 디바이스 명령으로의 번역은 **백엔드가 도메인 어휘집으로 수행한다.**

**§6.1(인바운드)에 새 행 추가**
> `REQ-901 / REQ-1202` | 백엔드 | **action 어휘집** — 발행 가능한 action id · 파라미터 스키마 · 필요 역할

**왜 필요한가**: 이게 없으면 F9의 액션 선언도, F12의 LLM 도구도 하드코딩됩니다. v3 §2.4 추후 확정에 "action 어휘집"이 Tier 2로 올라가 있으니, **제 문서에는 "수신 대상"으로 등재**해 두는 게 맞습니다.

# D. 미결(§7) · 위험도(§6.3) 갱신

## 해소되어 **삭제**할 것

- §7.1 — "REQ-903의 '낙관적 표시 vs 확인 후 반영' 선택 기준은 액션 정의 시점에 개별 판단하는 것으로 가정" → **v3에서 확인 후 반영 + 백엔드 completed 승격으로 확정.**
- §6.3 위험 "**높음** — REQ-907 아웃바운드 이벤트 스키마" → **해소.** 작성 주체와 필드가 확정됨.
- §6.3 위험 "**높음** — REQ-201 식별자 체계(컨테이너 ID / 디스크립터 ID / Entity ID 대응)" → **해소.** Entity=`agent_id`/`sensor_id`, Node=`site_id`로 확정.

## 새로 **추가**할 것

**§6.3 위험도**

| 위험 | 내용 | 완화 |
|---|---|---|
| **높음** | **레지스트리 조회 API 형태 미정**(v3에서 Tier 2) — F3와 REQ-203(미배포 표시)이 여기 걸림 | 정적 구성 파일로 개발 진행(REQ-204). 회의에서 우선순위 상향 요청 |

| 중간 | **스트림 변환 지점 미정**(Tier 2) — REQ-502·704 | 녹화 파일 + `frame_ref` 스틸로 선행 구현 |

**§7.2 미결**

- **`origin.path` 4값으로는 "음성으로 말했고 LLM이 해석했다"가 표현되지 않는다.** `voice`로 적으면 LLM 개입이, `llm_suggestion`으로 적으면 음성 입력이 사라져 사고 원인(STT 오인식 / LLM 오해석)을 구분할 수 없다. **REQ-908과 직결** — v3에서도 미해결. (별도 문서 `가시화_음성LLM_요구사항_260819.md` 참조)
- **레지스트리 조회 형태와 핸드오버 통지가 Tier 2**라, 그때까지 F3·REQ-203이 정적 구성 파일에 의존한다.

# 회신할 것

v3 §5에 저에게 온 확인 요망이 있습니다.

> **현우 (가시화)** — v1 반영본에 추가 이견 없는지(감사 백엔드 작성 · 상태 3층 · 레지스트리 · 구독 축). 이벤트 보고 경로(O-5)는 자리만.

**네 건 모두 제 요청대로 반영됐으므로 "이견 없음"으로 회신**하면 됩니다. 다만 두 가지를 덧붙일 만합니다.

1. **레지스트리 조회의 Tier 2 우선순위 상향** — 형태가 안 정해지면 REQ-203(미배포 표시)이 구현 불가라, 다른 Tier 2 항목보다 앞에 두었으면 한다.
2. **action 어휘집도 같은 이유로 앞순위** — F9 액션 선언과 F12 도구 세트가 여기 걸린다.

**회의 안건**으로는 v3 §4에 이미 올라가 있습니다 — "로봇 상태 즉시 제공: retained vs 백엔드 캐시(잠정: 백엔드 캐시 + 즉시 푸시)". 제 선호와 같으니 그대로 지지하면 됩니다.
