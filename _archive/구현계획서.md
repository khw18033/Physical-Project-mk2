# 2. 확정 아키텍처

## 2-1. 세 데이터 평면

| 평면 | 역할 | 주요 경로 | 가시화 원칙 |
|---|---|---|---|
| 업무 | 상태·명령·계획·이벤트 | 말단↔엣지 MQTT, 엣지↔서버 Kafka | 게이트웨이 구독·명령 API만 사용 |
| 관측 | metric·log·trace | OpenTelemetry, Prometheus 계열 | 요약과 원본 경로 및 집약 계층을 구분 |
| 미디어 | 영상 픽셀 | 별도 미디어 경로 (`AI-C-14`) | 브로커에 픽셀을 싣지 않음. 뷰어 출력 분기는 합의 대기 |

웹과 Unity는 브로커·DB·AI 모듈에 직접 연결하지 않는다. 백엔드의 가시화 클라이언트 게이트웨이와 레지스트리 계약을 사용한다.

## 2-2. 클라이언트 구조

```text
백엔드/목 게이트웨이
  ├─ WebSocket: 상태·명령 결과·계획·영상 메타/합성 프레임
  ├─ HTTP: 레지스트리·역할/범위·지표·감사·시나리오
  ├─ 웹 대시보드: 운영 화면 7개
  └─ Unity 트윈 뷰어: 공간 배치·보간·상태 진단
```

두 클라이언트는 상태 3층, 집약 표기, 좌표 기준계, 원천 종류, 재접속 정책을 같은 의미로 해석한다. 브라우저 전용 계약은 두지 않는다.

## 2-3. 영상 인지 경계

- 온디바이스 Raspberry Pi 결과는 진행영역·접근 변화 등 **최소 안전 판단**이다.
- 엣지 결과는 분류·추적·궤적 등 **선택형 정밀 인지**다.
- 화면은 두 결과의 출처를 분리하고, 연계가 없으면 관측 소스별 추적을 유지한다.
- `frame_ref`가 버퍼에 없으면 현재 프레임으로 계산한 값을 정합 결과로 표시하지 않는다.
- 선택 기능의 미배포와 장애를 구분하려면 capability 상태 전달 계약이 추가로 필요하다.

# 4. 남은 작업 순서

## Phase 1 — 문서 정합 복구 (원본 정합 완료)

- Mermaid의 T3를 MAC 기반에서 `device_id` 기반으로 수정한다. **원본 완료, 조판 PNG 대기.**
- 데이터 흐름을 업무·관측 2평면에서 미디어 포함 3평면으로 수정한다. **원본 완료, 조판 PNG 대기.**
- 쉬운 설명, 프로토타입 설명서, 구현 현황과 본 계획서를 최신화했다.
- 활성 Markdown 정합은 완료했다. 쉬운 설명 PDF는 재생성됐고, T3·DF-1 PNG와 프로토타입 PDF는 조판 도구가 있는 환경에서 별도 재생성한다.

완료 기준: 활성 Markdown 사이의 구현 건수, 데이터 평면, 회의 안건, 우선순위가 서로 일치한다.

## Phase 2 — 잔여 표시 4건 (완료)

| ID | 작업 |
|---|---|
| `VZ-I-08` | 위험도 상태(평시·관찰·경보·복구) 표시 |
| `VZ-I-10` | AI 실패 이벤트 알림 |

| `VZ-U-03` | 결심자·운영자·개발자 추상화 계층 뷰 |

상대 파트의 추가 계약 없이 진행 가능한 다음 구현 묶음이다.

구현 결과: 판단·알림 화면에서 위험 단계와 근거, AI 실패 즉시 알림, 역할별 세 깊이를 표시한다. 가시화 자체 처리 지연은 60초 창으로 관측 경로에 발행한다.

## Phase 3 — 음성·LLM 4건 (다음 단계 · 합의 대기)

대상은 `VZ-L-01`~`04`다. 다음 합의 전에는 구현을 고정하지 않는다.

1. 의도 해석을 `AI-C-09`의 `task_type=intent_parse`로 호출하는 주체
2. 해석 결과 출력 스키마의 소유자와 필드
3. GenAI provider 부재 시 비-GenAI 경로 또는 기능 비활성 정책
4. `DISABLED`·`DEGRADED` capability 상태의 가시화 전달 경로

## Phase 4 — 노드 편집기 (우선 구현 완료)

노드 그래프 탭의 기본 화면은 **임무 → Sub task → 로봇 실행·영상·센서·제어 근거**를 잇는 관제 그래프다. `plan`·`plan_progress` 이벤트로 대기·진행·완료·실패·건너뜀을 실시간 표시하며, 각 Sub task에 관측 근거 노드를 연결·해제한다. source→transform→sink 데이터 파이프라인 편집기는 별도 보조 모드로 유지하고 시험 토큰·명시적 반영·되돌리기를 적용한다. `VZ-L-04`의 LLM 초안은 계약 확정 뒤 이 절차 앞에 연결한다.

## Phase 5 — Unity 시뮬레이터 2단계

현재 Unity는 뷰어다. 계약이 안정된 뒤 목 장치 원천을 Unity 시뮬레이터로 교체하되, 뷰어가 시뮬레이터 내부 상태를 직접 읽는 우회 경로는 만들지 않는다. 모든 값은 기존 게이트웨이 왕복을 거친다.

## 합의 대기

- `VZ-U-06`: 미확인 탐지 그룹 전달 형식
- `VZ-C-06`: 실물·시뮬레이션 원천 종류의 발행 주체와 와이어 형식
- 미디어 평면에서 뷰어로 나가는 WebRTC/HLS 등 출력 분기와 소유 파트
- ACK의 요청 식별자 에코, 좌표계 손잡이, 자세(orientation), 레지스트리 변경 통지

# 6. 변경 관리 원칙

- 요구사항 시트가 바뀌면 ID 존재 여부뿐 아니라 **소분류와 의미**를 함께 대조한다.
- 문서에는 구현 완료, 목 데이터로 검증, 계약 대기, 미구현을 구분해 적는다.
- 외부 계약이 정해지지 않은 필드 이름을 가시화 코드에서 임의로 고정하지 않는다.
- 생성된 PDF·PNG보다 Markdown·Mermaid 원본을 먼저 수정하고, 재생성 여부를 명시한다.
- 미커밋 작업은 완료 건수에 포함하지 않으며 기존 작업자의 변경을 보존한다.
