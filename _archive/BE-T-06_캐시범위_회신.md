# `BE-T-06` 캐시 범위 회신 — 이대규

> 대규 시트 `BE-T-06`의 *"캐시 범위는 상태 전체(3층+last_seen)를 기준으로 두되 세부 필드 범위는 가시화 요구 확인 후 조정한다. [회의 확정 대기]"* 에 대한 답.

# A. 그대로 보낼 메시지

아래를 복사해서 보내면 됩니다.

---

`BE-T-06` 캐시 범위 확인 요청 건 답변이야.

**결론부터 — 필드가 아니라 채널 단위로 갈라야 해.** "상태 전체"만으로는 부족하고, 반대로 **전 채널을 다 캐시하면 오히려 화면이 거짓말을 해.**

**캐시해서 구독 즉시 내려줘야 하는 것 (7개)**

`state`(3층+`last_seen`+`stale_threshold_ms`) · `telemetry`(위치·배터리) · `actuator_state` · `control_lock` · `plan`(승인 대기) · `plan_progress` · `video_meta`

이유는 하나야 — **이 값들이 없으면 화면이 "모른다"를 그릴 수밖에 없는데, 실제로는 서버가 알고 있어.** 특히 센서는 평시 1분 주기라 캐시가 없으면 재접속 후 최대 1분간 빈 화면이야.

**절대 캐시하면 안 되는 것 (3개)**

- `command_result` — 재접속하면 **지난 명령 결과가 방금 온 것처럼** 뜬다. 관제에서 이건 위험해
- `video_frame` — 옛 프레임 한 장이 **정지 화면인데 현재처럼** 보인다
- `detections` — `frame_ref`가 지금 화면에 없는 프레임을 가리켜서 **박스가 엉뚱한 데** 뜬다

**안 줘도 되는 것 (2개)**

`heartbeat`(서버가 이미 `availability`로 판정해서 `state`에 실어주니 중복) · `metrics`(질의 프록시로 따로 조회하는 경로가 있음)

**한 가지 더 — 캐시된 값의 `ts`는 원래 발행 시각 그대로 줘.** 푸시 시점으로 다시 찍으면 `stale` 판정이 리셋돼서 **오래된 값이 새 값처럼** 보여. 화면은 `ts`만 보고 "이게 얼마나 묵은 값인가"를 판단하니까, 캐시에서 왔다는 별도 표시는 필요 없어.

목 게이트웨이는 지금 전 채널을 캐시하고 있어서 위 3개가 그대로 재생되는 상태야. 내 쪽에서 고칠게.

# B. 근거 (물어보면 보여줄 것)

## 채널별 판단

| 채널 | 캐시 | 왜 |
|---|---|---|
| `state` | **필요** | 3층 + `last_seen` + `stale_threshold_ms`. 현황판 첫 화면의 근거. 상태 4종(정상/장애/미배포/판단 불가)이 전부 여기서 파생 |
| `telemetry` | **필요** | 카드의 값과 **트윈 화면의 초기 배치**. 위치를 모르면 로봇을 어디에 놓을지 알 수 없다 |
| `actuator_state` | **필요** | 액추에이터는 표준 3층과 별개인 **자기 어휘**(대기·동작 중·완료·오류)를 쓴다. 현재 상태를 모르면 버튼 판단 불가 |
| `control_lock` | **필요** | 잠금을 모르면 **안 눌리는 버튼을 계속 누르게 된다**. `VZ-O-05`의 존재 이유 |
| `plan` | **필요** | 승인 대기 계획이 재접속으로 사라지면 **승인이 유실**된다 |
| `plan_progress` | **필요** | 진행 중 임무가 어느 구간까지 갔는지 |
| `video_meta` | **필요(경량)** | 패널 열 때 fps·해상도 규격 판단. 픽셀이 아니라 메타만 |
| `heartbeat` | 불필요 | `availability` 판정 근거인데 그 판정을 서버가 이미 해서 `state`에 실어준다. 중복 |
| `metrics` | 불필요 | 질의 프록시(`BE-Q-01`)로 조회하는 별도 경로가 있다 |
| `command_result` | **금지** | 지난 결과가 새 결과로 보인다. 마지막 조작 이력은 감사 조회(`VZ-I-05`)로 따로 받는다 |
| `video_frame` | **금지** | 정지 화면이 현재 영상처럼 보인다 |
| `detections` | **금지** | `frame_ref` 정합이 깨져 박스가 엉뚱한 위치에 뜬다. `VZ-I-07`이 막으려는 문제 그 자체 |

## `ts`를 다시 찍으면 안 되는 이유

화면은 `stale` 판정을 **직접 하지 않습니다**(서버 판정을 따르는 것이 계약). 다만 값이 얼마나 묵었는지는 `ts`로 읽습니다.

캐시 푸시 시점으로 `ts`를 다시 찍으면 **1분 전 값이 방금 값으로 보이고**, 그 직후 서버가 `stale`로 판정을 내리면 화면에서 "방금 왔는데 판단 불가"라는 앞뒤 안 맞는 상태가 됩니다.

원래 발행 시각을 그대로 주면 화면이 스스로 판단할 필요 없이 정확히 그려집니다. **별도의 "캐시에서 왔음" 표시는 요청하지 않습니다** — `ts`로 충분하고, 필드를 하나라도 덜 만드는 쪽이 낫습니다.

# C. 내 쪽 후속 작업

목 게이트웨이(`mock-gateway/hub.ts`)의 `publish()`가 **채널 구분 없이 전부 캐시**합니다.

```
this.cache.set(key, env);   // 227행 — video_frame·detections·command_result도 여기 걸린다
```

그래서 재접속하면 위 3개가 그대로 재생됩니다. **지금까지 이걸 못 본 이유는 재접속 검증을 현황판(`state`)에서만 했기 때문**입니다. 영상 탭을 연 채로 서버를 재시작하면 바로 드러납니다.

→ 캐시 대상 채널을 화이트리스트로 바꾸고, `agg-*` 시나리오처럼 **재접속 시 금지 채널이 안 오는지 확인하는 시나리오**를 하나 추가합니다.
