# 작업 지시: 그래프에서 되돌아가기 · 노드가 화면 안에 · STT 복구

**선행**: 시나리오 연계 (`reports/2026-09-01_시나리오연계.md` · 착수 시점에 커밋돼 있어야 한다)
**대상 요구사항**: `VZ-D-01`~`D-07`(탭① 디버깅) · `VZ-L-01`(발화) · `VZ-C-02`(STT 없어도 화면은 뜬다)
**기준 커밋**: 착수 시점의 `HEAD`
**날짜**: 2026-09-01

---

## 왜 하나

사용자가 완성된 화면을 쓰다가 걸린 것 셋이다. 셋 다 **기능이 없는 것이 아니라
길이 막혀 있는 것**이다 — 되돌아갈 길, 노드까지 닿는 길, 음성이 서비스에 닿는 길.

| # | 무엇 | 성격 |
|---|---|---|
| 1 | 노드 그래프에서 마일스톤으로 되돌아갈 수 없다 | 탐색이 한 방향뿐 |
| 2 | 「임무 전체」 그래프의 오른쪽 노드가 화면 밖으로 잘린다 | 배치가 폭을 모른다 |
| 3 | STT 서비스에 닿지 않아 녹음을 쓸 수 없다 | 원인 진단부터 |

**착수 순서는 3 → 1 → 2.** 3은 원인 파악이 먼저라 시간이 얼마나 걸릴지 모르고,
1은 작고, 2는 배치 알고리즘을 새로 써야 해서 가장 크다.

## 1. 노드 그래프 → 마일스톤 되돌아가기

### 지금

탭①의 이동은 **마일스톤 → 노드 그래프 → 액션 아이템** 한 방향뿐이다.

- 액션 아이템 → 그래프: 팝업을 닫으면 돌아간다 (`ActionModal` 의 `onClose` 가
  `screen === 'detail'` 일 때 `setScreen('graph')`)
- **그래프 → 마일스톤: 없다.** `GraphScreen` 의 머리줄(`section-title`)에는 제목과
  토글 둘(DAG/트리 · 이 마일스톤/임무 전체)뿐이다.

유일한 길은 상단 공통 바의 **임무 이름 버튼**(`mission-identity` → `onDebuggerHome()`)인데,
그게 「마일스톤으로 돌아가기」라는 것을 화면 어디에도 적어 두지 않았다. **발견할 수 없는 길은
없는 길이다.**

### 할 것 — 머리줄에 이동 경로(breadcrumb)를 둔다

버튼 하나만 있어도 되지만, 이동이 세 단계라 **지금 어디에 있는지와 어디로 돌아갈 수 있는지를
같이** 보여주는 편이 낫다. 사용자가 말한 「마일스톤으로 돌아가는 버튼」은 이 안에 포함된다.

```
마일스톤  ›  MS-C 위험 수위 도달 시 닫기  ›  T-43c close_gate 발행
└ 누르면 마일스톤 목록      └ 누르면 이 마일스톤의 그래프
```

- **맨 앞 「마일스톤」은 항상 있고 항상 눌린다.** 이것이 사용자가 요구한 되돌아가기다.
- 가운데 칸은 지금 보고 있는 마일스톤. **「임무 전체」 범위일 때는 `임무 전체 N노드`** 로 적는다.
- 마지막 칸은 액션 아이템 팝업이 열려 있을 때만 나온다.
- `screen` 이 `replay`·`failure` 일 때도 같은 줄이 나와야 한다 — 그 화면들도 `GraphScreen` 이고
  지금 똑같이 갇혀 있다.

### 붙이는 자리

- `GraphScreen` 에 `onBack()` 프롭을 더하고 머리줄 맨 앞에 그린다.
- `MissionDebugger` 가 넘긴다: `onBack={() => navigate('milestones')}` — **기존 `navigate()`
  헬퍼를 쓴다.** 그것이 `modalTask` 정리까지 함께 한다. 직접 `setScreen` 을 부르면 팝업 상태가 남는다.
- 마일스톤 칸을 누르면 `onScope('milestone')` 도 함께 되돌린다 — 「임무 전체」로 보다가
  목록으로 나갔다 다시 들어왔는데 범위가 전체로 남아 있으면 어리둥절하다.

### 하지 말 것

- 상단 공통 바의 임무 이름 버튼을 **없애지 마라.** 지금 동작하는 유일한 길이고,
  단독 빌드(전달본)에서도 같은 자리다.
- 전달본(`MSN-260826-01`)의 화면 구조는 그대로다 — 머리줄에 한 줄이 느는 것뿐이다.

## 2. 「임무 전체」 그래프가 화면 밖으로 나간다

### 지금 — 배치가 화면 폭을 모른다

`src/graph/layout.ts` 의 `dagLayout()` 은 **깊이 하나당 열 하나**를 무조건 오른쪽으로 붙인다.

```ts
{ x: 30 + column * 220, y: 55 + row * 150 }
```

세 편의 「임무 전체」는 거의 일직선 사슬이라 깊이가 그대로 열 수가 된다.

| 편 | 노드 | 최대 깊이 | 계산된 폭 |
|---|---|---|---|
| `MSN-260831-01` | 17 | 14 | 약 3,330 px |
| `MSN-260831-02` | 18 | 14 | 약 3,330 px |
| `MSN-260831-03` | 16 | **15** | 약 **3,550 px** |

화면 폭의 두세 배다. `.graph-canvas` 는 인라인 `width` 로 그 값을 그대로 받고
`min-width:1120px` · `overflow:hidden` 을 갖고 있어서, **패널 안에서 가로로 스크롤되지 않는다.**
넘치는 폭은 페이지 전체를 옆으로 늘려 버리고, 첫 화면에서 오른쪽 노드는 보이지 않는다.
가로 스크롤 막대를 만들어 해결하지 마라 — 사용자가 요구한 것은 **첫 화면에 다 들어오는 것**이다.
3편이 가장 길어 눈에 먼저 걸렸을 뿐 세 편 모두 같은 상태다.

### 할 것 — 폭을 알고 접어 배치한다(band wrap)

사용자가 정한 요건이 명확하다.

> 세로 길이를 늘리고, 무작정 가로 배치가 아닌 탭 안에 다 들어오도록.
> **사용자가 임의로 노드 위치를 바꿀 수 있으니 초기 화면에서 모든 노드가 화면 안에 들어오기만 하면 된다.**

즉 **자동 정렬·확대축소·미니맵 같은 것을 만들 필요가 없다.** 접어 넣기만 하면 된다.

1. `TaskGraph` 가 **자기 컨테이너의 실제 폭을 잰다** — `ResizeObserver`(또는 마운트 시
   `clientWidth` + `resize` 리스너). 잰 값이 없을 때의 대비값을 하나 둔다.
2. `dagLayout(tasks, availableWidth)` 로 서명을 바꾼다.
   - `perBand = max(MIN_COLS, floor((availableWidth - PAD) / COL))`
   - 깊이 `d` → `band = floor(d / perBand)`, `col = d % perBand`
   - `x = PAD + col * COL`
   - `y` 는 **밴드마다 그 밴드에서 가장 높은 열의 노드 수**를 반영해 쌓는다.
     1편 MS-D 처럼 한 열에 노드가 셋인 곳이 있어서, 밴드 높이를 상수로 두면 겹친다.
3. `treeLayout()` 도 같은 폭 제한을 받는다. 원래 세로로 긴 배치라 폭만 접으면 된다.
4. `.graph-canvas` 의 `min-width:1120px` 를 없애고 폭을 컨테이너에 맞춘다.
   지금은 인라인 `width` 가 계산된 최대 x 를 그대로 받아 페이지를 옆으로 늘린다.
   **세로는 노드 위치에서 계산해 늘린다**(이미 그렇게 하고 있으니 밴드 수만 반영되면 된다).
5. 드래그 경계(`Math.min(width - NODE_WIDTH, …)`)가 **새 폭**을 쓰게 한다.
   지금은 옛 `width` 를 쓰므로 접은 뒤에도 화면 밖으로 끌 수 있다.
6. `MIN_COLS`(예: 3) 아래로 좁아지는 창에서는 접기를 포기하고 가로 스크롤을 허용한다.
   한 열짜리로 접으면 세로가 터무니없이 길어진다.

### 밴드를 넘는 엣지

마지막 열 → 다음 밴드 첫 열로 되돌아가는 연결선이 생긴다. `connectionPath()` 는 가로 거리로
곡선 모양을 정하므로 **그대로 두면 화면을 가로지르는 긴 곡선**이 된다. 두 가지 중 하나로 처리하라.

- 밴드를 넘는 엣지만 아래로 크게 도는 곡선으로 (되돌아가는 참조 엣지 `↺` 와 **다른 색·실선**으로 — 둘이 헷갈리면 안 된다)
- 또는 밴드 끝/시작에 이어짐 표시(`▸`)를 두고 선을 짧게 끊는다

**어느 쪽이든 되돌아가는 참조 엣지(점선 `↺`)와 시각적으로 구별되어야 한다.**
하나는 「줄바꿈」이고 하나는 「루프」다.

### 사용자가 옮긴 위치는 지키기

`movedPositions` 는 계산된 기준 위치를 덮어쓴다. **창 크기가 바뀌었다고 사용자가 옮긴 노드를
되돌리지 마라** — 기준 배치만 다시 계산하면 된다. 지금 `useEffect(() => setMovedPositions({}),
[layoutMode])` 가 배치 모드 전환 때만 초기화하는데, 그 성질을 유지한다.

### 확인

- 세 편 각각 **「임무 전체」 + DAG/트리 네 조합**에서 노드가 하나도 잘리지 않는다
- 마일스톤 범위에서도 마찬가지 (3편 MS-D 는 6노드 사슬이라 접기 전에도 아슬아슬했다)
- 창을 좁혔다 넓혔다 해도 노드가 겹치지 않는다
- `verify:layout` 은 드래그로 노드와 연결선이 함께 움직이는지를 본다 — **접기 뒤에도 통과해야 한다**

## 3. STT 서비스에 닿지 않는다

### 화면이 말해 주지 않는 것이 문제의 절반이다

지금 화면에 뜨는 문구는 하나다.

> STT 서비스에 닿지 않습니다. 음성 인식만 꺼졌고, 아래에 문장을 직접 넣을 수 있습니다.

이 문장으로는 **서비스가 안 떠 있는 것인지, 떠 있는데 브라우저가 막는 것인지** 알 수 없다.
`SttClient.probe()` 가 `catch { return false }` 로 사유를 통째로 버리기 때문이다.

**원인을 고치는 것과 별개로 이것부터 고쳐라.** 다음에 또 막혔을 때 진단이 몇 초로 줄어든다.

- `probe()` 가 실패 사유를 함께 돌려준다(`{ alive: false, reason }`).
  - `TypeError: Failed to fetch` + 서비스 미기동 → 「서비스가 떠 있지 않습니다 (8801)」
  - CORS 거부 → 「서비스는 떠 있는데 브라우저가 막았습니다 — 출처 목록 확인」
  - 그 외 → 원문 그대로
- 화면 문구에 **`STT_BASE_URL` 과 사유 한 줄**을 함께 적는다. 지금도 URL 은 다른 자리에
  적혀 있지만 실패 문구에는 없다.
- `capabilities()` 의 계약(수동 입력은 항상 열림)은 **바꾸지 마라.** `verify:no-stt` 가 그것을
  검사한다. 늘리는 것은 `note` 의 내용뿐이다.

### 원인 진단 — 이미 배제한 것부터

정적으로 확인해 배제했다. **아래는 다시 보지 마라.**

| 확인한 것 | 결과 |
|---|---|
| 가상환경 | `stt/.venv` 정상. Python 3.10.10, `fastapi 0.141.1` · `uvicorn 0.52.4` · `faster_whisper 1.2.1` · `ctranslate2 4.8.1` · `python_multipart 0.0.32` 전부 설치돼 있다 |
| `registry.json` 경로 | `web-dashboard/mock-gateway/registry.json` 실재 |
| CORS 출처 목록 | `service.py` 의 `ALLOWED_ORIGINS` 에 `localhost:5174`·`127.0.0.1:5174` 둘 다 있다 |
| Vite 포트 밀림 | `vite.config.ts` 가 `strictPort: true` 라 5175 로 밀리지 않는다 — **이 가설은 아니다** |
| 엔진 임포트 실패 | `engines/__init__.py` 가 임포트 실패를 삼키고 `load_errors()` 로 보관한다. 기동을 막지 못한다 |
| 이식본 무결성 | `verify:stt-port` 통과 — `engines/*.py` 가 stt-lab 원본과 바이트 동일 |
| 마지막 성공 기록 | `stt/recordings/` 의 마지막 파일이 **2026-08-28 17:53**. 그 뒤로 성공한 인식이 없다 |

### 진단 순서 — 위에서부터

**모두 Windows 쪽에서 실행한다.** 이 저장소의 `.venv` 는 Windows 가상환경이라
리눅스 셸에서는 돌지 않는다.

1. **`npm run dev` 콘솔의 `[stt]` 로 시작하는 줄을 찾는다.** 답이 여기 있을 확률이 가장 높다.
   `dev-stt.mjs` 가 spawn 실패·비정상 종료를 각각 다른 문구로 남긴다. 다른 로그에 묻혀
   지나가기 쉬우니 위로 스크롤해서 확인하라.
2. **`npm run dev:stt` 를 단독으로 띄운다.** 파이썬 트레이스백 전문이 보인다.
   정상이면 세 줄(`viz-debugger stt → …` · `registry → …` · `recordings → …`)이 찍히고
   uvicorn 이 8801 을 잡는다.
3. **브라우저 개발자도구 → 네트워크**에서 `GET http://127.0.0.1:8801/stt/transcribe` 를 본다.
   - 요청 자체가 실패(`ERR_CONNECTION_REFUSED`) → 서비스가 안 떠 있다 → 1·2 로 돌아간다
   - **405 가 왔는데 콘솔에 CORS 오류** → 서비스는 살아 있고 출처 문제다.
     `probe()` 는 405 도 「살아 있음」으로 치지만 CORS 로 거부되면 `fetch` 가 예외를 던져
     똑같이 「닿지 않음」이 된다 — **증상이 같아 지금은 구별할 수 없다.** 위의 사유 표시가
     필요한 이유가 정확히 이것이다
4. **포트 8801 을 다른 프로세스가 잡고 있는지** 확인한다(`netstat -ano | findstr 8801`).
   앞선 세션의 uvicorn 이 남아 있으면 새 프로세스가 바인딩에 실패하고 조용히 죽는다.
5. 여기까지 다 정상인데도 안 되면 **첫 인식 시점의 모델 내려받기**를 의심한다.
   `faster-whisper` 는 첫 호출에 모델을 받는다. 망이 막혀 있으면 `POST` 가 오래 매달리다
   실패한다 — 다만 그 경우 **probe 는 성공**하므로 지금 증상과 다르다.

### 고친 뒤

- **원인을 보고서에 한 줄로 남긴다.** 다음에 또 나올 종류의 문제다.
- 원인이 「환경 준비」 쪽이면 `viz-debugger/stt/README.md` 에 그 항목을 더한다.
- `stt/service.py` 를 고쳤다면 `verify:stt-port` 는 `engines/*.py` 만 대조하므로 통과하지만,
  **엔진 파일은 여전히 무수정이어야 한다.**

## 검증

| 검사 | 무엇을 |
|---|---|
| `verify:layout` | 접기 배치 뒤에도 드래그로 노드와 연결선이 함께 움직이는가 |
| **`verify:layout` 확장** | **계산된 배치의 최대 x 가 주어진 폭을 넘지 않는가.** 세 편 × 두 배치 모드 × 두 범위로 본다 — 이번 문제가 다시 나면 여기서 잡힌다 |
| `verify:no-stt` | 서비스가 전부 실패해도 화면이 뜨고 **수동 입력이 살아 있는가**. `capabilities()` 계약 불변 |
| `verify:stt-port` | `engines/*.py` 바이트 동일 |
| 기존 15종 | 전부 유지 (기존 14 + `verify:tab-scope`) |

`verify:standalone` 은 Windows 에서 실행한다 — 리눅스 셸에서는
`@rollup/rollup-linux-x64-gnu` 를 못 찾아 실패하는 환경 문제가 있다.
