## 왜 하나

지금 통합 앱은 **문장을 넣어도 화면이 바뀌지 않는다.**

- 탭①은 `scenarios/MSN-260826-01.json` 한 편이 번들에 박혀 있다. `main.tsx`가 그 파일을 모듈 상수로
  읽고, 되감기 시각(`41`·`95`)·마일스톤 수(`7건`)·배정 대상(`MS-C`)·상단 바의 임무 이름까지 그 한 편에
  맞춰 손으로 적혀 있다.
- 발화 패널은 인식까지는 실제인데, 「이 발화로 임무 생성 요청」을 누르면 `mission_from_utterance`가
  게이트웨이에서 **`unknown_action`으로 거부**된다. 뒤 세 칸(의도 분석·마일스톤 분리·태스크 생성)은 목이다.
- 탭①과 탭②~⑤는 **다른 세계**다(요구사항정의서 7.8). 탭①은 `go1-02`·`cam-4f`, 탭②~⑤는
  `robot-01`·`camera-02`·`sensor-01`·`actuator-01`. 겹치는 장비가 하나도 없어 탭①에서 무슨 일이
  일어나도 탭②~⑤는 모른다.

**그래서 세 가지를 한 번에 본다** — 문장 하나가 들어오면 ① 마일스톤·태스크·하드웨어가 그 문장의 것으로
바뀌고, ② 승인하면 재생이 시작되고, ③ 재생되는 동안 탭②~⑤의 **호환되는 자리**가 같은 시간축으로 따라
움직인다. 이걸 보려고 시나리오 대본 세 편을 만든다. **실제 시나리오에서 탭별로 데이터가 어떻게 연결되고
어떻게 작동하는지를 화면에서 보는 것**이 목적이다.

## 딱 하나만 틀리면 안 되는 것 — 이것은 LLM이 아니다

문장에서 마일스톤을 뽑는 것은 `VZ-G-01`(마일스톤 분리)·`VZ-G-02`(태스크 생성)이고 **로컬 LLM이 필요하다.
이번 작업은 그것을 만드는 것이 아니다.** 이번 작업은 **미리 써 둔 대본 세 편 중 문장에 맞는 것을 찾아
꺼내는 것**이다 — 키워드 대조다.

그래서 화면이 그 사실을 감추면 안 된다.

- 진행 막대의 뒤 세 칸은 지금 `목` 배지다. 대본이 맞으면 **`대본` 배지**로 바뀌고 문구는
  `의도 분석 → 대본 조회` · `마일스톤 분리 → 대본에서 읽음` · `태스크 생성 → 대본에서 읽음`이다.
  **어느 키워드가 맞아서 어느 대본이 골라졌는지**를 그 자리에서 보여준다.
- 맞는 대본이 없으면 **없다고 한다.** 비슷한 것을 억지로 고르지 않는다. 게이트웨이가
  `command_result`로 `no_script_match`를 돌려주고 상단 알림(`VZ-I-10`, 「탭①의 생성 실패」)에 올라간다.
- `REQ-1207`(LLM 관여 표시)의 정신 그대로다 — 나중에 LLM이 들어오면 **대본 조회는 그 뒤의 대조군이자
  시연 안전망**으로 남는다. 둘이 화면에서 구별되어야 하므로 배지 이름을 지금 갈라 둔다.

**둘째 선 — 대본은 우리 목(B)이지만 탭②~⑤의 자리는 남의 자리(A)다.** 대본이 돌 때 탭②~⑤에
그려지는 수위·개도율·탐지 박스는 여전히 하드웨어·AI·백엔드가 줄 데이터의 **합성본**이다. 8/31 대조표의
A/B 분류는 바뀌지 않는다. 바뀌는 것은 「`scenario` 모드에서 **대본 등장 장비에 한해** 합성값을 그린다」는
예외 하나이고, 그 예외는 배지로 드러난다. **대본에 안 나오는 장비(`robot-02`·`sensor-04`·`actuator-02`…)는
대본 중에도 자리표시다.** 그래야 「이 값은 대본이 준 것」과 「이 자리는 아직 아무도 안 준 것」이 갈린다.

## 대본 세 편 — 사용자가 준 단계 그대로

**단계를 더하거나 빼지 않는다.** 실패 분기를 지어 넣지 않는다 — 사용자가 준 것은 성공 경로이고, 실패는
기존 결함 주입(`REQ-1409`)으로 사용자가 넣는다. 아래 시간(30초·10초·3분·10분)은 사용자가
「임의로 정한 것, 확정 아님」이라고 했다. **대본 파일에는 그 값을 그대로 적는다.** 시연에서 짧게
보이는 것은 **배속으로만** 한다 — 값을 줄여 적으면 대본이 거짓말이 된다.

마일스톤·태스크에는 **하드웨어 어휘를 넣지 않는다**(`REQ-1408`, `verify:hierarchy`가 잡는다).
`robot-01`·`camera-02` 같은 이름은 `assignedTargets`·`target`·액션 아이템에만 나온다.
태스크 종료는 **평가 통과로만** 성립한다(`REQ-1403`·`REQ-1505`) — 아래 표의 「평가로 끝나는 태스크」는
`awaiting_evaluation → done` 전이와 근거값을 반드시 기록에 남긴다.

### 넷째 편 — `MSN-260826-01`은 그대로 라이브러리에 든다

「415호에서 503호로 이동해줘」도 문장으로 통해야 한다. 파일은 **한 글자도 고치지 않는다**
(`verify:scenario`가 그 파일을 자리 수까지 검사한다). 대본 형식의 새 필드는 전부 **선택**이라 옛 파일이 그대로 유효해야 한다.
이 편은 `go1-02` 세계라 탭②~⑤에 아무것도 따라 움직이지 않는다 — **그것도 화면에 적는다**
(「이 대본은 구역 장비와 연결되지 않은 구판 세계입니다」).

## 대본 파일 형식 — 기존 위에 얹는다

`scenarios/MSN-260831-0N.json`. `src/model/types.ts`의 `Scenario`를 **확장**한다(대체가 아니다).
새 필드는 전부 선택이고, 아래 이름은 제안이다 — 더 나은 이름이 있으면 바꾸되 보고서에 적는다.

```
{
  "missionId": "MSN-260831-03",
  "title": "월류방어벽 자동 개폐",
  "world": "registry",                       ← 'registry' | 'legacy'. 옛 파일은 없으면 legacy
  "utterance": { "text": "...", "engine": "script", "confidence": ... },   ← 7.8 미결 그대로. 아래 §계약 참조
  "match": {
    "must": [["월류방어벽", "방어벽", "수문"]],   ← 바깥 배열 = AND, 안쪽 = OR (동의어·오인식 변형)
    "any":  ["가동", "개폐", "작동"],
    "normalize": "공백 제거 · 소문자"
  },
  "cast": ["sensor-01", "actuator-01"],       ← 탭②~⑤에서 그려도 되는 장비. 전부 registry.json에 실재해야 한다
  "durationSec": 420,
  "milestones": [...], "tasks": [...], "events": [...],     ← 기존과 같다. 마일스톤 상태는 정적으로 적지 않는다(아래 §탭①)
  "world_timeline": [                         ← 탭②~⑤용. 같은 atSec 축
    { "atSec": 0,   "entity": "sensor-01", "drive": { "water_level_m": 1.42 } },
    { "atSec": 30,  "entity": "sensor-01", "drive": { "water_level_m": 1.61 } },
    ...
  ],
  "commands": [                               ← CommandEngine을 실제로 통과하는 명령
    { "atSec": 95, "entity": "actuator-01", "action": "close_gate", "producedBy": "backend", "taskId": "T-13" }
  ],
  "map": { ... }                              ← 2편만. 503호 평면·카메라 시야·사각지대 칸
}
```

**`world_timeline`은 채널 봉투를 직접 적지 않는다.** 장치의 값을 「몰아 주는」 것이고, 실제 발행은 그 장치가
평소 쓰는 경로(`SensorDevice.publishNow()` 같은)로 나간다. 봉투(seq·ts·quality·coordinate_frame)와
캐시 정책을 만드는 규칙이 허브에 하나 있는데 대본이 봉투를 또 만들면 두 벌이 된다 — `mission-trace.ts`가
`hub.publish()`를 거치는 것과 같은 이유다. **대본이 도는 동안 등장 장비의 무작위 흔들림은 멈춘다**
(`sensor-01`의 랜덤 워크가 대본 값과 싸우면 안 된다). 대본이 끝나거나 닫히면 다시 흔들린다.

**`commands`는 `CommandEngine.submit()`을 실제로 통과한다.** 그래야 탭③에 4단계가 뜨고 `actuator_state`가
엔진에서 나온다. 발행 주체는 사람이 아니다 — 감사 필드의 actor는 임무 ID, `produced_by`는 대본이 적은 값
(`backend` — 중계자는 백엔드다, `plans.ts` 머리말 참조), `input_mode`는 `click`·`voice`가 아닌 것이어야 한다.
`voiceAudit.ts`가 `click | voice`만 허용하면 **하나 늘리되** 그 이유를 주석에 적고 `verify:voice-audit`이
그대로 통과해야 한다. 임무가 낸 명령이 사람이 누른 것처럼 감사에 남으면 안 된다.

## 흐름 — 문장에서 재생까지

```
발화 패널 (녹음 → STT → 수정 → 판정)  또는  문장 직접 넣기
   │  issueCommand({ action: 'mission_from_utterance', params: { text } })   ← 출구 하나, 고치지 않는다

   └─ 있음 → 계획 제안 (PlanEngine.propose 에 대본을 넣는다 · decision = pending)
              │   탭①에 마일스톤·태스크·하드웨어가 「제안」 상태로 뜬다. 진행 사건은 하나도 없다
              ▼
          승인 (VZ-U-07 · REQ-1506)   ← 거부하면 아무것도 재생되지 않는다
              │
              ▼
          재생 시작 — trace_event(탭①) + world_timeline(탭②~⑤) + commands(탭③) 를 배속으로
          렌더 모드 → scenario (자동) · 배지 「대본 재생 중 · 합성 데이터 · MSN-…」
              │
              ▼

```

- **매칭은 게이트웨이가 한다.** 라이브러리와 매처는 의존성 없는 순수 TS로 `src/scenarios/`(또는 그에 준하는
  한 곳)에 두고 게이트웨이와 브라우저가 **같은 파일**을 import 한다. 두 벌이면 갈라진다.
- **단독 빌드(게이트웨이 없음)에서도 문장 → 탭① 전환은 동작해야 한다.** 그때는 브라우저의 로컬 재생기가

  둘을 비교할 때 축이 달라진다.

## 탭① — 한 편에 박힌 것을 푼다

**화면 구조는 바꾸지 않는다.** HCI 전달본(`HANDOFF.md`)의 화면 다섯과 논의 항목 8건은 그대로다.
바꾸는 것은 「어느 대본이든 그릴 수 있게」 하는 것뿐이다.

- `src/data/scenario.ts`의 모듈 상수 `scenario`를 **현재 임무 저장소**로 바꾼다. `MSN-260826-01`이 기동 시
  기본이고(전달본 그대로), 대본이 승인되면 바뀐다. `main.tsx`·`shared/registry.ts`·`commandEgress.ts`
  (`entity` 기본값 `'MSN-260826-01'`)·`TopBar.tsx`·`AppShell.tsx`의 임무 이름 버튼이 전부 이 저장소를 본다.
- **손으로 적힌 값을 전부 없앤다**: `41`·`95`(되감기 시각) · `7건` · `MS-C`(배정 대상) · `T-31`·`T-35`.
  되감기 슬라이더의 최대는 `durationSec`, 그래프 진입은 **클릭한 마일스톤**의 태스크, 실패 화면은 실패한
  태스크가 있으면 그것, 없으면 「이 대본에는 실패가 없습니다 — 결함 주입으로 만들 수 있습니다」.
- **마일스톤 상태는 정적 필드가 아니라 태스크 상태를 접은 결과다.** 지금 `MSN-260826-01.json`은 마일스톤에
  `status`를 손으로 적어 두었는데 되감기하면 태스크는 되돌아가고 마일스톤은 그대로라 서로 안 맞는다.
  `statusesAt(t)`가 마일스톤도 함께 돌려준다. 옛 파일의 정적 `status`는 무시하되 **지우지 않는다**.
- **재생을 실제로 받는다.** 지금 탭①은 게이트웨이의 `trace_event`를 받지 않고 번들의 `events`를 슬라이더로만
  본다. 이제 `TraceStore`에 `trace_event`가 쌓이고, 슬라이더에 **「따라가기(live)」** 위치가 생긴다 —
  재생 중에는 머리를 따라가고, 사용자가 뒤로 끌면 그 시점을 그린다(`REQ-1405` — 되감기 중 명령 차단은
  그대로). 재생이 끝나면 슬라이더는 지금과 똑같은 되감기 도구다.
- 하드웨어 패널: `world: 'registry'` 대본은 `cast` 장비를 보여주고 원천 표기는 `registry.json (목)`,
  `legacy` 대본은 지금처럼 `임무 시나리오 (목)`. 카드 3행은 여전히 자리표시다(8/31 결정, `VZ-D-07`).
  **탭①이 `tabs/data/`를 import 하면 단독 빌드가 오염된다** — `cast`는 대본 파일에서 읽고, 실재 여부는
  검증 스크립트가 `registry.json`과 대조한다.
- 발화 패널: 대본이 맞으면 `대본` 배지와 **맞은 키워드·고른 대본 ID**를 보여준다(§이것은 LLM이 아니다).
  제안 상태에서 승인·거부 버튼은 기존 `PlanApproval`(`VZ-U-07`)을 쓴다 — 새 승인 UI를 만들지 않는다.

### 1단계 — 대본 세 편 (코드보다 먼저)

파일 셋을 쓰고 **`verify:script-library`**를 먼저 만든다. 검사할 것:
`cast`·`world_timeline.entity`·`commands.entity`가 전부 `registry.json`에 실재 / `atSec` 단조 증가 /
`commands.action`이 그 장비의 `ACTION_CATALOG`에 있음 / 마일스톤·태스크 제목에 하드웨어 어휘 없음
(`verify:hierarchy`는 **계약 스키마**가 하드웨어 필드를 거부하는지를 보는 것이라 제목 문구는 안 본다 —
`registry.json`의 entity ID·`display_name`·`entity_type`이 제목에 나오면 실패하는 검사를 **새로** 둔다) / 평가로 끝나는 태스크마다 `awaiting_evaluation → done`과 근거값 /
2편의 `derived` 사건에 `derived_from`·`attempt: 2` / `match.must`가 비어 있지 않음 /
**세 문장이 각각 자기 대본에만 맞고**, 「415호에서 503호로 이동해줘」는 넷째 편에만 맞고,
「안녕하세요」는 아무 대본에도 안 맞음. 음성 대조군 포함 — 검사를 무력화한 사본이 실패로 잡히는가.

**판정**: 세 편이 이 검사를 통과한다. 화면은 아직 안 건드렸다.

### 2단계 — 매처와 게이트웨이
