# MK2 엣지 점검 — 로봇–엣지만 도는 지금, 엣지에 있어야 할 것이 깔려 있고 도는가

작성 2026-11-19 · 이대규(BE) · 점검 대상: **지금 로봇이 붙어 도는 엣지 기기**(아래 0-2)
**팀 내부 공유용 — 저장소에 올리지 않는다.** 주소를 실제 값으로 적었다(토큰은 이 점검에 필요 없어 적지 않았다).

> **이 문서는 읽기만 한다.** 설치 · 설정 변경 · 서비스 켜고 끄기가 없다. 결과를 파일로 남기고, 그 결과를 보고
> 무엇을 깔지 · 켤지는 그다음에 정한다(4장). 서버 연결(원격)은 이 점검이 끝난 뒤의 일이다(5장).

---

## 0. 왜 · 어디서

### 0-1. 왜 이 점검을 하나

- 원래 MK2 는 **로봇 → 엣지(노트북) → 서버** 였다. 지금은 **로봇 → 엣지** 까지만 돈다. 서버를 안 거치는 것은 괜찮다 — 목적은 잘 도는 것이다.
- 그런데 MK2 설계는 엣지에 **MQTT 브로커만 두지 않았다.** 관측(OpenTelemetry Collector · 엣지 Prometheus), 업무 데이터 브릿지, 엣지 가용성 신호 같은
  것을 **엣지에** 두기로 했다(1장). 그중 무엇이 지금 엣지에 **깔려 있고(설치)** · **떠 있고(실행)** · **제 일을 하는지(동작)** 를 모른다.
- 그래서 먼저 엣지만 확실하게 짚는다. 서버 쪽(원격 연결)은 그다음이다.

### 0-2. 어느 기기에서 하나

## 1. MK2 가 데이터를 어떻게 다루기로 했나 — 설계 요약

근거: BE 저장소 `docs/be/00-architecture.md` §2 · §3 · §4 · §5 · §8-3 · `docs/be/01-standalone-implementation-plan.md` Phase 3 ·

### 1-1. 데이터 세 갈래 — 갈래마다 길이 따로다

| 갈래 | 말단 → 엣지 | 엣지 안 | 엣지 → 서버 | 서버 안(저장) | 화면 |
|---|---|---|---|---|---|
| **업무**(상태 · 생존 · 심박 · 명령) | MQTT `1883` | **Mosquitto** · **MQTT→Kafka 브릿지**(검증 · 격리) | Kafka `100.102.8.102:9095` | 계측 → TSDB · 감사 · 레지스트리 · 임무 실행 기록 → MySQL | WS `8765/state` |
| **관측**(metric · log · trace) | OTLP gRPC `4317` | **OTel Collector(Agent)** · **엣지 Prometheus**(metric 원본 보관) | metric 은 **서버가 엣지에서 요약만 당긴다**(페더레이션 — 서버 → 엣지 `9090`) · log · trace 는 원본 그대로 서버 Collector `4316` | Prometheus · Loki · Tempo | Grafana |
| **영상** | RTP/UDP `5004` | **미디어 게이트웨이**(홉1 수신 · 프레임 재조립 · 번호 · 시각) | WS `8766/ingest`(홉2) | 저장 안 함(중계만) | WS `8765/media` |

- 세 갈래는 **같은 엣지를 지나지만 엣지 안에서 다른 프로그램**이다. 하나가 죽어도 다른 둘은 흐른다.
- 엣지 → 서버는 전부 **엣지가 서버로 나가는 방향**이다. **예외 하나 — 관측 metric 페더레이션은 서버가 엣지 `9090` 으로 들어온다**(엣지 방화벽에 서버 주소를 열어야 한다).

### 1-2. 관측은 세 층이다 — 어디서 만들고 어디에 쌓나

| 층 | 무엇 | 만드는 곳 | 쌓는 곳 | 엣지와의 관계 |
|---|---|---|---|---|
| A. 백엔드 자기 관측 | 브릿지 · 저장 · 게이트웨이가 잘 도는가(`be_*`) | 서버의 BE 프로그램 | 서버 Prometheus · Loki | 엣지에서 도는 엣지 브릿지도 낼 수 있다(`MK2_OTEL_ENDPOINT`) — 지금 엣지 브릿지는 끄고 돌린다(빈칸 하나) |
| **B. 말단 노드 관측** | 노드 CPU · 메모리 · 디스크 · MQTT 발행 성공/실패 · 발행 지연 + 명령 경로 span | **말단**(HW `pi/common/otel_metrics.py` · `otel_trace.py`) | **엣지 Collector → 엣지 Prometheus(원본)** → 서버는 요약만(`hw_*` · `system_cpu/memory`) · log · trace 는 서버 Loki · Tempo | **엣지가 받는 층이다** — 이 점검의 핵심 |
| C. 업무 값의 관측 표현 | 수위 · 배터리 · 속도 같은 업무 값을 지표로도 | 값을 받은 쪽 — **지금 구현은 서버 저장 소비자(`backend/storage/derive.py`) 하나** | 서버 Prometheus | 엣지에는 구현이 없다 |

말단(B층)이 내는 다섯(HW `otel_metrics.py`) — 엣지 Prometheus 에서는 이름이 밑줄로 바뀌어 `system_cpu_utilization…` · `system_memory_utilization…` ·
`system_filesystem_free…` · `hw_publish_count_total` · `hw_publish_duration_…` 으로 보인다. resource 속성 `service.name = hw-<종류>-node` · `hw.entity_id` · `hw.node_id` · `hw.zone_id`.

정해 둔 규칙 셋(그대로 지킨다):
- **엣지 Prometheus 가 원본(raw)을 짊어진다** — 서버로 원본을 몰지 않는다(부하가 구역 수에 비례). 서버는 `/federate` 로 `hw_*` · `system_cpu/memory` 만 당긴다.
- **경계 표기** — 엣지 Prometheus 가 `external_labels` 로 `agg_layer="edge"` · `zone_id="zoneA"` 를 붙인다. 서버가 직접 모은 것에는 이 표가 없다(BE-S-06).
- **장치 생사 · 치명 오류는 요약에 섞지 않는다** — 페더레이션이 `up` 을 당기지 않는다. 생사의 주 신호는 MQTT LWT · 하트비트(업무 평면)다.

### 1-3. DB — 엣지에는 DB 를 두지 않는다

- TSDB · MySQL 은 **서버에만** 있다. Kafka 브로커도 엣지에 없다(브릿지가 서버 Kafka 로 원격으로 쓴다).
- 엣지에 남는 기록은 셋뿐이다 — ① 엣지 Prometheus 의 metric 원본(관측) ② 엣지 브릿지의 **격리 파일**(형식이 틀린 업무 메시지) · **미전송 파일**(서버로 못 보내고 버린 것)
  ③ (말단 쪽) HW 노드의 spool(브로커와 끊긴 동안 말단이 쌓는 것 — 5000건).

## 2. 점검 — 블록을 붙이고, 파일을 가져온다

- **기록은 손으로 옮기지 않는다.** 블록이 결과를 파일로 남긴다 — Windows `C:\mk2_edge\logs\edge_check_<시각>.txt` · Linux `~/mk2_edge/logs/edge_check_<시각>.txt`.
- 끝나면 그 파일을 이대규에게 준다(모을 곳: 이대규 PC `C:\Users\asdfa\physical mk2\Claude outputs\261021_실측재개\261119 엣지 점검\`). 메신저 · USB 어느 것이든 된다.
- **로봇 노드 · 엣지 프로그램을 평소처럼 켜 둔 상태에서** 한다(2-2 가 지금 흐르는 것을 본다).

### 2-1. Windows 엣지 — 깔려 있나 · 떠 있나 (일반 PowerShell, 관리자 아님)

PowerShell 창 하나에 **블록을 통째로** 붙인다. 파일 찾기 때문에 몇 분 걸릴 수 있다.

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8

& {
  "# MK2 엣지 점검 2-1 — $(Get-Date -Format 'yyyy-MM-dd HH:mm:ss')"

  "== 1 듣는 TCP 포트 (1883 MQTT · 9001 MQTT-WS · 4317/4318 OTLP · 8888/8889 Collector · 9090 Prometheus · 9105 가용성 · 6443 K3s)"

  "== 7 파이썬 · 패키지 (엣지 브릿지 · 관측에 쓰는 것)"
  py -0p
  $pys = @(Get-CimInstance Win32_Process -Filter "Name like 'python%'" | Select-Object -ExpandProperty ExecutablePath) + @("C:\mk2_edge\venv\Scripts\python.exe") |
    Where-Object { $_ -and (Test-Path $_) } | Select-Object -Unique

  "== 9-1 이 기기의 방화벽 — 프로그램으로 건 것"

  "== 10 WSL (K3s · 리눅스 쪽 엣지가 있나)"

  "# 끝 $(Get-Date -Format 'HH:mm:ss')"
```

- 빨간 오류 줄 몇 개(`tailscale` · `py` · `wsl` 이 없는 기기 등)는 「없다」 는 결과다. 그대로 둔다.

### 2-2. Windows 엣지 — 지금 제 일을 하나 (2분, 읽기만)

## 3. 결과 읽는 법 — 항목마다 세 칸

**깔려 있다**(설치) → **떠 있다**(실행) → **제 일을 한다**(동작). 앞 칸이 없으면 뒤 칸은 볼 것도 없다.

| # | 깔려 있다 | 떠 있다 | 제 일을 한다(서버 없이) |
|---|---|---|---|
| E1 Mosquitto | 2-1 「4」 에 `mosquitto.exe` · 「3」 서비스 / 2-3 「3」 | 「1」 에 `1883` 이 **`0.0.0.0`**(또는 그 기기 주소)로 — `127.0.0.1` 만이면 말단이 못 붙는다 · 「5」 에 `listener 1883 0.0.0.0` | 2-2 「E1」 에 `zoneA/robot/go1-001/state` · `…/status` · `…/heartbeat` 가 센다 · 「E1-2」 봉투에 `schema_version` · `source_id` · `node_id` · `zone_id` · `timestamp` |
| E2 엣지 브릿지 | 「8」 에 `backend\ingest\bridge.py` + `11-13 판인가 … True` · 「7」 에 `paho` · `confluent-kafka` · `jsonschema` | 「2-1」 명령줄에 `-m backend.ingest.bridge` | (서버가 있어야 — 다음 단계) |
| E3 Collector | 「4」 에 `otelcol*.exe` · 「6」 에 `otel*.yaml` | 「1」 에 `4317`(**`0.0.0.0`** — 말단이 다른 기기) · `8889` | 2-2 「E3」 에 `hw_*` · `system_*` 줄 · 「E3-1」 `otelcol_receiver_accepted_metric_points` 가 0 이 아니다 |
| E4 엣지 Prometheus | 「4」 에 `prometheus.exe` · 「6」 에 `prometheus*.yml` | 「1」 에 `9090` | 2-2 「E4」 `healthy` · 대상 `edge_collector up` · 설정에 `agg_layer: edge` · 질의에 `hw_*` · `system_*` 이 센다 |
| E5 K3s | 「10」 WSL 배포판 → 2-3 「2」 `k3s enabled=` · 「3」 | `k3s active` · 「1」 `6443` | 「9」 노드 목록(HW 범위) |
| E6 홉1 수신 | 「8」 에 `edge_rtp_receiver.py` 또는 `media_gateway.py` | 「1-1」 UDP `5004` 를 `python` 이 잡고 있다 | HW 수신단 로그 · 파일 크기(30초에 2MB 근처) |
| E7 홉2 | 「8」 에 `hop2_sender.py` · `edge_gateway.py` | — | (서버가 있어야 — 다음 단계) |
| E8 가용성 판정기 | 「8」 에 `availability.py` | 「1」 에 `9105` | 2-2 「E8」 에 장치별 줄 |
| T1 업무 목적지 | — | 2-4 `HW_BROKER_HOST` = 이 엣지의 주소 · 로그 `[접속] <주소>:1883` | 2-2 「E1」 과 맞물린다 |
| T2 말단 관측 | 2-4 「OpenTelemetry 가 있나」 = `있다` | `HW_OTEL_ENDPOINT=http://<이 엣지>:4317` · 로그 `[otel] … 로 15초마다 export` | 2-2 「E3」 에 그 노드의 `hw_*` |
| T3 영상 홉1 | — | `HW_MEDIA_SENDER=go1_relay` · `HW_MEDIA_DEST_HOST` = 이 엣지(또는 비어 있고 브로커가 이 엣지) | E6 과 맞물린다(`stream_start` 를 보낸 뒤) |

- **`HW_OTEL_ENDPOINT` 미설정 — 관측 발신 비활성** 이 찍히면 T2 는 꺼져 있는 것이다(설계상 기본값). 그러면 E3 · E4 가 떠 있어도 **말단 지표는 안 온다.**
- **`[otel] 초기화 실패(ModuleNotFoundError …)`** 는 주소는 넣었지만 그 환경에 패키지가 없다는 뜻이다(1-5 의 도커 이미지).

## 4. 결과가 나오면 — 정할 것 (지금은 정하지 않는다)

결과 파일을 보고 BE 가 항목별로 「있다 · 없다 · 반쯤」 을 정리한 뒤, 없는 것마다 무엇을 할지 고른다. 지금 보이는 갈림길만 적는다.

| 물음 | 이 점검으로 알게 되는 것 |
|---|---|
| E3 · E4(관측 스택)가 없으면 — 엣지에 깔 것인가, 서버 연결과 같이 할 것인가, 이번 범위에서 뺄 것인가 | 엣지 OS · 빈 포트 · 파이썬 유무(깔 수 있는 자리인지) |
| 깐다면 — 서버가 없는 동안 log · trace 는 어디로 보낼 것인가(서버 `4316` 으로 두면 재시도만 쌓인다) | Collector 가 이미 있다면 그 설정 |
| T2(말단 관측)를 켤 것인가 — HW 설정(`HW_OTEL_ENDPOINT`) + 도커 이미지에 패키지를 넣어야 한다 | 로봇 노드가 도커인지 systemd 인지 · 패키지 유무 |
| E8(가용성 판정기)를 엣지에서 돌릴 것인가 — 최종 판정은 서버(Phase 5)이고, 이름 `up` 을 그대로 내면 Prometheus 자동 `up` 과 부딪힌다(BE-S-03 gap ④ — `hw_entity_up` 개명 요청) | 이미 돌고 있는지 |
