## §1 회신 — 스키마 필드 확정

### 1-1. 요청: `pi/common/schema.py` 편집 4개

이 파일 하나만 고치면 전 노드에 반영된다(HW가 어댑터를 한 곳에 모아둔 설계 그대로다).

> **적용 범위 — 노드별 추가 작업 없음.** 이 4개는 `common/schema.py`의 `envelope()`·`iso_now()`·모듈 상단 플래그에만 있고, `envelope()`를 호출하는 **모든 노드**(`sensor_node`·`robot_node`·`actuator_node`·증강 `analyzer`)에 **일괄 자동 반영**된다. 노드마다 따로 고칠 것은 없다 — `schema.py` 한 파일이 전부다.

**① 순번 필드명 `seq` → `sequence_id`**

```python
# before
    if seq is not None:
        env["seq"] = seq
# after
    if seq is not None:
        env["sequence_id"] = seq
```

계약(`contracts/common/message.schema.json`)의 필드명이 `sequence_id`다. 이름이 다르면 백엔드는
그 필드를 **없는 것으로 취급**한다 — 오류가 나지 않고 순번 추적만 조용히 죽으므로 발견이 늦다.
`envelope(seq=...)` **인자 이름은 그대로 두었다** — 호출부(`node.py`·`analyzer.py`)는 무변경이다.

**② timestamp를 RFC3339 콜론 오프셋으로**

```python
# before
import time
def iso_now():
    return time.strftime("%Y-%m-%dT%H:%M:%S%z")
# after
from datetime import datetime, timezone
def iso_now():
    # 로컬 타임존 aware → 콜론 있는 오프셋(+09:00). RFC3339/계약 date-time 정합.
    return datetime.now(timezone.utc).astimezone().isoformat(timespec="seconds")
```

**이것이 4개 중 가장 중요하다.** `strftime("%z")`는 `+0900`을 내는데 계약의 `date-time` 포맷은
`+09:00`을 요구한다. 백엔드는 수신 즉시 포맷까지 실제로 검증하며(fail-closed), **불합격 메시지는
정상 토픽으로 재발행하지 않고 격리**한다. 즉 이 편집 전에는 **모든 메시지가 전량 격리**된다
(백엔드 음성 테스트에서 실제로 거부되는 것을 확인했다).

> 부수 효과: `schema.py`에서 `time` 모듈 사용처가 사라진다. 동작에는 지장이 없으나, `time`을
> 다른 곳에서 쓰지 않으면 린터(flake8 등)가 **unused import** 경고를 낼 수 있으니 CI 린트를
> 쓴다면 `import time`을 지우면 된다(안 써도 동작은 무해). 편집 전후 모두 `time.` 사용을 전수
> 확인했다.

**③ `device_id` 별칭 제거**

```python
LEGACY_DEVICE_ID = True   →   LEGACY_DEVICE_ID = False
```

§1.1의 "`source_id` 단일화 시점"에 대한 답이다 — **지금 확정한다.** 계약은 `source_id`를 정본으로
하고 `device_id` 별칭을 포함하지 않는다. 별칭이 계속 나가면 대역·저장이 낭비되고, 파서가 어느
쪽을 정본으로 볼지 모호해진다(HW가 지적한 그대로다).

**④ 봉투 계약 버전을 계약값으로**

```python
SCHEMA_VERSION = "1.3"   →   SCHEMA_VERSION = "1.0"
```

`1.3`은 드리프트다. 이 필드는 **봉투 계약의 버전**이지 펌웨어 버전이 아니다(펌웨어는
`fw_version`으로 이미 별도로 싣고 있다). 계약 현재 버전은 `1.0`이다.

### 1-2. `schema_version` 표기 규칙 (§1.2 "semver? 정수?"에 대한 답)

**`MAJOR.MINOR` 형식의 문자열**이다. 작성 시점의 값은 `"1.0"`.

> ⚠ **2026-09-10 현재 값은 `"1.1"`이다** — 선택 필드 `session_id` 추가(= 아래 기준대로 MINOR).
> 적용 방법은 [§6-2](#s6-2). **`"1.0"`도 계속 통과하므로 혼재 기간에 격리는 나지 않는다.**

- 스키마 정규식: `^[0-9]+\.[0-9]+$` — 정수 단독(`1`)도, PATCH 포함 semver(`1.0.0`)도 거부된다.
- 올리는 기준: **기존 필드의 의미·타입이 바뀌면** MAJOR 또는 MINOR를 올린다. 선택 필드 추가처럼
  구버전 소비자가 깨지지 않는 변경은 MINOR.
- 소유·발급은 백엔드다. HW는 계약이 올라갈 때 이 상수만 따라 바꾸면 된다.
- **HW가 계약 변경을 아는 방법:** 계약(`message.schema.json`) 버전이 올라가면 백엔드가
  인계 문서(이 문서 같은)나 커밋으로 통지한다. HW가 임의로 올리지 않는다 — 이번 `1.3`
  드리프트처럼 표기가 갈리는 것을 막기 위해서다.

### 1-3. `seq`(→`sequence_id`) 범위 (§1.3 "채널별 독립 순번 vs 전역"에 대한 답)

**현재의 채널별 독립 순번을 그대로 수용한다. HW는 바꾸지 않아도 된다.**

실측에서 확인된 현재 동작이다(같은 시각의 한 노드):

| 채널 | 순번 | 근거 |
|---|---|---|
| `heartbeat` | 12 | `BaseNode.hb_seq` |
| `state` | 1 | `BaseNode.seq` |
| `status`·LWT | **없음** | `envelope(identity)`를 순번 없이 호출 |

Phase 1은 이 값을 **실어 나르기만** 한다. 유실·역전 검출의 정확한 의미(채널별로 볼지, 소스별로
합칠지, 재기동 시 리셋 규칙을 어떻게 둘지)는 **백엔드 Phase 2(저장 2축)에서 확정**해 다시
회신한다. 그때 필요한 변경이 생기면 상수·설정 수준이지 구조 변경은 아닐 것으로 본다.

> ✅ **이 약속은 이행됐다 — [§6-1](#s6-1)을 보라.**
> Phase 2(저장 축)가 끝나 검출 단위와 채널별 의미가 확정됐고, 그에 따른 요청 하나
> (`session_id` 신설)가 [§6-2](#s6-2)에 있다.

`status`에 순번이 없는 것은 정상으로 받아들인다 — 봉투 필수 5필드
(`schema_version`·`source_id`·`node_id`·`zone_id`·`timestamp`)만 있으면 통과한다.

### 1-4. `device_id` 제거의 내부 영향 — HW 브랜치 전수 확인 결과

편집 ③이 HW 내부 소비자를 깨뜨리는지 백엔드가 코드로 확인했다. **둘 다 안전하다.**

| 위치 | 코드 | 판정 |
|---|---|---|
| `pi/edge/monitor.py:56` | `payload.get("source_id") or payload.get("device_id") or topic.split("/")[2]` | ✅ `source_id` 우선 |
| `pi/augment/analyzer.py:92` | `p.get("source_id") or p.get("device_id") or msg.topic.split("/")[2]` | ✅ `source_id` 우선 |

그 밖의 `device_id` 검출은 봉투와 무관하다 — protobuf 명령의 `Capability.device_id`,
`/etc/device_id` 파일 경로, 중복 채번 경보 문구.

**요청:** 위 2곳 외에 봉투의 `device_id`를 직접 읽는 소비자(대시보드·스크립트·노트북 코드 등)가
있으면 `source_id`로 갱신해 달라. 백엔드가 볼 수 있는 범위(HW 브랜치 `*.py`·`*.js`·`*.html`)
에서는 위 2곳이 전부였다.

**`seq` 이름 변경도 안전하다:** HW 전체에서 **봉투의 `seq` 필드를 읽는 소비자가 없다.** 검출된
`seq`는 전부 RTP 시퀀스 번호(미디어 경로, 무관)이거나 `envelope(seq=...)` 호출 인자였다.

### 1-5. 편집이 맞게 됐는지 확인하는 법 (HW 자가 확인)

백엔드 파이프라인 없이 HW 쪽에서만 확인할 수 있다. 편집 4개를 적용한 노드를 띄우고, **발행
로그**(노드가 찍는 발행 출력)나 **`mosquitto_sub`**(둘 중 편한 것)로 실제 나가는 봉투를 한 번
들여다보면 된다. 예:

```bash
# 브로커에서 한 채널을 잠깐 구독해 실제 봉투를 눈으로 확인
mosquitto_sub -h <브로커> -t 'zoneA/sensor/wl-001/state' -v
```

봉투에서 아래 4가지가 보이면 편집이 맞게 된 것이다:

1. `sequence_id` 키가 있다(편집 전 이름 `seq`가 **아니다**). — 편집 ①
2. `timestamp`가 `...T21:29:25+09:00`처럼 **콜론 있는 오프셋**이다(`+0900` 아님). — 편집 ②
3. `device_id` 키가 **없다**(`source_id`만 있다). — 편집 ③
4. `schema_version`이 `"1.0"`이다. — 편집 ④ → ⚠ **2026-09-10부터 목표값은 `"1.1"`**([§6-2](#s6-2))

`status` 채널은 `sequence_id`가 없어도 정상이다(§1-3). 나머지 세 가지(②③④)는 모든 채널에서
동일하게 보여야 한다.

> **`session_id`까지 적용했다면** 다섯 번째로 `session_id` 키가 보이고, **한 프로세스가 사는
> 동안 값이 같고 재시작하면 바뀐다**([§6-2](#s6-2)). `timestamp`에 밀리초까지 보이면
> [§6-9](#s6-9)의 권고까지 들어간 것이다.

## §2 회신 — 토픽 도메인 체계

HW는 MQTT만 발행하므로 **§2는 코드 변경이 없다.** 확인과 정보 전달이다.

### 2-1. `{domain}` 자리에 구역(zoneA) — 그대로 유지

현재 구조 `{zone}/{etype}/{eid}/{channel}`을 **확정으로 받는다.** 백엔드 ingest는 이 구조를 전제로
구독한다.

### 2-2. `{type}`(etype) 어휘 — `sensor / robot / actuator / analysis` 확인

이 넷을 그대로 쓴다. 백엔드는 **etype에 무관하게** 잡도록 구독하므로(§2-3), 어휘가 늘어도 백엔드
코드는 바뀌지 않는다.

### 2-3. 채널 이름 — 텔레메트리 3채널은 **한 칸을 더 쓰지 않는다**

백엔드 ingest의 구독 패턴은 정확히 셋이다:

```
+/+/+/state      +/+/+/status      +/+/+/heartbeat
```

MQTT의 `+`는 **한 계층만** 대응하므로 이 패턴은 **정확히 4칸인 토픽만** 잡는다. 따라서:

- `zoneA/sensor/wl-001/state` → 잡힌다.
- `zoneA/analysis/wl-001/state`(증강 분석) → **같은 경로로 잡힌다.** 백엔드 코드 변경 없음.
- `terminal/wl-001/downlink`(명령, 3칸) → **패턴에 안 맞아 배달 자체가 되지 않는다.**

§2.3의 걱정("`cmd/ack`처럼 한 칸 더 들어가는 채널이 와일드카드 구독에 영향")은 **소멸했다.**
명령 경로가 `common/physical_command.py`의 규약(`terminal/<device_id>/downlink|uplink` +
protobuf)으로 이동해 구 JSON `cmd/*` 채널이 폐기됐기 때문이다. 텔레메트리 평면과 명령 평면이
토픽 형태부터 분리되어, 백엔드는 명령을 **구독하지 않는 것으로** 격리한다.

**따라서 요청한다: 텔레메트리 채널은 4칸 구조를 유지하고, 계층을 더 파지 말아 달라.** 새 채널이
필요하면 백엔드에 먼저 알려 달라 — 채널이 늘면 Kafka 토픽과 저장 경로가 함께 생겨야 한다.

### 2-4. MQTT → Kafka 매핑 (§2.4에 대한 답)

**원본 미러가 아니다.** 채널별로 3개의 Kafka 토픽에 싣는다.

| MQTT 토픽 | Kafka 토픽 | 파티션 키 |
|---|---|---|
| `{zone}/{etype}/{eid}/state` | `mk2.telemetry.state` | `source_id` |
| `{zone}/{etype}/{eid}/status` | `mk2.telemetry.status` | `source_id` |
| `{zone}/{etype}/{eid}/heartbeat` | `mk2.telemetry.heartbeat` | `source_id` |

- **장치별·구역별 토픽을 만들지 않는다.** `zone_id`·`source_id`는 이미 봉투 안에 있고, 토픽에는
  **데이터의 성격(채널)만** 담는다. 구역·장치가 늘어도 토픽 수가 늘지 않는다.
- **파티션 키가 `source_id`**라 한 장치의 메시지는 항상 같은 파티션에 들어간다 → **장치별 순서가
  보장**된다. 이것이 `source_id`를 필수로 두는 실용적 이유다.
- **값은 HW가 보낸 JSON 바이트 그대로** 싣는다. 백엔드는 재직렬화하지 않는다(필드 순서·수치
  표현이 원본 그대로 보존된다).
- 이름은 점 구분 소문자이며 **언더스코어를 섞지 않는다**(Kafka 메트릭 이름 변환 충돌 회피).

**HW 코드 변경은 필요 없다.** 이 매핑은 백엔드 내부 규약이다.

## §3 백엔드 수신 규약 — HW가 알아두면 좋은 것

1. **수신 즉시 봉투를 strict 검증한다(포맷 포함).** 필수 5필드와 `date-time` 형식을 실제로
   assert한다. 전환기·관용 모드는 없다.

## §4 검증 결과 — 이 회신의 근거

편집 4개를 적용한 `sensor_node`(로컬 사본)를 **개발 PC에서 실행**해 **서버 Mosquitto로 발행**하고,
서버의 백엔드 파이프라인으로 관통시켰다. 실제 배치(말단=엣지 쪽, 브로커=서버)와 같은 방향이다.

| 항목 | 결과 |
|---|---|
| 관통 경로 | 노드(PC) → MQTT → ingest 봉투 검증 → Kafka 3토픽 → 저장 sink + WebSocket push |
| 채널 | `state`(60초)·`status`(10초)·`heartbeat`(5초) **3채널 전부 도달** |
| 지속 | 약 13분 (heartbeat 순번 1→163 **연속, 유실 0**) |
| **봉투 검증 격리** | **0건** — 4편집 적용 후 단 한 건도 거부되지 않았다 |
| 실제 봉투 | `{"schema_version":"1.0","source_id":"wl-001","node_id":"DESKTOP-...","zone_id":"zoneA","timestamp":"2026-09-07T21:29:25+09:00","sequence_id":159,"channel":"heartbeat"}` |
| 버퍼(HW-R-09) | 접속 완료 전 첫 계측이 spool에 적재됐다가 접속 후 재전송되는 것을 확인 |
| 명령 경로 | `terminal/wl-001/*`는 백엔드가 구독하지 않아 무해하게 무시됨 |

`node_id`는 `/etc/node_id`가 없어 hostname으로 채워졌다(설계된 폴백). 실배포에서는 `/etc/node_id`
또는 `HW_NODE_ID`로 지정하면 된다.

### 6-1. `sequence_id` 의미 확정 (§1-3 약속 이행)

**HW가 지금 하는 대로가 맞다. 채널별 독립 순번을 그대로 확정한다.** 아래는 그 결정의 내용이고,
HW 쪽 변경은 §6-2(`session_id`) 하나뿐이다.

**① 검출 단위는 `(source_id, channel, session_id)` 다.**

- **채널마다 순번이 독립인 것이 맞다.** 카운터가 물리적으로 둘이기 때문이다 —
  `node.py:57`의 `self.seq`(state)와 `node.py:56`의 `self.hb_seq`(heartbeat). 소스별로 합치면
  **매 메시지가 갭으로 잡힌다.**
- **`session_id`가 구간의 경계다.** 프로세스가 다시 뜨면 순번이 0부터 시작하는데, 경계를 모르면
  그 리셋이 거대한 역전으로 보인다(§6-2).

**② `status`에 순번이 없는 것을 정상으로 확정한다. 검출 대상에서 아예 뺐다.**

`node.py:200`의 `publish_status()`가 `envelope(self.identity)`를 **순번 없이** 호출하고,
LWT(`node.py:92`)도 같다. 순번이 없으므로 셀 것이 없다 — 백엔드 갭 검출 질의가 `status` 채널을
명시적으로 제외한다. **HW는 여기에 순번을 붙이지 않아도 된다.**

**③ 갭이 곧 유실이 아니다. 채널·타입마다 다르게 판정한다.**

| 채널·타입 | QoS | spool | 백엔드 판정 | 근거(소스) |
|---|---|---|---|---|
| `state` (센서·액추에이터) | 1 | 탄다 | **유실 후보**(`loss_candidate`) | `sensor_node.py:113` qos=1 |
| `state` (로봇) | **0** | 탄다 | 갭은 세되 **유실로 단정하지 않는다** | `config.py:103` `ROBOT_STATE_QOS = 0` |
| `heartbeat` | 0 | **안 탄다** | 갭은 세되 **유실로 단정하지 않는다** | `node.py:237` `qos=0, allow_spool=False` |
| `status` | 1 | 안 탄다 | **검출 제외**(순번 없음) | `node.py:200`·`:217` |
| `state` (증강 분석) | 0 | — | **검출 제외**(전역 순번 공유) | `analyzer.py:38`·`:138` |

**하트비트 침묵을 장애로 단정하지 않는 이유가 하나 더 있다** — `robot_node.py`의
`heartbeat_enabled()`가 임무 중에는 하트비트를 **아예 끈다**. 그것이 설계이므로 백엔드가 그걸
장애로 읽으면 임무 중인 로봇이 전부 장애가 된다.

**④ 재전송 구간의 성긴 `state`는 유실이 아니다.**

`spool.py:91-116`의 `_downsample()`이 `kind == CONTINUOUS`인 레코드만 버킷당 1건으로 솎는다.
평시 `state`는 `reason == "periodic"`일 때 `CONTINUOUS`이므로(`sensor_node.py:102`), 두절 복구
구간에서는 **정상적으로 표본이 솎인다.** 백엔드는 `reason`과 `replayed`를 함께 저장해 이것을
유실과 구분한다 — **HW의 다운샘플 정책을 바꿀 필요가 없다.**

**⑤ 발행 실패로 spool에 들어가도 순번이 증가하는 것 — 그대로 두어도 된다(변경 요청 아님).**

백엔드는 순번을 **"발행 시도 번호"** 로 해석한다. 이 동작을 바꾸지 않아도 검출이 성립한다.

> **우리는 이렇게 읽었다:** 위 표의 QoS·spool 조합이 "이 채널의 유실은 설계된 동작인가"를 가른다.
> **답이 없으면:** 위 표대로 간다. 이미 구현·검증까지 끝냈다(`docs/be/queries/gap-detection.sql`).

### 6-2. 🟡 `session_id` 신설 요청 — `schema.py` **2줄**

**요청하는 변경은 이것이 전부다.** `envelope()` 한 곳이라 **전 노드에 자동 반영**되고 노드별
작업이 없다(편집 4개와 같은 성질이다).

```python
# pi/common/schema.py

# ① 모듈 전역에 한 줄 추가 (SCHEMA_VERSION 근처)
#    `import uuid` 는 이미 있다(schema.py:16) — 새 import 가 필요 없다.
SESSION_ID = uuid.uuid4().hex[:12]   # 프로세스 1회 기동을 가리킨다. 파일에 저장하지 않는다.

# ② envelope() 안에 한 줄 추가 (schema.py:121-127 의 dict)
def envelope(identity, seq=None, correlation_id=None):
    env = {
        "schema_version": SCHEMA_VERSION,
        "source_id": identity.entity_id,
        "node_id": identity.node_id,
        "zone_id": identity.zone_id,
        "timestamp": iso_now(),
        "session_id": SESSION_ID,        # ← 추가
    }
```

**왜 `birth` 경계로는 부족한가 — 오판이 두 방향이다.**

`_on_connect`가 항상 `publish_status("birth")`를 부르므로(`node.py:122`) `birth`는 신뢰할 수 있는
표식이다. 백엔드는 지금 그것을 폴백 경계로 쓴다. 문제는 **`birth`가 프로세스 재시작이 아닐 때도
나간다**는 것이다:

- 브로커가 끊겼다 다시 붙으면 → `_on_connect` 재호출 → `birth` 발행. **그런데 프로세스는 살아
  있어서 `self.seq`는 이어진다.** → 순번이 안 끊겼는데 구간만 쪼개진다.
- 구역이 바뀌면 `node.py:258`이 `self._connect()`를 다시 부른다 → 역시 `birth`. 순번은 유지된다.

`session_id`는 **프로세스가 다시 떴을 때만** 바뀌므로 순번 리셋과 정확히 같이 움직인다.
그리고 spool 재전송분이 **원래 세션을 달고 오는** 것도 이 방식의 이점이다 — 재전송을 새 구간으로
오해하지 않는다.

**함께 갱신할 것 — 편집 ④의 목표값이 바뀌었다.**

```python
SCHEMA_VERSION = "1.3"   →   "1.1"      # §1-1 편집 ④의 "1.0" 이 아니다
```

규격이 이번에 **1.1로 올랐다**(선택 필드 `session_id` 추가 = 버전 정책상 MINOR). §1-2에 적은
기준 그대로다. **`"1.0"`도 계속 통과하므로 혼재 기간에 격리는 나지 않는다** — 정규식이
`^[0-9]+\.[0-9]+$`이고, 백엔드가 `"1.0"`·`"1.1"` 양쪽을 통과시키는 것을 테스트로 못 박아 두었다.

> **우리는 이렇게 읽었다:** `SESSION_ID`는 프로세스 수명과 같아야 하므로 **모듈 전역**이 맞고,
> 파일에 저장하면 안 된다(저장하면 재시작해도 같은 값이 되어 의미가 사라진다).
> **답이 없으면:** 백엔드는 `status`의 `birth`를 경계로 쓰는 **폴백 경로로 계속 돈다.** 이미
> 구현·검증돼 있어 데이터가 사라지지는 않는다. 다만 위의 두 오판이 남는다.

### 6-5. ⚪ `origin_kind`·`entity_id` 미발행 — 그리고 **요구사항 사본이 낡았다**

`schema.py:119-134`의 `envelope()`에는 이 둘이 없다. Phase 1·2 실측 공통 헤더에서도 확인했다.

**`origin_kind` (실물/시뮬 구분) — 구현 누락이 아니라 요구사항 사본의 문제다.**
근거 요구사항인 **BE-C-07(원천 종류 표기 규약)이 HW 브랜치의 요구사항 정의서 사본에 없다.**
전체 공유 스프레드시트에는 있다. 즉 HW는 **애초에 이 항목을 받지 못했다.**

> §6-10과 모순처럼 보일 수 있어 정리한다. HW 브랜치 사본은 **HW 자기 행(HW-*)은 더 새롭지만**
> (HW가 직접 개정했으므로), **다른 파트 행(BE-*·AI-*)은 그 뒤 동기화되지 않았다.** BE-C-07이
> 그 예다. 그래서 §6-10에서 "HW 사본을 전체 시트에 반영해 달라"(HW 행 방향)고 하면서, 여기서는
> "BE 행은 전체 시트가 기준"이라고 하는 것이다 — 방향이 반대인 두 요청이 아니라 **같은 사본이
> 행마다 신구가 다르다**는 한 사실이다.

**`entity_id` — 지금은 무해하다.** 선택 필드이고, 백엔드는 대장의 키를 **공통 헤더의
`source_id`** 로 잡았다(공통 헤더가 필수로 보장하는 값이 그것뿐이라서). 다만 **노드 하나에 개체가
여럿인 배포**에서는 필요해진다.

> **우리는 이렇게 읽었다:** 둘 다 선택 필드이므로 지금 안 보내도 저장·검증이 깨지지 않는다.
> 실제로 두 칼럼은 실노드 데이터에서 `NULL`이고 **그것이 정상**이다.
> **답이 없으면:** `origin_kind` 미기재는 조회 시 **`real`(실물)로 해석**한다. `entity_id`는
> `NULL`로 둔다. 둘 다 백엔드가 임의로 채워 넣지 않는다 — 채우면 "생산자가 안 보낸 것"과
> "백엔드가 채운 것"을 나중에 구분할 수 없다.

> **우리는 이렇게 읽었다:** 이건 유실이 아니라 생산자 구조다.
> **답이 없으면:** 백엔드는 증강 분석을 **갭 검출 대상에서 제외**한다(이미 그렇게 구현했다).
> 대상별 순번이 필요해지면 `seq`를 `dev`별 dict로 바꾸면 되지만, **지금 요청하지 않는다** —
> 검출에서 뺐으므로 얻는 것이 없다.

**③ `Identity(dev, node_id, ZONE, "", "", "analysis")` — 빈 `mac`·`ip`가 들어온다.**

`analyzer.py:123`이 `mac`·`ip`를 빈 문자열로 만든다. **백엔드가 가드를 넣었다** — 빈 문자열이
오면 대장의 기존 값을 **덮지 않는다**(음성 대조 테스트로 확인). 그래서 지금 당장의 피해는 없다.

한 가지 덧붙인다: 확인해 보니 **`analyzer`는 `status`를 발행하지 않는다**(`c.publish`가
`:136` 한 곳뿐). 그래서 이 빈 값이 실제로 대장까지 도달하는 경로는 **현재 없다.** 가드는
그래도 넣어 두었다 — 나중에 `analyzer`가 `BaseNode`를 상속하게 되면 바로 도달한다.

> **우리는 이렇게 읽었다:** 증강 분석은 물리 노드가 아니라 **파생 워크로드**라 `mac`·`ip`를
> 가질 이유가 없고, 빈 문자열은 "없다"는 뜻으로 읽었다. 값을 채우라는 요청이 아니다.
> **답이 없으면:** 백엔드 가드로 계속 막는다. HW 변경 없이 안전하다.

### 6-7. 🟡 `state`의 `reason` 어휘 확인 요청

> **묻는 것:** 아래 표가 **맞는지, 그리고 늘어날 계획이 있는지.**
> **우리는 이렇게 읽었다:** 세 노드의 `_publish_state()` 호출부에 문자열 리터럴로 박힌 값을
> 전수 읽었다. 설정·환경변수로 바뀌는 값은 없었다.

| 타입 | 어휘 | 개수 | 근거 |
|---|---|---|---|
| 센서 | `periodic` · `threshold_exceeded` · `threshold_cleared` · `rapid_change` | **4** | `sensor_node.py:84-87` |
| 로봇 | `periodic` · `mode_changed` · `battery_low` | **3** | `robot_node.py:76`·`:120`·`:126` |
| 액추에이터 | `periodic` · `progress` · `state_{idle\|moving\|done\|error\|unknown}` | **7** | `actuator_node.py:77-78`·`:119`, 상태 5종은 `actuator_link.py:26` |

**저장 층이 `periodic`을 특별히 본다.** 재전송 구간의 `periodic`은 다운샘플로 솎인 것이지
유실이 아니라는 판정의 근거가 이 값이다(§6-1 ④).

> ⚠ **어휘가 늘어도 격리되지 않게 만들어 두었다.** `reason`·`device_status`·`actuator_state`를
> **`enum`으로 고정하지 않았다.** `additionalProperties: false`를 안 쓰는 것과 같은 이유다 —
> 어휘가 하나 늘면 전량 격리되는 사고를 만들지 않기 위해서다. 관측된 어휘는 스키마의
> `$comment`에만 적어 두었다.
>
> **답이 없으면:** 위 표를 관측된 어휘로 문서에만 남기고 **검증에는 쓰지 않는다.** 새 값이
> 와도 통과한다.

**액추에이터에 헷갈리는 자리가 하나 있다(정보):** `progress`는 **필드 이름이자 `reason` 값**이다.
필드 `progress`는 0.0~1.0 진행률이고(`actuator_node.py:98`), `reason: "progress"`는 "동작 중 진행
보고"라는 뜻이다(`:77`). 스키마 설명에 둘을 구분해 적어 두었다.

### 6-8. 본문 항목 목록과 누락값 형태 — 확정 통지

**§3의 3번 항목이 미뤄 둔 것을 여기서 닫는다.** 본문 규격 6종을 신설하고 백엔드 ingest에
**2단 검증**(공통 헤더 → 본문)을 켰다. 항목은 전부 HW 소스에서 그대로 읽었다.

| 채널·타입 | 필수 | 선택 | 근거 |
|---|---|---|---|
| `state`/sensor | `reason`·`device_status`·`water_level_m`·`unit`·`alert`·`mode` | `replayed` | `sensor_node.py:103-112` |
| `state`/robot | `reason`·`device_status`·`battery_pct`·`position`·`speed_mps`·`robot_mode`·`internal_seq` | `mission`·`replayed` | `robot_node.py:99-113` |
| `state`/actuator | `reason`·`device_status`·`actuator_state`·`position`·`progress`·`feedback_ok`·`control_locked` | `lock_reason`(null 허용)·`detail`·`replayed` | `actuator_node.py:92-105` |
| `state`/analysis | `subject_id`·`value`·`window_s`·`samples`·`above_threshold`·`threshold_m` | `trend_m_per_min`(null)·`eta_to_threshold_min`(null) | `analyzer.py:125-135` |
| `status` (공통) | **`event`·`status` 둘뿐** | `device_status`·`registration`·`uptime_s`·`buffer`·`publish_failures`·`reason` + 노드 고유 필드 | `node.py:201-212` |
| `heartbeat` | (없음) | — | `node.py:234-235` |

**HW가 알아야 할 규칙 넷:**

1. **모르는 필드는 통과한다.** `additionalProperties`를 `false`로 두지 **않았다.**
   `status_extra()`(`node.py:212`)가 노드마다 다른 필드를 반환하도록 설계된 훅이라 **필드가 느는
   것이 정상 동작**이기 때문이다. 실측으로 확인했다 — 센서의 `mode`·`mode_source`·
   `report_interval_s`·`alert`·`last_value`는 규격에 선언돼 있지 않은데 통과했다.
2. **필수 필드 누락은 격리된다.** 저장 층이 값의 존재를 가정하려면 이건 막아야 한다.
   음성 대조로 확인했다 — `device_status`가 빠진 로봇 `state`가 실제로 격리됐고 Kafka 토픽에
   나타나지 않았다.
3. **`status`의 필수를 `event`·`status` 둘로만 잡은 이유는 LWT다.** LWT 본문에는 `registration`도
   `buffer`도 없다(`node.py:92-94`). 세게 걸면 **급사 신호가 격리된다.**
4. **`event` 어휘를 5종으로 읽었다** — `birth`·`summary`·`rebirth`·`shutdown`(`node.py:203`,
   `rebirth`는 `:260`) + LWT의 `death`(`node.py:93`). 이것도 `enum`으로 고정하지 않았다.

**누락값 표현 — 구분이 필요한 항목은 둘로 확정했다.**

| 항목 | 형태 | 왜 |
|---|---|---|
| `state`의 계측값(`water_level_m`·`battery_pct` 등) | `{value, state}` (`unsupported` / `unavailable`) | 센서 읽기가 실패하면 **발행 자체가 안 되고**(`sensor_node.py:66-72`의 `except → return`), 3회 연속이면 `device_status`가 `fault`가 된다. 화면은 "센서 없음"과 "센서 고장"을 달리 그려야 한다 |
| `status.registration` | `{value, state}` | LWT엔 **원래 없다**(`unsupported`) vs 있어야 하는데 없다(`unavailable`) |
| **나머지 전부** | 명시적 `null` | `status.buffer`는 `node.py:208`에서 항상 채워지고 빠지는 경우가 LWT뿐이라 `registration`과 중복 → 기본형으로 내렸다 |

> **우리는 이렇게 읽었다:** 위 표의 항목은 각 노드의 `payload.update({...})`에서 **그대로** 읽었다
> — 표는 요약이고 소스가 근거다. 필수/선택의 경계는 "그 노드가 **항상** 싣는가"로 갈랐다.
> **HW가 지금 할 일은 없다.** 누락값 형태는 **값이 없을 때만** 쓰는 표현이고, 현재 노드는 값이
> 있을 때만 발행하므로 현행 코드가 그대로 통과한다. 다만 **이 목록과 다르게 읽은 항목이 있으면
> 알려 달라** — 특히 "항상 싣는다"고 본 필수 항목 중 조건부인 것이 있다면.
> **답이 없으면:** 위 확정대로 간다. 이미 구현·검증까지 끝냈다.

### 6-9. ⚪ `timestamp` 해상도 권고 — `seconds` → `milliseconds`

`schema.py:34`의 `iso_now()`가 초 해상도다(`strftime("%Y-%m-%dT%H:%M:%S%z")`, 편집 ② 후에도
`timespec="seconds"`면 같다). **로봇 20Hz면 1초에 20건이 같은 `timestamp`를 갖는다.**

**저장에는 문제가 없다** — 유일 키를 도착 좌표로 잡았기 때문이다(§6-4). 영향은 둘이다:

- `lag_s`(서버 도달 지연) 정밀도가 초 단위로 뭉갠다. 이 값은 재난 모드 지연 상한(BE-S-07)의
  측정 재료라 정밀도가 의미가 있다.
- 되감기 해상도가 초 단위가 된다.

고치는 법은 §6-3에 적었다 — **편집 ②와 같은 한 줄**이다.

> **우리는 이렇게 읽었다:** 초 해상도는 HW-S-08("모든 메시지에 타임스탬프")의 요구를 채우지만,
> 로봇 20Hz·액추에이터 20Hz(HW-A-01)에서는 **한 초 안의 순서를 시각으로 못 가른다.** 권고이지
> 요구가 아니다 — 저장은 순번·도착 좌표로 순서를 지킨다.
> **답이 없으면:** 초 해상도 그대로 받는다. 저장·검출은 정상 동작한다.

### 6-10. ⚪ 요청 — HW 브랜치의 요구사항 시트를 전체 공유 스프레드시트에 반영해 달라

백엔드 설계 세션(2026-09-09)에서 두 사본을 대조한 결과 **10곳이 어긋나 있고, 그 10곳이 HW
브랜치의 `SRS.md` §9.11 개정 6건 + `METHODOLOGY.md` §2-5 정정 4건과 정확히 일치**한다. 반대

> **답이 없으면:** 백엔드는 위 표대로 파트별 기준을 나눠 쓴다. 추적표에 그 기준을 명시해 두었다.

### 6-11. 🟡 증강 분석(K3s)은 「노드별 작업 없음」의 **예외다**

**§1-1과 §6-2에 적은 *"`envelope()` 한 곳이라 전 노드에 자동 반영되고 노드별 작업이 없다"* 는
증강 분석에는 성립하지 않는다.** 백엔드가 늦게 확인했다. 정정한다.

| 근거 | 내용 |
|---|---|
| `pi/augment/Dockerfile:20` | `COPY common/ /app/common/` — **`schema.py`가 이미지에 구워진다** |
| `pi/deploy/k8s/augment-analyzer.yaml:40-41` | `image: …@sha256:<digest>` + `imagePullPolicy: IfNotPresent` — **digest 고정** |
| `pi/augment/analyzer.py:27,124` | `from common import schema` → `schema.envelope(ident, seq=seq)` |

즉 **`schema.py`를 고쳐도 이미 배포된 파드는 옛 코드로 계속 돈다.** pi 노드 셋(센서·로봇·
액추에이터)은 systemd로 소스에서 바로 돌기 때문에 자동 반영이 맞지만, 증강 분석만 다르다.

**배포 형태에 따라 갈린다:**

| 매니페스트 | `schema.py` 변경 반영 방법 |
|---|---|
| `augment-analyzer-dev.yaml` | hostPath 마운트(`:33-44`) → **파드 재시작만으로 반영** |
| `augment-analyzer.yaml`(운영) | **재빌드 → digest 갱신 → 매니페스트 `image:` 교체 → 재배포**. 절차는 `pi/augment/build.sh`에 이미 있다 |

**지금 당장 급하지는 않다.** HW README 「다음 할 일」이 *"증강 컨테이너 이미지 빌드 — 현재는
매니페스트만"* 이라 적고 있고, 운영 매니페스트가 `REPLACE_WITH_DIGEST` 자리표시자이며, K3s
제어평면은 2026-08-31에 철수됐다(pi7이 원래 클러스터로 원복). **지금 증강 분석은 돌고 있지
않으므로 이 문제가 지금 발현되지 않는다.**

**문제는 나중이다.** 이미지를 빌드해 배포한 뒤 `schema.py`가 또 바뀌면(예: `session_id`)
**배포된 파드만 조용히 갈린다.** 그리고 공통 헤더 불합격은 **오류가 아니라 격리**라(§3의 2번)
증강 분석만 사라져도 눈에 띄지 않는다 — 원래 간헐 발행이라 부재를 알아채기 어렵다.

> **우리는 이렇게 읽었다:** 증강 층은 *"없어도 안전 루프 무사"*(`k3s/README.md:27`)이므로
> 이것이 안전을 해치지는 않는다. 다만 **수위 추세·임계 도달 예측이 통째로 사라진 채 넘어가는
> 것**을 막으려면 빌드 시점에 이 사실을 알고 있어야 한다.
> **답이 없으면:** 백엔드는 아무 조치도 하지 않는다. 이것은 질문이 아니라 **통지**다 —
> 이미지를 빌드·배포할 때 `schema.py`의 최신 상태가 들어갔는지 한 번만 확인해 달라.

- **`session_id` 경로**: HW가 아직 안 보내므로 **가짜 발행자로만** 확인했다. 실노드는 `birth`
  폴백 경로로 동작한다.
- **로봇·액추에이터·증강 분석 실노드**: 서버 브로커에 붙어 있지 않아 **가짜 발행자로만** 확인했다.
  본문은 HW 소스를 그대로 베꼈고 **증강 분석은 위 3건의 결함까지 그대로 재현**해 두었다 —
  결함을 고쳐서 흉내 내면 검증이 아무것도 확인하지 못하기 때문이다.
- **실노드 관통**: §6-3의 편집 4개가 들어와야 가능하다.

### 7-0. 한 장 요약

| 물음 | 답 |
|---|---|
| 실어 보낼 계획이 있는가 | **있다.** 백엔드가 만드는 모든 명령(`Command`)에 싣는다 |
| 형식은 W3C `traceparent`인가 | **그렇다.** W3C Trace Context의 `traceparent` **한 필드**(`00-<trace-id 32hex>-<span-id 16hex>-<flags 2hex>`). `tracestate`는 **싣지 않는다** |
| 어디에 싣나 | **protobuf 본문 필드** — `Command` 메시지에 `string traceparent` 1개 추가. Kafka 헤더·MQTT 속성이 아니다(아래 7-2) |
| 언제 | **실배선은 Phase 6.** `.proto` 개정은 `BACKEND_AGENDA` §3(문자열/열거형 파라미터) 때문에 어차피 한 번 하므로 **같은 개정에서 함께** 넣는다 |
| 답이 없으면 | **HW는 현행대로 두면 된다.** 필드가 없으면 새 trace를 시작하는 지금 동작(`otel_trace.py:76-79`)이 맞고, Phase 6에서 필드가 들어오면 그대로 이어 붙는다 |

### 7-1. 우리는 이렇게 읽었다

`otel_trace.py:16-21`은 *"백엔드가 명령 페이로드에 W3C `traceparent`를 실어 보내면 우리 span이 그 trace의
자식으로 붙는다 … 없으면 새 trace를 시작한다"* 이고, `:77`이 `TraceContextTextMapPropagator().extract(carrier=cmd)`로
**명령 본문에서 직접** 찾는다. 즉 HW는 이미 *"본문 안에 `traceparent` 키가 있다"* 를 전제로 짜 두었다.
우리는 그 전제를 **그대로 채택**한다 — 형식도 위치도 HW 코드가 기대하는 것과 같다.

### 7-2. 왜 본문인가 — Phase 2의 Kafka 헤더와 다른 이유

Phase 2에서 백엔드는 `ingest_at`·`entity_type`을 **Kafka 헤더**에 실었다(§6). 이유는 하나였다 — *"HW가 보낸
원본 JSON 바이트를 건드리지 않는다"*(재직렬화하면 원본이 사라진다). **명령은 그 조건이 성립하지 않는다.**
명령은 **백엔드가 만드는 메시지**라 지킬 원본이 없고, 만드는 쪽이 필드를 넣으면 그만이다. 게다가 HW의
`extract(carrier=cmd)`가 본문을 보도록 이미 짜여 있으므로, 본문 밖(MQTT 5 user property 등)에 실으면
HW가 그 자리를 읽는 코드를 **새로** 써야 한다. 본문이 양쪽 작업량이 가장 적다.

### 7-3. HW 작업량 — "코드 변경 없음"이 아니다 (셋)

protobuf는 미리 약속한 틀(`.proto`)에 맞춰 이진으로 싣는다. **틀에 없는 값은 넣을 자리 자체가 없다** —
JSON처럼 키 하나를 더 얹는 것과 다르다. 그래서 다음이 필요하다.

| # | 무엇 | 어디 | before → after |
|---|---|---|---|
| ① | `.proto`에 필드 1개 | `schema/physical_command.proto:28-34` `message Command` | `int64 deadline_unix_ms = 5;` 다음에 **`string traceparent = 6;  // W3C Trace Context. 비어 있으면 새 trace 시작`** — 번호는 제안값(7-4 ①) |
| ② | protobuf 객체 → dict 배선 한 줄 | `pi/common/otel_trace.py:77` | `extract(carrier=cmd)` → `extract(carrier={"traceparent": cmd.traceparent} if cmd.traceparent else {})`. **`carrier`는 `.get()`이 있는 매핑이어야 한다** — 지금 `_on_command(env.command)`(`physical_command.py:164`)가 넘기는 것은 protobuf `Command` 객체라 그대로 넣으면 `extract`가 실패한다 |
| ③ | 옛 말단 호환 확인 | — | proto3는 **모르는 필드를 무시**하므로 옛 말단이 새 필드가 붙은 명령을 받아도 파싱은 된다. 다만 HW가 배포 중인 말단에 그것이 실제로 성립하는지(pb 라이브러리 버전 포함) **확인 요청** |

> **정보 — 스냅샷 `260909`에서 확인한 것.** `node.py:52`가 `otel_trace.create()`로 추적기를 만들고 `:340`에서
> 닫지만, **`begin(cmd)`를 부르는 곳이 `pi/` 어디에도 없다**(`physical_command.py`의 `_on_command`·`_execute`
> 포함). `BACKEND_AGENDA` §10-3의 *"구현·검증 완료"* 가 이 스냅샷 뒤의 브랜치를 가리키는 것이라면 알려 달라 —
> 백엔드는 실배선(Phase 6) 때 그 브랜치를 근거로 대조한다.

### 7-4. 확인 요청 2건

| # | 물음 | 우리 제안(답이 없으면 이대로) |
|---|---|---|
| ① | **`.proto` 필드 번호를 누가 정하나** — `.proto`는 HW 소유(*"실제 통신의 source of truth"*, `physical_command.proto:2`)다 | HW가 정한다. 제안: `Command.traceparent = 6`. 백엔드는 HW가 확정한 `.proto`를 그대로 가져와 컴파일한다 — 백엔드 쪽 사본을 따로 두지 않는다 |

### 7-5. 시점과 순서

1. **Phase 6(명령·감사) 착수 시** 백엔드가 `command_id`(BE-X-01)와 함께 `traceparent`를 만들어 싣는다.
   백엔드 span은 Phase 3에서 만들지 않았다(테스트용 가짜 span 1건으로 Collector→Tempo 경로만 확인).
2. `.proto` 개정은 **§3(문자열/열거형 파라미터)와 한 번에** — 두 번 고치면 말단 재배포가 두 번이다.

### 8-0b. 먼저 — 미디어 평면은 봉투 규약 밖이다, 그리고 규격 초안 하나를 새로 연다

우리가 [§3](#)에서 통보한 *"수신 즉시 봉투를 **strict 검증**한다 … 전환기·관용 모드는 없다"*, *"불합격은 정상 토픽으로 재발행하지 않는다"*는 **MQTT 봉투(업무 평면)** 이야기다. **미디어 헤더는 그 규율을 따르지 않는다** — 예외를 먼저 적어 두지 않으면 HW가 같은 strict 규율을 기대한다.

| | 업무 평면(봉투) | 미디어 평면(방식 B 헤더) |
|---|---|---|
| 검증 | 공통 헤더 → 채널 본문 2단, strict | **필수·타입만**(`frame_ref`·`encoding`·`keyframe`·`width`·`height`). 값 어휘(`encoding`이 `h264`인지)는 **보지 않는다**, 페이로드는 **열지 않는다** |
| 불합격 처리 | 격리 파일 + `be.ingest.rejected` | **그 프레임만 버리고 연결은 유지**(`be.gateway.media_rejected{stage}`). 격리 파일 없음 |

그리고 §2에서 우리가 HW에 걸어 둔 *"새 채널이 필요하면 백엔드에 먼저 알려 달라"*의 **역방향**으로 통지한다 — **백엔드가 탐지 결과 규격 초안 `contracts/common/detections.schema.json`을 새로 열었다.** 생산자는 AI(진나영), 소비자는 가시화(김현우)이고, HW와 닿는 자리는 **온디바이스 안전 판단 결과(HW-R-04)를 그 형식으로 낼 때**뿐이다([8-4](#s8-4)). 채널·토픽은 아직 없다(Phase 6).

### 8-2. §10-7 회신 — 권고 ① 수용, 종단까지 native 코덱

**우리는 이렇게 읽었다:** HW는 Go1 5카메라의 H.264(464×400@30, 0.55Mbps/카메라)를 **디코드 없이 RTP로 중계**하는 `go1_relay`(RFC 6184)와 JPEG 경로(`rtp_jpeg`) **양끝을 다 만들어 놓고** 엣지 수신 코덱의 결정을 기다렸다. §10-7 표(지연 0.1ms vs 37ms+디코드, CPU 0.05 vs 0.65코어, 무선 대역 0.55 vs 3.6Mbps)가 근거다.

**답: ①.** 소스별로 native 코덱을 그대로 — 그리고 **엣지에서도 서버에서도 디코드하지 않고 뷰어까지 간다.** 우리 문서(v8 §5-10·`02-media-path.md` §1-2-2)의 *"JPEG로 통일. H.264 폐기"*는 근거 (1)이 *"엣지가 이미 JPEG를 쥐어 재인코딩이 필요하다"*였는데 **그 전제가 틀렸다**(엣지는 AU 재조립만 한다). 이번 Phase에서 그 문서를 정정했다. 뷰어는 JPEG를 `createImageBitmap`으로, H.264를 **WebCodecs**로 디코드한다 — 우리 확인용 뷰어에서 `avc1.42C01E` 디코드·표시를 실측했다.

**규격 — 미디어 헤더** [`media-header.schema.json`](../../contracts/common/media-header.schema.json) (예시 [`examples/media-header-*.json`](../../contracts/common/examples/)):

| 연결 | `ws://<서버 tailscale IP>:8766/ingest?source_id=<카메라 키>&token=<엣지 토큰>` — **엣지가 클라이언트**로 붙는다(엣지에 인바운드 불필요). 토큰은 별도 경로로 전달. 같은 `source_id`의 두 번째 연결은 4409로 거부 |

| 상한 | AU 하나 ≤ 8MB(`MK2_MEDIA_MAX_FRAME_BYTES`). 넘으면 그 프레임만 버린다 |

🔴 **AU 경계 판정과 `keyframe` 플래그는 HW 구현에 없다 — 우리가 새로 정하는 규칙이다.** `go1_relay.py:166`은 로봇 웹소켓 청크 하나를 `split_annexb`로 NAL로 자를 뿐 **청크 = AU**라고 믿고, `edge/media_gateway.py`는 RTP 마커로 프레임을 재조립하되 **NAL 타입으로 IDR 여부를 판정하는 코드가 양끝 어디에도 없다.** 위 표의 「AU 경계」·「`keyframe`」이 그 빈자리다 — **홉2 송신기 규격으로 요청한다**([8-10](#s8-10) ①).

**HW가 이미 가진 것이 어디에 쓰이나:** `go1_relay`·`media_gateway`는 **홉1 그대로**(pi7→엣지 RTP). C안(HTTP multipart, `go1_cam_view.py`의 MJPEG 대비 경로)은 우리 `02-media-path.md` §1-3-3의 **폴백 카드**다 — 이번에 구현하지 않았다.

**SDP는 홉1 사안이다 — `.proto`를 앞당기지 않는다.** §10-7 끝의 *"SDP는 말단이 세션 수립 시 명령 회신에 실어 보낸다"*는 pi7↔엣지(홉1) 이야기이고, HW가 `CommandStatus.detail`(`physical_command.proto:56`, 문자열)에 JSON을 넣는 우회를 이미 쓰고 있어(`mission-command.md` §3) 그것으로 충분하다. 홉2는 헤더의 `encoding`·`codec`으로 해결된다. ⚠ **근거를 넓힌다:** `CommandResult.result`(`:62`)뿐 아니라 **`Command.parameters`도 `map<string, double>`**(`:32`)이라 명령에 문자열을 실을 자리가 **애초에 없다.** 그래서 Phase 6의 `.proto` 개정 범위가 넓고(§3 문자열 파라미터·§7-3 `traceparent`·이것), **그 대신 `stream` 하나만 [8-11](#s8-11)의 우회로 먼저 푼다.**

### 8-2b. IDR 간격 실측 요청을 철회한다 — 대신 두 가지를 묻는다

우리 지시서 초안은 "IDR 간격을 실측해 달라"고 적었는데 **HW `pi/bench/go1_cam_view.py:38-39`에 실측이 이미 있다** — *"464x400 H.264 baseline, 도착 간격 33.3ms(30fps, p90 34.1 — 버스트 없음), 프레임 평균 2.4KB, 키프레임 약 0.48초 간격"*(pi7, 2026-08-31). 철회한다.

**대신 묻는다:**
1. **그 IDR 간격(≈0.5초 = GOP 15)이 `HW_*` 환경변수로 조절 가능한가.** 서버 drop-old는 GOP 경계에서만 버리고 IDR에서만 재개하므로, **느린 링크에서 뷰어 프레임률이 0.5초 단위로 끊긴다**(Phase 4 실측: 링크를 500kbit로 조이자 불연속 19개가 전부 IDR 위치). GOP를 줄이면 부드러워지고 대역이 는다 — 조절 손잡이가 있는지가 답이다.
2. **그 값이 로봇 펌웨어 인코더의 설정에서 오는 것이라면, 말단(pi7)에서 바꿀 수 있는가.** 없으면 그대로 두고 뷰어 쪽에서 감수한다.

⚠ **`go1_cam_view.py`를 「홉3 참조 구현」이라고 부르지 않는다.** 파일 자신이 *"운영 구성요소가 아니다 — 말단에서 영상이 실제로 나오는가를 사람이 확인하기 위한 것"*(`:5`)이라 적었고, 경로가 **나노 → pi7 → 브라우저**라 중앙 서버 구간이 통째로 빠져 있다. drop-old도 GOP 인지 상태기계가 아니라 **`QUEUE_MAX=8` 큐 길이 제한**(`:60`)이고 키프레임 여부를 보지 않는다(복구는 브라우저 `decodeQueueSize>30` 재동기, `:499`). **「기법 참조로 가치가 크다」** — WS 프레이밍·WebCodecs 클라이언트(`prefer-software` `:477-481`)·NTP식 시계 보정·브라우저 결함 5건 수정·**MJPEG 폴백**(`:172-`, WebCodecs 없는 브라우저로 자동 분기 — 단 파이에서 H.264→MJPEG **완전 재인코딩**이라 대가가 크다)이 전부 거기서 나왔고, 우리 확인용 뷰어와 VZ 통지에 그 다섯을 옮겨 적었다.

### 8-3. §8 회신 — `capture_timestamp`는 ISO 유지, epoch ms는 우리 문서 불일치였다

**답:** 기준은 [`frame-reference.schema.json`](../../contracts/common/frame-reference.schema.json) — `capture_timestamp`는 **ISO date-time 문자열**(콜론 있는 오프셋 + 밀리초 — HW `schema.py:55-60` `iso_now()`와 같은 규칙). **v8 §6-9의 "epoch ms 정수"가 규격 파일과 어긋난 것**이었고, 봉투 `timestamp`와 frame_ref가 같은 표기를 쓰는 것이 의도다. `02-media-path.md` §1-6-2 예시(`1735120000123`)는 이번 Phase에서 정정했고(회신 전에 커밋됨), 같은 서술이 있던 우리 plan·Phase 1 지시서도 고쳤다. v8 docx §6-9는 저장소 밖이라 따로 정정한다.

**HW에 부탁:** **SDD §5.5.2**(*"`capture_timestamp`는 epoch 밀리초 정수"*, `SDD.md:545`)와 **SRS §9.7 「해소된 미결」 O-8 행**(`SRS.md:678`)을 ISO로 맞춰 달라. HW 코드 변경은 없다 — HW는 frame_ref를 발급하지 않는다(§10-4 머리말).

**`capture_timestamp`의 뜻(규격 설명에 적었다):** **엣지가 프레임 경계(AU)를 확정한 시각**이다. 촬영 시각이 아니고, 말단 내부 지연(카메라→인코더→pi7→RTP→엣지 재조립)이 포함되며, 보정되지 않았다. 크기 근거로만 — HW `go1_cam_view.py`의 뷰어 지연 실측(순정 0.3~0.4초)이 그 상한의 감을 준다. 규격값이 아니다.

**사실 질문(답이 있으면 Phase 7 보정 설계가 사라진다):** **imageai 웹소켓 프레임(로봇 → pi7)에 Go1이 찍은 촬영 시각이 실려 있는가?** 있으면 엣지가 그것을 `capture_timestamp`로 옮겨 편향이 사라지고, 없으면 소스별 보정은 Phase 7(트윈)에서 다룬다.

### 8-4. §10-4 회신 — ㉰ 정합 등급을 규격에 둔다

§10-4는 하위 질문이 둘이다.

**ⓐ 선택지 ①②③ → ㉰(③ "백엔드가 정한 방식").** 탐지 메시지에 **메시지 단위 `alignment`**(string, 알려진 값 `frame`·`unaligned`는 `$comment` — enum 아님)를 둔다. **뷰어 규칙은 fail-safe**: `alignment=="frame"`이고 `frame_ref`가 있을 때만 프레임 정합, **그 외(부재·모르는 값 포함) 전부 unaligned**로 그린다(시각 근사 없이 "최신 프레임 위에 참고 표시"). ①의 "시각으로 근사 정합"은 쓰지 않는다 — 온디바이스 프레임은 엣지를 거치지 않아 `capture_timestamp`의 시각 축이 다르고, 근사 정합이 틀리면 **틀린 박스가 맞는 것처럼** 보인다. ②(오버레이 제외)는 ㉰의 부분집합이다 — `alignment`를 안 실으면 그렇게 된다. 온디바이스 결과의 `origin`은 `{tier:"device", kind:"safety_minimal"}`([`detections.schema.json`](../../contracts/common/detections.schema.json) 초안). **온디바이스 실물이 없어 이번에 검증하지 않았다** — HW 자신이 *"구현 전에 규약만 정하면 되는 사안"*이라 적은 그대로다.

**ⓑ "BE-C-03·VZ-I-07이 「HW가 frame_ref를 쓴다」를 전제하는데 v8 엣지 단일 발급과 어긋난다 — 어느 쪽으로 정리하나."** **두 요구사항의 문면을 「엣지가 발급한 frame_ref를 그대로 실어 나른다」로 읽는다.** 말단은 발급하지 않는다 — **하드웨어 쪽 조치는 없다.** 우리 추적표 BE-C-03에 그렇게 적었다. ⚠ SRS §9.10의 `rb-01_ondevice` 제안은 §10-4 머리말(*"하드웨어는 v8을 그대로 따른다"*)로 이미 철회된 것이므로 충돌로 다루지 않는다.

### 8-5. §10-5 회신 — q 우선. 해상도 변경은 스트림 재개 사건

**답: ① q 상향이 기본, ② 해상도 하향은 마지막 수단, ③ 프레임 간 압축 코덱 전환은 로봇에서 이미 답(H.264 native — 8-2).** 근거는 **HW 자신의 실측**(1080p q5→12: 9.7→5.5Mbps, CPU 불변 — `SRS.md:769`) + `go1_cam_view.py` 실측(464×400 H.264 프레임 평균 2.4KB). `HW_MEDIA_QUALITY` 선반영이 곧 답이다.

**해상도 변경이 "스트림 재개 사건"인 이유 셋:** ① 미디어 헤더 `width`/`height`와 탐지 `bbox_space.reference.width/height`(09-21 개명 전 `coord.ref_*`)의 기준이 바뀌어 **재선언**해야 한다 ② H.264면 SPS가 바뀌어 **새 IDR + 뷰어 디코더 재구성**이 필요하다 ③ AI가 **원본 해상도를 기대**한다(자르기·리사이즈·보정 금지, 탐지 튜닝이 464×400에 묶임 — 2026-09-17 대조 §4-2). 그래서 해상도는 값이 아니라 **세션 경계**다.

**대역 상한은 우리가 정하지 않는다** — 현장 회선 미실측이고 우리 `02-media-path.md` §3-2 「평면 간 QoS」는 미결 그대로다. Phase 4 실측은 연구실 링크를 `tc`로 500kbit까지 조인 한 조건뿐이다(그 조건에서 서버 drop-old가 IDR 경계로 재개하는 것까지 확인).

### 8-6. §10-6 회신 — 해석이 맞다. 소스가 정한다

**답: 맞다.** v8의 *"pull 기본"*은 이번 Phase에서 **"소스 종류별 정적 정책"**으로 손질했다(`02-media-path.md` §1-2-3) — 로봇은 push(명령을 받고 말단이 송출), 표준 IP 카메라는 pull(엣지가 RTSP 접속). **런타임 협상이 아니다** — HW가 `config.py`의 `MEDIA_SENDER` 한 줄로 정하는 그대로다. HW가 쓴 *"표준 IP 카메라만 pull(RTSP)"*을 **그대로 승인한다.**

⚠ **홉1의 push/pull과 홉2의 연결 방향은 다른 층이다.** 홉2(엣지→서버)는 **항상 엣지가 클라이언트**로 서버 `/ingest`에 붙는다 — 엣지에 인바운드를 열 필요가 없고, 서버는 엣지 주소를 몰라도 된다. 개폐 명령(HW-R-07 `stream`)의 **우리 쪽 배선은 Phase 6**이다 — 그리고 그 명령이 지금 규약 경로로 호출되지 않는다는 것이 [8-11](#s8-11)이다.

| tar.gz 하나 PUT, 서버가 아카이브 안 `manifest.json`을 꺼내 읽는다 | **PUT 두 번** — ① `PUT <base>/<세션>.manifest.json`(수 KB) → 2xx → ② `PUT <base>/<세션>.tar.gz` |

**이유:** `pack()`이 `tarfile`의 `sorted(listdir())` 순서로 묶어 매니페스트가 **수만 장의 JPEG 뒤**에 오고, gzip은 seek이 안 되므로 **0.7GB를 통째로 풀어야 한 줄을 읽는다.** 게다가 `json.dump`가 `pack()` **뒤**(`capture_upload.py:187-189`)라 아카이브 안에 들어가는 것은 *"그 시점 디렉터리에 있던 매니페스트"*다 — `go1_capture_teleop` 세션의 첫 실행이면 **아예 없고**, 재실행이면 직전 것이다. ⚠ *"`json.dump`를 `pack()` 앞으로 옮겨 달라"*는 요청은 **철회한다** — `man["frames"]["uri"]`(`:179`)가 업로드 성공 **뒤**에 채워지므로 앞으로만 옮기면 **HW 로컬 매니페스트에 업로드 주소가 영영 안 남는다**(옮기려면 dump가 두 번이어야 한다). **별도 PUT이 양쪽에 가장 싸다.**

**최종 저장 위치는 URL이 아니라 매니페스트가 정한다.** `http_put`이 `base_url + "/" + os.path.basename(path)`(`:120`)라 URL에는 `{세션디렉터리명}.tar.gz`만 실리고 **`entity_id`가 한 번도 실리지 않는다** — `session_id`는 `"{entity_id}/{name}"`(`:71`)인데 그 앞칸이 URL에 없어서, **로봇 2대가 같은 분에 세션을 시작하면 파일명이 같아 서로 덮어쓴다.** 그래서 서버는 ① 아카이브를 임시 파일로 받고 → ② **앞서 받은 매니페스트의 `source_id`·`session_id`로** 최종 경로 `<저장 루트>/<source_id>/<세션 마지막 칸>.tar.gz`를 정해 → ③ 원자적 rename 한다. 경로 순회 방어(`..`·`/`·절대경로·널바이트 거부, `session_id`의 첫 슬래시 하나만 허용)도 URL이 아니라 매니페스트 값에 건다.

**`frame_ref_base`는 채우지 않는다**(`:102` *"엣지가 디코드 시점에 발급"* — 촬영본은 엣지를 거치지 않으므로 발급 주체가 없다). 프레임 n의 시각은 매니페스트의 `t0_unix + (n-1)×interval_s`(`:91-93`) 그대로 쓴다. 매니페스트에 선택 필드 **`correlation_id`** 한 칸(어느 명령·임무의 촬영인지)을 받아 주면 저장한다 — 없으면 null.

**그전까지 HW 기본값(파이 로컬 적재)이 맞다.** 그리고 **촬영본이 세 곳에 쌓인다**(pi 로컬 · VZ `mission-history/images/robot/` · 우리 4b) — AI 저장본까지 포함한 중복 정리는 **Phase 5/6 안건**으로 올렸다(plan Phase 6 이월).

### 8-11. 🔴 신설 — `stream` 명령이 규약 경로로 호출되지 않는다

**사실:** `Command.parameters`가 `map<string, double>`(`physical_command.proto:32`)인데 `robot_node.py::validate()`(`:196-199`)가 `params.get("action")`이 문자열 `"start"`/`"stop"`이길 요구한다 → 규약 경로로 온 `stream`은 **ACK 이전에 100% `INVALID_ARGUMENT`(`invalid_stream_action`)로 거부**된다. 그런데 `stream`이 `ACTIONS`·`PHYSICAL_ACTIONS`(`:575-577`)에 등록돼 **Capability로는 「지원한다」고 선언**된다. HW `README.md`의 *"영상 온디맨드 6.8Mbps ✅"*는 **2026-09-03에 폐기된 레거시 JSON `cmd` 토픽**으로 한 검증이다(`HW-interface/README.md` §4).

**왜 지금 문제인가:** 이것이 **길 A(엣지가 붙어 계속 보내는 상시 송출 프로파일 — Phase 4 결정 10)를 실제 로봇으로 켜는 것**과 **Phase 6의 온디맨드 개폐 배선**을 **둘 다 막는다.** 우리 §5-1 표의 §3 행에 함정 자체는 적혀 있었으나 예시가 `set_mode`·`levee`뿐이라 `stream`이 같은 함정이라는 것을 아무도 연결하지 않았다 — 이번에 §5-1 §3 행을 고쳤다.

**요청:** `.proto` 개정 없이 **action 이름을 `stream_start` / `stream_stop`으로 쪼갠다** — HW가 `mission-command.md`(`:59-62` *"임무 종류는 문자열 파라미터가 아니라 action 이름 자체를 어휘로"*)에서 이미 쓰는 우회법이다. `robot_node.py:333`의 같은 원칙.

⚠ **무비용이 아니다 — 둘을 같이 옮겨야 한다:**
- ⓐ `dest_host`·`session_id`(`:544-547`)도 문자열이라 **명령별 목적지·세션 지정 능력을 잃는다** — 폴백(`config.MEDIA_DEST_HOST`, `f"s-{int(time.time())}"`)이 있으니 동작은 하지만, 세션 이름을 백엔드가 정해 줄 수 없다(Phase 6에서 `correlation_id`로 대신한다).
- ⓑ `validate()`의 **중복 start 가드**(`:194-195` *"이미 열린 스트림에 start를 또 보내면 두 번째 ffmpeg가 같은 포트로 붙어 엣지가 두 스트림을 섞어 받는다"* → `ALREADY_EXISTS`)를 **`stream_start`로 함께 옮겨 써야** 한다.

**답이 없으면:** 온디맨드 개폐는 Phase 6에서 `.proto` 개정(문자열 파라미터)까지 기다린다 — 그때까지 실물 로봇 영상은 HW가 손으로 `stream`을 켜는 방식으로만 홉1이 열린다.

#### 9-2-1. 🔴 팀 tailnet — **초대 구조가 아니다. 그리고 주소가 바뀐다**

**백엔드가 해 드릴 수 있는 것이 없다.** Tailscale 에서 tailnet 소속은 **로그인 계정**이 정한다. 기기는 *"로그인한 계정의 tailnet"* 에 들어간다.

우리 팀은 **기기 11대가 전부 팀 공용 구글 계정 하나 아래**에 있다(`_serverinfo/260916_phase3_tailscale.txt` — *"tailnet 계정: 팀 공용 구글 계정"*). 즉 **초대 링크를 받는 것이 아니라, 그 PC 에서 `tailscale up` 하고 브라우저가 뜨면 팀 공용 계정으로 로그인**하면 끝이다.

> **계정 자격증명은 김현우(VZ) 씨가 갖고 있다.** 그쪽에서 받으시면 된다.

**🔴 그리고 — 지금 주신 `<HW 개발 PC 구 주소(개인 tailnet)>` 은 쓸 수 없다.**

HW 문서가 직접 적었다 — *"이 PC의 tailscale이 **개인 계정**이라 팀 서버가 안 보입니다."* **tailnet 마다 주소를 따로 발급한다.** 팀 tailnet 에 합류하는 순간 **다른 `100.x.y.z` 를 받는다.**

그래서 넣었던 방화벽 세 줄(`8766`·`9095`·`4316` ← `<HW 개발 PC 구 주소(개인 tailnet)>`)은 **이미 지웠다.** 엉뚱한 주소를 열어 두는 것이 더 나쁘다.

**합류하신 뒤에 이 한 줄의 출력을 주시면 된다:**

```bash
tailscale ip -4
```

`100.` 으로 시작하는 주소 한 줄이 나온다. **그 값을 받는 즉시 세 줄을 다시 넣는다.** 넣었다 지운 것은 낭비가 아니라 **절차·문법 확인**이 됐다 — 주소만 갈아 끼우면 된다.

> 그때 **엣지 토큰**(`MK2_EDGE_TOKEN`)도 같이 보내겠다. 방화벽이 열려도 토큰이 없으면 `4401` 이다.

#### 9-2-2. `wl-001/20260910-134408` 삭제

**대조부터 했고, 같은 세션이 맞다. 차이가 정확히 1바이트다.**

```
go1-001/20260910-134408.tar.gz   1,274,114 B
wl-001 /20260910-134408.tar.gz   1,274,115 B      <- 1바이트 크다
```

**1.27 MB 아카이브 둘이 1바이트 차이**다 — 같은 촬영본을 매니페스트의 `source_id` 만 바꿔 다시 담았다는 뜻이다.

> ⚠ **1바이트의 부호로 글자 수를 역산하지는 않는다.** `.tar.gz` 라 ⓐ tar 가 512바이트 블록으로 패딩하고 ⓑ gzip 압축을 거치므로, 원본 1글자 차이가 결과 파일에서 **+1 이 될지 −1 이 될지 0 이 될지 정해지지 않는다.** 실제로 짧은 이름(`wl-001`) 쪽이 1바이트 **크다.** 판정 근거는 **부호가 아니라 「1.27 MB 중 1바이트만 다르다」는 크기 자체**이고, 여기에 세션 이름이 같다는 것과 §5-3 의 HW 설명이 더해진다.

**처리 방식 — 행을 지우는 것이 아니라 아카이브를 purge 한다.** 촬영본 저장소는 **append-only** 로 설계했고 `mk2_app` 에 **DELETE 권한이 애초에 없다**(`SELECT, INSERT, UPDATE` 뿐). 그래서 제거 경로가 따로 있다:

```sql
UPDATE media_capture
SET archive_path = NULL, archive_bytes = NULL, purged_at = UTC_TIMESTAMP(6)
WHERE session_id = 'wl-001/20260910-134408'
```

+ 아카이브 파일 삭제. **용량은 회수되고, 「이런 세션이 올라왔다가 지워졌다」는 기록은 묘비로 남는다.** 나중에 *"그 촬영본 어디 갔나"* 를 추적할 수 있다.

**실행 완료(2026-09-21).**

```
아카이브 삭제: <촬영본 루트>/wl-001/20260910-134408.tar.gz   (1,274,115 B 회수)
행 표시(purged_at): 1 행
빈 디렉터리 wl-001/ 제거
```

`wl-001/` 디렉터리까지 비워 없앴다. **남은 촬영본은 `go1-001/` 아래 6세션**(09-10 넷 + 09-19 합성 둘)이다.

> 원인(§5-3)에 대한 답은 [9-2-4](#s9-2-4)다. **삭제는 증상 처리이고, 조용한 폴백을 없애는 것이 본체다.**

### 9-8. `lag_s` — 우리가 봤다

*"`lag_s` 는 저희가 볼 수 없어 확인 못 했습니다 — 그쪽 파이프라인 값이라 한 번 봐 주십시오."*

주신 `session_id` 둘(`a3c70e60504d`·`c86c3e607947`)로 TSDB 를 걸러 조회했다. **시간대 착오가 없는 방법이라 그 값으로 잡았다.**

**창이 HW 가 적은 것보다 넓었다** — 그 `session_id` 로 들어온 것 전부를 잡았기 때문이다.

```
처음 2026-09-21 07:26:09.727+00 → 마지막 07:47:12.801+00   1,036건   lag_없음 0
```

KST 로 **16:26:09 ~ 16:47:12, 21.05분**이다(HW 가 적은 창은 `16:26:59 ~ 16:38:24`, 11.4분 / 557건).

| | 건수 | 분 | **분당** |
|---|---:|---:|---:|
| HW 계수 | 557 | 11.4 | **48.9** |
| 우리 TSDB | 1,036 | 21.05 | **49.2** |

🔴 **분당 건수가 같다.** HW 가 센 창이 우리 것의 일부일 뿐이고, **브로커에서 TSDB 까지 새는 구간이 없다.** `lag_없음 0` 이라 **1,036건 전부 헤더가 제대로 실려 왔다.**

```
 source_id |  channel  |  n  | min_s  | avg_s | p90_s | max_s | 시계앞섬 | 재생
-----------+-----------+-----+--------+-------+-------+-------+----------+------
 go1-001   | heartbeat | 253 | -0.005 | 0.003 | 0.012 | 0.034 |      136 |    0
 go1-001   | state     | 252 | -0.004 | 0.000 | 0.002 | 0.042 |      114 |    0
 go1-001   | status    | 129 | -0.004 | 0.014 | 0.019 | 0.041 |       20 |    0
 wl-001    | heartbeat | 252 | -0.005 | 0.000 | 0.002 | 0.070 |      148 |    0
 wl-001    | state     |  22 | -0.004 | 0.057 | 0.040 | 1.002 |        8 |    1
 wl-001    | status    | 128 | -0.004 | 0.000 | 0.002 | 0.012 |       62 |    0
```

**읽는 법 넷:**

**① 지연은 사실상 없다.** p90 이 전부 **40ms 이하**, 최대도 **70ms**다(아래 ③의 한 건 제외). 말단이 찍은 시각과 브릿지가 받은 시각이 거의 같다. **`lag_s` 는 정상 범위다**(§6-13 ⑥ 의 확인 항목 ⑤ — 이것으로 닫힌다).

**② 「시계앞섬」 488건(47%)은 나쁜 신호가 아니라 좋은 신호다.** 절반이 음수인데 **크기가 5ms 이하**다(`min_s -0.005`). 시계가 틀어졌으면 **100% 음수 + 일정한 큰 값**이 나온다. **0 주변에서 ±5ms 로 흔들린다는 것은 NTP 동기가 잘 돼 있다는 뜻**이다. 우리가 음수를 버리지 않고 `clock_skew` 플래그로 보존하는 이유가 이것이다 — 버렸으면 이 판독이 불가능했다.

**③ 🔴 이상치는 정확히 한 건이다 — `wl-001/state` 의 `1.002초` + `재생 1`.** `replayed` 는 *"생산자가 스스로 재전송이라고 말한 것"* 이다. 60초 주기 채널의 22건 중 1건이고 **값이 정확히 1초**다 — spool 재전송으로 읽힌다. **격리는 0건이었으니 내용은 정상**이고, 그 채널의 `avg_s 0.057` 도 이 한 건이 끌어올린 값이다(나머지 21건은 0 근처다). **조치할 것이 없다** — 재전송이 표식과 함께 제대로 도착했다는 기록이다.

**④ 채널 주기가 숫자로 맞는다.** 21.05분 창에서 `wl-001/state` 가 **22건** — **60초 주기** 그대로다. *"`wl-001/state` 12건은 보고 주기 60초라 정상입니다. 10분 이상을 요구하신 이유가 이것이었습니다"* 라고 적으신 그 채널이고, 더 긴 창에서 보니 **주기가 흔들리지 않는다**는 것까지 확인됐다.

> 🔴 **확인 항목 ①②(공통 헤더·본문 2단 검증 격리)는 아직 우리가 격리 파일을 직접 열어 보지 않았다.** *"격리 파일에 이 구간 것이 없어야 정상입니다"* 라고 적어 주신 그것이다 — **단계 1 착수 때 함께 조회하고 결과를 알려 주겠다.** 지금 답할 수 있는 것은 ⑤(`lag_s`)와, 그 구간 **1,036건이 전부 TSDB 에 들어왔다**는 사실(= 브릿지가 하나도 안 버렸다)까지다. 격리됐다면 TSDB 에 안 들어왔을 것이므로 **간접 증거로는 ①② 도 0건에 가깝다.**

> **`lag_s` 의 뜻:** `ingest_at - ts` — **말단이 찍은 시각과 브릿지가 받은 시각의 차**다. 네트워크 지연 + 말단·서버 시계차가 같이 들어 있다(`bridge.py:126` 주석 — *"lag_s 가 네트워크 지연이 아니라 우리 처리 시간을 재게 된다"* 는 그 반대 실수를 막는 주석이다). 그래서 **음수도 정상**이다(말단 시계가 서버보다 앞서면). `clock_skew` 를 같이 본 이유다.

| 키프레임 | 46장 전달 (입력 IDR 60 → **46/60 ≈ 77%**) | **50/50 = 100%** |

**두 실측이 같은 것을 보여 준다 — 버릴 때 GOP 경계에서 버리고, 다음 IDR 에서 재개한다.** 끊는 자리가 다르면 뷰어 디코더가 깨지는데, 양쪽 다 그렇지 않았다.

> 🔴 **되묻는 것 하나 — 숫자가 안 맞는다.** 홉1 수신 **900** 에서 홉2 전송 **643** 이면 차이가 **257** 인데, 버린 것으로 보고된 수는 **64**(역압)다. **193장의 행방이 표에 없다.** 다른 자리에서 또 버렸는지, 아니면 두 숫자가 **서로 다른 구간·창**을 잰 것인지 알려 달라 — 이 값이 「버리기가 어디서 일어나는가」를 가르는 입력이다.
>
> ⚠ **키프레임 비율도 다르다** — 우리는 50/50(100%), HW 는 46/60(77%). 조건이 달라서(링크 조임 vs 지연 주입) 직접 비교는 못 한다. **실서버 관통 때 「IDR 이 전부 갔는가」를 같이 재 주시면** 두 경로를 합쳐 판정할 수 있다.

| type | 개수 | 뜻 |

| **9 (AUD)** | **892** | = 프레임 892장과 **정확히 일치** |

### 9-13. 구형 retained 삭제 — **판단이 정확히 맞다**

*"`zoneA/robot/go1-sim/status` 에 9월 10일 시뮬레이터의 `birth` 가 retained 로 박혀 있었습니다(1.3 + `device_id`, `session_id` 없음). **브릿지가 붙는 순간 구독 즉시 재생돼 첫 격리 1건이 됐을 자리**라 미리 지웠습니다."*

**그 판단이 맞다.** 근거 둘:

1. **retained 는 구독 즉시 재생된다** — 브릿지가 `+/+/+/status` 로 구독하는 순간 브로커가 그 메시지를 한 번 밀어 준다. 새로 발행되는 것이 아니라 **과거가 되살아난다.**
2. **그 본문이 지금 규격에서 100% 격리다** — `schema_version: "1.3"` 은 우리가 받는 `"1.1"` 이 아니고, `device_id` 는 편집 ③으로 없앤 필드다. **공통 헤더 strict 검증에서 그대로 걸린다.**

그러면 실측 시작하자마자 격리 파일에 1건이 찍히고, **원인이 「지금 흐르는 것」이 아니라 「9월 10일에 박힌 것」이라 찾는 데 시간이 걸린다.** 미리 지운 것이 옳다.

> 📌 **규율로 남긴다 — 브릿지를 새 브로커에 처음 붙이기 전에 retained 를 훑는다.** 엣지 브로커·드론 브로커(pi3)에도 같은 것이 박혀 있을 수 있다. 확인은 한 줄이다:
> ```bash
> mosquitto_sub -h <브로커> -t '+/+/+/#' -v -W 2      # retained 만 2초간 받아 본다
> ```

### 9-14. 🔴 그런데 — **지금 서버로 오는 업무 데이터가 0이다**

부록과 §8 을 맞춰 읽으면 이렇게 된다:

| 부록 | `/etc/hw-node.env` — `HW_BROKER_HOST` → **엣지** |
|---|---|
| §8 | `[완료] 업무 평면 — 엣지 브로커 경유` |
| §8 | `6b-3 · 엣지 브릿지 → Kafka 9095` — 🔴 **tailnet + 백엔드 저장소 대기** |

**말단은 엣지 브로커로 발행하고, 엣지 브릿지는 아직 안 섰다.** 그 사이에 서버 Mosquitto 는 아무것도 못 받는다.

🔴 **이건 결함이 아니다 — 실측준비 v2.2 §3-1-2 가 설계한 그대로다.** 다만 **순서의 결과**를 적어 둔다:

- **뷰어(`/state`)에 로봇이 안 뜬다.** VZ 방화벽·어댑터는 준비됐지만 **데이터가 없다.**
- **TSDB 행이 안 는다.** 실측 뒤 증가분을 가르는 기준선(2,381행)은 그대로다.
- §6-13 ⑥ 검증 때 *"발행 대상을 일시적으로 서버로 돌렸고 끝난 뒤 다시 엣지로 되돌렸다"* 고 적으신 그 상태다. **우리 TSDB 의 마지막 행이 16:47:12 인 것이 그 증거**다([9-8](#s9-8)).

**그래서 순서는 이렇게 된다:**

```
팀 tailnet 합류 → 방화벽 3줄 → 백엔드 zip 전달 → 엣지 브릿지 기동(9095) → 그때부터 뷰어에 로봇이 뜬다
```

**VZ 가 붙어 보는 시점을 그 뒤로 잡아야 한다** — 그전에 붙으면 「연결은 되는데 화면이 빔」이 나오고, 그건 어댑터 문제가 아니라 **위쪽이 아직 안 선 것**이다. VZ 에도 같은 내용을 적었다.

> 💡 **급하면 중간 단계가 있다** — 말단 하나만 `HW_BROKER_HOST` 를 **서버**로 잠시 되돌리면(§6-13 ⑥ 때 하신 그것), 엣지 없이도 `/state` 관통을 먼저 볼 수 있다. **관문 C-a(뷰어에 업무 데이터 도달)를 tailnet 과 분리해 미리 닫는 방법**이다. 필요하시면 말씀해 달라.
