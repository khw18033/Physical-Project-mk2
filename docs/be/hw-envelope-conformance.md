## §1 회신 — 스키마 필드 확정

### 1-1. 요청: `pi/common/schema.py` 편집 4개

이 파일 하나만 고치면 전 노드에 반영된다(HW가 어댑터를 한 곳에 모아둔 설계 그대로다).

> **적용 범위 — 노드별 추가 작업 없음.** 이 4개는 `common/schema.py`의 `envelope()`·`iso_now()`·모듈 상단 플래그에만 있고, `envelope()`를 호출하는 **모든 노드**(`sensor_node`·`robot_node`·`actuator_node`·증강 `analyzer`)에 **일괄 자동 반영**된다. 노드마다 따로 고칠 것은 없다 — `schema.py` 한 파일이 전부다.

**① 순번 필드명 `seq` → `sequence_id`**

```python
# before
    if seq is not None:
        env["seq"] = seq
# after
    if seq is not None:
        env["sequence_id"] = seq
```

계약(`contracts/common/message.schema.json`)의 필드명이 `sequence_id`다. 이름이 다르면 백엔드는
그 필드를 **없는 것으로 취급**한다 — 오류가 나지 않고 순번 추적만 조용히 죽으므로 발견이 늦다.
`envelope(seq=...)` **인자 이름은 그대로 두었다** — 호출부(`node.py`·`analyzer.py`)는 무변경이다.

**② timestamp를 RFC3339 콜론 오프셋으로**

```python
# before
import time
def iso_now():
    return time.strftime("%Y-%m-%dT%H:%M:%S%z")
# after
from datetime import datetime, timezone
def iso_now():
    # 로컬 타임존 aware → 콜론 있는 오프셋(+09:00). RFC3339/계약 date-time 정합.
    return datetime.now(timezone.utc).astimezone().isoformat(timespec="seconds")
```

**이것이 4개 중 가장 중요하다.** `strftime("%z")`는 `+0900`을 내는데 계약의 `date-time` 포맷은
`+09:00`을 요구한다. 백엔드는 수신 즉시 포맷까지 실제로 검증하며(fail-closed), **불합격 메시지는
정상 토픽으로 재발행하지 않고 격리**한다. 즉 이 편집 전에는 **모든 메시지가 전량 격리**된다
(백엔드 음성 테스트에서 실제로 거부되는 것을 확인했다).

> 부수 효과: `schema.py`에서 `time` 모듈 사용처가 사라진다. 동작에는 지장이 없으나, `time`을
> 다른 곳에서 쓰지 않으면 린터(flake8 등)가 **unused import** 경고를 낼 수 있으니 CI 린트를
> 쓴다면 `import time`을 지우면 된다(안 써도 동작은 무해). 편집 전후 모두 `time.` 사용을 전수
> 확인했다.

**③ `device_id` 별칭 제거**

```python
LEGACY_DEVICE_ID = True   →   LEGACY_DEVICE_ID = False
```

§1.1의 "`source_id` 단일화 시점"에 대한 답이다 — **지금 확정한다.** 계약은 `source_id`를 정본으로
하고 `device_id` 별칭을 포함하지 않는다. 별칭이 계속 나가면 대역·저장이 낭비되고, 파서가 어느
쪽을 정본으로 볼지 모호해진다(HW가 지적한 그대로다).

**④ 봉투 계약 버전을 계약값으로**

```python
SCHEMA_VERSION = "1.3"   →   SCHEMA_VERSION = "1.0"
```

`1.3`은 드리프트다. 이 필드는 **봉투 계약의 버전**이지 펌웨어 버전이 아니다(펌웨어는
`fw_version`으로 이미 별도로 싣고 있다). 계약 현재 버전은 `1.0`이다.

### 1-2. `schema_version` 표기 규칙 (§1.2 "semver? 정수?"에 대한 답)

**`MAJOR.MINOR` 형식의 문자열**이다. 작성 시점의 값은 `"1.0"`.

> ⚠ **2026-09-10 현재 값은 `"1.1"`이다** — 선택 필드 `session_id` 추가(= 아래 기준대로 MINOR).
> 적용 방법은 [§6-2](#s6-2). **`"1.0"`도 계속 통과하므로 혼재 기간에 격리는 나지 않는다.**

- 스키마 정규식: `^[0-9]+\.[0-9]+$` — 정수 단독(`1`)도, PATCH 포함 semver(`1.0.0`)도 거부된다.
- 올리는 기준: **기존 필드의 의미·타입이 바뀌면** MAJOR 또는 MINOR를 올린다. 선택 필드 추가처럼
  구버전 소비자가 깨지지 않는 변경은 MINOR.
- 소유·발급은 백엔드다. HW는 계약이 올라갈 때 이 상수만 따라 바꾸면 된다.
- **HW가 계약 변경을 아는 방법:** 계약(`message.schema.json`) 버전이 올라가면 백엔드가
  인계 문서(이 문서 같은)나 커밋으로 통지한다. HW가 임의로 올리지 않는다 — 이번 `1.3`
  드리프트처럼 표기가 갈리는 것을 막기 위해서다.

### 1-3. `seq`(→`sequence_id`) 범위 (§1.3 "채널별 독립 순번 vs 전역"에 대한 답)

**현재의 채널별 독립 순번을 그대로 수용한다. HW는 바꾸지 않아도 된다.**

실측에서 확인된 현재 동작이다(같은 시각의 한 노드):

| 채널 | 순번 | 근거 |
|---|---|---|
| `heartbeat` | 12 | `BaseNode.hb_seq` |
| `state` | 1 | `BaseNode.seq` |
| `status`·LWT | **없음** | `envelope(identity)`를 순번 없이 호출 |

Phase 1은 이 값을 **실어 나르기만** 한다. 유실·역전 검출의 정확한 의미(채널별로 볼지, 소스별로
합칠지, 재기동 시 리셋 규칙을 어떻게 둘지)는 **백엔드 Phase 2(저장 2축)에서 확정**해 다시
회신한다. 그때 필요한 변경이 생기면 상수·설정 수준이지 구조 변경은 아닐 것으로 본다.

> ✅ **이 약속은 이행됐다 — [§6-1](#s6-1)을 보라.**
> Phase 2(저장 축)가 끝나 검출 단위와 채널별 의미가 확정됐고, 그에 따른 요청 하나
> (`session_id` 신설)가 [§6-2](#s6-2)에 있다.

`status`에 순번이 없는 것은 정상으로 받아들인다 — 봉투 필수 5필드
(`schema_version`·`source_id`·`node_id`·`zone_id`·`timestamp`)만 있으면 통과한다.

### 1-4. `device_id` 제거의 내부 영향 — HW 브랜치 전수 확인 결과

편집 ③이 HW 내부 소비자를 깨뜨리는지 백엔드가 코드로 확인했다. **둘 다 안전하다.**

| 위치 | 코드 | 판정 |
|---|---|---|
| `pi/edge/monitor.py:56` | `payload.get("source_id") or payload.get("device_id") or topic.split("/")[2]` | ✅ `source_id` 우선 |
| `pi/augment/analyzer.py:92` | `p.get("source_id") or p.get("device_id") or msg.topic.split("/")[2]` | ✅ `source_id` 우선 |

그 밖의 `device_id` 검출은 봉투와 무관하다 — protobuf 명령의 `Capability.device_id`,
`/etc/device_id` 파일 경로, 중복 채번 경보 문구.

**요청:** 위 2곳 외에 봉투의 `device_id`를 직접 읽는 소비자(대시보드·스크립트·노트북 코드 등)가
있으면 `source_id`로 갱신해 달라. 백엔드가 볼 수 있는 범위(HW 브랜치 `*.py`·`*.js`·`*.html`)
에서는 위 2곳이 전부였다.

**`seq` 이름 변경도 안전하다:** HW 전체에서 **봉투의 `seq` 필드를 읽는 소비자가 없다.** 검출된
`seq`는 전부 RTP 시퀀스 번호(미디어 경로, 무관)이거나 `envelope(seq=...)` 호출 인자였다.

### 1-5. 편집이 맞게 됐는지 확인하는 법 (HW 자가 확인)

백엔드 파이프라인 없이 HW 쪽에서만 확인할 수 있다. 편집 4개를 적용한 노드를 띄우고, **발행
로그**(노드가 찍는 발행 출력)나 **`mosquitto_sub`**(둘 중 편한 것)로 실제 나가는 봉투를 한 번
들여다보면 된다. 예:

```bash
# 브로커에서 한 채널을 잠깐 구독해 실제 봉투를 눈으로 확인
mosquitto_sub -h <브로커> -t 'zoneA/sensor/wl-001/state' -v
```

봉투에서 아래 4가지가 보이면 편집이 맞게 된 것이다:

1. `sequence_id` 키가 있다(편집 전 이름 `seq`가 **아니다**). — 편집 ①
2. `timestamp`가 `...T21:29:25+09:00`처럼 **콜론 있는 오프셋**이다(`+0900` 아님). — 편집 ②
3. `device_id` 키가 **없다**(`source_id`만 있다). — 편집 ③
4. `schema_version`이 `"1.0"`이다. — 편집 ④ → ⚠ **2026-09-10부터 목표값은 `"1.1"`**([§6-2](#s6-2))

`status` 채널은 `sequence_id`가 없어도 정상이다(§1-3). 나머지 세 가지(②③④)는 모든 채널에서
동일하게 보여야 한다.

> **`session_id`까지 적용했다면** 다섯 번째로 `session_id` 키가 보이고, **한 프로세스가 사는
> 동안 값이 같고 재시작하면 바뀐다**([§6-2](#s6-2)). `timestamp`에 밀리초까지 보이면
> [§6-9](#s6-9)의 권고까지 들어간 것이다.

## §2 회신 — 토픽 도메인 체계

HW는 MQTT만 발행하므로 **§2는 코드 변경이 없다.** 확인과 정보 전달이다.

### 2-1. `{domain}` 자리에 구역(zoneA) — 그대로 유지

현재 구조 `{zone}/{etype}/{eid}/{channel}`을 **확정으로 받는다.** 백엔드 ingest는 이 구조를 전제로
구독한다.

### 2-2. `{type}`(etype) 어휘 — `sensor / robot / actuator / analysis` 확인

이 넷을 그대로 쓴다. 백엔드는 **etype에 무관하게** 잡도록 구독하므로(§2-3), 어휘가 늘어도 백엔드
코드는 바뀌지 않는다.

### 2-3. 채널 이름 — 텔레메트리 3채널은 **한 칸을 더 쓰지 않는다**

백엔드 ingest의 구독 패턴은 정확히 셋이다:

```
+/+/+/state      +/+/+/status      +/+/+/heartbeat
```

MQTT의 `+`는 **한 계층만** 대응하므로 이 패턴은 **정확히 4칸인 토픽만** 잡는다. 따라서:

- `zoneA/sensor/wl-001/state` → 잡힌다.
- `zoneA/analysis/wl-001/state`(증강 분석) → **같은 경로로 잡힌다.** 백엔드 코드 변경 없음.
- `terminal/wl-001/downlink`(명령, 3칸) → **패턴에 안 맞아 배달 자체가 되지 않는다.**

§2.3의 걱정("`cmd/ack`처럼 한 칸 더 들어가는 채널이 와일드카드 구독에 영향")은 **소멸했다.**
명령 경로가 `common/physical_command.py`의 규약(`terminal/<device_id>/downlink|uplink` +
protobuf)으로 이동해 구 JSON `cmd/*` 채널이 폐기됐기 때문이다. 텔레메트리 평면과 명령 평면이
토픽 형태부터 분리되어, 백엔드는 명령을 **구독하지 않는 것으로** 격리한다.

**따라서 요청한다: 텔레메트리 채널은 4칸 구조를 유지하고, 계층을 더 파지 말아 달라.** 새 채널이
필요하면 백엔드에 먼저 알려 달라 — 채널이 늘면 Kafka 토픽과 저장 경로가 함께 생겨야 한다.

### 2-4. MQTT → Kafka 매핑 (§2.4에 대한 답)

**원본 미러가 아니다.** 채널별로 3개의 Kafka 토픽에 싣는다.

| MQTT 토픽 | Kafka 토픽 | 파티션 키 |
|---|---|---|
| `{zone}/{etype}/{eid}/state` | `mk2.telemetry.state` | `source_id` |
| `{zone}/{etype}/{eid}/status` | `mk2.telemetry.status` | `source_id` |
| `{zone}/{etype}/{eid}/heartbeat` | `mk2.telemetry.heartbeat` | `source_id` |

- **장치별·구역별 토픽을 만들지 않는다.** `zone_id`·`source_id`는 이미 봉투 안에 있고, 토픽에는
  **데이터의 성격(채널)만** 담는다. 구역·장치가 늘어도 토픽 수가 늘지 않는다.
- **파티션 키가 `source_id`**라 한 장치의 메시지는 항상 같은 파티션에 들어간다 → **장치별 순서가
  보장**된다. 이것이 `source_id`를 필수로 두는 실용적 이유다.
- **값은 HW가 보낸 JSON 바이트 그대로** 싣는다. 백엔드는 재직렬화하지 않는다(필드 순서·수치
  표현이 원본 그대로 보존된다).
- 이름은 점 구분 소문자이며 **언더스코어를 섞지 않는다**(Kafka 메트릭 이름 변환 충돌 회피).

**HW 코드 변경은 필요 없다.** 이 매핑은 백엔드 내부 규약이다.

## §3 백엔드 수신 규약 — HW가 알아두면 좋은 것

1. **수신 즉시 봉투를 strict 검증한다(포맷 포함).** 필수 5필드와 `date-time` 형식을 실제로
   assert한다. 전환기·관용 모드는 없다.
2. **불합격은 정상 토픽으로 재발행하지 않는다.** 사유·원문·수신시각과 함께 격리 파일에 남는다.
   즉 **형식이 틀리면 조용히 통과하는 대신 조용히 사라진다** — 그래서 편집 ②가 중요하다.
3. ~~**채널 본문(payload)은 아직 검증하지 않는다.** 봉투만 본다. `water_level_m` 같은 본문 필드의
   스키마는 채널별로 따로 만들 때 다시 알린다. 지금은 본문에 무엇이 있든 통과한다.~~
   → ⚠ **2026-09-10 변경됨.** Phase 2가 본문 검증(2단)을 켰다. **필수 항목이 빠지면 이제 격리된다.**
   무엇이 필수이고 무엇이 아닌지, 모르는 필드는 어떻게 되는지는 **[§6-8](#s6-8)** 에 있다.
4. **retained `status`를 그대로 받는다.** 백엔드가 구독을 걸면 브로커가 마지막 retained `status`
   1건을 즉시 밀어주며, 이는 다른 메시지와 똑같이 처리된다.
5. **Phase 1은 가용성을 판정하지 않는다.** `status`(birth/summary/shutdown)와 LWT(death),
   `heartbeat`를 **흘려보내기만** 한다. 최종 가용성 판정은 백엔드 단일 지점에서 하며(Phase 5),
   그때 엣지의 1차 판정(`pi/edge/monitor.py`·`edge/availability.py`)과의 관계를 정리해 회신한다
   (`BACKEND_AGENDA §10-2`·§5 관련).

## §4 검증 결과 — 이 회신의 근거

편집 4개를 적용한 `sensor_node`(로컬 사본)를 **개발 PC에서 실행**해 **서버 Mosquitto로 발행**하고,
서버의 백엔드 파이프라인으로 관통시켰다. 실제 배치(말단=엣지 쪽, 브로커=서버)와 같은 방향이다.

| 항목 | 결과 |
|---|---|
| 관통 경로 | 노드(PC) → MQTT → ingest 봉투 검증 → Kafka 3토픽 → 저장 sink + WebSocket push |
| 채널 | `state`(60초)·`status`(10초)·`heartbeat`(5초) **3채널 전부 도달** |
| 지속 | 약 13분 (heartbeat 순번 1→163 **연속, 유실 0**) |

`node_id`는 `/etc/node_id`가 없어 hostname으로 채워졌다(설계된 폴백). 실배포에서는 `/etc/node_id`

### 6-1. `sequence_id` 의미 확정 (§1-3 약속 이행)

**HW가 지금 하는 대로가 맞다. 채널별 독립 순번을 그대로 확정한다.** 아래는 그 결정의 내용이고,
HW 쪽 변경은 §6-2(`session_id`) 하나뿐이다.

**① 검출 단위는 `(source_id, channel, session_id)` 다.**

- **채널마다 순번이 독립인 것이 맞다.** 카운터가 물리적으로 둘이기 때문이다 —
  `node.py:57`의 `self.seq`(state)와 `node.py:56`의 `self.hb_seq`(heartbeat). 소스별로 합치면
  **매 메시지가 갭으로 잡힌다.**
- **`session_id`가 구간의 경계다.** 프로세스가 다시 뜨면 순번이 0부터 시작하는데, 경계를 모르면
  그 리셋이 거대한 역전으로 보인다(§6-2).

**② `status`에 순번이 없는 것을 정상으로 확정한다. 검출 대상에서 아예 뺐다.**

`node.py:200`의 `publish_status()`가 `envelope(self.identity)`를 **순번 없이** 호출하고,
LWT(`node.py:92`)도 같다. 순번이 없으므로 셀 것이 없다 — 백엔드 갭 검출 질의가 `status` 채널을
명시적으로 제외한다. **HW는 여기에 순번을 붙이지 않아도 된다.**

**③ 갭이 곧 유실이 아니다. 채널·타입마다 다르게 판정한다.**

| 채널·타입 | QoS | spool | 백엔드 판정 | 근거(소스) |
|---|---|---|---|---|
| `state` (센서·액추에이터) | 1 | 탄다 | **유실 후보**(`loss_candidate`) | `sensor_node.py:113` qos=1 |
| `state` (로봇) | **0** | 탄다 | 갭은 세되 **유실로 단정하지 않는다** | `config.py:103` `ROBOT_STATE_QOS = 0` |
| `heartbeat` | 0 | **안 탄다** | 갭은 세되 **유실로 단정하지 않는다** | `node.py:237` `qos=0, allow_spool=False` |
| `status` | 1 | 안 탄다 | **검출 제외**(순번 없음) | `node.py:200`·`:217` |
| `state` (증강 분석) | 0 | — | **검출 제외**(전역 순번 공유) | `analyzer.py:38`·`:138` |

**하트비트 침묵을 장애로 단정하지 않는 이유가 하나 더 있다** — `robot_node.py`의
`heartbeat_enabled()`가 임무 중에는 하트비트를 **아예 끈다**. 그것이 설계이므로 백엔드가 그걸
장애로 읽으면 임무 중인 로봇이 전부 장애가 된다.

**④ 재전송 구간의 성긴 `state`는 유실이 아니다.**

`spool.py:91-116`의 `_downsample()`이 `kind == CONTINUOUS`인 레코드만 버킷당 1건으로 솎는다.
평시 `state`는 `reason == "periodic"`일 때 `CONTINUOUS`이므로(`sensor_node.py:102`), 두절 복구
구간에서는 **정상적으로 표본이 솎인다.** 백엔드는 `reason`과 `replayed`를 함께 저장해 이것을
유실과 구분한다 — **HW의 다운샘플 정책을 바꿀 필요가 없다.**

**⑤ 발행 실패로 spool에 들어가도 순번이 증가하는 것 — 그대로 두어도 된다(변경 요청 아님).**

백엔드는 순번을 **"발행 시도 번호"** 로 해석한다. 이 동작을 바꾸지 않아도 검출이 성립한다.

> **우리는 이렇게 읽었다:** 위 표의 QoS·spool 조합이 "이 채널의 유실은 설계된 동작인가"를 가른다.
> **답이 없으면:** 위 표대로 간다. 이미 구현·검증까지 끝냈다(`docs/be/queries/gap-detection.sql`).

### 6-2. 🟡 `session_id` 신설 요청 — `schema.py` **2줄**

**요청하는 변경은 이것이 전부다.** `envelope()` 한 곳이라 **전 노드에 자동 반영**되고 노드별
작업이 없다(편집 4개와 같은 성질이다).

```python
# pi/common/schema.py

# ① 모듈 전역에 한 줄 추가 (SCHEMA_VERSION 근처)
#    `import uuid` 는 이미 있다(schema.py:16) — 새 import 가 필요 없다.
SESSION_ID = uuid.uuid4().hex[:12]   # 프로세스 1회 기동을 가리킨다. 파일에 저장하지 않는다.

# ② envelope() 안에 한 줄 추가 (schema.py:121-127 의 dict)
def envelope(identity, seq=None, correlation_id=None):
    env = {
        "schema_version": SCHEMA_VERSION,
        "source_id": identity.entity_id,
        "node_id": identity.node_id,
        "zone_id": identity.zone_id,
        "timestamp": iso_now(),
        "session_id": SESSION_ID,        # ← 추가
    }
```

**왜 `birth` 경계로는 부족한가 — 오판이 두 방향이다.**

`_on_connect`가 항상 `publish_status("birth")`를 부르므로(`node.py:122`) `birth`는 신뢰할 수 있는
표식이다. 백엔드는 지금 그것을 폴백 경계로 쓴다. 문제는 **`birth`가 프로세스 재시작이 아닐 때도
나간다**는 것이다:

- 브로커가 끊겼다 다시 붙으면 → `_on_connect` 재호출 → `birth` 발행. **그런데 프로세스는 살아
  있어서 `self.seq`는 이어진다.** → 순번이 안 끊겼는데 구간만 쪼개진다.
- 구역이 바뀌면 `node.py:258`이 `self._connect()`를 다시 부른다 → 역시 `birth`. 순번은 유지된다.

`session_id`는 **프로세스가 다시 떴을 때만** 바뀌므로 순번 리셋과 정확히 같이 움직인다.
그리고 spool 재전송분이 **원래 세션을 달고 오는** 것도 이 방식의 이점이다 — 재전송을 새 구간으로
오해하지 않는다.

**함께 갱신할 것 — 편집 ④의 목표값이 바뀌었다.**

```python
SCHEMA_VERSION = "1.3"   →   "1.1"      # §1-1 편집 ④의 "1.0" 이 아니다
```

규격이 이번에 **1.1로 올랐다**(선택 필드 `session_id` 추가 = 버전 정책상 MINOR). §1-2에 적은
기준 그대로다. **`"1.0"`도 계속 통과하므로 혼재 기간에 격리는 나지 않는다** — 정규식이
`^[0-9]+\.[0-9]+$`이고, 백엔드가 `"1.0"`·`"1.1"` 양쪽을 통과시키는 것을 테스트로 못 박아 두었다.

> **우리는 이렇게 읽었다:** `SESSION_ID`는 프로세스 수명과 같아야 하므로 **모듈 전역**이 맞고,
> 파일에 저장하면 안 된다(저장하면 재시작해도 같은 값이 되어 의미가 사라진다).
> **답이 없으면:** 백엔드는 `status`의 `birth`를 경계로 쓰는 **폴백 경로로 계속 돈다.** 이미
> 구현·검증돼 있어 데이터가 사라지지는 않는다. 다만 위의 두 오판이 남는다.

### 6-3. 🔴 §1-1의 편집 4개가 `260909` 브랜치에 아직 없다

**이것이 지금 가장 급하다.** HW 브랜치 스냅샷(`260909`)의 `pi/common/schema.py`를 직접 열어

> ⚠ **이 판단의 근거는 백엔드가 2026-09-09에 받은 브랜치 스냅샷이다.** 그 뒤에 이미 반영하셨다면
> 이 항목은 넘어가셔도 된다 — **반영됐는지는 §1-5의 자가 확인법**(발행되는 공통 헤더를 한 번 들여다보기)으로
> 1분이면 알 수 있다. 단, ④의 목표값은 `"1.0"`이 아니라 **`"1.1"`** 이다(아래).

| 편집 | §1-1에서 요청한 값 | **`260909` 실제** | 근거 |
|---|---|---|---|
| ① `seq` → `sequence_id` | `env["sequence_id"] = seq` | `env["seq"] = seq` | `schema.py:129` |

```python
# pi/common/schema.py:32-34
from datetime import datetime, timezone

def iso_now():
    # 콜론 있는 오프셋(+09:00) + 밀리초. RFC3339 / 규격 date-time 정합.
    return datetime.now(timezone.utc).astimezone().isoformat(timespec="milliseconds")
```

> **우리는 이렇게 읽었다:** 편집 4개는 **우리 로컬 작업본에만** 적용돼 있었고 HW 브랜치에는
> 반영되지 않았다. 우리가 만든 사본을 근거로 삼으면 "HW가 실제로 무엇을 보내나"를 우리가 고친
> 파일로 판단하게 되므로, **근거는 항상 HW 브랜치 스냅샷으로만 삼았다.**
> **답이 없으면:** Phase 2 저장 검증은 가짜 발행자와 Phase 1이 남긴 실측 데이터로 이미 끝냈다.
> 다만 **실노드 관통 검증은 이 편집이 들어올 때까지 불가능하다.** 백엔드는 그것을
> "검증됨"으로 적지 않고 미완으로 남겨 두었다.

### 6-5. ⚪ `origin_kind`·`entity_id` 미발행 — 그리고 **요구사항 사본이 낡았다**

`schema.py:119-134`의 `envelope()`에는 이 둘이 없다. Phase 1·2 실측 공통 헤더에서도 확인했다.

**`origin_kind` (실물/시뮬 구분) — 구현 누락이 아니라 요구사항 사본의 문제다.**
근거 요구사항인 **BE-C-07(원천 종류 표기 규약)이 HW 브랜치의 요구사항 정의서 사본에 없다.**
전체 공유 스프레드시트에는 있다. 즉 HW는 **애초에 이 항목을 받지 못했다.**

> §6-10과 모순처럼 보일 수 있어 정리한다. HW 브랜치 사본은 **HW 자기 행(HW-*)은 더 새롭지만**
> (HW가 직접 개정했으므로), **다른 파트 행(BE-*·AI-*)은 그 뒤 동기화되지 않았다.** BE-C-07이
> 그 예다. 그래서 §6-10에서 "HW 사본을 전체 시트에 반영해 달라"(HW 행 방향)고 하면서, 여기서는
> "BE 행은 전체 시트가 기준"이라고 하는 것이다 — 방향이 반대인 두 요청이 아니라 **같은 사본이
> 행마다 신구가 다르다**는 한 사실이다.

**`entity_id` — 지금은 무해하다.** 선택 필드이고, 백엔드는 대장의 키를 **공통 헤더의
`source_id`** 로 잡았다(공통 헤더가 필수로 보장하는 값이 그것뿐이라서). 다만 **노드 하나에 개체가
여럿인 배포**에서는 필요해진다.

> **우리는 이렇게 읽었다:** 둘 다 선택 필드이므로 지금 안 보내도 저장·검증이 깨지지 않는다.
> 실제로 두 칼럼은 실노드 데이터에서 `NULL`이고 **그것이 정상**이다.
> **답이 없으면:** `origin_kind` 미기재는 조회 시 **`real`(실물)로 해석**한다. `entity_id`는
> `NULL`로 둔다. 둘 다 백엔드가 임의로 채워 넣지 않는다 — 채우면 "생산자가 안 보낸 것"과
> "백엔드가 채운 것"을 나중에 구분할 수 없다.

### 6-8. 본문 항목 목록과 누락값 형태 — 확정 통지

**§3의 3번 항목이 미뤄 둔 것을 여기서 닫는다.** 본문 규격 6종을 신설하고 백엔드 ingest에
**2단 검증**(공통 헤더 → 본문)을 켰다. 항목은 전부 HW 소스에서 그대로 읽었다.

| 채널·타입 | 필수 | 선택 | 근거 |
|---|---|---|---|
| `state`/sensor | `reason`·`device_status`·`water_level_m`·`unit`·`alert`·`mode` | `replayed` | `sensor_node.py:103-112` |
| `state`/robot | `reason`·`device_status`·`battery_pct`·`position`·`speed_mps`·`robot_mode`·`internal_seq` | `mission`·`replayed` | `robot_node.py:99-113` |
| `state`/actuator | `reason`·`device_status`·`actuator_state`·`position`·`progress`·`feedback_ok`·`control_locked` | `lock_reason`(null 허용)·`detail`·`replayed` | `actuator_node.py:92-105` |
| `state`/analysis | `subject_id`·`value`·`window_s`·`samples`·`above_threshold`·`threshold_m` | `trend_m_per_min`(null)·`eta_to_threshold_min`(null) | `analyzer.py:125-135` |
| `status` (공통) | **`event`·`status` 둘뿐** | `device_status`·`registration`·`uptime_s`·`buffer`·`publish_failures`·`reason` + 노드 고유 필드 | `node.py:201-212` |
| `heartbeat` | (없음) | — | `node.py:234-235` |

**HW가 알아야 할 규칙 넷:**

1. **모르는 필드는 통과한다.** `additionalProperties`를 `false`로 두지 **않았다.**
   `status_extra()`(`node.py:212`)가 노드마다 다른 필드를 반환하도록 설계된 훅이라 **필드가 느는
   것이 정상 동작**이기 때문이다. 실측으로 확인했다 — 센서의 `mode`·`mode_source`·
   `report_interval_s`·`alert`·`last_value`는 규격에 선언돼 있지 않은데 통과했다.
2. **필수 필드 누락은 격리된다.** 저장 층이 값의 존재를 가정하려면 이건 막아야 한다.
   음성 대조로 확인했다 — `device_status`가 빠진 로봇 `state`가 실제로 격리됐고 Kafka 토픽에
   나타나지 않았다.
3. **`status`의 필수를 `event`·`status` 둘로만 잡은 이유는 LWT다.** LWT 본문에는 `registration`도
   `buffer`도 없다(`node.py:92-94`). 세게 걸면 **급사 신호가 격리된다.**
4. **`event` 어휘를 5종으로 읽었다** — `birth`·`summary`·`rebirth`·`shutdown`(`node.py:203`,
   `rebirth`는 `:260`) + LWT의 `death`(`node.py:93`). 이것도 `enum`으로 고정하지 않았다.

**누락값 표현 — 구분이 필요한 항목은 둘로 확정했다.**

| 항목 | 형태 | 왜 |
|---|---|---|
| `state`의 계측값(`water_level_m`·`battery_pct` 등) | `{value, state}` (`unsupported` / `unavailable`) | 센서 읽기가 실패하면 **발행 자체가 안 되고**(`sensor_node.py:66-72`의 `except → return`), 3회 연속이면 `device_status`가 `fault`가 된다. 화면은 "센서 없음"과 "센서 고장"을 달리 그려야 한다 |
| `status.registration` | `{value, state}` | LWT엔 **원래 없다**(`unsupported`) vs 있어야 하는데 없다(`unavailable`) |
| **나머지 전부** | 명시적 `null` | `status.buffer`는 `node.py:208`에서 항상 채워지고 빠지는 경우가 LWT뿐이라 `registration`과 중복 → 기본형으로 내렸다 |

> **우리는 이렇게 읽었다:** 위 표의 항목은 각 노드의 `payload.update({...})`에서 **그대로** 읽었다
> — 표는 요약이고 소스가 근거다. 필수/선택의 경계는 "그 노드가 **항상** 싣는가"로 갈랐다.
> **HW가 지금 할 일은 없다.** 누락값 형태는 **값이 없을 때만** 쓰는 표현이고, 현재 노드는 값이
> 있을 때만 발행하므로 현행 코드가 그대로 통과한다. 다만 **이 목록과 다르게 읽은 항목이 있으면
> 알려 달라** — 특히 "항상 싣는다"고 본 필수 항목 중 조건부인 것이 있다면.
> **답이 없으면:** 위 확정대로 간다. 이미 구현·검증까지 끝냈다.

### 6-9. ⚪ `timestamp` 해상도 권고 — `seconds` → `milliseconds`

`schema.py:34`의 `iso_now()`가 초 해상도다(`strftime("%Y-%m-%dT%H:%M:%S%z")`, 편집 ② 후에도
`timespec="seconds"`면 같다). **로봇 20Hz면 1초에 20건이 같은 `timestamp`를 갖는다.**

**저장에는 문제가 없다** — 유일 키를 도착 좌표로 잡았기 때문이다(§6-4). 영향은 둘이다:

- `lag_s`(서버 도달 지연) 정밀도가 초 단위로 뭉갠다. 이 값은 재난 모드 지연 상한(BE-S-07)의
  측정 재료라 정밀도가 의미가 있다.
- 되감기 해상도가 초 단위가 된다.

고치는 법은 §6-3에 적었다 — **편집 ②와 같은 한 줄**이다.

> **우리는 이렇게 읽었다:** 초 해상도는 HW-S-08("모든 메시지에 타임스탬프")의 요구를 채우지만,
> 로봇 20Hz·액추에이터 20Hz(HW-A-01)에서는 **한 초 안의 순서를 시각으로 못 가른다.** 권고이지
> 요구가 아니다 — 저장은 순번·도착 좌표로 순서를 지킨다.
> **답이 없으면:** 초 해상도 그대로 받는다. 저장·검출은 정상 동작한다.

### 6-10. ⚪ 요청 — HW 브랜치의 요구사항 시트를 전체 공유 스프레드시트에 반영해 달라

### 6-11. 🟡 증강 분석(K3s)은 「노드별 작업 없음」의 **예외다**

**§1-1과 §6-2에 적은 *"`envelope()` 한 곳이라 전 노드에 자동 반영되고 노드별 작업이 없다"* 는
증강 분석에는 성립하지 않는다.** 백엔드가 늦게 확인했다. 정정한다.

| 근거 | 내용 |
|---|---|
| `pi/augment/Dockerfile:20` | `COPY common/ /app/common/` — **`schema.py`가 이미지에 구워진다** |
| `pi/deploy/k8s/augment-analyzer.yaml:40-41` | `image: …@sha256:<digest>` + `imagePullPolicy: IfNotPresent` — **digest 고정** |
| `pi/augment/analyzer.py:27,124` | `from common import schema` → `schema.envelope(ident, seq=seq)` |

즉 **`schema.py`를 고쳐도 이미 배포된 파드는 옛 코드로 계속 돈다.** pi 노드 셋(센서·로봇·
액추에이터)은 systemd로 소스에서 바로 돌기 때문에 자동 반영이 맞지만, 증강 분석만 다르다.

**배포 형태에 따라 갈린다:**

| 매니페스트 | `schema.py` 변경 반영 방법 |
|---|---|
| `augment-analyzer-dev.yaml` | hostPath 마운트(`:33-44`) → **파드 재시작만으로 반영** |
| `augment-analyzer.yaml`(운영) | **재빌드 → digest 갱신 → 매니페스트 `image:` 교체 → 재배포**. 절차는 `pi/augment/build.sh`에 이미 있다 |

**지금 당장 급하지는 않다.** HW README 「다음 할 일」이 *"증강 컨테이너 이미지 빌드 — 현재는
매니페스트만"* 이라 적고 있고, 운영 매니페스트가 `REPLACE_WITH_DIGEST` 자리표시자이며, K3s
제어평면은 2026-08-31에 철수됐다(pi7이 원래 클러스터로 원복). **지금 증강 분석은 돌고 있지
않으므로 이 문제가 지금 발현되지 않는다.**

**문제는 나중이다.** 이미지를 빌드해 배포한 뒤 `schema.py`가 또 바뀌면(예: `session_id`)
**배포된 파드만 조용히 갈린다.** 그리고 공통 헤더 불합격은 **오류가 아니라 격리**라(§3의 2번)
증강 분석만 사라져도 눈에 띄지 않는다 — 원래 간헐 발행이라 부재를 알아채기 어렵다.

> **우리는 이렇게 읽었다:** 증강 층은 *"없어도 안전 루프 무사"*(`k3s/README.md:27`)이므로
> 이것이 안전을 해치지는 않는다. 다만 **수위 추세·임계 도달 예측이 통째로 사라진 채 넘어가는
> 것**을 막으려면 빌드 시점에 이 사실을 알고 있어야 한다.
> **답이 없으면:** 백엔드는 아무 조치도 하지 않는다. 이것은 질문이 아니라 **통지**다 —
> 이미지를 빌드·배포할 때 `schema.py`의 최신 상태가 들어갔는지 한 번만 확인해 달라.

#### ① `pi/common/schema.py` — 고칠 곳 다섯 (한 파일)

import uuid                      # 이미 있다(schema.py:16) — 추가 불필요
from datetime import datetime, timezone   # 편집 ②: time 대신 이것

SCHEMA_VERSION = "1.1"           # 편집 ④  ("1.3" → "1.1". §1-1의 "1.0"이 아니다)

def iso_now():

# ── envelope() ────────────────────────────────────────

    if seq is not None:
        env["sequence_id"] = seq         # 편집 ①  ("seq" → "sequence_id")
    ...

| | |
|---|---|
| 보내는 쪽 | 백엔드(BE·DT) / 이대규 |
| 받는 쪽 | 하드웨어(HW) / 조병현 |

| 대상 안건 | `BACKEND_AGENDA` **§10-3** — *"명령에 trace 컨텍스트를 실어 보낼 계획이 있는가? 있다면 W3C `traceparent`인가?"* (§5-1에서 *"Phase 3 이후 회신"* 으로 약속한 것) |
| 우선순위 | ⚪ — **Phase 6(명령) 착수 전까지**만 오면 재작업이 없다 |

<a id="s7-0"></a>

### 7-0. 한 장 요약

| 물음 | 답 |
|---|---|
| 실어 보낼 계획이 있는가 | **있다.** 백엔드가 만드는 모든 명령(`Command`)에 싣는다 |
| 형식은 W3C `traceparent`인가 | **그렇다.** W3C Trace Context의 `traceparent` **한 필드**(`00-<trace-id 32hex>-<span-id 16hex>-<flags 2hex>`). `tracestate`는 **싣지 않는다** |
| 어디에 싣나 | **protobuf 본문 필드** — `Command` 메시지에 `string traceparent` 1개 추가. Kafka 헤더·MQTT 속성이 아니다(아래 7-2) |
| 언제 | **실배선은 Phase 6.** `.proto` 개정은 `BACKEND_AGENDA` §3(문자열/열거형 파라미터) 때문에 어차피 한 번 하므로 **같은 개정에서 함께** 넣는다 |
| 답이 없으면 | **HW는 현행대로 두면 된다.** 필드가 없으면 새 trace를 시작하는 지금 동작(`otel_trace.py:76-79`)이 맞고, Phase 6에서 필드가 들어오면 그대로 이어 붙는다 |

### 7-1. 우리는 이렇게 읽었다

`otel_trace.py:16-21`은 *"백엔드가 명령 페이로드에 W3C `traceparent`를 실어 보내면 우리 span이 그 trace의
자식으로 붙는다 … 없으면 새 trace를 시작한다"* 이고, `:77`이 `TraceContextTextMapPropagator().extract(carrier=cmd)`로
**명령 본문에서 직접** 찾는다. 즉 HW는 이미 *"본문 안에 `traceparent` 키가 있다"* 를 전제로 짜 두었다.
우리는 그 전제를 **그대로 채택**한다 — 형식도 위치도 HW 코드가 기대하는 것과 같다.

### 7-2. 왜 본문인가 — Phase 2의 Kafka 헤더와 다른 이유

Phase 2에서 백엔드는 `ingest_at`·`entity_type`을 **Kafka 헤더**에 실었다(§6). 이유는 하나였다 — *"HW가 보낸
원본 JSON 바이트를 건드리지 않는다"*(재직렬화하면 원본이 사라진다). **명령은 그 조건이 성립하지 않는다.**
명령은 **백엔드가 만드는 메시지**라 지킬 원본이 없고, 만드는 쪽이 필드를 넣으면 그만이다. 게다가 HW의
`extract(carrier=cmd)`가 본문을 보도록 이미 짜여 있으므로, 본문 밖(MQTT 5 user property 등)에 실으면
HW가 그 자리를 읽는 코드를 **새로** 써야 한다. 본문이 양쪽 작업량이 가장 적다.

### 7-3. HW 작업량 — "코드 변경 없음"이 아니다 (셋)

protobuf는 미리 약속한 틀(`.proto`)에 맞춰 이진으로 싣는다. **틀에 없는 값은 넣을 자리 자체가 없다** —
JSON처럼 키 하나를 더 얹는 것과 다르다. 그래서 다음이 필요하다.

| # | 무엇 | 어디 | before → after |
|---|---|---|---|
| ① | `.proto`에 필드 1개 | `schema/physical_command.proto:28-34` `message Command` | `int64 deadline_unix_ms = 5;` 다음에 **`string traceparent = 6;  // W3C Trace Context. 비어 있으면 새 trace 시작`** — 번호는 제안값(7-4 ①) |
| ② | protobuf 객체 → dict 배선 한 줄 | `pi/common/otel_trace.py:77` | `extract(carrier=cmd)` → `extract(carrier={"traceparent": cmd.traceparent} if cmd.traceparent else {})`. **`carrier`는 `.get()`이 있는 매핑이어야 한다** — 지금 `_on_command(env.command)`(`physical_command.py:164`)가 넘기는 것은 protobuf `Command` 객체라 그대로 넣으면 `extract`가 실패한다 |
| ③ | 옛 말단 호환 확인 | — | proto3는 **모르는 필드를 무시**하므로 옛 말단이 새 필드가 붙은 명령을 받아도 파싱은 된다. 다만 HW가 배포 중인 말단에 그것이 실제로 성립하는지(pb 라이브러리 버전 포함) **확인 요청** |

> **정보 — 스냅샷 `260909`에서 확인한 것.** `node.py:52`가 `otel_trace.create()`로 추적기를 만들고 `:340`에서
> 닫지만, **`begin(cmd)`를 부르는 곳이 `pi/` 어디에도 없다**(`physical_command.py`의 `_on_command`·`_execute`
> 포함). `BACKEND_AGENDA` §10-3의 *"구현·검증 완료"* 가 이 스냅샷 뒤의 브랜치를 가리키는 것이라면 알려 달라 —
> 백엔드는 실배선(Phase 6) 때 그 브랜치를 근거로 대조한다.

### 7-4. 확인 요청 2건

| # | 물음 | 우리 제안(답이 없으면 이대로) |
|---|---|---|
| ① | **`.proto` 필드 번호를 누가 정하나** — `.proto`는 HW 소유(*"실제 통신의 source of truth"*, `physical_command.proto:2`)다 | HW가 정한다. 제안: `Command.traceparent = 6`. 백엔드는 HW가 확정한 `.proto`를 그대로 가져와 컴파일한다 — 백엔드 쪽 사본을 따로 두지 않는다 |
| ② | **옛 말단이 새 필드가 붙은 명령을 받아도 깨지지 않는가** | proto3 규격상 모르는 필드는 무시된다. 그래도 HW가 실제 말단(pi7 등)에서 한 번 확인해 달라 |

### 7-5. 시점과 순서

1. **Phase 6(명령·감사) 착수 시** 백엔드가 `command_id`(BE-X-01)와 함께 `traceparent`를 만들어 싣는다.
   백엔드 span은 Phase 3에서 만들지 않았다(테스트용 가짜 span 1건으로 Collector→Tempo 경로만 확인).
2. `.proto` 개정은 **§3(문자열/열거형 파라미터)와 한 번에** — 두 번 고치면 말단 재배포가 두 번이다.
3. 그 전까지 HW는 **아무것도 바꾸지 않아도 된다.** 지금 동작(필드 없음 → 새 trace)이 곧 기본값이다.

### 7-6. 정보 한 줄 — `otel_metrics.py` 머리말 주석

`otel_metrics.py:17`이 아직 *"export 주기 60초(HW-C-05)"* 라고 적고 있으나 **동작은 `config.OTEL_EXPORT_INTERVAL`
(15초)**이고 `BACKEND_AGENDA` §10-1이 15초로 종결했다. **주석만 낡았다** — 코드 변경 없음, 주석 한 줄 정리 권고.
(Phase 3에서 백엔드 A층 export 주기도 15초로 맞췄다 — `MK2_OTEL_EXPORT_INTERVAL` 기본값.)

### 7-7. 이 회신의 근거 (실측)

- Phase 3 결과: 백엔드 3개(`be-ingest`·`be-storage`·`be-gateway`)가 OTLP로 서버 Collector(`127.0.0.1:4316`)에
  metric·log를 내고, Collector가 metric→Prometheus·log→Loki·trace→Tempo로 분배한다. 엣지(임시)에서 보낸
  span이 서버 Tempo에서 `service.name=hw-sensor-node`로 조회됐다(HW `otel_trace.py`의 `cmd.receive → cmd.execute
  → cmd.result` 모양을 흉내 낸 가짜 span). **HW의 실제 span은 아직 한 건도 받지 못했다**(7-3 정보 참조).
- pytest 184건 전건 통과(서버, 2026-09-16) — 그중 `test_fake_span_reaches_tempo`가 Collector→Tempo 경로의 근거다.
