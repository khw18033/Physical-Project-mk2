## 0. 이 문서의 성격과 읽는 법

### 0-1. 구성 — 버킷 A vs 버킷 B

- **버킷 A (경로 설계, §1):** 구간(말단→엣지 / 엣지→서버 / 서버→뷰어) × **전송 방법** ×
  **어디를 거치나** × **왜 그 선택인가**. 즉 "바이트가 어떤 방법으로 어디를 지나는가."
- **버킷 B (경로 확정 후, §3):** 방법·경로가 정해진 뒤의 동작 디테일(트리거 작동 방식, 재연결,
  콜드스타트, 저장 방식, 키관리, QoS 등). **경로 자체를 바꾸지 않는 것.**

이 두 버킷을 섞지 않는다. 특히 요구사항 도출과 구현 접근을 airtight 분리한다(§3-1 vs §3-2).

### 0-2. 설계 대전제

**국가 인프라급으로 설계한다. 캡스톤은 이 설계의 특수 사례로 자동 포함된다.** 각 결정은 **"추상
요구(무엇을 지원해야 하나) + 현재 배포 프로파일(캡스톤에서 무엇을 고르나)"**으로 분리해
서술한다. 특정 모드·기술(길 B, WebSocket, Tailscale 등)을 국가 전제인 것처럼 단정하지 않는다 —
그것들은 우리의 현재 배포 선택이다. 태그: `[국가 인프라]`, `[확장 축]`, `[확인 필요]`.

### 0-3. 전송 기술은 "지금 쓰는 구현(교체 가능)"이다

미디어 경로의 전송 기술(말단↔엣지 RTP/UDP, 엣지↔서버 WebSocket, 원격 구간 Tailscale, 뷰어
WebSocket — 현재 프로파일은 터널 위 `ws`+토큰, tailnet 밖 뷰어용 WSS는 Phase 6)은 **고정된 필수
기술이 아니라, 전송/미디어 어댑터 뒤에 숨는 지금 쓰는 구현(교체 가능)**이다.

- **AI-C-08(미디어 입력 관리):** "카메라 URL, 장치 경로, codec, **전송 방식**은 미디어 어댑터
  내부에 숨기고 인지 기능은 공통 영상 입력만 소비해야 한다."
- **AI-C-06(메시지 전송):** "공통 전송 인터페이스로 송수신하고 **구간별 실제 전송 기술은
  어댑터에서 선택**해야 한다."
- **AI-C-12(인프라 제공자 추상화):** 현재 기술은 "현재 배포의 구현 선택일 뿐 핵심 코드의 필수
  기술로 하드코딩하지 않는다."

요구사항 층에서는 "미디어는 공통 인터페이스로 전송하고 실제 기술·경로 보호는 어댑터가
선택한다"로 쓰고, 이 문서(설계 근거)에서는 그 어댑터의 현재 구현을 구체적으로 다룬다.

**요구사항:** BE-T-07(미디어 뷰어 중계 — 소스·전송 기술·전송 모드에 고정되지 않은 틀).

## 1. 경로 확정 사항 (버킷 A)

### 1-0. 전체 경로 한눈에

미디어(영상)는 업무·관측·명령 3종 데이터와 근본적으로 다르므로 **별개 평면(경로)**으로
처리한다. 현재 배포의 전체 경로는 네 구간이다.

```
카메라/로봇        구역 엣지노드            중앙 서버(백엔드)         뷰어(관제 화면)
   │                  │                        │                      │
   │──[홉1]──────────▶│                        │                      │
   │  RTP/UDP         │ 액세스 유닛(AU) 재조립   │                      │
   │  (native 코덱)    │ frame_ref 부착          │                      │
   │                  │ (디코드하지 않는다)      │                      │
   │                  │──[홉2, 길 A·B]─────────▶│                      │
   │                  │  WebSocket(방식 B)      │ 중계(헤더만 읽음)      │
   │                  │  = 헤더 + native AU     │ drop-old(GOP 인지)    │
   │                  │  ══ Tailscale 터널 위 ══│ 토큰 인증·source_id   │
   │                  │                        │──[뷰어 분기]────────▶│
   │                  │                        │  WebSocket(방식 B)    │ 디코드(WebCodecs/
   │                  │                        │  ══ 터널 위 ws+토큰 ══│ createImageBitmap)
   │                  │                        │  (WSS는 Phase 6)      │ + 탐지 오버레이
   │                  │  [별도] 탐지·트윈 결과 → Kafka(업무 간선) → 백엔드 → 뷰어(상태 WS)
```

**핵심 성질(현재 배포 기준):**
- **[Phase 4 정정, 결정 10] 홉2는 길 A(상시 원본 상향)·길 B(온디맨드 중계)를 둘 다 지원하고,
  현재 개발 단계 = 길 A다.** 엣지가 클라이언트로 서버 `/ingest`에 붙어 계속 보내고, 서버는 뷰어가
  없으면 버린다(결정 4-b). 길 B의 절약은 서버→엣지 개폐 명령(Phase 6)에 있다 — §1-3-1.
- **구간마다 전송 방식이 다르다** — 홉1 RTP/UDP(카메라 native), 홉2·뷰어 WebSocket. 이 전환은
  억지가 아니라 **엣지=AU 재조립 지점 + 브라우저=종점 제약**의 필연(§1-6-3). **[Phase 4 정정,
  결정 1]** 코덱은 소스 native 그대로 종단까지 간다 — 엣지는 재조립만 하고 디코드하지 않는다.
- **frame_ref**가 엣지의 AU 재조립 시점부터 뷰어까지 동반된다(탐지 오버레이 정합 근거). 서버는
  헤더를 검증만 하고 `frame_ref`를 바이트 그대로 전파한다(원칙 10, `tests/test_media_relay.py`).
- **엣지↔서버 = Tailscale 터널**을 미디어·명령(Kafka)·관측(OTLP)이 공유(§1-4-6). **[Phase 4
  정정, 결정 5] 서버↔뷰어 = 같은 터널 위 `ws` + URL 쿼리 토큰** — 뷰어는 tailnet 구성원이다.
  tailnet 밖 뷰어용 WSS는 Phase 6(§1-5-0).

### 1-1. 대전제 — 미디어는 3종 데이터와 근본적으로 다르다

"왜 미디어에 MQTT/Kafka/OTLP를 안 쓰나"의 답이자 모든 비교의 출발점이다.

| 축 | 업무 데이터(수위 등) | 미디어(영상/사진) |
|---|---|---|
| 크기 | 작음(수십~수백 바이트) | 큼(프레임당 수십 KB~수 MB) |
| 빈도 | 초·분 단위 | 초당 15~30 프레임(연속 스트림) |
| 지연 민감도 | 초~분 허용 | 실시간(수백 ms 넘으면 트윈·감시 무의미) |
| 유실 허용 | 유실 안 됨(재난 데이터) | 프레임 몇 장 빠져도 됨(다음 프레임이 옴) |
| 보존 | 조회·감사 필요 | 대부분 실시간 소비 후 버림(일부만 저장) |

MQTT·Kafka·OTLP는 "작고 신뢰성 중요한 메시지"용 도구다. 미디어는 "크고 연속적이고 유실 허용"
이라 메시지 전송이 아니라 **스트리밍**이 필요하다. **MK1 선례가 이를 이미 실증** —
`media_transport.py` 주석: "MQTT는 수 KB 경량 메시지 전용, JPEG 한 장(50~150KB)×30fps = 초당
수 MB → 브로커 과부하." 대안(3종과 한 평면 합치기)은 브로커 과부하로 성립 불가.

**요구사항:** AI-C-08(영상은 업무·관측 경로와 분리된 별도 미디어 경로).

#### 1-1-1. 서버 비전 소비자의 자리 — 문만 열어 둔다 (Phase 4 결정 11)

"중계 경로는 페이로드를 열지 않는다"(§1-3-3)의 **주어는 서버가 아니라 중계 경로**다. 별도
소비자가 `/media?source_id=…`에 뷰어처럼 붙어 **자기 프로세스에서** 프레임을 디코드·추론하는
것은 중계와 무관하며 금지가 아니다. 그 산출물은 `detections.schema.json` 초안의
`origin.tier="server"`로 표시된다(`device`=pi7 온디바이스 / `edge`=엣지 노트북 / `server`=서버).
`frame_ref` 단일 출처는 깨지지 않는다 — 서버 비전은 헤더의 값을 **읽어서 그대로 붙일 뿐 새로
만들지 않는다**(원칙 10의 금지는 "재생성"이다). 산출물 형식은 **좌표 JSON**(이미지 번인 금지),
지연 예산은 VZ 버퍼 48프레임 = 15fps 기준 약 3.2초 안. **실제 모델·추론 배선·GPU 예산·중복
제거는 Phase 4 범위 밖**이며 이 절은 자리만 잡는다.

### 1-2. 홉1 — 말단(카메라/로봇) → 엣지노드

**경로 관점에서 홉1이 답하는 질문은 하나:** "말단에서 엣지로 이미지가 어떤 형식으로 오는가?"
→ **[Phase 4 정정, 결정 1] 소스 native 코덱의 액세스 유닛(AU).** 로봇(Go1)은 H.264, 고정
CCTV는 JPEG — 카메라가 무엇이든(RTSP·RTMP·SDK·Farsight 등) 하드웨어가 영상을 얻는 방법은
소스별로 다르지만, 엣지 입장에선 "AU 경계를 확정하고 `frame_ref`를 붙일 수 있다"만 성립하면
경로는 정해진 것이다. 소스 종류·출력 프로토콜의 세부는 미디어 어댑터(AI-C-08)가 흡수하며
버킷 B(§3). ⚠ **말단은 pi7이고 엣지는 엣지 노트북이다**(지시서 §2-2b) — pi7은 H.264를
디코드 없이 RTP로 패킷화해 엣지로 보낼 뿐, `frame_ref`를 찍지 않는다.

> 아래 RTP/코덱/연결 방식은 **미디어 어댑터 뒤에서 지금 쓰는 구현(교체 가능)**이다.

#### 1-2-1. 전송 프로토콜 — RTP over UDP (현재 배포)

**결정: RTP over UDP로 통일. 표준 IP 카메라는 앞에 RTSP로 세션을 연다.**

- **TCP vs UDP:** TCP는 순서 보장·유실 재전송(느리지만 확실). UDP는 연결 없이 던짐, 재전송·
  순서 보장 없음(빠르고 지연 적음, 실시간 영상).
- **RTP:** UDP 위 실시간 미디어 운반 규격. 조각마다 순번·타임스탬프·코덱표시를 붙임.
- **RTSP:** 영상을 안 나르고 재생 제어(PLAY/TEARDOWN)와 세션 협상만 하는 리모컨. 표준 IP
  카메라는 펌웨어에 RTSP 서버가 있어 접속 후 협상해야 RTP를 내보낸다.

**왜 RTP/UDP인가:**
- 영상은 프레임 한 장 잃어도 다음 프레임이 오니 유실 허용. TCP처럼 재전송을 기다리면 오히려
  화면이 밀려 끊긴다 → UDP가 맞다.
- 실시간이라 지연이 생명. HTTP(TCP)는 재전송으로 지연이 튄다.
- CCTV 업계 표준이 RTSP/RTP(조병현 HW-R-07·HW-S-06이 근거로 Axis RTSP 인용).
- RTP가 순번·타임스탬프를 실어줘 **frame_ref 재료가 공짜로 따라온다.**
- 홉1은 전부 로컬 LAN이라 UDP 약점(유실·방화벽)이 거의 무력화.

**RTSP는 소스별로 갈린다(전송 계층은 동일):** 로봇 온보드는 RTP 단독으로 충분, 고정 IP 카메라는
`rtsp://…`로 접속만. 어느 쪽이든 전송 계층은 RTP/UDP로 동일.

**대안 배제:** HTTP/WS(TCP)=카메라 native와 싸우고 재전송 지연; WebRTC/SRT=로컬 LAN엔
과함(NAT통과·암호화 장점이 로컬에선 무의미).

#### 1-2-2. 코덱 — 소스 native 코덱을 종단까지 그대로 (Phase 4 결정 1)

**[Phase 4 정정] 결정: 소스 native 코덱을 그대로 중계한다. 현재 배포 프로파일 = 로봇 H.264 종단 /
고정 CCTV JPEG 종단.** 이 문서의 이전 판은 *"JPEG로 통일. H.264 폐기"*였고 그 근거 (1)이 *"엣지가
이미 JPEG를 쥐어 H.264로 보내려면 재인코딩이 필요하다"*였다 — **틀린 전제였다.** 엣지는 디코드하지
않고 **AU 재조립만** 한다(HW `go1_relay`가 pi7에서 H.264를 디코드 없이 RTP로 내보내고, 엣지
`media_gateway`가 받는 구조). 그래서 "그냥 전달"의 효율 논거는 H.264 쪽에 붙는다.

- **규격이 어떻게 받치나:** 미디어 헤더의 `encoding`이 코덱을 **선언**한다(알려진 값 `h264`·`jpeg`는
  `$comment`, **enum 아님** — 생산자 어휘를 잠그지 않는다). 서버는 **필수·타입만 검증하고 값 어휘를
  보지 않으며 페이로드를 열지 않는다**(`media-header.schema.json`, `tests/test_contract_media.py`의
  `valid-unknown-encoding` 예시). 뷰어는 모르는 `encoding`을 디코드하지 않고 상태로 표시한다.
- **H.264가 방식 B와 어긋나지 않는 이유:** "한 메시지 = 한 AU + `frame_ref`"다. 프레임 간 의존은
  헤더의 `keyframe` 플래그와 서버 drop-old의 GOP 인지(§1-3-3)가 흡수한다 — IDR에서만 재개하고,
  IDR에는 SPS/PPS를 인밴드로 싣는다. **AU 경계 판정과 `keyframe` 플래그는 HW 구현에 없다** —
  우리가 홉2 송신기 규격으로 새로 정해 요청한다(`hw-envelope-conformance.md` §8).
- **뷰어 디코드:** JPEG는 `createImageBitmap`, H.264는 **WebCodecs**(`codec` RFC 6381 문자열을
  헤더에 싣고 `description`은 주지 않는다 — Annex-B in-band). Phase 4 실측에서 브라우저
  `avc1.42C01E` 디코드·표시 확인(`backend/gateway/console.html`).
- JPEG의 장점(프레임 독립·손실 전파 없음·디코드 가벼움)은 그대로 유효하며 고정 CCTV 프로파일이
  그 값을 쓴다. **코덱 선택은 소스별 프로파일이지 경로의 결정이 아니다.**

#### 1-2-3. 연결 방식 — 소스가 정한다 (Phase 4 결정 8-2)

**[Phase 4 정정]** 이전 판의 *"pull 기본"*을 **"소스 종류별 정적 정책"**으로 손질한다 — 로봇은
push(RTP를 엣지로 송출, 로봇 쪽 `config.py`의 `MEDIA_SENDER` 한 줄로 결정), 표준 IP 카메라는
pull(엣지가 `rtsp://…`로 접속). **런타임 협상이 아니다.** 어느 쪽이든 전송 계층은 RTP/UDP로
동일하고, RTP 재조립은 엣지의 FFmpeg/GStreamer가 처리한다(디코드는 하지 않는다 — §1-2-2).
⚠ **홉1의 push/pull과 홉2의 연결 방향은 다른 층이다** — 홉2는 항상 엣지가 클라이언트로 서버에
붙는다(결정 4-b, §1-3-1). 엣지에 인바운드를 열 필요가 없다.

#### 핵심 개념 — 무선 ≠ 인터넷 (홉1이 로컬인 이유)

"무선(전파)"과 "인터넷(로컬망을 벗어나 통신사 백본을 탐)"은 **독립된 두 축**이다. **로봇이 같은
WiFi 공유기에 붙은 엣지로 쏘는 건 "무선"이지만 "로컬"** — 인터넷 미경유. 그래서 홉1은 노출이
아니라 **암호화 불필요**. (암호화가 필요한 건 인터넷을 실제 건너는 홉2·뷰어.)

### 1-3. 홉2 — 엣지노드 → 중앙 서버

홉1과 조건이 정반대다(거리 멂, 소비자 여럿, 안 올리는 선택 가능).

#### 1-3-1. 근본 갈림길 — 전송 모드. 길 A·B 동시 지원, 현재 개발 단계 = 길 A (Phase 4 결정 10)

**이건 국가 전제가 아니라 배포 프로파일 선택이다.** 미디어 전송에는 두 모드가 있고, 어느
쪽인지는 배포 프로파일이 정한다.

- **길 A(상시 원본 상향):** 원본을 항상 서버로 올린다. 중앙에서 뭐든 가능하나 대역폭·저장·
  노출 부담이 크다.
- **길 B(엣지 처리 + 온디맨드 중계):** 엣지가 로컬 소비(탐지·트윈)하고 결과만 상향, 원본은
  관제사가 볼 때만 온디맨드 중계.

**추상 요구:** "미디어 전송은 상시-원본(길 A)과 온디맨드-중계(길 B)를 모두 지원하며, 배포
프로파일이 선택한다."

**[Phase 4 정정, 결정 10] 길 A·B를 둘 다 지원하고 소스별 프로파일로 고른다. 현재 개발 단계 =
길 A.** 이전 판의 *"현재 배포(캡스톤) = 길 B"*를 이렇게 고친 이유는 **구현이 이미 그렇게 돌기
때문**이다 — 결정 4-b(엣지가 클라이언트로 붙어 계속 보낸다) + 엣지 입구에서 안 버린다 +
"뷰어가 없으면 서버가 버린다"를 합치면 홉2는 길 A다. 길 B의 절약(현장 회선·로컬 처리)은 **서버→
엣지 개폐 명령**에서 나오고 그 배선은 Phase 6이다. ⚠ 길 A를 실제 로봇으로 **켜려면** HW `stream`
명령이 필요한데 지금은 `Command.parameters`가 `map<string,double>`이라 호출 불가다 — `stream_start`/
`stream_stop` 우회를 HW에 요청한다(`hw-envelope-conformance.md` §8). 길 B의 논거(대규모에서
대부분의 영상은 아무도 안 보고, 관측 페더레이션과 같은 결)는 그대로 유효하며 **프로파일이 고를
때의 근거**로 남는다.

**결정 4-b — open 신호는 연결 자체다.** `/media?source_id=…&token=…`에 **붙는 것이 켜기, 끊는 것이
끄기**. 상시(페이지 로드 시 연결)와 온디맨드(패널 열 때 연결)가 **같은 메커니즘**이고 서버는 그
차이를 모른다. `video{entity, open}` 같은 제어 메시지를 두지 않는다.

#### 1-3-2. 결과 데이터(현재 배포) — 업무 데이터라 기존 Kafka 간선 재사용

길 B의 현재 배포에서 탐지 박스·트윈 상태·이벤트는 영상이 아니라 **업무 데이터**다. 기존 홉2
업무 간선(Kafka)을 재사용하고 frame_ref를 동반. **Kafka를 쓰는 이유는 결과가 업무 데이터라
기존 간선을 그대로 쓰는 것**이며 새 전송을 열지 않는다.

**요구사항:** AI-R-02·AI-C-08(위험/판단 결과는 업무 데이터 평면으로 전달).

#### 1-3-3. 원본 영상(온디맨드) — WebSocket 방식 B (현재 배포)

**결정: 엣지→서버 원본 중계는 WebSocket, 뷰어 분기와 같은 방식 B 형식(프레임+frame_ref).
Tailscale 터널 위로.**

**핵심 개념 A — "웹소켓 1초 지연"의 정체 = 버퍼블로트, drop-old로 해결:**
"웹소켓 영상이 1초씩 밀린다"는 웹소켓 프로토콜이 느려서가 아니라 **버퍼블로트** 때문이다. 링크가
빼낼 수 있는 속도보다 빠르게 `send()`하면 전송 안 된 데이터가 큐(`bufferedAmount`)에 쌓이고,
큐에 갇힌 데이터가 오래돼 지연이 계속 커진다.

**해결책이 곧 우리 설계 — 최신 프레임만/오래된 프레임 드롭.** `bufferedAmount`가 임계 위면 새
프레임을 보내지 않고 버린다(뒤에 더 최신 프레임이 오니 낡은 건 드롭). **드롭 로직이 있으면
지연이 바운드된다 — 링크가 느려지면 프레임을 잃지(fps↓) 지연이 늘지 않는다.** 관제엔 정확히
맞는 트레이드오프. (정직한 단서: 드롭은 큐 무한증가는 막지만, 이미 TCP에 넘어간 바이트의 순간
스톨(head-of-line)은 못 막음. 깨끗한 링크에선 비쟁점, 손실 심한 링크에선 잔여 약점.)

**Phase 4 구현 — 뷰어 소켓마다 GOP 인지 drop-old**(`backend/gateway/media.py` `DropOldPolicy`·
`ViewerSlot`, `tests/test_media_dropold.py` 18건):
- **`T_drop` = 150ms × 배출률**(뷰어 소켓이 실제로 빼내는 바이트/초의 EWMA, 최근 60장 지평).
  하한 = 평균 AU 2장, 상한 = 1MB(`MK2_MEDIA_BUFFER_MAX_BYTES`). 배출이 멈추면 `in_flight/멈춘
  시간`으로 배출률을 즉시 깎아 `T_drop`이 바로 줄어든다(EWMA가 옛 값을 붙들지 않게).
- **`T_hard` = max(4×`T_drop`, IDR 최대 크기 2장)** — H.264에서 GOP를 자르면 다음 IDR까지 화면이
  없으므로 IDR 여유를 준다. 최근 60장에 `keyframe=false`가 한 장도 없으면(JPEG처럼 GOP가 없는
  스트림, **관측으로 판정하지 `encoding` 값으로 판정하지 않는다**) `T_hard := T_drop`.
- **상태 기계 `WAIT_IDR` / `FLOWING`:** 새 뷰어는 첫 IDR까지 기다린다(첫 전송은 항상 keyframe).
  `buffered > T_drop`이면 IDR이 올 때까지 GOP 단위로 버리고(`gop_cut`), `> T_hard`면 IDR도 버린다.
  드롭 뒤 재개는 반드시 IDR에서 — 실측에서 불연속 19개 전부 IDR 위치였다(아래).
- **회계에서 빠지는 바이트 둘:** `websockets` 전송 버퍼 `write_limit`(`MK2_MEDIA_WRITE_LIMIT`,
  8KB)과 커널 송신 버퍼 `SO_SNDBUF`(`MK2_MEDIA_SNDBUF`, 64KB → Linux 실효 128KB). **지연 바운드
  = `T_drop + write_limit + sndbuf`** 를 링크율로 나눈 값이지 150ms가 아니다 — 150ms는 서버 큐
  몫이다. `sndbuf`를 커널 자동조정에 맡기면(값 0) loopback MSS 64KB 탓에 ~1.4MB까지 커져 링크가
  멈춰도 수십 초분이 우리 회계 밖에 쌓인다 — 그래서 2026-09-19 사용자 결정 A로 64KB를 잡았다.
  값을 더 낮추면(예 16KB) 같은 링크에서 지연은 줄지만 DERP 경유 처리량 상한이 내려간다(다음 결정 항목).
- **서버가 바운드하지 못하는 경우 — 링크는 빠른데 뷰어 앱이 느릴 때.** 초과분이 뷰어 쪽 커널
  수신 버퍼(Windows는 `SO_RCVBUF`를 무시하고 자동조정, 브라우저도 같다)에 쌓여 서버 `send()`가
  막히지 않는다 → 서버 드롭 0, 지연은 뷰어 안에서 커진다. **뷰어가 자기 큐를 관리해야 한다**
  (VZ 통지 항목 — 최신 프레임만 rAF 주기로 그린다).

**Phase 4 실측(2026-09-19, 서버 ↔ 컴퓨터 임시 엣지, Tailscale 직접 경로 2ms/22ms):**
- 빠른 뷰어(직접 경로): 173/173 · 브라우저 2954장 gaps 0 · 첫 프레임 keyframe · 도착 age p50 7ms
  p90 9ms(콜드스타트 215ms). 단계 7 브라우저 세션 전체 회계 **3836장 송신 · 드롭 0**.
- 링크를 500kbit로 조인 뒤(서버 `tc tbf`, 30초): 송신 745 → 수신 538, **드롭 207·GOP 절단 20,
  불연속 19개 전부 IDR에서 재개, IDR 50/50 전달, 바이트 동일**. 지연 p50 1.97s·p90 2.34s·max 2.53s
  — 바운드 `(T_drop 5.7KB + write_limit 8KB + sndbuf 128KB)/62KB/s ≈ 2.3s`와 일치. **지연의
  대부분은 sndbuf 몫**이고 서버 큐 몫은 ≈92ms였다.
- 실측 조건은 연구실 배치의 한 링크율뿐이다. 현장 회선·DERP 경유·실물 엣지는 범위 밖(§3-3).

**핵심 개념 B — WS vs RTP 단계별 지연 예산 (진짜 차이는 손실 거동):**
프레임 한 장이 엣지→관제까지 가는 시간(Tailscale 직접 연결·국내 가정, 추정치 — 단 **터널 왕복은 Phase 3에서 3ms, Phase 4에서 2ms/22ms로 실측**됐다, §1-4-1):
- **경로 A — WebSocket 종단간:** 인코딩 0(소스 native AU 그대로) + 메시지 구성 ~0.1ms + 암호화 ~0.05ms +
  엣지→서버 ~15~40ms + **서버 통과 ~0.1~2ms**(디코드·재인코딩 없음 — Phase 4 실측 직접 경로 age p50 7ms) + 서버→뷰어 ~5~40ms +
  브라우저 디코드/렌더 ~2~8ms ≈ **30~90ms(나빠도 ~150ms).**
- **경로 B — RTP/UDP 후 서버에서 WS 변환:** 위와 같되 RTP 패킷화 ~0.5~2ms + **서버
  변환(재조립→frame_ref 재부착→WS 재구성) ~1~7ms** 추가 ≈ **35~100ms.**

**결론:** 깨끗한 링크에선 두 경로가 거의 같다(둘 다 수십~100ms, **1초 근처 아님**). RTP의 "서버
변환"은 ~1~7ms로 싸지만 WebSocket은 그 변환을 **아예 안 한다.** 즉 "RTP 변환이 싸다"는 "RTP가
낫다"가 아니라 "RTP가 크게 나쁘진 않다"까지만 증명. **진짜 차이는 변환 비용이 아니라 손실
거동:** RTP/UDP는 손실 시 프레임 버리고 즉시 계속(우아한 열화), WebSocket/TCP는 재전송 스톨.
깨끗한 링크면 WS, 나쁘면 WebRTC(상향 카드).

**왜 WebSocket이 이 조건에 맞나 (선택 근거):**
1. **[Phase 4 정정] 엣지가 AU 경계를 확정하고 frame_ref를 붙인 뒤에는 "메시지 하나 = AU 하나"가
   자연 단위다** → RTP로 다시 패킷화하면 서버에서 재조립·재부착을 한 번 더 해야 한다(이전 판의
   "이미 디코드된 JPEG" 전제는 틀렸지만, 재감싸기가 낭비라는 결론은 같다).
2. **frame_ref 묶기가 핵심 요구** → WebSocket은 프레임+frame_ref를 **한 메시지로 원자적** 전송
   → 오버레이 정합 정확. RTP/WebRTC/SRT는 메타를 별도로 실어 재정합 드리프트가 돌아옴.
   (frame_ref는 시간이 아니라 **정확성**에서 WS가 이김.)
3. **종점이 브라우저** → 어차피 WS 변환 필요 → 엣지→서버도 WS면 **서버가 변환 없이 흘려보내는
   중계**가 됨(대칭성 이득).
4. **온디맨드·소수·저지연 허용(현재 배포)** → TCP 약점(재전송 지연)이 세게 안 물림.

**갈아탈 트리거 (대비책):**
- **밀리초 지연이 생명(원격 정밀 조종)** → WebRTC로 상향. (영상 자체론 더 낫지만 frame_ref
  정합·연결 복잡도가 대가.)
- **상시 연속 고레이트를 공개망으로** → SRT(방송용). 지금은 Tailscale 안이라 불필요.
- **WebSocket 자체가 안 됨** → HTTP POST(MK1 검증). 전환은 자동 감지(구현 §3-2).

#### 1-3-4. 저장 — 중계·저장 모드, 현재 배포 = 중계 기본 + 촬영본 저장소(4b)

"스트림을 연다"는 연결 유지지 저장이 아니다. **미디어 경로는 중계(pass-through)와 저장(store)
모드를 지원하며, 어느 쪽인지는 배포 프로파일이 정한다.** 현재 배포 = 중계 기본(서버는 통과점)
+ 필요 시 엣지 단기 링버퍼. **저장이 필요한 배포**(상시 녹화, 5초 주기 저장)는 저장 모드를
프로파일로 선택하며, 저장 위치·방식·at-rest 암호화는 경로 밖 별도 사안(§3).

**[Phase 4 결정 9] 스트림 저장과 별개로 「촬영본(정지 촬영 세션)」 저장소를 둔다 — HW #15.**
로봇의 스캔·텔레옵 촬영 세션(`session_id` 하나 = JPEG 낱장 묶음 + 매니페스트)은 스트림이 아니라
**임무 종료 시 일괄 업로드되는 파일**이다. 새 저장 제품(S3 호환·MinIO·MongoDB)을 들이지 않고
**파일시스템 + 작은 HTTP PUT 수신단**(포트 8767, `<서버 tailscale IP>` 바인딩, 토큰, 별도 systemd
유닛)으로 받는다 — HW 업로더가 서명 없는 단순 PUT 한 방이기 때문이다. **PUT은 두 번**: 매니페스트
(`<session>.manifest.json`)를 먼저, 2xx 뒤 `<session>.tar.gz`. 최종 경로는 **URL이 아니라 매니페스트의
`source_id`·`session_id`가 정한다**(로봇 2대가 같은 분에 시작하면 URL 파일명이 같다). 아카이브 안은
뒤지지 않고, `frame_ref_base`는 채우지 않는다(엣지를 거치지 않아 발급 주체가 없다 — 시각은
`t0_unix + n×interval_s`). 보존은 **용량 상한 + 오래된 세션부터**. MySQL `media_capture` 한 행 =
세션 하나(매니페스트 원본 통째 보존, 다중 소스 병합은 HW #14 뒤). 입구는 Phase 4 뒤에도 남긴다.

**구현(Phase 4 4b, 2026-09-19):** [`backend/gateway/capture.py`](../../backend/gateway/capture.py)(별도 프로세스 —
대용량 PUT은 블로킹이라 WS 게이트웨이의 asyncio 루프에 올리지 않는다, systemd `mk2-capture`) ·
[`infra/sql/mk2_media_capture.sql`](../../infra/sql/mk2_media_capture.sql)(DDL + GRANT `SELECT, INSERT, UPDATE`, DELETE 없음) ·

매니페스트 검증 → `INSERT` → 원자적 rename → `COMMIT`**(rename 실패 시 롤백) — 파일만 놓이고 행이 없거나 그 반대가
되지 않는다. 서버 실측: 저장 `201` · 재전송 `200 already_stored`(파일·행 유지) · 스캔 세션 `kind` 보존 · 매니페스트
없는 아카이브 `409` · 잘못된 토큰 `401`(파일·행 없음) · 보존 dry-run이 오래된 세션부터 선정. 실제 삭제 경로는 이
Phase에서 켜지 않았고(선정만), **행은 어떤 경우에도 지우지 않는다**(`purged_at`만). 실물 HW 촬영본 적재는 0건 —
입구 개통은 HW에 따로 통지한다. ⚠ MySQL `JSON` 칼럼은 값을 보존하지 수의 표기까지 보존하지 않는다(`t0_unix` 17자리
float의 마지막 자리) — 원본 바이트가 필요해지면 별도 칼럼을 더한다.

**요구사항:** BE-T-07(중계·저장 모드)·BE-S-09(이벤트 트리거 캡처·at-rest 암호화·촬영본 저장소).

### 1-4. 엣지 ↔ 서버 연결 — Tailscale 터널

#### 1-4-1. 문제와 결정 — 왜 VPN인가

원격지에서 시연할 경우 엣지↔서버는 지역이 달라 같은 LAN이 안 되고, 전용선이 없으면 물리적으로
인터넷 회선을 타야 한다. 제약은 "영상이 인터넷에 노출되면 안 됨."

**요구 세 개가 겹친다:** (1) 암호화(노출 방지), (2) 엣지가 사설 IP/CGNAT라 서버가 못 찾는 문제
해결(안정 오버레이 IP), (3) 양방향(서버→엣지 명령, 엣지→서버 미디어·결과). **VPN 오버레이가
셋을 한 번에** 푼다.

**국가 인프라 vs 현재 배포:** 국가 인프라는 전용망(전용선/사설 WAN)으로 공용 인터넷 미경유를
전제. **현재 배포에서는 전용망이 없으므로 Tailscale VPN**으로 공용망 노출 없이 연결(전용선의
현재 배포 대체).

> **실측 상태(2026-09-16, Phase 3).** Tailscale이 **서버에 설치됐다**(1.102.4, `tailscaled`
> enabled, 팀 공용 계정). 임시 엣지(연구실 컴퓨터, Wi-Fi 사설망 뒤)와의 연결을 관측 2계층
> 검증에 실제로 썼다 — `tailscale ping`이 **처음엔 DERP 릴레이(72ms)였다가 다음 시도에 직접
> 경로(3ms)**를 잡았다. 즉 §1-4-5의 "직접 연결이 잡히면 릴레이를 거치지 않는다"가 이 배치에서
> 확인됐다. **다만 연구실 공유기 뒤의 컴퓨터이며 현장 회선·전용 엣지 장비는 아니다** — 아래
> 지연 예산의 나머지 항목은 여전히 추정이다.
>
> **Phase 4(2026-09-19)** 같은 배치에서 미디어·Kafka(EDGE 리스너 9095)·관측(OTLP 4316 +
> 페더레이션)이 **하나의 터널을 실제로 공유**하며 관통했다 — `tailscale ping` 직접 경로 2ms(컴퓨터→
> 서버)/22ms(서버→컴퓨터). 실측 뒤 임시 노출(8766·9095·4316·`edge_federate`)은 되돌렸고 뷰어
> 입구 8765만 남겼다 — 그 뒤 **단계 10에서 4b 촬영본 입구 8767을 열었다**(ufw pi7 `/32`, 되돌림
> 대상 아님 — 결정 9 ㄴ). **현재 열린 MK2 입구는 8765·8767 둘이다**(`infra/README.md` §3).
> **실물 엣지가 서면 compose 주석 판을 되살리고 주소만 바꾼다.**

**대안 배제:**
- **역터널(Cloudflare Tunnel·frp·ngrok·SSH -R):** 인바운드 포트 0으로 CGNAT엔 강하나,
  (a) "한 서비스 노출"용이라 양방향에 어색, (b) **제3자 릴레이가 TLS를 자기 쪽에서 종단해
  트래픽을 평문으로 봄** → 개인정보가 핵심인데 제3자가 영상을 보는 건 자기모순. (Tailscale
  릴레이는 종단간 암호화라 내용을 못 봄.)
- **게이트웨이(공인 IP VPS):** 사실상 릴레이 직접 구축 → 운영 부담·병목·VPS가 트래픽 봄.
- **전용선/사설 APN:** 공개 인터넷 물리적 회피(국가 인프라 전제). 비용 때문에 캡스톤엔 비현실.

#### 1-4-2. 왜 Tailscale인가 (현재 배포 구현)

- **Tailscale = WireGuard를 무설정 메시로 만든 것.** NAT 통과 자동, 수동 키 관리 없음,
  WireGuard라 처리량 높고 오버헤드 낮음.
- **WireGuard 직접(raw):** NAT 통과를 수동 설정해야 함 → 원격 CGNAT엔 Tailscale 자동화가 실익.
- **OpenVPN:** 느리고 설정 복잡. **ZeroTier:** 자체 프로토콜·L2 지향, 같은 링크에서 Tailscale이
  빠름(L2 불필요).

> 범위 밖: 코디네이션 서버 형태·자체호스팅 여부 같은 세부 운영은 "외부 노출 없이 전송"이라는
> 이 절의 주제를 벗어나므로 다루지 않는다.

#### 1-4-3. 핵심 개념 — "인터넷을 거친다" ≠ "인터넷에 노출된다"

비유: 인터넷=우편 시스템. 대전→서울 편지는 무조건 거친다. 하지만 **밀봉(암호화)하고 정확한
수신인에게만(비공개) 보내면, 거쳤어도 아무도 내용을 못 봤다.**

- **거친다(transit):** 패킷이 공유 인프라를 통과. 원거리면 무조건.
- **노출된다(exposure):** 3차원 — **도달성**(공인 IP 열린 포트로 아무나 접속 시도),
  **가독성**(평문이라 경로에서 읽힘), **지속성**(제3자 색인·저장).

**MK1이 "노출"이었던 이유:** 공인 IP(210.x) + 열린 포트(도달성) + 평문 HTTP/MJPEG(가독성).
프로토콜이 HTTP라서가 아님. → 암호화(가독성 0)+비공개 도달(도달성 0)이면 거쳐도 노출 0.

#### 1-4-4. 핵심 개념 — 암호화는 터널(입구/출구)이지 영상 데이터가 아니다

- **터널(연결) 암호화 — 입구/출구:** VPN·TLS·SRTP. 앱은 평문을 터널에 던지고 터널이 자동
  암호화(양 끝). **영상 바이트를 손대지 않음.** ← 우리가 쓰는 것.
- **페이로드(내용) 암호화 — 데이터 자체:** 앱 코드에서 바이트 직접 암호화. ← 우리 모니터링엔
  불필요.

**Tailscale을 켜면 그 안 모든 것(영상·메시지)이 입구에서 자동 암호화. 백엔드 코드에 크립토
0줄** — VPN 켜기(설정) 또는 TLS 엔드포인트(`wss://`, `https://`).

#### 1-4-5. 핵심 개념 — 직접 연결(90%+) vs DERP 폴백

상용 VPN이 느린 건 암호화가 아니라 **우회**(먼 공유 출구 서버로 돌려보냄) 때문. **Tailscale은
두 기기를 직접(P2P) 잇는 걸 우선**하고 직접 NAT 통과 성공률이 **90% 이상**이라, 직접이면
엣지→서버가 원래 물리 경로로 가고 암호화만 얹힘 — **우회 없음.**
- **폴백(DERP 릴레이):** 직접 실패 시(symmetric NAT·UDP 차단). DERP는 TCP라 우회+head-of-line.
  WebSocket(TCP)이 DERP(TCP)를 타면 TCP-over-TCP로 이중 스톨 → 이 경우만 느릴 수 있음.
- **확인·완화:** `tailscale ping <서버>` → `via <ip>:<port>`(직접) vs `via DERP(xxx)`(릴레이).
  릴레이에 묶이면 서버 옆 peer relay(UDP·직접에 필적)로 우회 거리 제거.
- **유리한 조건:** 우리 배포는 국내(하천↔랩, 짧은 RTT) + 온디맨드 소수 스트림이라 최악의
  릴레이도 감당.

#### 1-4-6. 핵심 — 3평면이 단일 터널을 공유한다

엣지↔서버 구간엔 **미디어 + 명령(Kafka) + 관측(OTLP)**이 **전부 그 하나의 Tailscale 터널**을
탄다(Tailscale이 L3라 안에 뭐가 흐르든 실림).

- **왜 다 타나:** 서버를 서버의 **Tailscale IP(100.x)로 주소지정**하면 OS 라우팅이 그 대역을
  Tailscale 인터페이스로 보냄. 즉 강제가 아니라 "서버에 사설로 도달"의 결과.
- **Kafka/OTLP는 Tailscale을 모른다:** 그냥 어떤 IP로 TCP 연결을 여는 것뿐, 밑에서 WireGuard가
  암호화·라우팅을 대신함. Tailscale이 Kafka를 대체하는 게 아니라 그 밑에 암호화된 IP 링크가
  깔린 것.
- **채널·실시간성 불변:** Kafka 토픽·OTLP 스트림·미디어 WS는 같은 도로를 공유할 뿐 합쳐지지
  않음. 직접 연결이면 추가 지연 0(암호화 µs). Kafka 자체 TLS를 따로 안 켜도 터널이 암호화 →
  설정 단순.
- **정직한 단서(버킷 B):** 세 평면이 같은 물리 회선을 공유하니 좁은 현장 회선에선 영상이 명령을
  밀 수 있음(QoS) → §3.

#### 1-4-7. 법적 근거 — "인터넷 금지"가 아니라 "암호화 요구"

로봇 카메라는 법적으로 **이동형 영상정보처리기기**(개인정보보호법 제25조의2, 2023.9.15 시행)에
해당. 공개된 장소 사람 촬영은 원칙 제한 + 촬영사실 표시 의무.

**핵심:** 안전성 확보조치 기준 **제7조제4항** — "개인정보를 정보통신망을 통하여 인터넷망
구간으로 송·수신하는 경우에는 안전한 암호 알고리즘으로 암호화하여야 한다." 즉 **법은 "인터넷
경유"를 금지하지 않고 "경유 시 암호화"를 요구.** "인터넷에 올리지 마라"는 법적으로 "암호화 없이
공개망에 노출/전송하지 마라". 해외(GDPR 제32조)도 동일(전송 중·저장 중 암호화+접근통제).
- **탈출구:** 비식별화하면 개인정보가 아니게 되나, **실시간 얼굴 블러가 불가능**하므로 우리는
  비식별화가 아니라 **경로 암호화**로 보호한다(§3에서 비식별화 제외 사유).

#### 1-4-8. 계층 구분 — VPN은 도로, 영상은 그 위로

```
영상 운반: WebSocket(방식 B) = 프레임 + frame_ref   ← "영상이 흐르는 방법" (L7)
전송 계층: TCP
VPN 터널: Tailscale (암호화 폐쇄망)                 ← 이 위를 감싸는 배관 (L3)
물리 회선: 공용 인터넷                              ← 실제 도로
```

VPN은 RTP/WS를 대체하는 게 아니라 그 트래픽이 흐르는 길 전체를 감싸는 배관. 엣지↔서버에
붙고(홉1은 같은 LAN이라 불필요), **현재 프로파일에서는 서버↔뷰어도 같은 터널 위다**(뷰어가
tailnet 구성원 — §1-5-0. tailnet 밖 뷰어용 WSS는 Phase 6).

**요구사항:** BE-T-08(엣지↔서버 보안 오버레이) — AI-C-17의 백엔드 짝.

### 1-5. 뷰어 분기 — 서버 → 뷰어(관제 화면)

받는 쪽이 기계(엣지·서버)에서 **사람이 보는 브라우저**로 바뀐다. 브라우저는 정해진 프로토콜만
(HTTP/HTTPS·WebSocket·WebRTC) — RTP/UDP를 직접 못 받아 어디선가 뷰어용으로 변환해야 한다.

#### 1-5-0. 두 홉의 보호 방식 — 추상 요구와 현재 프로파일 (Phase 4 결정 5)

- **엣지↔서버:** 양쪽 다 우리 인프라(엣지 노드 + 우리 서버) → **Tailscale VPN**(§1-4).
- **서버↔뷰어(추상 요구):** 전송 암호화 + 허가된 관제사만 + 백엔드가 원본 URL을 직접 노출하지
  않음(§1-5-3). **"거친다≠노출된다"** 원칙이 여기도 동일.

**[Phase 4 정정] 현재 프로파일 — 뷰어는 tailnet 구성원이다. 터널 위 `ws` + URL 쿼리 토큰.**
이전 판은 *"모든 관제사 브라우저에 Tailscale을 까는 건 표준이 아니므로 WSS+인증"*이라 적었는데,
VZ 코드 주석(*"관제 웹(노트북)·로봇(pi7)·탐지(데스크톱)가 전부 테일넷으로 붙는다"*)과 브라우저
관측 입구(4318, Tailscale IP에만 바인딩 — 결정 7 A)가 **뷰어가 안에 있다**고 전제하므로 두 전제가
양립하지 않았다. 「뷰어는 tailnet 구성원」으로 통일한다. 그러면 전송 암호화는 터널이 하고(§1-4-4),
인증은 토큰이, 도달성은 서버 `<서버 tailscale IP>` 바인딩 + ufw `/32`(호스트 파이썬 포트라 ufw가
진짜 통제다)가 맡는다. **tailnet 밖 뷰어(외부 관제·시연장 게스트)용 WSS는 Phase 6**에서 관측 대체
경로와 함께 연다 — `CLAUDE.md` 원칙 3의 `WSS`는 그 프로파일을 가리킨다.

- **토큰 규칙(구현):** `MK2_WS_TOKEN`(뷰어)·`MK2_EDGE_TOKEN`(엣지)을 URL 쿼리 `token=`으로 받는다.
  **loopback 바인딩이면 없어도 열고, loopback이 아닌데 비어 있으면 기동 시점에 변수 이름을 대며
  죽는다**(`settings.require_token`). 불일치·부재는 **close 4401**, 경로 밖은 4404, `source_id`
  없음은 4400, 같은 `source_id`의 두 번째 엣지는 4409. 토큰은 로그에 `***`로만 찍힌다(음성 대조:
  journal·Loki에 토큰 문자열 0건). RBAC(BE-Q-04)는 Phase 6.

#### 1-5-1. 결정 — WebSocket 전용 채널 + frame_ref 묶음

**결정: 영상 전용 WebSocket 채널(`/media`, 현재 프로파일 `ws`+토큰)로 프레임+frame_ref를 묶어
보낸다. 브라우저가 디코드해 `<canvas>`에 그린다.**

**대안 비교·배제:**
- **MJPEG:** "`<img>`가 프레임별 헤더(frame_ref)를 못 읽음"이 정확한 논거 — 직접 `fetch`+
  ReadableStream 파싱하면 되지만 그건 WebSocket 바이너리 프레이밍을 지저분하게 재발명하는
  것이라 이점 없음.
- **HLS:** 세그먼트 기반이라 지연이 본질적으로 초 단위(LL-HLS도 2~5초) → 실시간 관제 실격.
- **WebRTC:** **영상 자체론 WebSocket보다 낫다(sub-초·기본 암호화·손실 강함).** 배제는
  (1) frame_ref 묶기 어색(미디어 SRTP, 메타 별도 DataChannel→재정합), (2) 연결 수립 복잡
  (시그널링·STUN/TURN·ICE·SDP), (3) 관제엔 WS 지연으로 충분 → **정밀 원격조종 상향 카드.**

#### 1-5-2. 채널 분리 — 영상 vs 상태·명령

**결정: 영상 전용 WS 채널을 상태·명령 WS(BE-T-03)와 분리.** 근거 넷:
1. **Head-of-line:** 한 WS에 섞으면 큰 영상 프레임이 TCP 버퍼에서 작은 명령 메시지를 뒤로 막음.
   명령은 지연 민감+재난 제어라 유실 불가 → 영상이 명령을 밀면 안 됨.
2. **손실 의미가 다름:** 영상 유실 허용(drop-old), 명령 유실 불가. 한 채널에 drop-old를 걸면
   명령 드롭 위험.
3. **수명 주기:** 영상은 온디맨드, 상태·명령은 상시. 분리하면 영상 채널을 껐다 켜도 상태·명령이
   안 흔들림.
4. **캐시 정책의 전제:** 캐시가 채널마다 갈림(§1-5-4). 한 스트림이면 채널별 캐시 정책을 걸 수
   없음. **채널 분리는 재접속 캐시 설계 성립의 토대.**

- **스트레스 테스트:** 앱 레벨 우선순위 큐를 매겨도 밑의 TCP는 바이트를 순서대로 직렬화하니 이미
  버퍼에 든 영상을 명령이 추월 못 함. **별도 WS=별도 TCP 스트림=진짜 독립**이라야 해결.
- **구현(Phase 4):** 같은 포트 8765에 **경로로 분리** — `/state`(상태·명령, `write_limit` 32KB)와
  `/media?source_id=…`(영상, `write_limit` 8KB + `SO_SNDBUF`). 주소·포트는 같고 뷰어는 두 번째
  소켓을 연다. 엣지 입구 `/ingest`는 별도 포트 8766(`MK2_MEDIA_INGEST_PORT`, 0이면 닫힘 — Phase 4
  실측 뒤 닫아 두었다). 서버는 `source_id`당 엣지 하나만 받고, 뷰어는 `source_id`별로 여럿이
  붙어 각자 drop-old를 받는다(`Relay.fan_out`).

#### 1-5-3. 담당 구분 (VZ-I-06 빈칸 채움)

- **백엔드(이대규):** 엣지 영상을 뷰어용으로 중계(헤더 검증·`source_id` 분기·drop-old)·인증/권한
  통제(원본 URL 직접 노출 안 함, 터널 위 `ws`+토큰 — WSS 종단은 Phase 6 프로파일). BE-T-07·
  BE-T-03 근거. **[Phase 4 정정] `frame_ref`는 백엔드가 부착하지 않는다 — 엣지가 부착하고
  백엔드는 바이트 그대로 전파한다**(원칙 10).
- **가시화(김현우):** 받은 프레임을 디코드해 `<canvas>`에 그리고 탐지 박스 오버레이(출처 구분),
  화면 구성. VZ-I-06·VZ-I-07 근거. (백엔드가 형식 초안 제공 — `vz-media-interface.md`.)
- **엣지(HW):** AU 재조립·`frame_ref` 부착·홉2 송신기(방식 B). 실물이 아직 없어 Phase 4는
  `tests/media_publisher.py`가 그 참조 구현이다.

#### 1-5-4. 재접속 정확성 — 뷰어 분기의 요구사항 제약

**재접속·정지 시 낡은 것을 live로 그리지 마라.**
- **재접속 시 캐시 금지 3종:** `video_frame`(옛 프레임이 정지 화면인데 현재처럼),
  `detections`(frame_ref가 지금 없는 프레임을 가리켜 박스가 엉뚱한 데), `command_result`(지난
  결과가 방금처럼). 반대로 `state`·`telemetry`·`actuator_state`·`control_lock`·`plan`·
  `plan_progress`·`video_meta`는 캐시.
- **캐시값 ts는 원본 발행 시각 유지:** 푸시 시점으로 다시 찍으면 stale 판정이 리셋됨.
- **영상 staleness 감지 — [Phase 4 정정] 기준은 도착 시각이다.** 정상 운영 중에도 스트림이
  얼어붙으면 "X ms간 새 프레임이 **도착하지** 않음 → 정지 표시". `frame_ref.capture_timestamp`는
  엣지가 프레임 경계를 확정한 시각(촬영 시각이 아니고 말단 지연을 포함하며 미보정)이라 뷰어
  시계와 비교하면 편향이 든다 — staleness는 뷰어의 마지막 도착 시각으로 판정한다. **카메라 영상
  가용성**은 **장치 가용성(availability)**과 별개 신호이고, 카메라 하드웨어 연결 상태(VZ-D-07의
  한 칸)는 또 다른 축이라 HW 계약에 속한다.
- **`video_meta`**(캐시 7종의 하나)는 Phase 4에서 미디어 헤더 규격만 정했고 **상태 채널 발행은
  Phase 5로 이월**한다 — 실체는 `source_id`별 `encoding`·`width`·`height`·`codec`과 마지막 도착
  시각, 발행 시점은 `/ingest` 첫 프레임과 해상도 변경(스트림 재개 사건).

**요구사항:** BE-T-06(재접속 캐시)·가시화 VZ-I-02/VZ-I-06.

### 1-6. 공통 요소 — 세 구간이 하나로 맞물리나

#### 1-6-1. frame_ref — 경로 전체를 관통 + 뷰어에서 합류

frame_ref는 홉1(RTP가 순번·타임스탬프를 실어줌 → **엣지가 AU를 재조립하며 부착**)에서 출발해
홉2·뷰어(방식 B)까지 관통. **핵심 구조:** 영상은 미디어 WS 경로로, 탐지(detections)는 Kafka→상태
WS 경로로 흐르다 **뷰어에서 합류.** 뷰어에서 두 경로의 frame_ref가 F==F로 맞아야 오버레이 정확 —
경로 종점의 실제 관문.

- **성립 조건(단일 출처):** frame_ref는 엣지에서 **한 번만** 찍히고, 그 프레임에서 파생된 영상과
  탐지가 **둘 다 그 값을 실어 나를 때만** 정합. AI가 자기 번호를 새로 만들면 어긋남. 서버 중계는
  **바이트 그대로** 전파한다(Phase 4 `tests/test_media_relay.py` — 수신 blob이 송신 blob과 동일).
- **[Phase 4 결정 2] `capture_timestamp`는 ISO date-time 문자열(콜론 오프셋 + 밀리초)이고 epoch ms가
  아니다.** 이 문서의 이전 예시(§1-6-2)가 우리 규격 파일(`frame-reference.schema.json`)과 어긋나
  있었다 — 규격이 기준이다. 뜻은 **"엣지가 프레임 경계를 확정한 시각"**(촬영 시각이 아니고 말단
  지연을 포함하며 미보정). 상관키는 frame_ref **밖** — 미디어 헤더·탐지의 선택 `correlation_id`.
- **온디바이스 탐지의 정합 등급(결정 3):** 탐지 메시지의 **`alignment`**(string, 알려진 값
  `frame`·`unaligned`는 `$comment`). 뷰어 규칙은 **fail-safe** — `alignment=="frame"`이고 `frame_ref`가
  있을 때만 프레임 정합, **그 외(부재·모르는 값 포함) 전부 unaligned**로 그린다.

#### 1-6-2. 인터페이스 규격 — 방식 B · bbox 좌표계 (실제 포맷)

**웹소켓 메시지 — 방식 B:** `[4바이트 big-endian: 헤더 길이][JSON 헤더][페이로드 바이트]`. 수신 측은
앞 4바이트로 헤더 길이 읽고 → JSON 파싱(frame_ref·encoding·keyframe…) → 나머지가 페이로드(H.264
AU 또는 JPEG). (base64로 JSON에 넣으면 33% 부풀어 배제.) 규격 파일
[`media-header.schema.json`](../../contracts/common/media-header.schema.json), 예시 6개
`contracts/common/examples/media-header-*.json`(음성 4개 포함), 구현 `media.encode_frame`/`decode_frame`.

```
[헤더길이:4B][{"frame_ref":{"source_id":"go1-001_front",
                            "capture_timestamp":"2026-09-18T12:00:00.123+09:00",
                            "sequence_id":4837},
              "encoding":"h264","keyframe":true,"width":464,"height":400,
              "codec":"avc1.42E01E","correlation_id":null}][H.264 AU 바이트]
```

| 헤더 필드 | 필수 | 뜻 |
|---|---|---|
| `frame_ref` | ✅ | `frame-reference.schema.json` 그대로(`$ref`, `additionalProperties:false`) — 엣지가 부여 |
| `encoding` | ✅ | 페이로드 코덱 선언. string, `$comment` `h264`·`jpeg` — **enum 아님** |
| `keyframe` | ✅ | 이 AU만으로 디코드 시작 가능한가(IDR). JPEG는 항상 `true`. **서버 drop-old의 유일한 페이로드 지식** |
| `width`·`height` | ✅ | 원본 해상도(탐지 `bbox_space.reference.{width,height}`와 같은 값). 바뀌면 스트림 재개 사건(§10-5 회신) |
| `codec` | 선택 | RFC 6381 문자열(WebCodecs `VideoDecoderConfig.codec`). `description` 없음 — Annex-B in-band |
| `correlation_id` | 선택 | 명령 산출물일 때의 상관키. frame_ref 밖에 둔다(결정 2) |

서버는 이 헤더를 **필수·타입만** 검증하고(값 어휘·페이로드는 보지 않는다), 헤더가 아닌 것(텍스트
프레임·헤더 길이 초과·JSON 아님·필수 누락·타입 불일치)은 **그 프레임만 버리고 연결은 유지**한다
(`be.gateway.media_rejected{stage}`). 헤더에 `additionalProperties:false`를 두지 않는다 — 생산자가
필드를 더 실어도 된다(단 `frame_ref` 안은 잠겨 있다).

**bbox 좌표계(탐지 — 상태 WS로 전달, 규격 초안 [`detections.schema.json`](../../contracts/common/detections.schema.json)):**

> 🔄 **2026-09-21 개명.** 2026-09-21 VZ 회신으로 `coord{normalized, ref_width, ref_height}` → `bbox_space{format, origin, reference{width,height}}` 로 확정됐다 — 소비자(VZ)가 이미 그 이름으로 구현해 두었고 초안이라 비용이 0이었다. **값의 뜻은 하나도 안 바뀌었다.**

```json
{
  "type": "detections",
  "frame_ref": { "source_id": "go1-001_front", "capture_timestamp": "2026-09-18T12:00:00.123+09:00", "sequence_id": 4837 },
  "alignment": "frame",
  "origin": { "tier": "edge", "kind": "precise" },
  "bbox_space": { "format": "normalized", "origin": "top-left", "reference": { "width": 464, "height": 400 } },
  "boxes": [
    { "x": 0.34, "y": 0.51, "w": 0.12, "h": 0.20, "label": "person", "confidence": 0.88 },
    { "x": 0.70, "y": 0.30, "w": 0.08, "h": 0.15, "label": "obstacle", "confidence": null }
  ]
}
```
- **`format:"normalized"`**(우리 기본값): 0~1 비율(뷰어 해상도 무관). `"absolute"` 도 규격이 받는다 —
  최종 확정은 생산자(AI) 회신 뒤다. **`origin:"top-left"`(하이픈)** — VZ가 리터럴로 고정한 값이고
  이전 예시의 `top_left`(밑줄)는 값이 달랐다. **`reference{width, height}`**: 기준 해상도 = 미디어
  헤더의 `width`/`height`.
- **[Phase 4 정정] 출처는 `boxes[].source`가 아니라 메시지 단위 `origin{tier, kind}`다.** `tier`
  (`device`=pi7 온디바이스 / `edge`=엣지 노트북 / `server`=서버 — 결정 11)·`kind`(`safety_minimal`
  / `precise`) → 가시화가 색·스타일 구분(VZ-I-07). ⚠ 공통 헤더의 `origin_kind`(실물/시뮬/재생)와는
  **다른 축**이다.
- `alignment`: §1-6-1의 fail-safe 규칙. 이 초안은 **2026-09-19 현재 어떤 검증 경로도 로드하지 않는다**
  — 생산자(AI)·소비자(VZ)에게 통지하고 회신을 받은 뒤 `payload/`로 올린다.
- 규약 소유권: BE-C-03(frame_ref 형식)·VZ-I-07(좌표계 선언). 영상 frame_ref와 탐지 frame_ref가
  동일해 두 값을 맞춰 정합.

#### 1-6-3. 세 구간 통일 — 억지가 아니라 필연

```
카메라 ─RTP/UDP─▶ 엣지 ─WS(방식 B)─▶ 서버 ─WS(방식 B, 터널 위 ws+토큰)─▶ 뷰어
        (native)  [AU 재조립 지점] [Tailscale 위]   (인증 중계, 헤더만)     (디코드)
```

홉1만 RTP, 홉2·뷰어는 WS인 게 짜깁기가 아닌 이유 둘:
1. **[Phase 4 정정] 엣지 = AU 재조립 지점(디코드 지점이 아니다).** 엣지 앞(카메라 native RTP
   패킷)/뒤(경계가 확정된 AU + frame_ref를 WS 메시지 하나에)가 갈리는 게 자연. 코덱은 바뀌지
   않는다.
2. **브라우저 = 종점 제약.** 브라우저가 RTP를 못 받으니 뷰어는 무조건 WS/WebRTC → "뷰어가 WS면
   홉2도 WS로 맞춰 서버를 중계기로"라는 대칭. **세 구간 통일은 뷰어(종점) 제약에서 거꾸로 홉2를
   정한 것.**

## 2. 예상 질문 세트

**구조 전체**
- **미디어 경로 전체를 한 문장으로?** → 카메라→엣지 RTP(native 코덱), 엣지가 AU를 재조립해
  frame_ref를 붙이고, 엣지→서버→뷰어는 WebSocket 방식 B(헤더+AU) 그대로 중계(서버는 헤더만
  읽고 GOP 인지 drop-old), 전 구간 Tailscale 터널 위·뷰어는 토큰. 홉2는 길 A·B 둘 다 지원하고
  지금은 길 A.
- **왜 미디어가 별개 평면?** → 미디어는 크고 연속적이고 유실 허용 스트림, 3종은 작고 신뢰성
  중요한 메시지. MK1이 코드 레벨 분리(JPEG×30fps=초당 수 MB→브로커 과부하). AI-C-08.

**모드·프로파일**
- **온디맨드(길 B)냐 상시 원본(길 A)이냐?** → **둘 다 지원**하며 소스별 배포 프로파일이 선택.
  국가 전제가 특정 모드를 강제하지 않음. **현재 개발 단계 = 길 A**(엣지가 붙어 계속 보내고 뷰어가
  없으면 서버가 버린다). 길 B의 절약은 서버→엣지 개폐 명령(Phase 6)에 있다.
- **전송 프로토콜을 왜 이걸로 고정?** → 고정이 아니라 **전송/미디어 어댑터(AI-C-06/08/12) 뒤의
  현재 배포 구현.** 상위 인지·가시화는 공통 인터페이스만 소비하고, 기술 교체는 어댑터 교체로.

**구간별 선택 + 대안**
- **홉1 왜 RTP?** → 카메라 native RTSP/RTP, 로컬 LAN이라 UDP 약점 무력화, 실시간이라 TCP
  재전송 독. WebRTC·SRT는 로컬엔 과함.
- **홉2 왜 WebSocket?** ← 제일 찔릴 곳. → 엣지가 AU 경계와 frame_ref를 확정한 뒤에는 "메시지
  하나 = AU 하나"가 자연 단위(RTP 재패킷화는 서버 재조립을 한 번 더 부름), frame_ref를 원자적으로
  묶어 정합 정확, 종점이 브라우저라 서버가 변환 없이 중계. **WebRTC가 영상 자체론 낫지만**
  frame_ref 정합·연결 복잡도가 대가 → 밀리초 생명이면 WebRTC 상향.
- **뷰어 왜 WebSocket?** → MJPEG는 `<img>`가 frame_ref 못 읽음, HLS는 초 단위 지연 실격,
  WebRTC는 정합·복잡도 대가. 대가는 뷰어가 디코더(WebCodecs)를 만드는 것.
- **왜 JPEG로 통일하지 않나?** → 엣지가 디코드하지 않으므로 JPEG 통일은 재인코딩을 부른다.
  코덱은 소스별 프로파일(로봇 H.264·CCTV JPEG)이고 헤더 `encoding`이 선언, 서버는 값을 보지 않는다.

**보호·연결**
- **왜 VPN? 왜 Tailscale?** → 전용선은 국가 인프라 전제(현재 배포엔 비현실→Tailscale 대체),
  역터널은 제3자가 트래픽 봄(자기모순). Tailscale=WireGuard 속도+NAT통과·키관리 자동.
- **서버→사용자 보호는?** → 현재 프로파일은 뷰어가 tailnet 구성원이라 **같은 터널 위 `ws` +
  토큰**(전송 암호화는 터널, 인증은 토큰, 도달성은 바인딩+ufw `/32`). tailnet 밖 뷰어용 **WSS는
  Phase 6.** 백엔드가 원본 URL을 직접 노출하지 않음.
- **느린 뷰어가 다른 뷰어를 막나?** → 아니다. 뷰어 소켓마다 독립 drop-old(§1-3-3). 단 링크가
  빠르고 **앱**이 느린 경우는 서버가 못 잡는다 — 뷰어가 자기 큐를 관리해야 한다.
- **관측·명령도 암호화? Kafka로 연결하면?** → Kafka로 연결하면 됨. 명령·관측이 같은 Tailscale
  터널을 타 자동 암호화(별도 작업 0). Kafka는 Tailscale을 모르고 채널·실시간성은 그대로.
- **"인터넷 안 거친다"면서 시연은 왜 거쳐?** → 제약의 본질은 "공용망에 노출"이지 "물리 회선
  경유"가 아님. 법(제7조제4항)도 경유 금지가 아니라 암호화 요구.

**대비가 약한 지점 (정직하게)**
- **WebRTC가 영상엔 더 나은데 왜 WS** → 영상↓ 대신 frame_ref 정합↑·서버 단순↑를 취한
  트레이드오프. 밀리초 생명이면 WebRTC 상향. ("WS가 다 낫다"고 하면 약해짐.)

## 3. 버킷 B — 경로 확정 후 액션 항목

**§3-1(요구사항 도출 = 무엇을 해야 하나)과 §3-2(구현 = 무엇을 하려고 이렇게 만드나)를 airtight
분리한다.**

### 3-1. 요구사항 도출 시 (무엇을 해야 하나)

- **frame_ref 단일 출처 (3자 회의 핵심 안건):** frame_ref는 **엣지에서 한 번 찍고 전파,
  AI(진나영)는 재생성하지 않는다.** "형식 합의(BE-C-03)"는 필요조건이지 충분조건이 아님 —
  "단일 출처" 규칙을 못박아야 오버레이 정합이 성립.
- **전송 모드 지원(길 A/B):** "미디어 전송은 상시-원본과 온디맨드-중계를 모두 지원, 배포
  프로파일이 선택"을 요구사항으로. 관련: BE-T-05(온디맨드 중계)·조병현 HW-R-07(온디맨드 스트림)·
  VZ-I-06(온디맨드 재생)이 이미 온디맨드 능력을 정의.
- **상황 인지 — 프리뷰 경로 여부:** 순수 온디맨드면 클릭 전엔 아무것도 안 보임. **[Phase 4]
  경로는 길 A·B 동시 지원(결정 10)이므로 프리뷰는 "저레이트 상시 소스"라는 프로파일로 표현할 수
  있다 — 필요 여부는 요구사항에서.**
- **존-진입 자동 트리거 `[확장 축]`:** 로봇이 구역 진입 시 그 구역 카메라 자동 표시는 **디지털
  트윈 연동**(DT-04 커버리지·DT-07 로봇 투입). **지금은 "인식만"** 하고 미디어 경로에 배선하지
  않음.
- **저장 모드·이벤트 캡처:** 저장이 필요한 배포는 이벤트 트리거 캡처(재난 시 주변 N초 — "상시
  링버퍼"도 "영구 저장"도 아닌 제3의 것)를 요구사항으로. 식별 가능 영상 저장 시 **at-rest
  암호화** 의무. (BE-S-09)
- **재접속 캐시 소유권 확정:** 권위 있는 캐시가 백엔드(BE-T-06)냐 게이트웨이냐 한 곳으로. 어느
  쪽이든 `video_frame`·`detections`·`command_result`는 재생 금지, ts 원본 유지.
- **(크로스 문서 sync) VZ-I-06 [확인 요망] 해소:** 엑셀 viz 시트 VZ-I-06 뷰어 출력 담당이 아직
  [확인 요망]인데, 본 문서 §1-5-3에선 이미 확정(백엔드 변환·중계 / 가시화 표시). 최종화 때 엑셀
  태그 해소.

> **비식별화는 요구사항에서 제외한다.** 영상이 실시간인 이상 얼굴 블러가 실시간으로 되어야
> 하는데 무리다. **비식별화가 불가능하기 때문에 그 대응으로 경로를 암호화(Tailscale 터널, tailnet 밖 뷰어는 WSS)한
> 것**이다.

### 3-2. 구현 시 (무엇을 하려고 이렇게 만드나)

> "요구사항을 구현할 때의 방식"이다. 요구사항("~해야 한다")이 아니라 구현 접근("~하는 방식으로
> 처리")으로 읽는다.

- **온디맨드 트리거 메커니즘 — [Phase 4 정정, 결정 4-b] 뷰어 쪽 신호는 연결 자체다.**
  `/media?source_id=…`에 붙는 것이 켜기, 끊는 것이 끄기. 서버→엣지 방향(엣지가 스트림을 열고
  닫는 개폐 명령, 명령 평면 Kafka → HW `stream_start`/`stream_stop`)은 **Phase 6** — 그 배선이
  들어와야 길 B의 절약이 생긴다. 지금은 엣지가 붙어 있는 동안 계속 보내고 뷰어가 없으면 서버가
  버린다(길 A).
- **미디어 WS 재접속·스트림 재개:** Tailscale 직접↔DERP 전환·회선 깜빡임 시 WS 끊길 수 있음 →
  자동 재연결·스트림 재개. **[Phase 4]** 재접속하면 `sequence_id`가 리셋될 수 있으므로 뷰어의
  `frameLag`류 계산은 순번 차가 아니라 세션 경계로 끊는다(VZ 통지). 서버 쪽은 같은 `source_id`의
  두 번째 엣지를 4409로 거부하고, 엣지가 끊기면 뷰어는 붙어 있는 채로 다음 엣지를 기다린다.
- **HTTP POST 폴백 전환 트리거:** WS 실패 감지 → POST로 자동 전환. 자동 감지 방식 규약. **[Phase 4]**
  구현하지 않았다(폴백 카드로만 유지 — HW C안 HTTP multipart가 후보).
- **온디맨드 콜드스타트 지연 측정:** 요청~첫 프레임까지(명령 하향→엣지 RTSP 열기→AU 재조립→WS
  상향). 1~3초일 수 있음. 정상 스트림 지연(수십~100ms)과 별개 지표. **[Phase 4]** 서버 구간의
  콜드스타트(뷰어 연결→첫 keyframe 전송)는 `be.gateway.media_coldstart` 히스토그램으로 잰다
  (버킷 0.1…30초). 실측 215ms(직접 경로, GOP 0.5초).
- **뷰어측 drop-old:** **[Phase 4 구현]** 서버가 뷰어 향 소켓마다 GOP 인지 drop-old를 적용(느린
  브라우저 하나가 중계 전체를 막지 않게 — §1-3-3). 회계 지표 `be.gateway.media_frames{outcome}`
  ·`media_gop_cut`·`media_rejected{stage}`·`media_ingress`·`clients{endpoint}`. **라벨에 `source_id`를
  넣지 않는다**(A층 — 장치 수만큼 시계열이 곱해진다). `source_id`별 회계는 연결 종료 시 로그 한 줄
  (`/media 종료 source_id=… sent= dropped= gop_cut= max_buffered= …`)로 Loki에 남긴다.
- **평면 간 QoS:** 세 평면이 같은 터널·회선 공유 → 좁은 회선에서 영상이 명령을 굶기지 않게
  미디어 대역 상한/명령 우선. (§1-4-6 물리층 미결의 대응처) **[Phase 4]** 미결 그대로 — 대역 상한은
  현장 회선 미실측이라 우리가 정하지 않는다(HW §10-5 회신).
- **360 ingest 흡수(어댑터):** Insta360 Pro2 + Farsight. 실제 출력이 RTSP native가 아닐 수
  있음 → 엣지 미디어 어댑터가 **AU 경계 + frame_ref가 붙은 방식 B 프레임**으로 정규화(코덱은
  헤더가 선언). 이질적 소스를 어댑터 뒤로 숨겨 하위를 소스-불가지로.
- **미디어=영상 전용 스코핑:** 카메라 오디오는 미디어 경로에 안 실음(음성 명령은 관제사 입력=
  명령 평면).
- **동시 스트림 분배 상한:** 엣지가 스트림 몇 개까지 여나.
- **Tailscale 운영:** 무인 현장 엣지 키 만료 처리, DERP 폴백 시 서버 옆 peer relay, 현장 LTE
  MTU 조정.

### 3-3. 검증 — 현장 리허설 체크리스트

이론(수십~100ms·15fps)은 현장 WiFi가 와일드카드라 실측으로 닫는다.
1. 현장 엣지 `tailscale ping <서버>` → **direct 확인**. `via DERP`면 서버 옆 peer relay.
2. drop-old 켠 상태 **정상 지연 측정** — 500ms 이내면 WebSocket 확정.
3. **실제 링크 fps** — ~15면 MK1 재현 성공.
4. 손실 심해 스톨 나면 WebRTC 상향 검토.

**Phase 4에서 닫은 것 / 남은 것:** 1·2는 연구실 배치(컴퓨터 임시 엣지)에서 닫았다 — 직접 경로
2ms/22ms, 정상 지연 age p50 7ms, 링크를 500kbit로 조여도 drop-old가 IDR 경계에서 재개(§1-3-3).
**남은 것:** 현장 회선·DERP 경유·실물 엣지 노트북·실물 로봇 영상(0장)·VZ 뷰어 접속·GOP 경계로
인한 프레임률 불균일(느린 링크에서 IDR 간격 0.5초 단위로 끊긴다 — HW에 IDR 간격 조절 가능
여부를 묻는다)·`MK2_MEDIA_SNDBUF` 하향 여부.
