## 0. 이 문서의 성격과 읽는 법

### 0-1. 성격

이 문서는 **백엔드·디지털 트윈 파트의 아키텍처 정본**이다. 전송·저장·관측 구조 전체를
5구간(말단↔엣지 / 엣지 내부 / 엣지↔서버 / 서버 내부 / 서버↔사용자)으로 나눠, 각 구간의
컴포넌트·데이터 흐름·결정 근거를 담는다. 각 결정에는 대안을 실제로 뒤집어 본 결과(반증)와
정직한 약점을 함께 기록한다 — "정당화"가 아니라 "왜 이 구조가 견고한가"의 근거를 남기기
위해서다. 구체 로직(디지털 트윈 내부 알고리즘, 프로세스 spawn/kill 방식)은 요구사항·구현
영역이므로 여기서는 데이터 흐름 수준까지만 다룬다.

### 0-2. 서술 원칙 — 어댑터 / 배포 프로파일

아키텍처 전반을 **"추상 요구(무엇을 지원해야 하나) + 현재 배포 프로파일(캡스톤에서 무엇을
고르나) / 어댑터 뒤의 현재 배포 구현"**으로 서술한다.

MQTT · Kafka · OpenTelemetry · K3s · Tailscale은 **"어댑터 뒤의 현재 배포 선택"**이지
프레임워크 핵심에 하드코딩된 필수가 아니다. AI 파트 요구사항(AI-C-06/08/12/15)이 이미 이
프레이밍을 명문화했고, 백엔드 시트도 같은 방식을 쓴다(BE-T-01 "전송 인터페이스는 백엔드
확정, MQTT는 현재 배포"; BE-S-01 "구체 저장 제품은 배포 환경에서 확정"; BE-Q-04 "범위
통제는 국가 인프라 축이라 캡스톤 단일 도메인에서는 전 범위로 간주").

이로써 "왜 X로 고정했냐"에 **"고정이 아니라 현재 배포, 어댑터 교체 가능"**으로 답한다.

### 0-3. 두 렌즈 — 국가 인프라 전제 / 캡스톤 현재 배포

모든 결정을 두 렌즈로 본다.

1. **국가 인프라 전제** — 말단에 수백·수천 장치, 다구역. 설계의 기준 스케일.
2. **캡스톤 현재 배포** — 하천/로봇 1~2대. 무엇이 축소 가능한가.

**핵심: 국가 인프라급으로 설계하고, 캡스톤은 이 설계의 특수 사례로 자동 포함된다.** 캡스톤
규모로 축소해서 설계하지 않는다. 태그: `[국가 인프라]`, `[확장 축]`, `[확인 필요]`.

## 1. 대전제 — 데이터 성격이 구조를 결정한다

대전제는 세 겹이며, 세 대안(시나리오별 백엔드 / 단일 채널 통일 / 영상 합치기)을 실제로
뒤집었으나 모두 성립하지 않았다.

### 1-1. 하나의 뼈대로 여러 도메인

장치 대분류(로봇/센서/카메라/액추에이터)는 다르지만 **백엔드가 보는 것은 데이터
성격**(업무/관측/영상)이므로, 채널·규약은 하나로 통일하고 시나리오 차이(하천/로봇)는 배포
프로파일로 둔다.

**반증** — 로봇과 센서가 "사실 같은 말"인지 뒤집으면 산출물은 다르다(로봇=상태 50ms+영상+
추론+임무 / 센서=수위 저주기). 그러나 그 차이는 **채널 선택이 아니라 페이로드·주기·방향의
차이**이고, 같은 채널(업무 MQTT / 관측 OTLP / 영상 미디어)이 둘 다 나른다. 즉 "통일"의 뜻은
**전송 구조·규약의 통일**이지 페이로드 통일이 아니다.

**정직한 약점** — "한 사례 종속" 위험. 하천 전용 개념(수문·차수벽·펌프·수위 임계)이 뼈대에
새면 로봇 시나리오가 안 맞는다. **방어선: 도메인 특화를 어휘집/배포 프로파일로 격리하고
뼈대는 도메인 불가지.**

**요구사항:** BE-C-06(도메인·배포 프로파일 분리) — AI-C-15의 백엔드 짝.

### 1-2. 2평면 × 2구간 + 브라우저 + 영상

채널을 기능이 아니라 **데이터 성격**이 결정한다. 업무=MQTT(말단)/Kafka(백본),
관측=OTLP/페더레이션, 브라우저=WebSocket, 영상=별개. 기능이 늘어도 채널 표는 안 늘어난다.

**반증 (돌발 채널 우려의 정면 답)** — 대안 두 개를 뒤집으면:
- **MQTT 하나로 통일** → OpenTelemetry 4부품(규격·Collector·저장소 연동·trace 상관)을
  자체 제작해야 한다. 그 비용이 채널 하나 줄이는 이득보다 크다.
- **OTel 하나로 통일** → **MQTT는 전송, OTel은 관측 "규격"이라 층이 다르다**(값을 나르는
  도구가 아님). "둘 다 데이터 보내는 거 아니냐"의 정확한 답이 이 층 구분이다.

**이 결정의 진짜 값은 "채널 수 최소화"가 아니라 "채널 선택의 결정론화"다** — 데이터 성격이
채널을 자동 결정 → 개발자가 매번 판단할 게 0 → 통제 불가한 돌발 채널이 안 생긴다.

**정직한 약점** — 채널이 여전히 2개(업무/관측)라 "완전 하나"는 아니다. OTel 4부품 재발명
비용 때문에 감수한 것이며, "선택을 결정론화해 통제 가능하게 만들었다"로 방어한다.

**요구사항:** BE-C-01(공통 스키마)·BE-S-02(OTel 파이프라인)·AI-C-14(경로 분리).

### 1-3. 영상은 별개 평면

영상은 3종 데이터와 근본이 다르다(크고 연속·유실 허용 스트림) → 별개 미디어 평면. MQTT/
Kafka/OTLP는 작고 신뢰성 중요한 메시지용, 영상은 스트리밍.

**반증** — 한 평면 합치기는 브로커 과부하로 성립 불가(MK1 `media_transport.py` 주석:
JPEG 한 장 50~150KB × 30fps = 초당 수 MB). 대안이 애초에 안 선다.

**요구사항:** BE-T-07(미디어 뷰어 중계)·BE-S-09(미디어 저장 모드)·AI-C-08/14. 상세는
[`02-media-path.md`](02-media-path.md)가 권위.

## 2. 전체 경로 한눈에 (5구간)

```
[말단]              [구역 엣지노드]              [중앙 서버(백엔드)]           [사용자(가시화)]
센서노드            Mosquitto(MQTT 브로커)       Kafka(다중 소비자 팬아웃)     관제 화면(브라우저)
로봇 온보드    ─┐   MQTT→Kafka 브릿지            ├─ AI 추론(진나영)            Grafana(개발용)
액추에이터      │   OTel Collector(Agent)         ├─ TSDB 저장(계측)
카메라          │   엣지 Prometheus(raw·요약)     ├─ MySQL(감사·레지스트리)
   │            │   K3s                           ├─ 디지털 트윈
   │  업무      │       │                          ├─ 가용성 통합 지점
   ├─MQTT──────▶│       │  업무                    ├─ 상관·감사
   │  관측      │       ├─Kafka───────────────────▶│  Collector(Gateway)→Loki·Tempo
   ├─OTLP──────▶│       │  관측                     │       │
   │  영상      │       ├─OTLP(log·trace 원본)─────▶│  WS 게이트웨이(서버 안)
   └─RTP/UDP───▶│       ├─Prometheus 페더레이션────▶│  = Kafka 소비자 + WebSocket 서버
      (JPEG)    │       │                           │       │  실시간 WS 푸시
                │       │  ══ Tailscale 터널 위 ════│       ├──────────────────▶ 관제 화면
                │       └─영상 WS(방식 B)───────────▶│  중계 ─WSS+인증─▶ 뷰어(영상+오버레이)
                                                     │  질의 프록시 ◀── 조회(지표·감사·레지스트리)
```

**핵심 성질:**
- **2평면**(업무 / 관측) + **영상 별평면**. 데이터 성격이 채널을 자동 결정한다.
- **구간마다 전송이 다르다** — 말단↔엣지 MQTT/OTLP, 엣지↔서버 Kafka/페더레이션, 브라우저 WS.
- **엣지↔서버는 단일 Tailscale 터널**을 업무·관측·영상이 공유한다(논리 채널은 분리).
- **부하가 구역 수에 비례**하도록 엣지가 1차 수용(브로커·Collector·Prometheus raw).

## 3. 구간 1 — 말단 ↔ 엣지

**구간 구조:** 말단은 무거운 서버를 안 깔고 **라이브러리만**(paho-mqtt, OTel SDK), 받아주는
브로커·수집기는 **엣지**에 있다(설치 비대칭). 이 위에서 업무=MQTT, 관측=OTLP 발신, 명령=MQTT
하달, 생사=LWT+하트비트가 흐른다.

### 3-1. 업무 데이터 = MQTT (핵심 결정)

**결정:** 말단↔엣지 업무 데이터(수위·로봇 상태 등)는 경량 브로커 pub/sub인 **MQTT 5.0 + TLS**.

**대안 배제 (반증 우선):**

| 후보 | 배제 이유 |
|---|---|
| **MQTT (선택)** | 경량 브로커 pub/sub. 다대다·잦은 소량 최적. LWT로 급사 감지, QoS로 전송 보장 |
| ZeroMQ | 브로커리스 P2P. 서로 주소를 다 알아야 함, 동적 멤버십 부담 |
| Kafka | 무겁고(JVM) 과함. 다중 소비자 버퍼는 백본 몫 |
| RabbitMQ | 소비하면 사라지고 무거움. 다대다엔 MQTT가 가벼움 |
| DDS | 로봇 **몸체 내부** 제어용(ROS2 기반). 말단↔엣지 텔레메트리가 아님 = 범위 밖 |

**정직한 약점:**
- ZeroMQ가 순수 지연은 더 낮다(브로커 홉 없음). 우리는 그 홉을 감수하고 decoupling·LWT·동적
  멤버십을 얻는다 — 로컬 LAN이라 지연이 병목이 아니다.
- 단일 브로커(Mosquitto)가 병목·SPOF가 될 수 있다 → **구역별로 엣지 브로커를
  분산**(부하가 구역 수 비례), 극단은 EMQX(1억 연결급).

**두 렌즈:** 국가는 다대다·수백 장치라 견고. **캡스톤은 규모가 줄어도 무거워지는 요소가
없다** — MQTT는 저사양·소량용이라 규모가 줄면 부담도 줄 뿐(paho-mqtt는 수 MB, JVM 오버헤드
없음). 무거움은 브릿지(JVM)부터 생긴다. 캡스톤에서 오히려 유리.

**표현 주의:** **"저사양"은 캡스톤 부가 근거로 강등**한다 — 핵심 근거는 다대다·잦은 소량·LWT·
QoS·pub/sub이고 장치 사양과 무관하게 성립한다(국가 인프라는 저사양이 아닐 수 있음).

**요구사항:** BE-T-01(말단↔엣지 MQTT 확정) — 조병현 HW-C-01(후보 MQTT)을 확정.

### 3-2. 관측 = OTLP 발신 + 설치 비대칭

같은 노드가 수위(업무·MQTT)와 자기 CPU·메모리·전송 성공률(관측·OTLP)을 **둘 다** 낸다 —
중복이 아니라 성격 분리. 말단은 OTel **SDK만**, 수집기(Collector)는 엣지에. 무거운 서버를 각
말단에 안 두고 엣지에 모으는 대칭 구조.

**요구사항:** BE-S-02(OTel Agent+Gateway)·조병현 HW-C-05(OTel 계측 5종).

### 3-3. 명령 하달 = 엣지→말단 MQTT

명령의 마지막 홉(엣지→말단)은 MQTT로 확정: (1) 이미 있는 MQTT 채널 재사용(새 채널 안 만듦),
(2) pub/sub이라 특정 토픽 발행 시 해당 장치만 수신, (3) QoS로 유실 방지, (4) ACK 왕복 자연.
서버→엣지 구간은 §5-4, 명령 상관·감사는 §6-5.

**요구사항:** BE-A-01(액션 어휘집 번역)·조병현 HW-C-06(제어 ACK).

### 3-4. 생사 감지 = LWT + 하트비트

감지 수단 두 겹: (a) MQTT LWT(급사 시 브로커가 대신 '죽음' 발행, 즉시), (b) 하트비트
타임아웃. 효율: 임무 중 로봇은 상태 데이터가 하트비트를 겸해 별도 하트비트 생략(중복 제거).
**두 평면 통합·최종 판정은 백엔드 단일 지점(§6-4).**

**요구사항:** BE-T-04(가용성 판정)·조병현 HW-S-05(하트비트)·HW-S-07(오프라인 감지).

### 3-5. 적응형 주기 전환 — 스코프 경계

하달되는 것 중 "리포트 주기 전환 명령"(평시 저주기 ↔ 재난 고주기)이 있다. **데이터
흐름**(무엇이 흐르나) 관점은 아키텍처 범위, **방식**(프로세스 spawn/kill)은 요구사항 영역.

**요구사항:** 조병현 HW-S-03/S-04(이벤트 고주기·주기 전환)·HW-C-03(K3s).

## 4. 구간 2 — 엣지 박스 내부 구성요소

요소 다섯: Mosquitto / MQTT→Kafka 브릿지 / Collector(Agent) / 엣지 Prometheus / K3s.

### 4-1. Mosquitto (MQTT 브로커)

구역 안 모든 말단이 값·명령을 던지는 우체국. 브로커가 엣지에 있어야 말단이 라이브러리만 두고
발행자·구독자가 decouple된다. retained(최신값 1개)는 **브로커 직접 구독자용**으로 유지 —
브라우저 재접속 스냅샷은 retained가 아니라 백엔드 캐시(§7-4).

### 4-2. MQTT→Kafka 브릿지 (실체 정밀화)

**결정:** 말단은 MQTT, 백본은 Kafka로 구간마다 전송이 다르므로 둘을 잇는 중계를 엣지에 둔다.
올림=MQTT→Kafka, 내림(명령)=Kafka→MQTT(양방향).

**반증** — 브릿지의 존재는 **"구간별 전송이 다르다"의 논리적 귀결**이다. 말단부터 Kafka로
통일하면 불필요하나 저사양 말단에 Kafka는 무겁다(§3-1). 백본까지 MQTT로 통일하면 불필요하나
MQTT는 저장 안 해 다중 소비자 버퍼가 안 된다(§5-1). 구간이 다른 게 맞다면 브릿지는 자동 정당.

**브릿지 연결의 실체 (통념과 다름 — 검색 확정):**
브릿지는 "kafka connect mqtt 커넥터"라는 단일 물건이 아니라 두 겹이다.
- **Kafka Connect(워커)** = 커넥터를 실행하는 런타임/프레임워크(JVM 프로세스). "그릇".
- **MQTT Source 커넥터** = 그 그릇에 꽂는 플러그인. "MQTT 토픽 구독 → Kafka 토픽 쓰기"
  로직만 담긴 JAR. (명령 하달 Kafka→MQTT는 Sink 방향.)

**연결이 어디서 맺어지나:** Kafka Connect 워커가 **가운데** 서서 양쪽으로 각각 클라이언트
연결을 건다 — 한쪽은 워커 안 MQTT Source 커넥터가 MQTT 클라이언트로 엣지 Mosquitto에
접속·구독, 다른쪽은 워커가 Kafka 프로듀서로 서버 Kafka에 접속. 즉 **"서버 Kafka가 엣지
MQTT를 직접 구독"하는 게 아니다.** Kafka는 스스로 나가 구독하는 물건이 아니라 누가 프로듀서로
써넣어 줘야 하는 로그다. 그 "써넣는 자"가 브릿지. 통로에 있는 것은 특별 프로토콜이 아니라
**그냥 두 개의 TCP 연결**(MQTT 클라이언트 하나 + Kafka 프로듀서 하나).

**"엣지에 Kafka 없음"의 정확한 뜻:** 엣지에 까는 것은 **Kafka Connect 워커(런타임)까지**다.
Kafka Connect의 유일한 하드 전제는 "접속할 Kafka 브로커"인데, 그 브로커가 **로컬일 필요는
없다**(서버 Kafka에 원격 접속). 정리: **"엣지에 Kafka 브로커/저장소는 없다"는 맞고, "엣지에
Kafka Connect 워커(JVM 런타임)는 있다"가 정확하다.**

**위치가 왜 엣지인가** — 브릿지를 엣지에 두면 MQTT 연결은 로컬, Kafka 프로듀서 연결이
원격(엣지→서버 **아웃바운드**) → 사설IP·방향 문제 자연 해소. 서버에 두면 서버가 사설망 뒤 각
구역 브로커로 역방향 접속해야 하고 구역 수만큼 연결 관리.

**정직한 약점(자원):** Kafka Connect 자체는 메모리를 많이 안 쓰나 **JVM은 JVM**이다(최소 수백
MB 힙). paho-mqtt(수 MB)와 체급이 다르다. 그래서 "Kafka가 무겁다"의 정확한 위치는 **"말단엔
무겁고 엣지엔 감당"**이다. 변환 지연은 µs~ms급, 실시간 병목은 Kafka produce(§5-1)이지 브릿지가
아니다.

**구현체 여지 (이월):** Kafka Connect + MQTT Source(표준·유연·JVM 무거움) vs EMQX/Mosquitto
네이티브 Kafka 브릿지(가벼움·브로커 종속, JVM 워커 안 띄움). **캡스톤 엣지가 저사양이면 후자
유리.** 아키텍처 결정(브릿지 둔다)은 유지, 구현체 선택은 구현으로.

**요구사항:** BE-T-02(엣지↔백엔드 브릿지).

### 4-3. Collector(Agent) + 엣지 Prometheus (이원 저장 — 중복 아님)

**"엣지에 Collector와 Prometheus를 둘 다 두는 게 중복 아닌가"의 답:**

**역할이 다르다:**
- Collector 하나로 저장까지? → Collector는 **수집·가공·배송**(receiver→processor→exporter)
  까지지 **저장·집계·쿼리·경보**를 안 한다. metric을 시계열로 저장하고 요약을 만드는 건
  Prometheus 표준 기능. Collector로 저장하려면 자체 제작 = 바퀴 재발명.
- Prometheus 하나로 수집까지? → Prometheus는 scrape(pull) 기반 시계열 전용이라 log·trace를
  못 담는다(log=Loki, trace=Tempo). 세 종류를 규격대로 받아 가르는 건 Collector 몫.

즉 **Collector = 관측 3종의 수집·라우팅 창구, Prometheus = 그중 metric의 저장·요약·경보**.
층이 달라 둘 다 필요하다.

**Prometheus pull의 실체:** scrape는 **"HTTP로 /metrics 엔드포인트를 주기적으로 GET"** 하는
것뿐이다. 그 엔드포인트가 누구냐에 따라:
- **방식 A — Collector를 긁는다:** Collector에 Prometheus exporter를 붙이면 Collector가
  /metrics를 노출. 엣지 Prometheus가 그 Collector 엔드포인트를 scrape. 흐름 = 말단
  →(OTLP push)→ Collector →(Prometheus scrape). **Prometheus는 Collector까지만 가고 말단까지
  직접 안 간다.**
- **방식 B — 노드를 직접 긁는다:** 각 말단이 자체 /metrics 노출(node_exporter) → 엣지
  Prometheus가 각 노드를 직접 scrape. Collector 안 거침.

**방식 A에서 노드별 생사(up) 잡기 (국가 인프라 적합):** 국가 규모는 수백 노드를 Prometheus가
직접 긁는 게 부담이라 방식 A가 맞다. 방식 A에서도 노드 생사를 잃지 않는다:
- Prometheus 내장 `up`은 **직접 scrape하는 대상**(방식 A면 Collector)에 대해서만 자동 생성 →
  Collector 생사만 반영(노드 생사 아님).
- **노드 생사는 "신호 끊김 감지"로:** PromQL `absent_over_time(metric{node="X"}[5m])`로 특정
  노드 시계열이 최근 없으면 죽음(표준). 개념이 "up=0 받기"에서 **"신호 끊김 감지"**로 바뀌고
  결과는 같다. **그래서 생사 주력이 MQTT LWT인 게 더 타당해진다** — 관측 평면 up은 방식에
  따라 노드 생사를 못 볼 수도 있는 보조 신호.

**엣지 Prometheus 주 목적** — 구역 관측 지표 **저장·요약(federate)**. 생사 up은 scrape
부산물이지 Prometheus를 두는 이유가 아니다. **엣지 Prometheus가 raw를 짊어짐** = 부하를 구역
수에 비례하게 하는 설계 의도(국가 확장의 뿌리).

**요구사항:** BE-S-02(파이프라인)·BE-S-03(관측 저장 계층화).

### 4-4. K3s — 스코프 경계

엣지에 K3s(라즈베리파이용 경량 쿠버네티스) 존재. 아키텍처 관점은 **"엣지에 K3s 존재한다"**는
배치 사실까지 — 백엔드는 실행 요청 접점(BE-X-06)만, 실제 배포는 K3s. 생명주기 "방식"은
요구사항 이월.

**요구사항:** BE-X-06(AI 프로세스 실행 관리 접점)·조병현 HW-C-03(K3s 배포).

## 5. 구간 3 — 엣지 ↔ 서버

가장 무거운 구간. 여섯 하위결정 + Tailscale 터널.

### 5-1. 업무 데이터 = Kafka (핵심 결정 — 두 렌즈 정면)

**결정:** 엣지↔서버 업무 데이터는 분산 커밋 로그 **Kafka**로 전송한다. 브릿지가 MQTT→Kafka로
넘긴다.

**국가 인프라 렌즈 — 반증:**
- 서버 소비자가 하나뿐이면 → 순수 전송(MQTT)으로 충분. 그러나 서버엔 저장·트윈·AI 등 **다중
  소비자**가 같은 데이터를 각자 다른 속도로 읽어야 한다. MQTT는 전달하면 사라져 안 된다.
- 소량이고 재난 폭주 없으면 → 경량 스트리밍(NATS)도 됨. 그러나 국가 규모는 구역별 대량 유입
  + 재난 폭주 → 처리량·유실 완충 필요.
- 최저 지연이 생명이면 → NATS(sub-ms). 그러나 골든타임 초~분이라 Kafka 10~50ms로 충분.

**정직한 약점(검색 확인):** 프로듀서를 90→900개로 늘리면 중앙값 지연 60%↑, p99 3배, 9노드
브로커 CPU 100% 도달. 즉 **국가 규모에서 Kafka도 무한 공짜가 아니라** 프로듀서(구역 브릿지)
폭증 시 튜닝(배칭·파티션·클러스터 증설) 필요. "무한 확장"이 아니라 **"튜닝·증설로 확장 가능"**이
정직한 표현.

**캡스톤 렌즈 (핵심):** 업계 반론 — "80% 유스케이스에서 Kafka는 과하다. 킬로바이트를 옮기려고
3AZ·RF=3·6~7노드를 배포한다." 딱 캡스톤 상황이다. 그러나:
- **Kafka를 고르는 근거는 데이터 양이 아니라 다중 소비자 구조**다(AI·DB·트윈이 서버에서 각자
  오프셋으로 독립 읽기). 소량 데이터라도 다중 소비자가 있으면 유효 — 반론을 비껴간다.
- 반론의 진짜 교훈은 **배포 모델**이다. 과함을 피하는 길은 "Kafka를 버린다"가 아니라 **"Kafka를
  작게 배포할 수 있다"**(단일 브로커·복제 없이·KRaft 모드급). **무거움의 원인은 Kafka 설계가
  아니라 배포 규모이며, 배포는 상황에 맞게 줄일 수 있다.**

**대안 NATS JetStream — 비교 (안 바꿔도 방어 자산):**
- **엣지 내부 측면(결정적):** NATS로 가면 오픈소스 NATS가 MQTT 3.1.1을 서버에서 직접 종단하고
  장치 세션을 같은 JetStream 스트림에 영속화 → **Mosquitto + 브릿지 두 물건이 NATS 하나로
  합쳐져 브릿지 자체가 사라진다.** §4에서 씨름한 것(브릿지 실체·JVM 워커 오버헤드)이 증발.
- **자원:** NATS 단일 바이너리 ~17MB, 의존성 0 vs Kafka JVM 브로커.
- **NATS 약점:** 컨슈머 그룹 정교함(오프셋 관리·재처리), 대규모 트랙레코드·Schema Registry
  생태계는 Kafka가 앞섬.
- **지연 실측:** 구조적 종단 지연 차이 ≈ 한 자릿수 ms(NATS) vs 수십 ms(Kafka), 폭 대략
  10~40ms. **캡스톤 기준(수십 ms 무의미)에 들어옴** → 지연을 이유로 NATS 전환할 필요 없음.
  NATS의 값은 지연이 아니라 엣지 단순화.

**결정: Kafka 확정 (캡스톤 포함).** 국가 인프라 렌즈에서 정당하고, 캡스톤에서도 다중
소비자(AI·DB·트윈)가 서버에 있어 유효하다. NATS는 "검토했고 국가 인프라 전제·다중 소비자로
Kafka 유지"의 근거 자산으로 남긴다.

**요구사항:** BE-T-02(Kafka 브릿지)·BE-S-04(재난 아카이브 기반).

### 5-2. 관측 metric = 페더레이션 요약

엣지 Prometheus가 raw 로컬 보관, 백엔드 Prometheus가 요약만 pull(federate). 부하가 장치 수가
아니라 **구역 수 비례**. 국가는 견고(수백만 노드 raw를 중앙에 몰면 폭증하니 요약만).
페더레이션이 유일한 방법은 아니나 Prometheus federate가 저장·쿼리·경보를 표준으로 한 번에 줘
바퀴 재발명 회피. **캡스톤은 구역 1개면 이점 미발현이나 2계층 구조는 유지(확장 자리 확보).**

**요구사항:** BE-S-03(관측 저장 계층화).

### 5-3. log·trace = 원본 전달

log·trace는 요약하면 의미 깨짐(에러 로그를 평균 못 냄)이라 원본 그대로 엣지 Collector→서버
Collector. 서버 Collector가 log→Loki, trace→Tempo 분배. **양이 많은지 적은지 예측 어려워 요약
안 하는 게 안전**(metric은 대량 시계열이라 요약 가치 확실, log·trace는 단정 못 하고 손실 큼).

**요구사항:** BE-S-02(관측 파이프라인).

### 5-4. 명령 서버→엣지 = Kafka (A안)

명령의 서버→엣지 구간은 Kafka(업무 간선 재사용), 엣지→말단은 브릿지가 Kafka→MQTT 전환.
근거: 채널 통일(서버가 전송 하나만 관리) + 파티션 내 순서 보장. **사설IP는 근거 아님**(B안
MQTT 직송도 엣지가 서버로 먼저 연결하면 우회됨). **압도적 우위 아님** — 일관성 우선 선택.

**명령 실시간성 (검색 확인) — 중대하지 않음:** Kafka→MQTT 변환 총 지연 = 서버 Kafka
produce~consume(십수 ms) + 브릿지 변환(µs~ms) + 로컬 MQTT publish(ms 이하) ≈ **수십 ms
이내**(최악 p99에서도 100ms 아래).
- **관제성 명령**(펌프 켜라, 로봇 구역 가라, 주기 전환): 골든타임 초~분이라 수십 ms 무시 가능.
- **로봇 정밀 원격 조작(WASD 텔레오퍼레이션):** 이건 이 경로가 아니라 **WebRTC 에스컬레이션
  경로**로 분리(제어+저지연 영상 별도). 원격 조종은 170ms 이하 쾌적, 300ms까지 적응 가능 —
  우리 수십 ms는 임계에 한참 못 미침. 영상 동반 정밀 조종은 영상 왕복(수백 ms~1초)이 병목이라
  WebRTC.

**요구사항:** BE-A-01/A-02/A-04(명령 번역·발행)·BE-X-03(4단계 승격).

### 5-5. 장치 생사 = 별개 경로

생사 신호는 요약과 별개. 업무 평면(엣지가 MQTT LWT·하트비트로 판정 → Kafka로 백엔드) + 관측
평면(Prometheus up 또는 **방식 A면 metric 침묵 감지 absent** — §4-3). 두 평면 감지, 통합·판정은
백엔드 단일 지점(§6-4).

**요구사항:** BE-T-04(가용성)·조병현 HW-S-07.

### 5-6. 전송 계층 = Tailscale 터널

**엣지↔서버는 물리적으로 인터넷을 거치므로, 미디어(WS)+명령/업무(Kafka)+관측(OTLP)이 모두
하나의 Tailscale 터널** 위를 탄다.

**강제냐 겸사겸사냐 — 강제다(단 "Tailscale이라서"가 아니라 "사설망이라서"):** 엣지(현장)와
서버는 서로 다른 사설망에 있고 공용 인터넷을 사이에 둔다. 엣지는 보통 NAT/방화벽 뒤(공인 IP
없음). 사설 IP는 인터넷에서 라우팅 불가 — 이게 "사설 IP" 문제의 실체. **연결 가능성 자체를
만들려면 터널/VPN이 필요**하고, 그게 Tailscale(WireGuard). 즉 **"터널을 타야 한다"는
강제(사설망 때문), "그 터널이 Tailscale이다"는 교체 가능한 현재 배포 선택.**

**QoS 문제의 정확한 정체 — "경로가 다른데 왜 서로 미나":** '경로'가 두 층에서 다른 뜻이라
혼선이 생긴다.
- **층 1 — 논리적 경로(프로토콜/채널):** 영상=WS, 업무=Kafka, 관측=OTLP. 이 층에서는 나뉜다
  — 영상이 Kafka 토픽에 안 섞이고 명령이 WS로 안 간다. **채널 분리는 이 논리층 얘기**이고,
  버퍼·큐 오염은 이 층에서 해결됐다.
- **층 2 — 물리적 경로(회선/대역폭):** 세 논리 채널이 최종적으로 나가는 물리 출구는 하나 —
  현장 엣지의 **인터넷 회선(업링크)**. WS든 Kafka든 OTLP든 전부 그 하나의 회선·하나의
  Tailscale 터널을 통과한다. 여기가 공유 지점.

**터널이 "작아지는" 게 아니다**(Tailscale은 회선이 주는 만큼 나름). 문제는 터널 크기가 아니라
**물리 회선(업링크)의 총 대역폭이 유한**하다는 것. 현장 업링크가 20Mbps인데 영상(JPEG 30fps
초당 수 MB)이 회선을 거의 채우면, 같은 회선을 나가려던 명령·관측 패킷이 큐에서 대기(지연 급증
= bufferbloat)하거나 드롭. **논리 채널은 분리돼도 물리 회선 진입 경쟁에서 영상 부피가 명령
적시성을 침해**한다 — 버퍼 오염이 아니라 회선 대역 경쟁.

**직접 연결(90%+) vs DERP 폴백:** Tailscale은 두 기기를 직접(P2P) 잇는 걸 우선하고 직접 NAT
통과 성공률이 90% 이상. 직접이면 원래 물리 경로로 가고 암호화만 얹힘(우회 없음). 직접
실패(symmetric NAT·UDP 차단) 시 DERP 릴레이(TCP)로 폴백 — WebSocket(TCP)이 DERP(TCP)를
타면 TCP-over-TCP로 이중 스톨이라 이 경우만 느릴 수 있음. 확인: `tailscale ping <서버>` →
`via <ip>` (직접) vs `via DERP` (릴레이).

**해결 상태:** 논리층(채널 분리)은 해결. **물리층(회선 대역 경쟁 = QoS)은 미디어 경로 문서
버킷 B로 이월**(패킷 우선순위: 명령·관측을 영상보다 먼저 / 영상 비트레이트 적응).

- **국가:** 전용망(전용선/사설 WAN) 전제. Tailscale은 그 자리의 현재 배포 대체.
- **캡스톤:** 전용선 없으니 Tailscale VPN으로 공용망 노출 없이 연결.

**요구사항:** BE-T-08(엣지↔서버 보안 오버레이) — AI-C-17의 백엔드 짝. 상세는
[`02-media-path.md`](02-media-path.md) §1-4.

## 6. 구간 4 — 서버 박스 내부

앞 구간의 이월(다중 소비자 실현·생사 통합·재생 재료 위치)이 여기서 닫힌다.

### 6-1. Kafka 다중 소비자 팬아웃

브릿지가 올린 업무 데이터를 서버의 여러 소비자(AI 추론 / DB 저장 / 디지털 트윈)가 **각자
독립 오프셋으로** 읽는다.

**반증:** 셋을 하나로 합치면 한 소비자의 지연/실패가 나머지를 오염(AI 추론이 느릴 때 DB 저장
까지 밀림). 독립 소비자라야 격리. SLA·실패 양상이 다르다(추론 지연 / 저장 내구성 / 트윈
최신성). **팬아웃은 Kafka 선택의 값의 실현.**

**두 렌즈:** 국가 견고. **캡스톤도 로봇 1~2대라도 서버엔 AI(진나영)·DB·트윈(이대규) 세 소비자가
그대로 존재 → 팬아웃 값이 캡스톤에서도 실현.** "데이터 적어도 다중 소비자면 Kafka 유효"가
여기서 눈에 보인다.

### 6-2. 저장소 분리 — 데이터 성격 분류 (2축)

**데이터를 만드는 건 하드웨어(조병현)·AI(진나영)·가시화(김현우)이고 백엔드는 저장·중계·번역만**
하므로, "무슨 데이터가 있나"는 3개 파트 생산물을 본다.

**최종 저장 분류:**

| 저장 대상 | 저장소 | 성격 |
|---|---|---|
| 센서 계측값·로봇 상태 추이·액추에이터 상태 추이 | **TSDB** (InfluxDB/TimescaleDB 후보, 제품 미확정) | 시간축 위 수치 |
| 명령 감사(누가·언제·왜)·계획 승인 | **MySQL** (감사 테이블) | 이벤트 원장, 정합성·트랜잭션·위조 불가 |
| 장치·구역·식별자 등록 | **MySQL** (레지스트리 테이블) | 준정적 관계 매핑(같은 관계형, 다른 테이블) |
| metric / log / trace | Prometheus / Loki / Tempo | 관측 평면(별개) |

| 저장 안 함 (전송 층 = WS 푸시) | 시작점 → 도착점 |
|---|---|
| 트윈 상태(위치·검출) | 백엔드 트윈(Kafka에서 읽어 계산) → 화면 |
| 명령 진행(ACK→완료) | 백엔드 승격 → 화면 (최종결과만 감사에) |
| 장치 가용성(online/offline) | 백엔드 생사 통합 지점(§6-4) → 화면 |

- **미정:** 미디어(영상) — 저장 여부 자체가 미결.
- **제외:** RBAC — 근본 뿌리 약함(국가 인프라 확장, 캡스톤 불필요), 목록에서 삭제.

**DB 형태별 성격 (판단 기준):**
- **시계열(TSDB):** (시각, 값) 점이 시간축으로. "수위 09:00=1.23". 추이 조회·append.
- **관계형(MySQL):** 개체 간 관계·소속·참조. "device_001은 zone_A 소속". 조인·참조 무결성·
  트랜잭션. 스키마 안정적.
- **문서형(MongoDB):** 스키마 유동적 문서. **이 프레임워크에서 확정 채택 없음.**

**왜 감사가 MySQL:** 관계형이라 command_id·actor·시각·결과·origin.path를 구조화 레코드로
정합성 있게 남기고(BE-S-05: 요약·필터 없이 전량 직행), actor·시각을 백엔드가 주입해 위조 불가,
감사 조회 API가 "누가 언제 이 게이트 열었나"를 SQL로 질의. **명령 이력(감사)은 기술
추적(trace, Tempo)과 다른 목적**이다 — 근본이 "업무상 명령 이력·책임 추적과 기술적 처리 경로·
지연 추적은 서로 다른 목적"으로 명시하므로 "명령 이력이 Tempo에 흡수된다"는 틀리다.

**"상태·이력" 세 번째 분류:** BE-S-01이 "센서 계측·로봇 상태·명령 이력"을 묶었으나 뜯으면 —
로봇 상태는 시계열(TSDB), 명령 이력은 감사(MySQL)·trace(Tempo)로 **각각 다른 작업으로 분산**
된다(command_id로 상관될 뿐 "흡수"는 아님). 남는 "상태 변화 이력"이 무엇인지 정의 불명확 →
**독립 저장 축으로 확정 못 함, 요구사항 구체화 대기.**

**로봇 상태 용도 이원:** 실시간 값(50ms)=WS 게이트웨이 구독 푸시(저장 조회 아님), 저장(이력·
트윈 시의성)=TSDB. **"실시간은 WS"의 뜻:** 데이터를 DB에 넣고 화면이 주기 폴링(pull)하는 게
아니라, 도착 즉시 백엔드가 화면으로 밀어줌(push). 50ms를 폴링하면 초당 20회 DB를 두드려 부담.

**요구사항:** BE-S-01(시계열 저장)·BE-S-05(감사 MySQL 직행)·BE-Q-03(레지스트리)·BE-C-02(식별자).

### 6-3. 서버 Collector(Gateway) → Loki·Tempo

엣지 Collector가 원본 전달한 log·trace를 서버 Collector(Gateway 역할)가 받아 log→Loki,
trace→Tempo 분배. metric은 페더레이션으로 서버 Prometheus에 별도. Collector 거치니 저장소
바뀌어도 노드·엣지 코드 불변.

**요구사항:** BE-S-02.

### 6-4. 장치 가용성 통합 단일 지점 (업무평면 우선)

두 평면(업무 MQTT LWT / 관측 up·absent) 이중 감지 → 서버에서 **하나의 권위 있는 상태로 통합**,
충돌 시 **업무 평면 우선**.

**반증:** MQTT만 믿으면 "살아있는데 metric만 안 오는 부분 장애"를 놓침(관측이 잡음). 통합 안
하면 한 평면 "살아있음"/다른 평면 "죽음"의 분열된 진실(split-brain) → 화면·경보·명령이 뭘
믿을지 모름. 단일 통합에서 하나의 진실.

**업무 평면 우선 규칙:** MQTT 세션 online이면 **가용**(지표 결손이어도), MQTT 세션 offline이면
지표(up=1) 존재해도 **불가용**. 명령을 주고받을 수 있는지가 1차 기준이기 때문.

**실시간성·자원:**
- **자원:** 매우 가벼움. 장치별 최신 생사 상태 테이블을 메모리에 두고 두 신호 대조. 장치 수만큼
  작은 레코드(수백~수천이라도 KB~MB). CPU 거의 0.
- **실시간성:** 업무 평면(MQTT LWT 즉시~수십 ms) — 관측 평면(Prometheus scrape 15초~1분).
  **통합 지점 실시간성은 업무 평면이 결정 → 급사 판정 수십 ms급.** 관측 평면은 부분 장애 잡는
  보조라 초~분 지연 무방.

**상태 3층:** 단일 값으로 뭉치지 않고 자기보고(device_status)·서버판정(availability)·
오케스트레이터(deployment)로 분리해 가시화가 파생값을 만들게 한다.

**요구사항:** BE-T-04(가용성 판정)·BE-X-07(제어 잠금)·조병현 HW-S-07·가시화 VZ-U-01.

### 6-5. 상관·감사

- **상관(correlation):** 서버가 raw로 DB에 붓지 않고 **ID로 연결** — command_id(명령↔ACK↔결과,
  QoS 1+멱등), trace_id, entity_id/node_id/zone_id. "명령 내렸는데 어떻게 됐나" 추적 가능.
- **감사(audit):** 무슨 명령이·언제·누구에 의해·어떤 결과로 → 영속 저장(**업무 흐름의 저장
  결정이지 별도 채널 아님**). actor는 토큰에서, 시각은 서버 시각으로 백엔드가 주입(위조 불가).
- **명령 결과 4단계 승격:** ACK → 수행 중 → 물리 상태 변화 → 완료/실패. 되돌리기 어려운
  명령(모터·수문·펌프)은 ACK가 아니라 실제 수행 결과로 확정 표시.

**요구사항:** BE-X-01(command_id 발급)·BE-X-02(감사 작성)·BE-X-03(4단계 승격)·BE-X-04(계획
승인)·BE-X-05(AI 실패 중계)·BE-Q-02(감사 조회).

### 6-6. 재난 아카이브

**Kafka 프레이밍 주의 — 자기모순 함정:** 재난 아카이브는 **Kafka의 여러 소비자 중 하나(저장
소비자)**이지 Kafka가 존재하는 이유가 아니다.
- Kafka를 고른 이유 = 다중 소비자 독립 읽기(§5-1). 불변.
- **"재생/재학습을 위해 Kafka를 쓴다"고 하면 자기모순** — Kafka 보존(retention)은 완충 버퍼이지
  아카이브가 아니고, 아카이브는 별도 영속 저장소.
- **재생·학습 재료 위치 = 데이터 평면(아카이브), 관측 평면 아님**(관측 metric은 요약만).

**재난 데이터의 정확한 위치:** 재난 구간 업무 데이터 = 센서 계측값 그 자체 = **TSDB에 저장되는
데이터**. 별도 "저장소 종류"가 아니다. TSDB 보존 기간 안이면 그대로 학습이 긁어가고, 오래
보관해야 하면 재난 구간만 장기 보존 위치로 옮긴다. 즉 **"TSDB 계측 데이터의 보존 기간·위치"
문제**이지 독립 저장소가 아니다. 아카이브→진나영 Continual Learning(AI-L-01) 핸드오프 지점까지만.

**요구사항:** BE-S-04(재난 구간 장기 보존)·조병현 HW-S-03(재난 고주기).

## 7. 구간 5 — 서버 ↔ 사용자(가시화)

**사람(관제사)이 보는 화면으로 무엇이 어떻게 나가고, 사람 조작이 어떻게 들어오나.** 브라우저는
MQTT·Kafka 브로커에 직접 못 붙으므로(BE-T-03), 백엔드가 **WS 게이트웨이**를 두고 중계.

### 7-1. 실시간 채널 = WS 게이트웨이 (구성 실체)

**결정:** 브라우저는 내부 전송에 직접 못 붙으므로 백엔드가 WebSocket 게이트웨이를 두고 실시간
값(로봇 상태·트윈·명령 결과·계획 진행·가용성)을 구독 푸시.

**반증:** 브라우저가 브로커에 직접 붙으면? (1) 브라우저는 MQTT/Kafka 프로토콜을 네이티브로 못
말함(WebSocket/HTTP만), (2) 사설망 뒤 브로커에 외부 브라우저 직접 접근 불가, (3) 인증·권한·
rate limit을 브로커에 직접 노출. 불성립 → 게이트웨이 필요. 실시간을 저장소 폴링으로? 50ms를
폴링하면 초당 20회 DB 두드리고 주기 늦추면 트윈 끊김. 불성립 → WS 푸시. 즉 **"브라우저 프로토콜
한계 + 사설망 + 실시간 푸시 필요"의 필연적 귀결.**

**왜 WebSocket:** 서버가 브라우저로 미는(push) 양방향 지속 연결 필요. HTTP 폴링은 지연·부하
큼, SSE는 올림(명령) 안 됨, gRPC-web은 양방향 스트리밍 제약. WebSocket이 양방향 지속 연결이라
내림(상태 푸시)·올림(명령)을 한 채널로.

**게이트웨이는 어디에 연결되나:**
```
서버 Kafka  ↔  서버 WS 게이트웨이(서버 안)  ↔  사용자(화면)
```
게이트웨이는 **서버 안** 컴포넌트다. 브라우저가 Kafka에 직접 붙는 게 아니다.
- **내림(서버→화면):** 서버 Kafka에 업무 데이터가 흐름 → **게이트웨이가 Kafka 소비자로 붙어**
  읽음 → WebSocket으로 브라우저에 푸시.
- **올림(화면→서버):** 브라우저가 WebSocket으로 명령을 게이트웨이에 → 게이트웨이가 백엔드
  로직 거쳐 Kafka로.

**게이트웨이는 §4-2의 MQTT↔Kafka 브릿지(Kafka Connect 워커, 단순 프로토콜 변환)와 성격이
다르다** — **Kafka 소비자이면서 동시에 WebSocket 서버인 백엔드 애플리케이션**으로, 구독 관리·
인증·권한·상태 캐시(§7-4)·명령 번역 연결(§7-2)까지 하는 백엔드 로직 덩어리다. 한쪽 발은
Kafka(소비자), 다른 발은 WebSocket(브라우저 대면). 브라우저는 오직 이 게이트웨이하고만
WebSocket으로 대화하고 Kafka 존재를 모른다.

**실시간 값의 출처는 셋:** 업무 데이터(로봇 상태·트윈)는 Kafka에서, 장치 가용성은 생사 통합
지점(§6-4)에서, 명령 결과(진행)는 백엔드 승격에서 모아 WebSocket 한 채널로 푸시.

**정직한 약점:** 모든 실시간 트래픽의 단일 통로라 SPOF·부하 집중 → 게이트웨이 수평 확장, 구독
범위 한정(VZ-I-11이 "관심 영역만 구독" 자리 확보). 캡스톤은 게이트웨이 하나로 충분.

**요구사항:** BE-T-03(WS 게이트웨이)·가시화 VZ-I-01/VZ-I-11.

### 7-2. 명령 발행 (올림)

사용자 조작은 추상 action+params로 WS 게이트웨이를 통해 백엔드에 발행. 브라우저는 장치 명령
형식을 모르고 추상 동작만 보내며 백엔드가 어휘집으로 번역(BE-A-01). command_id는 백엔드 발급.
이후 경로(백엔드→엣지 Kafka→말단 MQTT)는 §3·§5 기검증.

**요구사항:** BE-A-01(액션 어휘집)·BE-X-01(command_id)·가시화 VZ-O-01.

### 7-3. 조회 프록시

실시간 아닌 조회(과거 지표·감사 이력·레지스트리)는 백엔드 질의 프록시 경유. 브라우저가 저장소에
직접 접근 안 하고 프록시가 자격증명 은닉·권한·rate limit·사설IP 저장소 접근 대신. §7-1과
대칭(실시간 푸시 / 조회 pull, 둘 다 백엔드 경유).

**요구사항:** BE-Q-01(지표 프록시)·BE-Q-02(감사 조회)·BE-Q-03(레지스트리)·BE-Q-04(RBAC 강제)·
BE-T-05(사설 IP 라우팅).

### 7-4. 재접속 스냅샷 = 백엔드 캐시

브라우저가 화면을 새로 열거나 재접속하면 각 대상 최신 상태를 구독 즉시 1회 받음. 백엔드가 상태를
캐시하고 구독 시점 즉시 푸시.

**반증 (retained 스레드 종결):** MQTT retained로 하면? **브라우저는 브로커에 직접 안 붙는다** —
백엔드 경유. retained를 쓰려면 백엔드가 브로커 retained를 받아 다시 넘겨야 하는데, 그럴 바엔
백엔드가 직접 캐시하는 게 경로 단일. 즉 **retained(브로커 직접 구독자용)와 백엔드 캐시(브라우저
재접속용)는 소비자가 달라 다른 도구.**

**캐시 정책 (채널별):**
- **캐시함** (없으면 화면이 '모른다'를 그리는 상태 채널): state 3층+last_seen · telemetry ·
  actuator_state · control_lock · plan · plan_progress · video_meta.
- **캐시 안 함** (재접속 시 낡은 것이 현재처럼 보이는 채널): command_result · video_frame ·
  detections.
- **캐시값 타임스탬프는 원래 발행 시각 유지** — 푸시 시점으로 다시 찍으면 staleness 판정이
  리셋돼 1분 전 값이 새 값처럼 보임.

**요구사항:** BE-T-06(재접속 캐시)·가시화 VZ-I-02.

### 7-5. 영상

관제용 영상은 업무·관측과 분리된 별도 미디어 경로로 뷰어에. 뷰어가 못 그리는 원본 규격(RTSP)을
미디어 어댑터가 재생 가능 규격으로 흡수. 상세(RTP→WS→WSS, Tailscale)는
[`02-media-path.md`](02-media-path.md)가 권위.

**요구사항:** BE-T-07(미디어 뷰어 중계)·가시화 VZ-I-06.

### 7-6. 종착지 (Grafana / 관제 화면)

**프레이밍:** Grafana는 자리표시 예시이자 **개발용**이고, **최종 종착지는 관제 화면**이다. "관제
화면 vs Grafana 역할 분리"는 결정된 역할 분리가 아니다.

**실제 질문 = "종착지가 무엇이든 모든 데이터가 갈 수 있는가":**
- **Grafana:** TSDB·Prometheus·Loki·Tempo를 데이터 소스로 붙여 읽을 수 있다(네이티브 지원).
- **관제 화면:** 조회는 질의 프록시(§7-3), 실시간은 WS 게이트웨이(§7-1)로 받아 같은 데이터 다
  받을 수 있다.

→ **종착지가 Grafana든 관제 화면이든 모든 데이터가 갈 수 있다.** 경로가 다를 뿐(Grafana=저장소
직접 소스 / 관제 화면=백엔드 경유). 단 도구 특성 차이(결정된 역할 분리 아님): 관제 화면은
실시간 값(50ms·트윈)을 WS 푸시로 받아 실시간에 강하고, Grafana는 저장소 폴링 도구라 50ms급
실시간 트윈에 부적합(지표·이력 추이가 자연스러움).

## 8. 관통 원칙 · 이음새

### 8-1. 업무 중앙(Kafka) / 관측 분산(페더레이션) 비대칭

**"왜 업무는 중앙집중인데 관측은 분산인가"의 답 = 요약 가능성의 차이.**
- 관측 metric은 요약해도 됨(15초 평균으로 운영 뷰 충분, 상세는 엣지 raw 조회) → 엣지 분산+요약
  으로 부하를 구역 수 비례로 억제(BE-S-03).
- 업무 데이터는 다중 소비자(트윈·AI·DB)가 원본을 각자 읽어야 함 — 수위 추이를 15초 평균내면
  순간 급변을 놓쳐 트윈·위험판정이 깨짐. 그래서 원본 스트림을 중앙 Kafka로(BE-T-02).

**"요약해도 되는가"가 분산/중앙을 가른다.**

### 8-2. 카메라 캘리브레이션 경계

순서 관계로 두 작업이 나뉜다.
- **AI-E-02 (진나영):** 카메라 자동 보정 프로파일 생성(내부 파라미터·왜곡).
- **DT-04 (이대규):** 그 보정 결과로 FOV를 바닥에 투영해 커버리지·관측 사각 영역 산출.

**AI-E-02(보정) → DT-04(공간 커버리지)가 소비**하는 관계로 다른 작업. 상세 경계는 디지털
트윈 영역이라 요구사항 단계 확정.

## 부록 A — 예상 질문 빠른 참조

| 질문 | 답 |
|---|---|
| 왜 MQTT? 대안은? | 다대다·잦은소량·LWT·QoS·pub/sub. ZeroMQ(주소 관리 지옥)·Kafka(무겁고 다중소비자는 백본)·RabbitMQ(소비 후 소멸)·DDS(로봇 내부) 배제 |
| 여기도 Kafka로 통일하면? | 저사양 말단에 JVM 무겁고 과함. 다중소비자 버퍼는 백본 몫 |
| 채널 두 개 왜? 통일 안 하나? | 데이터 성격이 자동 결정 → 돌발 채널 없음(결정론화). MQTT 통일 시 OTel 4부품 재발명 |
| OTel도 데이터 보내는 거 아니냐? | MQTT는 전송, OTel은 관측 규격. 층이 다름(값 나르는 도구 아님) |
| 로봇 1~2대에 Kafka 과하지 않나? | 근거는 데이터 양이 아니라 다중 소비자 구조(AI·DB·트윈). 캡스톤은 작게 배포 가능(3AZ·RF=3는 국가 프로파일) |
| NATS 안 쓰냐? | 캡스톤만 보면 브릿지 제거·경량 우위이나, 국가 규모 처리량·생태계로 Kafka. 지연 차이(10~40ms)는 캡스톤에 무의미 |
| 재난 아카이브 때문에 Kafka? | 아니오. Kafka는 다중 소비자 때문. 아카이브는 소비자 중 하나. 재생/학습은 데이터 평면(아카이브), 관측 평면 아님 |
| 브릿지 왜 필요? 엣지에 Kafka 있나? | 구간별 전송이 달라 필연. 엣지엔 Kafka 브로커/저장소는 없고 Kafka Connect 워커(또는 네이티브 브릿지)는 있음. 엣지→서버 아웃바운드로 사설IP 해소 |
| Collector랑 Prometheus 중복 아니냐? | 수집·라우팅(Collector, 3종) vs metric 저장·요약·경보(Prometheus). 층이 다름 |
| Prometheus는 pull 아니냐? | scrape = /metrics를 GET. Collector 긁기(A)/노드 직접(B) 공존. 노드 생사는 방식 A면 absent 감지(주력은 MQTT LWT) |
| 브라우저가 왜 브로커에 직접 안 붙나? | 프로토콜 한계+사설망+인증. WS 게이트웨이(서버 안)가 Kafka 소비자+WebSocket 서버로 중계 |
| 명령이 느려서 로봇 못 움직이나? | 관제 명령 수십 ms(골든타임 초~분 대비 무시). 정밀 WASD는 WebRTC 분리 |
| 왜 업무 중앙(Kafka), 관측 분산(페더레이션)? | 요약 가능성 차이. 관측은 요약 가능(분산+요약), 업무는 다중소비자가 원본 필요(중앙) |
| Tailscale 왜 쓰나? | 엣지-서버가 사설망 뒤라 터널 없이 연결 불가. 터널은 강제, Tailscale은 교체 가능 |
| 좁은 회선서 영상이 명령 민다는 게? | 논리 채널은 분리(버퍼 안 섞임). 물리 회선 하나를 공유해 영상 부피가 명령 적시성 침해(대역 경쟁). QoS는 미디어 경로에서 대응 |
| 저장소는 뭐 쓰나? | 계측 시계열=TSDB(제품 미확정), 감사·레지스트리=MySQL(테이블 분리), 관측=Prometheus/Loki/Tempo. 트윈·명령진행·가용성은 저장 아님(WS 푸시) |
| 가용성은 어떻게 판정하나? | 업무 평면(MQTT 세션)+관측 평면(up/absent) 이중 감지 → 서버 단일 통합, 충돌 시 업무 평면 우선(세션 online이면 가용) |
