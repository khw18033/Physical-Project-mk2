## §1 방식 B 프레임 형식 — `frame_ref`는 객체다

**웹소켓 바이너리 메시지 하나 = 프레임(액세스 유닛) 하나.**

```
[4바이트 big-endian: 헤더 길이][JSON 헤더(UTF-8)][페이로드 바이트]
```

```json
{
  "frame_ref": { "source_id": "go1-001_front", "capture_timestamp": "2026-09-18T12:00:00.123+09:00", "sequence_id": 4837 },
  "encoding": "h264", "keyframe": true, "width": 464, "height": 400,
  "codec": "avc1.42E01E", "correlation_id": null
}
```

| 필드 | 필수 | 뜻 | 우리는 이렇게 읽었다 |
|---|---|---|---|
| `frame_ref` | ✅ | **객체** `{source_id, capture_timestamp(ISO), sequence_id}` — [`frame-reference.schema.json`](../../contracts/common/frame-reference.schema.json). 엣지가 부여, 서버는 바이트 그대로 전파 | VZ 목의 `frame_ref: number`(`vision.ts:84`)·`frame_seq`(`:36`)는 **VZ 스스로 "미결·가정"이라 적어 둔 값**이다(`gateway/vision.ts:142-143` *"AI와 하드웨어의 프레임 참조 형식이 다르다 … 여기서는 정수 frame_seq로 가정한다"*). **VZ-I-07 원문은 복합키(원천 식별자·촬영 시각·시퀀스 번호)**이므로 우리 객체안이 VZ 요구사항과 같은 방향이다 |
| `encoding` | ✅ | 페이로드 코덱 **선언**. string, 알려진 값 `h264`·`jpeg`는 `$comment`(enum 아님) | **모르는 값은 디코드하지 않고 상태로 표시**한다 — 서버도 값을 검증하지 않는다 |
| `keyframe` | ✅ | 이 프레임만으로 디코드를 시작할 수 있는가(IDR). JPEG는 항상 `true` | 뷰어는 **첫 keyframe까지 디코더에 넣지 않는다** — 서버가 첫 전송·드롭 뒤 재개를 항상 keyframe으로 보장하지만 재연결 직후 방어는 뷰어 몫 |
| `width`·`height` | ✅ | 원본 해상도 | **VZ `VideoFrame.reference{width,height}`가 이 자리다**(`vision.ts:40-41` *"탐지의 bbox_space.reference와 같은 값이어야 한다"*) — [§6](#s6) ④ |
| `codec` | 선택 | RFC 6381 문자열 = WebCodecs `VideoDecoderConfig.codec`. `description`은 없다(Annex-B in-band) | H.264 디코더 구성에 그대로 쓴다 |
| `correlation_id` | 선택 | 명령 산출물일 때의 상관키 | 표시용. `frame_ref` 밖에 있다(결정 2) |

⚠ **VZ 쪽 변경은 타입 하나가 아니다.** `frame_ref`가 객체가 되면 — 버퍼 조회 키(`frameAt(seq)`가 `f.frame_seq === seq` 정수 동등 비교, `vision.ts:240-241`) · `frameLag` 계산(`:337` 정수 뺄셈) · 표시(`VideoOverlayView.tsx`의 `{report.frameLag}프레임`)까지 걸린다. 키는 `(source_id, sequence_id)` 쌍으로, `frameLag`는 같은 `source_id` 안의 `sequence_id` 차로.

⚠ **재접속하면 `sequence_id`가 리셋된다**(엣지가 붙을 때마다 0부터). `frameLag`를 순번 차로 계산하면 그 순간 음수·거대값이 된다 — **리셋 경계는 세션**(엣지 재연결)이다. 순번이 줄어들면 새 세션으로 보고 버퍼를 비운다.

**답이 없으면:** 객체 그대로 간다 — 이것이 규격 파일이다.

## §2 연결 = 켜기 — 제어 메시지가 없다

`ws://<서버 tailscale IP>:8765/media?source_id=<카메라 키>&token=<토큰>`에 **붙는 것이 켜기, 끊는 것이 끄기**다.
`video{entity, open}` 같은 제어 메시지를 쓰지 않는다(VZ 목 `protocol.ts`의 그 메시지는 우리 게이트웨이에 보내지 않는다 — 보내도 무시된다).

- **페이지 로드 때 붙으면 상시, 패널 열 때 붙으면 온디맨드** — 같은 메커니즘이고 서버는 그 차이를 모른다(Phase 4 결정 4-b).
- 첫 프레임은 항상 `keyframe=true`다. 붙은 뒤 첫 프레임까지의 시간(콜드스타트)은 서버 지표로 재고 있다 — 직접 경로 실측 215ms(GOP 0.5초).
- 엣지가 아직 안 붙어 있으면 소켓은 열리고 프레임만 안 온다 — "연결됨인데 영상 없음"은 정상 상태일 수 있다. 엣지가 붙으면 그때부터 흐른다.
- 서버는 뷰어 소켓마다 **GOP 인지 drop-old**를 건다 — 느린 뷰어 하나가 다른 뷰어를 막지 않는다. 다만 [§5](#s5) 끝의 주의를 보라.

**답이 없으면:** 이대로. VZ 코드의 `video{open}` 발신부는 지워도 되고 남겨도 된다(무해).

## §4 `entity` ↔ `source_id` 대응 — `/media`는 카메라 단위다

- VZ 목의 `robot-01`·`robot-01-cam`이 아니다 — [§12](#s12).

**답이 없으면:** 화면 설정값으로 간다.

## §5 🔴 디코드보다 앞선 단계 — 전송층에 바이너리 수신 경로 자체가 없다

`WsTransport.onMessage`는 `JSON.parse(String(ev.data))`(`WsTransport.ts:178`)로 시작하고 실패하면 `catch { return }`(`:179-181`)이라,
방식 B 프레임(Blob)이 오면 **아무 로그 없이 조용히 버려진다** — 「연결됨인데 영상만 안 옴」으로 보이는 **가장 진단하기 나쁜 실패 모드**다.
VZ 저장소 전체에서 `binaryType`·`ArrayBuffer`·`createImageBitmap`·`drawImage`가 **0건**이다(2026-09-17 대조).

**필요한 순서:**

| # | 무엇 | 왜 |
|---|---|---|
| ① | **`ws.binaryType = 'arraybuffer'`** | 기본값 `blob`이면 `.arrayBuffer()`가 비동기라 `sub.handler(envelope)`의 **동기 계약이 깨진다** |
| ② | `onMessage`를 **`typeof ev.data === 'string'`** 기준으로 텍스트/바이너리 2갈래 분기 | 텍스트는 지금 코드, 바이너리는 ③으로 |
| ③ | `[4B][JSON][페이로드]` 파서 | `DataView.getUint32(0)` → 헤더 → 나머지 슬라이스. 헤더 JSON 실패·길이 초과는 **카운터 + 상태 표시** |
| ④ | 디코드 — JPEG는 `createImageBitmap(new Blob([payload]))` + `drawImage`, **H.264는 WebCodecs `VideoDecoder`**(`codec` = 헤더의 `codec`, `description` 없음, `hardwareAcceleration: 'prefer-software'`) | 모르는 `encoding`은 디코드하지 않고 상태로 표시 |

**`catch { return }`에 최소한 카운터 하나를 붙여 달라** — 지금 구조에서는 형식이 틀려도 화면에 아무 신호가 없다.

**HW가 실기에서 고친 브라우저 결함 5건**(`pi/bench/go1_cam_view.py`, 464×400 H.264 실기) — 우리 확인용 뷰어(`backend/gateway/console.html`)에도 옮겨 적었다:

1. `hardwareAcceleration: 'prefer-software'` — 이 해상도에서는 소프트웨어 디코드가 밀리초대이고 하드웨어 경로가 오히려 늦는다.
2. **최신 프레임만 rAF 주기로** 그린다 — 디코더 출력을 전부 그리면 밀린다.
3. **보조 타이머** — 탭이 뒤로 가면 rAF가 멈춘다.
4. `desynchronized` 제거 — vsync 한 주기를 아끼려던 옵션이 오히려 찢김.
5. `Cache-Control: no-store` — 옛 JS를 캐시로 재사용.

**MJPEG 폴백 참조 구현도 HW에 이미 있다**(`go1_cam_view.py:172-` — WebCodecs 없는 브라우저로 자동 분기, 단 파이에서 H.264→MJPEG **완전 재인코딩**이라 대가가 크다). 우리 경로에서는 폴백이 아니라 **JPEG 소스(고정 CCTV)**가 그 자리다.

⚠ **서버가 못 지켜 주는 것 하나 — 뷰어 앱이 느릴 때.** 링크는 빠른데 브라우저가 디코드·렌더를 못 따라가면 초과분이 **브라우저·OS 수신 버퍼**에 쌓이고 서버 `send()`가 막히지 않아 **서버 drop-old가 발동하지 않는다**(Phase 4 실측: Windows 뷰어를 5초 정지시켜도 서버 드롭 0, 지연은 뷰어 안에서 5초). **뷰어가 자기 큐를 관리해야 한다** — 위 2번(최신 프레임만)과 `decodeQueueSize` 임계 재동기(HW `:499`)가 그것이다.

## §12 `target_entity_id`(개체)와 미디어 `source_id`(카메라)가 같은 이름으로 다른 축을 가리킨다

→ **갈라서 적는다:** `target_entity_id`에는 **개체 키 `go1-001`**, `/media` 구독과 탐지 `frame_ref.source_id`에는 **카메라 키 `go1-001_front`**. [`frame-reference.schema.json`](../../contracts/common/frame-reference.schema.json)의 *「봉투의 source_id와 같은 식별 체계를 쓴다」*는 **체계가 같을 뿐 값이 같지 않다**는 뜻이다.

## §13 `origin.kind`(탐지 정밀도)와 공통 헤더 `origin_kind`(실물/시뮬/재생)는 다른 축이다

## §14 그 밖 — 캐시 10종 · `capture_timestamp` 뜻 · 촬영본 세 곳

- **캐시 정책 확인은 「금지 3종」이 아니라 10종 전체다.** 우리 [`00-architecture.md`](00-architecture.md) §7-4의 캐시 7(`state`·`telemetry`·`actuator_state`·`control_lock`·`plan`·`plan_progress`·`video_meta`) + 금지 3(`command_result`·`video_frame`·`detections`)은 **VZ `web-dashboard/README.md:381-382`·`gateway/server.ts:752`와 한 건도 어긋나지 않는다.** ⚠ VZ `config.ts`는 이후 5채널이 더해져 실제로 **8/10**이고 헤더 주석의 「7/3」은 낡은 숫자다 — *"VZ가 8종을 더 관리 중"*까지 적어 둔다. 캐시값 ts는 원래 발행 시각 유지.
- **`capture_timestamp`의 뜻:** **엣지가 프레임 경계를 확정한 시각**이다. 촬영 시각이 아니고 말단 내부 지연이 포함되며 보정되지 않았다. ISO date-time(콜론 오프셋 + 밀리초). 그래서 **스트림 staleness는 이 값이 아니라 도착 시각으로 판정한다**([§8](#s8) §7.10).
- **VZ도 `mission-history/images/robot/`에 영상 프레임을 따로 저장하고 있다** — 촬영본이 세 곳(pi 로컬·VZ·우리 4b 저장소)에 쌓이므로 **중복 정리를 Phase 5/6 안건으로 올렸다.** 단 VZ 쪽은 *"DB가 보관할 이력의 자리표시"*라 적혀 있어 "VZ가 하니 우리는 안 해도 된다"로 읽지 않는다.

{ "type": "data", "sub": "<그쪽이 붙인 구독 ID 그대로>", "envelope": { … 아래 11칸 … } }
```

**ⓑ 구독을 안 보낸 클라이언트**(우리 확인용 뷰어·회귀 시험) — Phase 1 echo 그대로 `{channel, topic, key, message}`.

> **가르는 기준은 「구독표가 비었나」 하나다.** 경로(`/state2`)도 쿼리 파라미터도 늘리지 않았다 — **VZ 가 접속 즉시 구독을 보내기 때문에** 그것만으로 갈린다. 코드를 더 고칠 것이 없다.

#### `envelope` 11칸

| 칸 | 값 | 비고 |
|---|---|---|
| `zone` | 메시지의 `zone_id` | `zoneA` |
| `node` | `node_id` | 발행 **물리 노드**(`pi7`) |
| `entity` | `entity_id`, 없으면 `source_id` | `go1-001` |
| `channel` | `state` · `heartbeat` | 🔴 **`status` 는 구독자에게 안 간다** — VZ `Channel` 타입에 없어 화면이 무엇을 할지 계약에 없다 |
| `ts` | `timestamp` | ISO date-time |
| `seq` | `sequence_id` | 없거나 이상하면 **`0`** (예외를 던지지 않는다) |
| `payload` | **원래 메시지 통째** | 🔴 [15-6](#s15-6) — `StateLayers` 모양이 아니다 |
| `quality` | `"good"` | **잠정 고정값** |
| `aggregation` | `"raw"` | **잠정 고정값** |
| `scope` | 구독의 `scope` 를 되돌려준다(없으면 `"all"`) | |
| `coordinate_frame` | `null` | **잠정 고정값** |

> **잠정값 셋이 문제없다**고 확인해 준 것 — `quality` 는 저장만 하고 읽는 화면이 없고, `raw` 는 정상 RAW 로 처리되고, `coordinate_frame:null` 은 그 줄만 숨긴다 — 이 답이 **이번 판을 그대로 가게 한 근거**다. 그 자리를 먼저 맞출 필요가 없다는 확인을 받고 갔다.

#### 선택자(selector) 매칭 규약 — **축 셋, 그리고 `node` 는 둘을 받는다**

```
selector = { entity: <값>|'*', node: <값>|'*', channel: <값>|'*' }
```

| 축 | 무엇과 비교하나 |
|---|---|
| `channel` | 봉투의 `channel` |
| `entity` | `entity_id`, 없으면 `source_id` |
| `node` | 🔴 **`node_id` **또는** `zone_id` 둘 중 하나와 맞으면 통과** |

**`node` 축이 둘을 받는 이유:** VZ 기본 선택자가 `{entity:'*', node:<zone>, channel:'*'}` 로 **구역을 `node` 자리에** 넣고 있다(`src/tabs/data/index.ts:60`). 그쪽 규약에 맞췄다 — 물리 노드로 거르고 싶으면 `node:'pi7'` 도 그대로 동작한다.

**⚠ 깨진 선택자는 전량 푸시로 물러서지 않는다.** dict 가 아닌 값이 오면 **0건**이다. 구독 계약이 깨졌는데 데이터를 쏟으면 원인이 묻히기 때문이다(시험 `test_깨진_선택자는_전량_푸시로_물러서지_않는다`).

**⚠ `subscribed`·`hello` 같은 응답은 만들지 않았다.** VZ `switch` 에 처리 가지가 없어 보내도 무시된다 — 범위를 넓히지 않았다. **`unsubscribe` 는 받는다.**

### 15-3. 물음 ②·③ 의 답

<a id="s15-3-1"></a>

#### 15-3-1. `alignment` **부재** — 수용한다. 기한을 붙여서

그쪽 구현은 이렇다:

```
alignment === 'frame'   프레임 정합
그 밖의 값이 실려 옴     정합하지 않는다 — 사용자 토글이 켜져 있어도
값이 아예 없음           옛 계약 — 사용자 토글이 정한다        ← 우리 규칙과 다른 줄
```

**수용한다.** 사유(*"부재까지 unaligned 로 두면 목 게이트웨이의 정합 시연이 통째로 죽는다"*)가 타당하고, **지금 실경로로 오는 탐지가 0건**이기 때문이다 — 탐지 채널·토픽 배선이 Phase 6 이고 `detections.schema.json` 은 *"어떤 검증 경로도 이 파일을 로드하지 않는다"* 고 적힌 초안이다. 즉 **`alignment` 없이 오는 것은 오늘 기준 목 데이터뿐**이라 위험이 0이다.

**🔴 다만 기한이 있다. 실물 탐지가 우리 경로로 오기 시작하면 「부재 = unaligned」로 되돌린다.** 그때부터 우리 규격은 `alignment` 를 **항상** 싣기 때문에, 부재는 「옛 계약」이 아니라 **생산자 결함**이다. 결함을 토글로 덮으면 **틀린 박스가 맞는 것처럼 보인다** — fail-safe 를 만든 이유 그 자체다.

**이 조건을 이 문서와 요구사항 추적표 양쪽에 적어 둔다.** 안 적으면 그 시점에 아무도 못 찾는다.

> **「정합하지 않았다는 사실을 화면이 적는다」는 정확히 옳은 처리다.** 안 적으면 정합 안 된 박스가 정합된 것처럼 보인다는 그쪽 판단이 이 안건의 핵심을 그대로 짚었다.

<a id="s15-3-2"></a>

#### 15-3-2. sidecar — **셋 다 `4318`(HTTP)**

`vz-stt`(`127.0.0.1:8801`)·`vz-gen`(`127.0.0.1:8802`)이 **관제 노트북에서 도는 사이드카**라 gRPC 도 가능하다는 것은 맞다. 그래도 **`4318` 로 모아 달라.** 근거 셋:

1. **`4316` 은 엣지 입구로 둔다.** 거기에 VZ 까지 섞이면 *"4316 에 문제가 생겼을 때 엣지 문제인지 VZ 문제인지"* 가 갈린다. 방화벽 줄도 하나로 끝난다.
2. **트래픽이 60초에 숫자 여섯이다** — `source`·`period_sec`·`measured_at`·`envelope_count`·`apply_delay_avg_ms`·`apply_delay_max_ms`. 프로토콜 효율을 따질 양이 아니다.
3. **브라우저가 이미 `@opentelemetry/exporter-metrics-otlp-http`(JSON)** 로 정해졌으니 사이드카도 같은 계열이면 VZ 쪽 코드가 단순해진다.

> **exporter 는 JSON 으로 받는다** — protobuf 변형은 필요 없다. **`③ https 아님`도 받았다** — `http://<서버>:4318` 평문 + ufw `/32` 로 간다. **https 로 바꾸게 되면 미리 알려 달라**(4318 TLS 가 필요해지고 그건 결정 7 범위 밖이다).
>
> **`①`·`②`·`③` 다 받았다 — [§10](#s10) 은 닫혔다.**
>
> - **`①` 기기 주소 둘**(관제 데스크톱·노트북)을 받아 **`8765` 는 이미 열었다**(ufw `/32` 두 줄).
> - **`②` origin 은 넷을 다 열겠다** — 두 기기 × `:5174`(통합 빌드)·`:5175`(단독 빌드). **시연 때 어느 쪽을 띄울지 정해 주지 않아도 된다.** exporter 는 **JSON** 으로 받는다(protobuf 변형 불필요).
> - **`③` http 그대로 간다** — `http://<서버 tailnet 주소>:4318` 평문 + ufw `/32`. **https 로 바꾸게 되면 미리 알려 달라**(4318 TLS 가 필요해지고 결정 7 범위 밖이다).
>
> **남은 것은 우리 쪽 작업이다** — `4318` ufw `/32` 두 줄 + Collector 의 tailnet 바인딩·CORS 에 그 네 origin 을 넣는 것. **단계 1 에서 한다.**

### 15-4. §4 탐지 규격 — **VZ 이름으로 바꿨다. 규격 파일을 이미 고쳤다**

*"「초안이라 비용이 0」이라고 한 그쪽 제안을 받는다"* — 받았으니 **그 자리에서 고쳤다.**

```diff
- "coord":      { "normalized": true, "origin": "top-left", "ref_width": 464, "ref_height": 400 }
+ "bbox_space": { "format": "normalized", "origin": "top-left", "reference": { "width": 464, "height": 400 } }
```

| 고친 파일 | 무엇 |
|---|---|
| `contracts/common/detections.schema.json` | `coord` → `bbox_space`. 최상위 `required` 도 `["bbox_space","boxes"]` |
| `contracts/common/examples/detections-draft-valid.json` · `…-no-alignment.json` | 예시 둘 |
| `tests/test_contract_media.py` | **`"coord" not in props` 를 단언한다** — 옛 이름이 남으면 시험이 죽는다 |

**값 어휘는 여전히 `enum` 이 아니다**(`string` + `$comment`). 모르는 값이 와도 규격이 거부하지 않고, 판정은 화면의 fail-safe 가 한다 — [15-3-1](#s15-3-1)과 같은 원칙이다.

**`format` 기본값:** *"우리 쪽에는 기본값이 없다. 무엇을 보낼지는 그쪽이 정하면 된다"* 에 대한 답 — **우리는 `normalized` 로 보낸다.** 해상도가 바뀌어도 비율은 안 깨지기 때문이다. `absolute` 인데 `reference` 가 미디어 헤더의 `width`/`height` 와 어긋나면 **박스가 통째로 밀린다** — 더 나쁜 실패다.

> ⚠ **최종 확정은 AI(진나영) 회신 뒤다** — 그 규격의 **생산자가 AI** 이고 아직 회신 전이다. **실측 단계는 `normalized` 로 간다.**

**`origin.tier` 에 `server` 를 넣어 준 것** — 전에는 `tier !== 'device' && tier !== 'edge'` 로 **서버 탐지를 통째로 드롭**하고 있었다고 했는데, 그 한 줄이 Phase 6 에 서버 중계 탐지가 붙는 순간 원인 못 찾을 자리였다. 지금 넣어 둔 것이 맞다.

### 15-5. §7 구역 식별자 — **판단이 옳다. 값은 `zoneA` 다**

*"값을 통째로 `zoneA` 로 바꾸면 기존 시연 경로가 빈 화면이 되고, 그대로 두면 관문 C-a 가 성립하지 않는다 — 어느 쪽을 골라도 한쪽이 죽는다."*

**정확한 진단이고, 연결 설정의 한 칸으로 옮긴 것이 정확한 해법이다.** 주소를 바꾸는 사람이 구역도 같이 바꾼다 — 그 둘은 원래 같이 움직이는 값이다.

**우리 서버에 붙을 때 그 칸에 넣을 값은 `zoneA` 다.** 선택자 모양 `{entity:'*', node:<zone>, channel:'*'}` 은 그대로 두면 된다 — 우리 `node` 축이 **`node_id` 와 `zone_id` 둘 다** 본다([15-1](#s15-1)).

> 🔴 **이것이 이번 실측에서 「연결은 되는데 화면만 빔」의 첫 번째 원인 후보다.** 우리 회귀 시험에 `zone-503` 을 넣으면 **0건**이 나오는 것을 음성 시험으로 박아 뒀다(`test_구역_식별자가_어긋나면_아무것도_안_간다`).

<a id="s15-6"></a>

### 15-6. 🔴 §8 `StateLayers` — **동의한다. 이번에 억지로 채우지 않는다**

*"실측대비용 임시 구현에 3층을 억지로 채우게 하면 그 모양이 그대로 굳는다"* — **그 판단에 동의한다.** 어댑터가 `payload` 에 원래 메시지를 통째로 넣는 것은 설계이지 누락이 아니다.

| | |
|---|---|
| 이번 실측에서 화면에 보일 모습 | **로봇 상태 = 「알 수 없음」** |
| 그것이 | 🔴 **결함이 아니라 합격 모습이다** |
| 왜 | 가용성 판정(`availability`)이 Phase 5 안건이고, 3층 계약은 Phase 5 정식 계약과 함께 정한다 |
| 이번 실측이 판정하는 것 | **경로가 살아 있는가** — 로봇 → 엣지 → 서버 → 뷰어로 업무 데이터가 **끊기지 않고 도착하는가** |

**3층 모양이 아니면 「알 수 없음」으로 두는 가드**와 **레지스트리 밖 개체는 판정을 안 그리고 원문을 적는** 처리, 둘 다 맞다. 그 둘이 있어서 이번 판이 **빈 화면이 아니라 「원문은 흐르는데 판정이 없는 화면」**으로 보인다 — 그게 정확히 이번에 봐야 할 그림이다.

> **어댑터가 `StateLayers` 를 채울지는 Phase 5 정식 계약과 함께 정한다.** 그때까지 이 어댑터는 **되돌릴 수 있는 상태로** 두었다 — `state_session` 의 수신 루프 한 줄을 되돌리면 구독표가 비고, 구독표가 비면 지금 형식 가지로만 간다.

<a id="s15-7"></a>

### 15-7. 새 안건 — 드론 두 물음의 답

드론 작업 중 물어본 둘에 대한 답을 여기에도 남긴다(구두로 먼저 전달했다).

#### ① 구독 패턴 — **둘 다 아니다. 더 넓다**

`backend/ingest/bridge.py:61` 이 거는 구독은 셋이고, **구역까지 와일드카드**다:

```
+/+/+/state      +/+/+/status      +/+/+/heartbeat      (QoS 1)
```

`zoneA/+/+/state` 도 `zoneA/robot/+/state` 도 아니다. **`zoneA/drone/x500-001/state` 는 그대로 걸린다.**

#### ② 🔴 진짜 답 — `drone` 은 **개체 타입 어휘에 없다. 그런데 격리가 아니라 통과다**

브릿지가 토픽 두 번째 칸을 개체 타입(etype)으로 읽는다 → `drone`. 본문 2단 검증에서 `state` + `drone` 규격 파일을 찾는데 없다(`state.{sensor,robot,actuator,analysis}.schema.json` 넷뿐).

**그때 통과시킨다.** `envelope.py::validate_payload` 가 *"규격이 없는 조합(모르는 개체 타입 등)은 **통과시키고 기록만** 한다 — 새 노드 타입이 첫 메시지부터 격리되면 안 되기 때문"* 이라고 설계돼 있다.

| 단계 | 드론 `state` |
|---|---|
| 구독 `+/+/+/state` | ✅ 걸린다 |
| 1단 공통 헤더 strict | ✅ 필수 5칸만 맞으면 통과 |
| 2단 본문 검증 | ⚠ **건너뛴다** — 로그 한 줄만 |
| Kafka → `/state` → 뷰어 | ✅ **간다** |

**즉 드론 상태는 이미 화면까지 흐른다. 다만 본문이 엉망이어도 안 걸린다.**

**검증을 켜는 법 — 파일 하나. 파이썬 변경 0.** `backend/contracts.py::known_entity_types()` 가 어휘를 디렉터리에서 유도하므로(*"파이썬에 어휘를 적지 않고 파일에서 유도한다"*), `contracts/common/payload/state.drone.schema.json` 을 넣는 순간 켜진다.

> 🔴 **그래서 필요한 것: 드론 `state` 본문 항목 목록.** 필드 이름·타입·필수 여부, `reason` 어휘가 있으면 그 목록, 그리고 **실제 발행 메시지 한 건**이면 가장 확실하다. 받으면 `state.robot.schema.json` 을 본떠 만들어 넣고, HW 회신의 etype 어휘도 **넷 → 다섯**으로 개정한다.

#### ③ 브로커 둘 — **한 프로세스로는 못 본다. 둘 띄우면 된다**

> ⚠ 실제 주소는 이 문서에 적지 않는다(저장소가 Public 이다) — **별도 전달 값**에 있다.

`IngestBridge` 가 `mqtt.Client` 를 **하나** 만들고 주소도 환경변수 한 쌍(`MK2_MQTT_HOST`·`MK2_MQTT_PORT`)이다. **한 프로세스 = 브로커 하나.**

해결은 **브릿지를 둘 띄우는 것**이고 이게 설계상 정상 모양이다. 둘 다 같은 Kafka 로 produce 하고 토픽이 `mk2.telemetry.<채널>` 이라 **거기서 합류한다.**

> 🔴 **드론 브로커 주소는 pi3 의 사설 LAN(`<pi3 LAN 주소>:1883`)이라 서버에서 못 닿는다.** 드론 브릿지는 **pi3 와 같은 망에 있는 기기**에서 돌아야 한다 — 마침 이번 실측에서 업무 평면 브릿지를 **엣지로 옮기기로** 했으므로(실측준비 v2.2 §3-1-2) 구조가 이미 그 모양이다. 브릿지는 **환경변수 넷만 바꾸면 어디서든 돈다(코드 변경 0)**.
>
> ⚠ 둘 띄울 때: **`MK2_QUARANTINE_PATH` 를 반드시 갈라 달라**(같으면 어느 브로커 것인지 못 가린다). 로그의 `client_id` 는 `"mk2-ingest"` 고정이라 두 프로세스가 같아 보인다 — 필요하면 환경변수로 빼겠다.

### 15-8. 🟡 코덱 문자열 — HW 실측값이 규격 예시와 다르다

HW 가 실물 Go1 정면 스트림의 SPS 를 직접 파싱했다.

| | 실물 Go1 정면 | 합성 fixture(Phase 4 브라우저 실측) | 규격 `description` 의 예시 문자열 |
|---|---|---|---|
| 코덱 문자열 | **`avc1.424028`** | `avc1.42C01E` | `avc1.42E01E` |
| profile | `0x42` Baseline | `0x42` 같음 | `0x42` 같음 |
| constraint | `0x40` | `0xC0` | `0xE0` |
| level | **`0x28` = Level 4.0** | `0x1E` = Level 3.0 | `0x1E` = Level 3.0 |

⚠ **셋이 다 다르다 — 그래서 어느 것도 상수로 박으면 안 된다.** 규격의 `avc1.42E01E` 는 `description` 안의 **예시 문자열**일 뿐이고 실측값도 fixture 값도 아니다(`enum` 이 아니라 어떤 값이든 통과한다).

**「코덱 문자열은 헤더에서 읽는다 — 상수로 안 박았다」는 그쪽 구현이 정확히 맞았다.** `decoder.configure({codec})` 에 예시값을 박아 뒀으면 실물 스트림에서 설정이 실패했을 자리다. HW 송신기도 **매 SPS 마다 다시 읽어 헤더에 싣는다.**

> 서버는 `codec` 을 **열지 않는다**(원칙 10 — 바이트 그대로 전파).

**같이 알아야 할 것 하나 — IDR 이 0.49초마다 온다.** HW 실측으로 로봇 인코더가 `IDR 15`(GOP 14.9 / **0.49초**)로 고정돼 있고 **환경변수로 못 바꾼다**(로봇 쪽 파이프라인이라 HW 손이 안 닿는다). 그래서:

- 느린 링크에서 서버 drop-old 가 발동하면 **화면이 최대 0.49초 멈췄다가 다음 IDR 에서 재개**된다.
- 우리 drop-old 가 **GOP 인지**로 도는 이유가 이것이다 — GOP 중간에서 끊으면 디코더가 깨진다.
- 🔴 **그 공백을 「끊김·오류」가 아니라 「재개 대기」로 표시하는 편이 낫다.** 실제로는 정상 동작이라, 오류로 보이면 실측 중에 없는 문제를 쫓게 된다.
