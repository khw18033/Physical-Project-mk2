<a id="s1-2"></a>

### 1-2. 빠진 것 — 임무 정의 (추가 요청)

사건 열만으로는 가시화가 되감기·격리를 할 수 없다. 사건과 **별도로** 아래가 필요하다.

| 필요한 것 | 왜 |
|---|---|
| 태스크 목록 | 접기의 시작 상태(전부 대기)를 만든다. 사건이 한 번도 없는 노드도 화면에 있어야 한다 |
| 마일스톤 소속 · 배정 대상 | 마일스톤 상태는 값으로 오지 않고, 소속 태스크를 접어 만든다 |
| deps(선행 노드 여럿) | 격리(VZ-D-05)는 실패 노드에서 deps를 거꾸로 따라간다. 분기·합류라 `parent_ref` 한 칸에 안 담긴다 |

- 현재 가시화는 판마다 **임무 정의 전체**(마일스톤·태스크·deps·대상·액션 아이템·평가 기준)를 사건 열과 따로 파일로 남기고, 다시보기가 둘을 함께 읽는다. DB가 붙으면 이 자리가 필요하다.
- **형태는 백엔드 판단에 맡긴다.** 예: ① 임무(판)당 1행 — 정의 JSON과 시작·끝 시각·결과(VZ-D-04 이력 목록에도 쓰인다) ② 첫 사건(`mission_generated`/`created`)의 `detail`에 정의 전체.
- 현재 구현에서 구조는 승인 때 정해지고 판 도중에 바뀌지 않는다. 다만 VZ-D-01은 액션 아이템 전개 중 **파생 태스크가 생길 수 있다**고 적으므로, 구조가 바뀌면 새 정의를 다시 넣을 수 있어야 한다.

<a id="s1-3"></a>

### 1-3. `event_key` — 권고 형태 대신 이것을 쓰겠다

```
{mission_id}:{가시화 내부 순번}
```

- 가시화 내부 순번은 생산자별 대역으로 나뉘어 **한 판 안에서 유일**하고, 가시화도 이 순번으로 중복을 흡수한다.
- 권고 형태보다 짧고, 같은 노드·같은 시각의 서로 다른 사건이 먹힐 일이 없다.
- 이 키는 **`mission_id`가 판마다 유일하다는 전제**에서 성립한다. [§2-4](#q4)에서 판마다 새 ID를 주기로 했으므로 같은 대본의 두 판이 같은 키를 낼 일은 없다.

<a id="s1-4"></a>

### 1-4. DAG 밖 사건과 엣지 사건 — 칼럼 두 곳의 규칙

**(가) DAG 밖 사건은 `mission` 계층으로 적는다.** 가시화는 명령 출구를 지나는 모든 명령을 사건으로 기록하는데, 그중에는 DAG 노드가 아니라 **장비**를 향한 명령이 있다(제어 뷰 노드의 수동 제어, 로봇 명령).

| 칼럼 | 값 |
|---|---|
| `layer` | `mission` |
| `node_ref` | 임무 ID |
| `target_entity_id` | 장비 ID |

새 계층(`entity` 등)을 두지 않고 `mission` 하나만 더하는 쪽을 골랐다. 장비는 이미 있는 `target_entity_id` 칸이 담는다.

**(나) 엣지·AI 서버가 낸 사건은 어휘 셋을 유지하고 `actor_id`로 가른다.** pi1 중계(엣지)와 탐지(AI 서버)가 낸 사건이 있는데, VZ-D-02 어휘는 AI·백엔드·사람 셋뿐이다.

| 원천 | `actor_kind` | `actor_id` (예) |
|---|---|---|
| 탐지(AI 서버) | `ai` | `detect-server` |
| pi1 중계(엣지) | `backend` | `pi1` |

어휘에 엣지를 더하면 VZ-D-02 원문을 고쳐야 하므로, 어휘는 그대로 두고 구체 원천을 `actor_id`에 적는다.

## §2 질문별 답

<a id="q2"></a>

### 2-2. `event_type` 어휘

**읽기 확인 — ✅ 맞다.** 8종 상태와 1:1이 아니다. 예: 실패 사건 하나가 실패한 노드는 `failed`로, 그 때문에 못 돈 노드는 `not_executed`(미수행)로 만든다. 그래서 가시화는 사건마다 결과 상태를 `detail.status`로 따로 싣는다.

**지금 쓰는 값** (가시화 구현 기준 — 확정 목록은 아니다)

| 값 | 뜻 | 주로 누가 |
|---|---|---|
| `created` | 노드가 생김 | backend(대본 재생) |
| `started` | 실행 시작 | backend(로봇·중계·탐지) |
| `progress` | 진행 중 사실. 상태는 안 바뀐다 | backend |
| `evaluated` | 평가 판정. 결과는 `detail.status`(완료·평가 대기·건너뜀) | backend |
| `failed` | 실패. 사유는 `detail.code`·`message`. **아래 4단계로 나눈다** | backend |
| `derived` | 재실행·파생. `attempt`가 오르고 `parent_ref`를 채운다 | backend·human |
| `mission_generated` | AI가 임무를 생성. 생성 근거는 `detail` | ai |
| `proposal_accepted` | 사람이 제안을 승인 | human |
| `mission_restarted` | 사람이 처음부터 다시 | human |
| (명령 action 이름) | 사람이 낸 명령. 추상 action 이름 그대로 | human |

**실패 단계 — 4단계로 나눈다**

VZ-D-05가 격리 결과에 "실패 단계와 사유"를 함께 표시하라고 요구하므로, 단계를 `event_type` 값으로 가른다. 사유 코드는 지금처럼 `detail.code`·`message`에 그대로 둔다.

| `event_type` | 단계 | 예 (현재 `code`) |
|---|---|---|
| `plan_failed` | 생성·검증 실패 — 임무·태스크를 만들거나 검증하다 실패 | — |
| `dispatch_failed` | 하달 실패 — 대상이 거절했거나 전달되지 않음 | 로봇 거절 코드 |
| `execution_failed` | 수행 중 실패 | `estop`, `path_failed` |
| `evaluation_failed` | 평가 미통과 — 실행은 끝났지만 기준을 못 넘음 | `battery_too_low` |

- 현재 구현은 아직 `failed` 하나로 적는다. 위 네 값으로 바꾸는 것은 쓰기 배선 때 한다([§4](#s4)).
- 자유 문자열이라 백엔드 변경은 없다(문의 §3과 같다).

<a id="q3"></a>

### 2-3. 보존 기간

- 가시화 요구사항에는 기간이 없다 → **기본값(무기한)에 동의한다.** 기간이 필요해지면 팀 합의 안건으로 올린다.
- **요약만 남기는 방식은 안 된다.** VZ-D-02: "기록을 요약해 받으면 되감기(VZ-D-04)와 경로 격리(VZ-D-05)가 성립하지 않는다." 지난 임무를 골라 되감으려면 사건 열 전체가 남아야 한다.
- **이해 확인 — ✅ 맞다.** 계측 표본은 여기 오지 않는다. 가시화도 로봇 영상 프레임·중계 피드·탐지 로그를 기록 열과 따로 저장하고, 기록 열에는 노드 사건과 드문 `progress`만 넣는다. 현재 대본 기준으로 한 판에 15~72건이다.

<a id="q4"></a>

### 2-4. `node_ref`·`mission_id`

| | 답 |
|---|---|
| 누가 부여하나 | 둘 다 가시화 — VZ-D-01 "이 계층의 생산 주체는 가시화다", VZ-G-01 "임무 하나와 마일스톤 목록으로 분리" |
| `node_ref` 형식 | 대본·생성기가 주는 문자열(예: `T-NB4`). 불투명 문자열로 다뤄 달라 |
| `node_ref` 유일 범위 | **한 임무 안에서만.** 다른 임무에 같은 ID가 나올 수 있으므로 `(mission_id, node_ref)` 조합 전제가 맞다 |
| 재실행 | **같은 `node_ref`를 유지하고 `attempt`만 올린다**(현재 구현) |
| `mission_id` 형식 | 생성 임무: `MSN-GEN-YYMMDD-HHMMSS`(생성 시각). 대본 임무: 대본 ID(예: `MSN-260915-01`) |
| `mission_id` 유일 범위 | **판(실행 한 번)마다 유일.** 아래 |

**`mission_id`는 판마다 새로 준다.** 지금은 생성 임무만 판마다 새 ID이고, 대본 임무는 같은 대본을 다시 돌리면 같은 ID를 쓴다. 그대로 보내면 백엔드에서 두 판이 한 임무로 합쳐지므로 바꾼다.

- 대본 임무도 **대본 ID + 판 시작 시각**으로 판마다 새 `mission_id`를 만든다. 생성 임무가 이미 쓰는 규칙(생성 시각을 넣는다)과 같다.
- 어느 대본이었는지는 `detail`에 대본 ID로 남긴다.
- 백엔드 변경은 없다 — `run_id` 칼럼을 따로 두지 않는다.

<a id="q5"></a>

### 2-5. `attempt` — ✅

- **노드 단위.** 재실행 대상이 태스크 노드다(VZ-D-08 "실패한 태스크의 파라미터 수정 후 재실행").
- **생산자(가시화)가 세서 보낸다.** 현재 구현도 그렇다(예: 경로 재탐색·이동 회차). 백엔드는 세지 않아도 된다 — 기본값 그대로다.
- 액션 아이템 단독 실행(VZ-D-08)의 회차는 요구사항·구현 모두 아직 없다. 생기면 같은 규칙(그 노드 단위)을 따른다.

<a id="q6"></a>

### 2-6. 구간 질의 — ✅ ②

- **②로 확정한다.** VZ-N-02 전달 경로 원문이 "(내부 처리) / 실제 조회는 VZ-I-03·I-04·I-05·I-06 경로"다. 범위 계산은 가시화 내부이고, 조회는 기존 지표 질의(VZ-I-04 → BE-Q-01)로 간다.
- 현재 구현도 뷰 노드를 태스크에 이으면 (대상 장비, 구역, 시작~끝)을 가시화가 기록에서 계산한다.
- 백엔드는 기본값대로 **계측 구간 질의(대상, 시작, 끝)만** 열면 된다. 시작·끝은 가시화가 UTC 절대 시각으로 바꿔 보낸다. ①은 현재 요구사항으로는 필요 없다.

<a id="q7"></a>

### 2-7. 8종 상태 파생 — ✅ ②

- **②로 확정한다.** VZ-D-06 전달 경로 "(내부 처리) / 상태는 VZ-D-02 기록에서 파생", VZ-D-04 "(내부 처리) / 이력 조회: 백엔드→가시화". 문서가 망설인 D-04의 "앞에서부터 접어"도 가시화 내부 처리다.
- 현재 구현도 가시화가 접는다. 사건마다 `detail.status`가 실려 있어서, 접기는 노드별 마지막 상태를 고르는 일이라 가볍다. 백엔드가 대신할 이유가 없다.
- 백엔드에 필요한 것: `mission_id`로 사건 열을 `seq` 순으로 돌려주는 것 + 임무 정의([1-2](#s1-2)). 백엔드는 8종 어휘를 몰라도 된다.

<a id="q8"></a>

### 2-8. 모델 승인 기록

- 감사(`audit_log`)에 함께 넣는 데 **이의 없다.** 성격이 감사와 같다는 읽기에 동의한다.
- 다만 승인 대상은 **모델·판단 정책·환경 지식 3종**이다(VZ-U-08·AI-L-06). `subject_kind`가 `model` 하나로 셋을 담는지, 셋으로 나누는지 정해 달라.
- VZ-U-08은 가시화에서 배치·구현 시기가 미정이고, "승인 정보의 계약을 AI 파트와 합의하기 전에는 구현하지 않는다"로 걸려 있다. BE-* 신설 여부는 백엔드·팀 판단에 맡긴다.

<a id="q9"></a>

### 2-9. `seq` 비연속 — 확인

확인했다. 가시화는 서버 `seq` 간격으로 유실을 판단하지 않는다.
