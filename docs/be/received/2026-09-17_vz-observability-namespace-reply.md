## ① 한 장 요약

- 관측 스택에 지표를 내는 쪽이 하드웨어(`hw.`)·백엔드(`be.`)에 가시화까지 셋이 돼서, 이름이 겹치지 않게 규약을 미리 알려 온 **통지**다. 질문 문서가 아니다. (§0)
- 🔴는 없다. 제일 높은 것은 🟡 먼저 2건(접두사 `vz.`, 라벨 금지 목록), 그다음 🟡 곧 필요 2건(`service.name`, 발신 대상)이다. (§0)
- 회신은 "이 규약대로 간다" 한 줄이면 된다고 하고, **가시화가 지표 발행을 시작하기 전**에만 읽으면 된다고 한다. (§0, 할 일 5)
- 지금 가시화 코드는 관측 스택에 아무것도 발행하지 않으므로 **당장 부딪히는 코드는 없다.**
- 다만 **발신 경로·주기·접두사**가 우리 요구사항이나 실제 구성과 어긋난다(⑥). 특히 **브라우저에서는 문서가 말한 경로로 보낼 수 없다.** 그래서 회신 한 줄로는 부족했고, 가시화 쪽에서 정할 것 다섯 개를 2026-09-17에 정했다(⑦).

## ② 백엔드가 정한 규약 ★

### 2-A. 지표 이름 (§1)

| 규칙 | 내용 |
|---|---|
| 접두사 | 가시화는 **`vz.`**(하드웨어 `hw.`, 백엔드 `be.`와 같은 방식). `system.cpu.utilization` 같은 OTel 표준 이름은 접두사 없이 그대로 |
| 표기 | **점(`.`)으로 구분한 소문자.** `_`는 직접 넣지 않는다. 수집기(Collector)가 Prometheus로 넘길 때 `_`로 바꾸고 `_total`을 붙인다 |
| 단위 | 이름에 넣지 않고 **OTel `unit` 필드로** 준다(`ms`·`s`·`By`·`1`). ⚠ gauge에 `unit="1"`을 주면 이름 끝에 `_ratio`가 붙는다 |
| 계기 종류 | 늘기만 하는 값은 counter(재기동하면 0부터), 오르내리는 값은 UpDownCounter, 마지막 값은 gauge |
| 백엔드의 읽기 | VZ-O-04는 가시화의 **자기 관측**이다. 장치·업무 값은 백엔드가 이미 내므로(`be.telemetry.*`) 가시화가 다시 내지 않는다 |

### 2-B. 라벨 (§2)

| ⛔ 금지 라벨 | 이유 |
|---|---|
| `session_id` | 재기동할 때마다 새 값 |
| `sequence_id` · `internal_seq` | 메시지마다 다르다 |
| 시각(`timestamp`·`ts`·`capture_timestamp` 등) | 매번 다르다 |
| 프레임 식별자(`frame_id`·`frame_ref` 등) | 프레임마다 다르다 |
| `command_id` · `correlation_id` | 명령마다 다르다(trace 속성으로는 써도 된다) |

- **허용 예:** `component`, `outcome`(`ok`/`fail`), `channel`, `zone_id`.
- `source_id`는 장치별 지표에만 쓰고, **자기 관측 지표에는 붙이지 않는다.**
- 백엔드는 금지 라벨이 들어오면 코드에서 `ValueError`로 거부한다. 가시화도 보내기 전에 같은 검사를 하라고 권한다.

### 2-C. `service.name` (§3)

- 가시화는 컴포넌트마다 **`vz-<컴포넌트>`**, `service.namespace=mk2`로 적는다. 문서의 예는 `vz-viewer`·`vz-twin`·`vz-console`이다.
- ⚠ Prometheus에서 `service.name`은 `job`이 아니라 `exported_job`으로 보인다. 그래서 지표에서 컴포넌트를 가르려면 **`component` 라벨을 직접 붙이는 편이 안전하다.**

### 2-D. 발신 대상 (§4)

| 항목 | 값 |
|---|---|
| 프로토콜 | **OTLP gRPC만.** HTTP(4318)는 열려 있지 않다 |
| 주소 | 서버 안에서 돌면 `127.0.0.1:4316`. 서버 밖이면 Phase 4에 열릴 `<서버 tailscale IP>:4316`(TLS·인증은 BE-T-08) |
| 하지 말 것 | Prometheus(7861)·Loki(3100)·Tempo(4317) 저장소에 직접 쓰기 |
| 주기 | metric export **15초**("HW·백엔드와 같다"고 적음) |
| 장애 시 | 수집기가 죽어도 가시화는 멈추면 안 된다. SDK나 주소가 없으면 아무것도 안 하고 넘어간다(no-op) |

## ③ 답해야 할 것

회신 형식은 "이대로 간다" 한 줄, 다른 게 필요하면 항목과 이유를 적어 달라는 것이다(할 일 5). 문서에는 항목별 기본값이 따로 없고, 전체 기본값 하나만 있다: "백엔드는 `be.`만 쓰니 충돌은 없다. 다만 가시화가 접두사 없이 내면 나중에 분리하기 어렵고, 그 비용은 가시화 쪽에서 난다."

| 우선 | 항목 | 백엔드 규약 | 그대로 받으면 되나 | 절 |
|---|---|---|---|---|
| 🟡 먼저 | 접두사 | `vz.` | ✅ 받았다. 우리 정의서의 `viz.*`는 `vz.*`로 고쳤다(⑥-1) | §1 |
| 🟡 먼저 | 금지 라벨 | 목록 5종 | △ 우리 쪽 식별자가 목록에 없다(⑥-5) | §2 |
| 🟡 곧 필요 | `service.name` | `vz-<컴포넌트>` | △ 문서 예시가 우리 실제 구성과 다르다(⑥-4) | §3 |
| 🟡 곧 필요 | 발신 대상 | 수집기 `127.0.0.1:4316`, gRPC | ❌ 브라우저에서는 이 경로로 못 보낸다(⑥-3) | §4 |
| — | 주기 | 15초 | ❌ VZ-O-04 원문은 60초(⑥-2) | §4 |
| ⚪ 정보 | 충돌 실측 | `vz_` 접두사 0건 | 받기만 하면 된다 | §5 |

## ④ 답변 말고 해야 할 일

**지금은 없다.** 문서도 가시화가 발행을 시작하기 전에만 읽으면 된다고 한다.

발행을 붙일 때 할 일은 원문 「가시화가 할 일」 1~4다: `vz.` 이름, 보내기 전 라벨 검사, `service.name`, 수집기 발신과 장애 시 no-op. 세부는 ⑦에서 정한 대로 한다(접두사 `vz.`, 60초, 브라우저는 OTLP/HTTP, 컴포넌트 셋, 우리 식별자도 금지 라벨).

- 가시화가 **무엇을** 계측할지도 대상이 아니다 — VZ-O-04의 몫이다. (§0)

## ⑥ 요구사항·실제 구성과 어긋나는 것

### 6-A. 지금 코드 상태 (대조 기준)

- OTel SDK가 없고 **관측 스택으로는 아무것도 발행하지 않는다.** 화면에도 「관측 스택 발행 — 연결 예정」으로 뜬다 ([observability.ts:308](../viz-debugger/src/shared/observability.ts#L308)).
- **60초 창 집계는 이미 한다.** 기록 발생률, 로그 용량, 되감기 계산 시간, 수신 지연, 재연결, JS 메모리, 알림 병합을 재서 개발자 패널과 JSON(논문 측정축 D)으로 내보낸다 ([observability.ts](../viz-debugger/src/shared/observability.ts)).
- 옛 대시보드 이식본은 60초마다 **목 게이트웨이**의 `/observability/client-metrics`로 JSON을 POST한다. 게이트웨이는 메모리에 20개만 들고 있다 ([selfObservability.ts](../viz-debugger/src/tabs/data/selfObservability.ts), [server.ts:300](../viz-debugger/gateway/server.ts#L300)).
- 지표 이름은 OTel 형식이 아니라 필드 이름(camelCase)이고, 라벨은 없다.
- 정의서에 적힌 음성 지표(`vz.stt.latency` 등)는 아직 코드에 없다.

### 6-B. 어긋나는 곳
