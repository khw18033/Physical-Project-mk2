# 변경 작업 가이드 — 요구사항·설계가 추가/변경될 때

이 문서는 **요구사항이나 설계·공통 규격이 추가·변경될 때 어떻게 작업하는가**를 담는다. 상황에 맞는
시나리오를 찾아, 거기 적힌 파일을 새 채팅방에 첨부하고 적힌 프롬프트로 시작하면 된다. 세 시나리오
각각이 독립적으로 완결돼 있으므로, 자기 상황에 맞는 하나만 봐도 된다.

지금까지의 진행은 **아키텍처 설계 → 저장소 기반 만들기 → Phase별 구현**이었다. 요구사항·설계
변경은 이 흐름의 앞쪽(설계층)을 다시 건드리는 일이므로, "다음 Phase 구현"과는 성격이 다르다.
그래서 챙기는 파일도 다르다.

---

## 0. 공통 원리 (세 시나리오 모두에 적용)

1. **요구사항 정의서 엑셀은 4개 파트(조병현·이대규·진나영·김현우)가 한 파일이다.** 전체 엑셀을
   주면 내 파트와 팀원 파트가 모두 포함된다. 단, 엑셀만으로는 "무엇이 바뀌었는지"를 알 수 없으므로
   **변경분 설명(텍스트, 또는 새 엑셀과 함께)이 반드시 따라붙어야 한다.**

2. **먼저 "층위"를 가른다.** 변경이 (a) 요구사항 텍스트만 바뀐 것인지, (b) 아키텍처·규격 구조를
   바꾸는 것인지 판단한다. 대부분은 (a)이며, 이 경우 `requirement-traceability.md`·
   `01-standalone-implementation-plan.md`만 갱신하고 아키텍처·규격은 건드리지 않는다. (b)일 때만
   `00-architecture.md`·`contracts/`까지 갱신한다. ("아키텍처 결정 층위의 변경 0"과 "요구사항
   텍스트 층위의 변경"은 별개다 — 텍스트가 바뀌어도 구조는 그대로일 수 있다.)

3. **공통 규격(`contracts/common/`)을 건드리는 변경은 팀 전체에 파급된다.** 공통 헤더·식별자·frame_ref는
   조병현·진나영·김현우가 모두 따르는 기준이다(AI-C-01 등이 "백엔드 규격을 따른다"고 명시). 규격을
   바꾸면 세 파트 전부에 영향이 가므로, 갱신안에 "규격 변경 = 팀 전체 파급"을 명확히 표시하고 팀
   합의를 거친다. 혼자 바꾸지 않는다.

4. **이 작업은 "설계 반영"이다.** 산출물은 코드가 아니라 기준 문서(아키텍처·규격·계획·추적표)의
   갱신안이다. 반영이 끝나 기준 문서를 커밋한 뒤, 그것을 코드로 만드는 것은 그다음 **평소 Phase
   흐름**(고정 세트 + 작업 지시서 뽑기 → VS Code 구현)을 따른다. 즉 변경 작업은 "설계층으로 잠시
   올라갔다가, 갱신이 끝나면 다시 구현으로 내려오는" 두 단계다.

## 2. 시나리오 1 — 내(백엔드) 요구사항이 추가/변경됐을 때

내 BE-* 요구사항 자체가 바뀐 경우다. 내 파트 기준 문서에 반영한다.

**새 채팅방에 첨부할 파일**
- `docs/be/requirement-traceability.md` — 기존 47건 중 무엇이 바뀌는지 대조하는 1차 도구.
- `docs/be/01-standalone-implementation-plan.md` — 어느 Phase에 들어가는지, 이미 진행한 Phase에
  영향을 주는지.
- `docs/be/00-architecture.md` — 변경이 구조에 닿는지 판단하는 근거.
- `docs/be/02-media-path.md` — 변경이 영상·미디어에 닿을 때.
- `contracts/common/message.schema.json` — 변경이 공통 헤더·식별자에 닿을 때.
- `contracts/common/frame-reference.schema.json` — 변경이 frame_ref에 닿을 때.
- `contracts/common/README.md` — 위 규격을 건드릴 때 함께.
- `CLAUDE.md` — 변경이 절대 원칙과 충돌하는지 확인.
- `reports/`의 관련 Phase 보고서 — 변경이 이미 구현된 Phase에 영향을 줄 때.
- `infra/README.md` — 변경이 인프라·스택에 닿을 때.
- **[별도 첨부]** 전체 요구사항 엑셀 + **변경분 텍스트**(어느 BE-* 항목이 어떻게 바뀌는지).

**첫 프롬프트**
> 내 백엔드 요구사항이 바뀌었어(변경분 첨부 + 전체 엑셀). 첨부한 기존 문서를 기반으로, 먼저 이
> 변경이 (a) 요구사항 텍스트만 바뀐 것인지 (b) 아키텍처·규격 구조를 바꾸는 것인지 판단해줘.
> `requirement-traceability.md`로 기존 47건 중 무엇이 바뀌는지 대조하고 — 텍스트만이면
> traceability·plan 갱신안만, 구조를 바꾸면 `00-architecture.md`·`contracts/` 갱신안까지 만들어줘.
> 이미 구현된 Phase(예: Phase 1)에 영향을 주면 짚어줘. 공통 규격(공통 헤더·식별자·frame_ref)을 건드리면 팀
> 전체 파급이라 반드시 표시해. 지금은 설계 반영 단계지 코드 구현이 아니야.

**반영 후:** 나온 갱신안을 검토해 기준 문서에 반영하고 커밋한다. 그 요구사항을 실제 코드로 만드는 것은
그다음 평소 Phase 흐름을 따른다(구현할 Phase에서 작업 지시서를 뽑아 VS Code에서 구현).

## 3. 시나리오 2 — 팀원 요구사항이 추가/변경됐을 때

조병현·진나영·김현우 중 누군가의 요구사항이 바뀐 경우다. **먼저 그 변경이 내 백엔드에 영향을
주는지부터 판단한다** — 바뀐 팀원 항목이 내 BE-*나 공통 규격과 연관점으로 걸리는지 본다. 안 걸리면
내 파트는 반영하지 않는다(그 팀원 브랜치의 일). 걸리면 그 연결점만 내 기준 문서에 반영한다.

**새 채팅방에 첨부할 파일**
- `docs/be/requirement-traceability.md` — 팀원 변경이 내 47건 중 무엇과 걸리는지 대조.
- `docs/be/00-architecture.md` — 걸리는 지점이 내 구조의 어디인지 판단.
- `docs/be/01-standalone-implementation-plan.md` — 그 영향이 어느 Phase에 닿는지.
- `docs/be/02-media-path.md` — 팀원 변경이 영상·미디어 경로와 걸릴 때.
- `contracts/common/message.schema.json` — 팀원 변경이 공통 헤더·식별자를 참조·요구할 때.
- `contracts/common/frame-reference.schema.json` — frame_ref와 걸릴 때.
- `contracts/common/README.md` — 위 규격이 관련될 때 함께.
- `CLAUDE.md` — 걸리는 변경이 내 원칙과 충돌하는지.
- `reports/`의 관련 Phase 보고서 — 이미 구현된 내 코드에 영향을 줄 때.
- `infra/README.md` — 인프라와 걸릴 때.
- **[별도 첨부]** 전체 요구사항 엑셀 + **변경분 텍스트**(어느 팀원의 무슨 항목이 어떻게 바뀌는지).
- **[걸릴 때만]** 바뀐 팀원의 브랜치 파일 중 관련된 것 — 예: 조병현 규격 관련이면
  `pi/common/schema.py`, 진나영 규격 정합이면 `contracts/ai/` 관련 파일.

**첫 프롬프트**
> 팀원(누구인지 명시) 요구사항이 바뀌었어(변경분 첨부 + 전체 엑셀). 이게 내 백엔드에 영향을
> 주는지부터 판단해줘 — 바뀐 팀원 항목이 내 BE-* 규격·연관점에 걸리는지 확인하고, 안 걸리면 '내
> 파트 반영 불필요'로 결론 내줘. 걸리면 그 연결점이 내 아키텍처·규격·plan·traceability 중 무엇을
> 건드리는지, 텍스트 층위인지 구조 층위인지 판단해서 갱신안을 만들어줘. 특히 그 항목이 내 공통
> 규격(공통 헤더·frame_ref)을 참조하면 규격 파급이니 표시해. 지금은 설계 반영 단계야.

**반영 후:** 내 기준 문서에 반영할 게 있으면 갱신·커밋한다. 코드 반영이 필요하면 그다음 평소 Phase
흐름을 따른다. 규격이 걸린 변경이면 팀과 합의된 내용인지 먼저 확인한다.

## 4. 시나리오 3 — 설계·공통 규격 자체를 바꾸거나 추가할 때

요구사항이 아니라 내가 직접 아키텍처·규격 결정을 바꾸려는 경우다(예: 저장 방식 변경, 채널 추가,
공통 헤더 항목 추가·수정, 미디어 경로 변경). 요구사항 대조가 아니라 **기준 문서 수정과 파급 분석**이
중심이다.

**새 채팅방에 첨부할 파일**
- `docs/be/00-architecture.md` — 바꿀 대상 기준 문서(최우선).
- `contracts/common/message.schema.json` — 공통 헤더·식별자를 바꿀 때.
- `contracts/common/frame-reference.schema.json` — frame_ref를 바꿀 때.
- `contracts/common/README.md` — 규격을 바꿀 때 함께(적용 범위 정책·버전).
- `contracts/common/examples/envelope-valid.json` — 공통 헤더를 바꾸면 예제도 함께 갱신 대상.
- `docs/be/02-media-path.md` — 미디어 설계를 바꿀 때.
- `docs/be/01-standalone-implementation-plan.md` — 변경이 Phase 순서·이월에 미치는 영향.
- `docs/be/requirement-traceability.md` — 이 설계 변경이 어느 BE-* 요구사항에 걸리는지 역방향 확인.
- `CLAUDE.md` — 변경이 절대 원칙과 충돌하는지(성격별 저장 분리·데이터 성격이 채널 결정·Kafka는 장기저장
  아님 등).
- `reports/`의 관련 Phase 보고서 — 이미 구현된 Phase에 파급되는지.
- `infra/README.md` — 인프라·스택 구성에 닿을 때.
- **[공통 규격·공통 규약을 바꿀 때]** 팀원 3브랜치의 관련 파일 — 그 규격을 쓰는 부분(파급 확인용).
- **[별도 첨부]** 바꾸려는 내용 설명 텍스트.

**첫 프롬프트**
> 설계/규격을 바꾸려고 해(변경 내용 첨부). 첨부한 기준 문서를 기반으로, 이 변경이 (a) `CLAUDE.md`
> 절대 원칙과 충돌하는지 (b) 기존 아키텍처 결정·규격과 어떻게 연결·상충하는지 (c) 어느 BE-*
> 요구사항과 이미 구현된 Phase에 파급되는지 분석하고, 영향받는 기준 문서(`00-architecture.md`·
> `contracts/`·`plan`·`traceability`)의 갱신안을 만들어줘. 공통 규격(공통 헤더·식별자·frame_ref)을 바꾸면
> 조병현·진나영·김현우 전부에 파급되니 팀 합의 항목으로 명확히 표시해. 지금은 설계 반영 단계야.

**반영 후:** 갱신안을 검토해 기준 문서에 반영·커밋한다. 규격을 바꾼 경우 팀에 파급 내용을 공유하고
합의한다. 코드 반영이 필요하면 그다음 평소 Phase 흐름을 따른다.

## 5. 세 시나리오 공통 — 반영이 끝난 뒤

1. 나온 갱신안을 검토해 해당 기준 문서 파일에 반영하고 커밋한다(변경분 텍스트가 아니라 기준 문서 자체를
   갱신해야 다음 작업이 그 위에서 이어진다).
2. 변경으로 새 작업이 생기면 `01-standalone-implementation-plan.md`의 해당 Phase 항목이나 "지금
   당장 할 일"에 반영하고, 필요하면 `requirement-traceability.md`의 상태를 갱신한다.
