# 채팅방 진입 가이드 — 설계방 / 구현방 (백엔드 파트)

> 이 문서는 **새 채팅방을 열 때 무엇을 업로드하고 어떻게 진행하는지**를 박아둔 것이다.
> 채팅방은 길어지면 인수인계되거나 Phase마다 새로 열리며, **새 채팅방은 아무것도 기억하지
> 못한다.** 그래서 매번 아래 파일 세트를 업로드해 컨텍스트를 재구성한다. 기억은 사람이 아니라
> 파일(`docs/be/` + 계약 + 코드 + 직전 `reports/`)이 들고 있다.
>
> 채팅방은 두 종류다: **설계방**(무엇을 어떻게 만들지 정해 작업 지시서를 뽑는 곳, §1)과
> **구현방**(실제 코드를 짜거나 고치는 곳, §2). 주는 파일이 다르다 — 설계는 문서·계약이면
> 되지만, 구현은 거기에 **실제 코드 파일**까지 필요하다. (구현은 원래 VS Code Claude Code가
> 맡는다. 채팅방 구현은 "한 조각을 깊게" 할 때의 보조 수단이다 — §2-C.)

작성: 이대규 / 대상: 백엔드(BE) 파트 설계·구현 루프

---

## 0. 이 프로젝트의 작업 방식 한눈에

**설계는 채팅방에서, 구현은 VS Code에서.** 세 장소가 원을 돈다.

```
  ┌────────────────────────────────────────────────────────────────┐
  │                                                                │
  ▼                                                                │
[설계 채팅방]  ──작업 지시서 파일──▶  [작업 폴더(git repo)]  ──▶  [VS Code Claude Code]
 (파일 업로드로       = 인수인계            = docs·reports·code           = 구현
  맥락 재구성)                                    ▲                         │
  ▲                                              │                         │
  └──────직전 reports/ 를 다시 업로드◀───────reports/ 에 기록◀────────────┘
```

한 바퀴 = 한 작업 단위(대략 Phase 하나 또는 그 일부). 채팅방에 무슨 파일을 올릴지는 설계방이
§1, 구현방이 §2. 한 사이클의 6단계 흐름은 §3.

## 1. 새 설계 채팅방을 열 때 업로드할 파일

### 1-A. 고정 세트 — 매번 무조건 업로드 (9개)

이 아홉 개는 어떤 Phase를 설계하든 항상 준다. 이것이 "백엔드 파트의 기억" 전체다.

## 2. 구현방을 열 때 업로드할 파일 (채팅방에서 코드를 짤 때)

**설계방과 무엇이 다른가:** 설계방은 "무엇을 어떻게 만들지" 정하는 곳이라 문서·계약이면 됐다.
**구현방은 실제 코드를 짜거나 고치는 곳**이라, 지금 repo에 **이미 있는 코드 파일**까지 봐야
한다. VS Code Claude Code는 repo 폴더를 통째로 자동으로 읽지만, 채팅방은 **네가 준 파일만**
본다. 그래서 **이번 작업이 실제로 건드리는 코드 + 그 코드가 의존하는 코드**를 손으로 골라
올려야 한다.

핵심 원리: **"이 파일 없이 코드를 정확히 짤 수 있나?" → 없으면 준다.** repo 전체를 통째로 올리지
않는다(파일이 많아 맥락이 흐려지고 채팅방 업로드 한계에 걸린다). 그 작업에 실제로 쓰이는 것만.

### 2-A. 3층으로 고른다

**1층. 규칙·맥락 — 항상 (3~4개)**

1. **`CLAUDE.md`** — 코드 규약(`implements:` 태그·폴더 구조·절대 원칙 15개·금지 사항).
2. **`docs/be/tasks/작업지시_phaseN.md`** — 이번에 무엇을 구현하는지(제일 중요).
3. **`docs/be/00-architecture.md`** — 왜 이 구조인지(구현이 아키텍처를 어기면 안 됨).
4. (미디어 Phase면) **`docs/be/02-media-path.md`**.

**2층. 계약 — 코드가 계약을 다루면 (필요 시)**

- **`contracts/common/message.schema.json`**, **`frame-reference.schema.json`** — 봉투·frame_ref를
  다루는 코드면 필수(필드명·구조를 정확히 맞춰야 함). Phase 1·5·6·7은 거의 필요.

**3층. ★ 실제 코드 파일 — 그 작업이 건드리는 것 전부 (구현방의 핵심)**

지금 repo에 이미 있는 코드 중, 이번 작업이:
- **수정할 파일** — 고칠 대상.
- **의존하는 파일** — 그 파일이 import·참조하는 것(안 주면 시그니처를 모른다).
- **연동할 상대 파일** — 새 코드가 붙을 상대(예: `ingest`가 넘길 `gateway` 인터페이스).
- **`infra/docker-compose.yml`** — 인프라에 붙는 작업이면(포트·서비스 이름을 알아야 붙는다).

**참고:** 직전 `reports/*.md`(앞에서 무엇이 어떻게 됐는지).

### 2-B. Phase별 예시 — Phase 1 구현을 채팅방에서 한다면

- 1층: `CLAUDE.md` · `docs/be/tasks/작업지시_phase1.md` · `docs/be/00-architecture.md`
- 2층: `contracts/common/message.schema.json` (봉투 검증)
- 3층(실제 코드):
  - `infra/docker-compose.yml` (Phase 0 산출 — Kafka·Mosquitto가 어느 포트로 뜨는지)
  - `backend/ingest/` 에 이미 만든 코드가 있으면 그것
  - 조병현 `sensor_node.py` · `config.py` · `schema.py` (붙일 발행자 + 그게 쓰는 설정·스키마)
- 참고: 직전 `reports/....phase0....md`

### 2-C. 언제 채팅방 구현이 낫고, 언제 VS Code가 나은가

구현을 통째로 채팅방에서 하는 것은 파일 고르기가 번거롭다. VS Code Claude Code는 이 고르기를
자동으로 해주는 것이 최대 장점이다. 그래서 섞어 쓴다.

| 채팅방 구현이 좋은 것 | VS Code가 나은 것 |
|---|---|
| 한 파일짜리 로직(예: "봉투 검증 함수 하나 짜줘") | 여러 파일에 걸친 작업 |
| 알고리즘·정규식·쿼리 같은 조각 | 파일 간 import·연동 |
| "이 코드 왜 이래?" 리뷰·디버깅 | repo 전체 맥락이 필요한 것 |
| 설계 겸 프로토타입 한 조각 | 실제 통합·실행 |

**한 조각을 깊게 파고 싶을 때는 채팅방, 여러 파일을 실제로 엮을 때는 VS Code.** 채팅방에서 만든
조각은 결과를 VS Code로 가져가 repo에 붙인다.

## 3. 작업 흐름 6단계 (한 사이클)

### 단계 1 — 설계방에서 "무엇을 어떻게" 뽑기

- §1의 파일 세트를 업로드하고, 첫 메시지로 "이번엔 Phase N을 설계하자"(또는 직전 보고서
  첨부하며 "Phase N-1 끝났고 Phase N 지시서 뽑자")라고 연다.
- 설계방이 그 Phase를 **어떻게 구현할지** 정하고 → **작업 지시서 한 장**으로 뽑는다.
- 작업 지시서에 담기는 것: 대상(Phase N·근거 문서) / 배경(왜 지금) / 제약(반드시 지킬 것) /
  단계 + 각 단계 DoD / 이번에 하지 않는 것 / 완료 판정(체크리스트) / **보고 항목(§단계 5)**.

### 단계 2 — 작업 지시서를 작업 폴더에 넣기

- 뽑은 작업 지시서를 repo에 커밋한다. **위치: `docs/be/tasks/작업지시_phaseN.md`** (tasks 폴더가
  없으면 만든다).
- `git add . && git commit -m "docs: Phase N 작업 지시서" && git push`.
- **"작업 폴더로 옮긴다" = git commit.** 이 순간 설계 결과가 repo에 박혀 VS Code가 볼 수 있다.

### 단계 3 — VS Code Claude Code가 읽고 구현

- VS Code에서: **"CLAUDE.md랑 docs/be/tasks/작업지시_phaseN.md 읽고 그대로 구현해줘."**
- Claude Code가 CLAUDE.md(상시 규칙) + 작업 지시서(이번 태스크)를 읽고 코드를 만든다. 설계는
  이미 문서로 나와 있으므로 새로 설계하지 않고 지시서 범위대로 구현한다(plan 모드 토글 불필요).
- 일부를 채팅방에서 구현하고 싶으면(한 조각 로직·리뷰·디버깅) 구현방을 열고 §2의 파일 세트를
  올린다. 여러 파일을 엮는 작업은 VS Code가 낫다(§2-C).

### 단계 4 — 구현이 코드로 저장됨

- Claude Code가 만든 결과가 repo 파일로 생긴다(예: Phase 0이면 `infra/docker-compose.yml`).
- 커밋·push. **구현 실체는 "코드 파일 자체"에 저장된다.**

### 단계 5 — 기록이 두 곳에 갱신됨 (작업 지시서 "보고" 항목이 트리거)

작업 지시서 맨 끝의 **"보고" 항목**이 Claude Code에게 이걸 시킨다(CLAUDE.md의 규약과 합쳐져
사실상 자동으로 이어짐):

- **(A) `reports/YYYY-MM-DD_HHMM_phaseN.md` — 새로 생성.** 배경 / 한 일 / 검증 / **다음**.
  마지막 "다음"이 다음 사이클의 씨앗.
- **(B) `docs/be/requirement-traceability.md` — 해당 행 갱신.** 이번 Phase가 건드린 BE-* 요구사항의
  상태·구현 위치·테스트를 갱신(예: `미착수 → 부분`).

둘 다 커밋·push. (만약 Claude Code가 코드만 만들고 멈추면 "CLAUDE.md 규약대로 reports 남기고
traceability 갱신해줘" 한 줄로 리마인드.)

### 단계 6 — 다시 처음으로 (원이 닫힘)

- Phase N 끝. 다음은 Phase N+1.
- **직전 `reports/*.md`를 들고** 새 설계 채팅방을 연다(§1-A 고정 세트 + 이 보고서 + Phase N+1
  관련 파트 자료).
- 첫 메시지: "Phase N 끝났고(보고서 첨부), Phase N+1 작업 지시서 뽑자." → 단계 1로 복귀.

> **핵심:** traceability.md가 갱신돼 있으니 새 설계방은 그것만 봐도 전체 진행 상태를 안다.
> reports는 "직전에 구체적으로 뭘 했나", traceability는 "전체가 얼마나 채워졌나". 이 둘이 새
> 채팅방의 기억을 복원한다.

## 4. 파일별 역할 (누가 무엇을 기록하나)

| 파일 | 역할 | 언제 갱신 |
|---|---|---|
| `CLAUDE.md` | 상시 규칙집. 매 구현 세션이 읽음 | 거의 안 바뀜(규칙 바뀔 때만) |
| `docs/be/00-architecture.md` | 아키텍처 정본 | 구조 결정 바뀔 때만 |
| `docs/be/02-media-path.md` | 미디어 경로 정본 | 미디어 결정 바뀔 때만 |
| `docs/be/01-...plan.md` | Phase 순서·"지금 당장 할 일" | Phase 진행하며 체크박스 갱신 |
