# 설계방 진입 가이드 (백엔드 파트)

> 이 문서는 **새 설계 채팅방을 열 때 무엇을 업로드하고 어떻게 진행하는지**를 박아둔 것이다.
> 설계 채팅방은 길어지면 인수인계되거나 Phase마다 새로 열리며, **새 채팅방은 아무것도 기억하지
> 못한다.** 그래서 매번 아래 파일 세트를 업로드해 컨텍스트를 재구성한다. 기억은 사람이 아니라
> 파일(`docs/be/` + 계약 + 직전 `reports/`)이 들고 있다.

작성: 이대규 / 대상: 백엔드(BE) 파트 설계·구현 루프

---

## 0. 이 프로젝트의 작업 방식 한눈에

**설계는 채팅방에서, 구현은 VS Code에서.** 세 장소가 원을 돈다.

```
  ┌────────────────────────────────────────────────────────────────┐
  │                                                                │
  ▼                                                                │
[설계 채팅방]  ──작업 지시서 파일──▶  [작업 폴더(git repo)]  ──▶  [VS Code Claude Code]
 (파일 업로드로       = 인수인계            = docs·reports·code           = 구현
  맥락 재구성)                                    ▲                         │
  ▲                                              │                         │
  └──────직전 reports/ 를 다시 업로드◀───────reports/ 에 기록◀────────────┘
```

한 바퀴 = 한 작업 단위(대략 Phase 하나 또는 그 일부). 아래 §2에 6단계로 상세.

## 1. 새 설계 채팅방을 열 때 업로드할 파일

### 1-A. 고정 세트 — 매번 무조건 업로드 (9개)

이 아홉 개는 어떤 Phase를 설계하든 항상 준다. 이것이 "백엔드 파트의 기억" 전체다.

**상시 문서 (repo 경로 → 무엇인가):**

1. **`CLAUDE.md`** (루트)
   — 구현 규칙집. 폴더 구조·`implements:` 태그·절대 원칙 15개·금지 사항·작업 방식. 설계할 때
   "무엇을 지켜야 하는가"의 기준.
2. **`docs/be/00-architecture.md`**
   — 아키텍처 정본. 5구간 구조와 각 결정의 근거(반증·정직한 약점·예상 질문). "왜 이 구조인가".
3. **`docs/be/01-standalone-implementation-plan.md`**
   — 구현 착수 계획. Tier A/B/C 분류 + Phase 0~7 순서 + 각 Phase DoD + "지금 당장 할 일".
   **"이번에 무슨 Phase를 하는가"의 출발점.**
4. **`docs/be/02-media-path.md`**
   — 미디어 경로 정본(4구간·frame_ref·버킷 A/B). 미디어와 무관한 Phase에도 넣어둔다(경로가
   다른 결정과 얽히므로).
5. **`docs/be/requirement-traceability.md`**
   — BE-* 47건 상태표. **"지금까지 뭐가 됐고 뭐가 안 됐는지"를 한눈에.** 새 채팅방이 진행
   상황을 복원하는 핵심.

**파트 간 계약 (repo 경로 → 무엇인가):**

6. **`contracts/common/message.schema.json`**
   — 공통 봉투(9필드). 모든 메시지의 머리. 필드명·필수/선택의 기준.
7. **`contracts/common/frame-reference.schema.json`**
   — frame_ref(탐지 오버레이 정합 근거).
8. **`contracts/common/README.md`**
   — 계약 경계 정책(파트 경계는 JSON Schema다·백엔드 소유권·버전 정책).
9. **`contracts/common/examples/envelope-valid.json`**
   — 봉투 정상 예제. 계약이 실제로 어떤 모양인지.

> 참고: `README.md`(루트)는 위 문서들의 요약이라 설계방 업로드 필수는 아니다. 프로젝트를 처음
> 접하는 사람에게 전체를 빠르게 보여줄 때만 추가.

### 1-B. 그때그때 추가 — 진행 상황·Phase에 따라

고정 세트에 더해, 이번에 설계할 Phase가 무엇이냐에 따라 아래를 골라 추가한다.

**항상 (두 번째 사이클부터):**

- **직전 Phase의 `reports/YYYY-MM-DD_HHMM_*.md`**
  — 바로 앞에서 무엇을 했고 무엇이 미결이며 "다음"이 무엇인지. **원을 닫는 다리.** 첫 사이클
  (Phase 0)에는 아직 없으므로 생략.

**이번 Phase가 특정 파트와 얽힐 때 — 그 팀원 자료:**

- **Phase 1 (파이프라인 관통)** → 조병현 `sensor_node.py` (BE-C-01/02 봉투로 발행하는 실제
  발행자. 가짜 발행자로 붙일 대상). 필요 시 조병현 브랜치 zip.
- **Phase 3 (관측 파이프라인)** → 조병현 `otel_metrics.py` (말단 OTel 계측 5종), 기존
  `docker-compose_260617.yml`·OTel/Grafana 설정.
- **Phase 4 (미디어 경로)** → `docs/be/02-media-path.md`는 이미 고정 세트에 있음. 추가로 MK1
  `media_transport.py` 참고 시.
- **Phase 5 (가용성 판정기)** → 진나영 `simulation/backend.py` (백엔드 가용성 mock — 실물로
  교체할 대상), 조병현 `monitor.py`.
- **Phase 6 (상관·감사·명령)** → 진나영 AI 실패/위험 판정 계약(`contracts/ai/`), 조병현
  `sensor_node.py`의 cmd 4단계.
- **Phase 7 (디지털 트윈)** → 진나영 AI-S/E 관련(연계 신뢰도·카메라 보정), Unity 관련(가시화
  파트 — Tier C).

**인프라 이관이 걸릴 때:**

- 기존 `docker-compose_260617.yml`, Grafana 대시보드, OTel Collector 설정 등 — 서버에 이미
  깔린 것을 파악·재구성할 때(Phase 0·3).

**요구사항 원본을 다시 볼 때:**

- 요구사항 정의서(엑셀) — traceability로 부족해 원문 정의를 확인해야 할 때만.

> 판단 기준: **"이번 Phase의 작업 지시서를 뽑는 데 필요한 것"**만 추가한다. 필요 없는 파트
> 자료까지 다 올리면 맥락이 흐려진다.

## 2. 작업 흐름 6단계 (한 사이클)

### 단계 1 — 설계방에서 "무엇을 어떻게" 뽑기

- §1의 파일 세트를 업로드하고, 첫 메시지로 "이번엔 Phase N을 설계하자"(또는 직전 보고서
  첨부하며 "Phase N-1 끝났고 Phase N 지시서 뽑자")라고 연다.
- 설계방이 그 Phase를 **어떻게 구현할지** 정하고 → **작업 지시서 한 장**으로 뽑는다.
- 작업 지시서에 담기는 것: 대상(Phase N·근거 문서) / 배경(왜 지금) / 제약(반드시 지킬 것) /
  단계 + 각 단계 DoD / 이번에 하지 않는 것 / 완료 판정(체크리스트) / **보고 항목(§단계 5)**.

### 단계 2 — 작업 지시서를 작업 폴더에 넣기

- 뽑은 작업 지시서를 repo에 커밋한다. **위치: `docs/be/tasks/작업지시_phaseN.md`** (tasks 폴더가
  없으면 만든다).
- `git add . && git commit -m "docs: Phase N 작업 지시서" && git push`.
- **"작업 폴더로 옮긴다" = git commit.** 이 순간 설계 결과가 repo에 박혀 VS Code가 볼 수 있다.

### 단계 3 — VS Code Claude Code가 읽고 구현

- VS Code에서: **"CLAUDE.md랑 docs/be/tasks/작업지시_phaseN.md 읽고 그대로 구현해줘."**
- Claude Code가 CLAUDE.md(상시 규칙) + 작업 지시서(이번 태스크)를 읽고 코드를 만든다. 설계는
  이미 문서로 나와 있으므로 새로 설계하지 않고 지시서 범위대로 구현한다(plan 모드 토글 불필요).

### 단계 4 — 구현이 코드로 저장됨

- Claude Code가 만든 결과가 repo 파일로 생긴다(예: Phase 0이면 `infra/docker-compose.yml`).
- 커밋·push. **구현 실체는 "코드 파일 자체"에 저장된다.**

### 단계 5 — 기록이 두 곳에 갱신됨 (작업 지시서 "보고" 항목이 트리거)

작업 지시서 맨 끝의 **"보고" 항목**이 Claude Code에게 이걸 시킨다(CLAUDE.md의 규약과 합쳐져
사실상 자동으로 이어짐):

- **(A) `reports/YYYY-MM-DD_HHMM_phaseN.md` — 새로 생성.** 배경 / 한 일 / 검증 / **다음**.
  마지막 "다음"이 다음 사이클의 씨앗.
- **(B) `docs/be/requirement-traceability.md` — 해당 행 갱신.** 이번 Phase가 건드린 BE-* 요구사항의
  상태·구현 위치·테스트를 갱신(예: `미착수 → 부분`).

둘 다 커밋·push. (만약 Claude Code가 코드만 만들고 멈추면 "CLAUDE.md 규약대로 reports 남기고
traceability 갱신해줘" 한 줄로 리마인드.)

### 단계 6 — 다시 처음으로 (원이 닫힘)

- Phase N 끝. 다음은 Phase N+1.
- **직전 `reports/*.md`를 들고** 새 설계 채팅방을 연다(§1-A 고정 세트 + 이 보고서 + Phase N+1
  관련 파트 자료).
- 첫 메시지: "Phase N 끝났고(보고서 첨부), Phase N+1 작업 지시서 뽑자." → 단계 1로 복귀.

> **핵심:** traceability.md가 갱신돼 있으니 새 설계방은 그것만 봐도 전체 진행 상태를 안다.
> reports는 "직전에 구체적으로 뭘 했나", traceability는 "전체가 얼마나 채워졌나". 이 둘이 새
> 채팅방의 기억을 복원한다.

## 3. 파일별 역할 (누가 무엇을 기록하나)

| 파일 | 역할 | 언제 갱신 |
|---|---|---|
| `CLAUDE.md` | 상시 규칙집. 매 구현 세션이 읽음 | 거의 안 바뀜(규칙 바뀔 때만) |
| `docs/be/00-architecture.md` | 아키텍처 정본 | 구조 결정 바뀔 때만 |
| `docs/be/02-media-path.md` | 미디어 경로 정본 | 미디어 결정 바뀔 때만 |
| `docs/be/01-...plan.md` | Phase 순서·"지금 당장 할 일" | Phase 진행하며 체크박스 갱신 |
| `docs/be/tasks/작업지시_phaseN.md` | 한 태스크의 설계 결과 = 인수인계 | 태스크마다 새로, 끝나면 아카이브 |
| **코드** (`backend/`·`infra/`·`tests/`) | 구현 실체 | 구현할 때 |
| `reports/YYYY-MM-DD_HHMM_*.md` | "무엇을 했나" 작업 로그 | 태스크 끝날 때마다 새로 |
| `docs/be/requirement-traceability.md` | 요구사항 47건 상태 | 코드 만들 때마다 해당 행 |
| `contracts/common/*` | 파트 경계 계약(정본) | 계약 변경 시(신중히, 팀 합의) |
