# 인터페이스 명세 — 가시화 파트 ↔ 대규(OTel 관측 스택)

**작성일**: 2026-08-18
**작성**: 현우 (가시화)
**상대 파트**: 대규 — OpenTelemetry 기반 관측 스택 백엔드
**근거**: `요구사항정의서.md` v0.2 §6, `260818_회의록.md` §4
**상태**: 초안 제출 — 대규 파트 검토 및 회신 대기

> 회의 §4의 "공통 인터페이스 문서 1개(모듈별 데이터 수신부 / 송신부 명세)"에 붙일
> **가시화 모듈 ↔ 관측 스택 구간**의 시트다. 아래 표는 그대로 통합 시트에
> 붙일 수 있는 구조로 작성했다.
>
> 작성 원칙: **확정된 사실이 아니라 논의 가능한 안(案)** 이다. 회의 §5의 주문
> ("완벽하지 않아도 논의 가능한 안을 가져오면 코멘트를 받을 수 있다")에 따라,
> 특히 아웃바운드는 우리가 필드안을 먼저 제시한다.

## 0. 한 장 요약

| 방향 | 건수 | 핵심 | 늦으면 생기는 일 |
|---|---|---|---|
| **받아야 하는 것** (인바운드) | 8건 | Prometheus 질의 규약 + **계층 식별자 ↔ 라벨 대응 규칙** | 우리 화면이 데이터에 닿지 못한다. 목 데이터로는 Phase 3까지만 간다 |
| **줘야 하는 것** (아웃바운드) | 4건 | **제어 명령 이벤트 스키마(REQ-907/908)** | 양쪽 모두 재작업. 회의 §6.3에서 위험도 "높음"으로 지정된 항목 |

**가장 먼저 확정해야 할 2건**

1. **O-1 제어 명령 이벤트 스키마** — 대규 파트의 OTel 설계와 **동시에** 확정되어야 한다. 우리가 먼저 필드안을 냈으므로 대규 쪽 코멘트만 받으면 된다.
2. **I-2 계층 식별자 ↔ 라벨 대응 규칙** — 이것이 없으면 I-1(질의)을 받아도 쓸 수 없다. Zone/Node/Entity를 라벨로 어떻게 표현할지가 정해지지 않으면 우리는 메트릭을 화면의 어느 컴포넌트에 붙일지 결정할 수 없다.

## 1. 받아야 하는 것 (인바운드 — 대규 → 가시화)

### I-1. Prometheus 질의 인터페이스 및 응답 스키마

- **관련 요구사항**: REQ-702, REQ-701, NFR-005
- **필요한 이유**: F7 DataSource의 첫 구현체다. 우리는 수집기를 만들지 않고 **질의만** 한다(요구사항정의서 §3 제외 항목).
- **받아야 할 항목**

| 항목 | 우리가 필요한 형태 | 비고 |
|---|---|---|
| 엔드포인트 | 접속 주소(환경별: 로컬/개발/운영) | `datasource.schema.json`의 `endpoint`에 그대로 들어간다 |
| 질의 방식 지원 여부 | instant / range / streaming 각각 가능한지 | `capabilities` 3개 불리언에 대응. F8 validator가 이 값으로 파이프라인을 사전 검증한다 |
| 인증 방식 | `none` / `basic` / `bearer` / `mtls` 중 하나 + 시크릿 전달 경로 | **자격 증명 값 자체는 우리 디스크립터에 기록하지 않는다** (시크릿 저장소 참조 키만 받는다) |
| 응답 스키마 | 표준 Prometheus HTTP API 응답 그대로인지, 게이트웨이로 감쌌는지 | 감쌌다면 그 스키마 필요 |
| 질의 제한 | 타임아웃 권장값, 동시 질의 수 제한, rate limit | `defaultTimeoutMs` 기본값 결정에 필요 |
| 보존 기간·해상도 | 원본 유지 기간, 다운샘플링 시점과 간격 | range query의 유효 구간 결정. 그래프 렌더러의 기본 조회 범위가 여기서 나온다 |

### I-2. 계층 식별자 ↔ 메트릭 라벨 대응 규칙 ★

- **관련 요구사항**: REQ-301, REQ-702, REQ-202
- **필요한 이유**: 우리는 Zone / Node / Entity 3단 계층으로 화면을 구성한다(F3). 관측 스택에서 오는 메트릭이 **어떤 라벨로 이 계층에 대응되는지**가 정해져야 "이 메트릭은 화면의 어느 컴포넌트 것인가"를 판정할 수 있다. 규칙이 없으면 F2 자동 프로비저닝과 F3 드릴다운이 둘 다 성립하지 않는다.
- **받아야 할 항목**
  - Resource attribute / 메트릭 라벨의 **명명 규약** (예: `service.name`, `deployment.environment`, 위치·구역을 나타내는 속성 키)
  - 우리 Zone / Node / Entity에 각각 대응하는 속성 키
  - 메트릭 이름 규약(접두어 체계, 단위 표기)
  - 동일 대상이 여러 이름으로 나타날 수 있는지 여부 (별칭 존재 시 정규화 규칙)
- **비고**: 나영 파트의 REQ-201(컨테이너 ID ↔ 디스크립터 ID ↔ Entity ID)과 **같은 문제의 다른 면**이다. 세 파트가 각자 정하면 어긋난다. 가능하면 대규·나영·현우 3자가 한 번에 확정하는 편이 낫다.

### I-3. Grafana 조회 API 및 인증 방식

- **관련 요구사항**: REQ-703 (ADR-003)
- **필요한 이유**: 조사 결과 그라파나는 대체 대상이 아니라 **흡수 대상**으로 판단했다(`docs/research/2026-08-18_grafana-dynamic-datasource.md`). 이미 구축된 대시보드·쿼리 자산을 재작성 없이 소비한다.
- **받아야 할 항목**: Grafana 인스턴스 주소, API 토큰 발급 경로, 기존 대시보드/패널 목록, 대시보드 JSON 조회 가능 여부, 사용 중인 데이터소스 UID 목록
- **우선순위**: 중간 — 그라파나 자산이 아직 없다면 이 항목은 보류해도 무방하다.

### I-4. 스트림(영상·고빈도 텔레메트리) 전송 규약

- **관련 요구사항**: REQ-704, REQ-407, REQ-502
- **필요한 이유**: 폴링 질의로는 영상과 고빈도 텔레메트리를 다룰 수 없다. F7 안에서 push 소스를 1급으로 취급해야 한다.
- **받아야 할 항목**

| 항목 | 내용 |
|---|---|
| 전송 프로토콜 | WebSocket / gRPC / RTSP / HLS 중 무엇인지 |
| 엔드포인트 규약 | 대상별 주소 구성 규칙 |
| 프레임 메타데이터 | 프레임 타임스탬프의 기준 시계(단조 증가 여부, UTC 여부) |
| 백프레셔 정책 | 소비자가 못 따라갈 때 드롭인지 버퍼인지 |
| 재연결 규약 | 끊김 시 재개 방식(마지막 오프셋 기준 재개 가능한지) |

- **비고**: 영상 소스는 하드웨어 파트에서 직접 올 수도 있다. **경유 여부를 대규가 정해줘야** 우리가 어느 쪽과 계약할지 정해진다. (요구사항정의서 §3에는 "본 레이어는 하드웨어에 직접 접촉하지 않고 관측 스택을 경유한다"고 적었으나, 영상은 예외일 수 있다.)

### I-5. 감사 로그 조회 API

- **관련 요구사항**: NFR-002, REQ-907
- **필요한 이유**: 우리는 감사 로그를 **저장하지 않는다**(§3 제외 항목). 그러나 "이 게이트를 마지막으로 조작한 사람이 누구인가"를 화면에 표시하려면 **되읽어야** 한다. 쓰기만 하고 읽지 못하면 책임 소재 추적이 운영 화면에서 확인되지 않는다.
- **받아야 할 항목**: 조회 API 주소, 질의 가능한 필터 축(대상 / 기간 / 발행자 / 발행 경로), 페이징 방식, 조회 권한 모델
- **비고**: O-1에서 우리가 **쓰는** 필드가 여기서 **필터 축으로 조회 가능**해야 한다. 두 항목은 짝이다.

### I-6. 권한·역할 모델

- **관련 요구사항**: NFR-001, REQ-902
- **필요한 이유**: 제어 액션 발행 권한을 RBAC으로 관리해야 한다(NFR-001). 우리는 화면에서 **1차 차단**을 하지만, 역할 정의 자체는 우리가 만들 수 없다.
- **받아야 할 항목**: 역할 목록과 각 역할의 제어 권한 범위, 사용자 신원 확인 방식(SSO / 토큰), 우리 화면이 현재 사용자 역할을 조회하는 API
- **비고**: 최종 검증은 백엔드 책임이다(REQ-906). 우리 쪽 검증은 UX 목적의 사전 차단이다.

### I-7. 시각 기준(clock) 규약

- **관련 요구사항**: REQ-407, REQ-907, REQ-1104
- **필요한 이유**: 영상 프레임 · 메트릭 · 제어 이벤트 세 가지를 한 화면에 겹쳐 표시한다(REQ-504). 시각 기준이 다르면 겹쳐 놓은 것이 서로 다른 순간을 가리킨다.
- **받아야 할 항목**: 타임스탬프의 타임존과 정밀도(ms/µs/ns), NTP 동기화 여부, 서버 시각과 엣지 노드 시각의 차이 허용 범위
- **우선순위**: 중간 — 다만 Phase 3에서 반드시 필요하다.

### I-8. 각 데이터의 추상화 수준·집약 가능성

- **관련 요구사항**: REQ-1101, REQ-1102
- **필요한 이유**: F11(계층적 가시화)은 "원본 → 구성 요소 → 집약 지표"를 선언해야 성립한다. 어떤 메트릭이 이미 집약된 값이고 어떤 것이 원본인지 구분되지 않으면, 우리가 다시 집약해서 **이중 집약**이 발생한다.
- **받아야 할 항목**: 메트릭별 원본/집약 구분, 이미 집약된 경우 집약 함수와 창 크기(rate/avg/sum, window), 원본 데이터에 접근 가능한지 여부
- **비고**: 이것은 대규 혼자의 항목이 아니라 전 파트 대상 질문이다(요구사항정의서 REQ-1101). 다만 데이터가 전부 OTel을 경유하므로 대규가 먼저 답할 수 있다.

## 2. 줘야 하는 것 (아웃바운드 — 가시화 → 대규)

> 회의 §4 수문 예시: "수문 데이터는 Prometheus에 저장되지만, '수문을 열어라'는
> 명령 이벤트가 저장되지 않으면 누가·언제·어디서·어떤 방식으로 의사결정했는지
> 확인할 수 없다." 아래 O-1이 그에 대한 답이다.

### O-1. 제어 명령 이벤트 스키마 ★ (우리가 먼저 내는 안)

- **관련 요구사항**: REQ-907, REQ-908, REQ-1305, NFR-002
- **우리가 발행하는 시점**: F9 제어 액션이 발행될 때마다 1건. 성공/실패와 무관하게 **발행 시도 자체**를 기록한다.
- **제안하는 필드안**

| 필드 | 타입 | 필수 | 내용 | 근거 |
|---|---|---|---|---|
| `event.name` | string | ✔ | 고정값(예: `control.command.issued`) | 이벤트 종류 식별 |
| `event.timestamp` | timestamp | ✔ | 발행 시각 (I-7 규약 준수) | "언제" |
| `command.id` | string | ✔ | 발행 건별 고유 ID. 결과 이벤트와 짝을 맞추는 키 | 상태 반영(REQ-903) |
| `actor.id` | string | ✔ | 발행한 사용자 식별자 | "누가" |
| `actor.role` | string | ✔ | 발행 시점의 역할 | NFR-001과 대조 |
| `origin.path` | enum | ✔ | **`manual` / `voice` / `llm_suggestion` / `auto`** | **REQ-908 — v0.2의 핵심 추가분** |
| `origin.client` | string | ✔ | 발행이 일어난 화면·단말 식별자 | "어디서" |
| `target.zone` / `target.node` / `target.entity` | string | ✔ | 명령 대상 (I-2 라벨 규약과 동일 체계) | "무엇에" |
| `action.id` | string | ✔ | 선언된 제어 액션 식별자(REQ-901) | |
| `action.params` | object | ✔ | 발행한 파라미터 값 | 사후 재현 |
| `action.paramsValid` | bool | ✔ | 클라이언트 1차 검증 통과 여부(NFR-003) | 검증 우회 시도 탐지 |
| `result.status` | enum | | `accepted` / `rejected` / `timeout` / `failed` | REQ-904. 결과 확정 시 후속 이벤트로 발행 |
| `voice.transcript` | string | | 인식된 발화 원문 | **REQ-1305** — `origin.path=voice`일 때 필수 |
| `voice.confidence` | number | | STT 신뢰도 | 오인식 사후 판별 |
| `llm.model` | string | | 제안을 만든 모델 식별자 | `origin.path=llm_suggestion`일 때 필수 |
| `llm.suggestionId` | string | | 제안 단위 ID. 어떤 제안을 수락한 결과인지 | REQ-1204 |
| `llm.userModified` | bool | | 사용자가 제안을 수정한 뒤 수락했는지 | 제안 그대로 수락 ≠ 검토 후 수정 수락 |
| `trace.id` | string | | 상위 추적 ID (OTel trace 연계) | 대규 파트 설계에 맞춤 |

- **대규에게 묻는 것**
  1. 이 이벤트를 **OTel Log Record**로 받을지, **Span Event**로 받을지, 별도 API로 받을지.
  2. 속성 키 명명 규약 — 위 표는 우리 편의로 지은 이름이다. **OTel semantic convention에 맞는 이름이 있으면 그쪽을 따른다.**
  3. `result.status`를 같은 이벤트에 뒤늦게 갱신하는 방식이 가능한지, 아니면 별도 이벤트 2건(발행 / 결과)으로 나눠야 하는지. **후자를 기본으로 가정하고 설계 중이다.**
  4. 필수/선택 구분에 대한 이견.
  5. 보존 기간 — 감사 목적이므로 메트릭보다 길어야 한다고 보는데, 정책이 있는지.

### O-2. LLM·자동 생성 관여 표시

- **관련 요구사항**: REQ-1207, NFR-011
- **내용**: 제어 명령 외에도, LLM이 **가공한 데이터**가 화면에 표시된 경우 그 사실이 기록되어야 한다. 관측된 사실과 모델이 생성한 해석은 로그에서도 구별되어야 한다(NFR-011).
- **줘야 할 것**: LLM 가공 노드(REQ-1205)가 실행될 때의 이벤트 — 입력 데이터 참조, 사용 모델, 생성 결과의 요약, 사용자에게 표시되었는지 여부
- **우선순위**: 낮음 — Phase 4 이후. 다만 **O-1의 스키마를 정할 때 확장 여지를 남겨둬야** 나중에 별도 체계를 또 만들지 않는다.

### O-3. 가시화 레이어 자체의 텔레메트리

- **관련 요구사항**: NFR-004, NFR-008, NFR-009
- **내용**: 우리 앱 자체의 상태(대시보드 반영 지연, 노드 편집기 응답성, LLM 호출 지연·실패율)를 OTel로 내보낼 수 있다. 성능 목표 수치(NFR-004/008)를 **측정 가능하게** 만드는 유일한 경로다.
- **묻는 것**: 프런트엔드에서 직접 OTel로 내보내는 것을 허용하는지, 아니면 게이트웨이를 경유해야 하는지. 브라우저용 수집 엔드포인트(CORS 포함)가 제공되는지.
- **우선순위**: 낮음 — 다만 **비용이 거의 없고 성능 요건 검증에 직결**되므로 조기 합의 시 이득이 크다.

### O-4. 우리가 등록한 DataSource 디스크립터 목록

- **관련 요구사항**: REQ-701, F8
- **내용**: 우리가 어떤 소스를 어떤 질의 방식으로 소비 중인지를 담은 디스크립터(`contracts/datasource.schema.json` 형식)를 대규 파트에 공유한다.
- **필요한 이유**: 대규 쪽에서 **부하 예측과 라벨 변경의 영향 범위 파악**이 가능해진다. 스키마를 바꿀 때 무엇이 깨지는지 우리에게 묻지 않고도 알 수 있다.
- **우선순위**: 낮음 — 파일 공유만으로 성립한다. 계약 협의가 아니라 통보 항목이다.

## 3. 합의 순서 및 위험도

| 순서 | 항목 | 위험도 | 사유 | 지연 시 우회 |
|---|---|---|---|---|
| 1 | **O-1** 제어 명령 이벤트 스키마 | **높음** | 대규의 OTel 설계와 동시 확정 필요. 늦으면 양쪽 재작업 | 우회 불가. Phase 6 착수 조건이다 |
| 2 | **I-2** 계층 ↔ 라벨 대응 | **높음** | 없으면 I-1을 받아도 화면에 붙일 수 없음 | 임시 규약을 우리가 정해 진행 후 교체 (교체 비용 발생) |
| 3 | I-1 Prometheus 질의 | 중간 | 표준 API면 추정 가능 | 로컬 Prometheus로 대체 진행(계획서 Phase 3) |
| 4 | I-5 / I-6 감사 조회 · 권한 | 중간 | Phase 6에 필요 | 목 데이터로 화면만 선행 |
| 5 | I-4 스트림 규약 | 중간 | Phase 3 미디어 파이프라인의 전제 | 로컬 영상 파일로 대체 |
| 6 | I-7 시각 기준 | 낮음 | 관례적 기본값(UTC, ms) 가정 가능 | 가정 후 진행, 어긋나면 보정 |
| 7 | I-3 / I-8 / O-2 / O-3 / O-4 | 낮음 | 후속 Phase | 보류 가능 |

> **1·2번이 회의 §4에서 지목된 "통합 시 불일치" 리스크의 실체다.** 나머지는 전부
> 우회 경로가 있다 — REQ-204(이벤트 소스 부재 시 정적 구성 동작)를 요구사항에
> 넣어둔 이유가 이것이다. **우리 파트는 대규 파트의 진척에 블로킹되지 않는다.**

## 4. 대규에게 보내는 질문 목록 (회신 요청)

1. 제어 명령 이벤트를 **OTel Log / Span Event / 별도 API** 중 무엇으로 받겠는가? (O-1)
2. 위 필드안 중 **빼야 할 것 / 이름을 바꿔야 할 것**이 있는가? 특히 OTel semantic convention에 이미 대응 이름이 있는 필드. (O-1)
3. 발행 이벤트와 결과 이벤트를 **2건으로 나누는 것**에 동의하는가? (O-1)
4. Zone / Node / Entity를 **어떤 resource attribute·라벨로 표현**할 것인가? 나영 파트의 컨테이너 식별자 체계와는 어떻게 잇는가? (I-2)
5. 감사 로그를 **되읽는 API**를 제공할 계획이 있는가? 없다면 우리 화면은 "누가 마지막으로 조작했는지"를 표시할 수 없다. (I-5)
6. 영상 스트림이 **관측 스택을 경유하는가**, 하드웨어 파트에서 우리로 직접 오는가? (I-4)
7. 프런트엔드에서 **브라우저 → OTel 직접 전송**이 허용되는가? (O-3)
8. 메트릭 중 **이미 집약된 것과 원본**을 구분해 알려줄 수 있는가? (I-8)

## 5. 우리가 지키기로 하는 것

계약은 양방향이므로, 받는 조건만이 아니라 우리 쪽 준수 사항도 명시한다.

- 관측 스택 구현체에 **직접 종속되는 코드를 상위 계층에 두지 않는다.** 전부 F7 DataSource 인터페이스 뒤에 둔다(NFR-005). 대규 파트가 구현체를 교체해도 우리 화면 코드는 바뀌지 않는다.
- **수집기·저장소를 우리가 만들지 않는다.** 질의와 발행만 한다(요구사항정의서 §3).
- **자격 증명을 우리 계약 파일에 기록하지 않는다.** 시크릿 저장소 참조 키만 담는다(`datasource.schema.json`의 `auth.secretRef`).
- 제어 명령의 **실제 실행·검증을 우리가 수행하지 않는다.** 선언·노출·발행·표시까지다(REQ-906).
- 질의 부하가 커지는 구성(짧은 폴링 주기 등)을 도입할 때 **사전에 공유한다.** O-4가 그 수단이다.
