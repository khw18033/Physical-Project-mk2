## 0. 요약 — 다섯 가지를 어떻게 받는가

| # | 피드백 | 현재 상태 | 수용 방식 |
|---|---|---|---|
| 1 | 트윈은 데이터 소스를 몰라야 한다(SAR·드론·360·CCTV 무관) | ◐ 말단→엣지는 이미 소스 중립. 트윈만 로봇 전용 | 서버가 스키마 소유. **결측은 null**, 다른 센서가 채우면 그때 채움 |
| 2 | 로봇과 1:1 결합 금지 (Unity↔Go1 직결 금지) | ❌ **정면 위반** — Unity가 Go1 SDK와 UDP 직결 | 상태·명령을 서버 경유로 승격. 3단계 이행(§2-3) |
| 3 | 로봇 데이터 저장 형태 정의 | ❌ 미정의 (오늘 만든 촬영본이 로컬에만 쌓임) | 3계층 분류 + 업로드 스키마 제안(§3) |
| 4 | 엣지/클라우드 청사진 | ◐ 엣지 구성요소는 있으나 분담 기준 없음 | **지연·데이터량·소유권** 3기준으로 분담표 확정(§4) |
| 5 | 백엔드(OTEL) 연동 | ◐ 말단 OTLP 발신 구현, 서버 미연결 | 관측/제어 분리 + Grafana 투트랙(§5) |

**핵심 한 줄**: 지금 우리 시스템에서 "로봇에 종속된 곳"은 정확히 두 군데다 —
`go1_sdk_pc.cpp`(어댑터, 종속이 **의도된** 곳)와 **Unity 직결 UDP 경로**(종속이 **새어 나온** 곳).
전자는 유지, 후자는 걷어낸다.

## 1. 데이터 소스와 분리 — 트윈은 무엇이 찍었는지 모른다

### 1-1. 수용

**서버가 스키마의 주인**이고, 트윈은 약속된 형식만 받는다. 트윈이 `a,b,c`를 요구하는데
소스가 `a,b,d,e`만 주면 **서버가 `c`를 null로 채워 내려보내고**, 다른 센서가 `c`를 채우면
그때부터 값이 실린다. 트윈은 어느 센서가 채웠는지 알 필요가 없다.

### 1-2. HW 쪽 함의 — 로봇도 "센서 소스 중 하나"다

말단 노드는 이미 소스 중립적인 봉투를 쓴다(`pi/common/schema.py`):

```json
{ "schema_version": …, "source_id": "go1-001", "node_id": "pi7",
  "zone_id": "zoneA", "timestamp": "…", "seq": 12, "channel": "state", … }
```

`source_id`만 바뀔 뿐 SAR·CCTV·수위센서가 같은 봉투를 쓴다. **여기는 이미 맞다.**
바꿔야 하는 건 트윈이 이 봉투가 아니라 로봇 전용 UDP 텍스트를 직접 받고 있다는 점이다(§2).

### 1-3. 결측 표현 규칙 — **모르는 값을 0으로 채우지 않는다**

이 규칙은 추상론이 아니다. 오늘(2026-09-10) 실제로 밟았다.

> Go1 내부 텔레메트리가 **전부 0인 프레임**을 계속 발행했다. 파서가 그걸 그대로 읽어
> "배터리 0%, 자세 0°, 위치 원점"이라는 **그럴듯한 거짓값**을 상위로 올렸다. 그 결과
> 배터리 경보가 오발동했고, 임무가 `battery_too_low` 로 거부될 뻔했다.
> 고친 방식: 전부 0인 프레임은 `go1_state_zeroed`(데이터 부재)로 보고, 배터리 "모름"은
> `None` 으로 둔다 — 0% 와 구별해야 하기 때문이다. (`pi/robot/go1_link.py`)

그래서 계약으로 못박는다:

| 상태 | 표현 | 금지 |
|---|---|---|
| 값이 있다 | 그 값 | — |
| 아직 없다 / 센서가 안 준다 | `null` | `0`, `-1`, 빈 문자열로 대체 금지 |
| 값이 오래됐다 | 값 + `stale_s` | 최신값인 척 금지 |

**서버가 blank로 채워 내려보낸다**는 피드백은 이 규칙과 정확히 같은 이야기다.
말단은 모르면 `null`을 올리고, 서버는 트윈 스키마에 맞춰 `null`을 채워 내려보낸다.

### 1-4. 백엔드에 필요한 것

- 트윈이 요구하는 **필드 목록과 타입**(= 서버가 보장할 스키마).
- `null` 허용 필드와 필수 필드의 구분.
- 여러 소스가 같은 필드를 채울 때의 **우선순위·병합 규칙**(예: 위치를 로봇 odom과
  SAR가 둘 다 준다면 누가 이기는가, 아니면 둘 다 남기고 트윈이 고르는가).

## 2. 로봇과 1:1 결합 금지

### 2-1. 지금 어디가 결합돼 있나 (정확히)

| 경로 | 현재 | 결합 여부 |
|---|---|---|
| 명령 (임무·제어) | MQTT5+Protobuf 규약 `terminal/<id>/downlink` | ✅ 이미 분리됨 |
| 로봇 상태 → 트윈 | **`go1_sdk_pc` → Unity UDP 15101 직결** | ❌ 결합 |
| 텔레옵 → 로봇 | **Unity → UDP 15100 직결** | ❌ 결합 |
| 경로(자율주행) → 로봇 | **Unity → UDP 15110 직결(JSON)** | ❌ 결합 |
| 이동 여부 | **→ Unity UDP 5009 직결** | ❌ 결합 |
| 좌표 규약 | Unity 월드 좌표를 SDK가 그대로 사용 | ❌ 기종 종속이 트윈까지 번짐 |

`HW-interface/bridge-contract.md`는 "새 로봇 = 어댑터 1개"를 목표로 썼지만, 실제로는
**Unity가 Go1의 좌표계·포트·텍스트 포맷을 직접 알고 있다.** 레인보우로보틱스로 바꾸면
어댑터만 갈아끼우는 게 아니라 Unity도 고쳐야 한다 — 피드백이 지적한 그대로다.

### 2-2. 이미 절반 와 있는 것 — 다중 로봇 릴레이

`HW-interface/multi-robot-contract.md` + `pi/robot/robot_state_relay.py`가
**신원(`node_id`, `robot_type`, `robot_id`)을 붙여 15201로 중계**하는 구조를 이미 만들었다.
이것이 "서버 경유"의 씨앗이다. 릴레이가 서버 쪽으로 올라가면 그대로 §2-3의 2단계가 된다.

### 2-3. 이행 3단계 — 시연을 깨지 않으면서 걷어낸다

직결 경로를 지금 당장 끊으면 캡스톤1 시연이 멈춘다. 그래서 **경로를 하나 더 띄우고
트윈이 그쪽으로 갈아타는 순서**로 간다.

**1단계(지금~시연): 신원 부여 + 이중 발신.** 로봇 상태를 릴레이 규약(15201, 신원 포함)으로도
보낸다. 직결(15101)은 살려 둔다. HW 작업 없음 — 이미 `--relay_ip` 로 동작한다.

**2단계: 서버 중계.** 릴레이 대상을 Unity가 아니라 **엣지 서버**로 바꾼다. 서버가 트윈
스키마로 변환해 트윈에 내려보낸다. 이때 §1의 null 규칙이 적용된다.
→ 트윈은 로봇 포트·텍스트 포맷을 더 이상 모른다.

**3단계: 명령도 규약으로 일원화.** 텔레옵·경로 주입을 UDP 직결에서
규약 action(`teleop`, `set_path`)으로 옮긴다. `scan_mission` 이 이미 그 선례다 —
**웹에서 명령 한 건을 보내면 로봇이 임무를 수행하고 ACK가 되돌아오는 경로가 오늘 검증됐다**
(`HW-interface/mission-command.md`).

> **제어 루프는 예외다.** 500Hz HighCmd 루프와 IMU 되먹임은 로봇 옆(엣지)에 남는다.
> 이건 결합이 아니라 물리 법칙이다 — 왕복 지연이 제어 주기를 넘으면 로봇은 넘어진다.
> "서버를 거친다"는 **목표·경로·상태**에 적용되고, **구동 루프**에는 적용되지 않는다.

### 2-4. 좌표 규약도 중립화해야 한다

현재 `coordinate-contract.md`는 "SDK가 Unity 월드 좌표를 그대로 쓴다"이다. 시연에는
문제없지만, **트윈이 바뀌면 로봇 코드가 바뀌는** 구조라 결합이다. 서버 경유가 되면
규약 좌표를 **물리 좌표(m, ENU 또는 건물 기준 로컬 프레임)** 로 두고, Unity 변환은
트윈 쪽에서 한다. → 2단계에서 같이 처리.

## 3. 로봇 데이터를 어떤 형태로 올리고 저장할 것인가

### 3-1. 세 종류를 갈라야 한다

같은 "로봇 데이터"라도 성질이 다르면 저장소도 달라야 한다.

| 종류 | 예 | 주기·크기 | 전송 | 저장 |
|---|---|---|---|---|
| **A. 연속 상태** | 위치·자세·속도·배터리 | 20Hz(임무)/0.2Hz(대기), 수백 B | MQTT QoS0 + OTLP metrics | 시계열 DB(Prometheus/TSDB) |
| **B. 이산 사건** | 명령 수락/결과, 임무 ACK, 모드 전환, 경보 | 건당, 수백 B | MQTT **QoS1**(유실 불가) | 이벤트/감사 DB(MySQL) |
| **C. 대용량 산출물** | 카메라 프레임, H.264, 포인트클라우드 | 10fps · 19KB/장 = **0.7GB/시간** | 별도 경로(RTP/HTTP PUT) | 객체 저장소 + 메타만 DB |

A와 B를 섞으면 안 되는 이유는 이미 코드에 적어 뒀다(`pi/robot/robot_node.py`):
연속값은 다음 표본이 50ms 뒤 오므로 유실이 상쇄되지만, 사건은 하나 빠지면 인과가 끊긴다.

### 3-2. C 를 지금 정해야 하는 이유

오늘 만든 촬영 도구(`pi/bench/go1_capture_teleop.py`)가 **정확히 C를 생산**한다.
지금은 파이 로컬에만 쌓이고(`~/captures/<날짜시각>/`) 서버로 갈 길이 없다.

```
~/captures/20260910-134818/
├── frame_000001.jpg …            10fps JPEG (464×400, 약 19KB)
├── session.json                  시작시각·카메라·fps·속도상한
└── teleop_log.csv                ts_unix, vx, vy, wz, estop
```

### 3-3. 제안 — 업로드 스키마

**원칙: 픽셀은 객체 저장소, DB에는 참조만.** 프레임 하나하나를 DB에 넣으면 시간당
36,000행이 쌓이고 백업이 불가능해진다.

```json
{
  "schema_version": "1.0",
  "kind": "capture_session",
  "session_id": "go1-001/20260910-134818",
  "source_id": "go1-001", "node_id": "pi7", "zone_id": "zoneA",
  "started_at": "2026-09-10T13:48:18+09:00",
  "duration_s": 86.0,
  "sensor": { "type": "camera", "position": "front",
              "fps": 10, "resolution": "464x400", "format": "jpeg" },
  "frames": { "count": 857, "bytes": 12300000,
              "uri": "s3://…/go1-001/20260910-134818/",
              "naming": "frame_%06d.jpg",
              "t0_unix": 1789014498.2, "interval_s": 0.1 },
  "motion": { "uri": "s3://…/20260910-134818/teleop_log.csv",
              "columns": ["ts_unix","vx","vy","wz","estop"] },
  "pose_track": null
}
```

- **프레임 시각은 `t0 + n/fps`** 로 복원한다. 파일마다 타임스탬프를 박지 않는 이유는
  10fps × 시간당 36,000개에 개별 메타를 붙이면 메타가 데이터보다 커지기 때문이다.
- `motion` 을 같이 올리는 게 핵심이다. **어느 사진이 어느 동작 중에 찍혔는지**가
  학습·분석의 전부인데, 지금 그 정보를 가진 곳은 파이뿐이다.
- `pose_track: null` — 위치 궤적은 아직 못 준다. §1-3 규칙대로 **0이 아니라 null**이고,
  나중에 SLAM/odom이 붙으면 그때 채운다. 이것이 피드백의 "blank로 주고 나중에 채운다"의
  HW 쪽 구현이다.

### 3-4. 백엔드에 필요한 것

- 객체 저장소 종류와 업로드 방식(S3 호환 PUT / 엣지가 대신 받아 올리기).
- 업로드 시점: 임무 종료 시 일괄 / 실시간 스트리밍 / 요청 시.
- 보존 기간과 용량 상한(0.7GB/시간이면 하루 촬영이 십 GB 단위다).

## 4. 엣지/클라우드 청사진

### 4-1. 분담 기준 세 가지

무엇을 어디에 둘지는 취향이 아니라 **세 기준**으로 갈린다.

1. **지연 예산** — 제어 루프(2ms)·안전 정지는 물리적으로 로컬이어야 한다.
2. **데이터량** — 원본 영상을 클라우드로 올리면 무선 대역이 먼저 죽는다.
3. **소유권/범위** — "이 구역 안에서만 의미 있는 정보"는 그 구역 엣지에 둔다.

### 4-2. 분담표 (피드백의 403호→503호 예시를 그대로 반영)

| 데이터 | 위치 | 근거 | 예 |
|---|---|---|---|
| 구동 루프·IMU 되먹임 | **로봇/파이(로컬)** | 지연 | HighCmd 500Hz, 회전 각도 닫기 |
| 원본 프레임·H.264 | **로컬 → 엣지** | 데이터량 | 10fps JPEG, 카메라 스트림 |
| 구역 지도·구역 내 경로·구역 장애물 | **엣지(구역별)** | 소유권 | 415호, 복도, 계단 |
| 로봇 상태 요약·임무 진행 | **엣지 → 클라우드** | 관제 | 20Hz는 엣지, 요약은 클라우드 |
| **글로벌 목표와 달성 여부** | **클라우드** | 소유권 | "403호 → 503호", 성공/실패 |
| 명령 감사·command_id | **클라우드** | 소유권 | 누가 언제 무엇을 시켰나 |

**로컬 데이터와 서버 데이터의 구분**이 피드백의 요지인데, 우리 코드에는 이미 그 경계가
있다 — 말단의 `spool`(두절 대비 버퍼)이 "아직 서버 것이 되지 못한 로컬 데이터"다.

### 4-3. 캡스톤1 현재 규모와 확장 지점

지금은 **로봇 1 · 엣지 1(pi7) · 서버 1**이라 하이브리드를 논할 필요가 없다.
다만 다음 두 가지가 나타나면 구조를 바꿔야 한다:

| 신호 | 문제 | 대응 |
|---|---|---|
| 엣지가 2개 이상 | 구역 간 이동 시 상태 소유권 이관 | 이관 프로토콜 또는 스트리밍 백본 |
| 로봇이 여러 대 + 구독자 여러 곳 | 팬아웃·순서·재처리 | **Kafka 기반 스트리밍** |

Kafka로 가는 판단 기준을 미리 적어 둔다 — "규모가 커지면"은 판단이 안 되므로:
**① 구독자가 3개 이상(트윈·AI·관제)이고 ② 재처리(리플레이)가 필요하며 ③ 엣지가 2개 이상**
이면 그때 넘어간다. 지금은 셋 다 아니므로 MQTT로 충분하다.

> 참고: pi7은 지금 **브로커까지 겸하고 있다**(2026-09-10, mosquitto 1883/9001).
> 로봇 옆에 브로커를 둔 이유는 현장 네트워크가 핫스팟으로 바뀌어도 명령 경로가
> 살아 있어야 하기 때문이다. 이것이 사실상 **엣지 서버의 첫 형태**다.

## 5. 백엔드(OTEL) 연동

### 5-1. 이미 있는 것

- 말단 OTLP 직접 발신 구현(`pi/common/otel_metrics.py`, `otel_trace.py`), v8 §5-3·5-8로 확정.
- 엣지가 하트비트·LWT로 Prometheus `up` 파생(`edge/availability.py`).
- 명령 경로에 trace/span 계측(10-3).

즉 **관측 배관은 깔려 있고 수신단(서버)만 비어 있다.**

### 5-2. 수용하되 갈라야 하는 것 — 관측 경로로 제어하지 않는다

"OTEL 플러그인으로 로봇 컨트롤·디버깅까지"는 방향으로는 맞지만, **관측 파이프라인을
제어 경로로 쓰면 안 된다.** 이유는 세 가지다.

| 관측(OTEL/Prom) | 제어(MQTT 규약) |
|---|---|
| 단방향(장치→서버) | 양방향, 응답·ACK 필수 |
| 샘플링·유실 허용 | 유실 불가(멱등·취소·결과 4단계) |
| 15초 배치 | 즉시성 |

**따라서 투트랙으로 간다.**

```
 [관측 트랙]  말단 ──OTLP──▶ Collector ──▶ Prometheus/Tempo ──▶ Grafana (보기·디버깅)
 [제어 트랙]  웹/백엔드 ──MQTT5+Protobuf──▶ 말단 ──ACK──▶ 백엔드 ──▶ 웹
                                    ↑
                    Grafana 버튼은 여기(백엔드 API)를 호출한다. OTLP 로 명령을 보내지 않는다.
```

Grafana에서 "로봇 제어"를 하고 싶다면 **패널의 링크/버튼이 백엔드 명령 API를 호출**하고,
백엔드가 규약으로 내려보내면 된다. 그러면 감사(command_id)·멱등·취소가 그대로 유지된다.

### 5-3. 디버깅 관점에서 지금 바로 이득인 것

오늘 하루에만 다음 세 가지를 **로그를 사람이 눈으로 뒤져서** 찾았다.

| 증상 | 실제 원인 | 관측이 있었다면 |
|---|---|---|
| 미션이 8회전 내내 헛돎 | 로봇 상태 두절(HighState 미수신) | `robot_state_alive` 게이지 하나면 즉시 보임 |
| 배터리 경보 오발동 | 0으로 채워진 프레임을 값으로 읽음 | `battery_pct` 가 null이 아니라 0인 것이 그래프에 남음 |
| 키를 눌러도 로봇이 안 움직임 | `go1-sdk` 서비스 죽어 있음 | `up{service="go1-sdk"}` |

**HW가 내보낼 관측 지표 후보**(백엔드 수신단이 서면 바로 붙는다):

```
robot_state_alive{robot_id}          0/1   로봇이 상태를 올려보내는가
robot_battery_pct{robot_id}          %     (모르면 미발행 — 0으로 채우지 않는다)
mission_ack_total{robot_id,event}    counter
mission_duration_seconds{robot_id}   histogram
capture_frames_total{robot_id}       counter
teleop_cmd_rate{robot_id}            gauge
```

## 7. 수용하지 않는(=조건부로 받는) 한 가지

**"로봇 제어·트윈 쪽은 서버를 거쳐 약속된 프로토콜로만 통신"** — 목표·경로·상태에는 전면 수용한다.
다만 **구동 제어 루프(500Hz)와 안전 정지는 로봇 옆에 남긴다.** 서버를 거치면 왕복 지연이
제어 주기를 넘어 로봇이 넘어진다. 실측으로도 근거가 있다 — 무선 왕복이 약 150ms인데
제어 주기는 2ms다(`pi/common/config.py` 주석, SRS 9.4).

즉 경계는 이렇다:

```
서버를 거친다 :  임무 목표 · 경로 · 상태 보고 · 명령/ACK · 저장
로봇 옆에 남는다 :  구동 루프 · IMU 되먹임 · E-stop · 원본 영상 인코딩
```

이 경계는 피드백과 어긋나지 않는다. **"로봇과 1:1로 묶이지 않는다"는 것과 "제어 루프를
원격에 둔다"는 다른 이야기**이며, 어댑터(`go1_sdk_pc`)가 그 경계를 담당한다 —
새 로봇이 오면 이 파일 하나를 새로 쓰면 된다.
