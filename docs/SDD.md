## 1. 설계 원칙

이 다섯 가지가 이후 모든 설계 판단의 기준이다. 충돌하면 위쪽이 이긴다.

| # | 원칙 | 근거 |
|---|---|---|
| **P1** | **안전 루프는 네트워크에 의존하지 않는다.** 계측·임계 판정·자율 주기 전환·버퍼링은 브로커·엣지·오케스트레이터가 전부 죽어도 동작해야 한다 | 재난 골든타임. SRS §9.2 |
| **P2** | **평면을 합치지 않는다.** 업무(MQTT)·관측(OTLP)·미디어는 별개 경로다. 업무가 막혀도 관측으로 원인이 보여야 한다 | AI-C-08, BE-S-02 |
| **P3** | **미확정은 한 곳에 가둔다.** 백엔드가 확정권을 가진 스키마·토픽은 어댑터 한 파일에만 나타난다 | SRS C-5 |
| **P4** | **말단은 클라이언트만 둔다.** 브로커·수집기·데이터스토어를 말단에 설치하지 않는다 | AI-B-10 |
| **P5** | **상태는 뭉치지 않는다.** 자기보고·서버판정·오케스트레이터 판정은 다른 층이고, 계획된 종료와 장애는 다른 사건이다 | BE-T-04, VZ-U-01 |

## 2. 배치 구조

### 2.1 노드와 평면

```
┌─ 말단 (Raspberry Pi 5) ───────────────┐        ┌─ 구역 엣지노드 ──────────┐
│                                        │        │                          │
│  systemd (P1: 항상 살아있는 층)         │        │  Mosquitto (MQTT 5.0)    │
│   ├ 센서노드  sensor_node               │─업무──►│                          │
│   │  또는                               │        │  K3s server (제어평면)    │
│   ├ 로봇 온보드 robot_node              │─관측──►│  OTel Collector (Agent)  │
│   └ 액추에이터 actuator_node            │        │                          │
│                                        │─미디어►│  미디어 게이트웨이         │
│  k3s agent (증강 기능 층)               │◄─배포──│                          │
│   ├ AI 추론 파드                        │        └──────────┬───────────────┘
│   ├ 영상 분석 파드                      │                   │ Kafka
│   └ 심화 분석 파드                      │                   ▼
└────────────────────────────────────────┘             [백엔드 서버]
```

**두 개의 층이 한 노드에 공존한다.** systemd 층은 P1을 지키고, k3s 층은 HW-C-03을
충족한다. 둘을 섞지 않는 이유는 SRS §9.2 — k3s agent는 제어평면에 연결되지 못하면
컨테이너를 기동조차 하지 못하므로, 안전 루프를 거기 넣으면 그 실패 모드를 상속한다.

### 2.2 노드 종류별 책임 (요구사항 8: 로봇/센서 분할)

| | 센서노드 | 로봇 온보드 | 액추에이터 제어노드 |
|---|---|---|---|
| 실행 단위 | `sensor-node.service` | `robot-node.service` | `actuator-node.service` |
| Entity 예 | `wl-001` | `rb-01` | `gate-01` |
| 계측 원천 | 환경센서(수위·온도·습도) | 로봇 제어기(50Hz) + 카메라 | 액추에이터 제어기 |
| 상태 보고 | 평시 60초 / 사건 1Hz | 임무 중 20Hz / 대기 5초 | 동작 중 20Hz |
| 하트비트 | 항상 5초 | **대기 중에만** 5초 | 5초 |
| 명령 | 주기 전환, 진단 | 임무·주행·스트림 제어 | 물리 구동 |
| 특수 | report-by-exception | 영상·추론·내부 링크 | 안전 상태 유지·잠금 |
| **공유** | 등록·명령 4단계·버퍼링·관측·식별 (HW-C 공통 코어) | ← | ← |

세 노드는 **공통 코어를 상속**하고 계측 원천·보고 정책·명령 어휘만 다르다.

### 3.2 BaseNode — 공통 코어

세 노드가 공유하는 생애주기. 하위 클래스는 **훅만 채운다.**

```
BaseNode
├─ 생성      Identity 해석 → Spool → Metrics → MQTT 클라이언트(LWT 등록) → 명령 워커
├─ 접속      on_connect: 플래핑 판정 → cmd 구독 → Birth 발행 → 버퍼 재전송
├─ 주기 루프  tick 단위로 아래 훅을 각자의 마감시각에 호출
│    ├─ on_sample()          [하위 구현] 계측 수집·보고 판정
│    ├─ tick_heartbeat()     [공통] 단 heartbeat_enabled() 훅으로 억제 가능
│    ├─ publish_status()     [공통] 10초 상태 요약 (HW-C-04)
│    ├─ tick_identity()      [공통] zone/MAC/IP 변경 감시 (HW-C-07)
│    └─ spool.replay()       [공통] 재연결 시 순서 보존 재전송 (HW-R-09)
├─ 명령      ACTIONS 사전을 하위가 확장. 검증·중복억제·4단계는 공통
└─ 종료      SIGTERM/SIGINT → graceful shutdown 발행 (P5)
```

**하위 클래스가 구현하는 훅**

| 훅 | 반환 | 용도 |
|---|---|---|
| `on_sample(now)` | — | 계측 수집과 보고 판정. 노드마다 완전히 다르다 |
| `heartbeat_enabled()` | bool | 로봇은 임무 중 False (HW-R-02) |
| `device_status_extra()` | str\|None | 노드 고유의 fault 조건 |
| `status_extra()` | dict | 상태 요약에 덧붙일 노드 고유 필드 |
| `ACTIONS` | dict | 노드 고유 명령 어휘 |

### 3.3 메시지 봉투 (P3의 격리 지점)

```python
envelope(identity, seq=None, correlation_id=None) -> {
    "schema_version", "source_id", "node_id", "zone_id",
    "timestamp", "seq"?, "correlation_id"?, "device_id"(전환기 별칭)
}
```

백엔드가 필드명을 확정하면 **이 함수 하나만** 고친다. `LEGACY_DEVICE_ID` 플래그를
False로 내리면 별칭이 사라진다. 다른 파일은 필드명을 문자열로 알지 못한다.

## 4. 센서노드 설계 (HW-S)

### 4.1 수집과 보고의 분리

```
매 SAMPLE_INTERVAL:  read_sensor() ──► 창(window) 적재
                                   └─► 보고 판정
                                        ├ 임계 돌파      → threshold_exceeded  즉시
                                        ├ 임계 해제      → threshold_cleared   즉시
                                        ├ 급변(창 양끝)  → rapid_change        즉시
                                        └ 주기 도래      → periodic
```

**수집은 센서 최대 속도로, 보고는 사건이 있을 때만.** 원본을 전부 쥔 말단이 취사선택을
담당한다는 HW-S-01의 원칙이다.

급변 판정은 인접 두 샘플이 아니라 **창(기본 10초) 양끝의 차이**로 본다. 인접 비교는
잔물결을 사건으로 오인한다. 상승이 지속되는 동안 매 초 경보하지 않도록 급변 보고 자체에
최소 간격(10초)을 둔다.

### 4.2 주기 전환 3층 (SRS §9.2 확정)

```
         ┌──────────────────────────────────────────┐
 1순위    │ 로컬 자율   임계 돌파 → event(1Hz)         │ 네트워크 무관, 지연 0
         │            임계 해제 → normal(60s)        │
         └──────────────────────────────────────────┘
 2순위    │ MQTT 명령   set_mode / set_report_interval│ 엣지 오버라이드
         │            mode_source="command" 로 고정  │ 구역 단위 일관성
         │            → 자율 전환이 이를 덮지 않는다   │
         └──────────────────────────────────────────┘
 3순위    │ K3s 배포    AI 추론·영상 분석 파드          │ 증강 기능. 수 초 지연 허용
         └──────────────────────────────────────────┘
```

`mode_source`가 `command`인 동안 자율 전환은 억제된다. 엣지가 명시적으로 지정한 주기를
말단이 임의로 되돌리면 구역 단위 일관성(HW-S-04의 본래 목적)이 깨지기 때문이다.
`set_mode {mode:"auto"}` 로 자율 판정에 복귀시킨다.

### 4.3 실센서 교체 지점 (HW-S-01)

`read_sensor()` 단일 함수만 교체한다. 그 위의 창 적재·판정·보고·버퍼링·관측은 그대로다.
센서 데이터시트가 확정되면 `SAMPLE_INTERVAL`을 최대 유효 샘플링 속도로 내린다.

## 5. 로봇 온보드 설계 (HW-R) — 신규

### 5.1 3계층 구조

```
[로봇 제어기]  ──내부 링크 50Hz──►  [온보드 파이]  ──MQTT──►  [엣지노드]
 주행·구동 전담                      통신·버퍼·중계 전담
                                    │
                                    ├─ 카메라 ──► 온디바이스 추론 (HW-R-04)
                                    └─ 카메라 ──► 미디어 경로 (HW-R-07, 온디맨드)
```

**격리가 목적이다.** 외부 프로토콜과 구동 인터페이스를 온보드에서 갈라놓아, 통신 장애가
구동 로직에 직접 닿지 않게 한다(HW-R-06).

### 5.2 내부 링크 어댑터 (`controller_link.py`)

제어기 실물이 미정이므로 **인터페이스만 고정**하고 구현체를 갈아끼운다.

```python
class ControllerLink(ABC):
    def read_state() -> RobotState      # 50Hz — 배터리·위치·속도·모드
    def send_command(cmd) -> None       # HW-R-06 변환·전달
    def link_health() -> str            # ok | degraded | fault
```

| 구현체 | 대상 | 적용 판단 (SRS §9.4) |
|---|---|---|
| `SimLink` | 실물 없이 파이프라인 검증 | 지금 사용 |
| `CanLink` | 소형 주기 스칼라(배터리·위치·속도·모드) | 결정적 지연·프레임 우선순위 |
| `EthLink` | 가변 크기 인식 결과 | 구조화 데이터 |

소형 주기값은 CAN, 인식 결과는 Ethernet으로 **분리하는 하이브리드**를 기준으로 둔다.
공유메모리는 제어기와 파이가 물리적으로 별개 보드이므로 적용 불가.

### 5.3 보고 정책과 QoS

| 채널 | 임무 중 | 대기 중 | QoS | 근거 |
|---|---|---|---|---|
| `state` | 20 Hz | 5초 | **0** | 다음 샘플이 50ms 뒤 오므로 유실을 상쇄. QoS 1은 무선 왕복(~150ms)이 주기보다 길어 부적합 (SRS §9.4) |
| `heartbeat` | **정지** | 5초 | 0 | 임무 중엔 state가 하트비트를 겸한다 (HW-R-02) |
| `cmd/ack`·`cmd/result` | 이벤트 | 이벤트 | **1** | 이산 이벤트. 유실 불가 |
| 임계·이상 경보 | 이벤트 | 이벤트 | **1** | 이산 이벤트 |

> ⚠ 20Hz라는 수치의 근거(Nav2 `controller_frequency`)는 내부 제어 루프 주기이지 네트워크
> 전송 주기가 아니다(O-11). 실물 확보 후 무선망 실측으로 재산정한다. 설계는 주기를
> 설정값으로 두어 재산정 결과를 코드 수정 없이 반영할 수 있게 한다.

### 5.4 버퍼링 정책 분리 (O-12)

20Hz에서 10분 두절이면 12,000건이 쌓인다. 이를 전량 재전송하면 **막 복구된 저대역 링크를
과거 데이터로 막아** 정작 중요한 현재 상태와 명령 ACK가 밀린다.

| 데이터 종류 | 재전송 정책 | 근거 |
|---|---|---|
| **이산 이벤트** (모드 전환, 임계 경보, 배터리 저전압, 명령 결과, 임무 상태 전이) | **전량·시간순 재전송** | HW-R-09의 원 취지. 하나가 빠지면 사건의 인과가 끊긴다 |
| **연속 상태값** (위치·속도·배터리 추이) | **다운샘플 요약**(예: 1Hz로 압축) 후 재전송 | 궤적은 1Hz 표본으로도 복원 가능. 50ms 해상도가 사후 분석에 필요하지 않다 |

`Spool`에 레코드 분류(`kind: event | continuous`)를 추가하고 재전송 시 정책을 갈라 적용한다.
MQTT 5.0의 Message Expiry Interval을 보조로 사용한다.

### 5.5 영상 (HW-R-04 / HW-R-07)

| | HW-R-04 환경인식 | HW-R-07 관제 |
|---|---|---|
| 소비자 | 온디바이스 AI | 사람(관제사) |
| 해상도 | 다운스케일 640급 | 원본 |
| 전송 | 로컬(전송 없음) | 엣지로 온디맨드 15fps |
| 제어 | — | MQTT 명령으로 세션 개폐, 미디어는 별도 경로 |

**Pi 5에는 H.264 하드웨어 인코더가 없다(SRS §9.3 실기 확인).** 소프트웨어 인코딩만
가능하다. 다만 실측 결과 우려만큼 비싸지 않다:

| 용도 | 코어 사용 (4코어 중) |
|---|---|
| AI 입력 640x480@15 | 0.13 (3%) |
| 관제 1080p@15 veryfast | 0.70 (18%) |
| CCTV 상시 1080p@15 ultrafast | 0.41 (10%) |

1080p15 + 720p15 **동시** 인코딩 중에도 로봇 20Hz 보고가 19.9Hz 를 유지했다(전체 CPU
23.8%, 스로틀 없음). **영상 인코딩은 안전 루프를 굶기지 않는다** — 원칙 P1 이 실측으로 지지된다.

따라서:
- 상시 CCTV + 온디맨드 관제 스트림 동시 운용이 **CPU 상 가능하다.**
- 남는 예산은 **온디바이스 추론**이 가져간다. 지배 제약은 인코딩이 아니라 추론이다.
- HW-R-07 의 온디맨드는 CPU 가 아니라 **무선 대역폭** 때문에 유지한다.
- 합성 패턴 기준이므로 실제 카메라 영상에는 **1.5배 여유**를 둔다.

### 5.5.1 전송 경로 — 아키텍처 v8 확정 (2026-08-31)

v8 §5-10·6-8이 미디어 경로를 확정했다. 하드웨어가 담당하는 것은 **홉1(말단→엣지)** 뿐이다.

```
[말단]  카메라 → JPEG 인코딩 → RTP over UDP ──► [엣지]  수신·디코드(OpenCV/FFmpeg)
                                                          │ 로컬 소비(탐지·트윈)
                                                          │ 결과만 Kafka로
                                                          └─ 원본은 온디맨드일 때만
                                                             WebSocket으로 서버 중계
```

| 결정 | 근거 (v8) |
|---|---|
| **RTP over UDP** | 영상은 프레임 유실을 허용한다. TCP 재전송을 기다리면 오히려 화면이 밀린다. RTP가 조각마다 순번·타임스탬프를 실어 frame_ref 재구성에 맞는다 |
| **JPEG 코덱** | 프레임이 서로 독립이라 한 장 유실이 다음 프레임에 전파되지 않아 UDP와 궁합이 좋고, 프레임 단위 탐지 오버레이 정합이 단순하다. 대역폭은 크지만 홉1이 로컬 LAN이라 제약이 아니다 |
| **RTSP 서버 불필요** | 로봇 온보드는 코드를 우리가 통제하므로 포트·코덱을 양쪽에 두고 RTP를 직접 송출한다. 표준 IP 카메라(펌웨어에 RTSP 내장)만 엣지가 접속해 세션을 연다 |
| 원본을 서버로 상시 올리지 않음 | 엣지가 로컬 소비하고 결과만 올린다. 원본은 관제사가 볼 때만 |

**JPEG 실측으로 재측정 완료** (SRS §9.10). 1080p@15 에서 0.48 코어 — H.264(0.70)보다
오히려 싸다. 대신 대역폭이 2.4배이고, **품질(q)이 대역폭의 지렛대**다(1080p q=5→12 에서
9.7→5.5 Mbps, CPU 는 그대로). 하드웨어 JPEG 인코더는 없으나 위 수치상 문제되지 않는다.

⚠ **로봇의 홉1 은 무선이다.** v8 은 JPEG 대역폭을 "홉1이 로컬 LAN"으로 정당화하는데
고정 CCTV 는 맞지만 로봇은 아니다(실측 720p 6.8 Mbps, `wlan0` 경유). 미결 O-17.

### 5.5.3 Go1 실기 조사 결과 — 로봇이 이미 RTP 로 보낸다 (2026-08-31)

Unitree Go1 의 카메라 전송을 실기에서 조사했다. **v8 이 정한 전송 계층과 이미 같다.**

```
Go1 카메라(Nano) ──RTP/H.264 over UDP──► 지정 IP
포트 9201 전방 · 9202 턱 · 9203 좌 · 9204 우 · 9205 배
대상 IP: UnitreeCameraSDK 설정의 IpLastSegment → 192.168.123.<값>
```

**설계에 주는 함의.** 로봇 영상은 `media.py` 로 다시 인코딩할 필요가 없을 수 있다.
Go1 이 이미 RTP 로 내보내므로 엣지가 그대로 받으면 된다 — 말단에서 디코드·재인코딩하는
왕복이 사라지고 CPU 도 아낀다. 코덱만 H.264 로 v8 의 JPEG 와 다르다.

| 항목 | v8 규정 | Go1 실제 | 판단 |
|---|---|---|---|
| 전송 | RTP/UDP | **RTP/UDP** | 일치 |
| 코덱 | JPEG | **H.264** | 다름 — 엣지가 둘 다 받게 하거나 코덱 협의 필요 |
| 세션 제어 | MQTT 명령 | 설정파일 + 프로세스 기동 | 우리 `stream` 명령이 이 기동을 감싸면 된다 |

**막힌 지점 — 그리고 우회로.** RTP 경로를 쓰려면 카메라를 직접 열어야 하는데,
캘리브레이션된 카메라는 전부 로봇의 `camerarosnode` 가 잡고 있다. 비어 있던 턱 카메라로
시도하니 RTP 패킷은 나갔으나 SDK 가 캘리브레이션을 못 읽어 SPS/PPS 없는 스트림이라
디코드되지 않았다. Unitree 문서는 자체 영상 전송 시 `camerarosnode`·`imageai`·point cloud 를
죽이라고 명시하는데, 그러면 **로봇의 장애물 인식이 멈춘다.**

그래서 카메라를 여는 대신 **이미 열려 있는 통로에 붙었다.**

### 5.5.4 Go1 카메라 — 웹소켓 경로 (채택, 2026-08-31 실측)

Go1 의 `imageai/mLComSystemFrame` 은 카메라마다 `mqttControlNode` 를 띄워 두고
GStreamer `wssink` 로 **웹소켓에서 H.264 byte-stream 을 상시 제공한다.** 유니트리 앱이
영상을 보는 통로가 이것이다. 같은 통로에 클라이언트로 붙으면 로봇은 아무것도 달라지지
않는다 — 설정도, 프로세스도, 카메라 점유도 그대로다.

    카메라 → omxh264enc(600kbps, IDR 15) → wssink → ws://192.168.123.<노드>:<포트>

| ID | 위치 | 노드 | 포트 |
|---|---|---|---|
| 1 | 정면 | 192.168.123.13 | 9101 |
| 2 | 턱(하방) | 192.168.123.13 | 9102 |
| 3 | 좌측 | 192.168.123.14 | 9103 |
| 4 | 우측 | 192.168.123.14 | 9104 |
| 5 | 복부(하방) | 192.168.123.15 | 9105 |

**세 경로의 비교 — 대가가 없는 것은 하나뿐이다.**

| 방법 | 대가 |
|---|---|
| UnitreeCameraSDK 로 직접 열기 | `camerarosnode` 를 죽여야 한다 → 장애물 인식 정지 |
| camerarosnode 의 UDP 송출 설정 변경 | 설정 수정 + 재기동 → 같은 정지 |
| **웹소켓에 붙기 (채택)** | **없다** |

**실측 (pi7, 464x400 H.264 baseline):**

| 항목 | 값 |
|---|---|
| 도착 간격 | 33.3 ms (30 fps) · p90 34.1 ms — **버스트 없음** |
| 프레임 크기 | 평균 2.4 KB · 키프레임 약 0.48초 간격 |
| 카메라당 대역폭 | 0.58 Mbps |
| 5대 동시 | pi7 CPU 2~5% (4코어), 30 fps 유지 |
| 로봇 쪽 부하 변화 | 없음 (원래 항상 인코딩 중인 스트림) |

**변환하지 않는 것이 답이었다.** 처음에는 파이에서 H.264 를 풀어 MJPEG 로 다시 인코딩해
브라우저에 넘겼다. 그 변환 하나가 지연·CPU·대역폭을 전부 끌어올리고 있었다. 로봇이 이미
H.264 로 주므로 **바이트를 그대로 넘기고 브라우저가 하드웨어로 푸는 것**이 모든 면에서 낫다.

| | MJPEG 변환 | **무변환 통과** |
|---|---|---|
| 파이 내부 지연 | 37 ms | **0.1 ms** |
| 파이 CPU (5대) | 0.65 코어 | **0.05 코어** |
| 대역폭 | 3.6 Mbps | **0.58 Mbps** |
| 브라우저 요구 | 없음 | WebCodecs (Chrome/Edge 94+) |

이 결론은 **운영 경로에도 그대로 적용된다.** 엣지도 말단에서 재인코딩된 영상을 받을
이유가 없다 — 로봇의 H.264 를 그대로 받아 필요한 지점에서 한 번만 디코드하면 된다.

**MJPEG 경로에서 얻은 것.** 변환을 유지해야 하는 환경(WebCodecs 없는 브라우저)을 위해
대비 경로로 남겼고, 거기서 지연 함정 두 개를 확인했다.

- ffmpeg 기본은 **프레임 단위 멀티스레딩**이라 스레드 수만큼 프레임을 쥐고 있다가
  내보낸다. 처리량에는 좋지만 실시간 감시에서는 그 지연이 그대로 화면에 보인다.
  디코더·인코더 양쪽을 `-threads 1` 로 묶어 **301 ms → 37 ms**(디코더 −134, 인코더 −131).
- `-fflags nobuffer` 는 **넣으면 안 된다.** 출력이 파이프일 때 두어 프레임만 내보내고
  나머지를 통째로 버린다 — 같은 입력이 파일 출력 3.4 MB, 파이프 출력 29 KB 였다.
  프로세스는 정상 종료하고 오류도 남기지 않아 찾기 어렵다.

**구현**: `robot/go1_camera.py`(웹소켓 H.264 소스, 의존성 없음·읽기 전용),
`bench/go1_cam_view.py`(브라우저 확인용 뷰어 — 무변환 통과가 기본, MJPEG 은 대비 경로).
뷰어는 **지연을 스스로 측정해 화면에 표시한다.** 브라우저와 파이의 시계가 다르므로 NTP
와 같은 왕복 측정으로 차이를 뺀 뒤 파이 수신→화면 표시 구간을 보여 준다. 로봇 내부
지연은 기준 시각이 없어 포함되지 않으므로 표시값은 하한이다.

**남은 판단(O-20)**: 코덱이 H.264 라 v8 의 JPEG 와 다르다. 엣지가 둘 다 받을지, 코덱을
맞출지는 백엔드·AI 와 정해야 한다. 전송 계층(RTP/UDP)은 어차피 우리가 다시 싣는다.

### 5.5.5 구현 (`robot/media.py`)

`MediaSender` 추상 뒤에 `RtpJpegSender` 를 둔다(`ControllerLink`·`ActuatorLink` 와 같은 방식).
카메라 미확보 상태에서는 `HW_MEDIA_SOURCE=test` 로 테스트 패턴을 써 **경로 자체를 검증**한다.

```
MQTT  stream{action:start,dest_host,dest_port}
  → accepted → executing → [ffmpeg 기동·실송신 확인] → state_changed → completed
MQTT  stream{action:stop}
  → accepted → executing → [프로세스 그룹 정리] → state_changed → completed
```

설계에서 신경 쓴 세 가지

| 항목 | 이유 |
|---|---|
| **실제로 바이트가 나가는지 확인한 뒤에야 `state_changed`** | 프로세스가 살아 있는 것만으로는 부족하다. 살아서 인코딩만 하고 네트워크로는 아무것도 안 보내는 실패 모드가 실재한다(아래 RFC 2435) |
| **출력을 파이프가 아니라 파일로** | 파이프로 받아 놓고 읽지 않으면 버퍼가 차는 순간 ffmpeg 가 멈춘다. 또 stdout 에 나오는 **SDP** 는 엣지가 스트림을 여는 데 필요하므로 버리지 않고 회신에 싣는다 |
| **자체 프로세스 그룹 + 종료 훅** | 노드가 내려간 뒤 ffmpeg 가 남아 대역폭을 계속 먹지 않도록 `on_shutdown()` 에서 그룹째 정리한다 |

> **RFC 2435 함정.** `ffmpeg -c:v mjpeg -f rtp` 를 그대로 쓰면 한 바이트도 전송되지 않는다.
> ffmpeg 의 mjpeg 인코더는 기본이 최적화 허프만 테이블인데 RFC 2435 는 표준 테이블만
> 허용해 RTP 먹서가 매 프레임을 버린다. 프로세스는 살아 있고 CPU 도 쓰므로 증상이
> 보이지 않는다. **`-huffman default`** 로 해결. 실기에서 찾아낸 것이라 코드에 주석으로 남겼다.

**검증(pi7 → 노트북, 무선)**: 명령 전 0패킷 → 개시 후 **6.8 Mbps, RTP payload type 26(JPEG),
패킷 결손 0%** → 중복 개시 ACK 이전 거부 → 종료 후 0패킷, ffmpeg 잔여 프로세스 0.

### 5.5.2 frame_ref

`frame_ref = {source_id, capture_timestamp, sequence_id}` 를 프레임과 인지 결과 양쪽에
실어 결합한다. 타임스탬프만으로는 두 평면의 지연 차 때문에 정합이 깨진다(SRS §9.5).

v8 §6-9가 형식을 확정했다 — **`capture_timestamp` 는 epoch 밀리초 정수**다.
업무 메시지 봉투의 `timestamp`(ISO 8601 문자열)와 표기가 다르므로, 영상 경로에서는
`schema.py` 의 봉투를 그대로 쓰지 않고 frame_ref 전용 표기를 따른다(SRS O-13 확인 대상).

## 6. 액추에이터 제어노드 설계 (HW-A)

### 6.1 명령 4단계와 물리 확정

```
cmd 수신 ─► [검증] ─► accepted (cmd/ack)
                       │
                       ├─► executing      (cmd/result)  구동 시작
                       ├─► state_changed  (cmd/result)  ★ 피드백으로 확인한 물리 도달
                       └─► completed / failed
```

**ACK는 "받았다"이지 "했다"가 아니다.** 수문·펌프처럼 되돌리기 어려운 명령은
`state_changed`(센서·제어기 피드백으로 확인한 실제 상태 변화)가 확정 근거다(HW-A-04, BE-X-03).
물리 단계가 없는 설정 명령은 `physical:false`로 표시해, 소비자가 오지 않을 단계를 기다리지
않게 한다.

### 6.2 안전 상태 (HW-A-05)

```
정상 ──통신 두절/장치 오류──► [잠금]  신규 원격 제어 거부 + 사전 정의 안전 상태 유지
                                │
     ◄──복구 + 실제 상태 재확인 완료──┘   ※ 복구만으로 해제하지 않는다
```

두절 중 물리 상태가 바뀌었을 수 있으므로 **복구 직후의 명령을 그대로 받으면 안 된다.**
실제 상태를 먼저 읽어 내부 모델과 맞춘 뒤에 잠금을 푼다. 잠금 상태와 사유는 상태 요약에
실어 가시화가 제어 UI를 잠글 수 있게 한다(VZ-O-05).

## 7. K3s 설계 (HW-C-03)

### 7.1 역할 배치

| | 위치 | 구성 요소 |
|---|---|---|
| 제어평면 | **엣지노드에만** | k3s server (apiserver + 데이터스토어) |
| 워커 | 말단 각 노드 | k3s agent (kubelet + kube-proxy + containerd) |

말단에 server를 두면 apiserver와 내장 데이터스토어가 곧 서버형 미들웨어이자 SD카드 쓰기
폭탄이 되어 P4를 위반한다(SRS §9.1).

### 7.2 워크로드 분류

| 층 | 배포 방식 | 대상 | 실패 시 |
|---|---|---|---|
| 안전 필수 | **systemd** | sensor/robot/actuator node — 계측·임계판정·자율 전환·하트비트·LWT·버퍼링 | 시스템이 눈이 먼다. 절대 k3s에 넣지 않는다 |
| 증강 | **k3s Deployment/Job** | 온디바이스 AI 추론, CCTV·영상 분석, 심화 분석, 모델 버전 배포(HW-R-10) | 증강 기능만 소실. 안전 루프는 무사 |

### 7.3 운용 제약 (SRS §9.6)

| 항목 | 조치 |
|---|---|
| 이벤트 시점 image pull 금지 | 배포 시점에 pre-pull, `imagePullPolicy: IfNotPresent`, **태그 대신 digest 고정**. 이벤트 때는 스케줄링만 → 5초 이내 |
| SD카드 쓰기 마모 | agent에는 데이터스토어가 없으나 containerd 이미지 레이어와 컨테이너 로그가 실제 출처. `/var/lib/rancher`를 NVMe/USB SSD로 이설, kubelet 로그 회전 강제 |
| 자원 격리 | 모든 파드에 requests/limits. kubelet `--kube-reserved`/`--system-reserved`. `*-node.service`에 `OOMScoreAdjust=-500` — 폭주 컨테이너가 안전 루프를 굶기지 못하게 |
| 단절 중 거동 | kubelet은 apiserver 단절 시 실행 중 파드를 계속 돌리나 노드가 NotReady가 되고 재스케줄이 안 된다. **단절 중 파드 crash는 영구 중단으로 보고 설계** |
| 네트워크 회귀 | flannel·kube-proxy가 Debian 13 nftables 위에서 MQTT 1883에 간섭하지 않는지 **k3s 활성화 직후 회귀 검증 필수**. 현재 실기 검증은 전부 k3s 비활성 상태 결과 |

### 7.4 컨테이너 이미지 설계

- 베이스: `python:3.13-slim-bookworm` (arm64). 말단 아키텍처는 aarch64
- 공통 코어(`common/`)를 담은 베이스 레이어를 두고 노드별 이미지가 이를 상속 → pull 대상 축소
- 상주 서비스는 컨테이너화하지 않는다(§7.2). 컨테이너 이미지는 증강 기능 전용
