## 1. 핵심 요약
- API가 요청 메시지에 `string request_id` 필드를 추가해 요청을 고유하게 식별하고, 이를 통해 idempotency(멱등성)를 보장할 수 있도록 하는 설계 가이드라인이다.
- request_id 제공은 "must guarantee idempotency"로 명시되어, 필드를 노출하기로 한 이상 idempotency 보장은 선택이 아니라 요구조건이다.
- request_id 필드 자체는 optional로 두는 것을 권고하며, 포맷은 UUID를 권장하고 `google.api.FieldInfo.Format` UUID4 애노테이션과 결합할 것을 요구한다.
- 서버가 동일 request_id의 재요청(duplicate)을 감지하면 재실행하지 않고 이전의 성공 응답을 그대로 반환해야 한다고 명시한다.

## 2. 문서 목적
- 해결하려는 문제: 네트워크 장애 등으로 클라이언트가 응답을 받지 못해 동일 요청을 재전송할 때, 서버가 이를 별개 요청으로 처리해 side effect(예: 물리 동작, 리소스 생성)를 중복 실행하는 문제.
- 기술적 목표: 클라이언트가 요청에 부여하는 request_id 필드 하나로 idempotency와 안전한 재시도를 보장하고, 서버 측 중복 감지·응답 재사용 정책을 표준화하는 것.
- 다루는 범위: request_id 필드의 이름·타입·optional 여부·포맷(UUID) 권고, 서버의 중복 요청 처리 정책, Google API 전용 애노테이션(FieldInfo.Format) 결합 방식.

## 3. 핵심 개념 상세
### request_id
- 원문 표현: "add a `string request_id` parameter to request messages (including those of standard methods) in order to uniquely identify particular requests."
- 정의: 클라이언트가 요청 메시지에 채워 넣는, 해당 요청을 고유하게 식별하기 위한 문자열 필드.
- 역할: 네트워크 재시도, 클라이언트 재전송, 메시지 큐의 at-least-once 전달 등으로 동일한 논리적 요청이 여러 번 도착할 수 있는 분산 시스템에서, 요청 발신자가 미리 부여한 식별자로 "같은 요청의 재전송"과 "별개의 새 요청"을 구분하는 데 쓰인다. 물리 제어 명령처럼 중복 실행의 대가가 큰 도메인에서는 이 필드를 선택이 아니라 필수로 요구하도록 강화해 쓰기도 한다.

### Idempotency
- 원문 표현: "Providing a request ID must guarantee idempotency."
- 정의: 동일한 요청(같은 request_id)이 여러 번 전달되더라도 실제 side effect는 한 번만 발생하도록 보장하는 성질.
- 역할: 결제, 주문 생성, 물리 장치 제어 명령처럼 중복 실행이 실질적 피해로 이어지는 작업에서, 클라이언트의 재시도가 서버 측 부작용을 두 번 이상 발생시키지 않도록 보장하는 핵심 성질이다. 실무에서는 여기서 한 걸음 더 나아가 동일 식별자로 서로 다른 내용의 요청이 들어오면 이를 단순 중복이 아니라 충돌(conflict)로 판단해 거부하는 정책을 추가하기도 하는데, 이는 원문이 규정한 duplicate 처리 범위를 넘어서는 흔한 실무 확장이다.

### Duplicate Detection
- 원문 표현: "If a duplicate request is detected, the server should return the response for the previously successful request, because the client most likely did not receive the previous response."
- 정의: 서버가 이미 처리한 request_id로 다시 요청이 들어왔음을 감지했을 때, 새로 실행하지 않고 과거 성공 응답을 그대로 재반환하는 처리 방식.
- 역할: 요청 식별자를 키로 이전 응답을 캐시해 두었다가 동일 식별자의 재요청에 그대로 반환하는 구현 패턴의 근거가 된다. 물리적 동작을 유발하는 명령처럼 재실행 자체가 위험하거나 비용이 큰 작업에서 특히 중요한 안전장치다.

## 4. 구조 및 흐름
1. 클라이언트가 요청 메시지에 request_id(UUID 권장)를 채워 서버로 전송한다.
2. 네트워크 실패 등으로 클라이언트가 응답을 받지 못하면, 동일한 request_id를 담아 같은 요청을 재전송한다.
3. 서버는 수신한 request_id가 이전에 처리된 적이 있는지 확인한다.
4. 중복으로 판정되면 서버는 요청을 다시 실행하지 않고, 이전에 성공적으로 처리했던 응답을 그대로 반환한다.
5. request_id는 optional 필드이므로, 클라이언트가 이 필드를 채우지 않은 요청에는 위 idempotency 보장이 적용되지 않는다.

## 5. 핵심 주장과 근거
| 주장 | 근거 |
|---|---|
| request_id를 제공하면 idempotency는 반드시 보장되어야 한다 | "Providing a request ID must guarantee idempotency." |
| 중복 요청은 재실행이 아니라 기존 응답 재사용으로 처리해야 한다 | "If a duplicate request is detected, the server should return the response for the previously successful request, because the client most likely did not receive the previous response." |
| request_id 포맷을 UUID로 표준화하면 충돌 가능성이 줄어든다 | "When a value is required to be unique, leaving the format open-ended can lead to API consumers incorrectly providing a duplicate identifier. As such, standardizing on a universally unique identifier drastically reduces the chance for collisions when done correctly." |

## 6. 한계 및 부족한 점
- AIP-155는 request_id를 optional 필드로만 권고한다("Request IDs should be optional"). 물리 명령의 안전성·감사 추적이 중요한 시스템에서는 이 필드를 optional로 두지 않고 required로 격상해 AIP-155의 권고보다 강한 보장을 취하는 경우가 있는데, 이는 원문의 권고 범위를 넘어서는 설계 선택이다.
- Google API 생태계 밖에서 이 원칙을 재사용하려는 경우, `google.api.FieldInfo.Format` UUID4 애노테이션 같은 Google 전용 Protobuf 구현 의존성까지 가져올 필요는 없다 — request_id의 의미 원칙(요청 식별, 중복 감지, 응답 재사용)만 채택하고 구현 방식은 각 시스템의 직렬화·스키마 도구에 맞게 선택하면 된다.
- "safe retry"라는 표현 자체는 이번 조사에서 원문에 명시적으로 등장하지 않았다(원문 확인 안 됨). 재시도 안전성은 idempotency 보장의 결과로 서술되어 있을 뿐, AIP-155 문서 안에서 별도 용어로 정의되어 있지는 않다.
- 이번 조사 범위(Overview/rationale 일부)에서는 request_id의 유효 기간(retention), 서버 측 중복 판정 저장소 설계에 대한 구체적 가이드는 확인되지 않았다.

## 7. 원문 기반 핵심 문장
> "Providing a request ID must guarantee idempotency."
