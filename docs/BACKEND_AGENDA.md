## 0-1. 아키텍처 v8 반영 (2026-08-31 갱신)

v8 를 받아 대조한 결과 **안건 4건이 해소**되었다. 아래 본문에서 해당 절은 ✅ 로 표시하고
경위를 남겨 두었다(무엇이 어떻게 정해졌는지가 나중에 근거가 되므로 지우지 않는다).

| 해소된 안건 | v8 |
|---|---|
| frame_ref 형식 | §6-9 — `{source_id, capture_timestamp(epoch ms), sequence_id}` |
| 미디어 전송 규격 | §5-10·6-8 — 말단↔엣지 RTP/UDP + JPEG |
| [G2] command_id | §5-6 — 백엔드 발급, MySQL 감사. 말단은 에코 |
| 말단 OTLP 직접 발신 | §5-3·5-8 — 명시 확정 |

**v8 과 요구사항 정의서가 어긋나던 주기 3건은 백엔드 값으로 채택하고 정의서를 개정했다**
(하트비트 5초 · OTel export 15초 · 로봇 대기 5초). 하드웨어가 문서 간 상충을 붙들고 있기보다
전송 아키텍처의 소유자를 따르는 편이 맞다고 판단했다. 회신 불필요이며, 파급은 3번 항목 참조.

## 0. 읽는 방법

말단↔엣지 구간은 **동작하는 상태**다(라즈베리파이 pi7 실기 검증 완료). 아래는 "안 되는
것"이 아니라 **결정권이 백엔드에 있어서 하드웨어가 임시값으로 두고 있는 것**들이다.

하드웨어는 미확정 항목을 어댑터 한 곳(`pi/common/schema.py`)에 가둬 두었다. 확정이 오면
**그 파일 하나만 고치면** 전 노드에 반영된다. 그래서 지금 확정해 주실수록 재작업이 없다.

우선순위: 🔴 발표 전 필수 · 🟡 발표 전 권장 · ⚪ 이후

## 1. 🔴 스키마 필드 확정 (BE-C-01 / HW-C-02)

**배경.** 모든 말단 메시지는 공통 봉투를 싣는다. BE-C-01이 지정한 필드명으로 이미 정렬해
두었으나, 최종 확정 전이라 과도기 별칭을 함께 보내고 있다.

**하드웨어 현재 처리**

```json
{
  "schema_version": "1.3",
  "source_id": "wl-001",      "device_id": "wl-001",   ← 별칭 병기 (과도기)
  "node_id": "pi7",           "zone_id": "zoneA",
  "timestamp": "2026-08-31T12:00:00+0900",
  "seq": 42,                  "correlation_id": "cmd-001",
  "device_status": "ok"
}
```

**필요한 결정**
1. `source_id` 단일화 시점 — 확정 즉시 `LEGACY_DEVICE_ID=False` 한 줄로 별칭을 뺀다.
2. `schema_version` 표기 규칙(현재 `"1.3"` 문자열). semver? 정수?
3. `seq`의 범위 — 채널별 독립 순번으로 두었다. 전역 순번을 원하면 알려 달라.

**미확정 시.** 별칭이 계속 나가 대역과 저장이 낭비된다. 백엔드 파서가 어느 쪽을 정본으로
볼지 모호해진다.

## 2. 🔴 토픽 도메인 체계 (HW-C-02 / BE-T-01)

**배경.** 통합정립본 v3의 `{domain}/{type}/{id}/{channel}`에 맞춰 다음을 쓰고 있다.

```
zoneA/sensor/wl-001/{status|heartbeat|state|cmd|cmd/ack|cmd/result}
zoneA/robot/rb-01/...
zoneA/actuator/gate-01/...
zoneA/analysis/wl-001/state       ← 증강 분석 워크로드
```

**필요한 결정**
1. `{domain}` 자리에 **구역(zoneA)을 넣는 것이 맞는지.** 지금은 그렇게 두었다.
2. `{type}` 어휘 확정 — `sensor / robot / actuator / analysis` 로 쓰고 있다.
3. 채널 이름 확정 — 특히 `cmd/ack`·`cmd/result`처럼 **한 칸 더 들어가는 채널**을 허용할지.
   와일드카드 구독(`+/+/+/#`)에 영향이 있다.
4. MQTT 토픽 → **Kafka 주제 매핑 규칙**(BE-T-02 브릿지). 원본 유지 방침이면 위 구조가
   그대로 Kafka에 올라간다.

**미확정 시.** 구역이 늘어날 때 토픽을 다시 짜야 하고, 브릿지·가시화 구독이 함께 깨진다.

## 3. ✅ 하트비트 주기 — **백엔드 값 채택으로 종결**

> **v8 §5-1 의 5초를 채택**하고 요구사항 정의서를 그에 맞춰 개정했다(HW-S-05 · HW-S-07 ·
> HW-R-02 · HW-A-05). 하드웨어가 문서 간 상충을 붙들고 있기보다 전송 아키텍처의 소유자를
> 따르는 편이 맞다고 판단했다. **회신 불필요** — 아래는 판단 근거와 파급 기록이다.
>
> **파급**: HW-S-07 판정이 4초 → 20초. 다만 실측상 실질 악화는 **7.5초 → 15초**다
> (두 구성 모두 LWT 가 하트비트 타임아웃보다 먼저 잡는다). 프로세스 급사는 여전히 즉시.
> 감지 속도의 지렛대는 하트비트가 아니라 `keepalive` 이며, 이는 v8 이 정하지 않아
> 하드웨어가 10초(LWT 15초)로 두었다. 더 빠른 감지가 필요하면 알려 달라.

### (경위) 어떤 값들이 갈렸나

| 출처 | 값 |
|---|---|
| 요구사항 정의서 xlsx (HW-S-05) | **1 Hz** |
| 데이터 전송 및 아키텍처 v4 | 5초 |
| **데이터 전송 및 아키텍처 v8 §5-1** | **5초** (v4 유지) |

**하드웨어 현재 처리.** 정의서를 따라 **1 Hz**로 구현했다. 오프라인 판정이
"4회 미수신 = 약 4초"(HW-S-07)라서 1 Hz라야 정의서의 4초 판정이 성립한다.
5초 주기면 판정이 20초가 되어 요구사항과 어긋난다.

**필요한 결정.** 둘 중 하나로 통일. 값만 알려 주시면 `HW_HB_INTERVAL` 환경변수라
**코드 수정 없이** 반영된다.

**참고 실측.** 1 Hz × 3노드에서 브로커·말단 부하 문제 없음(노드 CPU 2.2%, 메모리 18M).
부하는 이 결정의 제약이 아니다 — **HW-S-07의 4초 판정을 지킬 것인가**가 쟁점이다.

**v8 이 이 충돌을 다루지 않았다.** §5-1은 하트비트 5초만 적고 HW-S-07의 오프라인 판정
시간은 언급하지 않는다. 둘 중 하나를 정해 주셔야 한다.
- (가) 하트비트 1 Hz 유지 → HW-S-07의 "약 4초" 그대로
- (나) 하트비트 5초 채택 → HW-S-07의 판정 시간을 **20초로 개정**해야 한다

## 4. ✅ [G2] 로봇 cmd/ack의 command_id — **v8로 해소**

> **v8 §5-6이 확정했다** — "백엔드가 명령을 만들 때 발급해 중앙 감사 저장소(MySQL)에
> 기록한다." 하드웨어의 에코 구현이 맞았다. 아래는 판단 경위 기록이다.

**통합정립본 v3 §5의 미회신 항목이었다.** BE-X-01("백엔드가 command_id를 발급하고 전 파트가

추가 질문: 로봇의 `plan_id`(경로 식별자)를 말단이 함께 실어야 하는가?
BE-X-01은 백엔드가 `command_id ↔ plan_id` 매핑을 보유한다고 되어 있어, 말단은
`command_id`만 에코하면 된다고 보고 있다.

## 5. 🔴 [G3] device_status를 누가 내는가 — 회신 요청

**통합정립본 v3 §5의 미회신 항목.** BE-T-04가 상태를 3층(자기보고·서버판정·오케스트레이터)
으로 나누라고 명시하므로, 하드웨어는 **자기보고 층을 직접 발행**하도록 구현했다.

| 값 | 하드웨어의 판정 기준 |
|---|---|
| `ok` | 정상 |
| `degraded` | 미전송 버퍼 존재 / 폐기 발생 / 브로커 단절 / 액추에이터 제어 잠금 |
| `fault` | 센서 읽기 3회 연속 실패 / 내부 링크 fault / 액추에이터 피드백 상실 |

**필요한 결정.** 이 판정 기준을 그대로 쓸지, 아니면 백엔드가 metric·log에서 파생할지.
후자라면 하드웨어는 원자료만 내고 이 필드를 뺀다.

## 6. 🔴 엣지노드 하드웨어 (A-2 / BE-T-01·BE-S-02)

**현재 상태.** 구역 엣지노드 전용 장비가 없어 **개발 PC**가 대신하고 있다.

| 구성요소 | 현재 위치 | 문제 |
|---|---|---|
| MQTT 브로커 | 개발 PC (Windows, Mosquitto) | PC가 꺼지면 구역이 멈춘다 |
| K3s 제어평면 | 개발 PC의 WSL2 | 위와 같음 + 파드 오버레이가 말단까지 닿지 않음 |
| OTel Collector | 검증용 최소 수신단 | BE-S-02의 Agent→Gateway 구조 아님 |
| 미디어 게이트웨이 | 없음 | HW-S-06·R-07 착수 불가 |

**필요한 것.** 현장용 리눅스 장비 1대(구역당). SSD 권장 — etcd는 쓰기 집약적이라
SD·eMMC가 버티지 못한다. 구성 절차는 `docs/EDGE_SETUP.md`에 정리해 두었으므로
장비만 오면 그대로 옮길 수 있다.

**미확정 시.** HW-C-03·HW-C-05의 "실물 검증"이 임시 구성 기준으로만 남는다.
발표 시연 중 개발 PC 의존은 위험 요소다.

## 7. 🟡 명령 결과 4단계 승격 — 하드웨어 발행 형식 확인 (BE-X-03)

하드웨어는 아래를 그대로 발행한다. 백엔드가 이 stage 값을 그대로 승격하면 되는지 확인 부탁.

```
cmd/ack     → stage: accepted | rejected   (+ error 사유)
cmd/result  → stage: executing | state_changed | completed | failed
              physical: true|false
```

**`physical: false`의 의미.** 주기 변경 같은 설정 명령은 **물리 상태 변화 단계가 없다.**
이 플래그가 없으면 소비자가 오지 않을 `state_changed`를 무한정 기다린다.

**액추에이터에서 특히 중요한 점.** 수문·펌프는 `accepted`가 아니라 **피드백으로 확인한
`state_changed`가 확정 근거**다. 도달을 확인하지 못하면 `failed(travel_timeout)`로 낸다 —
도달했는지 모르는 것을 완료로 올리지 않는다.

## 8. ✅ frame_ref 형식 — **v8로 해소**

> **v8 §6-9가 확정했다** — `{source_id, capture_timestamp, sequence_id}` 이며
> **`capture_timestamp` 는 epoch 밀리초 정수**다. 하드웨어가 요청했던 `sequence_id`
> 필수화가 반영되었다.
> **남은 확인 1건**: 업무 메시지 봉투의 `timestamp` 는 ISO 8601 문자열인데 frame_ref 는
> epoch ms 다. 두 표기가 공존하는 것이 의도인지 확인 부탁드린다.
>
> 아래는 판단 경위 기록이다.

### (경위) frame_ref 가 왜 순번을 필요로 하는가

**배경.** 영상은 미디어 평면, 인지 결과는 업무 평면으로 **서로 다른 지연**을 겪는다.
타임스탬프만으로 짝을 맞추면 오차가 누적되어 오버레이 정합이 깨진다.

**하드웨어 제안.** `frame_ref = {source_id, capture_timestamp, sequence_id}`에서
**`sequence_id`(단조 증가)를 필수로** 해 주시길 요청한다. 프레임 단위 결합은 순번으로만
확정된다.

**필요한 결정.** 필드명·타입·순번의 리셋 규칙(재기동 시 0부터? 계속?).

## 9. ✅ 말단 OTLP 직접 발신 — **v8로 해소**

> **v8 §5-3·5-8이 확정했다** — "각 노드는 자기 상태를 OpenTelemetry 규격(OTLP)으로
> 보낸다", "말단은 SDK 로 자기 지표를 OTLP 형식으로 포장해 수집기로 보낸다."
> 통합정립본 v3의 "OTel 미러는 백엔드 브리지" 문구는 v8 로 정리된 것으로 본다.
> 아래는 판단 경위 기록이다.

### (경위) 두 문서가 어떻게 갈렸나

| 출처 | 방침 |
|---|---|
| 통합정립본 v3 | "디바이스는 표준 MQTT만 발행, OTel 미러는 백엔드 브리지" [확정] |
| 데이터 전송 및 아키텍처 v4 · BE-S-02 | 각 노드가 OTLP로 직접 발신 → 엣지 Collector(Agent) |

**하드웨어 현재 처리.** 후자를 채택해 구현·검증했다. metric 5종(CPU·메모리·디스크 여유·
발행 성공/실패·발행 지연)이 OTLP/gRPC로 실제 도착하는 것을 확인했고, resource 속성에
`hw.entity_id`·`hw.node_id`·`hw.zone_id`를 실어 노드를 구분한다.

**필요한 결정.** 통합정립본 v3 문서 갱신 여부. 브리지 방식으로 되돌린다면 말단의 OTLP
발신을 끄고 관측 지표를 MQTT에 실어야 하는데, 이는 P2(업무·관측 평면 분리)와 충돌한다 —
업무 경로가 막혔을 때 원인을 볼 방법이 사라진다.

**남은 항목.** export 주기는 여전히 갈린다 — **10-1** 참조.

## 10. 🟡 TLS·인증 (BE-T-01)

BE-T-01이 MQTT **5.0 + TLS**로 확정했고, 하드웨어는 **5.0을 적용해 검증**했다(브로커 로그
`p5` 확인). TLS는 설정 자리만 두고 꺼져 있다.

**필요한 것.** 엣지 브로커의 CA·서버 인증서, 그리고 말단 인증 방식(클라이언트 인증서 vs
사용자명/암호). 받으면 `HW_TLS_CA` 등 환경변수만 채우면 켜진다.

## 10-1. ✅ OTel export 주기 — **백엔드 값(15초) 채택으로 종결**

> v8 §5-1 의 15초를 채택하고 정의서를 개정했다. 회신 불필요.

### (경위)

| 출처 | 값 |
|---|---|
| 요구사항 정의서 xlsx (HW-C-05) | **60초** |
| 계획서 초안 | 15초 |
| **아키텍처 v8 §5-1** | **15초** |

정의서만 60초이고 나머지 둘이 15초다. 하드웨어는 근거 계층(정의서 우선)에 따라 60초로
구현했으나, v8이 15초를 재확인했으므로 재판정이 필요하다.
`HW_OTEL_EXPORT_INTERVAL` 환경변수라 값만 주시면 코드 수정 없이 반영된다.

## 10-2. 🔴 Prometheus `up` 과 push 전용 말단 — 성립 여부 확인 (v8 표5 ↔ §5-8)

v8 표5는 장치 생사 감지의 하나로 **"엣지 Prometheus가 각 노드를 주기적으로 확인하다
응답이 없으면 up=0"** 을 든다. 그런데 §5-8은 말단이 **OTLP 로 push 만** 하고 서버를
두지 않는다고 한다.

**Prometheus 의 `up` 은 scrape(pull) 대상에만 생긴다.** push 전용 노드는 scrape 대상이
아니므로 그 노드의 `up` 이 존재하지 않는다.

| 해석 | 문제 |
|---|---|
| ① 말단이 `/metrics` 를 연다 | 말단에 서버를 두지 않는다는 §5-8과 충돌 |
| ② 엣지 Collector 를 scrape 하고 **말단별 라벨의 신선도**로 판정 | `up` 이 아니라 파생 지표. v8 문구와 다름 |
| ③ 말단 생사는 업무 평면만 쓴다 | §6-5의 "이중으로 두어 사각을 없앤다"와 다름 |

**하드웨어는 ②를 제안한다.** 말단에 엔드포인트를 열지 않고도 노드별 결손을 볼 수 있고,
§6-5의 "MQTT 세션 우선, 지표 결손은 별도 플래그"와도 맞는다.

## 10-3. 🟡 말단 trace(span) 계측 — **구현 완료, traceparent 형식만 확인 요청** (v8 §5-8)

v8 §5-8이 "말단에서 어디까지 계측할지는 구현 단계에서 정한다"고 하드웨어에 위임했다.
제안 범위 그대로 구현·검증했다(`common/otel_trace.py`, 2026-08-31).

**구현된 범위**: 명령 경로에만 span 3종 —
`cmd.receive`(수신·검증, accepted/rejected+사유) → `cmd.execute`(수행, 단계 승격은
event·실패는 ERROR) → `cmd.result`(회신 발행, 단계마다). 계측·하트비트 같은 고빈도
경로에는 span 을 만들지 않는다(저사양 말단에 부담이고, 그 경로의 문제는 metric 으로
보인다). 이 범위로 §5-7의 "장치 span 이 없으면 명령이 도달하지 못한 것"이 성립한다.

**백엔드 trace 에 잇는 준비도 되어 있다**: 명령 페이로드에 W3C `traceparent` 필드가
있으면 말단 span 이 그 trace 의 자식으로 붙는다(검증 완료 — 관제 클릭부터 물리 동작까지
한 사슬). `command_id` 는 별도 속성으로 항상 붙어 trace 가 없어도 상관 사슬은 남는다.

**확인 요청 한 가지**: 명령에 trace 컨텍스트를 실어 보낼 계획이 있는가? 있다면 필드는
W3C Trace Context 표준(`traceparent`)인가? 없으면 말단이 새 trace 를 시작한다(현 동작).

## 10-4. 🟡 온디바이스 추론 결과의 frame_ref — **규약 결정 요청** (v8 §6-9 ↔ §5-10 ↔ VZ-I-07)

> **하드웨어는 v8 을 그대로 따른다** — 말단은 frame_ref 를 발급하지 않는다.
> 아래는 "그렇게 하면 이 지점이 비는데 어떻게 채울지 정해 달라"는 요청이지
> 하드웨어가 규약을 바꾸자는 제안이 아니다.

세 문장이 함께 서지 않는다.

| 출처 | 내용 |
|---|---|
| v8 §6-9 | frame_ref 는 **엣지가 디코드 시점에 발급**, 생산 측은 **재생성 금지** |
| v8 §5-10 | 환경인식용 다운스케일 프레임은 **온보드 내부 처리라 네트워크 미디어 경로가 아니다** |
| VZ-I-07 | **온디바이스 안전 판단 결과**를 영상 위에 겹쳐 그린다(출처 구분 표시 포함) |

온디바이스 추론 프레임은 엣지를 거치지 않으므로 엣지가 그 프레임의 frame_ref 를 발급할
수 없다. 그런데 결과는 MQTT 로 올라가고 가시화가 오버레이해야 한다. **붙일 식별자가 없다.**

**언제 문제가 되나**: 관제 스트림이 **열려 있을 때만**이다. 닫혀 있으면(온디맨드라
평시 상태) 가시화에 영상 자체가 없어 오버레이할 대상이 없다. 또 HW-R-04 는 로봇 실물·
AI 모델 모두 미확보라 지금 막고 있는 것은 아니다 — **구현 전에 규약만 정하면 되는 사안**이다.

**선택지**(백엔드가 정해 주시면 하드웨어는 그대로 따른다):
① 온디바이스 결과에 `capture_timestamp` 만 싣게 하고 가시화가 시각으로 근사 정합
   (전 노드 NTP 동기이므로 BE-C-03·AI-C-03 전제와 맞는다) —
   **필드 하나만 열어 주시면 되고 v8 의 "엣지 단일 발급"도 깨지 않는다**
② 온디바이스 결과는 오버레이 대상에서 빼고 경보·텍스트로만 표시 (VZ-I-07 축소)
③ 그 외 백엔드가 정한 방식

참고로 BE-C-03("형식이 AI·**하드웨어**·가시화 간 공유되어야")과 VZ-I-07("AI·**하드웨어**와
동일한 형식을 사용")은 하드웨어가 frame_ref 를 쓰는 것을 전제한다. v8 의 엣지 단일 발급과
문구가 어긋나므로 어느 쪽으로 정리할지도 함께 알려 주시면 좋겠다.

## 10-5. 🟡 JPEG 대역폭 — 로봇의 홉1 은 무선이다 (v8 §5-10)

v8 은 JPEG 의 큰 대역폭을 "홉1이 로컬 LAN(기가비트)이라 제약이 아니다"로 정당화한다.
**고정 CCTV 는 맞지만 로봇은 이동체라 무선이다.**

**실측(pi7 → 노트북, `wlan0`)**: 720p@15 q=5 한 스트림이 **6.8 Mbps**. 한 대는 여유가
있으나 로봇이 늘거나 전파 환경이 나빠지면 곧 문제가 된다. v6 에 있던 "무선 대역폭이
부족하면 프레임 간 압축 코덱으로 전환" 단서가 **v8 에서 삭제**되어 문서상 탈출구도 없다.

**하드웨어 대응(선반영)**: 품질(q)이 대역폭의 지렛대임을 실측 확인했다 — 1080p 에서
q 5→12 로 9.7→5.5 Mbps 인데 CPU 는 그대로다. 해상도를 낮추기 전에 q 를 올리는 것을
기본으로 두고 `HW_MEDIA_QUALITY` 로 조절 가능하게 해 두었다.

**필요한 결정**: 무선 대역이 부족할 때의 방침 — ①q 상향 ②해상도 하향 ③프레임 간 압축
코덱 전환(v8 에서 삭제된 선택지) 중 무엇을 허용하는가.

## 10-6. 🟡 로봇 영상은 push 인가 pull 인가 (v8 §5-10)

v8 은 "연결은 **엣지가 카메라에 접속해 당기는 pull 을 기본**으로 한다"면서, 같은 절에서
로봇 온보드는 "RTP 를 **직접 송출**"(push)한다고 한다.

**하드웨어 구현은 push 다** — 온디맨드 개폐를 MQTT 명령으로 받는 이상(HW-R-07),
명령을 받고 말단이 송출을 시작하는 push 가 자연스럽다. 표준 IP 카메라만 pull(RTSP)로 본다.
이 해석이 맞는지 확인 부탁드린다.

## 10-7. 🔴 로봇 영상 코덱 — Go1 은 H.264 를 준다 (O-20, v8 §5-10)

**Go1 실기에서 확인된 사실 (2026-08-31).** 로봇은 5개 카메라 전부를 **이미 H.264 로
인코딩해 상시 송출**하고 있다(온보드 하드웨어 인코더, 464x400@30, 카메라당 0.55 Mbps).
말단(파이)은 이 스트림을 받아 **디코드·재인코딩 없이** RTP 로 중계하는 구현을 완료했다
(RFC 6184 패킷화, `robot/go1_relay.py` — 세션 개폐는 기존 MQTT `stream` 명령 그대로).

**v8 §5-10 은 JPEG 로 확정했는데, 로봇 영상에 그대로 적용하면 손해가 실측으로 크다.**

| | H.264 무변환 중계 | 파이에서 JPEG 재인코딩 |
|---|---|---|
| 말단 지연 | **0.1 ms** | 37 ms + 디코드 |
| 말단 CPU | **0.05 코어** | 0.65 코어 이상 |
| 홉1 대역폭 (무선!) | **0.55 Mbps** | 3.6 Mbps |

JPEG 의 장점(프레임 독립·유실 비전파)은 인정하나, 로봇 스트림은 IDR 이 0.5초 간격이라
유실 전파가 최대 0.5초에서 끊긴다. 홉1 이 무선인 로봇에서 대역폭 6.5배는 결정적이다.

**요청.** 엣지 미디어 게이트웨이의 수신 코덱 결정:
  ① 소스별 협상 — 로봇은 H.264, 고정 CCTV 는 JPEG (하드웨어 권고. 둘 다 구현 완료)
  ② H.264 로 통일 ③ JPEG 로 통일(로봇도 재인코딩 — 위 표의 비용 감수)
SDP 는 말단이 세션 수립 시 명령 회신에 실어 보낸다(`packetization-mode=1`, SPS/PPS 인밴드).

## 11. ⚪ 로봇 20 Hz의 근거 재산정 (HW-R-03)

**문제.** 정의서의 20 Hz 근거는 Nav2 `controller_frequency` 기본값인데, 이것은 **로봇 내부
제어 루프 주기**이지 네트워크 텔레메트리 주기가 아니다. 카테고리가 다르다.

**하드웨어 현재 처리.** 20 Hz를 **설정값**으로 두고 구현·실측했다(19.9 Hz 달성).
재산정 결과가 나오면 코드 수정 없이 반영된다.

**v8 추가 상충.** v8 §5-1은 로봇 상태를 "임무 중 50ms · **대기 5초**"로 적는데,
정의서(HW-R-03)는 "대기 중 **1초**"다. 대기 중 하트비트(HW-R-02, 대기 시에만 전송)와의
관계도 함께 정리해야 한다 — 상태가 5초면 하트비트가 생존 신호의 주 경로가 된다.

**함께 확정할 것 — QoS.** 20 Hz 상태 스트림은 **QoS 0**으로 보내고 있다. 다음 표본이
50 ms 뒤 오므로 유실이 상쇄되고, QoS 1 왕복(무선 실측 ~150 ms)이 주기보다 길어 부적합하다.
**이산 사건**(모드 전환·배터리 경보·명령 결과)만 QoS 1이다. 백엔드 저장 정책이 QoS 0
스트림을 전제로 하는지 확인 부탁.

## 12. ⚪ 두절 후 재전송 정책 (HW-R-09 / BE-S-01·BE-S-04)

**문제.** 20 Hz에서 10분 두절이면 12,000건이다. 이를 전량 재전송하면 막 복구된 저대역
링크가 과거 데이터로 막혀 **현재 상태와 명령 ACK가 뒤로 밀린다.**

**하드웨어 현재 처리.** 종류를 갈라 다룬다.

| 종류 | 정책 |
|---|---|
| 이산 이벤트(모드 전환·경보·명령 결과·임무 전이) | **전량·시간순 재전송.** 하나가 빠지면 사건의 인과가 끊긴다 |
| 연속 상태값(위치·속도·수위 추이) | **1 Hz로 다운샘플** 후 재전송 |

실측: 63초 두절 중 1,257건 적재 → **64건 재전송**(95% 감축), 잔량 0.
재전송분에는 `replayed: true` 표식을 실어 "지금 값"과 구분한다.

**필요한 결정.** BE-S-04(재난 구간 데이터 장기 보존, 지속 학습 재료)와 충돌하지 않는지.
연속값 원본이 학습에 필요하다면 다운샘플 대신 **말단에 보관 후 사후 수집**하는 방식으로
바꿔야 한다. 다운샘플 간격(현재 1 Hz)도 함께 정해 주시면 좋겠다.

## 13. ⚪ 환경 사전정보 제공 형식 (BE-A-05 / HW-R-08)

로봇이 구역 진입 시 맵·경로·환경정보를 **전체 1회 + 변경 시 델타**로 받는다.
필요한 것: 전달 채널, 스키마, **델타 유실 시 전체 재동기 요청 경로**.
델타만 있고 재동기 경로가 없으면 한 번 놓친 로봇이 조용히 낡은 맵으로 주행한다.
