## 1. 개요

### 1.1 목적

재난(하천 범람) 대응 IoT 텔레메트리 시스템에서 **말단 장치(센서노드·로봇 온보드·액추에이터
제어노드)와 구역 엣지노드 사이 구간**의 소프트웨어 요구사항을 확정한다. 이 문서는 xlsx
요구사항 정의서의 30건을 검증 가능한 형태로 재기술하고, 타 파트 요구사항에서 파생되는
하드웨어 측 제약을 함께 명시한다.

### 1.2 범위

**포함**: 말단 장치에서 동작하는 소프트웨어 — 계측 수집, 보고, 하트비트, 등록,
명령 수신·수행·응답, 두절 대비 버퍼링, 자기 관측, 컨테이너 패키징, 영상 송출.

**제외**: 엣지노드 자체의 로직(백엔드 파트), Kafka 브릿지(백엔드), AI 모델 자체(AI 파트),
가시화 화면(가시화 파트). 단 이들과의 **인터페이스**는 본 문서의 대상이다.

### 1.3 용어

| 용어 | 정의 |
|---|---|
| 말단(End node) | 현장에 설치되는 라즈베리파이 급 장치. 센서노드 / 로봇 온보드 / 액추에이터 제어노드의 3종 |
| 엣지노드(Edge node) | 구역 단위 서버. MQTT 브로커, K3s 제어평면, OTel Collector(Agent)를 보유 |
| Entity / Node / Zone | BE-C-02가 정의한 식별자 3계층. Entity=논리 개체, Node=물리 노드, Zone=구역 |
| 업무 평면 | 계측·상태·명령이 흐르는 MQTT 경로 |
| 관측 평면 | 노드 자기 지표가 흐르는 OTLP 경로. 업무 평면과 분리 |
| 미디어 평면 | 영상 픽셀이 흐르는 경로. 업무·관측과 분리(AI-C-08) |
| 상태 3층 | device_status(자기보고) / availability(서버판정) / deployment(오케스트레이터). BE-T-04 |
| 4단계 승격 | 명령 진행을 ACK→수행중→물리변화→완료·실패로 추적. BE-X-03 |

## 2. 전체 설명

### 2.1 시스템 맥락

```
                          [구역 엣지노드]
  [말단 장치]         ┌──────────────────────┐        [백엔드 서버]
  ┌───────────┐  MQTT │ Mosquitto (브로커)    │ Kafka  ┌──────────┐
  │ 센서노드   │──5.0─►│ K3s 제어평면(server)  │───────►│ 저장·트윈 │
  │ 로봇 온보드 │──OTLP►│ OTel Collector(Agent)│        │ 임무·감사 │
  │ 액추에이터  │──미디어►│ 미디어 게이트웨이      │        └──────────┘
  └───────────┘       └──────────────────────┘             │
        ▲  K3s 워커로 편입 (컨테이너 배포/제거)                  ▼
        └──────────────────────────────────────────    [가시화 클라이언트]
```

말단은 **세 개의 분리된 평면**으로 엣지와 통신한다. 업무 경로가 막혀도 관측 경로로 원인을
볼 수 있어야 하므로 평면을 합치지 않는다.

### 2.2 말단 장치 분류 (요구사항 8: 로봇과 센서 분할)

| 구분 | 장치 | 담당 요구사항 | 특성 |
|---|---|---|---|
| **S계열** | 센서노드 (라즈베리파이 + 환경센서) | HW-S-01~08 | 고정 설치, 상시 전원, 저주기 보고가 기본. 사건 시 고주기 |
| **R계열** | 로봇 온보드 (라즈베리파이 + 제어기 + 카메라) | HW-R-01~10 | 이동, 배터리 구동, 고주기(20Hz) 상태 보고, 영상·추론 부하 |
| **A계열** | 액추에이터 제어노드 (수문·차수벽·펌프) | HW-A-01~05 | 되돌리기 어려운 물리 구동. 안전 상태 유지가 최우선 |
| **공통** | 위 3종 전부 | HW-C-01~07 | 전송 규격·스키마·등록·명령·관측·식별의 공통 기반 |

S계열과 R계열은 **동일한 공통 기반(HW-C) 위에서 서로 다른 상위 기능을 갖는다.** 하트비트·
등록·명령 ACK·버퍼링·관측은 공유하고, 계측 로직과 주기·영상 처리·구동 인터페이스가 갈린다.

### 2.3 운용 환경 (실측, 2026-08-31)

| 항목 | 값 |
|---|---|
| 말단 하드웨어 | Raspberry Pi 5, 8GB RAM, 마이크로SD 128G(여유 90G) |
| OS / 런타임 | Debian 13 (trixie), 커널 6.12.47, Python 3.13.5 |
| 시각 동기 | chrony, 엣지/상위 NTP 대비 오차 77µs 실측 |
| 통신 | 유선/무선 IP망. 현장망은 인터넷 단절 가능(국가 인프라 전제) |
| 설치 라이브러리 | paho-mqtt 2.1.0, opentelemetry 1.44.0(sdk·otlp grpc/http), psutil 7.2.2, grpcio 1.83.0 |
| 오케스트레이션 | k3s·kubectl 설치됨(서비스 비활성). cgroup memory 활성 |

### 2.4 제약

- **C-1** 저사양 말단이므로 상시 상주 기능을 최소화한다. 브로커·수집기·중앙 저장소 등
  **서버형 미들웨어를 말단에 설치하지 않는다** (AI-B-10).
- **C-2** 현장망 단절이 상시 발생할 수 있으므로 말단은 엣지 부재 상태에서도 계측을 계속하고
  데이터를 잃지 않아야 한다.
- **C-3** 마이크로SD는 쓰기 마모가 있다. 버퍼·로그의 쓰기량을 통제한다.
- **C-4** 되돌리기 어려운 물리 명령은 중복 실행되지 않아야 한다(QoS 1 재배달 환경).
- **C-5** 전송 프로토콜·스키마·식별자 체계의 **결정권은 백엔드**에 있다(HW-C-01, HW-C-02).
  하드웨어는 확정 전까지 어댑터 계층으로 격리해 확정 시 국소 수정으로 흡수한다.

### 2.5 가정 및 의존

| ID | 가정·의존 | 미충족 시 영향 |
|---|---|---|
| A-1 | 엣지노드가 MQTT 브로커를 제공한다 | 말단은 버퍼링으로 버티나 실시간성 상실 |
| A-2 | 엣지노드가 K3s server(제어평면)를 제공하고 말단을 워커로 편입한다 | HW-C-03·S-03·S-04 불가 |
| A-3 | 엣지노드가 OTel Collector(Agent)를 제공한다 | HW-C-05 미달, 노드 동작에는 영향 없음 |
| A-4 | 백엔드가 command_id를 발급한다 (BE-X-01) | 말단이 임시 발급해야 하며 상관 사슬이 끊김 |
| A-5 | 센서 모델이 선정되어 데이터시트가 확보된다 | HW-S-01 샘플링 주기 확정 불가 |
| A-6 | 로봇 제어기·액추에이터 실물이 확보된다 | HW-R·HW-A 계열 검증 불가 |

## 3. 외부 인터페이스 요구사항

### 3.1 업무 평면 — MQTT (HW-C-01)

**IF-MQTT-1** 말단↔엣지 구간은 **MQTT 5.0**을 사용한다. (BE-T-01 확정)
**IF-MQTT-2** 최종 운용에서는 TLS를 적용한다. 인증서는 엣지가 제공한다.
**IF-MQTT-3** 토픽 체계는 `{zone}/{type}/{entity}/{channel}` 로 한다.
통합정립본 v3의 `{domain}/{type}/{id}/{channel}`과 정렬하며, 최종 표현은 백엔드 확정을 따른다.

| 채널 | 방향 | QoS | retained | 근거 |
|---|---|---|---|---|
| `status` | 말단→엣지 | 1 | ○ | 등록·요약·종료. retained라야 늦은 구독자가 즉시 현재값 확보(BE-T-06/VZ-I-02) |
| `heartbeat` | 말단→엣지 | 0 | × | 다음 신호가 곧 오므로 유실 허용 |
| `state` | 말단→엣지 | 1 | × | 계측·로봇 상태. 유실 불가 |
| `cmd` | 엣지→말단 | 1 | × | 명령 |
| `cmd/ack` | 말단→엣지 | 1 | × | 수신 확인(1단계) |
| `cmd/result` | 말단→엣지 | 1 | × | 2~4단계 |

**IF-MQTT-4** 세션 단절 감지를 위해 LWT(Last Will)를 등록한다. 브로커가 대신 발행하는
`status` 메시지로 급사를 알린다.

### 3.2 메시지 스키마 (HW-C-02 / BE-C-01 · BE-C-02)

**IF-MSG-1** 모든 발행 메시지는 다음 공통 봉투를 포함한다.

| 필드 | 의미 | 근거 |
|---|---|---|
| `schema_version` | 스키마 버전 | BE-C-01 |
| `source_id` | Entity 식별자 (예: `wl-001`) | BE-C-01 / BE-C-02 |
| `node_id` | 물리 노드 식별자 (예: `pi7`) | BE-C-02 |
| `zone_id` | 구역 식별자 | BE-C-02 |
| `timestamp` | 측정·발행 시각 (ISO 8601, 오프셋 포함) | HW-S-08 / BE-C-03 |
| `seq` | 채널별 순번 | 유실·순서 판정 |
| `correlation_id` | 명령 상관키(command_id 에코) | BE-X-01 |
| `device_status` | 자기보고 상태 ok/degraded/fault | BE-T-04 |

**IF-MSG-2** 확정 전까지 `device_id`를 `source_id`의 별칭으로 병기한다. 확정 시 어댑터
한 곳에서 제거한다.

### 3.3 관측 평면 — OTLP (HW-C-05 / BE-S-02)

**IF-OTEL-1** 말단은 자기 지표를 **OTLP로 엣지 Collector(Agent)** 에 발신한다.
Agent가 가공해 백엔드 Collector(Gateway)로 모은다.
**IF-OTEL-2** metric 최소 5종: CPU 사용률, 메모리 사용률, 디스크 여유, 발행 성공/실패 건수,
발행 지연. export 주기 60초.
**IF-OTEL-3** 관측 경로 부재가 업무 기능을 중단시켜서는 안 된다.

> ⚠ **상충**: 통합정립본 v3는 "디바이스는 표준 MQTT만 발행, OTel 미러는 백엔드 브리지"로
> 기재. 아키텍처 v4와 BE-S-02는 각 노드의 OTLP 직접 발신. **본 SRS는 후자를 채택**하며
> v3 문서 갱신을 백엔드에 요청한다. (미결 O-3)

### 3.4 오케스트레이션 — K3s (HW-C-03)

**IF-K3S-1** 말단은 엣지노드 K3s의 **워커(agent) 노드로 편입**된다. 제어평면(server)은
엣지에 둔다 — 말단에 서버형 미들웨어를 두지 않는다는 C-1과 정합.
**IF-K3S-2** 말단의 수집·보고·모니터링 기능은 기능 단위 컨테이너로 패키징한다.
**IF-K3S-3** 컨테이너의 생존 감시·자동 재기동은 K3s(liveness probe·파드 상태)가 담당한다.
노드 자체의 생존 확인은 HW-S-05 하트비트가 담당한다. **둘은 다른 층이다.**

### 3.5 미디어 평면 (HW-S-06 / HW-R-07)

**IF-MED-1** 영상 픽셀은 MQTT·Kafka·OTLP에 싣지 않고 별도 미디어 경로로 전송한다(AI-C-08).
**IF-MED-2** 최종 소비자가 브라우저이므로 엣지에 미디어 게이트웨이를 두어 뷰어가 재생 가능한
형식으로 변환한다(VZ-I-06). 말단↔엣지 구간 규격과 엣지↔뷰어 구간 규격은 다를 수 있다.
**IF-MED-3** 프레임과 인지 결과의 정합을 위해 `frame_ref(source_id, capture_timestamp,
sequence_id)`를 유지한다(BE-C-03 / VZ-I-07).

## 4. 기능 요구사항

표기: **상태** ✅구현·검증 완료 / ◐부분 / ⏳미착수 / ⛔선행조건 미충족

### 4.1 공통 (HW-C)

#### HW-C-01 하드웨어–엣지노드 전송 인터페이스
- **요구**: 백엔드가 최종 확정한 전송 인터페이스·프로토콜을 따라 송수신한다.
- **확정 내용**: MQTT 5.0 + TLS (BE-T-01).
- **검증**: 말단이 MQTT 5.0(protocol level 5)으로 접속하고 브로커 로그에 `p5`로 기록됨.
  TLS는 인증서 확보 후 핸드셰이크 성공 확인.
- **상태**: ◐ — MQTT 5.0 적용·검증 완료, TLS 미적용(엣지 인증서 부재)

#### HW-C-02 표준 메시지 규격·채널/토픽 체계
- **요구**: 공통 스키마(장치ID·타임스탬프·값·상태코드·스키마 버전)와 합의된 채널 구조를 따른다.
- **검증**: 발행 전 채널의 메시지가 §3.2 봉투 필드를 모두 포함하는지 스키마 검사.
- **상태**: ◐ — BE-C-01 필드로 정렬 완료, 백엔드 최종 확정 대기

#### HW-C-03 컨테이너 기반 구조 (K3s 배포·제거)
- **요구**: 수집·보고·모니터링 기능을 기능 단위 컨테이너로 패키징하고, 엣지 K3s가 말단을
  워커로 편입해 상황에 따라 배포/제거한다. 기능별 장애 격리와 셀프힐링을 확보한다.
- **검증**: 말단이 `kubectl get nodes`에 Ready로 표시됨. 기본 컨테이너 상주 확인.
  컨테이너 강제 종료 시 K3s가 자동 재기동. 고주기 컨테이너 배포/제거 왕복.
- **상태**: ✅ (임시 엣지) — 개발 PC 의 WSL2 에 K3s server 를 세워 pi7 을 **워커로 편입**하고
  증강 컨테이너의 배포 → 셀프힐링(Exit 137 → 자동 재기동) → 제거 왕복을 검증했다.
  구성 절차는 `docs/EDGE_SETUP.md`.
  ⚠ WSL2 는 **검증용 임시 구성이며 검증 후 철수**했다(pi7 은 원래 클러스터의 워커였다).
  현장에는 전용 장비가 필요하다 — 재현 절차는 EDGE_SETUP §6.

#### HW-C-04 장치 상태·구역 등록 관리
- **요구**: 최초 접속 시 구역·장치 정보를 등록(Birth)하고 단절 시 즉시 반영(Death)한다.
  상태 요약을 10초 주기로 갱신한다. Sparkplug Birth/Death 패턴과 동일.
- **검증**: 접속 시 retained `status`에 등록 정보 발행. 10초마다 요약 갱신.
  급사 시 LWT death, 계획 종료 시 shutdown으로 **구분** 발행.
- **상태**: ✅

#### HW-C-05 관측 데이터(OpenTelemetry) 계측
- **요구**: CPU/메모리, 전송 성공·실패, 지연을 OTel 규격으로 계측해 엣지 Collector에 전달.
- **검증**: Collector 수신단에서 metric 5종이 60초 간격으로 도착하고 resource 속성에
  entity/node/zone이 실려 있음을 확인.
- **상태**: ✅ (수신단 대체) — pi7 에서 OTLP/gRPC 로 metric 5종이 60초 주기로 실제 도착함을
  확인했다. resource 속성에 entity/node/zone 이 실린다. 발행 지연은 PUBACK 왕복으로
  실측되며(2.2~52 ms), QoS 0 발행은 왕복이 없으므로 지연 표본에서 제외한다.
  ⚠ 검증에 쓴 것은 최소 수신단이며 **엣지 Collector(Agent) 실물은 여전히 부재**(A-3)

#### HW-C-06 제어 명령 수신 및 ACK 응답
- **요구**: 명령(주기 변경, 프로세스 기동/종료, 임무 하달, 모터 구동)에 수신 확인(ACK)과
  수행 결과를 응답한다. 되돌리기 어려운 명령은 하달→수신확인→수행결과까지 하나의 절차로 보장.
- **파생(BE-X-03)**: 진행을 ACK→수행중→물리변화→완료·실패 4단계로 발행한다.
  물리 단계가 없는 설정 명령은 그 사실을 명시한다(`physical:false`).
- **파생(BE-X-01)**: command_id는 백엔드가 발급하며 말단은 에코한다.
- **파생(VZ-O-01)**: 명령은 추상 `action`+`params` 형태이며 `expires_at` 경과 시 실행 금지.
- **파생(C-4)**: 동일 command_id 재배달 시 재실행하지 않고 이전 응답을 재송신한다.
- **검증**: 물리 명령 4단계 왕복, 설정 명령 3단계, 거부 4종(누락·미지원·만료·파라미터),
  중복 배달 억제.
- **상태**: ✅

#### HW-C-07 고유 device_id 기반 장치 식별·엣지노드 매핑
- **요구**: 최초 등록 시 고유 device_id 제공. 엣지는 device_id↔MAC·IP·유형·구역·엣지노드를
  매핑 관리. **MAC은 네트워크 정보로만 쓰고 영구 식별자로 단독 사용하지 않는다.**
- **파생**: 네트워크 또는 구역 변경 시 갱신 등록한다. 구역 변경 시 옛 구역의 retained 등록을
  삭제해 유령 장치가 남지 않게 한다.
- **검증**: `/etc/device_id` 기반 등록. zone/MAC/IP 변경 주입 시 재등록 발행.
  동일 device_id 중복 접속 시 경보.
- **상태**: ✅

### 4.2 센서노드 (HW-S)

#### HW-S-01 계측값 수집
- **요구**: 수위·온도·습도 등 환경센서의 원시값을 **센서가 낼 수 있는 최대 속도로 상시 수집**한다.
  필터링·다운샘플링의 취사선택은 원본을 모두 쥔 말단이 담당한다. 수집값에 측정 시각과 장치ID 부여.
- **주기**: 선정 센서 데이터시트의 최대 유효 샘플링 속도
- **검증**: 데이터시트 기준 샘플링 주기로 수집되고, 수집과 보고가 분리되어 있음을 확인.
- **상태**: ⛔ — 센서 미조달(A-5). 가짜 생성기로 파이프라인만 검증. 교체 지점 1개 함수로 격리

#### HW-S-02 계측 데이터 전달 (평시)
- **요구**: **상시 상주하는 기본 수집 컨테이너**가 계측값을 저주기(1분)로 엣지에 전달한다.
  임계값 초과·**급변(변화율 초과)** 은 로컬에서 즉시 감지해 보고 주기와 무관하게 즉시 발행한다
  (report-by-exception, SCADA 표준 패턴). 기본 컨테이너는 하트비트와 함께 항상 유지된다.
- **주기**: 평시 60초 + 사건 시 즉시
- **검증**: 60초 주기 보고. 임계 3.0m 돌파 시 즉시 발행. 히스테리시스로 경계 떨림 억제.
  임계 미도달 상태에서도 변화율 초과 시 즉시 발행.
- **상태**: ✅ (가짜 센서 기준) — 단 "기본 수집 컨테이너" 형태는 ⏳ (HW-C-03 의존)

#### HW-S-03 이벤트 모드 고주기 보고
- **요구**: 강우 감지·수위 임계 초과 등 이벤트 시 **엣지노드의 쿠버네티스가 센서노드에
  고주기 모니터링 컨테이너를 배포**하여 1초 주기 보고로 전환한다. 상황 종료 시 컨테이너
  제거로 평시 복귀. 재난 골든타임 때문에 실시간성에 준하는 갱신이 필요.
- **주기**: 1초 (1 Hz)
- **검증**: 이벤트 주입 → 고주기 컨테이너 배포 → 1초 보고 → 종료 시 제거·평시 복귀.
- **상태**: ◐ — 1Hz 보고 로직 구현·검증. **컨테이너 배포 형태는 ⏳**(HW-C-03 의존)

#### HW-S-04 적응형 주기 전환 명령 수신
- **요구**: 엣지가 상황 판단에 따라 모니터링 모드를 전환한다. **전환의 실체는 쿠버네티스를
  통한 컨테이너 배포/제거이다.** 센서 단독 판단이 아닌 엣지 주도 제어로 구역 단위 일관성 확보.
- **검증**: 엣지의 배포/제거 조작만으로 보고 주기가 바뀜. 센서 단독으로는 평시 모드를 유지.
- **상태**: ◐ — MQTT 명령 경로 구현·검증. **컨테이너 경로 ⏳**. 두 경로의 역할 분담은 설계 쟁점(O-5)

#### HW-S-05 센서노드 하트비트
- **요구**: 상시 노드가 자신의 생존을 엣지에 주기 전송한다. **하트비트는 노드 수준의 생존
  확인이며, 개별 기능 컨테이너의 생존은 K3s liveness probe가 감시**한다. "센서값 무변화"와
  "노드 장애"와 "컨테이너 장애"를 구분하기 위해 계측과 별도 채널이 필요.
- **주기**: 1초 (1 Hz)
- **검증**: 1Hz 하트비트 수신. 컨테이너만 죽였을 때와 노드가 죽었을 때가 구분됨.
- **상태**: ✅ (노드 하트비트) — 컨테이너 층 구분은 HW-C-03 의존

#### HW-S-06 고정 비전센서(CCTV) 영상 전달
- **요구**: 구역 고정 카메라의 영상 스트림을 엣지로 상시 전달한다. 객체 탐지는 엣지·서버가
  수행하고 카메라는 촬영·전달만 담당한다. 위치가 고정되어 상대 거리 산출이 용이하므로
  디지털 트윈의 1차 구성·동기화 및 신규 객체 출현 감지의 기준 입력이 된다.
- **주기**: 상시 15 fps
- **검증**: 엣지에서 15fps 스트림 수신. frame_ref로 프레임 역추적 가능.
- **상태**: ⛔ — 카메라 미조달, 미디어 게이트웨이 부재

#### HW-S-07 오프라인 감지 및 상태 반영
- **요구**: 센서노드의 비정상 종료·전원 차단·통신 두절을 엣지가 감지해 메인서버에 반영한다.
  **확정 프로토콜의 세션 단절 감지를 우선 사용**하고, 없으면 하트비트 타임아웃을 사용한다.
- **주기**: 하트비트 4회 연속 미수신(약 4초) 후 즉시 반영
- **검증**: 급사 시 LWT 즉시 + 하트비트 4회 미수신 판정의 이중 감지. 계획 종료와 구분.
- **상태**: ✅ (엣지 대역을 `monitor.py`로 대행. 엣지노드 구축 시 이전)

#### HW-S-08 시각 동기화(타임스탬프)
- **요구**: 모든 말단(로봇 온보드 포함)이 NTP로 시각을 동기화하고 모든 계측에 측정 시각을
  포함한다. 서버 병합·정렬과 트윈 시의성 판단의 전제.
- **검증**: chrony 동기 상태 확인, 전 메시지에 오프셋 포함 ISO 8601 타임스탬프 존재.
- **상태**: ✅ (실측 오차 77µs)

### 4.3 로봇 온보드 (HW-R)

> R계열은 실물 로봇 확보 전이다(A-6). 공통 기반(HW-C)과 HW-R-02·R-09는 S계열에서 검증된
> 코드를 재사용하므로, 로봇 확보 시 상위 기능만 추가하면 된다.

#### HW-R-01 로봇 내부 데이터 전달 (제어기→온보드)
- **요구**: 제어기가 배터리·위치·속도·동작 모드·온디바이스 인식 결과를 온보드 파이로 전달한다.
  외부 통신·버퍼링·중계를 온보드에 위임해 제어기는 주행·임무에 자원을 집중한다.
- **주기**: 20 ms (50 Hz) — ROS 2 Control JointTrajectoryController `state_publish_rate` 기본값
- **검증**: 50Hz 수신 확인, 유실률 측정. 내부 수집 주기가 외부 전송 주기보다 빠름을 확인.
- **상태**: ⛔

#### HW-R-02 하트비트 전송
- **요구**: 온보드가 생존 상태를 주기 전송한다. **임무 수행 중에는 상태 데이터(HW-R-03)가
  하트비트를 겸하므로 대기 상태에서만 별도 전송**한다.
- **주기**: 대기 중 1 Hz
- **검증**: 대기 중 1Hz 하트비트, 임무 중 하트비트 정지 + 상태 데이터로 생존 판정 유지.
- **상태**: ⛔ (S계열 하트비트 로직 재사용 예정)

#### HW-R-03 상태 데이터 전달
- **요구**: 내부 수집 상태(배터리·위치·속도·동작 모드)를 엣지로 전송한다. 관제가 실시간
  상황 파악과 임무 할당·이상 판단의 기초로 사용한다. **HW-R-05의 수행 시작/완료/실패 보고를
  이 채널에 포함**한다.
- **주기**: 임무 중 50 ms (20 Hz) — Nav2 `controller_frequency` 기본값 / 대기 중 1 Hz
- **검증**: 임무 중 20Hz 도달률, 대기 중 1Hz. 서브태스크 상태 전이가 포함됨.
- **상태**: ⛔

#### HW-R-04 환경인식용 이미지 및 온디바이스 인식
- **요구**: 로봇 카메라 프레임을 온보드 경량 인지 모델 입력으로 사용한다. **온디바이스
  하드웨어가 파이와 카메라뿐이므로 metric distance 센서를 전제하지 않는다.** 객체 의미 분류
  하나에 안전을 의존시키지 않고, 영상에서 직접 확인 가능한 진행영역·객체 접근 변화로
  최소 안전 기능을 구성한다. 정밀 분류·추적은 AI 파트 모델과 연동.
- **입력 규격**: 다운스케일(640급)
- **검증**: 추론 FPS 실측, 최소 안전 판단의 오검출/미검출률.
- **상태**: ⛔ (AI 파트 일정 동기화 필요)

#### HW-R-05 임무(서브태스크) 수신
- **요구**: 엣지가 생성한 서브태스크를 온보드가 수신·검증한다. 수행 시작/완료/실패 보고는
  HW-R-03에 포함해 회신한다. 서브태스크 단위 검증·디버깅(어느 단계에서 실패했는지 판별)이 목적.
- **주기**: 이벤트 기반
- **검증**: 잘못된 임무 거부, 정상 임무의 단계별 상태 전이 추적.
- **상태**: ⛔ (HW-C-06 공통 명령 체계 위에 구축)

#### HW-R-06 제어 명령 내부 전달 (온보드→제어기)
- **요구**: 수신한 서브태스크·제어 명령을 제어기가 실행 가능한 형태로 변환·전달한다.
  **외부 프로토콜과 구동 인터페이스를 온보드에서 격리해 통신 장애가 구동 로직에 직접
  영향을 주지 않게 한다.**
- **검증**: 통신 두절 주입 시 구동 로직이 영향받지 않고 안전 상태를 유지함.
- **상태**: ⛔

#### HW-R-07 관제용 고해상도 영상 스트림 (온디맨드)
- **요구**: 관제사가 로봇 시점 영상을 확인해야 할 때(사각지대 확인·원격 판단·증거 확보)
  **원본 해상도** 스트림을 엣지로 전송한다. HW-R-04의 640급 AI 입력과 달리 사람이 소비한다.
  요청 시에만 스트림을 열어 무선 대역폭 소모를 최소화한다.
- **주기**: 온디맨드, 전송 중 15 fps
- **검증**: 세션 개시/종료 제어 왕복. 미요청 시 대역 점유 0.
- **상태**: ⛔

#### HW-R-08 구역 사전 정보(맵·경로) 수신
- **요구**: 구역 진입 시 맵·경로계획·환경정보 **전체**를 수신하고, 이후 변화 발생 시
  엣지가 **변경분(델타)만 즉시 푸시**한다. 변화 감지·배포 주체는 엣지(구역의 CCTV·센서
  이벤트가 모두 엣지로 모이므로). 로봇에는 모델이 아니라 주행·임무 수행에 필요한 환경
  정보만 전달해 로봇 측 연산 부담을 최소화한다.
- **검증**: 전체 수신 1회 + 델타 적용. 델타 유실 시 전체 재동기 경로 존재.
- **상태**: ⛔ (BE-A-05 제공 의존)

#### HW-R-09 통신 두절 시 버퍼링·재전송
- **요구**: 두절 시 상태·인식 데이터를 로컬 버퍼링하고 재연결 시 미전송분을 재전송한다.
  **재전송 시 원래 측정 시각의 타임스탬프를 유지해 순서를 복원**할 수 있어야 한다.
- **검증**: 두절 주입 → 적재 → 복구 → 순서 보존 전량 재전송, 잔량 0.
- **상태**: ✅ (S계열에서 구현·실기 검증 완료. R계열에 그대로 재사용)

#### HW-R-10 온디바이스 AI 모델 수신·적용
- **요구**: 구역·임무에 맞는 경량 모델을 엣지에서 수신해 온디바이스 추론에 적용한다.
  **모델 식별자와 버전을 관리하고 적용 성공·실패 상태를 엣지에 보고**한다.
- **검증**: 모델 교체 왕복, 롤백, 적용 실패 보고.
- **상태**: ⛔ (K3s 이미지 배포 및 AI 파트 모델 준비 의존)

### 4.4 액추에이터 제어노드 (HW-A)

#### HW-A-01 액추에이터 상태 수집
- **요구**: 수문·차수벽·펌프·모터 제어기의 현재 동작 상태를 수집·관리한다. 상태는 최소
  **대기 / 동작 중 / 동작 완료 / 오류 / 상태 확인 불가**를 구분할 수 있어야 한다.
- **주기**: 50 ms (20 Hz)
- **검증**: 5종 상태가 실제로 구분되어 보고되는지. 특히 `unknown`(상태 확인 불가)이
  `close`와 뭉개지지 않는지 — 피드백이 끊긴 수문을 '닫힘'으로 오인하면 사람이 위험해진다.
- **상태**: ✅ (SimActuator) — 5종 구분·20Hz 진행 보고 검증. 실물 결선 대기

#### HW-A-02 액추에이터 제어 명령 수신
- **요구**: 엣지로부터 사전 정의된 물리 제어 명령(수문 개방·폐쇄, 차수벽 작동, 펌프 가동·정지)을
  수신해 대상 액추에이터에 전달한다.
- **상태**: ⛔ (현재 `levee` 액션이 자리표시자로 4단계 흐름만 검증)

#### HW-A-03 제어 명령 수신 확인 (ACK)
- **요구**: 즉시 ACK. 수행 불가 시 거부 또는 오류 원인을 함께 반환.
- **설계**: 수행 불가 판정을 **ACK 이전**에 한다. 받아 놓고 나중에 failed 로 돌려주면
  되돌리기 어려운 명령을 다루는 관제가 "일단 갔다"고 오해하는 시간이 생긴다.
- **상태**: ✅ — 잠금·미지원 장치·잘못된 목표·구동 중(busy) 4종을 ACK 단계에서 거부

#### HW-A-04 실제 수행 결과 확인
- **요구**: **ACK와 실제 물리 동작 완료를 구분**한다. 동작 중 상태를 20Hz로 수집·보고하고,
  구동 후 센서·제어기 피드백으로 목표 상태 도달 여부를 확인해 완료·실패를 즉시 보고한다.
- **설계**: 도달을 확인하지 못하면 `travel_timeout` 으로 **실패 처리**한다 — 도달했는지
  모르는 것을 완료로 올리지 않는다.
- **상태**: ✅ (SimActuator) — 피드백 도달 확인 후에만 `state_changed`→`completed`

#### HW-A-05 통신 두절·비정상 상태 안전 처리
- **요구**: 통신 두절·장치 오류 시 **신규 원격 제어 실행을 제한**하고 사전 정의된 안전 상태를
  유지한다. 복구 후 **현재 실제 상태를 우선 재확인한 뒤** 원격 제어를 재개한다.
- **주기**: 제어노드 하트비트 1Hz / 4회 미수신 시 통신 장애 판정 / 복구 시 즉시 재동기화
- **파생(VZ-O-05)**: 잠금 상태와 사유를 가시화가 표시할 수 있도록 보고한다.
- **검증**: 두절 → 잠금 + 안전 상태 복귀 → 복구 → **실제 상태 재확인 후** 해제.
  잠금 중 명령은 사유(`control_locked:comm_loss`)와 함께 거부.
- **상태**: ✅ (SimActuator) — 피드백 상실·통신 두절 두 경로 모두 검증

## 9. 타당성 검토 결과 및 설계 결정

각 쟁점을 서로 다른 모델 3종에 독립적으로 검토시키고, 상충하거나 근거가 약한 주장은
**pi7 실기에서 직접 확인**해 확정했다. 확인되지 않은 주장은 확정 근거로 쓰지 않는다.

### 9.1 K3s 워커 편입은 타당하다 — 단 제어평면은 엣지에만

| 확인 사항 | 근거 |
|---|---|
| k3s **agent**는 kubelet·kube-proxy·containerd만 띄운다. etcd·apiserver는 server 노드 몫 | K3s 공식 문서 |
| agent 정상상태 소비 **RAM 268MB / 코어의 10%** (Pi 4B 기준 95퍼센타일) | K3s Resource Profiling |
| agent 최소 요구 1 core / 512MB, server는 2 core / 2GB | K3s Requirements |

Pi 5 8GB에서 268MB는 3.4%로 **자원상 문제 없다.** agent는 서버형 미들웨어가 아니라
원격 제어평면의 클라이언트이자 워크로드 런타임이므로 **AI-B-10과 충돌하지 않는다.**
반대로 **말단에 k3s server를 두면 apiserver+내장 데이터스토어가 곧 서버형 미들웨어이자
SD카드 쓰기 폭탄이 되어 AI-B-10 위반**이다. → IF-K3S-1을 확정한다.

### 9.2 주기 전환의 실체는 컨테이너 배포가 아니다 (O-5 해소)

원문 HW-S-03/S-04는 "전환의 실체는 쿠버네티스를 통한 컨테이너 배포/제거"라고 규정한다.
그러나 다음 두 사실이 이를 재난 대응 경로로 쓸 수 없게 만든다.

1. **k3s agent는 server에 연결되지 못하면 kubelet·containerd 자체를 시작하지 못한다**
   (k3s-io/k3s#1686). 즉 **엣지 링크가 끊긴 상태에서 말단이 재부팅되면 파드가 하나도 뜨지
   않는다.** static pod로도 우회되지 않는다.
2. 파드 기동은 이미지가 **pre-pull 되어 있을 때만** 5초 이내이고, pull이 필요하면 통상
   **30~60초**다.

재난은 정의상 링크가 가장 불안정한 시점이다. 골든타임의 크리티컬 패스에 네트워크 의존과
수십 초 지연, 그리고 **완전 실패 모드**를 넣는 설계는 성립하지 않는다.

**확정: 3층 구조로 나눈다.**

| 순위 | 경로 | 성질 | 담당 |
|---|---|---|---|
| 1 | **로컬 자율 전환** — 임계·급변을 말단이 스스로 판정해 즉시 고주기 전환 | 네트워크 무관, 지연 0. 브로커·엣지가 죽어도 동작 | HW-S-02, HW-S-03 |
| 2 | **MQTT 주기 전환 명령** — 엣지의 원격 오버라이드 | 왕복 수십~수백 ms. **구역 단위 일관성**이라는 HW-S-04 본래 목적을 달성 | HW-S-04 |
| 3 | **K3s 컨테이너 배포/제거** — AI 추론·CCTV 분석·로봇/액추에이터 앱 등 **증강 기능** | 수 초 지연 허용. 없어도 안전 루프가 깨지지 않음 | HW-C-03, HW-R-10 |

즉 **"즉시성은 상주 프로세스가, 증강은 컨테이너가"** 담당한다. HW-C-03의 배포/제거 시연은
증강 기능으로 성립하므로 요구사항은 그대로 충족된다.

**상주 프로세스는 systemd로 유지한다** — k3s에 넣는 순간 위 실패 모드 1번을 상속한다.

### 9.3 Pi 5에는 H.264 하드웨어 인코더가 없다 (실기 확인)

모델 간 주장이 엇갈려 pi7에서 직접 확인했다. 비디오 장치가 전부 `pispbe`(PiSP 백엔드 ISP)이고
Pi 4의 `bcm2835-codec` 계열 인코더 노드가 존재하지 않는다. `v4l2-ctl --list-formats-out`
어디에도 H264 출력 형식이 없다. → **영상 인코딩은 소프트웨어(libx264)로만 가능**하다.

**실측 결과 (pi7, 4코어, 세 노드 + k3s agent 상주 중, 각 20초, libx264 zerolatency)**

| 용도 | 해상도 | preset | 코어 사용 | 4코어 대비 |
|---|---|---|---|---|
| AI 입력 (HW-R-04) | 640x480 @15 | veryfast | 0.13 | 3% |
| 관제 (HW-R-07) | 1280x720 @15 | veryfast | 0.33 | 8% |
| 관제 (HW-R-07) | 1920x1080 @15 | veryfast | **0.70** | 18% |
| 관제 고품질 | 1920x1080 @15 | faster | 0.93 | 23% |
| CCTV 상시 (HW-S-06) | 1920x1080 @15 | ultrafast | 0.41 | 10% |
| CCTV 상시 (HW-S-06) | 1280x720 @15 | ultrafast | 0.19 | 5% |

**안전 루프 간섭 검증 (가장 중요한 항목)**: 1080p15 + 720p15 를 **동시에** 인코딩하는
동안(전체 CPU 23.8%, 70.3°C, 스로틀 없음) 로봇 상태 보고가 **19.9 Hz 를 유지**했다.
인코딩 부하가 안전 루프를 굶기지 않는다 — SDD 설계 원칙 P1 이 실측으로 지지된다.

**결론 정정**: 착수 전 우려와 달리 **하드웨어 인코더 부재가 영상 경로를 막지 않는다.**
상시 CCTV + 온디맨드 관제 스트림 동시 운용이 CPU 상 가능하다. 다만
- 합성 패턴(testsrc2) 기준이므로 실제 카메라 영상(노이즈·디테일)은 더 든다. **1.5배 여유**를 둔다.
- 남는 예산은 **온디바이스 AI 추론**이 가져간다. 지배 제약은 인코딩이 아니라 추론 쪽이다.
- HW-R-07 의 온디맨드는 CPU 가 아니라 **무선 대역폭** 때문에 여전히 필요하다.

### 9.4 로봇 고주기 텔레메트리 — 근거와 QoS 재검토 필요

| 쟁점 | 검토 결과 |
|---|---|
| HW-R-03의 "Nav2 20Hz" 근거 | `controller_frequency`는 **로봇 내부 제어 루프 주기**이지 네트워크 텔레메트리 주기가 아니다. 근거로는 약하며, 무선망 실측 RTT·처리량 기반으로 재산정해야 한다 (신규 미결 O-11) |
| QoS 선택 | 20Hz 상태 스트림은 **QoS 0** — 다음 샘플이 50ms 뒤 도착해 유실을 상쇄하며, QoS 1은 왕복 지연(무선 실측 ~150ms)이 주기보다 길어 부적합. 하트비트·명령 ACK·임계 경보 등 **이산 이벤트만 QoS 1** |
| HW-R-09와 20Hz의 충돌 | 10분 두절 = 12,000건. 복구 직후 저대역 링크에 과거 데이터를 전량 쏟으면 **현재 상태와 명령 ACK가 밀린다.** → **이산 이벤트는 전량·시간순 재전송, 연속 상태값은 다운샘플/요약**으로 분리 (신규 미결 O-12) |
| 브로커 수용 대수 | Mosquitto 처리량 자체는 여유가 크나(수만 msg/s), 실제 병목은 무선 백홀·말단 직렬화·구독자 fan-out이다. **현장 실측 없이 대수를 단정할 수 없다** |
| 제어기↔온보드 내부 링크 | 소형 주기 스칼라(배터리·위치·속도·모드)는 CAN(FD), 가변 크기 인식 결과는 Ethernet 계열로 **분리하는 하이브리드**가 현실적. 공유메모리는 별도 보드이므로 적용 불가 |
| 온보드 동시 부하 | 50Hz 수신 + 20Hz 발행은 부담이 작으나, **영상 인코딩과 CPU 추론이 상시 CPU를 잠식**한다. §9.3에 따라 하드웨어 인코더 오프로드는 불가하므로 추론 가속기(NPU) 또는 영상 이벤트 트리거형 전환이 필요 |

### 9.5 frame_ref는 타임스탬프만으로 부족하다

영상은 미디어 평면, 인지 결과는 업무 평면으로 서로 다른 지연을 겪는다. 타임스탬프만으로
짝을 맞추면 오차가 누적되어 VZ-I-07의 오버레이 정합이 깨진다. **단조 증가하는
`sequence_id`를 함께 실어** 프레임 단위로 결합해야 한다. → IF-MED-3 유지, 백엔드와
형식 확정 필요(O-9).
