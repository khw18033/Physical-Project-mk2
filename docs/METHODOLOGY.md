# 제1부. 요구사항을 어떻게 만들었나

## 1. 출발점과 문제 인식

출발점은 팀 공용 요구사항 정의서(`피지컬팀 프로젝트 mk2.xlsx`)의 하드웨어 30건이었다.

```
HW-R  로봇        10건
HW-S  센서         8건
HW-C  공통         7건
HW-A  액추에이터    5건
────────────────────
              총 30건
```

각 항목은 **ID / 대분류 / 소분류 / 요구사항 정의 / 전달 경로 / 제안 주기 / 주기 선정 이유 /
연관분야 / 연관점 / 담당**의 10개 열로 되어 있었다. 주기마다 근거 URL(ROS 2 Control,
Nav2, MAVLink 등)이 붙어 있어 근거는 충실했다.

**그러나 이대로는 구현·검증의 기준이 되지 못했다.** 이유는 셋이다.

| 문제 | 구체 사례 |
|---|---|
| **검증 방법이 없다** | "하트비트를 주기적으로 전송한다"는 무엇을 관찰해야 충족인지 안 적혀 있다 |
| **타 파트가 거는 제약이 안 보인다** | 백엔드 시트의 BE-X-03(명령 결과 4단계 승격)은 하드웨어가 반드시 지켜야 하는데 HW 시트에는 없다 |
| **문서 간 상충이 숨어 있다** | 하트비트 주기가 정의서는 1 Hz, 아키텍처 v4는 5초 |

그래서 30건을 **검증 가능한 형태로 재기술**하는 작업(SRS)부터 했다.

## 2. 도출 절차 5단계

### 2-1. 원문 전수 추출

요약본이 아니라 **원문 전체**를 읽어야 했다. 조건절·예외가 요약에서 탈락하기 때문이다.

```python
wb = openpyxl.load_workbook('피지컬팀 프로젝트 mk2.xlsx', data_only=True)
ws = wb['조병현']
for r in ws.iter_rows(min_row=2, max_row=31, values_only=True):
    print(r[0], r[2], r[3])   # ID / 소분류 / 요구사항 정의 전문
```

**이 단계에서만 드러난 것들** — 요약으로는 놓쳤을 내용이다.

| 요구사항 | 원문에만 있던 결정적 내용 |
|---|---|
| HW-S-02 | "센서노드에 **상시 상주하는 기본 수집 컨테이너**가 …" — 컨테이너 구조가 전제 |
| HW-S-03 | "**엣지노드의 쿠버네티스가** 고주기 모니터링 컨테이너를 **배포하여** 1초 주기로 전환" |
| HW-S-04 | "**전환의 실체는 쿠버네티스를 통한 컨테이너 배포/제거이다**" |
| HW-S-05 | "개별 기능 컨테이너의 생존은 **K8s liveness probe**가, 노드 생존은 하트비트가" — 층이 다르다 |
| HW-A-01 | 상태 5종에 "**상태 확인 불가**"가 따로 있다 |
| HW-R-07 | HW-R-04는 AI용 640급, R-07은 **사람이 보는 원본 해상도** — 다른 스트림 |

특히 HW-S-03/S-04의 "컨테이너 배포가 주기 전환의 실체"는 당시 구현(MQTT 명령 방식)과
정면으로 달랐다. 원문을 읽지 않았으면 요구사항 미충족을 모르고 지나갔을 것이다.

### 2-2. 타 파트 요구사항에서 하드웨어 제약 추출

하드웨어 시트만 보면 절반만 보인다. 나머지 세 시트(백엔드 41건 · AI 63건 · 가시화 47건)에서
**하드웨어가 반드시 지켜야 하는 항목**을 걸러냈다.

```python
# 필터 조건: 연관분야에 '하드웨어'가 있거나, 본문에 'HW-' 참조가 있는 행
rel = str(r[7])
if '하드웨어' in rel or 'HW-' in ' '.join(str(c) for c in r if c):
    ...
```

이렇게 **19건**을 추출해 SRS §6에 "타 파트에서 파생되는 하드웨어 제약"으로 고정했다.

| 출처 | 하드웨어에 대한 요구 | 없었으면 |
|---|---|---|
| BE-C-01 | 공통 필드 봉투(`source_id`·`node_id`·`zone_id`…) | 자체 필드명으로 만들었다가 전면 재작업 |
| BE-T-04 | 상태를 3층으로 분리, 하드웨어는 `device_status` 자기보고 | 상태를 단일 값으로 뭉침 |
| BE-X-03 | 명령 결과를 ACK→수행중→물리변화→완료 **4단계**로 | ACK 하나로 끝냈을 것 |
| BE-X-01 | `command_id`는 백엔드가 발급, 말단은 에코 | 말단이 자체 발급 → 상관 사슬 단절 |
| AI-B-10 | 말단에 브로커·수집기 등 **서버형 미들웨어 설치 금지** | 말단에 K3s server를 올렸을 것 |
| AI-C-08 | 영상 픽셀을 MQTT/Kafka/OTLP에 싣지 말 것 | 업무 평면으로 영상을 보냈을 것 |
| VZ-O-01 | 추상 `action`+`params`, `expires_at` 만료 준수 | 평평한 명령 형식 유지 |
| VZ-U-01 | 정상/장애/의도적 미배포/판단불가 구분 가능하게 | 계획 종료와 급사를 같은 offline으로 |
| VZ-O-05 | 제어 잠금 상태·사유 보고 | 액추에이터 잠금이 화면에 안 보임 |

**이 단계의 판단 기준**: "다른 파트가 이 값을 소비하는가?" 소비한다면 그건 하드웨어의
요구사항이다. 시트가 다르다는 이유로 빠지면 통합 시점에 터진다.

### 2-3. 검증 가능한 형태로 재기술

각 요구사항에 **네 가지**를 붙였다. 핵심은 **검증**이다 — "어떻게 확인하는가"를 못 쓰면
그건 아직 요구사항이 아니라 희망이다.

```
#### HW-C-06 제어 명령 수신 및 ACK 응답
- 요구:   (원문의 의무 사항)
- 파생:   (타 파트에서 걸리는 제약 — BE-X-03, BE-X-01, VZ-O-01, C-4)
- 검증:   물리 명령 4단계 왕복, 설정 명령 3단계, 거부 4종, 중복 배달 억제
- 상태:   ✅ / ◐ / ⏳ / ⛔
```

**"검증" 칸을 쓰다가 발견한 요구사항 누락**이 여럿이었다. 예를 들어 HW-C-04의 검증을
쓰려니 "10초 주기 상태 요약"을 관찰할 방법을 적어야 했는데, 구현에 그 기능 자체가
없다는 것이 그때 드러났다.

### 2-4. 상충 판정과 근거 계층

문서가 여럿이라 값이 어긋나는 곳이 나왔다. **근거 계층을 먼저 정하고** 그에 따라 판정했다.

```
요구사항 정의서(xlsx)  >  아키텍처 문서(v4)  >  계획서 초안
```

정의서가 팀이 합의한 계약이고 나머지는 그 해석이라는 이유다.

| 미결 ID | 상충 | 판정 | 근거 |
|---|---|---|---|
| O-2 | 하트비트 1 Hz(정의서) vs 5초(v4) | **1 Hz** | 1 Hz라야 HW-S-07의 "4회 미수신=4초" 판정이 성립한다. 5초면 20초가 되어 정의서와 어긋남 |
| O-3 | 말단 OTLP 직접 발신 vs 백엔드 브리지 | **직접 발신** | 업무·관측 평면 분리 원칙. 업무 경로가 막혔을 때 원인을 볼 방법이 사라짐 |
| O-4 | OTel export 60초(정의서) vs 15초(계획서) | **60초** | 근거 계층 |

판정하고 끝내지 않고 **미결 항목으로 등록해 백엔드 회신을 요청**했다(총 13건,
`docs/BACKEND_AGENDA.md`). 하드웨어가 임의로 정한 것이 아니라 "이렇게 두었으니 확인해
달라"는 형태로 남긴 것이다.

### 2-5. 타당성 검토 → 요구사항 원문 수정

여기가 이번 작업에서 가장 중요한 단계다. **요구사항을 그대로 구현하는 것이 아니라,
구현 가능한지 먼저 따졌다.**

핵심 쟁점 3건을 **서로 다른 모델 3종에 독립적으로 검토**시키고, 주장이 엇갈리거나 근거가
약한 항목은 **실기에서 직접 확인**했다.

| 쟁점 | 검토 결과 | 확인 방법 |
|---|---|---|
| 말단에 K3s를 두는 것이 AI-B-10과 충돌하나 | agent는 kubelet·kube-proxy·containerd만(RAM 268 MB). **충돌 없음.** 단 server는 금지 | K3s 공식 자원 프로파일 |
| 컨테이너 배포로 주기를 전환해도 되나 | **부적합** | k3s-io/k3s#1686 |
| Pi 5에 H.264 하드웨어 인코더가 있나 | **모델 간 주장 상충** | **pi7 실기 확인** |

**결정적 근거 — 주기 전환을 컨테이너에서 떼어낸 이유**

1. k3s agent는 제어평면에 연결되지 못하면 **kubelet·containerd 자체를 시작하지 못한다**
   (k3s-io/k3s#1686). 즉 링크가 끊긴 상태에서 말단이 재부팅되면 파드가 하나도 안 뜬다.
2. 파드 기동은 이미지가 pre-pull 되어 있을 때만 5초 이내고, pull이 필요하면 **30~60초**다.

재난은 정의상 **링크가 가장 불안정한 시점**이다. 골든타임의 크리티컬 패스에 네트워크
의존과 수십 초 지연, 그리고 **완전 실패 모드**를 넣을 수는 없다.

그래서 요구사항 정의서(xlsx) 원문 4건을 정정했다. `sharedStrings.xml`만 외과적으로
교체해 **다른 팀원 시트는 바이트 그대로 보존**했다.

| 위치 | 정정 |
|---|---|
| HW-S-03 | "엣지 쿠버네티스가 컨테이너를 배포하여 전환" → **로컬 자율 판정이 주 경로**, 엣지 명령은 원격 오버라이드 |
| HW-S-04 | "전환의 실체는 컨테이너 배포/제거" → MQTT 제어 채널. 컨테이너는 증강 기능용 |
| HW-C-03 | 예시를 "수위 고주기 모니터링 컨테이너" → "영상 분석·AI 추론 등 증강 기능" |
| HW-S-02 | 하트비트 참조 오기 `HW-S-06` → `HW-S-05` (S-06은 CCTV 영상) |

**대신 요구사항이 약해지지 않도록** 3층 분담으로 재정의했다. HW-C-03의 "배포/제거" 시연은
증강 기능으로 그대로 성립한다.

| 순위 | 경로 | 성질 |
|---|---|---|
| 1 | 로컬 자율 전환 | 네트워크 무관, 지연 0. 브로커·엣지가 죽어도 동작 |
| 2 | MQTT 주기 전환 명령 | 엣지 오버라이드. HW-S-04의 본래 목적(구역 단위 일관성) 달성 |
| 3 | K3s 컨테이너 배포 | 증강 기능. 수 초 지연 허용, 없어도 안전 루프 무사 |

## 3. 요구사항에서 설계로 — 원칙을 먼저 세웠다

SRS가 "무엇을"이라면 SDD는 "어떻게"다. 설계 판단이 흔들리지 않도록 **원칙 5개를 세우고
충돌 시 우선순위를 정했다.**

| # | 원칙 | 근거 |
|---|---|---|
| **P1** | 안전 루프는 네트워크에 의존하지 않는다 | 재난 골든타임 |
| **P2** | 평면을 합치지 않는다 (업무 MQTT / 관측 OTLP / 미디어) | AI-C-08, BE-S-02 |
| **P3** | 미확정은 한 곳에 가둔다 | 백엔드에 확정권이 있음 |
| **P4** | 말단은 클라이언트만 둔다 | AI-B-10 |
| **P5** | 상태는 뭉치지 않는다 | BE-T-04, VZ-U-01 |

**P3의 실제 효과**: 백엔드 미확정 필드를 `pi/common/schema.py`의 `envelope()` 함수 하나에
가뒀다. 확정이 오면 그 함수만 고치면 센서·로봇·액추에이터 전 노드에 반영된다. 다른
파일은 필드명을 문자열로 알지 못한다.

**P1의 실제 효과**: 요구사항 8(로봇과 센서 분할)을 구현하면서 세 노드가 공통 코어
`BaseNode`를 상속하게 했고, 그 층 전체를 **systemd로 상주**시켜 k3s에 넣지 않았다.

# 제2부. 검증은 어떻게 했나

## 4. 검증 원칙

> **"동작한다"는 말은 실제 장비에서 관찰한 것만 쓴다.**

노트북 모의에서 통과한 것을 완료로 적지 않았다. 실제로 **모의에서 전부 통과했던 코드가
라즈베리파이에서 17건의 결함을 냈다.**

## 5. 검증 계층 4단계

```
① 로컬 모의        노트북 + Mosquitto           빠른 반복. 로직 오류를 싸게 잡는다
       ↓
② 실기 배포        라즈베리파이 pi7 + systemd    운영과 같은 형태로 돌린다
       ↓
③ 장애 주입        브로커 종료·kill -9·플래그    "정상 경로"가 아닌 곳을 판다
       ↓
④ 정량 실측        주기·지연·자원·부하           숫자로 요구사항 충족을 확인한다
```

각 단계에서 **다른 종류의 결함**이 나왔다.

| 단계 | 여기서만 나오는 결함 | 실제 사례 |
|---|---|---|
| ① | 로직 오류 | 로봇이 `zoneA/sensor/rb-01`로 발행 (entity_type 미전달) |
| ② | 환경·운영 결함 | **SIGTERM 미처리** — systemd로 돌려야만 드러난다 |
| ③ | 실패 경로 결함 | 모니터 재구독 누락, 액추에이터 잠금 미해제 |
| ④ | 정량 미달 | 20 Hz 목표인데 **16.5 Hz** |

## 6. 검증 도구

반복 가능성이 핵심이었다. 손으로 SSH 붙어 확인하면 재현이 안 된다.

| 도구 | 저장소 위치 | 용도·방법 |
|---|---|---|
| 주기 실측기 | `pi/bench/rate_probe.py` | 브로커를 구독해 N초간 **채널별 메시지 수를 세어 Hz 산출** |
| 관측 수신단 | `pi/bench/otlp_sink.py` | 최소 OTLP/gRPC 수신단. 말단이 **실제로 무엇을 보내는지** 확인 |
| 인코딩 벤치 | `pi/bench/encode_bench.sh` | bash 내장 `time`으로 (user+sys)/real → **코어 사용량** |
| 장애 주입 | 코드 내장 | `/tmp/rain`(강우), `/tmp/feedback_loss`(피드백 상실) 플래그 파일 |
| 원격 실행·배포 | (세션 로컬) | paramiko 기반 SSH 헬퍼. 자격증명을 환경변수로 받으므로 저장소에는 넣지 않았다 |

```bash
# 주기 실측 — 임무 하달 전후로 각각 돌려 비교한다
cd pi && python3 -m bench.rate_probe 10 "임무 중" "zoneA/robot/rb-01/#"

# 관측 실측 — 말단의 HW_OTEL_ENDPOINT 를 이 호스트로 향하게 한 뒤
cd pi && python3 -m bench.otlp_sink 120

# 인코딩 부하 실측
DUR=20 bash pi/bench/encode_bench.sh
```

**주기 실측이 왜 필요했나.** "20 Hz로 보낸다"는 코드를 읽어서는 확인되지 않는다.
브로커에서 실제로 세어 봐야 안다. 그렇게 재니 **16.5 Hz**였고, 이는 정확히 1/0.06초 —
발행이 20 ms 수집 틱에 양자화되어 60 ms 간격이 된 것이었다.

**관측 실측이 왜 필요했나.** OTLP 코드는 예외 없이 돌았지만, 그건 "발신을 시도했다"일 뿐
"무엇이 도착했나"가 아니다. 수신단을 세우니 `service.name`이 로봇 지표까지
`hw-sensor-node`로 고정되어 있었고, QoS 0 발행에 지연 0 ms를 기록해 히스토그램이 0으로
쏠려 있었다.

### 7-5. 정량 한계 — 부하를 걸고 확인

영상 인코딩이 안전 루프를 굶기는지가 설계 원칙 P1의 실증 대상이었다.

| 측정 | 값 |
|---|---|
| 640×480@15 veryfast | 0.13 코어 (3 %) |
| 1080p@15 veryfast | 0.70 코어 (18 %) |
| 1080p@15 ultrafast | 0.41 코어 (10 %) |
| **1080p+720p 동시 인코딩 중 로봇 상태 보고** | **19.9 Hz 유지** (전체 CPU 23.8 %, 70.3 °C, 스로틀 없음) |

측정 시 `-re` 옵션으로 소스를 **실시간 속도로** 흘렸다. 이게 없으면 인코더가 최대 속도로
돌아 항상 CPU 100 %가 나와 실제 운용 부하를 알 수 없다.

**결론이 뒤집힌 사례**: 착수 전에는 "하드웨어 인코더가 없으니 CPU가 지배 제약"으로 봤다.
실측하니 아니었다. 지배 제약은 인코딩이 아니라 온디바이스 추론 쪽이고, HW-R-07의
온디맨드는 CPU가 아니라 **무선 대역폭** 때문에 필요하다는 것으로 근거가 바뀌었다.

## 8. 검증 → 수정 → 재검증 루프

발견으로 끝내지 않고 **고친 뒤 같은 방법으로 다시 쟀다.** 대표 사례 셋이다.

### 사례 1 — 20 Hz 미달

```
① 실측        임무 중 상태 보고 16.5 Hz (목표 20 Hz)
② 원인        16.5 ≈ 1/0.06초. 발행이 20 ms 수집 틱 안에 있어 60 ms로 양자화
③ 1차 수정    next_wakeup() 훅 추가 → 루프를 발행 마감시각에도 깨움
④ 재실측      여전히 16.5 Hz.  ← 수정이 틀렸다
⑤ 재분석      깨어나도 발행이 on_sample 안에 있어 틱 게이트를 못 벗어남
⑥ 2차 수정    발행을 on_tick 훅으로 분리
⑦ 재실측      19.9 Hz ✅
```

1차 수정 후 **재측정하지 않았다면 고쳤다고 착각했을 것이다.**

### 사례 2 — 재접속 백오프

```
① 관찰   25초 두절 뒤 복구까지 60초 초과
② 원인   paho 기본 백오프 상한 120초 — 두절이 길수록 복구가 늦어진다
③ 판단   재난 대응과 방향이 반대다. 오래 끊겼을수록 밀린 데이터가 많아 빨리 붙어야 한다
④ 수정   reconnect_delay_set(max_delay=10)
⑤ 재검증 25초 두절 → 20초 내 재접속, 버퍼 35건 전량 재전송 ✅
```

### 사례 3 — 액추에이터 안전 잠금

```
① 검증   피드백 상실 → 잠금 ✅ / 명령 거부 ✅ / 복구 → 해제 ❌
② 원인   해제 경로가 통신 두절 케이스에만 걸려 있었다
③ 수정   해제 조건을 사유와 무관하게 통일 —
         "피드백이 살아 있고 상태가 확정적(대기·완료)일 때만" 해제
④ 재검증 피드백 경로 ✅ / 통신 두절 경로(수문이 open→close 안전 상태 복귀) ✅
```

## 9. 미검증으로 남긴 것과 그 이유

**검증하지 못한 것을 완료로 적지 않았다.** 상태 표기를 4단계로 나눈 이유다.

```
✅ 구현·검증 완료    ◐ 부분    ⏳ 미착수    ⛔ 선행조건 미충족
```

| 항목 | 상태 | 이유 |
|---|---|---|
| HW-S-01 실센서 수집 | ⛔ | 센서 미조달. 가짜 생성기로 파이프라인만 검증, 교체 지점을 `read_sensor()` 한 함수로 격리 |
| HW-R-01/06 제어기 링크 | ◐ | 로봇 실물 미확보. `SimLink`로 상위 파이프라인만 검증 |
| HW-A 계열 | ✅(SimActuator) | 액추에이터 실물 미확보. 링크 구현체 교체만 남음 |
| HW-S-06/R-07 영상 | ⛔ | 카메라·미디어 게이트웨이 부재. **인코딩 예산만 실측** |

**대체 검증을 쓴 곳은 무엇으로 대체했는지 명시**했다. "Collector 수신단으로 대체" ·
"WSL 임시 엣지" · "SimActuator" 처럼 적어 두면, 실물이 왔을 때 무엇을 다시 확인해야
하는지가 분명해진다.

## 10. 다중 모델 교차검토 — 판정은 실기로

설계 쟁점 3건을 서로 다른 모델에 독립 검토시켰다. **모델 답변을 근거로 채택하지 않고,
주장이 엇갈리거나 근거가 약하면 실기로 판정**했다.

| 쟁점 | 모델 간 | 판정 방법 | 결론 |
|---|---|---|---|
| Pi 5 H.264 하드웨어 인코더 | A: "사용" ↔ B: "없음" — **상충** | `v4l2-ctl --list-formats-out` 전수 확인 | **없음**. 비디오 장치가 전부 `pispbe` ISP. B가 맞음 |
| 인코딩이 지배 제약인가 | "CPU 고갈로 동시 운용 불가" | 실측 벤치 | **뒤집힘**. 1080p@15가 0.70코어 |
| HW-R-03의 20 Hz 근거 | Nav2 값은 내부 제어 루프 주기 | 문서 확인 | 근거 약함 → 미결 O-11로 등록, 설정값으로 분리 |

**모델 답변을 그대로 쓰지 않은 것이 실제로 유효했다.** 인코더 상충은 실기 한 번으로
갈렸고, "인코딩이 지배 제약"이라는 공통 예상은 실측으로 뒤집혔다.

## 11. 요약 — 방법의 뼈대

### 요구사항 도출

1. **원문을 전수로 읽는다.** 요약에서 조건절이 탈락한다
2. **타 파트 시트에서 하드웨어에 걸리는 것을 추출한다.** "다른 파트가 소비하는가"가 기준
3. **검증 방법을 못 쓰면 요구사항이 아니다.** 검증 칸을 쓰다가 누락이 드러난다
4. **상충은 근거 계층으로 판정하고 미결로 등록한다.** 임의로 정하고 넘어가지 않는다
5. **구현 가능한지 먼저 따진다.** 불가능하면 요구사항 원문을 근거와 함께 고친다

### 검증

1. **"동작한다"는 실제 장비에서 관찰한 것만.** 모의 통과는 완료가 아니다
2. **4계층으로 나눈다.** 모의 → 실기 → 장애 주입 → 정량 실측. 층마다 다른 결함이 나온다
3. **자동화한다.** 재현할 수 없는 검증은 검증이 아니다
4. **수정 후 같은 방법으로 다시 잰다.** 1차 수정이 틀린 경우가 실제로 있었다
5. **못 한 것은 못 했다고 쓴다.** 대체 검증은 무엇으로 대체했는지 명시한다
