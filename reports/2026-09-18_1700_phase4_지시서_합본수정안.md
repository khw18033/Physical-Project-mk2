## 0. 먼저 — 설계방 판정 하나를 철회한다

설계방 문서 **§7 「고치지 않는 것」**의 이 행을 **철회한다.**

> | §4 서버 상태 표 | Phase 3 보고서 「서버에 남은 것」과 **전 항목 일치** |

**왜 틀렸나.** 설계방은 `_serverinfo/` 원본을 읽지 못해 **Phase 3 보고서 한 겹**하고만 대조했다. 그래서 보고서에 없는 값은 검증 대상이 아니었다. 실제로 확인한 결과:

| v1 표의 값 | 실물 |
|---|---|
| tailnet에 **`pi4`·`pi6`** | 저장소·보고서·`_serverinfo`·설계 프롬프트 **전체에서 0건.** 유일한 `tailscale status` 원본(`_serverinfo/260916_phase3_tailscale.txt`)은 **7대**이고 거기에 `pi4`·`pi6`이 없다. 게다가 대조 보고서가 적은 `jin03`이 **빠져 있다** |
| `be_*` **이름 28개 = A층 11 + C층 12 + stale 5** | Phase 3 보고서 실측은 **`be_*` 21종(A 9 + C 12) + stale 5**. "28"·"A층 11"·"히스토그램 1개=3이름"은 **저장소 전수 grep 0건** |
| 브로커가 **`localhost:9092 (id: 1)`로 답함** | 어떤 명령 출력에도 없다 |
| C층 instant query **0건** | 근거 없음 |
| 컨슈머 그룹 4종 | Phase 3 **보고서**와도, Phase 3 **지시서**와도 **일치하지 않는다**(보고서엔 dedup이 없고, 지시서엔 `mk2-headerless-check`가 더 있다) |

그리고 표 머리의 **「2026-09-17」**이 근본 문제다. 설계 세션 전수를 확인한 결과 **그날 서버에서 실제로 돌아 결과가 돌아온 명령은 3회뿐**이었다(Loki·Tempo 조회 + compose md5 / ufw 9092 삭제 / ufw·systemd·df). **19행 중 6행만 당일 실측이고 나머지는 09-04~09-16 문서 전사다.**

> **설계방 문서가 사용자가 건넨 것이라고 해서 실물 확인보다 우선하지 않는다.** 대조 기준이 한 겹이면 그 한 겹에 없는 것은 보이지 않는다 — 그것이 이 건의 교훈이고, 같은 이유로 **이 합본의 판정도 §4의 「기각·재프레이밍」 목록처럼 근거를 붙여 뒤집을 수 있게 남겨 뒀다.**

**v2 반영:** 단계 0 표에 **근거 등급 칸**(`[실측 09-17]` / `[전사]` / `[미확인 → 단계 0에서 처음 확인]`)을 넣고, 출처 없는 4건을 **삭제**했으며, DoD 0-1을 등급별로 갈랐다. 표 전체는 **서버 명령 출력을 받는 대로 교체**한다.

## 4. 판정을 뒤집은 것 — 근거

### 4-1. 🔴 B10(compose DNAT 주석) — **설계방도 Cowork도 절반만 맞았다. compose 주석이 옳다**

| 누가 | 무엇이라 했나 |
|---|---|
| 설계방 B10 | *"`infra/README.md` §5가 실측으로 **반증한** 문장이다. README·plan은 고쳤는데 compose만 남았다"* → **고쳐라** |
| Cowork A6 | *"9100 실측은 「열면 통한다」를 보였을 뿐 「안 열면 막힌다」를 보이지 않았다"* → **음성 대조가 필요하다** |
| **실물 판정** | **두 문장은 서로 다른 패킷 경로를 말한다. 어느 쪽도 반증되지 않았다** |

근거:
- 9100은 `rpi-pushgateway`의 **0.0.0.0 publish** 포트이고(`docker-compose.yml:181-186`), 그 트래픽의 출발지는 **Prometheus 컨테이너 → `host.docker.internal:9100`**이다(`prometheus.yml:48-52` + `extra_hosts`). **`prometheus.yml:8` 주석이 원인을 직접 적어 두었다** — *"원인은 컨테이너→호스트 9100이 ufw에 막힌 것"*.
- 브리지로 들어온 패킷은 Docker의 `nat/DOCKER` 체인에서 **`-i <bridge> -j RETURN`에 걸려 DNAT되지 않는다.** 목적지가 호스트 자기 주소라 **로컬 배달 → `INPUT` → ufw 적용**. 그래서 열자 풀린 것이 맞다.
- compose 주석이 말하는 **외부 기기 → 발행 포트**는 물리 NIC로 들어와 `! -i <bridge>` 조건에 걸려 **DNAT → `FORWARD` → `DOCKER-USER`**로 간다. **ufw의 `INPUT`을 타지 않는다.**

**v2 반영:** 주석을 **지우지 않고 두 경로로 갈라 적는다**(단계 6-b). `infra/README.md` §5 정정 박스의 **"실측이 반증했다"도 같은 문장으로 고친다.** 운영 규칙(*"외부 포트는 ufw에도 반드시 연다"*)은 **그대로 유지**한다 — 근거 ②(장애 시 방화벽을 용의선상에서 제외)는 DNAT와 무관하게 타당하다.

> ⚠ **이 판정이 결정 6 β의 안전 전제를 바꾼다.** 이번 Phase는 평문 Kafka(9095)·평문 OTLP(4316)를 **팀 공용 tailnet**에 여는데 그 통제를 ufw `/32`에 걸고 있다. **docker 발행 포트라면 그 통제가 작동하지 않을 수 있다.** 그래서 **7-h 음성 대조**를 넣었다 — 허용 목록에 없는 tailnet 기기에서 `nc -vz` 한 줄이면 판정된다. **막지 못하면 결정 6 β를 "tailnet 내부 신뢰 전제"로 고쳐 적는다. 없는 통제를 있다고 적지 않는다.**

## X-3. 🔴 B10 판정이 서버 실측으로 확정됐다

ufw 출력에 **결정적 증거**가 있었다.

```
[ 6] 9100/tcp   ALLOW IN   172.16.0.0/12    # rpi pushgateway <- docker
[ 7] 9100/tcp   ALLOW IN   Anywhere
[36] 9110/tcp   ALLOW IN   172.18.0.0/16    # node-exporter <- dg prometheus
[37] 9120/tcp   ALLOW IN   172.18.0.0/16    # kube-state-metrics <- dg prometheus
```

세 줄 다 **소스가 도커 브리지 대역**이고 주석이 **`<- docker`**다. 즉 `infra/README.md` §5가 *"실측이 반증했다"*고 적은 9100 사건은 **「컨테이너 → 호스트」 경로를 연 것**이고, 그 경로는 DNAT를 타지 않아 `INPUT` = ufw가 적용된다. compose 주석이 말하는 **「외부 기기 → 발행 포트」**(DNAT → `FORWARD`) 경로는 여전히 ufw `INPUT`을 타지 않는다.

**→ 합본 §4-1의 판정이 맞았다. 서버 운영자도 이미 그렇게 알고 소스를 도커 대역으로 제한해 두었다.**

# 부록 Y — 2026-09-18 2차 서버 실측 반영 (지시서 v2 → v3)

> 1차에서 `[재실행 대기]`로 남았던 5행을 전부 받았다. **그중 하나(iptables)가 결정 하나를 뒤집었다.**

## Y-1. 🔴 제약 16 전면 개정 — ufw는 도커 발행 포트의 접근 통제가 아니다

**v2까지의 서술:** *"바인딩과 ufw는 층이 다르며 둘 다 한다. ufw `/32` = 통제인지는 단계 7-h로 판정한다."*
**v3:** *"ufw는 도커 발행 포트를 통제하지 못한다. 실질 통제는 바인딩 주소와 `DOCKER-USER` 둘뿐이다."*

근거 셋은 전부 2026-09-18 `iptables` 출력이다.

| # | 관측 | 뜻 |
|---|---|---|
| ① | `iptables -S FORWARD` 순서가 `… ts-forward → **DOCKER-USER** → **DOCKER-FORWARD** → … → ufw-before-forward …` | **도커가 ufw 체인보다 먼저 ACCEPT한다.** 외부發 발행 포트 트래픽은 ufw를 보지 못한다 |
| ② | `iptables -S DOCKER-USER`가 `-N DOCKER-USER` **한 줄뿐** | 지금 도커 발행 포트를 거르는 규칙이 **0개**다 |
| ③ | nat `DOCKER`에서 `-d 127.0.0.1/32`가 붙은 것은 **9092·7859·4316 셋뿐** | **실제로 막는 것은 compose의 바인딩 주소**다 |

**이로써 §3(1차 합본)에서 미해결로 남겼던 B10 논쟁이 최종 판정났다.** 두 문장은 서로 다른 경로였고, **compose 주석(213-216) 쪽이 옳았다.** `infra/README.md` §5의 *"실측이 이 서술을 반증했다"*가 틀린 문장이며, 단계 6-b에서 고친다.

**남는 ufw의 용도 셋** — ⓐ 컨테이너·호스트發 경로(`INPUT`을 탄다 — `[6] 172.16.0.0/12 # <- docker`가 그 경로) ⓑ 장애 원인 배제 ⓒ 🔴 **호스트 파이썬 프로세스(8765·8766·8767)는 DNAT를 안 타고 `INPUT`으로 들어오므로 여기서는 ufw가 진짜 통제다.**

## Y-2. 🔴 결정 6 β 개정 — 「평문 + ufw `/32`」 → 「평문 + 바인딩 + `DOCKER-USER` 한 줄」

v1·v2의 β는 **없는 통제를 근거로 평문 Kafka 입구를 tailnet에 여는 것**이었다. 개정안:

1. **바인딩이 1차 통제** — `"<서버 tailscale IP>:9095:9095"`. DNAT에 `-d …/32`가 붙어 tailnet 밖은 매치되지 않는다. `0.0.0.0` 금지.
2. **`DOCKER-USER` 한 줄이 2차 통제** — 체인이 비어 있고 `DOCKER-FORWARD`보다 먼저라 `-C || -I`로 멱등하게 넣으면 된다.
3. 🔴 **영속화에 `netfilter-persistent`·`iptables-save` 전체 덤프를 쓰지 않는다** — 이 서버는 **k3s·kube-router·flannel**이 `FORWARD`를 동적 관리하고 `-P FORWARD DROP`이다. 전체를 굳히면 다음 부팅에 충돌한다. **`mk2-docker-user-rules.service`(oneshot)**로 두 줄만 다시 넣는다.
4. **ufw 규칙은 계속 적되 「통제」라고 적지 않는다.**
5. **SASL은 Phase 6 그대로.** 다만 *"Phase 3이 4316을 같은 방식으로 열었던 선례"*는 **근거에서 뺀다** — 4316은 `127.0.0.1` 바인딩이라 tailnet에서 보이지도 않았다. 같은 방식이 아니었다.

**7-h도 바뀐다** — 판정이 아니라 **확인**이 되고, **2회**(규칙 전 = 연결됨 / 규칙 후 = 거부됨) 돌린다.

## Y-3. 🔴 §3-b 신설 — 범위 밖 노출 발견
