# 마일스톤 분리 10단계 — 태스크까지 낸다 (`VZ-G-02` 의 모델 쪽 절반)

**선행**: `978168b`(9단계 · 화면 적용) · 9단계 보고서 §9 의 1번
**대상**: `VZ-G-02` · 지시서 §5
**날짜**: 2026-09-07
**모델**: Qwen3 8B Q4_K_M · 정답셋 3편 × 발화 5개 = 판당 15건 · 온도 0 · seed 0

---

## 결론 먼저

**태스크 분리가 된다. 형식은 완전히 안정적이고, 정답 재현은 낮다.**

| | E3 (채택) |
|---|---|
| 스키마 통과 | **15/15** |
| 태스크를 낸 건 | **15/15** (노드 141건 · 편당 6~13) |
| 모델이 낸 `deps` | **0건** — 규칙 14를 15건 전부 지켰다 |
| 순환 | **0건** — `solveDeps()` 의 구조적 보장이 실제 출력에서도 유지됐다 |
| 태스크의 `target` 이 그 마일스톤 배정 안인가 | **123/123 (100%)** |
| 노드 문법 정확도 | **0.03** (조건부 0.31) |
| 그래프 f1 | **0.04** |
| 응답 시간 | 중앙값 **25.99초** · 최대 31.34초 (B 판의 4배) |

**화면에 켰다.** 켠 근거는 정답 재현이 아니라 **형식이 안정적이고 결과가 제안일 뿐**이라는
것이다 — 마일스톤도 개수 일치 33% 로 이미 붙어 있고, 낮으면 사람이 승인에서 거른다.
끌 수 있게 두었다(시간이 네 배다).

여기까지 오는 데 판이 셋 필요했고, **두 번 실패한 것이 이 라운드에서 가장 값이 나갔다.**

## 1. 세 판 — 실패 둘이 원인을 하나씩 짚었다

| 판 | 규칙 | 예시 | ctx | 태스크를 낸 건 | 결과 |
|---|---|---|---|---|---|
| **E** `__E-tasks` | 태스크 규칙 | **마일스톤까지만** | 8192 | **5/15** | 규칙을 무시했다 |
| **E2** `__E2-tasks-ctx8k` | 태스크 규칙 | 태스크까지 | 8192 | **0/15** | 출력이 전부 잘렸다 |
| **E3** `__E3-tasks-ctx16k` | 태스크 규칙 | 태스크까지 | **16384** | **15/15** | 된다 |

### E — 규칙과 예시가 어긋나면 **예시가 이긴다**

규칙 10 「`tasks` 는 빈 배열로 둔다」를 태스크를 내라는 규칙 일곱 줄로 갈아 끼웠다.
그런데 few-shot 예시는 그대로 `tasks: []` 를 보이고 있었다. 15건 중 **10건이 규칙을
무시하고 빈 배열을 냈다.**

7단계가 「예시가 준 것은 형판이 아니라 분할 입도의 일관성」이라고 적은 것의 더 강한
형태다 — **예시는 규칙을 이긴다.** 규칙 층의 모순(「빈 배열로 둬라」와 「내라」)은
`_replace_rule()` 로 없앴는데, **예시 층의 모순을 남겨 둔 것**이 이 판이 잡힌 자리다.

### E2 — 컨텍스트가 모자랐다. 그것은 모델의 실패가 아니다

예시에 태스크를 실었더니 프롬프트가 4,419 → **7,642 토큰**이 됐고, `ctx 8192` 에서 출력에
**567 토큰**밖에 안 남았다. 15건 전부 중간에서 잘렸다.

```
stop_reason: limit · prompt 7,625 + completion 567 = 8,192
원문 끝: … "milestone_id": "MS-C", "title": "503호 문을 열
```

표에는 **스키마 실패 15/15** 로 나타난다. 그런데 모델이 못 한 것이 아니라 **자리가
없었던 것**이고, 그 둘은 다른 실패다. 안 가르면 다음에 같은 일이 나도 진단이 처음부터
시작된다. 그래서 셋을 고쳤다.

- `CTX` 기본값을 8192 → **16384**. 옛 실행은 잘리지 않았으므로(4,400 + 2,048 < 8,192)
  그 숫자는 그대로 쓴다.
- `run-baseline` 이 `stop_reason === 'limit'` 을 **그 줄에서 경고로 적는다.**
- `report-baseline` 이 「⚠ 출력이 잘린 건 N (ctx …)」을 줄 아래 적는다.

그리고 실행 이름에 조건을 넣었다 — `__E2-tasks-ctx8k` · `__E3-tasks-ctx16k`.
**이름이 설정을 말한다**(6단계에 유령 `llama-server` 로 배운 것).

### 표가 죽는 자리를 하나 찾았다

E2 는 채점할 것이 하나도 안 남아 축의 평균이 전부 `null` 이 됐고, `report-baseline` 이
그 줄에서 **크래시했다**(`row.order_recall.toFixed`). 실행이 통째로 실패하는 것은 정상적인
결과 중 하나이므로 표가 그것을 그릴 수 있어야 한다 — 못 잰 축을 0이 아니라 「해당없음」
으로 적도록 고쳤다(이 저장소의 다른 자리와 같은 규칙).

## 2. `deps` 는 모델의 것이 아니다 — 그것이 지켜졌다

지시서 §5 의 핵심이다. 계약상 `deps` 는 required 라 문법에서 뺄 수 없으므로 **빈 배열로
내게 하고 규칙이 매단다.**

```
모델이 낸 deps          0건 / 141 노드   ← 규칙 14를 15건 전부 지켰다
규칙이 매단 deps       128건
순환                     0건
```

`solveDeps()` 는 「모든 엣지는 목록에서 앞선 노드만 가리킨다」가 구조적 보장이라 순환이
불가능한데, **실제 모델 출력 141 노드에서도 그것이 유지됐다.** 5단계가 `verify:dep-rules`
로 대본의 손으로 만든 DAG 를 복원해 보인 것이 여기서 처음으로 **모델이 낸 노드**에 걸렸다.

### 화면과 측정이 같은 함수를 쓴다

`deps` 를 매다는 자리는 `src/generate/proposal.ts` 하나이고(`withSolvedDeps`),
`run-baseline` 이 채점 전에 **그 함수를 부른다.** 두 벌이면 표의 그래프 숫자와 화면에
그려지는 그래프가 조용히 갈라진다. 모델의 원본은 `raw/` 가 그대로 들고 있다.

### 예시도 `deps` 를 보이지 않는다

태스크 판의 예시는 태스크를 보이되 **`deps` 는 언제나 빈 배열**이다. 정답의 의존을
보여주면 모델이 그것을 흉내 내고, 그 순간 §5 가 막으려던 것이 규칙이 아니라 **예시를
통해** 들어온다. `verify:no-leak` 이 그것을 검사한다.

## 3. 정답 재현은 낮다 — 그런데 그 원인의 대부분이 마일스톤 층에 있다

노드 문법 정확도 0.03 을 **그대로 읽으면 틀린다.** 7단계가 장비 위반을 「지어냄」과
「오선택」으로 가른 것과 같은 자리다.

| 정답 태스크 255건 중 | |
|---|---|
| **짝이 없다** (모델이 안 냈거나 자리가 밀렸다) | **226건 (89%)** |
| 짝이 있다 | 29건 |
| 그중 라벨이 맞다 | 9건 → **조건부 정확도 0.31** |

즉 0.03 은 「라벨을 못 붙인다」가 아니라 **「낼 태스크를 대부분 못 냈다」**이다.
편당 정답 16~18건인데 모델은 6~13건을 낸다.

그리고 채점기는 마일스톤을 정렬한 뒤 그 아래 태스크를 **인덱스로** 짝짓는다. 마일스톤
개수 일치가 33% 이고 03편은 제목 유사도가 0.00(아예 안 맞는다)이므로, **그 편의 태스크는
구조적으로 하나도 짝지어질 수 없다.**

> **태스크 축은 마일스톤 축의 실패를 상속한다.** 마일스톤이 안 맞으면 태스크는 잴 수 없다.

### `target` 은 100% 일관됐다 — 오선택은 물려받은 것이다

태스크의 `target` 이 몰리는 것이 눈에 띄었다(03편 v0 은 12건 중 10건이 `edge-node-a`).
「`target` 은 그 마일스톤의 `assigned_targets` 안에서 골라라」를 규칙으로 넣을까 하다가
먼저 쟀다.

```
그 마일스톤의 assigned_targets 안에서 골랐는가 — 123/123 (100%)
```

**규칙을 안 줬는데도 이미 100% 다.** 몰림은 태스크 층의 실패가 아니라 **마일스톤 층의
장비 오선택을 그대로 물려받은 것**이고, 규칙을 더해도 아무것도 안 바뀐다.
한 판을 아꼈고, 7단계가 남긴 「오선택」 문제가 태스크 층에서 증폭된다는 것을 알았다.

### 그래도 구조는 그럴듯하다

화면 경로로 대본에 없는 문장을 넣은 실제 결과다.

```
MS-A 5층 복도 주행 시작            T-1a [decide] 경로 계획      → T-1b [act] 복도 주행 → T-1c [verify] 주행 완료 확인
MS-B 복도 주행 중 사람 감지        T-2a [sense] 시야 영역 관측  → T-2b [decide] 사람 감지 판정
MS-C 감지된 사람 정보 기록 및 보고  T-3a [sense] 감지 정보 스냅샷 → T-3b [report] 감지 정보 보고
MS-D 복도 주행 종료 및 임무 종료    T-4a [act] 주행 종료         → T-4b [report] 임무 종료 처리 (target=null)
```

`decide → act → verify` · `sense → decide` · `sense → report` — **이것은 진짜 노드
문법이다.** 의존 8건은 전부 규칙이 매달았고 모델이 낸 것은 0건이다. `target=null` 도
지어내지 않고 비웠다.

## 4. 계약을 한 자리 열었다 — `task.target`

`solveDeps()` 의 「자원 순차」 규칙(같은 `target` 의 `act` 끼리는 순서를 지킨다)이 쓸 값이
계약에 없었다. 대본 JSON 과 정답셋에는 있는데 `task.schema.json` 에 없어서, 생성된
태스크를 계약으로 검증할 수도 없었다.

**5단계가 `node_kind` 를 올린 것과 똑같은 자리이고 똑같은 이유다.** 선택 필드로 올렸으므로
기존 예시는 무효가 되지 않는다(계약 예시 8건 재검증 · 어긋남 0).

## 7. 틀 밖 발화 셋을 넣어 봤다 — 절반은 되고 절반은 **구조적으로 안 된다**

정답셋 3편이 전부 「A에서 B로 이동」이거나 정해진 절차다. 태스크가 나오기 시작해서
**비로소 볼 수 있게 된 것**이 있어 그 틀 밖의 발화를 실제 서비스에 넣었다(대본 매칭 전부
`none`). 형식은 셋 다 완전히 버텼다 — 스키마 오류 0 · 순환 0 · 장비 목록 밖 `target` 0 ·
모델이 낸 `deps` 0.

### 되는 것 — 선형이면 틀 밖이어도 된다

```
발화: 503호에서 제자리에서 주변에 소화기가 있는지 찾아봐

MS-A 503호 내부 탐색 시작    T-1a [act] 센서 활성화 · T-1b [sense] 센서 데이터 수신
MS-B 503호 내부 주변 탐색    T-2a [sense] 주변 영역 스캔 → T-2b [decide] 데이터 분석
MS-C 소화기 위치 확인        T-3a [decide] 소화기 위치 탐지 → T-3b [report] 위치 기록
MS-D 소화기 존재 여부 판단   T-4a [decide] 존재 여부 판정 → T-4b [report] 보고
```

**이동 마일스톤을 억지로 만들지 않았다.** 출발지·도착지가 없는 명령에 「A에서 B로」 틀을
밀어 넣지 않았다. 「소화기」는 장비 목록에 없는 물체인데 `target` 에 넣지 않고 제목에만
뒀다 — 어휘 규칙을 지켰다.

### 안 되는 것 — 배타 분기와 루프가 **직렬로 꿰인다**

```
발화: 사람을 찾을 때까지 5층 복도를 계속 이동해

MS-C 사람 탐지 시 멈춤   T-3a [act] 이동 중지 → T-3b [verify] 정지 상태 확인
MS-D 사람 탐지 없음      T-4a [act] 이동 계속 → T-4b [verify] 이동 완료 확인   ← deps=["T-3b"]
MS-E 임무 종료
```

**모델은 분기를 알아봤다** — 「탐지 시 멈춤」과 「탐지 없음」을 갈라 냈다. 그런데 그 둘이
**순차로 꿰였다.** 읽으면 「멈추고 → 그 다음 계속 이동하고 → 끝낸다」이고, 되돌아가는
길이 없다. 조건부 발화(「있으면 보고하고 없으면 503호로 돌아와」)도 똑같이 순차가 됐다.

### 원인은 모델이 아니라 설계 세 곳이다

1. **`deps` 는 순서만 표현한다.** 「이 조건이면 이쪽」을 적을 자리가 계약에 없다.
   `evaluation.result`(pass/fail)는 **실행이 채우는 결과**이지 계획의 분기 조건이 아니다.
2. **`solveDeps` 의 마일스톤 경계 규칙이 전부 직렬로 꿴다.** 배타 분기든 루프든 예외가 없다.
3. **되돌아가는 엣지를 생성하지 않기로 명시적으로 정했다**(지시서 §5).

3번의 근거를 다시 봐야 한다. 그 결정은 「실행 전 계획에서 재탐색 루프를 **지어내는** 것은
사용자가 준 단계를 더하지 않는다 원칙 위반」이었고, 그것은 **발화에 루프가 없을 때**의
규칙이다. 「사람을 찾을 때까지」는 발화가 루프를 **명시적으로 요구**한다 — 지어내는 것이
아니라 받아 적는 것이다. **그 구분이 지금 코드에 없다.**

표현 형식은 이미 있다 — 대본 2편에 사람이 손으로 적은 `refEdges` 가 하나 있고
(`T-27c → T-23a` 재탐색 요청) 화면이 점선으로 그린다. **생성 경로만 그것을 안 만든다.**

### 가장 위험한 것은 이 실패가 **조용하다**는 것이다

분기를 순차로 꿰어도 스키마는 통과하고 순환도 없고 `verify:*` 27개가 전부 초록이다.
**틀렸다는 것을 기계가 아는 자리가 없다.** 지금 이것을 잡는 것은 승인 화면을 보는 사람의
눈 하나뿐이고, 그것은 승인 선의 마지막 방어선이지 첫 방어선이어서는 안 된다.

## 8. 남은 것

1. **마일스톤 층이 병목이다.** 태스크 축은 그 실패를 상속하므로, 개수 일치 33% 를
   올리지 않으면 그래프 f1 도 안 오른다. 8단계가 「단계 종류를 알려주는 것으로는 안
   된다」를 확인했으니 남은 길은 재료 쪽이고, 정답셋 3편에서 예시는 2편이 최대다.
2. **장비 오선택이 태스크 층에서 증폭된다.** 마일스톤 하나가 장비를 잘못 고르면 그 아래
   태스크 전부가 따라간다(`target` 일관성 100% 의 뒷면이다).
3. **응답 26초.** 프롬프트의 대부분이 예시다(7,642 토큰). 예시를 마일스톤까지만 보이면
   짧아지지만 그러면 E 판이 된다 — 태스크만 요약해 보이는 중간 형태를 재 볼 수 있다.
4. **예시 항목 차례** (9단계 §8 에서 적어 둔 것) — 태스크 예시는 계약 차례로 넣었고,
   `utterance` 만 아직 측정 경로의 차례를 따른다. 고치려면 다시 재야 한다.
5. **배타 분기와 루프** (§7). 이것이 지금 가장 큰 구멍이고, 8·10단계처럼 스위치 하나
   켜고 재는 일이 아니다 — 계약·규칙·화면이 같이 움직여야 한다. 먼저 할 것은 고치는
   것이 아니라 **못 한다는 사실을 화면과 기록에 드러내는 것**이다: 발화가 분기·루프를
   요구하는데 계획이 순수 사슬이면 경고. 완벽한 판별은 아니지만, 지금은 못 한다는
   사실조차 아무 데도 안 적힌다.
