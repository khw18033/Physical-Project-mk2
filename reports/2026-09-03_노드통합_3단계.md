## 1. 셸 5개소 — 어디로 갔나

지시서 §3의 표 그대로다.

| 지금까지 | 어디로 |
|---|---|
| `activeTab` · `app-tabs` nav · `TabView` 라우팅 | **삭제.** 무대는 하나(`tab-stage`)이고 그것이 캔버스다 |
| `useTabsDataLayer()` | **그대로 셸에 남았다.** 앱 수명과 같아야 하고 탭과 무관했다 |
| `TabGate` | **죽고 `NodeGate` 가 됐다** — 접힘이 노드 단위로 내려앉았다. `PanelGate` 는 그대로 |
| `HelpOverlay(tab=activeTab)` | **캔버스의 설명서**, 확대가 열려 있으면 **그 노드의 설명서** |
| 대본 띠의 「○○로」 | **「○○ 노드로」** — 없으면 만들고, 있으면 하이라이트 (§2) |

층 1(대본이 안 쓰는 것은 흐리게)은 탭 바에서 **팔레트로** 옮겨 앉았다. CSS 규칙까지 그대로
옮겼다 — 흐리게 하되 **막지 않는다**는 규칙은 한 글자도 바뀌지 않았다.

### 「하지 않을 것」은 하지 않았다

- **마일스톤 목록 화면은 그대로다.** `VZ-U-05` 대체의 근거이고 캔버스의 상위 화면이다 —
  「탭이 없어진다」는 뜻이지 「화면이 하나가 된다」는 뜻이 아니다. 렌더 확인에 못을 박았다.
- `useTabsDataLayer()` 를 옮기거나 끊지 않았다. `verify:no-tabs` 가 셸에 남아 있는지 본다.
- 공유 계층 16건 · `web-dashboard` · `stt-lab` · `scenarios/*.json` · `stt/engines/*.py` 무수정.

## 2. 「○○ 노드로」 — 탭과 다른 점

지시서 §3의 ★이 이 작업의 유일한 **신규 기능**이다.

> 지금 「갈 탭」 버튼은 탭이 이미 있으니 이동만 하면 됐다. 노드는 **캔버스에 아직 없을 수 있다.**
> 누르면 — **없으면 만들고(진행 중인 태스크에 연결한 채로), 있으면 하이라이트한다.**

경로는 이렇다. **셸은 캔버스 안을 모른 채 요청만 넣는다** — 탭을 걷어낸 이유가 그것이다.

```
대본 띠 버튼 → onOpenNode(kind, taskId)   (AppShell)
             → navigation { screen:'node', node:{kind,taskId} }   (IntegratedApp)
             → 그 태스크가 든 마일스톤으로 이동 + 요청 전달        (MissionDebugger)
             → 있으면 하이라이트 / 없으면 만들어 연결 + 하이라이트  (GraphScreen)
```

- `nowPlaying()` 이 이제 **`taskId` 를 함께 돌려준다** — 붙일 곳이 없으면 전역 노드가 되고,
  그러면 「연결이 곧 범위」가 이 경로에서만 깨진다. `verify:scenario-mode` 가 재생 중
  `taskId` 가 비지 않는지 본다.
- **같은 종류가 이미 있으면 만들지 않는다.** 누를 때마다 카드가 쌓이면 캔버스가 금세
  지저분해진다.
- 만든 노드는 **2.6초 반짝인다.** 만들어 주고 어디 생겼는지 말하지 않으면 사용자가 캔버스를
  훑어야 한다. 계속 반짝이면 그게 상태처럼 읽히므로 스스로 꺼진다.

### 만들다 잡은 결함 — 마일스톤 밖의 태스크

안내줄이 가리키는 태스크가 **지금 보고 있는 마일스톤 밖**일 수 있다(대본은 계속 흘러가는데
사용자는 앞 마일스톤을 보고 있는 흔한 상황이다). 그때 요청 한 번이 **마일스톤 이동과 노드
요청을 함께** 일으키는데, 이동 직후 첫 렌더에는 `canvas.nodes` 가 아직 **옛 마일스톤의
구성**이다. 거기서 바로 판정하면 「이미 있다」를 잘못 읽고 **아무것도 안 뜬다.**

그래서 요청을 **두 걸음**으로 나눴다 — 일단 세워 두고(`pendingNode`), 캔버스 구성이 그
슬롯 것으로 바뀐 다음 렌더에서 처리한다. 증상이 「눌렀는데 아무 일도 없다」뿐이라 나중에
찾기 어려운 종류였다.

## 3. 축→탭 표가 축→**노드종류** 표가 됐다

**표는 여전히 한 곳뿐이다**(`src/scenarios/axes.ts`). 오른쪽 칸이 탭 id 에서 뷰 노드 종류로
바뀌었을 뿐, 대응 자체는 한 글자도 바뀌지 않았다 — 탭②가 장치·위험 노드로, 탭③이 제어
노드로, 탭④가 지표 노드로, 탭⑤가 영상 노드로 그대로 옮겨 앉았다.

| 옛 이름 | 새 이름 |
|---|---|
| `ScenarioTab` · `TAB_LABEL` | `ViewNodeKindId` · **이름표는 없앴다**(아래) |
| `AXIS_TABS` | `AXIS_NODES` |
| `SCENARIO_PANELS[].tab` | `.node` |
| `tabsOfAxes` · `tabsOfScript` · `panelsOfTab` | `nodeKindsOfAxes` · `nodeKindsOfScript` · `panelsOfNode` |
| `scriptsUsingTab` | `scriptsUsingNode` |
| `verify:tab-scope` | `verify:node-scope` |

**이름표(`TAB_LABEL`)를 표에서 없앤 것**이 이번의 판단이다. 뷰 노드의 이름은 **등록된
렌더러**가 갖고 있고(`VZ-N-01` — 팔레트는 등록분에서 자동 구성된다), 표가 이름을 또 가지면
팔레트 버튼과 접힘 카드가 서로 다른 이름을 말하게 된다. 그래서 표에는 **id 만** 두고,
`verify:node-scope` 가 **표의 id 와 등록된 렌더러의 kind 를 대조**한다. 표에 이름표가 다시
생기면 그 검사가 실패한다.

`tabsOfAxes()` 가 항상 얹던 `debugger` 는 사라졌다 — 실행 노드는 늘 살아 있어 접힘 판정의
대상이 아니고, 그건 탭 시절 탭①이 표에 없던 것과 같은 이유다.

## 4. 구역 맵이 갈 곳을 잃을 뻔했다

탭②에는 패널이 셋 있었다: `RiskPanel` · `ZoneMapMini` · `DeviceGrid`. 그런데 지시서 §5의
장치·위험 노드 확대 규격은 **「`DeviceGrid` + `RiskPanel`」** 둘뿐이다. 그대로 옮기면
**구역 맵 미니뷰가 화면에서 사라진다** — `VZ-I-03`(구역·노드 매핑 표시)이 죽는 것이고,
이 작업의 대전제인 **「요구사항 삭제 0건」**이 깨진다.

축을 보면 답이 나온다: 구역 맵의 축은 `coverage`·`position` 이고 둘 다 `AXIS_NODES` 에서
**장치·위험 노드**를 가리킨다. 그래서 그 노드의 확대에 셋째로 넣었다. 패널마다 축이 달라
각자 접히는 것은 그대로다(3편에서는 구역 맵만 접힌다 — `verify:node-scope` 의 `PANEL_EXPECTED`
가 그 셋을 못으로 박고 있다).

## 5. 확대 상태를 모듈 저장소로 올렸다

`HelpOverlay` 가 「확대가 열려 있으면 그 노드의 설명서」를 보이려면 **셸이 캔버스의 확대
상태를 알아야** 한다. 그렇다고 셸에 프롭으로 올리면 셸이 다시 캔버스 안을 알게 되고, 상태를
양쪽에 복제하면 갈라진다.

그래서 원천을 `src/canvas/zoomState.ts` **하나**로 올리고 캔버스와 셸이 각자 구독한다.
2단계의 `useState` 가 이 저장소로 바뀐 것이고, **값은 여전히 하나**다(`ZoomTarget | null`).
`verify:no-tabs` 의 「한 번에 하나」 검사도 그 모양을 확인하도록 함께 고쳤다.

이것은 `activeTab` 류가 아니다 — 「몇 번째 탭」이 아니라 「어느 노드가 확대됐나」이고,
둘이 열릴 수 없다.

설명서 구역(`ManualScopeId`)도 탭 다섯에서 **캔버스 + 노드 4종**으로 바뀌었다. 확대 본문은
`ZoomOverlay` 가 `ManualScope.Provider` 로 감싸므로, 확대 안의 `<Explain>` 문단들이 그
노드의 설명서로 등록된다.

## 7. 지시서와 다르게 한 곳 — 넷

### ㄱ. `TabGate` 를 지우고 **`NodeGate` 로 되살렸다**

지시서는 「`TabGate` 는 **죽는다** → 접힘이 노드 단위로. `PanelGate` 만 살아 뷰 노드를
감싼다」이다. 그런데 `PanelGate` 하나로는 **「그 노드의 패널이 하나도 안 살 때 카드를 통째로
갈음하는」** 판정을 할 수 없다 — 그건 탭 시절 `TabGate` 가 하던 일이고, 판정 대상만 탭에서
노드로 바뀌었을 뿐 규칙은 그대로 필요하다. 그래서 **탭 개념은 죽이고 구조는 이름을 바꿔
살렸다**(`tab` → `kind`). 지시서 문면의 「죽는다」는 지켰다고 본다 — `TabGate` 라는 이름도
탭 어휘도 코드에 없다.

### ㄴ. 구역 맵을 장치·위험 노드의 확대에 **셋째로** 넣었다

§4에 적은 그대로다. 지시서 §5의 확대 규격은 둘이지만 그대로 두면 `VZ-I-03` 이 화면에서
사라지고 「삭제 0건」이 깨진다. 축이 이미 그 노드를 가리키고 있어 자리는 명확했다.

### ㄷ. 확대 상태를 **모듈 저장소로** 올렸다

§5에 적은 그대로다. 지시서에 없는 구조 변경이지만, `HelpOverlay` 요구(셸 5개소 중 넷째)를
상태 복제 없이 만족시키는 길이 이것뿐이었다.

### ㄹ. `README.md` · `HANDOFF.md` 를 함께 고쳤다

코드 단계에 문서를 건드리는 것이지만, 이 둘은 **이 앱을 처음 여는 사람이 읽는 문서**라
탭 바를 설명한 채로 두면 그 자리에서 바로 거짓이 된다. 루트의 논문·요구사항 문서는
0단계(v1.1)에서 이미 노드 캔버스를 **목표 상태로** 적어 뒀으므로 이번에 손대지 않았다 —
「예정」으로 적힌 표현이 남아 있는지는 다음 문서 갱신에서 한 번 훑는 것이 좋다(§8).

## 8. 남은 것

- **문서 한 번 훑기** — 루트 문서(요구사항정의서 §3.1 · 쉬운설명 · 프로토타입 설명서 ·
  기술스택 · 구현진행 · 논문진행)는 v1.1 개정에서 이 구조를 **목표**로 적었다. 이제 구현이
  따라잡았으므로 「전환 예정」류 표현과 폴더 트리(`TabGate` → `NodeGate` 등)를 한 번 맞추면
  된다. 코드 변경은 없다.
- **층 ① 대본 사이드카** (1단계 §5 ㄱ · 2단계 §8) — 이제 4종 요약이 실물이고 탭도 없으므로
  「첫 진입에 어떤 노드를 어디에」를 정할 근거가 다 모였다. 시연 구성과 함께 정하면 된다.
- **제어 요약의 구간 필터** (2단계 §7 ㄱ) — 명령에 임무 시각이 실려야 한다(게이트웨이 계약).
- **`5tab-baseline` 태그로 대조군 빌드** — 논문 §3-2 요인 B. `git checkout 5tab-baseline`
  뒤 `npm run build` 하면 그대로 탭 조건 참가자용 빌드다.
