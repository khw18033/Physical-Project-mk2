## 무엇이 문제였나

접속 주소가 **빌드 시점 환경변수**였다.

```
transport/index.ts   VITE_GATEWAY_WS  ?? 'ws://127.0.0.1:8790'
                     VITE_GATEWAY_HTTP ?? 'http://127.0.0.1:8790'
stt/SttClient.ts     VITE_STT_URL     ?? 'http://127.0.0.1:8801'
```

바꾸려면 다시 빌드해야 했다. 현장에서 게이트웨이·제어 노드 IP가 바뀔 때마다 빌드할 수 없다.

## 무엇을 했나

상단 바 「알림」 오른쪽에 **`⇄ 연결 관리`**. 대상은 넷이고, 목록의 원천은
`src/shared/connections.ts` **하나**다 — 화면은 그 목록을 그린다(손으로 넷을 적지 않는다).

| 대상 | 칸 | 지금 |
|---|---|---|
| 백엔드 WS 게이트웨이 | WebSocket · HTTP | 실제로 붙는다 |
| STT 서비스 | 주소 | 실제로 붙는다 |
| 제어 노드 | 주소 | **상대 없음 — 칸을 잠그고 「연결 예정」** |
| 디지털 트윈 | 주소 | **상대 없음 — 칸을 잠그고 「연결 예정」** |

뒤 둘은 주소를 넣어도 붙을 곳이 없다. 입력 칸을 **잠갔다** — 없는 것을 있는 척하지 않는다.

환경변수는 **기본값**이 됐다. `.env.local` 을 쓰던 개발 흐름은 그대로 살아 있고, 화면에서
넣은 값이 있으면 그것이 이긴다.

## `verify:one-gateway` 를 어떻게 지켰나 — 싱글턴 재연결 구조

지시서가 이 단계의 관문으로 지목한 이유가 명확했다. **주소가 상수에서 런타임 값이 되면
「여기저기서 URL 을 읽는」 길이 열리고, 그 순간 출입구가 갈라진다.**

### ① `GATEWAY` 를 상수에서 **게터**로 — 읽는 자리를 늘리지 않았다

`GATEWAY.http` 는 여섯 곳에서 읽힌다(`commandCenter` · `audit` · `metrics` · `registry` ·
`selfObservability` · `RiskPanel`). 그 자리를 `gatewayHttp()` 같은 함수 호출로 바꾸면
「URL 을 아는 곳」이 여섯 개 늘어난 것처럼 보이고 실제로도 갈라지기 쉽다.

```ts
export const GATEWAY = {
  get ws(): string { return connectionAddress('gateway', 'ws'); },
  get http(): string { return connectionAddress('gateway', 'http'); },
};
```

**읽는 쪽은 한 글자도 안 바뀌었고**, 부를 때마다 지금 값을 본다. 원천은 여전히 하나다.

### ② 싱글턴을 유지한 채 **끊고 다시 붙는다**

```ts
singleton = new WsTransport(() => ({ url: GATEWAY.ws, httpBase: GATEWAY.http }));
singleton.connect();
subscribeConnections(() => {
  if (주소가 그대로) return;          // STT 만 바뀐 경우까지 멀쩡한 연결을 흔들지 않는다
  singleton.close();
  singleton.connect();                // 같은 인스턴스 — 구독이 살아 있다
});
```

`WsTransport` 가 고정 설정 대신 **해석 함수**도 받게 했다(`WsTransportConfig | (() => …)`).
붙을 때마다 주소를 다시 읽으므로, 생성 시점에 굳지 않는다. 고정 설정을 주면 지금까지와
똑같아서 `verify:transport` 는 손대지 않았다.

**새 인스턴스를 만들지 않는 것이 핵심이다.** 만들면 그 위에 걸린 구독이 통째로 날아가고,
화면은 「연결됨」인데 값이 안 오는 상태가 된다. 같은 인스턴스를 닫았다 열면 `WsTransport` 가
기존 구독을 자동 복원한다.

### ③ 관문 검사를 **실제로 그것을 보게** 고쳤다

`verify:one-gateway` 는 목 게이트웨이를 띄워 채널이 흐르는지만 봤다 — **우리 전송 코드를
한 번도 지나지 않는다.** 그 상태로는 「주소가 런타임으로 바뀌어도 출입구가 하나인가」를
통과시켜도 아무 의미가 없다. 그래서 섹션을 더했다.

1. **`new WsTransport(` 는 소스 전체에 하나뿐이다** — 두 번째가 생기면 출입구가 둘이다
2. 게이트웨이를 **둘 띄우고 A → B 로 주소를 바꾼다**(화면이 하는 것과 같은 `saveConnections`
   호출). `getTransport()` 가 **같은 인스턴스**를 돌려주는지 본다
3. **A 를 죽이지 않은 채** 열림 진입 횟수가 늘어야 한다 — 「끊고 다시 붙었다」는 그 값이
   늘어야만 사실이다. 주소만 바꿔 두고 옛 연결에 그대로 붙어 있어도 `config.url` 과 상태는
   멀쩡해 보인다
4. 그 다음 A 를 죽여도 값이 계속 온다 — 정말 B 에 붙었고 **구독을 다시 걸지 않았다**
5. 음성 대조군 — 붙지 않는 주소로 바꾸면 반드시 열린 상태를 벗어난다

**대조군 확인**: `singleton.close(); singleton.connect();` 두 줄을 지운 사본으로 돌렸더니
③에서 「B 로 끊고 다시 붙기 (A 는 살아 있다) 시간 초과」로 잡혔다. 되돌리면 통과한다.

> 처음 쓴 판은 ③이 없어 **대조군을 못 잡았다.** 옛 연결이 살아 있는 동안 `config.url` 은 이미
> B 를 가리키고 상태도 `open` 이라 조건이 곧바로 참이 됐고, A 를 죽인 뒤에는 평소의 자동
> 재연결이 새 주소로 붙어 버려 「값이 계속 온다」도 참이 됐다. **A 가 살아 있는 동안의 재연결**
> 을 봐야 그 둘이 갈린다.

이 검사가 게이트웨이 셋과 소켓 여럿을 띄우므로 끝에서 `process.exit(0)` 으로 닫는다 —
붙지 못한 소켓 하나만 남아도 Node 의 이벤트 루프가 안 죽어 `npm run` 이 매달린다(실제로
한 번 매달렸다).

## STT 주소를 아는 면은 여전히 하나다

`verify:no-stt` 가 「`src/stt/` 밖에서 STT 주소를 알면 안 된다」를 검사한다 — `VITE_STT_URL`
이라는 **문자열 자체**가 마커다. 그래서 연결 저장소는 STT 의 환경변수를 읽지 않는다.

`SttClient.ts` 가 자기 환경변수를 읽어 `registerConnectionDefault('stt', 'base', …)` 로
**기본값만 심고**, 값은 `sttBaseUrl()` 로 저장소에서 읽는다. 상수였던 `STT_BASE_URL` 이
함수가 됐다(`UtterancePanel` 의 표시 한 곳도 따라 바뀜) — 상수면 모듈 적재 시점에 굳어
바꿔도 옛 주소로 부른다.

## 지켜야 하는 것 넷 (지시서 §3)

| | 어떻게 |
|---|---|
| 1. 출입구는 하나 | 위 §. `GATEWAY` 게터 · 싱글턴 유지 · 전송 생성 1곳 (검사로 고정) |
| 2. 대상 목록 한 곳 | `CONNECTION_TARGETS` 하나. `ConnectionsPanel` 은 그것을 `map` 한다 |
| 3. 새로고침에 살아남는다 | `localStorage['viz.connections.v1']` — **앱 전역 키**(임무별이 아니다. 접속 주소는 임무의 성질이 아니라 이 설치본의 성질이다). 읽기·쓰기 전부 `try/catch` 이고, 막혔으면 기본값으로 조용히 진행하되 **화면이 그 사실을 숨기지 않는다**(「이번 세션에만 적용」) |
| 4. 되돌아올 길 | **기본값 복원** 버튼. 틀린 주소를 넣으면 아무 데도 못 붙으므로 이 길이 없으면 갇힌다 |

기본값과 같은 칸은 **저장하지 않는다** — 나중에 기본값이 바뀌면 따라가야 하기 때문이다.

## 배지와 섞지 않았다

상단 `conn` 배지는 **상태**(지금 붙어 있나), 이 판은 **설정**(어디에 붙을 것인가). 판에
상태를 넣지 않았고, 대신 판의 머리글이 「지금 붙어 있는지는 상단 배지가 말한다」고 적는다.
섞으면 「연결 안 됨」이 주소가 틀린 것인지 서버가 죽은 것인지 알 수 없어진다.

## 검증

- **기존 verify 18종 + `typecheck` 전부 통과.** `verify:one-gateway` 는 위 섹션이 더해진
  채로 통과(9초).
- `verify:standalone` **무개정 통과**(Windows) — 단독 의존 그래프 51 → **52개 파일**
  (`shared/connections.ts` 하나가 늘었다. `ConnectionsPanel` 은 `shell/` 이라 안 들어온다).
- `npm run build` · `npm run build:standalone` 둘 다 성공.

## 지시서와 다르게 한 곳

**`verify:one-gateway` 를 「유지」가 아니라 확장했다.** 지시서 검증표는 이 검사를 「유지」로
적었지만, 있는 그대로는 우리 전송 코드를 한 번도 지나지 않아 이 단계가 깨뜨릴 수 있는 것을
**아무것도 보지 않는다**. 관문으로 지목된 검사가 관문 구실을 못 하면 통과가 무의미하므로,
기존 채널 검사는 한 줄도 건드리지 않고 주소 교체 섹션을 뒤에 붙였다.

## 하지 않은 것

- 공유 계층의 나머지 16건은 건드리지 않았다 — `VZ-C-07` 하나만 늘었다.
- 제어 노드·디지털 트윈에 붙는 코드를 만들지 않았다. 자리만 잠근 채로 뒀다.
- `verify:transport` 는 손대지 않았다 — `new WsTransport({url, httpBase})` 가 그대로 된다.
