## 요청

`VZ-U-02`(디지털 트윈 위치 렌더링)를 Unity로 만든다. 웹 대시보드는 그대로 두고 **Unity가
목 게이트웨이에 또 하나의 클라이언트로 붙어** 전역 좌표를 받아 공간에 배치한다.
Unity는 최종적으로 시뮬레이터 겸 뷰어가 되지만 **이번 범위는 뷰어뿐이다.**

## 판단

### 1. 왜 뷰어부터인가 — 구조로 강제한 것

Unity가 둘을 겸하면 **뷰어가 시뮬레이터의 내부 상태를 직접 읽는 지름길**이 생긴다. 화면은
완벽한데 파이프라인은 한 번도 안 거치고, 실제 백엔드를 붙이는 순간 전부 어긋난다.

그래서 이번 코드에는 **씬 안의 오브젝트가 서로의 Transform을 읽어 위치를 얻는 경로가 없다.**
위치의 출처는 하나뿐이다.

```
수신 봉투 → TwinStore → PoseBuffer → PoseInterpolator → EntityView
```

`Data/` 폴더에는 `GameObject`·`Transform`이 하나도 없다. 씬이 저장소를 읽는 방향은 있어도
저장소가 씬을 읽는 방향은 없으므로, 지름길을 만들려면 **폴더 경계를 넘는 것이 눈에 보인다.**

> 예외 하나를 남겼다 — `WorldLabel`의 빌보드가 카메라 Transform을 읽는다. 트윈 상태를
> 하나도 나르지 않는 순수 표현이라 허용했고, **예외인 이유를 그 파일 머리말에 적었다.**
> 다음 사람이 "여기도 Transform 읽네" 하고 위치를 읽기 시작하면 규칙이 무너진다.

### 2. 손잡이 변환을 **표현 계층**으로 본 근거 — 회의에서 그대로 쓸 것

Unity는 왼손 좌표계다. `BE-C-04`는 `y=위 · 바닥 x-z · 미터`로 **축만** 정하고 손잡이를
말하지 않는다. 백엔드가 로보틱스 관례(오른손)로 값을 주면 **좌우가 뒤집혀 보인다.**

뒤집기를 어디서 할지 두 안이 있었다.

**① 백엔드가 뷰어에 맞춰 준다 — 기각.**
백엔드가 특정 렌더러의 관례를 떠안기 시작하면 **뷰어가 둘이 될 때 무너진다.** 지금 이미
뷰어가 둘이다(브라우저·Unity). 한쪽 관례에 맞춰 주면 다른 쪽은 되돌려야 하고, 그 되돌림은
반드시 여기저기 흩어진다. 뷰어가 셋이 되면 계약이 셋이 된다. 이것은 `VZ-I-01`을
「브라우저」에서 「가시화 뷰어」로 일반화한 것과 **정확히 같은 논리**다 —
특정 클라이언트의 사정을 계약에 넣지 않는다.

**② 표현하는 쪽이 흡수한다 — 채택.**
계약은 하나로 남고, 렌더러 관례는 렌더러가 안다.

**이것은 "좌표 변환 금지"(`BE-C-04`·`DT-03`)의 예외가 아니다. 층이 다르다.**

| | 하는 일 | 누가 |
|---|---|---|
| **좌표 변환** (금지) | *어느 기준점에서 잰 값인가*를 바꾼다. 로봇 로컬 → 구역 → 사이트 전역 | **백엔드 단독** |
| **표현 변환** (여기) | *같은 점을 이 렌더러의 관례로 그린다* | 뷰어 경계 한 곳 |

경계는 `View/FrameConvert.cs` **한 파일**이다. 이 밖에 축을 만지는 코드가 없고, 그 사실을
파일 머리말에 박스로 적어 두었다 — 나중에 누가 "여기서 변환하네?" 하고 다른 데서도
시작하면 끝이기 때문이다.

**기본값은 OFF(변환 없음)로 두었다.** 근거 셋 —

1. **아직 합의 전이다.** ON을 기본으로 두면 "백엔드가 오른손으로 준다"를 코드가 먼저
   단정하는 것이 된다. 확정 안 된 것을 기본값으로 굳히지 않는다.
2. **계약 문구가 이미 렌더러 친화적이다.** `BE-C-04`는 `y=위 · 바닥 x-z`라고 썼는데,
   로보틱스 관례(ROS)는 `z=위`다. y-up을 명시했다는 것은 작성자가 이미 그래픽스 쪽
   프레임을 염두에 두었다는 신호로 읽었다. 확증은 아니지만 기본값을 고를 근거는 된다.
3. **"아무것도 하지 않음"이 안전한 기본이다.** 규칙 3의 기본 자세와 같은 방향이고,
   변환은 명시적으로 켜는 선택으로 남는다.

**비대칭 마커** — 씬 원점에 대문자 F 표식을 세웠다. 대칭인 물체만 있는 씬은 좌우가 뒤집혀도
아무도 못 알아챈다(로봇이 원을 그리면 뒤집힌 궤적도 똑같이 원이다). F는 거울상을 즉시
알아볼 수 있는 형태이고, 계약 좌표의 z-y 평면에 세워 **z 부호를 뒤집는 변환이 정확히 이 F를
뒤집게** 했다. **마커도 다른 모든 것과 같은 변환을 거쳐 그려진다** — 마커만 Unity 좌표로
직접 그리면 플래그를 뒤집어도 마커는 그대로라 무엇이 기준인지 알 수 없게 된다.

### 3. 웹과 Unity가 **같은 규칙을 두 번 구현**하게 된 목록

웹 코드를 C#으로 옮겨 붙이지 않았다. 프로세스 경계를 넘는 계약이므로 한쪽 타입을 가져다
쓰면 "서버를 갈아끼우면 클라이언트가 깨진다"는 결합이 생긴다. 대신 **어긋나면 어디가 먼저
티가 나는지**를 같이 적어 둔다 — 그게 이 중복을 감당 가능하게 만드는 유일한 방법이다.

| 규칙 | 웹 | Unity | 어긋나면 어디서 드러나나 |
|---|---|---|---|
| 상태 3층 → 표시 4종 매핑 | `src/data/statusModel.ts` | `Data/StatusModel.cs` | **즉시.** 같은 대상이 한쪽은 정상, 다른 쪽은 판단 불가 |
| `stale` 재계산 금지 | 〃 | 〃 | **평소에는 안 드러난다.** 사용자 PC 시계가 틀어진 날에만 |
| 집약 표기 정규화(두 철자) | `src/data/aggregation.ts` | `Data/AggregationSpec.cs` | 표기 형식이 바뀌는 날. 한쪽만 `unknown`으로 떨어진다 |
| 재집약 차단 | 〃 | 〃(관문만) | 뷰어가 요약을 그리기 시작할 때 |
| 권한 범위 판정(`zones`에 `*`) | `src/data/permissions.ts` | `Data/TwinStore.ApplyScope` | 좁은 역할로 로그인할 때(`role-narrow`) |
| 렌더 병합 100ms | `src/data/mergeScheduler.ts` | `Data/MergeScheduler.cs` | **계측값으로만.** 화면으로는 안 보인다 |
| 지수 백오프(500ms·×2·15s·±25%) | `src/transport/backoff.ts` | `Transport/Backoff.cs` | 서버 재기동 시 한쪽만 늦게 붙는다 |
| 구독 자동 복원 | `src/transport/WsTransport.ts` | `Transport/GatewayWebSocketTransport.cs` | 재연결 후 한쪽 화면만 빈다 |
| 표시 문구 사전(상태·집약 라벨) | 각 모듈 | 각 모듈 | **의미는 같고 글자만 다르다** — 아래 미결 2번 |
| 원천 종류 표기(`VZ-C-06`) | **없음** | `Data/OriginKindSpec.cs` | 웹에 붙이는 날 |

**가장 위험한 줄은 `stale` 재계산 금지다.** 어겨도 평소에는 두 화면이 같아 보이고, 시연
당일 노트북 시계가 몇 분 틀어져 있으면 그때 처음 갈린다. 그래서 양쪽 모두 서버가 준
`availability`를 그대로 쓰고, "최근 수신 N초 전"도 `envelope.ts - last_seen`으로 구한다 —
**두 값이 모두 서버 시각이라 클라이언트 시계가 개입하지 않는다.**

**두 번째로 위험한 줄은 렌더 병합이다.** 어긋나도 화면상 아무 일도 안 일어난다. 그래서
Unity 쪽에 계측기(`SceneUpdateMeter`)를 붙여 **씬 반영률을 숫자로 화면에 띄운다.**

### 4. 원천 종류(`VZ-C-06`) — 실패 방향을 먼저 정했다

목 게이트웨이는 아직 이 표기를 싣지 않는다. 그래서 이번에 확인해야 하는 것은
**"표기 부재를 `unknown`으로 다루는 경로가 실제로 도는가"** 였다.

> **표기가 없거나 못 읽으면 `unknown`으로 두고 그 사실을 화면에 표시한다.
> 실물로 단정하지 않는다.**

집약 표기에서 한 번 밟은 함정이다("모르면 raw"로 떨어뜨렸더니 재집약 차단이 조용히 풀렸다).
여기서 같은 실수를 하면 **표기 없는 시뮬레이션 값이 실물로 기록된다** — 감사에서 훈련과
실제가 같은 모양으로 남는 바로 그 사고다.

**집약 표기와 한 군데가 갈린다**는 점을 코드 주석에 남겼다. 집약은 "필드가 없는 채널"이
정상이라(상태·명령 채널에는 집약 개념이 없다) 부재를 `raw`로 본다. 원천 종류는 **모든 값에
붙는 메타**이므로 부재가 정상이 아니다. 그래서 부재도 `unknown`이고, 사유만 나눴다 —
`NotLabelled`(아직 안 붙였다) / `Unreadable`(붙였는데 못 읽는다). 통합 첫날 대응이 다르다.

씬에서는 **색과 모양이 함께** 바뀌므로 흑백에서도 실물과 시뮬레이션이 갈린다
(실물=흰 정육면체 / 시뮬=청록 구 / 재생=보라 캡슐 / 미상=회색 원반).

### 5. 연결 방식이 미정이라 — 전송을 인터페이스 뒤로 격리했다

게이트웨이 직결인지 웹 대시보드 경유인지 아직 정해지지 않았다. **지금 정하지 않아도 되는
것을 정하면 나중에 상위 코드까지 끌려간다.**

`ITwinTransport` 하나를 두고 구현체는 `GatewayWebSocketTransport`(직결) **하나만** 만들었다.
경로가 정해지면 구현체를 추가하고 `TwinViewer`의 생성 한 줄만 바꾼다. `Data/`·`View/`는
WebSocket도 URL도 토픽도 알지 못한다.

**가정 셋**을 명시해 둔다.

1. 직결로 붙는다고 가정했다(목 게이트웨이가 지금 그렇다). 경유 안이 되면 구현체를 바꾼다.
2. 접속 주소는 인스펙터 필드다. **하드코딩된 곳이 없다.** 8787/8788 어느 쪽이든 맞춘다.
3. `ClientWebSocket`을 썼으므로 **WebGL 빌드에서는 돌지 않는다.** 경유 안으로 가거나
   WebGL이 필요해지면 그 파일을 통째로 갈아끼우는 자리이고, README에 명시했다.

### 6. 스레드 경계를 **메서드 하나로** 눈에 보이게 했다

`ClientWebSocket`은 스레드 풀에서 돌고 Unity API는 메인 스레드 전용이다. 구현체가 콜백을
직접 부르면 호출자가 어느 스레드에 있는지 알 수 없어 **언젠가 반드시 "가끔 죽는" 버그**가
된다. 수신은 큐에 쌓고 메인 스레드가 `Update()`에서 `Pump()`로 꺼내 간다.

### 7. 하지 말라고 한 것 — 지켰다

- **시뮬레이션 없음.** 물리·이동 로직·가짜 값 생성 경로가 하나도 없다. 씬의 모든 위치는
  수신 봉투에서 온다.
- **제어 UI 없음.** `command`·`plan_decision` 메시지를 보내는 코드가 없고, `command_result`·
  `control_lock` 채널을 구독조차 하지 않는다.
- **좌표·축 변환 없음** (손잡이 한 곳 예외, 위 §2).
- **웹 대시보드 미변경.** 목 게이트웨이도 읽기만 했다.
- **패키지 추가 없음.** `com.unity.nuget.newtonsoft-json` 하나뿐. URP/HDRP·에셋 스토어·
  TextMeshPro 전부 도입하지 않았다.

## 검증

붙여 계측했다. 검증 하네스(에디터 스크립트 + 리포터 + 오케스트레이션 셸)는 일회성이라

### 검증 5 보강 — 좌표를 내는 대상에서 정지를 실제로 밟았다

목의 `sensor-02`는 좌표를 발행하지 않아 "제자리에 선다"를 위치로 보일 수 없다. 그래서
`MOCK_STALE_MS=8000`으로 게이트웨이를 띄우고 서버를 죽여 `robot-01`로 다시 확인했다.

| 시점 | 보간 모드 | 위치 |
|---|---|---|
| t=4s (정상) | 보간 중 | (12.308, 0, −10.492) |
| t=11s (서버 정지 5초) | **최신값 유지** | (17.420, 0, −7.073) |
| t=20s (서버 정지 14초) | **보간 정지** | (17.420, 0, −7.073) — **9초간 이동량 0.0000m** |

- 최신 표본을 넘어선 순간 **외삽 없이** 그 자리에 붙었고(최신값 유지),
- 서버가 준 임계 8,000ms를 넘기자 **보간 정지**로 넘어갔다.
- 이 구간 `availability`는 `online`으로 남아 있었다(서버가 죽어 stale 판정을 밀어줄 수
  없었다) — **정지 조건을 둘로 나눈 이유가 그대로 드러난 사례다.**

### 검증 9 — 두 클라이언트를 **동시에** 붙였다

같은 게이트웨이에 Unity 뷰어와 **웹 대시보드의 실제 데이터 레이어 모듈**
(`src/data/statusModel.ts`·`aggregation.ts`를 Node에서 그대로 import)을 동시에 접속시켜

### 검증 중 발견해 고친 것

**역할 조회가 조용히 사라지고 있었다.** `RequestRole()`을 연결 직후에 부르면 소켓이 아직
열리기 전이라 메시지가 버려지고, 화면이 영영 "권한 미수신"으로 남았다. 첫 실행에서
`권한 (미수신)`으로 드러났다. 구독과 **같은 이유로** 요청을 기억해 두었다가 연결이 열릴 때
보내도록 고쳤고, 재연결 시에도 다시 조회된다. 고친 뒤 `전 구역 운영자 · 범위 *`로 확인.

> 이 버그는 **화면에 숫자를 띄워 두지 않았으면 못 봤다.** `VZ-C-04`가 "화면 차단은 편의"
> 라서 없어도 아무 예외가 안 난다. 진단 패널이 값을 한 자리에 모아 놓은 덕에 잡혔다.

## 미결 사항

### 신규

1. **검증 9에서 어긋난 것 — 의미 불일치는 없다.** 표시 4종·3층·권한 범위·좌표계·집약 판정이
   20건 전부 일치했다. **2단계 시뮬레이터를 붙이기 전에 알아야 할 목록은 현재 비어 있다.**

2. **다만 표시 문구가 갈린다 — 의미가 아니라 글자다.** 집약 표기를 웹은 `원본 측정`,
   Unity는 `원본`으로 쓴다. 라벨 사전이 두 곳에 따로 있어서다. 지금은 무해하지만
   **관제사가 두 화면을 번갈아 보면 다른 말로 읽는다.** 사전을 계약 쪽으로 올릴지
   (서버가 표시 문구를 내려주는 안) 각자 두되 문구만 맞출지 결정 필요. → 회의 한 줄.

3. **`VZ-C-06` 원천 종류의 필드 형태 — 회의에 가져갈 안.** 봉투 최상위에 `origin_kind`를
   두고 `aggregation`과 같은 자리·같은 성격으로 다룬다.

   ```jsonc
   "origin_kind": "real"                    // 축약형

   "origin_kind": {                          // 객체형
     "kind": "simulated",                    // real | simulated | replay — 이 셋만
     "producer": "unity-sim-01",             // 어느 원천이 만들었나
     "session_id": "drill-2026-0821-01"      // 훈련 세션. 감사에서 같은 훈련을 묶는 근거
   }
   ```

   - 축약형/객체형 둘 다 받는 것은 `aggregation`이 이미 그래서 형태를 맞춘 것이다.
   - **`kind`는 세 값만 인정한다.** 모르는 철자를 추측해 늘리면 함정을 하나 더 만든다.
   - 이름이 바뀌면 Unity는 `OriginKinds.EnvelopeField` 상수 하나만 고친다.
   - **명령 요청에 동봉하는 후단은 이번 범위 밖이다** — Unity에 명령 경로가 없고,
     웹 대시보드의 명령에 붙이는 것은 별건이다.
   - 여전히 **붙여 줄 파트가 없으면 요구사항이 성립하지 않는다**(직전 보고서 미결 1번 유효).

4. **연결 방식이 미정이라 세운 가정** — 직결로 붙는다고 가정했다. 전송은 `ITwinTransport`
   뒤에 격리했고 구현체는 직결 하나뿐이다. **경유 안이 되면 구현체만 갈아끼운다.**
   `ClientWebSocket`을 썼으므로 **WebGL에서는 돌지 않는다**는 것이 이 가정에 딸린 비용이다.

5. **자세(orientation)가 계약에 없다.** 봉투는 **위치만** 준다. 로봇이 어느 쪽을 보고 있는지
   그릴 수 없다. `velocity`로 추정할 수는 있지만 **추정이므로 하지 않았다** — 보간과 추정을
   가르는 것과 같은 이유다. 트윈 화면에서 로봇의 향(向)은 관제 정보이므로 계약에 자리가 필요하다.

6. **손잡이 규약이 여전히 없다**(직전 보고서 미결 5번). 뷰어 기본값은 "변환 없음"이고
   근거는 위 §2에 적었다. 확정되면 플래그를 없애고 한쪽으로 고정한다.

7. **레지스트리 변경 통지 경로가 없다.** `VZ-I-03`은 "최초 1회 + 변경 통지 시 갱신"인데
   통지 채널이 정의되어 있지 않다. 뷰어는 지금 최초 1회만 받고, 배포 상태가 바뀌어도
   재생을 다시 해야 반영된다. 웹도 같은 상태다.
