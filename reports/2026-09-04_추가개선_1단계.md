# 추가 개선 1단계 — 캔버스가 화면 높이를 안다

**지시서**: `작업프롬프트_추가개선_260904.md` §1
**대상 요구사항**: `VZ-N-04`(사용자가 옮긴 노드를 되돌리지 않는다) · 기존 「첫 화면에 다 들어온다」
**기준 커밋**: `ebd2bd5` (요구사항 v1.2 문서 개정)

## 무엇이 문제였나

9/1에 「폭을 재서 접는다」를 넣을 때 **높이를 재지 않았다.** 결과가 셋이었다.

1. `columnsPerBand(availableWidth)` — 폭만 받으니 배치는 늘 **폭이 허락하는 최대 열**로 붙였다.
   16:9 모니터에서 그래프가 가로로 긴 띠가 되고 아래는 통째로 비었다.
2. 캔버스 높이 바닥값이 `Math.max(390, 내용)` — 작은 마일스톤은 큰 모니터에서도 390px 에서
   멈췄다. 노드를 아래로 끌어 놓을 자리도 그만큼밖에 없었다.
3. 세로가 얼마나 남는지 모르니 「이만큼은 접어도 된다」는 판단 자체가 불가능했다.

## 무엇을 했나

### 잰다 — 폭과 **창 바닥까지 남은 자리**

`TaskGraph` 의 `ResizeObserver` 가 폭과 함께 높이를 낸다. 세로는 자기 `clientHeight` 로 잴 수
없다 — 그 값이 곧 내용 높이라 자기를 되먹인다. 그래서 **창 바닥까지 남은 자리**를 잰다.

```
높이 = window.innerHeight − 캔버스 시작 y − 아래에 깔린 것 − 페이지 아래 여백
```

「아래에 깔린 것」(범례·안내줄·패널 아래 여백)은 고정 픽셀로 적지 않고 **패널 바닥과 캔버스
바닥의 차이**로 잰다. 캔버스가 커지면 패널도 같이 커지므로 이 차이는 캔버스 높이와 무관하고,
그래서 이 계산이 순환하지 않는다. 창 높이만 바뀌면 자리 크기는 그대로라 `ResizeObserver` 가
깨어나지 않으므로 `window.resize` 도 함께 듣는다.

바닥값은 **옛 390px 그대로** 남겼다(`MIN_CANVAS_HEIGHT`). 아주 낮은 창에서 지금보다 나빠지지
않는다는 뜻이다.

### 고른다 — 잰 상자에 맞춰 접는다

`columnsPerBand(availableWidth, availableHeight, columnHeights)`.

후보는 `MIN_COLS`(3) ~ 폭 최대 열이고, 그중 **잰 높이 안에 들어오면서 내용의 가로세로비가
잰 상자의 비에 가장 가까운 것**을 고른다. 비의 거리는 로그로 잰다 — 2배 넓은 것과 2배 좁은
것이 같은 만큼 어긋난 것이기 때문이다.

- 세로가 남으면 → 열이 줄고 밴드가 는다 (세로를 쓴다)
- 세로가 모자라면(어떤 후보도 안 들어오면) → 폭 최대 열. 더 접어 봐야 더 길어질 뿐이다
- **한 밴드에 다 들어가는 그래프는 접지 않는다** — 아래 §「지시서와 다르게 한 곳」 2

### 캔버스 바닥값을 잰 높이로

`Math.max(390, 내용)` → `Math.max(잰 높이, 내용)`. 작은 그래프도 창 바닥까지 자리를 차지한다.

## 실측

### 창 크기별 밴드 × 열 — 「임무 전체」 보기

「잰 높이」는 그 창에서 `TaskGraph` 가 재게 되는 값의 어림이다(상단 바·머리줄·범례를 뺀 나머지).

| 대본 | 창 | 잰 높이 | 전 (폭만 앎) | 후 (폭·높이) |
|---|---|---|---|---|
| `MSN-260831-01` (17노드) | 1366×768 | 390 | 6열 1310×905 | **그대로** |
| | 1600×900 | 590 | 7열 1530×905 | **그대로** |
| | 1920×1080 | 770 | 8열 1750×685 | **그대로** |
| | 2560×1440 | 1130 | 11열 2410×685 | **8열 1750×685** |
| `MSN-260831-02` (18노드) | 1366×768 | 390 | 6열 1310×905 | **그대로** |
| | 1600×900 | 590 | 7열 1530×905 | **그대로** |
| | 1920×1080 | 770 | 8열 1750×535 | **그대로** |
| | 2560×1440 | 1130 | 11열 2410×535 | **8열 1750×535** |
| `MSN-260831-03` (16노드) | 1366×768 | 390 | 6열 1310×605 | **그대로** |
| | 1600×900 | 590 | 7열 1530×605 | **그대로** |
| | 1920×1080 | 770 | 8열 1750×**385** | **7열 1530×605** |
| | 2560×1440 | 1130 | 11열 2410×**385** | **7열 1530×605** |

**세로를 더 쓰게 된 것은 3편의 큰 창 둘이다 — 385px → 605px (잰 높이 770·1130px).**
3편은 16노드가 거의 일직선이라 폭만 알던 배치가 2밴드짜리 납작한 띠로 붙였고, 그것이 이번
문제가 가장 크게 보이던 자리다.

1·2편의 2560px 열 줄임(11열 2410px → 8열 1750px)은 세로가 아니라 **가로**를 줄인 것이다.
높이는 그대로인데 폭이 660px 줄었다 — 큰 모니터에서 눈이 가로로 덜 움직인다.

작은 창(1366·1600)에서는 **한 픽셀도 바뀌지 않았다.** 세로가 애초에 모자라 접을 여지가 없다.

### 캔버스 세로 자체

바닥값이 390px → 잰 높이다. 1920×1080 창에서 어림 770px, 2560×1440 에서 1130px — 작은
마일스톤(2~3노드)도 이제 화면 아래까지 자리를 차지하고, 그만큼 노드를 끌어 놓을 자리가 는다.

## 검증

- `verify:layout` **확장** — 창 넷(1366×768 / 1600×900 / 1920×1080 / 2560×1440)에서 최대 y 를
  본다. 배치의 속을 흉내 내지 않고 **높이를 모르는 배치(대조군)와 아는 배치를 나란히 돌려
  결과만** 비교한다.
  - B. 대조군이 잰 높이 안에 들어왔으면 아는 배치도 **반드시** 들어온다
  - C. 대조군조차 안 들어오면 아는 배치가 **더 접지 않는다**(대조군과 같은 높이)
  - D. 세로가 남는 창에서는 **실제로 더 쓴다** — 0건이면 높이 인자는 죽은 인자다 (실측 2건)
  - E. 한 밴드에 다 들어가는 그래프는 **접지 않는다** (없던 `↵` 를 만들지 않는다)
  - 폭 상한·겹침 검사는 높이를 아는 배치에도 그대로 건다
  - 음성 대조군 셋 — 높이를 안 주면 옛 배치와 **한 픽셀도** 다르지 않다 / 세로가 무한히 남으면
    열이 줄어든다 / 세로가 모자라면 폭 최대 열을 쓴다
- **기존 verify 18종 + `typecheck` 전부 통과.** `verify:standalone` 은 Windows 에서 **무개정
  통과** (단독 의존 그래프 49개 파일).

## 지시서와 다르게 한 곳

1. **`columnsPerBand(width, height)` 가 아니라 `(width, height, columnHeights)` 다.**
   그 둘로는 「세로가 남는다」를 계산할 수 없다 — 접힌 높이는 열 수와 **각 열의 높이**가
   정하기 때문이다(밴드 높이 = 그 밴드에서 가장 높은 열). 열 높이 목록을 받으면 어떤 열
   수로도 결과 높이를 정확히 구할 수 있다. `dagLayout` 이 열 높이를 먼저 구하도록 순서만
   앞으로 옮겼다 — 열 안의 자리는 밴드 나눔과 무관해서 값은 달라지지 않는다.

2. **한 밴드에 다 들어가는 그래프는 세로가 남아도 접지 않는다.**
   지시서 문면(「세로가 남으면 열을 줄여 밴드를 늘린다」)을 그대로 넣었더니 1편 `MS-E`
   (3노드·깊이 4열)가 1920px 에서 2밴드로 접혔다. 한 줄에 다 들어가는 것을 굳이 접으면
   **읽을 이유가 없는 `↵ 줄바꿈`** 이 생긴다. 접기는 어차피 접힐 그래프를 더 낫게 접는
   일이므로 여기서 멈춘다. `verify:layout` 의 E 가 이것을 지킨다.

3. **「세로가 남으면 무조건 열을 줄인다」가 아니라 잰 상자의 비에 맞춘다.**
   최대한 줄이는 규칙으로는 2560×1440 에서 3편이 **870×825px** 짜리 세로 기둥이 됐다 —
   2560px 모니터에서 가로의 3분의 1만 쓰는 모양이라 오히려 나빴다. 상자의 비를 목표로 두니
   1530×605 로 안정된다. 「세로를 쓴다」는 지시의 취지는 지키되 방향만 상자에 맞췄다.

## 하지 않은 것 (지시서 §1 「하지 말 것」)

- 자동 정렬·확대축소·미니맵 — 만들지 않았다.
- 사용자가 옮긴 노드는 창 크기가 바뀌어도 그대로다. `movedPositions` 초기화는 여전히
  `[layoutMode]` 에만 걸려 있고 `layoutWidth`·`layoutHeight` 는 그 의존 배열에 없다 (`VZ-N-04`).
