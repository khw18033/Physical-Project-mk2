## 변경 사항

### 1. `구현계획서.md` v0.3 → v0.3.1

- **§3 협업 운영 프로세스 신설** (기존 3·4장은 4·5장으로 이동)
  - §3.1 요구사항 정립 5단계 — 각 단계별 본 파트 산출물과 진행 상태 표
    - 중요 판단: **4단계(계약 스키마 개정)는 3단계(인터페이스 확정) 이후**여야 한다.
      Phase 0 개정 항목 중 외부에 닿는 것(REQ-702/703/704, REQ-907/908)은 대기시키고,
      외부에 닿지 않는 것(REQ-405, REQ-105, REQ-504)만 선행한다. 순서를 뒤집으면 두 번 고친다.
  - §3.2 PM 체계 — PM은 대규. 따라서 본 파트는 **기다리는 쪽이 아니라 필드안을 먼저 내는 쪽**으로 움직인다.
  - §3.3 제출 현황 — 파트별 인터페이스 문서 작성 상태
- **Phase 7에 외부 일정 앵커 추가** — 시연 일정이 확정되면 그 날짜가 실질 마감이 되며, Phase 7을 앞당기고 시연 경로만 우선 완성한다.

### 2. `요구사항정의서.md` §6 도입부

인터페이스 시트가 별도 문서로 분리되었음을 명시. §6 표는 "어떤 계약이 필요한지의
목록", 필드 수준 명세는 `docs/interfaces/` 문서로 역할을 나눴다.

### 3. `docs/interfaces/2026-08-18_otel-interface.md` 신규 — 이번 요청의 본 산출물

가시화 파트 ↔ 대규(OTel) 구간의 수신부/송신부 명세. 회의 §4가 요구한 "공통
인터페이스 문서 1개"에 그대로 붙일 수 있는 표 구조로 작성했다.

- **받아야 하는 것 8건**: I-1 Prometheus 질의 규약 / **I-2 계층 식별자 ↔ 라벨 대응 ★** /
  I-3 Grafana API / I-4 스트림 전송 규약 / I-5 감사 로그 **조회** API / I-6 권한·역할 모델 /
  I-7 시각 기준 / I-8 데이터 추상화 수준
- **줘야 하는 것 4건**: **O-1 제어 명령 이벤트 스키마 ★**(18개 필드안 제시) /

- 합의 순서·위험도 표, 대규에게 보내는 질문 8개, 우리 쪽 준수 사항 5개

## 작성 중의 판단

1. **O-1을 우리가 먼저 냈다.** 회의 §5의 "완벽하지 않아도 논의 가능한 안을 가져오면
   코멘트를 받을 수 있다"에 대한 실행이다. 스키마 확정을 기다리면 Phase 6이 통째로 밀린다.
   `origin.path`(manual/voice/llm_suggestion/auto)가 REQ-908의 핵심이며, 회의 §4 수문
   예시가 요구한 "어떤 방식으로"에 직접 대응한다.

2. **I-5(감사 로그 조회 API)는 요구사항정의서 §6에 없던 항목이다.** §6은 감사 로그를
   아웃바운드로만 잡았는데, "이 게이트를 마지막으로 조작한 사람"을 화면에 표시하려면
   되읽어야 한다. **쓰기만 있고 읽기가 없으면 책임 소재 추적이 운영 화면에서 확인되지 않는다.**
   요구사항정의서 §6 표에 반영할지는 다음 개정에서 판단한다.

3. **I-6(권한·역할 모델)도 §6에 명시되지 않았던 항목이다.** NFR-001이 RBAC을 요구하는데,
   역할 정의는 우리가 만들 수 없다.

4. **I-2는 나영 파트의 REQ-201과 같은 문제의 다른 면이다.** 컨테이너 ID / 디스크립터 ID /
   Entity ID / 메트릭 라벨 — 네 체계의 대응이 각자 정해지면 어긋난다. 3자 동시 확정을 권고했다.

5. **I-4에서 요구사항정의서 §3과 충돌 가능성을 명시했다.** §3은 "하드웨어에 직접 접촉하지
   않고 관측 스택을 경유한다"고 적었으나, 영상 스트림은 예외일 수 있다. 대규의 판정이 필요하다.
