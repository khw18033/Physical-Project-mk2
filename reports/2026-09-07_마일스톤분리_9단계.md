**선행**: 8단계(D 판 · `reports/2026-09-07_마일스톤분리_8단계.md`) — 프롬프트를 **B 로 확정**

**날짜**: 2026-09-07
**모델**: Qwen3 8B Q4_K_M (화면이 고른다 — 아래 §6)

## 결론 먼저

**발화 패널의 뒤 세 칸이 `목` 을 뗐다.** 새 화면을 만들지 않았고 그 자리를 채웠다.

| 칸 | 전 | 후 | 누가 |
|---|---|---|---|
| 녹음 · 전사 · 검토 | 실제 | 그대로 | — |
| 의도 분석 · 마일스톤 분리 | `목` | **`VZ-G-01`** `generateMission()` | **모델** |
| 태스크 생성 | `목` | **`VZ-G-02`** `solveDeps()` | **규칙** (모델이 아니다) |

실제로 도는 것을 확인했다 — 대본에 없는 문장 하나로 마일스톤 6건이 나왔고, 제안은
승인 전까지 아무것도 실행하지 않았으며, 승인하자 생성 근거가 기록 열 첫 줄에 들어갔다
(§4의 실행 기록).

그리고 **7단계 §5 가 남긴 실패 유형 하나가 원천에서 사라졌다.** `utterance.confidence: 5`
는 이제 구조적으로 불가능하다 — 서비스가 부르는 쪽 값으로 덮어쓴다(§3).

## 1. 제안·수락 흐름 — 승인 선이 걸린 자리가 하나 늘었다

```
발화(음성 또는 직접 입력)
   ↓ 사람의 요청을 먼저 기록한다 (issueCommand · produced_by=human)
   ↓
키워드 대조 (matcher.ts)          ─── 맞으면 그 편이 제안이 된다 (대본 배지)
   ↓ 맞은 편은 예시에서 뺀다
generateMission()  VZ-G-01        ─── 마일스톤 목록 + 생성 근거
   ↓
solveDeps()        VZ-G-02        ─── deps 는 규칙이 매단다 (모델이 아니다)
   ↓
제안 상태  ← **여기까지가 이 패널의 일이다**
   ↓ 사람이 승인 (acceptProposal — 문은 하나)
현재 임무 · 캔버스 · 기록 열
```

### 대본이 맞으면 대본이 이긴다

이 결정이 흐름에서 가장 중요한 자리다. 대본 조회는 원래 주석이 적어 둔 대로 **LLM 뒤의
대조군이자 시연 안전망**이고, 모델이 그 자리를 조용히 가져가면 시연에서 무엇이 답했는지
아무도 모르게 된다. 그래서 대본이 맞은 경우 **모델의 답은 나란히 뜨기만 한다.**

사람이 원하면 버튼 하나(「이 AI 제안으로 바꾸기」)로 제안을 바꿀 수 있고, **바꿔도 여전히
승인 앞**이다. 바꾸는 것과 승인하는 것은 다른 일이다.

부수 효과가 하나 있다. 모델이 실제로 쓰이는 자리는 **대본이 못 맞히는 문장**이 되고,
그것이 정확히 이 기능이 필요한 자리다.

### 승인 전에는 기록 열이 비어 있다

제안 상태의 임무는 「승인 전에는 진행 사건이 하나도 없다」가 규칙이고, 열이 비어 있는
것이 곧 그 사실이다(`displayMission`). 그래서 **생성 근거도 승인 전에는 열에 안 넣는다** —
그 전까지는 제안이 들고 화면이 보여준다. 넣었으면 「아무 일도 없었다」가 깨진다.

거부하면 근거는 사라진다. 그것이 맞다 — 실행되지 않은 계획의 기록을 임무의 기록 열에
남기면 그 열이 「이 임무에 일어난 일」이 아니게 된다.

## 2. 배지 셋이 화면에서 어떻게 갈리는가

```
목    회색 빗금 · 회색 칩    아직 아무것도 안 했다 — 문장을 넣으면 무언가 뜬다
대본  초록 실선 · 초록 칩    키워드 대조로 미리 써 둔 편을 꺼냈다. LLM 이 아니다
AI    보라 실선 · 보라 칩    모델이 방금 만들었다 — 이름·프롬프트 지문·규칙이 함께 붙는다
      보라 **점선**          도는 중 (경과 초가 첫 칸에 붙는다)
```

**넷째 모양(점선)이 필요했다.** 끝난 것과 도는 것이 같은 얼굴이면 사람은 기다리는 줄
모른다 — 최대 12.2초다.

배지를 고르는 조건은 **화면에 한 줄뿐이다**(`producer`). 조건을 렌더 여기저기에 흩어
놓으면 「이 마일스톤은 누가 썼나」의 답이 렌더 순서에 달리게 된다.

```
genOutcome.proposed  → ai        모델의 답이 제안으로 서 있다
scriptMatch.matched  → script    대본이 이긴다
genPhase === running → running   도는 중
genOutcome !== null  → ai        대본이 못 맞혔고 모델이 냈다
그 외                → mock      아직 아무것도 안 했다
```

칸 문구도 주체를 말한다. AI 판의 셋째 칸은 「태스크 생성 → 노드 N · 의존 M **(규칙)**」
이다 — 「AI 가 deps 를 만들었다」로 읽히면 §5 의 결정이 화면에서 뒤집힌다.

### 되감기 화면에도 줄이 하나 늘었다

사람 조작 줄 위에 **AI 줄**이 생겼다. 같은 축에 찍히므로 「무엇이 만들었나 → 누가
받아들였나」가 위아래로 읽힌다. 대본에서 읽은 임무에는 AI 줄이 「생성 기록 없음」이라고
적힌다 — 빈 줄로 두지 않는다(사람 줄과 같은 규칙).

## 3. `utterance` 를 모델이 다시 쓰지 못하게 했다

7단계 §5 의 실패는 **모델이 되받아 적을 기회가 있어서** 생겼다. `mission_id` 와
`utterance` 는 부르는 쪽이 이미 아는 값이므로(6단계 §9), 서비스가 응답을 조립할 때
부르는 쪽 값으로 덮어쓴다(`_apply_caller_values`).

그 실패를 그대로 재현해 확인했다 — 7단계 A 판 1건이 낸 모양 그대로다.

```
덮어쓰기 전 계약 검증: ['$.utterance.confidence: 5 > 최대 1']
덮어쓰기 후 계약 검증: []
mission_id: MSN-260831-01
utterance : {"audio_ref": null, "text": "복도에 있는 …", "engine": "script", "confidence": 1}
기록에 남은 덮어쓰기:
  - {"field": "mission_id", "model": "MSN-WRONG-01", "used": "MSN-260831-01"}
  - {"field": "utterance",  "model": {… "confidence": 5}, "used": {… "confidence": 1}}
```

**검증은 덮어쓴 뒤에 한다.** 화면이 받는 것이 덮어쓴 객체이므로, 앞의 것을 재면 「통과
했다」가 화면이 든 것과 다른 객체의 이야기가 된다.

**덮어쓴 사실을 버리지 않는다.** 계약상 required 라 문법에는 그대로 두고(모델은 여전히
낸다), 무엇을 적었는지가 `extra.overwritten` 에 남는다. 그래서 「모델이 지시를 지켰는가」
축(`id_obeyed`)이 사라지지 않고 **그 기록을 읽는 쪽으로 옮겨졌다** — 고쳐 놓고 안 고친
척하지 않는다.

이 변경은 **8단계 측정 뒤에 넣었다.** 프롬프트를 확정하는 판(B 대 D)이 이 변경 전에
돌았으므로 그 표는 오염되지 않았고, 다음 실행부터는 스키마 통과율 축에서 이 유형이
빠진다 — 그 사실을 표가 아니라 여기 적어 둔다.

## 4. 기록에 남은 생성 근거 — 실제 실행

대본에 없는 문장으로 실제 서비스를 불러 확인했다.

```
발화: 5층 복도를 한 바퀴 돌면서 사람이 있는지 확인하고 알려줘
대본 매칭: none                      ← 대본이 못 맞힌다. 모델이 쓰이는 자리다
예시 3편: MSN-260831-01, -02, -03    ← 맞은 편이 없으므로 셋 다
가중치: Qwen3-8B-Q4_K_M              ← 화면이 고른다 (§6)
소요 11.96초 (첫 요청이라 적재 포함 25.3초)

생성 근거
  produced_by=ai · llama.cpp · 모델 Qwen3-8B-Q4_K_M · 스텁 false
  프롬프트 지문 107c2c5956246a23 (8,731자) · 문법 지문 3e2806814a745cd3
  규칙 12개 (rules_for() 가 준 그대로)
  재료: 장소 있음 · 장비 10건 · 예시 3편 · 노드 종류 규칙 없음
  스키마 오류 0건 · 덮어쓴 자리 0건

임무 MSN-GEN-260907-E2E
  MS-A 5층 복도 출발점에서 시작              [robot-01]
  MS-B 복도를 따라 이동하며 사람 탐지         [camera-02]
  MS-C 복도 끝에 도달                       [robot-01]
  MS-D 복도를 완전히 돌아서 출발점으로 돌아오기 [robot-01]
  MS-E 탐지된 사람 정보를 수집 및 보고        [robot-01]
  MS-F 임무 완료                            []
  태스크: 노드 0 · 의존 0

승인 선
  제안 뒤: current=MSN-260826-01 (안 바뀜) · phase=proposal · 기록 0건
  승인 뒤: current=MSN-GEN-260907-E2E · activatedBy=approval · playing=false
    seq   500,000 · T+0s · ai    · mission_generated · produced_by,model,prompt_digest,rules_applied,…
    seq 1,000,000 · T+0s · human · proposal_accepted
```

**열의 첫 줄이 「무엇이 만들었나」이고 그 다음이 「누가 받아들였나」다.** 그 순서가 뜻이고,
그것을 위해 `seq` 대역을 하나 더 갈랐다 — 열은 `(atSec, seq)` 순이고 둘 다 `atSec` 0 이라
대역 값이 순서를 정한다. 백엔드 1부터 · **AI 500,000부터** · 사람 1,000,000부터.
(처음에 AI 를 2,000,000 으로 두었더니 승인이 생성보다 먼저 읽혔고, `verify:proposal-gate`
가 그것을 잡았다.)

### 노드 0개를 0개라고 적는다

확정된 프롬프트(B)의 규칙 10은 「`tasks` 는 빈 배열로 둔다」이고 8단계는 그 형식을 바꾸지
않기로 했다. 그래서 `solveDeps()` 는 붙어 있으나 **매달 노드가 없다.** 화면은 그것을
「태스크 생성 → 노드 0개 (규칙 대기)」로 적는다.

대안 둘은 다 나쁘다 — 칸을 지우면 「`VZ-G-02` 의 어디까지 됐나」가 화면에서 사라지고,
노드를 지어내면 **모델이 낸 것이 아닌 것을 모델의 것으로 그리는 일**이 된다.
규칙이 실제로 도는지는 `verify:proposal-gate` 가 노드를 넣어 확인한다(관측→구동 순서가
복원되는지).

## 5. `verify:proposal-gate` — 대조군 포함

**승인 없이 제안이 캔버스에 올라가지 않는가.** 상태 기계를 Node 에서 그대로 돌린다.

| 보는 것 | |
|---|---|
| 제안은 실행이 아니다 | current·재생·`activatedBy` 가 안 바뀌고 **기록 열이 비어 있다** |
| 거부 | 제안이 사라지고 current 는 그대로 |
| 빈 승인 | 제안이 없으면 `acceptProposal()` 이 false 이고 아무것도 안 바뀐다 |
| 승인 | current 가 바뀌고 `activatedBy='approval'` |
| 근거 | `produced_by=ai`(모델·프롬프트 지문·규칙 목록) **다음에** `produced_by=human` 승인 |
| 문이 하나 | 대본 제안과 AI 제안이 **같은** `acceptProposal()` 을 지난다 |
| 그릴 수 없는 제안 | 마일스톤 0건은 제안으로 서지 않는다 |
| 규칙이 돈다 | 노드를 넣으면 `solveDeps()` 가 관측→구동 순서를 매단다 |
| 화면이 우회하지 않는다 | 발화 패널이 활성화 경로(`activateMission`·`acceptProposal`·`previewMission`)를 부르지 않는다 |

### 대조군 셋 — 전부 실제로 만들어 잡았다

```
제안이 곧바로 현재 임무가 되는 사본 (승인 건너뜀)
  → 제안만 했는데 현재 임무가 바뀌었다 (MSN-260826-01 → MSN-GEN-TEST-0001)
승인해도 생성 근거를 기록에 안 남기는 사본
  → 생성 근거가 기록에 0건이다 — 1건이어야 한다 (VZ-G-01 역추적)
발화 패널에 acceptProposal() 호출을 주입한 사본
  → 잡힘
```

셋째 대조군에는 함정이 하나 있었다. 패널의 머리말이 「승인의 문은 `acceptProposal()`
하나」라고 **설명**하고 있어서, 소스를 그대로 훑으면 그 설명이 위반으로 잡힌다.
규칙을 적어 둔 문장이 규칙 위반이 되면 사람은 설명을 지우게 되고, 그것이 이 저장소가
가장 피하려는 일이다 — 그래서 주석을 걷어낸 뒤에 훑고, **걷어내고도 실제 호출은 잡히는지**
를 대조군으로 확인한다.

### 이 검사가 가능해진 이유 — JSON import 에 속성 하나

`data/scenario.ts` 는 JSON 을 import 해서 Node ESM 이 열지 못했고, 그래서 그 파일에 걸린
규칙들은 전부 **소스 문자열 검사**로 내려앉아 있었다(그 사실이 `trace.ts` 머리말에 적혀
있다). `with { type: 'json' }` 를 붙이자 Node 가 그대로 연다 — 브라우저·Vite 는 이미
같은 문법을 쓰고 있었다(`LlmClient.ts` 의 계약 import).

**문자열 검사는 「그 함수가 실제로 무엇을 하는가」를 못 본다.** 이제 승인 선은 실제로
돌려서 확인한다.

## 6. 화면이 가중치를 고른다 — 안 짚고 넘어갈 수 없었던 자리

지시서에 없는 문제가 붙이는 중에 나왔다. **엔진은 모델 이름 없이 오는 요청을 거부한다** —
「아무거나 고르면 무엇을 쟀는지 알 수 없습니다」. 그 규칙은 측정에서 나왔지만 화면에도
그대로 걸린다: 어느 모델이 답했는지 모르는 제안에는 근거가 없다.

그래서 셋을 했다.

1. `probe()` 가 **가중치 목록과 지금 물고 있는 것**을 함께 가져온다. 화면에 `<select>` 가
   생겼고, 어느 것이 답할지가 눌리기 전에 보인다.
2. **이름을 코드에 박지 않았다.** README 가 「모델 목록은 코드에 없다」를 규칙으로 두고
   있고, 박는 순간 새 가중치를 넣는 일이 화면 수정이 된다.
3. 기본 선택은 **물고 있는 것 → 없으면 조건이 붙지 않은 것 중 가장 큰 것**이다.

3번이 필요했던 이유가 실제로 나왔다. 처음에 「목록의 첫 번째」로 두었더니
**EXAONE 이 골라졌다** — 이름순 첫 번째이고, 비상업 연구용 라이선스가 붙은 대조 모델이다.
시연·배포 경로가 그것을 조용히 물면 라이선스를 화면 밖에서 어기게 된다.

이름을 안 보면서 그것을 피하려고, **`models/` 에 그 가중치의 라이선스 전문이 함께 있는가**
로 갈랐다(`license_file`). 이 저장소는 조건이 붙은 가중치에만 전문을 받아 두었고, 그
사실이 곧 표식이다. 크기(`bytes`)를 두 번째 기준으로 쓴 것도 같은 이유다 — 이름이
아니면서 능력과 같은 방향으로 간다(4B 의 개수 일치는 0% 였다).

목록에서 **고르지 못하게 막지는 않았다.** 대조군으로 쓰는 것은 정당하고, 고르면
「별도 라이선스 (비상업 연구용)」이 그 줄에 적힌다.

```
EXAONE-3.5-7.8B-Instruct-Q4_K_M · 4.44 GB · 별도 라이선스 EXAONE-…LICENSE.txt
Qwen3-4B-Q4_K_M                 · 2.33 GB · 별도 라이선스 없음
Qwen3-8B-Q4_K_M                 · 4.68 GB · 별도 라이선스 없음   ← 기본 선택
```

### `verify:no-llm` 에 한 줄을 더했다

`shared/provenance.ts` 를 「생성과 무관해야 하는 것」 목록에 넣었다. 임무 저장소가 이
파일을 import 하므로, 이 파일이 생성 계층을 끌어오는 순간 `data/scenario.ts` 가 전이로
끌어오게 되고 그 목록 전체가 무의미해진다. **오늘 타입인 것이 내일 함수가 된다.**

근거의 *모양*을 `generate/` 밖 중립 자리에 둔 이유가 그것이다 — 임무 저장소는 「AI 가
만든 것에는 근거가 붙는다」만 알고, 어떤 서비스가 만들었는지는 모른다.

### `verify:human-trace` 의 대조군 하나가 줄끝에 매달려 있었다

「조작 시각을 임무 끝에 몰아 두는 사본」이 `'    atSec,\n'` 을 자리표로 쓰고 있었다.
`.gitattributes` 는 저장소 안을 LF 로 고정하지만 작업 트리는 환경의 관례를 따르므로
(`core.autocrlf`) **Windows 체크아웃에서는 CRLF 다.** 그때 사본이 안 만들어지고 검사는
「원본이 바뀌었나?」라고 말한다 — 원본은 그대로인데. 읽을 때 줄끝을 맞추도록 고쳤다.

같은 이유로 자리표도 정확히 했다. 9단계에 같은 모양의 AI 사건(`appendGenerated`)이
생겨서 `atSec,` 하나로는 어느 쪽인지 말할 수 없다 — 대역 이름(`HUMAN_SEQ_BASE`)까지 짚는다.

### 번들 — 모델은 사이드카다

`verify:standalone` 은 크기를 재지 않는다(셸/탭 경계만 본다). 그래도 이 저장소는 탭 이식
때부터 KB 를 적어 왔으므로 재서 적는다. **같은 커밋에서 이 작업 전후를 각각 빌드했다.**

| | 전 | 후 | 차이 |
|---|---|---|---|
| `standalone.js` | 333.90 kB | **372.56 kB** | +38.66 kB |
| (gzip) | 102.30 kB | **114.16 kB** | +11.86 kB |
| `standalone.css` | 32.36 kB | 35.22 kB | +2.86 kB |
| **모델** | 0 | **0** | 사이드카 (5.03 GB) |

늘어난 38.66 kB 의 절반은 **데이터**다 — `places.json` 16.2 KB · `equipment.json` 2.9 KB.
그라운딩 재료를 화면이 고르기 때문이고(측정 경로와 같은 조건), 나머지가 생성 계층
코드다. 배치 ①(생성 꺼짐)에서도 이만큼은 들어간다 — 계약과 재료는 빌드에 있고 모델만
없다.

## 8. 지시서와 다르게 한 곳 · 하는 중에 나온 것

| 지시 | 실제 | 왜 |
|---|---|---|
| 「발화 → 생성 서비스 → 제안」 | **대본이 맞으면 대본이 이긴다** | 대본 조회는 LLM 뒤의 대조군·시연 안전망이다(원래 주석). 모델이 그 자리를 조용히 가져가면 시연에서 무엇이 답했는지 모른다 — 대신 나란히 띄우고 사람이 버튼으로 바꾼다 |
| — (지시에 없음) | **가중치 선택 UI 를 더했다** | 엔진이 모델 없는 요청을 거부한다. 안 붙이면 화면의 생성 경로가 **한 건도 못 돈다** (§6) |
| — (지시에 없음) | **`license_file` 을 서비스가 낸다** | 기본 선택이 비상업 연구용 모델로 떨어졌다. 이름을 코드에 박지 않고 피하는 방법이 이것뿐이었다 |
| — (지시에 없음) | `scenario.ts`·`library.ts` 의 JSON import 에 `with { type: 'json' }` | 그것 없이는 `verify:proposal-gate` 가 소스 문자열 검사로 내려앉는다 (§5) |
| — (지시에 없음) | 되감기 축 나눗셈에 0 방어 | 생성된 임무는 `durationSec` 이 0이다(재생할 사건이 없다). 없으면 눈금 위치가 전부 `NaN%` 가 되고 CSS 에서 조용히 무시된다 |
| 보고서 이름 `2026-09-XX` | `2026-09-07` | |

### 고치지 않고 적어 두는 것 하나 — 예시의 항목 차례

`verify:no-leak` 6번(화면 예시 ≡ 측정 예시)을 붙이다가 나왔다.

문법(`gbnf.ts`)은 객체 항목 차례를 **계약의 `properties` 차례로 고정한다.** 그런데 예시가
보여주는 `utterance` 의 차례는 정답셋 파일에서 온 `text · engine · confidence · audio_ref`
이고, 계약은 `audio_ref · text · engine · confidence` 다. `lib/fewshot.mjs` 가 「예시가
다른 순서면 모델이 예시와 문법 사이에서 싸운다」고 적어 둔 그 상황이 `utterance` **안쪽**
에서 일어나고 있다.

**이번에 안 고쳤다.** 고치면 프롬프트 바이트가 바뀌고, 그러면 8단계가 확정한 B 판과 다른
조건이 된다 — **다시 재야 하는 변경**이지 붙이는 김에 끼워 넣을 변경이 아니다. 대신
화면을 측정 경로에 맞춰 두었고(글자까지 같다), `verify:no-leak` 이 둘을 대조하므로
**측정 경로가 계약 차례로 바뀌면 화면이 따라 바뀔 수밖에 없다.**
