## 단계 2 — 합성 프레임으로 서버를 관통시킨다 (2026-09-30)

기준 문서 단계 2: *"엣지가 오기 전에 서버 쪽 결함을 먼저 턴다. 이대규 컴퓨터를 임시 송신기로 쓴다."*
**영상 평면만 본다** — `/state`(업무 평면)는 단계 4-b 몫이라 이번에 켜지 않았다.

| 무엇 | 값 |
|---|---|
| 송신 | 이대규 PC → `ws://<서버 tailnet 주소>:8766/ingest` · `tests/media_publisher.py` · H.264 · 30fps · `--loop --count 600`(합성 파일 5바퀴) |

### 1 문서와 다르게 한 것

**① `source_id` 를 `stage2-chk` 로 했다**

- 기준 문서 단계 2 는 이름을 정하지 않았다(CLAUDE.md 의 명령 예시는 `go1-001_front`).
- HW 가 09-29 에 팀 tailnet 에 들어와 **같은 이름으로 서버 8766 에 붙을 수 있게 됐다.** 같은 이름의 송신 연결이 둘이면
  나중에 붙은 쪽이 `4409` 로 끊겨 판정이 흐려진다. 서버 로그에서 이번 것만 골라 보기도 쉽다.

### 2 발견한 것

**① 이대규 PC 시계가 서버보다 적어도 0.535초 앞선다**

- **실측 원문:** 뷰어가 받은 마지막 장의 `capture_timestamp` = `2026-09-30T17:16:29.625+09:00`(= 08:16:29.625 UTC,
  **PC 시계**로 보내기 직전에 찍은 시각) · 서버 로그 `08:16:29,090 … /ingest 종료 … 수신 600장`(**서버 시계**, 다 받은 뒤).
- **판정:** 시계가 맞으면 앞(찍은 시각)이 뒤(서버가 종료를 적은 시각)보다 빨라야 한다. **반대로 0.535초 늦다** →
  PC 시계가 서버보다 **적어도 0.535초 앞선다**(네트워크 지연만큼 더).
- **영향:** **단계 2 판정에는 없다** — 송신기와 확인용 뷰어가 같은 PC 라 같은 시계를 쓴다.
  🔴 **서버 쪽 시각과 섞어 지연을 재면 그만큼 틀린다**(기준 문서 §7 「종단 지연」). 지연을 잴 때는 그 기기 시계부터 본다 —
  엣지(HW PC)가 붙을 때도 같다.

**② 보내기 전 지표가 0 이었다 — 「값 0」인지 「시계열 없음」인지 이 출력으로는 못 가린다 (내 조회 함수 결함)**

- **실측:** `BEFORE ingress=0 sent=0 rejected=0`. 조회 함수가 빈 결과를 `0` 으로 찍는다
  (`print(r[0]["value"][1] if r else 0)`).
- **원인:** 안 봤다. 재기동(기준 문서 단계 1 ⚠ *"지표는 … 재기동마다 0"*)이거나, 한동안 안 쓰인 시계열이 내려간 것
  (Phase 4 작업로그 단계 7 발견 (d))일 수 있다.
- **영향:** **판정은 흔들리지 않는다** — 지표 차분(0 → 600)과 서버 로그 `수신 600장` 이 **서로 독립인 두 갈래**로 같은 값을 냈다.
- **남길 것:** 다음부터 조회 함수는 빈 결과를 `없음` 으로 찍는다 — 「0」과 「없음」을 섞지 않는다.

### 4 이 단계가 서버·장비에 남긴 것

- **서버 변경 없음** — 설정·방화벽·서비스 그대로. 지표와 로그에 `stage2-chk` 흔적만 남았다.
- **PC 변경 없음** — PowerShell 창의 환경변수 둘(`MK2_MEDIA_INGEST_URL`·`MK2_EDGE_TOKEN`)은 창을 닫으면 사라진다.
- **되돌릴 것 없음.**

### 5 검증하지 못한 것

- **서버 쪽 뷰어 회계 줄**(`/media 종료 source_id=stage2-chk sent=… dropped=… gop_cut=…`) — 확인용 뷰어를 끊지 않아
  아직 안 찍혔다. 뷰어 쪽 `gaps=0`·`drop_intervals=[]` 와 지표 `sent` **600** 으로 대신했다.

## 덧붙임 — 서버 쪽 뷰어 회계 (2026-09-30)

> 위 「5 검증하지 못한 것」의 한 줄을 닫는다. 확인용 뷰어를 끊은 뒤 찍혔다.

```
08:28:41,622 INFO mk2.gateway /media 종료 source_id=stage2-chk sent=600 dropped=0 gop_cut=0 max_buffered=10538 t_drop_at_max=35991 t_hard_at_max=143963 max_frame=10538 gop_seen=True
```

| 항목 | 값 | 읽는 법 |
|---|---|---|
| `sent` · `dropped` · `gop_cut` | **600 · 0 · 0** | 서버가 뷰어에게 600장을 다 보냈고 하나도 안 버렸다 — 뷰어 `frames=600`·`drop_intervals=[]` 와 같다 |
| `max_buffered` = `max_frame` | **10,538 B = 10,538 B** | 뷰어별 대기열(`media.py:373-374`)이 가장 많이 찼을 때가 **가장 큰 한 장뿐**이었다. 그때의 버리기 문턱 `t_drop_at_max` **35,991 B** 에 한 번도 닿지 않았다 |
| `gop_seen` | **True** | 키프레임이 아닌 장(P)이 섞인 흐름으로 알아봤다(`media.py:280` `has_gop()` — 전부 키프레임인 JPEG 면 False). 버릴 일이 생기면 GOP 단위로 버리는 쪽이다 |

→ **서버 쪽 뷰어 회계도 600 = 600.** 단계 2 에서 못 본 것이 남지 않았다.
