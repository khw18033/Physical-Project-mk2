# 2026-08-20 19:00 — 가시화 데이터 레이어와 목 게이트웨이 구현

**직전 보고서**: `2026-08-20_1730_scale-headroom-placeholders.md`
**커밋**: 이 보고서와 함께 커밋 (푸시 없음)

## 요청

가시화 파트의 **데이터 레이어와 목 퍼블리셔**를 만든다. 다른 파트의 계약이 확정되기 전에도
화면이 실제로 움직이게 하는 것이 목적이다. 세 덩어리 — 목 게이트웨이 서버, 데이터 레이어,
최소 화면 하나(`VZ-U-01` 구역 장치 현황판). 스택은 React + TypeScript + Vite.

주기 사양은 **김현우 시트 32행의 "제안 주기"·"주기 선정 이유" 열**을 그대로 따른다.

## 판단

### 목을 브라우저 밖에 둔 이유가 이번 설계의 전부다

목 데이터를 브라우저 안에 두면 옮길 때 전부 버려진다. 더 나쁜 것은 그 사이에 화면 코드가
**"값은 항상 즉시 있다"** 는 가정에 물든다는 점이다. 재연결도, 구독 복원도, 스냅샷 공백도
겪어보지 않은 코드가 된다. 그래서 별도 프로세스의 WS 서버로 만들고, 프런트는 처음부터
끊기고 붙는 것을 전제로 짰다. 전환 비용은 `.env.local` 두 줄이다.

### `stale` 판정 위치가 코드 구조를 결정했다

`REQ-205`의 "stale 판정은 백엔드가 서버 시각과 `last_seen`으로 수행한다"를 지키려니
화면의 **"최근 수신 0.05초 전"** 도 문제가 됐다. 클라이언트가 `Date.now() - last_seen`을
하면 결국 사용자 PC 시계에 의존하게 된다. 해결은 `envelope.ts - last_seen` —
**둘 다 서버 시각**이라 클라이언트 시계가 개입하지 않는다.

이 선택이 서버 쪽 주기를 하나 만들어 냈다. 경과 시간은 봉투가 도착해야 갱신되므로
`state` 채널을 5초마다 재발행해야 한다. 그런데 **5초는 이미 정해져 있던 숫자다** —
엣지노드의 구역 단위 상태 요약(HW-C-04)과 센서노드 하트비트(HW-S-05)가 5초이고,
`VZ-U-01`의 "구역별 현황판 갱신 5초"가 그 근거였다. 서로 다른 이유가 같은 숫자로 맞았다.

### 상태 4종 파생 — 판정 순서에 의미가 있다

목업 매핑표 5행을 코드로 옮기면서 순서가 필요했다. `ok + stale`이 판단 불가인 이유는
**stale을 `device_status`보다 먼저 보기 때문**이다. 마지막으로 들은 "나 괜찮아"가 몇 분 전
것이라면 그건 현재값이 아니다. 같은 논리로 `offline`도 `device_status`보다 앞이다.
이 순서를 `deriveDisplayStatus()` 한 곳에만 두고, 화면의 매핑표도 같은 순서로 행을 고르게
했다 — 표와 판정이 따로 놀면 표가 검증 수단이 되지 못한다.

### 자리만 연 세 필드는 "실어 나르는 것"만으로는 부족했다

`scope`·`aggregation`·권한 `scope` 셋 다 왕복시켰지만, `aggregation`은 거기서 멈추면
직전 보고서 미결 18번이 그대로 남는다. 그래서 **검사까지** 넣었다 —
집약 연산(`guardedMean`/`guardedSum`)을 거치지 않고는 평균을 낼 수 없게 만들고,
집약값이 들어오면 개발 모드에서 경고하고 **계산 자체를 막는다**. 경고만 띄우고 계산은
해 주면 아무도 안 고친다.

### 화면 병합은 명시적 모듈로 뺐다

`store` 안에 숨기면 "왜 화면이 100ms 늦나"를 나중에 아무도 못 찾는다.
`mergeScheduler.ts` 하나로 분리하고, 오프라인·판단불가 **전이**만 창을 건너뛰는
`flushNow()` 경로를 따로 뒀다 — `VZ-U-01`의 "오프라인 감지는 즉시"가 이것이다.

`AVAILABILITY_SWEEP_MS`(1초)는 시트에 없는 신설 상수다. 발행이 끊긴 대상은 아무도
메시지를 보내지 않으므로 서버가 스스로 훑지 않으면 stale 전이를 감지할 방법이 없다.
값은 "오프라인 감지는 즉시"를 만족하는 선에서 가장 성긴 값으로 잡았다.

### 봉투

```
{ zone, node, entity, channel, ts, seq, payload, quality, aggregation, scope }
```

`quality`는 계약에 정의가 없어 잠정 정의했다(미결 사항 참조) —
`good`(현재값 신뢰) / `degraded`(원천이 이상 자기보고) / `unknown`(현재값임을 확인 불가).

### 등록 대상 9개

목업의 6개에 `actuator-01`과 `edge-node-a`(관측 지표용)를 더했고, `sensor-04`는
매핑표 3행(`— · offline · deployed → 장애`)을 화면에서 확인할 대상이 달리 없어 포함했다.
`robot-03`은 어떤 채널로도 발행하지 않는다.

### 구독 축

`{entity, node, channel}` + 와일드카드. **node 축은 Zone 식별자도 받는다** —
레지스트리로 해석해 그 Zone의 모든 Node에 매칭하므로 `{node: "zone-503", channel: "state"}`가
성립한다. 정식 계약이 zone 축을 따로 둘지 계층 매칭으로 둘지는 미결이다.

붙여 렌더한 마크업으로 확인했다. 요청받은 8개 항목 기준:

### 구현하다 잡은 버그 3건

계약을 코드로 옮기면서 **문서만 봐서는 안 보이던 것**들이 나왔다. 기록해 둔다.

1. **첫 주기를 기다리면 스냅샷이 빈다.** 평시 1분 센서는 서버 기동 후 1분 동안 캐시가
   비어 있어 그 사이 구독한 화면이 `VZ-I-02`의 즉시 스냅샷을 못 받았다. 장치는 부팅하면
   곧바로 자기 상태를 보고하므로 기동 즉시 1회 발행하도록 고쳤다.
   → **계약 함의**: 백엔드 캐시가 "장치가 처음 보낸 뒤부터" 채워지면 같은 구멍이 생긴다.

2. **주기가 바뀌어도 이미 무장된 타이머는 안 바뀐다.** 센서가 이벤트 모드로 전환돼도
   다음 발행은 여전히 60초 뒤였다. 주기 상향(HW-S-03)이 이름만 남는 상태였다.

3. **정기 발행이 전이를 가로챘다.** 5초 정기 상태 발행이 전이 기록을 먼저 갱신해 버려
   1초 재판정 루프가 그 전이를 놓쳤다. 결과로 사유 문구가 비었고, 더 중요하게는
   **오프라인 감지가 최대 5초 늦어질 수 있었다.** 전이 소유권을 재판정 루프 하나로 모으고,
   사유 문구는 전이 순간에 쓰는 대신 현재 상태에서 파생시키도록 고쳤다.

## 미결 사항

### 이월

1~19. 직전 보고서 이월 유지. **18번은 이번 구현으로 해소** — 자리만 연 세 필드를
목 게이트웨이가 실제로 실어 나르고, `aggregation`은 데이터 레이어에서 검사까지 한다.
17번(규모 가정)은 `SCALE_ASSUMPTIONS` 상수로 코드에 박아 두었으나 **숫자 자체는 여전히 대기**.

### 신규 — 구현하며 드러난 계약의 빈칸

20. **`quality` 필드의 enum이 계약에 없다.** 봉투에 자리는 있는데 값 목록이 없어
    `good`/`degraded`/`unknown`으로 잠정 정의했다. `availability`(대상의 상태)와
    `quality`(봉투 한 건의 신뢰도)가 층이 다르다는 점도 문서에 없다.

21. **`aggregation`의 인코딩이 정해지지 않았다.** `"raw"` 축약 문자열이냐, 집약 계층까지
    담는 객체냐. 봉투 필드 구성이 10개로 고정이라 `aggregation_layer`를 형제 필드로 둘 수
    없어서, **둘 다 받아 정규화**하는 방식으로 갔다. 확정되면 `normalizeAggregation()`
    하나만 좁히면 된다.

22. **구독 축에 zone이 없다.** 계약 축은 `{entity, node, channel}`인데 "구역 단위 구독"이
    자연스러운 요구다. 이번에는 node 축이 Zone 식별자도 받는 계층 매칭으로 풀었다.
    정식 계약이 **zone 축을 추가할지, 계층 매칭을 규약으로 못 박을지** 결정이 필요하다.

23. **마지막 값만 보관하는 방식은 이산 이벤트를 잃는다.** 상태는 마지막 값이면 충분하지만
    **명령 결과는 4단계가 각각 의미를 갖는다**(`VZ-O-02`). 실제로 ACK와 '수행 중'을 같은
    순간에 발행했더니 100ms 병합 창 안에서 ACK가 사라졌다. 목에서는 두 단계를 시간상
    분리해 우회했지만, 계약이 **명령 결과에 이력 보관을 요구하는지** 정해야 한다.

24. **`actuator-01` 동작 중 주기가 100ms인지 200ms인지 엇갈린다.** 이번 지시는 100ms인데
    `VZ-O-02`의 "진행 상태 200ms 주기 수신"(HW-A-04)과 다르다. 지시대로 100ms로 구현하고
    `config.ts`에 주석으로 남겨 뒀다 — 확정되면 상수 하나만 고치면 된다.

25. **레지스트리가 `deployment` 초기값을 주는지 불명.** `REQ-201`상 `deployment`는
    오케스트레이터에서 상태 채널로 온다. 그렇다면 미배포 대상도 **상태 봉투는 하나 받아야**
    하는데(값은 없고 `deployment: not_deployed`만), 이게 백엔드 계약에 명시돼 있지 않다.
    이번 구현은 "레지스트리가 카드의 존재를, 상태 채널이 미배포 판정을" 주는 방식으로 갔다.

26. **`stale` 임계 60초는 목 기본값일 뿐이다.** `REQ-205` 근거 단락이 "임계값은 Tier 2"라고
    적고 있다. 대상 종류별로 달라야 할 가능성이 높다 — 15fps 카메라와 1분 주기 센서에
    같은 60초를 쓰면 카메라는 900프레임을 놓친 뒤에야 판단 불가가 된다.

27. **재연결 백오프 상한이 계약에 없다.** 0.5초→15초 지수 백오프로 잡았으나 근거는 없다.
    게이트웨이 재기동 시간과 관제 허용 공백을 기준으로 정해야 한다.
