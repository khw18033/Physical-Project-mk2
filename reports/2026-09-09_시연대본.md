## 1. 저장소가 0절 표와 다른 자리

### `node_kind` 는 대본에서 `nodeKind` 다

이름이 두 벌이다. **계약은 스네이크, 대본 JSON 은 카멜**이고 값은 같다.

| 자리 | 표기 | 값 |
|---|---|---|
| `contracts/task.schema.json` | `node_kind` (선택 필드) | `sense` `decide` `act` `verify` `report` |
| `scenarios/*.json` · `src/model/types.ts` | `nodeKind` | 같음 |

새 대본은 저장소를 따라 `nodeKind` 로 적었다. **3절이 제안한 라벨은 전부 실재한다** — 바꾼 것이 없고, 없는 라벨을 만들지도 않았다. `T-C1`(임무 종료 확인)만 3절 표에 없어서 `report` 를 골랐다. 다섯 중 「기록을 남기고 끝낸다」에 가장 가깝다.

### 같은 이름의 다른 타입이 넷 있다

지시서가 `node_kind` 라고만 적어서 어느 것인지 확인이 필요했다. 이번에 쓴 것은 첫 줄 하나뿐이다.

| 정의 자리 | 값 | 이번 작업과 |
|---|---|---|
| `src/model/types.ts:17` | sense decide act verify report | **이것을 썼다** |
| `src/scenarios/types.ts:63` | 같은 다섯을 그대로 다시 선언 | 중복이지만 손대지 않았다 |
| `src/scenarios/axes.ts:91` | device-risk control metrics video | 뷰 노드 종류 — 다른 축이다 |
| `src/shared/pipeline-contract.ts:24` | source transform sink | 파이프라인 — 다른 축이다 |

화면 표기는 `TaskGraph.tsx:52` 에서 관측·판정·구동·검증·보고로 번역된다.

### `layout.ts` 는 깊이 기반이 맞다 — 특례가 필요했다

3절 표에 있다. 자세한 것은 아래 3절.

### `shared/registry.ts` 는 장비 등록처가 아니다

0절 표가 「이번 대본의 장비를 여기 등록해야 하는가」를 물었는데, 이 파일은 **탭 경계**이지 장비 목록이 아니다. 장비의 원천은 `web-dashboard/mock-gateway/registry.json` 이고 `verify:script-library` 가 대본의 `cast` 를 그 파일과 대조한다. `robot-01` 은 이미 있어서 **등록할 것이 없었다.**

### 로봇에는 낼 명령이 없다

`gateway/commands.ts` 의 `ACTION_CATALOG` 에는 수문 둘(`actuator-01`·`actuator-02`)만 있다. 로봇 명령이 없으므로 새 대본의 `commands` 는 비어 있다. 1편도 같다. 3절의 「전진과 정지 명령」은 그래서 `params` 의 상수로만 남는다 — 지시서가 지시한 그대로다.

### `verify` 는 28종이었고 30종이 됐다

통합 스크립트가 없어 개별로 전부 돌렸다. 신설 둘은 `verify:script-door` 와 `verify:viewpoint-fill` 이다.

### 편수로 걸려 있던 검사가 사라질 뻔했다 — 고쳤다

`verify:script-library` 가 이렇게 돼 있었다.

```js
if (Object.keys(byId).length === 3) failures.push(...checkSpecifics(byId));
```

**대본을 더하는 순간 넷이 되어 1·2·3편의 시간값 검사가 통째로 안 돈다.** 상승 30초·유지 10초·하락 3분·재탐색 10분이 전부 여기 있다. 편수 조건을 「그 세 편이 목록에 있는가」로 바꾸고, 없으면 실패하게 했다. 사라지는 검사가 가장 나쁘다.

### 「수문」과 「문」이 겹친다

3편의 `must` 가 `["월류방어벽","방어벽","수문"]` 이다. 새 대본을 `문` 하나로 잡으면 「수문을 가동해」가 두 편에 함께 맞고, 매처는 **모호하면 고르지 않으므로** 3편이 거부된다.

어미까지 넣어 `문쪽`·`문으로`·`문앞` 으로 좁혔다. `verify:script-door` 가 「수문을 가동해」·「수문 개폐해줘」가 여전히 3편에 가는지 본다. 대조군으로 `must` 를 `문` 하나로 넓힌 사본이 모호 거부되는 것까지 확인한다.

### 띄어쓰기 두 형태는 이미 같은 값이다

1절이 `문쪽`·`문 쪽` 을 둘 다 넣으라고 했는데, `matcher.ts` 의 `normalize()` 가 공백을 지우므로 두 형태는 **정규화 뒤 같은 문자열**이다. 대본 `match` 에 중복으로 적지 않았다. 대신 `verify:script-door` 가 발화 변형을 **여섯 개**(띄어쓰기 양쪽 포함) 넣어 전부 이 편에 오는지 확인한다 — 발표장에서 실제로 나올 문장은 둘 다이기 때문이다.

### `stt/vocab.py` 는 저장소에 없다

1절의 「가능하면 hotword 에 문을 올린다」는 **하지 못했다.** `gateway/hub.ts` 주석이 그 파일을 가리키지만 저장소에 실물이 없고, hotword 는 `registry.json` 의 장비 이름에서 파생된다. 「문」은 등록된 장비가 아니라 올리려면 `registry.json`(web-dashboard) 이나 `stt-lab` 을 건드려야 하는데 **둘 다 이번 범위 밖**이다. 남겨 둔다.

### 태스크 수가 지시서 안에서 어긋난다

8절은 「태스크 열넷」이라 적었지만 3절 표를 그대로 세면 열여섯이고, `MS-C` 종료 태스크를 더해 **열일곱**이다. 상세한 3절을 따랐다. `verify:script-door` 는 열일곱을 못박지 않고 **구조**를 본다 — 마일스톤 셋, `T-A4-0~7` 여덟이 `T-A3` 하나에, `T-A5` 는 90도 하나에만.

### `MS-C` 에 태스크를 뒀다

순서도상 `MS-C` 는 태스크가 없는 종료 마일스톤이지만, `verify:script-library` 가 빈 마일스톤을 막는다(「이 마일스톤을 접을 태스크가 없다」). 접어도 영원히 pending 이기 때문이다. 2절이 미리 지시한 대비책대로 **「임무 종료 확인」 하나**를 뒀다.

## 3. 8분할 원형 배치에 준 특례의 범위

### 왜 필요했나

`dagLayout` 은 깊이로 열을 만든다. 여덟이 전부 `T-A3` 에 매달리므로 **깊이가 같고**, 한 열에 세로로 쌓여 `ROW`(150) × 8 = 1,200px 기둥이 된다. 순서도의 부채꼴이 아니고 첫 화면에도 안 들어온다.

### 어디까지가 특례이고 어디부터가 기존 코드인가

| | |
|---|---|
| **특례** | `src/graph/fanLayout.ts` 파일 하나와, `TaskGraph` 가 그것을 한 번 부르는 줄 하나 |
| **기존 코드** | `dagLayout` 이 낸 좌표 전부. 배치 엔진은 **한 줄도 고치지 않았다** |

`applyFanLayout(base, group)` 은 `dagLayout` 의 결과를 받아 **선언된 여덟 개의 키만** 덮고 나머지는 입력에서 그대로 옮긴다.

### 특례가 선언으로만 걸린다

태스크 id 를 배치 코드에 적지 않았다. 대본이 `viewpoints` 를 선언하고 배치는 그것만 본다.

```json
"viewpoints": { "parentTaskId": "T-A3", "taskIds": ["T-A4-0", "…", "T-A4-7"],
                "startAngleDeg": 0, "stepDeg": 45 }
```

선언이 없는 편은 덮을 것이 없어 좌표가 그대로 나간다. `verify:layout` 이 **네 편 각각에 대해 배치 무변경을 다시 잰다** — 특례가 새면 거기서 걸린다.

덮지 않는 경우가 둘 더 있다. 부모가 화면에 없을 때(「이 마일스톤」으로 `MS-B` 를 볼 때)와 여덟 중 하나라도 범위 밖일 때다. 원의 중심을 지어내지 않는다.

### 검사가 반지름을 고쳤다

처음 `CENTER_DROP` 을 `NODE_HEIGHT + RADIUS + 40` 으로 잡았더니 0도 노드가 부모와 **95px 로 겹쳤다.** 0도는 중심 바로 위라 부모와 가로가 같아 세로로만 벌어져야 하는데 그 여유가 모자랐다. `verify:layout` 이 폭 네 종에서 전부 잡았고 `RADIUS + NODE_HEIGHT × 1.5 + 40` 으로 고쳤다. 손으로 맞춘 값을 믿지 않는 것이 그 검사의 쓸모다.

### 무엇을 검사하나

폭 네 종(1120·1280·1440·1920)에서 여덟이 서로·이웃과 겹치지 않는가, 묶음 밖 노드가 안 움직였는가, 0도가 위·90도가 오른쪽(시계 방향)인가, 각도를 5도로 좁힌 대조군이 겹침으로 잡히는가.

## 4. 대본 사건과 라이브 채널을 가른 자리

**`src/viewpoint/source.ts` 한 곳이다.**

```
대본 재생 ─▶ scriptFrames() ─┐
                             ├─▶ ViewpointFrame ─▶ store.ts ─▶ fill.ts ─▶ 화면
실제 로봇·탐지 ─▶ liveFrame() ─┘        (열 하나)      (인덱스로 채운다)
```

이 파일 **위로는** 대본을 안다. **아래로는** 모른다 — `fill.ts` 가 받는 것은 프레임뿐이고 출처를 묻지 않으며, 물을 방법도 없다. `verify:viewpoint-fill` 이 `fill.ts` 소스에 `ScriptScenario`·`viewpointTimeline`·`atSec` 같은 낱말이 없는지 **파일 수준에서** 확인한다.

### 두 형식은 6절 표 그대로다

| 채널 | 값 |
|---|---|
| `robot_state` | `rotation_index` `yaw` `state` `last_cmd` `result` |
| `detection` | `index` `angle_deg` `door` `bbox` `confidence` `reason` |

게이트웨이가 이 두 채널을 **실제로 낸다**(`hub.publish`). 채널 이름과 값이 실제 장치가 낼 것과 같아서, 붙는 날 **발행하는 쪽만** 장치로 바뀌고 받는 쪽은 그대로다. 브리지(`missionBridge.ts`)는 봉투가 목 게이트웨이에서 왔는지 로봇에서 왔는지 묻지 않는다.

두 채널 모두 **캐시하지 않는다**(`CACHE_POLICY`). 한 건만 재생되면 여덟 중 한 칸만 켜진 화면이 현재처럼 보이고, 사용자는 나머지 일곱이 미도착인지 문 없음인지 구분할 수 없다. `trace_event` 와 같은 이유다.

### `rotation_index` 가 유일한 열쇠다

`yaw` 로 고르지 않는다 — 실제 로봇은 90도를 명령해도 88.4도가 오고 각도로 맞추면 칸이 어긋난다. 도착 순서로도 고르지 않는다 — 탐지가 268ms 걸려 순서가 뒤집힌다. 그래서 상태는 배열이 아니라 **인덱스로 찾는 표**다.

`verify:viewpoint-fill` 이 프레임을 **50번 뒤섞어** 결과가 같은지 보고, 탐지가 회전보다 먼저 온 최소 반례도 따로 본다. 대조군으로 「도착 순서로 채우는 구현」이 뒤섞기에서 달라지는 것을 확인한다.

## 5. 지시서와 다르게 한 곳

### 회전 구간을 0초가 아니라 6초에 놓았다

4절 표는 `atSec 0` 에 승인과 `T-A3` 시작을 함께 적었지만, 3절 `deps` 는 `T-A1 → T-A2 → T-A3` 이다. 0초에 회전을 시작하면 앞 둘이 아직 안 끝났는데 뒤가 도는 셈이 되어 DAG 와 화면이 어긋난다.

`T-A1`(0~3초)·`T-A2`(3~6초) 뒤로 회전 구간을 밀었다. **구간 안의 박자는 지시서 그대로다** — 인덱스 i 회전이 `6+2i`, 탐지가 `7+2i`, 여덟이 16초. `params.spin_seconds` 가 16이고 `verify:script-door` 가 그 16초와 1초 간격을 잰다. 대본에는 실시간 초를 적었고 압축은 기존 배속(`VIZ_SCENARIO_SPEED`)이 한다.

### 발화 변형을 넷이 아니라 여섯으로 검사한다

정규화가 공백을 지워 띄어쓰기 두 형태가 같은 값이 되므로, 대본 `match` 에는 중복을 적지 않고 **검사에서** 여섯 문장을 넣는다. 위 1절에 적었다.

### 화면 상태를 실행 상태와 다른 축으로 그렸다

4절의 상태 셋(대기·탐색 중·판정 완료)을 **테두리로만** 말한다. 노드 배경은 기존 8상태(pending·running·done…)가 이미 쓰고 있어서, 같은 자리에서 두 축이 싸우면 「이 노드가 실패인가 문이 없는가」를 못 읽는다. 초록은 테두리와 옅은 그림자로 준다. 점멸은 `prefers-reduced-motion` 에서 꺼진다.

### 화면이 대본이 아니라 열을 접게 되돌렸다

처음에 뷰포인트 상태를 `view.viewpointTimeline` 에서 곧바로 접게 만들었다. **`src/data/trace.ts` 머리말이 260904 에 고쳐 둔 실패가 정확히 그것이라** 되돌렸다 — 「받은 기록이 아니라 대본을 접는 것」. 목 데이터에서는 대본이 곧 정답이라 티가 안 나지만, 로봇이 붙으면 화면은 여전히 대본을 접는다. 그러면 6절의 「갈아끼우면 끝」이 거짓이 된다.

`src/viewpoint/store.ts` 에 열 하나와 입구 하나를 뒀다. 기록 열과 같은 구조다. 되감기는 「머리까지를 처음부터 다시 접는다」로 성립한다.

## 6. 범위 밖으로 두었다고 적을 것

- **2D 맵 뷰** — 만들지 않았다. `T-A1`·`T-A2`·`T-B1` 은 **노드로만 선다.** 경로 산출 결과는 `params.forward_distance_m: 4.2` 상수다. 맵 화면이 붙는 날 이 상수가 그 값을 받는다.
- **근거 이미지** — 없다. `image_ref: null` 이고 화면은 「미도착」이라고 적은 빈 액자를 그린다. **더미를 그려 넣지 않았다** — 발표에서 「이건 가짜입니다」를 말하게 되는 자리다.
- **`VZ-G-01` 생성 경로** — 미착수 그대로다. `viewFromGenerated` 에 `viewpoints: null`·`viewpointTimeline: []` 두 줄만 더했다. 타입이 요구해서이고 생성 동작은 안 바꿨다.
- **`MSN-260826-01`** — 한 글자도 안 고쳤다(`verify:scenario` 통과).
- **`web-dashboard`·`stt-lab`·레이아웃 엔진·되감기** — 손대지 않았다.
- **`liveFrame()` 을 부르는 장치** — 없다. 형식 합의가 끝나면 발행하는 쪽만 생긴다. 없는 소켓을 지어 붙이지 않았다.

## 7. 발표 전에 사람이 확인할 것

검사로 못 잡는 것들이다.

1. **실제 브라우저에서 여덟이 원으로 서는지.** 겹침은 폭 네 종에서 쟀지만 실제 창에서 눈으로 본 것은 아니다.
2. **텍스트 입력창이 첫 화면에 보이는지.** 매칭 경로가 음성과 같다는 것은 검사가 확인했지만(같은 `normalize`), 발표장에서 손이 갈 자리인지는 화면을 봐야 안다.
3. **배속에서 16초 구간이 눈으로 따라가지는지.** 기본 20배속이면 0.8초에 여덟이 지나간다. 시연에서 `VIZ_SCENARIO_SPEED` 를 낮춰야 할 수 있다.
4. **`MS-C` 의 「임무 종료 확인」이 순서도 설명과 안 어긋나는지.** 순서도에는 없는 태스크다.
