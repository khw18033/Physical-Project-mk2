## 1. 0절 확인 결과

### `.proto` 를 가져온 방법

원본은 `HW` 브랜치의 `schema/physical_command.proto` 하나다. 커밋 `7abf470` 에서 가져와
`viz-debugger/schema/` 에 두었고, **머리말에 출처·날짜·원본 커밋을 적었다.**

```
npm run schema:pull   # origin/HW 를 다시 받아 .proto → pbjs → pbts 까지 한 번에
```

`scripts/pull-schema.mjs` 가 그 일을 하고, 본문이 바뀌면 「`verify:command-encode` 를 다시
돌려라」를 출력한다. 스키마가 바뀌면 79·31 바이트가 달라질 수 있고 그때는 하드웨어와 다시
맞춰야 한다. **우리가 스키마를 고치지 않는다** — 고칠 일이 생기면 `HW` 브랜치에 요청한다.

### 봉투 이름이 지시서와 다르다

지시서 1절의 예시는 `Envelope` 인데 스키마의 실제 이름은 **`PhysicalCommandEnvelope`** 다.
저장소를 따랐다.

### `robot-01` 대 `go1-001` — registry 를 고치지 않았다

`task.target` 이 노드 카드에 그대로 찍힌다(`TaskGraph.tsx:437`). registry·대본 네 편의
`cast`·화면이 전부 `robot-01` 이고, 하드웨어는 `go1-001` 을 쓴다.

**바깥 세상의 이름을 경계 안에 두고 표 한 줄로 갈아 끼웠다.**

```ts
// src/physical/encode.ts
const TARGET_OF: Record<string, string> = { 'robot-01': HARDWARE_TARGET };
```

registry id 를 바꾸면 대본 네 편의 `cast` 와 `verify:script-library` 의 실재 대조가 전부
따라 움직이는데 그것은 이번 범위 밖이고, 화면에 찍히는 이름을 바꿀 이유도 없다.
`SttClient` 가 STT 주소를 혼자 아는 것과 같은 규칙이고, `verify:physical-port` 가
`go1-001` 이 `src/physical/` 밖에 나가는지 본다.

### `verify:standalone` 에는 KB 한도가 없다

**지시서 2절과 어긋나는 자리다.** 지시서는 그 검사가 「단독 빌드 오염을 KB 단위로 감시한다」고
적었지만, 실제로는 import 경계와 의존 그래프만 본다. 숫자 한도가 코드에 없다.

그래서 「한도 대비」라고 적을 기준선이 저장소에 없다. 증가분은 아래에 숫자로 남기되,
한도 판정은 사람이 해야 한다.

## 2. `verify:command-encode` 결과

**같았다.** 하드웨어가 실제로 쏴 보고 잰 두 수치와 우리 인코딩이 정확히 일치한다.

| 명령 | 하드웨어가 잰 값 | 우리 인코딩 |
|---|---|---|
| `ping` | 31 바이트 | **31 바이트** |
| `scan_mission{steps:8, forward_m:1.0}` | 79 바이트 | **79 바이트** |

```
0a4d0a0c636d642d30303030303030311207676f312d3030311a0c7363616e5f6d697373696f6e
22100a05737465707311000000000000204022140a09666f72776172645f6d11000000000000f03f
```

### 지시서에 hex 원문이 없다

§7 은 「자료의 79바이트 hex 와 같은가」라고 적었지만 **지시서 본문에는 길이만 있고 hex
문자열이 없다.** 그래서 길이로 대조하고, 그 길이가 우연이 아님을 따로 증명했다.

`command_id` 길이를 1자부터 40자까지 바꿔 가며 두 명령을 재면, **31 과 79 가 동시에
떨어지는 지점이 12자 하나뿐**이다. 두 수치가 한 점에서 만나는 것은 필드 번호·와이어 타입·
맵 인코딩이 전부 같을 때만 일어난다. 하나라도 어긋나면 두 길이가 같은 지점에서 만나지 않는다.

hex 원문을 받으면 `verify-command-encode.mjs` 의 `REFERENCE_HEX` 에 채우기만 하면 즉시
대조한다. 자리를 비워 두었다.

**참고**: 지시서 1절 예시의 `'cmd-' + Date.now()` 는 17자라 36·84 바이트가 나온다.
기준 수치를 잰 쪽은 12자 id 를 썼다. `nextCommandId()` 를 12자(`cmd-00000001`)로 맞췄다.

### 대조군 셋

`forward_m` 을 빼면 길이가 달라지고, `forward_m=0` 이어도 길이가 같으며(맵의 double 은
값이 0 이어도 8바이트 고정폭), `target` 을 `robot-01` 로 쓰면 길이가 달라진다.

## 3. 번들 증가분

| | 착수 전 | 착수 후 | 차이 |
|---|---|---|---|
| 단독 빌드 JS | 399.74 kB | 399.98 kB | **+0.24 kB** |
| 단독 빌드 JS (gzip) | 121.27 kB | 121.32 kB | **+0.05 kB** |
| 단독 빌드 CSS | 38.78 kB | 38.78 kB | 0 |
| 모듈 수 | 106 | 106 | 0 |

**증가가 사실상 0인 이유는 아직 화면이 경계 파일을 부르지 않기 때문이다.**
`src/physical/` 을 import 하는 곳이 그 디렉터리 밖에 한 곳도 없다(확인함). 늘어난 0.24 kB 는
`connections.ts` 에 연결 대상 하나를 더한 몫이다.

**실제 증가는 화면이 붙는 다음 단계에서 난다.** 그때 들어올 것은 `protobufjs/minimal` 과
생성 모듈(165 kB 원본, 트리셰이킹 뒤에는 쓰는 메시지만), 그리고 `mqtt` 다.

통합 빌드는 착수 후 520.21 kB(gzip 158.60) · 143 모듈이다. **착수 전 수치가 없다** —
0절이 요구한 것이 단독 빌드 수치였고 그쪽만 미리 쟀다. 다음 단계에서 이 값을 기준선으로 쓰면 된다.

### 정적 생성을 골랐다

지시서가 제시한 두 갈래 중 **정적 코드 생성**(`pbjs -t static-module`)을 골랐고, 커밋했다.
이유는 지시서가 든 둘 그대로다.

1. 런타임 파싱은 `protobufjs` 전체가 들어가지만 정적 생성은 `protobufjs/minimal` 이면 된다
2. 런타임 파싱은 `.proto` 를 정적 자산으로 서빙해야 하고, `dist/` 를 그대로 뿌리는 배포
   형태와 맞물려 경로 문제가 생긴다

여기에 하나 더 있다. **정적 생성은 타입이 나온다**(`pbts` 로 `protocol.d.ts`). 런타임 파싱은
전부 `any` 라, 필드 이름을 오타 내도 빌드가 통과하고 로봇 앞에서야 안다.

**`mqtt` 는 동적 import 다.** 정적으로 두면 로봇을 안 쓰는 단독 빌드까지 브로커 라이브러리를
지고 간다. `verify:no-physical` 이 정적 import 가 생기면 잡는다.

## 4. `step → index` 변환을 어디서 하는가

**`src/physical/uplink.ts` 의 `viewpointIndexOf()` 하나다.**

```ts
export function viewpointIndexOf(detail: StatusDetail | null, count = 8): number | null {
  if (detail === null) return null;
  if (detail.event !== 'scan_turn') return null;   // scan_turn 만 뷰포인트를 건드린다
  const index = detail.step - 1;                   // ← 여기 한 줄
  if (!Number.isInteger(index) || index < 0 || index >= count) return null;
  return index;
}
```

`verify:status-index` 가 이것부터 본다. 대조군 둘을 넣었다.

- **`index = step` 사본** — 한 칸 밀린 구현. 여덟 칸이 차례로 켜지고 초록도 하나 떠서
  눈으로는 못 잡는다. 좌표로만 잡힌다.
- **`yaw` 로 고른 사본** — 출발 방위가 350도면 0번 칸 대신 있지도 않은 8번을 노린다.
  드리프트가 왜 위험한지 그대로 나온다.

노드를 채우는 코드(`src/viewpoint/fill.ts`)는 그 인덱스가 로봇에서 왔는지 대본에서 왔는지
모른다. 260909 §6 에서 세운 규칙 그대로다.

## 5. 방향·거리를 정하는 함수

**`src/physical/presets.ts` 의 `missionGeometry()` 하나다.**

```ts
export function missionGeometry(params): MissionGeometry {
  return { steps, forwardDistanceM: forward, source: 'script' };
}
```

지금은 대본 `params` 의 상수를 내놓는다. 하드웨어 쪽이 `door_turn` 과 `move_forward` 를
우리가 산출한 경로대로 움직이게 바꿀 수 있다고 했고, 그때 **이 함수의 속만 바뀐다.**
`source` 필드를 둔 이유가 그것이다 — 값이 대본에서 왔는지 경로 산출에서 왔는지 화면과
보고서가 적을 수 있어야 한다.

명령을 쏘는 쪽(`missionLink.ts` 의 `commandForTask()`)은 이 함수가 준 값을 그대로 실을 뿐
출처를 묻지 않는다. 거리를 대본이 안 주면 **0 이다** — 지어내지 않는다.

### `scan_mission` 에 전진을 태우지 않았다

순서도가 스캔과 접근을 다른 마일스톤으로 갈라 놓았다. 명령 하나가 두 마일스톤에 걸치면
어느 노드를 언제 완료로 바꿀지 애매해진다. `forward_m=0` 으로 스캔만 시키고 접근은
`move_forward` 로 따로 쏜다 — **태스크 경계와 명령 경계를 맞추는 것**이 이 결정의 이유다.

## 6. 목 uplink 의 동작 범위

**진짜와 같은 바이트를 만든다.** `PhysicalCommandEnvelope` 로 인코딩해 내보내고 받는 쪽은
`decodeUplink` 를 그대로 지난다 — 목인지 아닌지 모른다. 화면에 가짜 경로를 따로 두면
진짜가 붙는 날 그 경로만 안 고쳐지기 때문이다.

| | |
|---|---|
| 흘리는 것 | `CommandStatus` step 1~8, 마지막에 `door_turn` 하나 — 모두 아홉 건 |
| `of` | **9** (스캔 여덟 + `door_turn` 하나). `forward_m=0` 일 때의 확정값 |
| 박자 | 2초 (1초 회전 + 1초 유지) — 대본 `MSN-260909-01` 과 같은 축 |
| 경고 | step 4 에 `note: turn_timeout` — 경고 표시가 실제로 뜨는지 본다 |
| 모르는 각도 | step 6 의 `yaw_deg: null` — 안 깨지는지 본다 |
| 그 밖 | `mockAcceptance`(거절 `robot_state_dead` 포함) · `mockResult`(SUCCEEDED·ABORTED) |

**문 유무는 목이 만들지 않는다.** 로봇이 안 주는 것을 목이 주면 「각도는 로봇, 문 유무는
대본」의 경계가 흐려진다. `verify:status-index` 가 목 소스에 `door: true` 가 있는지까지 본다.

## 7. 지시서와 다르게 한 곳

### `connections.ts` 에 브로커 주소를 두지 않았다

`stt`·`generate` 는 `connections.ts` 에 대비값을 적어 두는 것이 저장소 관례다. 로봇도 같게
했다가 **`verify:physical-port` 가 곧바로 잡았다** — 그게 바로 「두 곳에 적힌 주소」다.

로봇은 제약이 더 세다(§7 「MQTT 주소·토픽을 아는 면이 `src/physical/` 하나인가」).
브로커를 옮기거나 중앙 서버 경유로 바꿀 때 한쪽만 고쳐지면 화면이 「붙었다」고 말하면서
아무것도 못 받는다. `fallback` 을 비우고 기본값은 `PhysicalClient.ts` 가 심는다.

**부작용**: 「연결 관리」 화면이 `PhysicalClient` 가 로드되기 전에는 빈 주소를 보인다.
붙지 않았다는 사실을 그대로 말하는 것이라 그대로 두었다.

### `verify:status-index` 를 쓰다 내 시험값 둘이 틀렸다

고친 것은 검사이지 코드가 아니다. 기록해 둔다.

- 350도와 10도를 「감기니까 통과」로 적었는데, 실제 차이는 20도라 허용 15도를 넘는 게 맞다.
  355도와 5도(10도 차이)로 바꾸고, 350/10 은 **걸려야 한다**는 검사를 따로 넣었다.
- 드리프트 대조군을 step 3 · yaw 88.4 로 잡았는데 하필 `round(88.4/45) = 2` 로 우리 인덱스와
  같아 대조군이 안 걸렸다. step 1 · yaw 350 으로 바꿨다.

### 지시서에 없던 것 — 목이 소스 검사를 받는다

「문 유무를 목이 만들지 마라」는 §6 의 경계인데, 코드로 강제할 방법이 소스 검사밖에 없었다.
`verify:status-index` 가 `mockUplink.ts` 에 `door: true|false` 가 있는지 본다.

## 9. 다음 단계에서 이어야 할 것

이번 범위가 「하드웨어 채널만」이라 **화면에 붙이지 않았다.** 경계와 매핑과 목까지 서 있고,
화면이 부르기만 하면 되는 상태다. 다음에 붙일 자리 넷.

1. **연결 확인 버튼** (§3) — `ping` 을 쏘고 왕복이 도는지 보는 버튼. 발표 직전에 눌러
   초록을 보고 무대에 오른다. `PhysicalClient.send('ping')` 하나면 된다
2. **`T-A3`·`T-B2` 가 실제로 쏘는 자리** — `commandForTask()` 가 낼 명령을 화면이 발행
3. **`effectsOf()` 결과를 화면 상태로** — 거절 코드·문구 노출, 진행률, `door_turn` 전이
4. **주소 프리셋 넷을 고르는 UI** — `BROKER_PRESETS` 를 그리기만 하면 된다

붙일 때 통합 빌드 KB 를 다시 재야 한다 — 위 3절의 520.21 kB 가 그 기준선이다.

## 10. 발표 전에 사람이 확인할 것

- **핫스팟 정적 IP** — 받는 즉시 `presets.ts` 의 `venue` 한 줄
- **hex 원문** — 받으면 `REFERENCE_HEX` 에 채운다. 지금은 길이로만 대조하고 있다
- **실제 로봇과의 왕복** — 이 작업은 로봇 없이 증명한 것까지다. 브로커에 실제로 붙여
  `ping` 왕복이 도는지는 사람이 한 번 봐야 한다
