## 1. 0절 확인 결과 — 기존 「정지」 버튼이 무엇에 묶여 있었는가

버튼은 **두 곳에 각각** 있었고 같은 셋을 그렸다.

| 자리 | 버튼 | 쏘던 것 | 어디로 |
|---|---|---|---|
| `src/shell/AppShell.tsx:109` (통합 셸 머리줄) | ■ 정지 / ▶ 재시작 / ■ 중단 | `mission_pause` / `mission_resume` / `mission_abort` | 게이트웨이 |
| `src/views/TopBar.tsx:12` (단독 상단 바) | 같음 | 같음 | 게이트웨이 |

**`CommandTracker` 는 이미 지나고 있었다.** 셋 다 `issueCommand()` → `commandTracker.issue()` 로
가므로 4단계 추적과 감사가 이미 붙어 있었다. 없던 것은 셋이다.

- 로봇 MQTT 로는 아무것도 안 갔다 (게이트웨이 전용)
- 화면 잠금이 없었다
- 추적 중단이 없었다

**새로 만들지 않고 「■ 중단」을 살렸다.** 규약의 `abort` 와 뜻이 같고, 머리줄은 어느 화면에
있든 떠 있다(§4 「어느 화면에 있든 보여야 한다」). 두 곳이 각자 그리던 것을 `StopButton`
한 부품으로 모았다 — 두 곳에 같은 동작을 손으로 적으면 언젠가 한쪽만 고쳐진다.

`verify:emergency-stop` 이 두 셸 모두 `<StopButton />` 을 그리는지, 옛 `mission_abort` 가
남아 있지 않은지 본다.

### `CommandTracker` 에 출구가 하나뿐이었다

`issue()` 가 끝에서 늘 `getTransport().publishCommand()` 를 불렀다. 게이트웨이 전용이다.
`IssueOptions` 에 발행 함수를 받는 항목을 하나 더했고, **안 주면 지금까지와 한 줄도 다르지
않다.** 추적기를 우회해 MQTT 로 따로 쏘는 쪽은 택하지 않았다 — 그러면 `VZ-O-02`·`VZ-O-03`
이 로봇 명령만 못 본다.

## 2. 정지가 하는 넷이 각각 어디서 일어나는가

| # | 무엇 | 어디 |
|---|---|---|
| 1 | `abort` 발행 | `robotCommands.ts` 의 `emergencyStop()` — **실패할 수 있다** |
| 2 | 추적 중단 | `robotSession.ts` 의 `lockStopped()` → `applyEffects()` 가 즉시 막힌다 |
| 3 | 타이머·폴링 정지 | `lockStopped()` 의 `stopAllTimers()` |
| 4 | 화면 잠금 | `lockStopped()` 의 `commit({ stopped })` |

### 발행 실패와 화면 잠금은 갈려 있다

**함수를 갈라 둔 것이 그 보장이다.**

```ts
export async function emergencyStop(client) {
  let published = false; let failure = null;
  try { … client.send(STOP_ACTION, { reason: STOP_REASON.human }) … }
  catch (error) { failure = … }        // 던져도 아래로 내려온다
  return lockStopped(published, failure);   // 2·3·4 — 위 결과를 보지 않는다
}
```

`lockStopped()` 는 `published` 를 **기록만** 하고 잠금 여부에 쓰지 않는다. 검사가 셋을 본다.
발행이 실패했을 때, 예외를 던졌을 때, 클라이언트가 아예 `null` 일 때 — 셋 다 잠긴다.

### 연결이 없을 때

버튼을 **비활성화하지 않는다.** 눌리고, 못 보냈으면 크게 빨갛게 말한다.

```
정지 명령을 보내지 못했습니다 — 브로커에 붙어 있지 않습니다 — closed
```

검사가 `StopButton.tsx` 에 `disabled` 와 `confirm(` 이 없는지까지 본다.

### 재개

자동으로 안 돌아간다. 「정지 해제 — 다시 승인해야 합니다」 버튼이 나오는 길이고,
누르면 **승인이 같이 내려간다**(`releaseStopped()`). 사람이 다시 승인해야 로봇 관문이 열린다.

## 3. 정지 action 이름을 두는 상수

**`src/physical/presets.ts` 의 한 줄이다.**

```ts
export const STOP_ACTION = 'abort';
export const STOP_REASON = { human: 1, screen: 2, connection: 3 } as const;
```

`PhysicalAction` 타입이 `typeof STOP_ACTION` 으로 이 줄에서 끌려온다. 하드웨어가 다른 이름을
쓰겠다고 하면 **이 한 줄만 고치면 타입까지 따라온다.** 규약 질문 다섯 중 첫째가 그것이다.

작업 중에 `STOP_ACTION as PhysicalAction` 으로 캐스팅해 두었다가 되돌렸다 — `abort` 가
union 에 없는데 있다고 거짓말하는 캐스팅이었고, 이름을 바꾸는 날 타입이 안 따라온다.

**`reason` 말고 다른 파라미터를 더하지 않았다.** 검사가 파라미터 키 목록이 정확히
`['reason']` 인지 본다.

사람이 「연결 확인」을 눌러 실제로 붙을 때만 내려온다. 로봇을 안 쓰는 자리에서는 372 kB 를
지고 가지 않는다. `verify:no-physical` 이 정적 import 가 생기면 잡는다.

**본 덩어리의 +97 kB 는 `protobufjs/minimal` 과 생성 모듈이다.** 이건 갈라 둘 수 없다 —
`decodeUplink` 가 화면 갱신 경로에 있고, 그 경로는 지연 로딩을 끼우면 첫 uplink 를 놓친다.

**한도 판정은 사람이 해야 한다.** 2단계-A 보고서 1절에 적었듯 `verify:standalone` 에는
KB 한도가 없다 — 그 검사는 import 경계만 본다. 숫자는 위에 남긴다.

단독 빌드는 399.98 kB 그대로다. 로봇 패널이 통합 셸 쪽에만 붙어서 단독 번들은 안 늘었다.

## 5. 로봇 명령이 `CommandTracker` 를 지나는 경로

```
버튼 → robotCommands.issueScan/issueApproach
     → commandTracker.issue(entity='robot-01', spec, { publish })   ← 추적·감사가 여기서 걸린다
         · recordHuman()          VZ-D-08 사람 조작 기록
         · stages: ['issued']     VZ-O-02 4단계 추적
         · buildAuditPayload()    VZ-O-03 감사 필드
         → options.publish        ← **수단만 갈렸다**
             → PhysicalClient.send() → encodeCommand() → MQTT downlink
     → applyAck(commandId)        ← 상관 키가 우리 command_id 다. uplink 가 이 키로 돌아온다
```

`verify:command-through-tracker` 가 넷을 본다. 추적기 목록에 뜨는가, 발행 단계가 적히는가,
MQTT 로 나갔는가, **게이트웨이는 0번 건드리는가.** 대조군으로 추적기를 우회한 직접 발행이
목록을 안 늘리는 것과, 발행 수단을 안 주면 게이트웨이가 기본값인 것을 확인한다.

## 6. 지시서와 다르게 한 곳

### 정지 버튼을 한 번 새로 만들었다가 되돌렸다

`RobotPanel` 에 「■ 긴급 정지」를 새로 넣었다가 지웠다. §8 이 「새 정지 버튼 신설」을 금지한
것을 놓쳤다. 되돌리고 나니 오히려 맞았다 — 패널은 마일스톤 화면에만 있는데 머리줄은 늘 떠
있어서, §4 의 「어느 화면에 있든 보여야 한다」를 머리줄이 더 잘 지킨다.

패널에는 **상태 표시만** 남겼다: 정지 실패 문구, 「정지됨」 띠, 해제 버튼.

### `ping` 을 승인 관문에서 뺐다

§2 는 「승인 전 발행 0건」이다. `ping` 은 그 선 밖에 두었다. 임무 명령이 아니라 **발표 직전에
무대에 오르기 전 누르는 연결 확인**이고, 승인이라는 개념 자체가 없다. 승인 관문에 넣으면
「연결이 되는지 보려면 먼저 승인해야 한다」가 되어 §1 의 0번 버튼이 성립하지 않는다.

검사가 이 예외를 명시적으로 확인한다 — 승인 전 `ping` 은 나가고 임무 명령은 안 나간다.

### 대상 지정을 안 하는 규약을 코드가 저절로 지킨다

규약 2절이 「대상을 지정하지 않는다」인데, `PhysicalClient` 의 토픽이 이미 장비 하나로 고정돼
있어 지정할 자리가 없다. 따로 막을 것이 없었다.

### 검사 스크립트가 안 죽는 문제

`CommandTracker` 가 만료 타이머를 세워서 Node 가 TTL 이 다 될 때까지 안 죽었다. 검사 끝에
`commandTracker.clear()` 와 `process.exit(0)` 을 넣었다.

## 7. 하지 않은 것 (§8 그대로)

- **객체 탐지 연동 · 2D 맵 · 뷰포인트 배치와 색** — 범위 밖
- **`scan_mission` 에 `forward_m` 태우기** — 스캔과 접근은 갈려 있다
- **스캔 → 접근 자동 연결** — `door_turn` 이 와도 사람이 눌러야 간다.
  `canApproach()` 가 `door_turn` 전에는 버튼을 보여 주지도 않는다
- **승인 전 발행** — 검사가 0건을 센다
- **`CommandTracker` 우회**
- **규약 밖 파라미터** — `reason` 하나
- **핫스팟 IP 짐작** — `presets.ts` 의 `venue` 는 여전히 빈 줄이다

## 8. 이건 안전장치가 아니다

> **화면의 정지는 소프트웨어 정지다. 물리적 비상 정지는 로봇 본체와 조종기 쪽에 있다.**

화면 버튼은 네트워크를 타고 나간다. 브로커가 죽었거나 Wi-Fi 가 끊기면 **안 나간다.**
그때 화면은 잠기지만 로봇은 계속 걷는다.

**시험할 때도 발표할 때도 로봇 조종기를 든 사람이 옆에 있어야 한다.**

이 문장은 `StopButton.tsx` 와 `robotSession.ts` 머리말에도 적어 두었다. 발표 자료에도
같은 문장이 들어가야 한다.

- **실제 왕복** — 이 작업은 로봇 없이 증명한 것까지다. 브로커에 실제로 붙여 `ping` 이

## 10. 목으로 먼저 볼 수 있는 것 (§6)

로봇 없이 넷 중 셋을 확인할 수 있고, `verify:emergency-stop` 이 이미 그것을 자동으로 돈다.

- 목 uplink 가 `step` 을 흘리는 중에 정지 → **남은 `CommandStatus` 가 와도 노드가 더 안 찬다**
- 화면이 「정지됨」으로 잠기고 승인·접근이 안 눌린다
- 브로커 주소를 틀리게 두고 누르면 「보내지 못했습니다」가 뜬다

사람이 눈으로 볼 것은 **크기와 색**이다 — 정지 버튼이 다른 버튼과 충분히 떨어져 있는지,
실패 문구가 발표장 뒤에서도 읽히는지.
