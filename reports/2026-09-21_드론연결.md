# 드론(x500-001) 연결 — 1·2단계 (2026-09-21)

> 가시화 저장소. 지시서 `문서/작업프롬프트_가시화_드론연결_260921.md`,
> 계약 `문서/CONTRACT_x500.md`, 드론 쪽 구현 `문서/REPORT_bridge.md`.
> **작업 도중 방향이 한 번 바뀌었다**(장비 상태를 백엔드 `/state` 로). §2 에 적는다.

---

## 1. 무엇을 했나

연결 관리의 **로봇 칸**에서 주소를 pi3 로 바꾸면 드론에 붙는다. 칸은 새로 만들지 않았다.

```
연결 관리 (브로커 · 장비 · FC 링크)   pi3 브로커에 MQTT 직통 — ping · Capability
드론 상태 (배터리 · arm · 비행 모드)   백엔드 /state — 계약 봉투 (Kafka 경유)
```

**상태 경로는 하나다.** 드론 상태를 MQTT 로도 뜯으면 「어느 쪽이 진짜냐」가 생기고,
한쪽만 고쳐지는 날 화면은 연결됨인데 값만 옛것이 된다.

---

## 2. 도중에 바꾼 방향 — 걷어낸 것

처음에 드론의 MQTT `state` 를 직접 뜯게 짰다가, 백엔드 확인 결과 **상태는 `/state` 로
들어온다**는 지시를 받고 되돌렸다. `deviceState.ts` 에서 걷어낸 것 다섯:

| 걷어낸 것 | 무엇이었나 |
|---|---|
| `details` 칸 + `mergeDetails()` + `ENVELOPE_KEYS` | 드론 `state` 본문(`battery`·`flight`·`gps`·`attitude`·`warnings`)을 담는 자리. `null` 이 옛 값을 덮도록 한 병합 규칙 포함 |
| `battery.remaining_pct` 정규화 | 드론의 중첩 배터리를 Go1 의 평평한 `battery_pct` 칸으로 모으던 것 |
| `fcLink` 칸 | 드론 `state` 의 `fc_link`. **ping 응답 쪽으로 옮겼다** |
| `link`·`device_status` 를 `state` 채널에서도 읽기 | 드론이 `link` 를 `state` 에 1Hz 로 싣기 때문에 넣었던 것 |
| `staleAfterMs()` — 장비가 준 `state_interval_s` × 3 | 드론 1Hz → 3초. `STALE_AFTER_MS` 15초 상수로 되돌렸다 |

남긴 것은 **식별 한 줄**이다 — `receiveDeviceMessage` 가 `noteDeviceReport` 를 부른다.
상태를 그리는 것이 아니라 「누가 붙어 있나」를 아는 것이고, 연결 관리가 이미 붙어 있는
그 소켓에서 얻으므로 표시 경로를 늘리지 않는다.

`verify:drone-via-state` 가 **걷어낸 상태로 유지되는지**를 검사한다 — MQTT 경로가 드론
배터리를 뜯으면 실패한다.

## 3. `go1-001` 하드코딩을 걷어 낸 곳

상수가 적힌 자리는 둘이었고, 소비처 여덟이 전부 `hardwareTarget()` 한 함수를 지났다.

| 자리 | 전 | 후 |
|---|---|---|
| [`encode.ts:hardwareTarget`](../viz-debugger/src/physical/encode.ts) | 표 한 줄(`robot-01 → go1-001`) | **붙은 장비가 밝힌 id 가 먼저.** 못 들었을 때만 옛 표 |
| [`encode.ts:encodeCommand`](../viz-debugger/src/physical/encode.ts) | `hardwareTarget(...)` | `mappedTarget(...)` — 부르는 쪽이 지정한 대상을 안 덮어쓴다 |
| [`PhysicalClient` 생성자](../viz-debugger/src/physical/PhysicalClient.ts) | `this.target` 을 `readonly` 로 **굳힘** | 안 굳힌다. 쏠 때마다 `commandTarget()` 을 읽는다 |
| [`PhysicalClient.connect`](../viz-debugger/src/physical/PhysicalClient.ts) | `terminal/go1-001/uplink` 구독 | **`terminal/+/uplink`** — `Capability` 가 이 토픽으로 오므로 아는 id 로만 구독하면 영영 못 듣는다 |
| [`PhysicalClient.send`](../viz-debugger/src/physical/PhysicalClient.ts) | 굳은 대상으로 발행 | 대상이 없으면 **발행하지 않는다** |

**조회와 발행을 갈랐다.** 조회(`hardwareTarget`)는 못 들었을 때 옛 표로 물러서도 해롭지
않다 — 빗나가면 「아직 아무것도 안 왔습니다」가 뜰 뿐이다. **발행(`commandTarget`)은
물러서지 않는다.** 물러서면 드론에 붙은 채로 `terminal/go1-001/downlink` 에 명령이
떨어지고, pi3 에는 듣는 사람이 없어 조용히 사라진다. 같은 랜에 pi7 이 살아 있으면 더 나쁘다.

덧붙여 계약 §2 대로 **clientId 를 `web-<임의값>` 으로 명시**했다 — 웹이 `x500-001` 로
붙으면 드론 노드를 밀어낸다.

## 4. 장비 종류 판정 경로

원천 셋, **전부 장비가 발행한 것**이다. 주소는 안 본다 ([`deviceIdentity.ts`](../viz-debugger/src/physical/deviceIdentity.ts)).

| 원천 | 무엇을 주나 | 언제 |
|---|---|---|
| `capability{device_id, actions[]}` | 이름 · **어휘** | 노드가 붙는 순간 한 번. **retained 아님** |
| `status.registration{entity_id, entity_type, device_type}` | 이름 · **종류** | **retained** — 구독 즉시 |
| 상태 토픽 `{zone}/{etype}/{id}/{channel}` | 이름 · 종류 | 매 건 |

**`Capability` 만으로는 안 된다.** retained 가 아니라 늦게 붙은 웹은 영영 못 받고, 그것
하나만 관문으로 두면 Go1 도 드론도 `ping` 조차 못 낸다 — 계약 §11-4 가 「Capability 를
못 받았으면 `ping` 으로 확인하라」고 지정한 그 `ping` 을. 메우는 것이 retained `status` 다.

**종류 문자열을 우리가 목록으로 정하지 않는다.** 장비가 `drone` 이라고 하면 `drone` 이고,
처음 보는 종류(`submersible`)도 그대로 받는다 — 검사가 그것부터 본다.

⚠ **규약 `Capability` 에는 종류 칸이 없다**(`device_id` 와 `actions[]` 뿐). 계약 §8 ·
`REPORT_bridge` §7 이 같은 판단을 적었다. `.proto` 를 안 고치기로 했으므로 종류는 JSON
쪽에서 읽는다 — 지시서 초안이 「Capability(device_id, 종류)」라고 적은 것과 다른 점이다.

**후보가 둘이면 고르지 않는다.** 하나를 골라 두면 엉뚱한 장비로 명령이 나간다.

## 5. 상태 항목을 어디서 받아 어떻게 그리는가

| 무엇 | 어디서 | 어디에 |
|---|---|---|
| 브로커 | WebSocket 연결 | 연결 관리 1줄 |
| 장비 | `ping` 왕복 + **종류·device_id** | 연결 관리 2줄 |
| FC 링크 | `ping` 응답의 `result{fc_link}` (계약 §5) | 연결 관리 3줄 |
| 배터리 · arm · 비행 모드 · GPS · 자세 · 경고 | 백엔드 `/state` 계약 봉투 | 현황판 「레지스트리에 없는 개체」 |

**항목표가 우리 코드에 없다.** 현황판의 그 구획은 받은 `payload` 를 원문 그대로 적고
상태 판정을 하지 않는다 — 드론 필드를 하나도 안 적었고, 백엔드가 §13 대로 모양을
지키는 한 우리가 고칠 자리가 없다. 지시서 원칙 2 를 **항목표 없이** 지킨 셈이다.

### 줄을 넷으로 안 늘렸다 — 지시서와 다른 점

지시서는 「기존 브로커/로봇 두 줄에 한 줄 더」라고 적었지만 **줄은 260910 부터 이미
셋**이었다(브로커 · 단말 · 로봇). 셋째 줄은 원래부터 「단말 너머의 그 장비 자신이 붙어
있는가」였고, 드론에서 그 자리에 해당하는 것이 FC 링크다. 같은 물음이라 같은 줄에 두고
**이름만 장비에 맞춘다.** 넷으로 늘리면 `verify:connection-panel` 의 `lines.length === 3`
단언이 깨진다.

판정 근거는 **기종이 아니라 장비가 보낸 키 하나**다 — `fc_link` 를 실어 보낸 장비면 FC
링크 줄이고, 안 실었으면 옛 로봇 줄이다.

### FC 링크는 실시간이다

`ping` 은 누를 때 한 번이라 그대로 두면 「아까 눌렀을 때는 초록이었다」가 된다. TELEM
점퍼가 빠지면 라즈베리파이는 멀쩡한 채로 FC 만 끊기므로, 붙어 있는 동안 2초마다 다시
잰다 ([`linkWatch.ts`](../viz-debugger/src/physical/linkWatch.ts)).

**Go1 에는 아무 일도 안 일어난다** — `fc_link` 를 한 번이라도 실어 보낸 장비에만 돈다.
장비가 스스로 켜는 감시이고, 드론 쪽이 그 키를 빼면 저절로 멎는다.

## 5-2. 하드웨어 카드 — 「연결되면 항상」

카드의 원천이 **대본 배역**뿐이었다. 그래서 대본에 안 적힌 장비는 붙어 있어도 안 보였고,
드론이 정확히 그 경우였다. 이제 **배역 ∪ 지금 값이 흐르는 장비**다.

- **배역은 값이 안 와도 남는다** — 임무를 열어 보는 동안 로봇이 꺼져 있을 수 있고, 그때
  배역이 사라지면 이번 편에 무엇이 나오는지조차 알 수 없다. 하던 대본 시연은 그대로 돈다
- **30초 조용하면 빠진다** — 꺼진 장비를 끌어다 배정하면 아무 일도 안 일어나고 왜인지
  알 수 없다. 창은 가장 느린 주기(드론 `status` 10초)의 세 배다
- 카드마다 **「대본 등장 장비」인지 「연결된 장비」인지** 적는다

### 단독 빌드를 안 오염시키는 배선

그리는 쪽이 `/state` 저장소를 직접 읽으면 **단독 빌드에 대시보드 계층이 딸려 들어간다**
(`verify:standalone` — 측정축 D 가 오염된다). 그래서 방향을 뒤집었다.

```
tabs/data/index.ts      (봉투 도착) ─┐
physical/deviceState.ts (MQTT 도착) ─┴─► shared/connectedDevices.ts ◄─ registry.ts · main.tsx
```

받는 쪽이 밀어 넣고 그리는 쪽은 `shared/` 만 읽는다 — `registerConnectionDefault` 가 주소에
대해 하는 일과 같은 모양이다. 단독 빌드에는 `tabs/` 가 없으니 MQTT 쪽만 들어오고, 그것이
그 빌드에서 맞는 결과다. `verify:device-cards` 가 빌드 없이 그 그래프를 다시 훑는다.

같은 id 가 두 길로 오면 **나중 것이 이긴다** — Go1 이 `/state` 로 옮겨 가는 동안 두 길이
겹치는 기간에 카드가 둘로 갈라지면 안 된다.

## 5-3. 프리셋 — 테일넷 둘 + 직접 입력

드론이 붙으면서 목록이 여덟이 됐고 그중 둘은 고를 수도 없는 빈 줄이었다.
**무대에서 여덟 중 하나를 고르는 것은 고르는 게 아니라 찾는 것**이라, 실제로 골라야 하는
「Go1 이냐 드론이냐」 하나만 남겼다.

| 이름 | 주소 |
|---|---|
| `Tailscale (Go1)` | `ws://pi7.tailcb6bfb.ts.net:9001/mqtt` |
| `Tailscale (드론)` | `ws://pi3.tailcb6bfb.ts.net:9001` |
| `직접 입력` | — |

mDNS·랩 IP·발표장 주소는 계약 §1 과 `presets.ts` 주석에 남아 있다 — 필요하면 직접
입력에 넣는다. 규칙이 한 문장으로 정리됐다: **주소를 모르면 프리셋을 안 만든다.**
옛 규칙(빈 줄은 고를 수 없다)을 포함하면서 더 세다.

### ⚠ 드론 테일넷 **이름은 계약이 준 값이 아니다**

계약 §1 이 준 것은 테일넷 **IP**(`100.85.243.54`)이고 그마저 1883 왕복만 확인됐다.
이름은 pi7(`pi7.tailcb6bfb.ts.net`)·pi1(`pi1.tailcb6bfb.ts.net`)이 쓰는 테일넷을 그대로
따른 것이다 — 같은 테일넷에 MagicDNS 로 `pi3` 가 올라 있어야 풀린다.

IP 대신 이름으로 둔 이유는 **기계마다 규칙이 갈리지 않게** 하기 위해서다. IP 로 두면
「망이 바뀌면 테일넷 쪽」이라는 한 문장이 Go1 에만 맞고 드론에는 안 맞는다.
**실기에서 이름부터 확인할 것.** 안 풀리면 직접 입력에 `ws://100.85.243.54:9001`.

경로(`/mqtt`)는 드론 쪽에 안 붙였다 — 계약이 9001 을 확인한 형태가 경로 없는 쪽이고
(§1), 각자 확인된 모양을 그대로 둔다.

### 기존 검사 둘을 같이 고쳤다

`verify:physical-port` 와 `verify:connection-panel` 이 옛 모양(빈 `venue` 프리셋)에
못박혀 있었다. **느슨하게 푼 것이 아니라 규칙을 바꿔 다시 조였다** — 「빈 줄은 고를 수
없다」에서 「빈 줄이 아예 없다」로. `verify:physical-port` 의 경계 밖 금지 목록에
드론 주소 셋(`pi3.local` · `pi3.tailcb6bfb` · 두 IP)도 더했다. 기계가 둘이 됐는데
한쪽만 막으면 새로 붙는 쪽 주소가 새 나가는 것을 아무도 안 잡는다.

테일넷을 통째로 막지는 않았다 — `src/detect/` 가 같은 테일넷의 다른 기계를 쓰고
그것은 그 경계 안에 있는 것이 맞다.

---

### 「직접 입력」이 안 골라지던 것을 고쳤다

프리셋을 줄이고 나서 사람이 화면에서 찾아냈다 — **「직접 입력」을 골라도 목록이 곧바로
옛 프리셋으로 되돌아간다.** 주소를 손으로 고치면 그때는 넘어가서 「고칠 때만 되는」
것처럼 보였다.

원인은 그 항목의 `url` 이 빈 문자열이라는 것이다.

```js
onChange={(e) => { const p = find(e.target.value); if (p && p.url) setDraft(p.url); }}
//                                                        ^^^^^ 직접 입력은 여기서 걸린다
```

`setDraft` 를 안 부르니 주소가 안 바뀌고, 값을 내는 식이 **주소에서 되풀이해 유도**하므로
여전히 옛 프리셋을 찾아낸다.

고름은 주소에서 유도할 수 없다 — **「직접 입력」은 주소가 아니라 사람의 뜻**이다.
그래서 고른 것을 따로 기억하고(`presetChoice.ts`), 프리셋을 다시 고르면 풀린다.
주소는 안 건드린다 — 대개 그 주소를 조금 고치려고 직접 입력을 고른다.

식을 판에서 꺼내 함수 둘로 만든 이유는 **검사가 그것을 볼 방법이 없었기** 때문이다.
판은 JSX 라 검사가 글자로만 읽고, 고르는 동작은 글자로 안 드러난다. 이제
`verify:connection-panel` 이 옛 구현과 지금 구현을 나란히 재서 대조군으로 남긴다.

## 6. 정지 버튼

드론은 `Capability` 에 `ping` 하나만 선언한다. 정지는 조종기의 일이다.

판정은 **`actions` 목록 하나**로 한다. 기종을 안 본다.

| 값 | 언제 | 무엇을 |
|---|---|---|
| `yes` | 선언했다 | 보낸다 |
| `no` | 선언 안 했거나, 보냈더니 `UNIMPLEMENTED` 로 돌아왔다 | **안 보내고** 「조종기로 정지하세요」 |
| `unknown` | 아직 목록을 못 받았다 | **보낸다** |

`unknown` 에서 보내는 것이 요점이다. `Capability` 가 retained 가 아니라 못 받는 것이
정상인데, 그것을 「지원 안 함」으로 읽으면 **멈출 수 있는 로봇 앞에서 못 멈춘다고 말한다.**
Go1 의 평소 모습이 바로 `unknown` 이다.

안 보내는 경우에도 **화면은 그대로 잠긴다** — 사람이 정지를 눌렀으면 멈춘 것으로 다룬다.

## 8. 지시서와 다르게 한 곳

| 다르게 한 것 | 왜 |
|---|---|
| 줄을 넷이 아니라 **셋으로 유지**, 셋째 줄 이름만 바꿈 | 줄은 이미 셋이었고, 넷이면 `verify:connection-panel` 이 깨진다 (§5) |
| 종류를 Capability 가 아니라 **JSON(`registration`·토픽 etype)** 에서 읽음 | 규약 `Capability` 에 종류 칸이 없다. `.proto` 무수정 (계약 §8) |
| 「Capability 못 받으면 명령 안 보냄」을 **「장비가 밝힌 id 가 없으면」** 으로 | Capability 가 retained 가 아니라 그대로 하면 Go1·드론 둘 다 `ping` 조차 못 낸다 (계약 §11-4) |
| `verify:stale-state` 대신 **`verify:fc-link` + `verify:drone-via-state`** | 상태가 `/state` 로 가면서 대상이 둘로 쪼개졌다 — FC 링크는 연결 관리, 배터리·arm 은 현황판 |
| 드론 목을 **검사 코드 안에만** | 목 게이트웨이에 심으면 「목에서는 보이는데 실제로는 안 보이는」 차이를 무대에서 발견한다 |
| 배터리 경고 구간을 상수로 두지 **않음** | 현황판이 원문을 그대로 적고 판정하지 않는다 — 색을 칠할 자리가 아직 없다 |

## 9. 남은 것 · 사람이 확인할 것

| # | 항목 |
|---|---|
| 1 | **`gateway.zone` 이 `zoneA` 여야 드론 카드가 뜬다.** 현황판은 `{entity:'*', node:<zone>, channel:'*'}` 로 구독하고 목 게이트웨이는 `zone-503` 이다. 백엔드 주소 + `zoneA` 조합에서만 보인다 |
| 2 | **Go1 의 `status` 가 retained 인지 확인 안 됨.** 드론은 계약 §3-1 이 retained 로 못박았지만 pi7 은 확인이 없다. retained 가 아니면 붙은 직후 첫 `ping` 이 최대 6초 기다린다(주기 5초). 실패는 아니고 늦어지는 것이며, `awaitDeviceIdentity` 기본값을 `waitForRobot` 과 같은 6초로 맞춰 뒀다 — **실기에서 봐야 한다** |
| 3 | **드론 테일넷 이름(`pi3.tailcb6bfb.ts.net`)이 확인 안 됨.** 계약이 준 것은 IP(`100.85.243.54`, 1883 만 ✅)이고 이름은 pi7·pi1 의 테일넷을 따른 것이다. 안 풀리면 직접 입력에 IP 를 넣는다 — §5-3 |
| 4 | **계약 §9 — `battery`·`flight`·`gps`·`attitude` 가 값이 찬 모습은 아직 아무도 못 봤다.** FC 분리 상태였다. 기체를 붙이고 3단계 실기에서 처음 본다 |
| 5 | **전류 스케일 의심** — 디스암인데 12.2A. 계약이 참고값으로 표시했다 |
| 6 | https 페이지에서는 `ws://` 가 mixed content 로 차단된다 (계약 §1) |
