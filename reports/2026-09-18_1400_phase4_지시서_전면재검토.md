# 제1부 — Phase 4가 대체 무엇을 하려는 것인가

## 1-1. 한 문장

> **로봇 카메라의 영상이 관제 화면까지 흐르는 "두 번째 파이프"를 서버에 뚫는다. 그리고 그 파이프를 뚫는 김에, 서버 밖에 있는 엣지가 서버에 붙을 수 있게 문을 연다.**

## 1-2. 왜 영상만 따로 도는가 (가장 먼저 잡아야 할 그림)

지금까지 Phase 1~3에서 만든 것은 **업무·관측 파이프** 하나다.

```
말단 ─MQTT─▶ 엣지 ─Kafka─▶ 서버 ─TSDB/MySQL 저장─▶
                              └─ WS 게이트웨이(8765) ─▶ 관제 화면
```

여기에 영상을 태우면 안 된다. 이유는 크기다. JPEG 한 장 50~150KB × 30fps = 초당 수 MB. MQTT·Kafka는 "작고 잃으면 안 되는 메시지"용 도구라 브로커가 죽는다(MK1에서 실제로 겪었다). 그래서 `CLAUDE.md` 원칙 3이 **"영상 픽셀을 업무·관측 메시지에 싣지 않는다"**를 못 박았다.

그래서 영상은 **완전히 별개의 두 번째 파이프**로 흐른다. Phase 4가 만드는 것이 이 두 번째 파이프의 **서버 구간**이다.

```
카메라 ─(홉1)─▶ 엣지 ─(홉2)─▶ 서버 ─(뷰어 분기)─▶ 브라우저
        HW 몫          ★여기가 우리      ★여기가 우리       VZ 몫
```

**Phase 4에서 백엔드가 실제로 짜는 코드는 가운데 "서버" 상자 하나뿐이다.** 카메라에서 영상을 꺼내는 것은 HW, 화면에 그리는 것은 VZ. 우리는 **형식을 정하고 중계한다.** 지시서 §2-3 「역할 경계」 표가 이 말을 하고 있다.

|---|---|---|
| 1 | **규격 3개** (`media-header.schema.json` 신설 · `frame-reference.schema.json` 설명 개정 · `detections.schema.json` 초안) | "영상 한 장에 무슨 꼬리표가 붙는가"의 규약 |
| 2 | **`backend/gateway/media.py`** | 프레임을 받아 뷰어들에게 나눠주는 중계 코어 + 버리는 규칙(drop-old) |

## 1-4. "방식 B"가 무엇인가 — 이 설계의 핵심 아이디어

WebSocket 메시지 하나를 이렇게 만든다:

```
[4바이트 = 헤더 길이][JSON 헤더][영상 바이트 원본]
```

왜 이 모양인가. **영상 한 장과 그 영상의 꼬리표(frame_ref)를 "한 메시지"로 묶어 원자적으로 보내기 위해서다.** JSON 안에 base64로 영상을 넣으면 33% 부풀고, 영상과 메타를 따로 보내면 둘이 어긋난다(드리프트). 헤더 길이를 앞에 4바이트로 붙이면 받는 쪽이 "앞 4바이트 읽기 → 그만큼이 JSON → 나머지가 영상"으로 무조건 정확히 가른다.

**그리고 서버는 영상 바이트를 절대 열지 않는다.** 헤더(JSON)만 읽고, 영상 바이트는 그대로 흘려보낸다. 디코드도 재인코딩도 안 한다. 그래서 서버 통과 비용이 거의 0이고, 코덱이 무엇이든 서버 코드가 한 벌이다 — 이것이 **결정 1 "D — 소스 native 코덱을 그대로 중계"**의 의미다.

## 1-5. drop-old가 무엇이고 왜 필요한가

"웹소켓 영상은 1초씩 밀린다"는 말의 정체는 **버퍼블로트**다. 링크가 빼낼 수 있는 속도보다 빨리 `send()`하면 못 나간 프레임이 큐에 쌓이고, 큐에 갇힌 프레임이 오래돼서 화면이 계속 뒤처진다.

해결책이 곧 설계다. **큐가 임계 위면 새 프레임을 보내지 않고 버린다.** 뒤에 더 최신 프레임이 오니 낡은 것은 버려도 된다. 그러면 **링크가 느려질 때 프레임을 잃지(fps↓), 지연이 늘지 않는다.** 관제에는 정확히 맞는 교환이다.

H.264가 들어오면 여기에 한 겹이 더 붙는다. H.264는 프레임끼리 의존한다(P프레임은 앞 프레임이 있어야 그려진다). 그래서 아무 프레임이나 버리면 화면이 깨진다. 그래서 상태 기계가 둘이다:

- **FLOWING** — 정상. P프레임은 임계 `T_drop`, 키프레임(IDR)은 더 넉넉한 `T_hard`까지 봐준다.
- **WAIT_IDR** — 한 번 버린 뒤. **다음 키프레임이 올 때까지 전부 버린다.** 키프레임이 오면 다시 FLOWING.

그리고 **새로 붙은 뷰어의 초기 상태도 WAIT_IDR**이다. P프레임부터 주면 브라우저 디코더가 시작조차 못 하기 때문. JPEG는 모든 프레임이 키프레임이라 같은 코드가 그냥 통과한다.

## 1-6. frame_ref가 왜 이 Phase의 심장인가

영상과 **탐지 결과(박스)**는 서로 다른 길로 온다.

- 영상: 미디어 파이프 (`/media`)
- 탐지 박스: 업무 파이프 (Kafka → `/state`)

이 둘이 **뷰어에서 만나** 겹쳐져야 오버레이가 성립한다. "3번 프레임의 박스"가 "3번 프레임" 위에 그려져야지, 5번 프레임 위에 그려지면 사람이 엉뚱한 곳에 있다.

그래서 프레임마다 **frame_ref**(= `source_id` + `capture_timestamp` + `sequence_id`)라는 꼬리표를 달고, 두 길 모두 그 값을 실어 나른다. 뷰어에서 **F == F**로 맞을 때만 겹친다.

**규칙: frame_ref는 엣지가 딱 한 번 만들고, 그 뒤 아무도 새로 만들지 않는다**(`CLAUDE.md` 원칙 10). 서버가 재생성하면 정합이 무너진다. 그래서 DoD에 "송신 원본과 도착분이 **바이트 동일**"이 들어가 있다.

## 1-8. 왜 "미디어 하나짜리 Phase"가 아닌가 — 네 묶음이 한 Phase에 묶인 이유

이것이 이해가 안 되는 지점일 텐데, 이유는 단순하다. **넷 다 같은 한 개의 Tailscale 터널을 쓴다.**

```
엣지 ══════ 하나의 Tailscale 터널 ══════ 서버
      ├ 미디어(방식 B WS, 8766)       ← ①
      ├ 명령·업무(Kafka, 9095)        ← ②
      └ 관측(OTLP, 4316)              ← ③
```

터널을 이번에 처음 실제로 쓰므로, 그 위에 올라탈 것 셋을 **같이 올려야** 한 번의 임시 엣지 구축으로 전부 검증된다. 따로 하면 컴퓨터를 임시 엣지로 세웠다 되돌리는 일을 세 번 반복해야 한다. ④(회신·통지)는 ①②③에서 정해진 형식을 타 파트에 전달하는 일이라 마지막에 붙는다.

## 1-9. 이번에 **검증되지 않는** 것 — 정직하게

이걸 알고 있어야 보고서의 「검증 범위의 한계」를 제대로 쓸 수 있다.

- **실물 로봇 영상이 한 장도 안 흐른다.** 전부 합성 H.264/JPEG fixture다.
- **온디맨드가 검증되지 않는다.** fixture는 붙으면 계속 송출한다. 서버→엣지 개폐 명령은 Phase 6. 즉 02-media-path §1-3-1이 길 B(온디맨드)를 고른 근거인 **"대역을 아낀다"가 이번에 전혀 실증되지 않는다.**
- **현장 회선이 아니다.** 연구실 공유기 뒤 컴퓨터다(Phase 3 선례와 동일).
- **VZ 브라우저가 실제로 붙어 보지 않는다.** 확인용 `console.html` 수준까지다.
- **실노드(pi7) 관통은 범위 밖이다.** pi7 배포본이 09-14에도 구판(1.3)이다.

### 🔴 A3. 8765를 Tailscale IP 단일 바인딩하면 서버 pytest가 반드시 깨진다

**문제.** 단계 7-1 표는 8765(뷰어 `/state`·`/media`)의 바인딩을 `<서버 tailscale IP>`로 바꾸고, 단계 8에서 **그대로 남긴다**.

그런데 실물 코드는 이렇다:

```
backend/settings.py:148-150   ws_host()  → os.environ.get("MK2_WS_HOST", "127.0.0.1")   # 문자열 1개
backend/settings.py:157-163   ws_url()   → os.environ.get("MK2_WS_URL", "ws://127.0.0.1:{port}")
                                           ↑ ws_host() 를 참조하지 않는다. 127.0.0.1 하드코딩
tests/conftest.py:54-55       ws_url fixture = settings.ws_url()
tests/test_pipeline.py:152,163                test_ws_delivery
tests/test_observability_pipeline.py:141,151  test_gateway_metrics_with_ws_client
backend/gateway/console.html:14               value="ws://localhost:8765"
```

`MK2_WS_HOST`만 Tailscale IP로 바꾸면 서버는 그 주소에만 LISTEN하고, **pytest는 여전히 `ws://127.0.0.1:8765`로 붙어 접속 거부**된다. 테스트 2건이 확정적으로 깨진다. `console.html`도 같이 깨진다.

**DoD 7-3·8-4가 "pytest 184 + 신규 전건 통과"를 요구한다 — 단계 7·8의 바인딩과 양립 불가능하다.**

**수정안 — 다중 바인딩.**

> 단계 2-4 표와 단계 7-1 표의 8765 바인딩 칸을 **`127.0.0.1` + `<서버 tailscale IP>` 동시**로 고치고, 단계 2-1의 `backend/settings.py` 항목에 다음을 넣는다:
>
> > `MK2_WS_HOST`를 **콤마 구분 목록**으로 읽는다(`ws_host()` → `list[str]`). `websockets`의 `serve(handler, host, port)`는 `host`를 `asyncio.loop.create_server`에 그대로 넘기고, 그 함수는 **문자열 시퀀스를 받아 모든 주소에 바인딩**한다 — **이 동작을 단계 2에서 `ss -tlnp`로 실측해 판정한다.** 목록 지원이 실측으로 확인되지 않으면 서버를 두 번 열어(`asyncio.gather`) 같은 핸들러를 공유한다.
> > 서버 `.env`: `MK2_WS_HOST=127.0.0.1,<서버 tailscale IP>`
> > `ws_url()`은 그대로 둔다(테스트는 계속 loopback으로 붙는다). **`ws_url()`을 Tailscale 주소로 바꾸지 않는다** — 그러면 컴퓨터에서 도는 단위 테스트가 서버 주소를 찾게 된다.
>
> 단계 2-6 `console.html` 항목에 한 줄 추가:
> > 주소 입력칸의 기본값을 `ws://127.0.0.1:8765`로 두되 **화면에서 바꿀 수 있게** 한다(단계 7에서 컴퓨터 브라우저가 `<서버 tailscale IP>`로 붙어야 한다). 토큰도 같은 방식으로 **입력칸**에 둔다 — 파일에 적어 커밋하지 않는다.
>
> DoD 7-1에 추가:
> > **7-h** `ss -tlnp`에 8765가 **`127.0.0.1`과 `<서버 tailscale IP>` 둘 다** LISTEN이고, 서버에서 pytest가, 컴퓨터 브라우저가 동시에 붙는다.

### 🔴 A4. drop-old에서 **JPEG는 `T_drop`이 절대 적용되지 않는다** — 지연 바운드가 4배 무너진다

**문제.** 단계 2-3 상태 기계를 JPEG(모든 프레임 `keyframe=true`)에 대입하면 이렇게 축약된다:

```
FLOWING  + keyframe=true + buffered <= T_hard → 보낸다
FLOWING  + keyframe=true + buffered >  T_hard → 버린다 + WAIT_IDR
WAIT_IDR + keyframe=true + buffered <= T_hard → 보낸다 + FLOWING
```

**`keyframe=false` 분기가 한 번도 안 돈다. 즉 `T_drop`은 JPEG에서 죽은 코드다.**

그런데 `T_hard = max(4 × T_drop, 최근 IDR 5개 중 최대 바이트 × 2)`이다. JPEG 15fps·25KB 프로파일에 넣으면:
- `T_drop ≈ 56KB` (150ms 분량 — 지시서의 검산 그대로)
- `T_hard = max(4×56KB, 25KB×2) = 224KB`
- 바이트율 375KB/s → **224KB 큐 = 약 600ms 지연**

**즉 JPEG 프로파일의 실효 지연 바운드가 150ms가 아니라 ~600ms다.** 지시서 §2-3의 *"JPEG 15fps·25KB → ≈56KB"* 검산은 실제로 쓰이지 않는 값이고, DoD 7-c(*"지연이 150ms 근처로 바운드되는지"*)가 JPEG에서 실패한다. 고정 CCTV가 JPEG 종단이므로 실배포에 그대로 걸린다.

**원인.** `T_hard`의 존재 이유는 **"키프레임을 버리면 GOP가 통째로 끊기니 넉넉히 봐준다"**이다. 그런데 **GOP가 없는 스트림(전부 키프레임)에는 그 여유가 필요 없다.**

**수정안 — 한 줄 규칙 추가.**

> 단계 2-3의 임계 절에 다음을 넣는다:
>
> > **⚠ GOP가 없는 스트림에는 `T_hard`를 적용하지 않는다.** 최근 창(60프레임)에 `keyframe=false`가 **0건**이면 `T_hard := T_drop`으로 둔다. `T_hard`의 존재 이유는 GOP 절단 회피인데, 모든 프레임이 독립인 스트림에는 절단할 GOP가 없다. 이것을 넣지 않으면 **JPEG의 실효 임계가 `4 × T_drop`이 되어 지연 바운드가 150ms가 아니라 600ms가 된다**(15fps·25KB 기준 실계산).
>
> 음성 대조 표(§5 단계 4)에 한 줄 추가:
>
> > | **M8** | **JPEG에서 지연 바운드가 H.264와 같은 기준으로 잡힌다** | 느린 뷰어 + JPEG 프로파일에서 큐 바이트 최대치가 `T_drop` 근처에 머문다(`4×T_drop`이 아니다) |
>
> 완료 판정 17번을 고친다:
> > 17. `T_drop`이 시간 기준(150ms × 바이트율, 하한 AU 평균×2, 상한 1MB)이고, `T_hard = max(4×T_drop, 최근 IDR 최대×2)`**이되 최근 창에 non-keyframe이 0건이면 `T_hard = T_drop`**이다.

### 🔴 A5. `buffered` 회계에서 라이브러리 전송 버퍼가 빠져 있다 + `max_size`·`compression` 미지정

**문제 (a) — 백프레셔 회계.** 단계 2-3은 *"큐에 쌓인 바이트 합계가 곧 `buffered`다"*로 정의했다. 이 구조 자체는 옳다(브라우저 `bufferedAmount`에 기대지 않는 판단은 정확하다). 그런데 **`await websocket.send()`가 반환한 뒤에도 바이트는 아직 링크에 나가지 않았다** — `websockets`의 전송 버퍼(`write_limit`, 기본 수십 KB)에 들어가 있고 **그 바이트는 우리 큐에 없다.**

H.264 프로파일의 `T_drop ≈ 10.3KB`인데 회계에서 빠지는 전송 버퍼가 그보다 크면, **실제 지연은 `T_drop`이 아니라 `T_drop + write_limit`에 바운드된다.** 150ms를 목표로 잡았는데 실측이 몇 배로 나온다.

**문제 (b) — `max_size`.** `websockets`의 수신 메시지 크기 상한 기본값은 **1MB**다. 방식 B 메시지 하나 = AU 하나 + 헤더이므로, 큰 IDR이나 고해상도 JPEG가 오면 **close 1009로 엣지 연결이 끊긴다.** 지시서는 헤더 길이 상한(64KB)만 정했고 메시지 전체 상한을 말하지 않았다.

**문제 (c) — `compression`.** `websockets`는 permessage-deflate를 **기본으로 켠다.** 이미 압축된 JPEG/H.264를 다시 deflate하는 것은 순수한 CPU 낭비이고, 30fps × N 소스에서는 무시할 수 없다.

**수정안.**

> 단계 2-3의 `buffered` 정의 박스 끝에 추가:
>
> > **⚠ 큐 바이트만으로는 회계가 닫히지 않는다.** `send()`가 반환해도 바이트는 `websockets`의 전송 버퍼에 남아 있고 그것은 우리 큐에 없다. **소켓 생성 시 `write_limit`를 명시하고 그 값을 실측해(`ss -tno`의 Send-Q와 함께) 지연 바운드를 `T_drop + write_limit`로 문서화한다.** `write_limit`를 작게(예 8KB) 잡으면 회계 오차가 `T_drop`보다 작아진다. 기본값에 기대지 않는다 — 판본에 따라 다르다.
>
> 단계 2-4 표 아래에 추가:
>
> > **⚠ 소켓 옵션 3개를 기본값에 맡기지 않는다.**
> > - **`max_size`** — 기본 1MB다. 방식 B 메시지 하나가 AU 하나이므로 큰 IDR·고해상도 JPEG가 **close 1009로 엣지를 끊는다.** `MK2_MEDIA_MAX_FRAME_BYTES`(기본 8MB)로 명시하고, 그 값을 넘는 프레임은 **연결을 끊지 말고 프레임만 버리고 기록**하도록 상한을 넉넉히 잡은 뒤 우리 코드에서 판정한다.
> > - **`compression=None`** — 이미 압축된 바이트를 deflate하지 않는다.
> > - **`write_limit`** — 위 백프레셔 회계.
> > 세 값은 `/state`(작은 JSON)와 `/media`(큰 바이너리)가 달라야 하므로 **입구별로 따로 준다.**
>
> 부록 C 환경변수 표에 `MK2_MEDIA_MAX_FRAME_BYTES` · `MK2_MEDIA_WRITE_LIMIT` 두 행을 추가한다.

### 🟠 B1. VZ 전송층에 바이너리 경로가 **전혀 없고**, 실패가 **무음**이다

실물(`viz-debugger/src/transport/WsTransport.ts:175-181`):

```ts
private onMessage(ev: MessageEvent): void {
  let msg: Record<string, unknown>;
  try { msg = JSON.parse(String(ev.data)) as Record<string, unknown>; }
  catch { return; }        // ← 조용히 버린다. 로그도 상태도 안 남는다
}
```

저장소 전체에서 `binaryType` 0건, 전송층 `ArrayBuffer` 0건, `createImageBitmap`·`drawImage` 0건. 방식 B 프레임(Blob)이 도착하면 `String(Blob)` → `"[object Blob]"` → `JSON.parse` 예외 → **무음 폐기**. 화면은 "연결됨"인데 영상만 영원히 안 온다. `onerror`도 `lastError`도 안 찍힌다 — **가장 진단하기 나쁜 실패 모드**다.

부록 B 5번은 *"디코드 경로가 필요하다"*까지만 말한다. VZ가 이 문장을 읽고 "JPEG 디코드 함수 하나 추가"로 이해하면 며칠을 잃는다.

**수정안 — 부록 B 5번을 이렇게 늘린다:**

> **5. 전송층에 바이너리 경로를 새로 만들어야 한다 (디코드보다 앞선 단계다).**
> `/media` 소켓에는 **텍스트 JSON이 한 줄도 흐르지 않는다.** 전부 바이너리다. 현재 `WsTransport.onMessage`는 `JSON.parse(String(ev.data))`이고 실패 시 `catch { return }`이라, 방식 B 프레임이 오면 **아무 로그 없이 조용히 버려진다** — "연결됨인데 영상만 안 옴"으로 보인다.
> 필요한 순서:
> 1. `ws.binaryType = 'arraybuffer'` — Blob이면 `.arrayBuffer()`가 **비동기**라 `sub.handler(envelope)`의 동기 계약이 깨진다
> 2. `onMessage`를 `typeof ev.data === 'string'` 기준으로 **텍스트/바이너리 2갈래 분기**
> 3. `[4B 헤더길이][JSON][페이로드]` 파서
> 4. 디코드 — JPEG는 `createImageBitmap`+`drawImage`, H.264는 WebCodecs
> **`catch { return }`에 최소한 카운터 하나를 붙여 달라** — 지금 구조에서는 형식이 틀려도 화면에 아무 신호가 없다.

이대로면 서버가 `started_at`을 UTC로 변환할 수 없다(서버가 KST를 가정하면 그게 곧 추측이다).

**수정안 — 부록 A 8-10에 요청을 하나 더 넣고, 단계 10-2에 방어를 넣는다.**

> **부록 A 8-10 ⑧ 매니페스트 `started_at`에 오프셋을 붙여 달라** — before/after:
> ```python
> # before (go1_capture_teleop.py:250 / go1_scan_capture.py:268)
> time.strftime("%Y-%m-%dT%H:%M:%S", time.localtime(started))
> # after
> datetime.fromtimestamp(started, tz=timezone.utc).astimezone().isoformat(timespec="milliseconds")
> ```
> 지금 값은 오프셋이 없어 서버가 UTC로 변환할 수 없다. HW 자신의 `pi/common/schema.py:55-59` 규칙(콜론 오프셋 + 밀리초)과 같은 모양이면 된다.
>
> **단계 10-2에 방어**: `started_at`에 오프셋이 없으면 **`NULL`로 넣고 `manifest` 원본에는 원값을 보존한다.** 서버가 시간대를 추측해 채우지 않는다(원칙 10과 같은 성질 — 없는 정보를 만들어내지 않는다). 대신 `frames.t0_unix`(epoch, `capture_upload.py:91`)가 있으면 **그것으로 `started_at`을 채운다** — 이쪽이 모호하지 않다.

### 🟠 B6. `be.gateway.clients`의 `channel` 라벨이 기존 `be.gateway.push`의 `channel`과 **같은 이름 다른 뜻**이다

- 기존: `be.gateway.push{channel=state|status|heartbeat}` — **업무 채널**(`ws_echo.py:104`, Kafka 토픽 꼬리)
- 신규: `be.gateway.clients{channel=state|media|ingest}` — **입구 종류**

값 `"state"`가 양쪽에 있는데 뜻이 다르다. Grafana에서 같은 라벨 키로 조인하면 조용히 틀린다.

**수정안 — 단계 2-5 표의 `be.gateway.clients` 행 라벨을 `channel` → `endpoint`로 바꾼다.**

> | `be.gateway.clients` | updown | `component`·**`endpoint`**(`state`\|`media`\|`ingest`) | 기존 계기에 `endpoint` 라벨을 더한다. ⚠ **`channel`을 쓰지 않는다** — `be.gateway.push{channel=…}`가 이미 그 이름을 **업무 채널** 뜻으로 쓰고 있어(`ws_echo.py:104`) 값 `"state"`가 두 뜻으로 겹친다 |

같은 이유로 `be.gateway.media_frames`·`media_rejected`에도 `channel`을 쓰지 않는다(현재 안은 `outcome`·`stage`라 문제없다).

### 🟠 B7. 관측에 **엣지 수신 카운터가 없다** — "안 왔다"와 "버렸다"를 구분 못 한다

단계 2-5의 계기 4종은 전부 뷰어 향이다(`media_frames{sent|dropped}` · `media_gop_cut` · `media_coldstart` · `media_rejected`). **엣지 입구에서 받은 프레임 수가 없다.**

그래서 "화면에 영상이 안 나온다"일 때 **① 엣지가 안 보냄 ② 서버가 거부 ③ 서버가 드롭 ④ 뷰어가 못 그림**을 관측만으로 가르지 못한다. DoD 4-3이 `sent` 차분만으로 판정하는데, `sent`가 0일 때 원인이 ①인지 ③인지 알 수 없다. 이건 `infra/README.md` §4 「떠 있다가 아니라 흐른다」가 경계하는 바로 그 상태다.

**수정안 — 단계 2-5 표에 한 행 추가:**

> | `be.gateway.media_ingress` | counter | `component` | **엣지 입구에서 받아 헤더 검증을 통과한 프레임 수.** 이것이 없으면 "영상이 안 나온다"에서 *엣지가 안 보냄*과 *서버가 버림*을 가르지 못한다 |

DoD 4-3에 추가: *"`be_gateway_media_ingress_total`과 `…media_frames{outcome="sent"}`가 **둘 다** 증가하고, 느린 뷰어를 붙이면 **ingress는 계속 늘고 sent만 덜 는다**."* — 드롭이 서버에서 일어났다는 관측 증명이다.

## 2-8. 마지막으로 — 이 지시서를 어떻게 봐야 하나

**설계는 옳다.** 결정 9개는 실물 근거 위에 서 있고, 서로 모순되지 않으며, 설계 세션에서 한 번 일어난 오염(요구하지 않은 `encoding` enum)은 스스로 잡아 철회했다. 역할 경계와 시연 3갈래 구분은 이 프로젝트에서 가장 잘 만든 울타리다.

**문제는 전부 "실물과 문서 사이"에 있다.** 서버에서 확인하지 않은 값을 확인했다고 적은 것(A1), 고치지 않은 문서를 고쳤다고 적은 것(A2), 코드가 실제로 어떻게 생겼는지 확인하지 않고 바인딩을 바꾼 것(A3). 셋 다 같은 성질이다 — **"문서가 그렇게 말한다"를 "실물이 그렇다"로 옮겨 적은 것.** 공교롭게도 그건 설계 프롬프트가 가장 강하게 금지한 것이고(*"지어내지 말고 명령을 제시해 결과를 받아 근거로 써라"*), Phase 3에서 이미 한 번 경계했던 것이다.

나머지 셋(A4·A5·A6)은 성질이 다르다. **설계가 옳은데 세부가 한 겹 덜 내려간 것**이다. drop-old는 H.264만 보고 JPEG를 안 대입했고, 백프레셔는 우리 큐만 보고 라이브러리 버퍼를 안 봤고, ufw는 "연다"만 보고 "막는가"를 안 봤다. 셋 다 **음성 대조를 하나씩 추가하면 잡힌다** — 이 지시서가 이미 잘하고 있는 그 방식으로.
