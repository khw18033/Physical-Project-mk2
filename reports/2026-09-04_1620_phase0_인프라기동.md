# Phase 0 — 인프라 기동 (보고)

**작업 단위:** Phase 0 (인프라 기동)
**일자:** 2026-09-04
**근거 지시서:** [`docs/be/tasks/작업지시_phase0_인프라기동.md`](../docs/be/tasks/작업지시_phase0_인프라기동.md)
**검증 수단:** 헬스체크 (pytest 아님 — 지시서 4단계)

---

## 배경

Phase 1~ 백엔드 파이프라인이 딛고 설 인프라 스택을 먼저 세운다. 인프라는 Phase 0에서 한 번에
깔고, 이후 Phase에서는 그 위에 코드·설정·파이프라인만 올린다.

지시서는 스택 8개(Kafka·Mosquitto·OTel Collector·Prometheus·Grafana·Loki·Tempo·MySQL)를
올리되, **Kafka·MySQL은 "새로 설치", 나머지 6개는 "이관·헬스 확인"**으로 분류했다. TSDB는
제품 미확정이라 Phase 2로 제외.

### 지시서 전제와 실제의 차이

**지시서는 MySQL을 "새로 설치"로 분류했으나, 서버에는 MySQL을 포함해 7개가 이미 가동 중이었고
없는 것은 Kafka 하나였다.** 지시서 49행이 `"이미 도는지"는 구현 시 서버 상태로 판단하고, 도는
것은 정의 정리+헬스, 없는 것은 새로 설치한다`고 열어두었으므로, 서버 상태를 기준으로 진행했다.

즉 **이번 작업에서 실제로 설치한 것은 Kafka 하나**다.

### 2. Kafka 설치 (유일한 신규)

서버 compose 파일에 `kafka` 서비스 블록만 추가했다. **기존 11개 서비스 정의는 한 줄도 건드리지
않았다.**

- **이미지:** `apache/kafka:3.9.1` — Apache 공식 이미지, KRaft 네이티브라 ZooKeeper 컨테이너가
  필요 없다. Kafka 4.x는 변경 폭이 커서 안정 계열인 3.9를 택했다.
- **배포 규모:** KRaft 단일 노드, 복제 없음. 국가 프로파일(3AZ·RF=3)이 아니라 **현재 배포
  프로파일**이다(CLAUDE.md 원칙 15). 브로커 추가·파티션 확장으로 키울 수 있다.
- **역할 근거:** 엣지↔서버 업무 백본 + 서버 다중 소비자 팬아웃(아키텍처 §5-1, §6-1). Kafka를
  고른 이유는 데이터 양이 아니라 **다중 소비자 구조**다.

**설정값과 근거:**

| 설정 | 값 | 근거 |
|---|---|---|
| `KAFKA_NODE_ID` | `1` | 단일 노드 |
| `KAFKA_PROCESS_ROLES` | `broker,controller` | KRaft 겸용 (ZooKeeper 없음) |
| `KAFKA_CONTROLLER_QUORUM_VOTERS` | `1@localhost:9093` | 투표자가 자기 자신뿐 |
| `KAFKA_CONTROLLER_LISTENER_NAMES` | `CONTROLLER` | 리스너 3종 중 합의용 지정 |
| `KAFKA_LISTENERS` | `PLAINTEXT://0.0.0.0:9092`<br>`CONTROLLER://0.0.0.0:9093`<br>`INTERNAL://0.0.0.0:9094` | 외부 클라이언트 / KRaft 합의 / 같은 docker 네트워크 컨테이너 |
| `KAFKA_ADVERTISED_LISTENERS` | `PLAINTEXT://localhost:9092`<br>`INTERNAL://kafka:9094` | **Phase 1에서 교체 필요** — 아래 미결 참조 |
| `KAFKA_LISTENER_SECURITY_PROTOCOL_MAP` | 셋 다 `PLAINTEXT` | 인증·암호화 없음. 지시서가 "인증·TLS 운영 구성"을 Phase 0에서 제외 |
| `KAFKA_INTER_BROKER_LISTENER_NAME` | `INTERNAL` | 단일 노드라 실제 통신은 없으나 설정 필수 |
| 복제 인자 4종<br>(`OFFSETS_TOPIC` / `TRANSACTION_STATE_LOG` / `TRANSACTION_STATE_LOG_MIN_ISR` / `DEFAULT`) | 전부 `1` | 기본값 3이면 내부 토픽(`__consumer_offsets`) 생성이 즉시 실패한다 |
| `KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS` | `0` | 기본 3000ms 대기가 개발 중 불편. **운영 전환 시 상향** (승인됨) |
| `KAFKA_LOG_DIRS` | `/var/lib/kafka/data` | 기본값 `/tmp/kraft-combined-logs` 회피 |
| `KAFKA_LOG_RETENTION_HOURS` | `168` (7일) | **Kafka는 장기 저장소가 아니다**(CLAUDE.md 원칙 11). 다중 소비자 독립 읽기·단기 버퍼·단기 replay용. 장기 보존은 TSDB 몫(Phase 2) (승인됨) |
| `KAFKA_AUTO_CREATE_TOPICS_ENABLE` | `"false"` | 켜두면 오타 토픽이 자동 생성되어, 발행자는 성공했다고 믿는데 아무도 안 읽는 상황이 생긴다 (승인됨) |
| `ports` | `127.0.0.1:9092:9092` | Phase 0은 로컬 헬스체크만 필요. **Phase 1에서 변경** |
| `healthcheck` | `kafka-broker-api-versions.sh` | 프로세스 존재가 아니라 **실제 응답**을 확인 |

**겪은 문제 — 데이터 디렉터리 권한:**
`apache/kafka` 이미지는 컨테이너 안에서 **uid 1000(appuser)**으로 도는데 서버 작업 계정의 uid는
**1004**였다. `mkdir`만 하면 컨테이너가 쓰지 못해 기동이 실패한다. 다음으로 해결:
```
mkdir -p kafka_data
sudo chown -R 1000:$(id -g) kafka_data   # 소유자=컨테이너 appuser, 그룹=작업 계정
chmod 775 kafka_data
```

**기동:**
```
docker compose up -d kafka
```
**서비스 이름을 반드시 명시한다.** 생략하면 11개 전부가 대상이 되어, `:latest` 태그를 쓰는 기존
서비스들이 이미지 갱신 시 재생성될 수 있다.

기동 로그에서 `Kafka Server started` 확인, `docker compose ps`에서 `Up (healthy)` 확인.

**UFW:** 작업 중 `sudo ufw allow 9092` 실행(규칙 추가됨). 현재 바인딩이 `127.0.0.1`이라 실제
외부 노출은 없고, Phase 1에서 바인딩을 바꿀 때 함께 유효해진다.

### 3. 손대지 않은 것

- **나머지 7개 서비스** — 정의·데이터·설정 전부 무변경. 정지·재생성 없음.
- **MySQL** — 새로 설치하지 않았고, **DB·테이블도 만들지 않았다.** 지시서가
  "초기 스키마는 Phase 2·6에서, 여기선 컨테이너 기동까지"라고 명시했다.
- **Grafana** — 데이터소스·대시보드 무변경. provisioning 도입하지 않음.
- **설정 파일 5개** — 서버 `config/` 아래의 mosquitto·otel-collector·prometheus·loki·tempo
  설정을 그대로 두었다. 지시서 3단계가 "기존에 이미 있던 설정은 이관해 재사용한다(새로 안 짬)"
  라고 했고, 새로 짤 것이 없었다.

### 4. 저장소 쪽 정리

작업 방식이 **"작업 폴더에서 편집 → 서버에 복사·적용 → 결과를 가져와 수정"**이므로, 서버 실제
파일의 사본을 저장소에 둔다.

| 경로 | 내용 | 커밋 |
|---|---|---|
| `infra/docker-compose.yml` | 서버 compose 파일의 작업본 | ❌ gitignore |
| `infra/config/` | 서버 설정 파일 5개 사본 | ❌ gitignore |
| `_serverinfo/` | 서버 상태 조회 결과 | ❌ gitignore |

**커밋하지 않는 이유:** compose에 평문 비밀번호 4개(MySQL root/user, Grafana admin, Redis,
MongoDB)가 있고, `prometheus.yml` 주석에 내부망 IP가 남아 있다. 이 저장소는 Public이다.

## 설정 파일에서 확인된 사항

조치는 **해당 Phase에서** 한다. Phase 0에서 고칠 것은 없다. 아래가 Phase 1·3의 작업 내용을
구체화한다.

| 파일 | 확인된 것 | 무엇에 영향 | 언제 |
|---|---|---|---|
| `mosquitto.conf` | `allow_anonymous true`, ACL 없음 | 보안만. **Phase 1에는 오히려 유리** — 브릿지가 자격증명 없이 붙는다 | 운영 전환 시 |
| `mosquitto.conf` | `persistence` 설정 없음 (기본 `false`) | 브로커 재시작 시 retained 메시지 소실. 다만 정본이 "브라우저 재접속 스냅샷은 retained가 아니라 백엔드 캐시(BE-T-06)"로 정했으므로 MK2 핵심 영향은 작다 | Phase 1/5 |
| `otel-collector-config.yaml` | **`logs`·`traces` 파이프라인 없음 (metric만)** | 정본(§5-3·§6-3)은 "Collector가 log→Loki, trace→Tempo 분배"인데, 현재는 Loki·Tempo가 각각 직접 수신한다. **Collector를 안 거치므로 저장소를 바꾸면 애플리케이션을 고쳐야 하는 구조** | **Phase 3 핵심** |
| `otel-collector-config.yaml` | processor 없음 (`batch` 없음) | 수신 즉시 export → 부하 급증 시 유실·지연 | Phase 3 |
| `prometheus.yml` | `global.scrape_interval: 1s` | 정본(§6-4)이 상정한 "관측 평면 15초~1분"과 다르다. 시계열·디스크 부담이 15배. **바꾸면 기존 대시보드 해상도가 떨어지므로 단독 변경 불가** | Phase 3, **팀원 합의 후** |
| `prometheus.yml` | 페더레이션 없음 | BE-S-03의 "엣지 raw + 중앙 요약 pull" 2계층이 없다 | Phase 3 |
| `loki-config.yaml` | **retention 설정 없음** | 로그가 무제한으로 쌓인다. 지금은 유입이 거의 없어 무해 | **Phase 3 — 로그 파이프라인을 연결하기 *전에*.** 흘린 뒤 걸면 이미 쌓인 것은 안 지워진다 |
| `loki-config.yaml` | schema v11 + boltdb-shipper (Loki 3.x 기준 구식), `allow_structured_metadata: false`로 호환 유지 | 동작에 문제 없음. structured metadata 기능만 못 쓴다 | 필요해지면 |
| `tempo-config.yaml` | **OTLP를 직접 수신 (4317/4318)** | **이것이 Tempo가 4317을 점유하고 OTel Collector가 4316으로 밀린 이유다.** 포트 충돌은 증상, 원인은 구조 | Phase 3 |

## 지시서와 다르게 이행한 것

1. **MySQL을 새로 설치하지 않았다.** 지시서는 "새로 설치"로 분류했으나 서버에 이미 가동 중이었다.
   지시서 49행("'이미 도는지'는 구현 시 서버 상태로 판단")에 따랐다.

2. **완료판정 2 "`docker compose up` 후 8개 서비스가 전부 기동"을 "Kafka만 up + 나머지 7개는
   기존 인스턴스 헬스 확인"으로 이행했다.** 이미 잘 도는 7개를 한 번의 `up`에 포함시키면 정지·
   재생성이 일어나므로, **제약 2("이미 서버에 도는 기반을 지웠다 다시 깔지 않는다")를 우선**했다.

3. **완료판정 4의 "`.env`로 빼고 compose에는 placeholder만"을 "compose 파일 자체를 gitignore"로
   이행했다.** 제약 4가 명시한 목적은 **"비밀정보를 커밋하지 않는다"**이고, `.env`는 그 목적을
   이루는 수단으로 적힌 것이다. 그 수단의 전제는 "compose 파일이 저장소에 커밋된다"였는데,
   작업 방식상 compose 파일을 커밋하지 않기로 하여 전제가 사라졌다. **목적은 충족된다.**
   `.env`는 Phase 1에서 백엔드 코드가 접속 정보를 읽어야 할 때 실제로 필요해지므로 그때 만든다.

4. **지시서 용어 "이관"은 이번 작업에 해당 사항이 없었다.** 지시서의 "이관"은 "설정 정의를 옛
   compose 파일에서 MK2 저장소의 새 compose로 옮겨 적는다"는 뜻이었으나, **서버 compose 파일
   자체를 작업본으로 쓰기로 하여 옮겨 적을 대상이 없었다.** 실제로 한 일은 "Kafka 신규 설치"와
   "나머지 7개 헬스 확인" 둘뿐이다. → **다음 지시서에서 용어 정리 권장.**

| 토픽 이름·파티션 설계 | 없음. **토픽 이름에 `.`과 `_`를 섞지 말 것** (Kafka가 메트릭 이름 변환 시 충돌 경고) | Phase 1 |
| MQTT→Kafka 브릿지 구현체 | 미정 (Kafka Connect + MQTT Source / 브로커 네이티브 브릿지) | Phase 1 |
| Mosquitto `persistence` | 미설정 → 재시작 시 retained 소실 | Phase 1/5 |
| **OTel Collector logs·traces 파이프라인** | 없음 (metric만) | **Phase 3 핵심** |
| Collector `batch` processor | 없음 | Phase 3 |
| Prometheus `scrape_interval: 1s` | 정본 15s~1m과 상이 | Phase 3, 팀원 합의 후 |
| Prometheus 페더레이션 | 없음 (단일 Prometheus) | Phase 3 |
| **Loki retention** | 없음(무제한). **로그를 흘리기 전에 걸어야 함 — 순서 주의** | Phase 3 |
