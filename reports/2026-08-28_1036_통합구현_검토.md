## B. `verify:standalone`이 위반을 못 잡았다 — **수정함**

논문 측정축 D는 단독 빌드로 재기 때문에, 이 검사는 "관제·영상 탭 코드가 섞이지 않았다"를 보증하는
유일한 장치다. 그런데 판정문이 경로 구분자를 역슬래시로 하드코딩하고 있었다.

```js
if (next.includes(`${join(sourceRoot, 'shell')}\\`) || …) forbidden.push(next);
```

Windows에서만 맞고 그 외에서는 **어떤 위반도 매치되지 않는다.** 실제로 `standalone.tsx` 맨 위에
`import { AppShell } from './shell/AppShell.tsx';`를 주입하고 리눅스에서 돌린 결과 `✅ 통과`가 나왔다.

고친 내용 두 가지.

1. `relative(sourceRoot, next)`로 상대 경로를 만든 뒤 구분자를 `/`로 정규화해 판정한다.
2. **음성 대조군을 스크립트 안에 넣었다.** `verify:single-egress`가 이미 쓰던 방식으로,
   셸 import를 일부러 주입한 2차 스캔이 위반을 잡지 못하면 스크립트 자체가 실패한다.
   이제 이 검사가 무력화되면 조용히 통과하는 대신 소리를 낸다.

수정 후 리눅스에서 `✅ 통과 — 의존 그래프 17개 파일에 셸/다른 탭 import 0건, 주입 시 실패 검출`.

`verify:single-egress`는 문제없다. 전 파일을 세고 `commandEgress.ts` 하나만 남는지 확인하며,
음성 대조군도 이미 들어 있다. 실제로 `.publishCommand(` 호출은 `shared/commandEgress.ts` 한 곳뿐이고
`ActionModal.tsx`도 `issueCommand()`를 거친다.

## C. 공유 계층 여섯 중 다섯이 호출자 0건 — **경계가 아직 서지 않았다**

| 파일 | 호출자 | 상태 |
|---|---|---|
| `shared/commandEgress.ts` | 셸 3곳 · `ActionModal` 1곳 | **살아 있다.** verify로 지켜지기까지 한다 |
| `shared/notifications.ts` | 셸 · commandEgress | 살아 있다 |
| `shared/registry.ts` | **0** | `main.tsx`가 `scenario.hardware`를 직접 읽는다 |
| `shared/stores/traceStore.ts` | **0** | 실제 기록 열은 `data/scenario.ts`의 `humanTrace[]`다 |
| `shared/stores/latestValueStore.ts` | 0 | 탭②~⑥이 없으니 당연 |
| `permissions.ts` · `presentation.ts` · `observability.ts` | 0 | 선언만 |

뒤의 셋과 `latestValueStore`는 **받을 탭이 아직 없으니 비어 있는 게 맞다.** 자리를 먼저 잡아 두자는
것이 이번 작업의 취지였다.

**문제는 `registry.ts`와 `traceStore.ts`다.** 이 둘은 받을 쪽(탭①)이 이미 있는데도 우회당하고 있다.

- `registry.ts`는 `listRegisteredHardware()`를 내보내지만, 하드웨어 카드를 그리는 `main.tsx`는
  `scenario.hardware`를 직접 순회한다. 탭②를 이식하는 사람은 빈 경계를 보고 자기 방식으로 배선하게 된다.
- `traceStore.ts`는 "탭①의 되감기용 기록 열"이라고 주석에 적혀 있으나, `recordHuman()`은
  `data/scenario.ts`의 모듈 지역 배열에 넣는다. 2단계에서 기록 저장소를 갈아끼울 때 **두 곳을 고쳐야 한다.**

지금 배선하는 비용은 각각 한 줄~열 줄이다. **미루면 탭 이식 때 "어느 쪽이 원천인가"를 다시 정해야 하고,
그건 정확히 이번에 통합을 앞당긴 이유다.** 2단계 착수 전에 붙일 것을 권한다.
(이번에는 손대지 않았다. 탭①의 데이터 경로를 바꾸는 일이라 검토 범위를 넘는다.)
