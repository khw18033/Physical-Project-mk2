## 1. 더한 사건 네 종과 `payload` 의 실제 모양

`nodeId` 는 넷 다 **`commandId`** 다. 액션 아이템의 정체가 `TaskCommandRecord` 이고 그것을
가리키는 키가 그것이라 새 식별자를 만들지 않았다. 목에서는 액션 아이템의 `id` 가 곧
`commandId` 이고, 라이브에서는 로봇이 준 ack 의 것이다.

아래는 **실제로 흐른 값**이다(게이트웨이 왕복과 로컬 재생기에서 그대로 떠 왔다).

```
commanded  node=AI-0909-B2-2  by=backend  status=running
           payload { taskId: "T-B2", action: "move_forward",
                     parameters: { distance_m: 1, vx: 0.3 }, requestId: null }

answered   node=AI-0909-B2-2  by=robot    status=running
           payload { taskId: "T-B2", line: "MOVING · travelled_m=0.6",
                     index: null, answerKind: "status" }

expired    node=AI-0909-B3-1  by=robot    status=awaiting_evaluation
           payload { taskId: "T-B3", waitedMs: 4000,
                     reason: "정지 응답이 4초 안에 오지 않았다" }

adjusted   node=T-B2          by=human    status=rerunning
           payload { taskId: "T-B2", field: "speed", before: "0.35", after: "0.40" }
```

`producedBy` 에 **`robot` 을 더했다.** `backend` 로 뭉개면 「AI·백엔드·사람 셋 중 누가 만든
값인지 적는다」(§4-3)에 로봇이 백엔드라고 답하게 된다 — 그것은 다른 사실이다.

### 지시서와 다르게 한 곳 셋

**① `answered.payload` 에 `answerKind` 한 칸을 더했다.**
지시서 §1 표는 `{ taskId, line, index }` 셋이다. 수락·진행·종료를 못 가르면 화면이 줄
종류를 잃고, 무엇보다 **종료 줄만이 명령의 끝을 말하므로** 접기가 `done`/`failed` 를
정할 수 없다. 그 한 칸이 없으면 액션 층의 `status` 가 영영 `issued` 에 머문다.

**② `expired.status` 를 `failed` 로 안 적고 `awaiting_evaluation` 으로 적었다.**
기다림이 끝난 것이지 그 명령이 실패했다고 **안** 것이 아니다 — 로봇이 늦게 답할 수도,
이미 실행했을 수도 있다. 그 판정 불가가 이 값이다. 접기는 이 칸을 안 읽으므로
(§3의 「섞지 마라」) 화면 판정에는 영향이 없다.

**③ `adjusted` 의 `nodeId` 가 태스크일 수 있다.**
지시서는 「`nodeId` 는 `commandId` 다」라고 못박았다. 그런데 **값을 바꾸는 시점에 그
태스크가 명령을 낸 적이 없을 수 있다** — 실제로 `ActionModal` 의 입력칸은 「낸 명령이
0건일 때만」 뜬다(260912 결정). 그때 바꾸는 것은 계획값이므로 `nodeId` 는 그 태스크다.
**새 식별자를 만든 것이 아니라 이미 있는 노드를 가리킨다.** 접기에서 명령 행은
`commanded` 만 만들고, 태스크를 가리키는 조정은 `planAdjustments()` 가 따로 내놓는다.

이 때문에 `fold.ts` 의 태스크 층에 한 줄을 더해야 했다 — **액션 사건은 태스크 상태를
안 바꾼다**(`if (isActionEvent(event)) continue;`). 없으면 값 하나 고친 것이 그 태스크를
`rerunning` 으로 만든다. 아무것도 다시 돌지 않았는데.

### 현황판 값은 안 옮겼다

로봇 위치·배터리·연결 램프는 기록 열에 안 넣었다. 260828 의 「두 상태 모델은 합치지
않았다」가 그대로 유효하다. 명령만 옮긴 이유는 명령에 **낸 시각이 있고 상태가 전이하기**
때문이다 — 사건의 모양을 하고 있다.

## 2. 「아직」과 「영영」을 어떻게 갈랐나 — **이 작업의 핵심**

일지는 일어난 일만 덧붙인다. 그런데 **안 온 응답은 일어나지 않은 일**이라 적을 수가 없다.

그래서 응답이 아니라 **기다림이 끝났다는 사실**을 적는다. 기다린 것은 일어난 일이다.

```
        명령 났음 · 응답 0건 · 기한 사건 없음   →  아직 기다리는 중
        명령 났음 · 응답 0건 · 기한 사건 있음   →  영영 안 왔다
```

구현은 세 겹이다.

**① 기록** — `expired` 를 별도 사건으로 남긴다. 라이브에서는 이미 재료가 있던 자리를
그대로 썼다: `reportPauseAnswer(client, commandId, taskId, 4000)` 이 4초를 기다리고 안
오면 `notePauseFailure()` 를 부르는데, **그 자리에 기록 한 줄을 더했다.**

**② 접기** — `expired` 를 `status` 에 안 섞었다.

```ts
actions: Record<string, {
  taskId: string;
  status: 'issued' | 'running' | 'done' | 'failed';
  answered: number;
  expired: boolean;        // ← status 와 별개 칸
}>
```

섞으면 두 모양이 같은 값을 내놓는다. 실측으로 확인했다 — 시연 편의 `AI-0909-B3-1` 은
끝에서 `status=issued · expired=true` 다. `failed` 로 덮었다면 「명령이 실패했다」가 되고,
로봇이 답을 안 한 것인지 답이 실패였는지 영영 알 수 없다.

**③ 화면** — 두 딱지를 **다른 글자·다른 색**으로 적는다. 기록에서 갈려도 화면에서 같으면
사람은 끝내 못 본다.

```
응답 없음 (빨강)   기한이 끝났다. 「42초에 4초 기다렸습니다 — 정지 응답이 4초 안에 …」까지 적는다
대기 중  (노랑)   아직 기다리는 중이다
```

`verify:no-answer` 가 셋을 다 본다. 시료를 **넷**으로 짰다 — 기다리는 중 · 영영 안 옴 ·
답이 옴 · **답이 오고 나서 기한도 찍힌 것**. 마지막이 없으면 「응답이 온 명령이 무응답으로
잡히는」 사본(지시서가 못박은 대조군)을 만들 방법이 없다.

시각에 따라 뜻이 바뀌는 것도 본다 — 같은 `AI-0909-B3-1` 이 T+41 에는 「아직」, T+42 뒤에는
「영영」이다. 되감기가 이 구분에 닿는다는 뜻이다.

> 이 구분이 논문에도 값을 한다. 로봇 침묵이 원인인 실패가 지금은 계측 범위 밖인데,
> `expired` 가 그것을 기록 안으로 들인다 — §6-2 의 「도구가 원리적으로 못 찾는 경우」가 준다.

## 3. `fold` 를 세 층으로 늘리면서 순수 함수 성질을 어떻게 지켰나

**액션 층의 어휘와 접기를 `src/data/actionTrace.ts` 로 갈라 뒀다.** `fold.ts` 는 그 파일에서
`foldActions` 와 `isActionEvent` 만 끌어온다. 두 파일 다 저장소도 대본 파일도 React 도
모른다 — `robotSession` 을 import 하는 순간 `verify:scenario-mode` 와 `verify:fold-actions`
가 접기를 Node 에서 직접 못 돌린다.

**접기가 작업대를 볼 이유도 없다.** 명령이 기록 열에 들어와 있기 때문이다. 이것이 이번
설계의 요지다 — 「작업대를 읽되 순수하게」가 아니라 「작업대를 안 읽어도 되게」 만든 것이다.

`verify:fold-actions` 가 두 겹으로 지킨다.

1. **Node 에서 직접 부른다** (`verify:scenario-mode` 와 같은 방식). 두 파일이 React 나
   저장소를 끌어왔으면 검사가 `import` 에서 죽는다
2. **소스도 본다** — `import type` 이 아닌 실행 import 에 `robotSession` · `react` ·
   `scenarios/library` · JSON import 가 들어오면 실패. 지금은 안 끌어와도 내일 누가 한 줄
   적으면 끌어온다

`FoldedStatuses.actions` 는 화면이 읽는 표(`foldActions`)의 **요약**이다. 두 곳에서 따로
접지 않는다 — 따로 접으면 화면이 그리는 것과 접기 결과가 언젠가 어긋난다.

## 4. 라이브 기록과 목 기록을 대조한 결과

같은 `MSN-260909-01` 을 두 길로 돌리고 사건의 **모양**을 맞대 봤다(라이브는 가짜 로봇으로
`issueApproach` 를 실제로 태웠다).

### `payload` 키는 같다

```
commanded  라이브 {action,parameters,requestId,taskId}  ·  목 {action,parameters,requestId,taskId}  → 같다
answered   라이브 {answerKind,index,line,taskId}        ·  목 {answerKind,index,line,taskId}        → 같다
expired    라이브 (이 판에서는 안 남)                    ·  목 {reason,taskId,waitedMs}
```

`producedBy` 도 같다 — `commanded`=backend, `answered`=robot.

### 다른 곳 셋과 그 이유

**① `seq` 대역이 다르다 — 일부러 그렇게 했다.**
대본이 편 것은 `ACTION_SEQ_BASE`(1,500,000), 실제로 오간 것은 `LIVE_ACTION_SEQ_BASE`
(1,750,000)다. **시연 편을 로봇에 붙인 채 돌리면 두 재생기가 동시에 흐를 수 있다.** 한
대역을 나눠 쓰면 둘째로 도착한 쪽이 `TraceStore` 에서 중복으로 취급돼 **조용히 사라진다** —
하필 실제로 오간 쪽이 사라질 수 있다. 사람·AI 대역을 가른 것과 같은 이유다.

**② 라이브에 `scan_mission` 이 없다.** 이 판이 `issueApproach`(회전·직진·도착 정지)만
태웠기 때문이다. 스캔은 `issueScan` 이 내는 별도 경로다. 대본 쪽에 4건, 라이브 쪽에
3건인 것이 그 차이다.

**③ 라이브에 `expired` 가 없다.** 가짜 로봇이 **모든 명령에 답했기** 때문이다. 기한
사건은 답이 안 올 때만 난다 — 없는 것이 정상이고, 있으면 그게 결함이다.

### 접은 결과

```
 라이브                                          목
 cmd-00000001 T-B2 turn         done   답2      AI-0909-A3-1 T-A3 scan_mission done   답5
 cmd-00000002 T-B2 move_forward done   답2      AI-0909-B2-1 T-B2 turn         done   답2
 cmd-00000003 T-B3 abort        done   답2      AI-0909-B2-2 T-B2 move_forward done   답3
                                                AI-0909-B3-1 T-B3 abort        issued 답0 기한=true
```

**같은 태스크에 같은 명령 이름이 같은 순서로 붙는다.** `T-B2` 가 명령 둘(회전·직진)을
내고 `T-B3` 이 `abort` 를 내는 모양이 양쪽에서 같다 — 목 대본을 라이브가 실제로 내는
명령에 맞춰 썼기 때문이고, 그래서 이 대조가 뜻이 있다.

### 통합 빌드와 단독 빌드도 대조했다

같은 편을 게이트웨이로 한 번, 로컬 재생기로 한 번 돌렸다.

```
게이트웨이 (통합)   trace_event 69건 · 액션 층 15건 · layer=action_item · 대역=script
로컬 재생기 (단독)  열 69건       · 액션 층 15건 ·                        대역=script
```

**숫자도 대역도 같다.** 펴는 규칙이 `actionItemEvents()` 하나이기 때문이다 — 두 벌이면
두 빌드의 되감기가 갈리고 그것이 곧 측정축 D 의 오염이다.

되감기도 양쪽에서 같다 — T+31 에서 둘 다 `AI-0909-A3-1`(done·답5)과
`AI-0909-B2-1`(running·답1) 둘만 보인다.

### `?lang=en`

목의 로봇 줄이 영어로 바뀐다.

```
ko: 수락 | 촬영 뒤 대기 · 촬영 1 | 촬영 뒤 대기 · 촬영 3 | 촬영 뒤 대기 · 촬영 8
en: Accepted | Hold after the shot · shot 1 | Hold after the shot · shot 3 | …
```

`events[].payload.line` 을 `PAYLOAD_FIELDS` 에 더하고, 대본의 두 자리
(`tasks[].actionItems[].command.answers[].text` · `…command.expired.reason`)를
`DISPLAY_PATHS` 에 더했다. `verify:i18n-data` 가 빠진 것도 죽은 것도 0건으로 확인한다
(대본 6편 · 표시 문구 168개 · 보는 자리 20가지).

**실시간으로 받은 줄은 그대로 남는다** — 그것은 로봇이 준 값이지 우리가 쓴 문장이 아니다.
라이브 줄은 `uplinkWords()` 가 만들 때 이미 사전을 탄다.

## 5. 신설 검사 4종의 대조군이 **실제로 잡혔는지**

전부 잡혔다. 아래는 각 검사가 스스로 적은 줄이다.

| 검사 | 대조군 | 결과 |
|---|---|---|
| `verify:action-trace` | 열에서 `commanded` 를 지운 사본 · 실린 값을 계획값으로 바꾼 사본 · **`recordCommanded` 호출을 지운 `robotCommands.ts` 사본** | **3/3 검출** |
| `verify:fold-actions` | 액션 층이 빈 사본 · 기한을 `status` 에 섞은 사본 · 되감기를 무시하는 사본 · 액션 사건을 태스크로도 접는 사본 | **4/4 검출** |
| `verify:no-answer` | 기한을 안 보는 사본 · 응답을 안 보는 사본 · 기한을 `status` 에 섞은 사본 · 기한 사건을 버리는 사본 · 미래의 기한까지 읽는 사본 | **5/5 검출** |
| `verify:adjust-pair` | 후만 남긴 사본 · 조정을 백엔드가 한 것으로 적은 사본 · 조정을 접기에서 버리는 사본 · 계획값 조정을 안 내놓는 사본 · 미래의 조정까지 읽는 사본 | **5/5 검출** |

### 대조군을 짜면서 두 번 스스로 걸렸다

**①** `verify:fold-actions` 의 「액션 사건을 태스크로도 접는 사본」이 **처음에 안 잡혔다.**
조정을 T+20 에 넣고 T+30 에서 태스크 상태를 봤는데, T-B2 의 `started` 가 T+30 이라 그
사건이 조정을 덮어써 사본과 원본이 같은 값을 냈다. **T+25**(아직 안 시작한 시각)로
옮기니 잡혔다. 대조군이 안 잡히는 것을 보고서야 검사가 무의미했다는 것을 알았다.

**②** `verify:action-trace` 의 소스 사본이 **처음에 통과했다.** 기록 열은 덧붙이기
전용이라 앞 판의 명령이 그대로 남아 있는데, 가짜 로봇이 판마다 같은 `commandId`
(`cmd-00000001…`)를 써서 사본이 **앞 판의 기록을 보고** 통과했다. 사본 판에 다른 대역
(`mut-…`)을 주니 잡혔다.

둘 다 「대조군 없는 검사는 통과해도 아무것도 증명하지 않는다」가 그대로 일어난 자리다.

### 같은 커밋에서 고친 기존 검사 셋

「파일 하나를 고치면 그 파일을 보는 검사도 같은 커밋에서 고친다」를 지켰다.

| 검사 | 왜 깨졌나 | 어떻게 고쳤나 |
|---|---|---|
| `verify:replay` | 대조군 사본이 `src/data/.verify-*/` 안에 사는데 `fold.ts` 가 이웃 `actionTrace.ts` 를 끌어오게 돼 경로가 한 칸 깊어졌다 | **사본의 import 경로만** 올렸다. 원본은 안 건드렸다 |
| `verify:human-trace` | `produced_by=human` 정의 자리가 `data/trace.ts` 하나여야 하는데 `actionTrace.ts` 와 `robotCommands.ts` 둘이 늘었다 | `robotCommands.ts` 는 **코드를 고쳤다** — 「누가 눌렀나」(`issuedBy: 'human' \| 'mission'`)를 받고 값 변환은 정의 자리가 한다. `actionTrace.ts` 는 **층마다 정의 자리가 하나**라는 뜻으로 목록에 더했다. 이 목록 밖은 여전히 실패한다 |
| `verify:command-log` | 명령 표가 `commandsOfTask`/`logAtIndex` 를 읽는지 **이름으로** 보고 있었다 | 키를 새 읽는 자리로 바꾸고, **「작업대를 직접 읽으면 실패」를 새로 걸었다** — 빼는 것이 아니라 더한 것이다 |

`verify:sdk-bridge` 도 한 번 빨갰다. 브리지 명령(`sdk_start`)이 액션 사건을 만들었기
때문인데, 이것은 **검사가 옳았다** — 순서도에 자리가 없는 명령(`NO_NODE`)을 액션 층에
넣으면 어느 노드도 보여 줄 수 없는 외톨이 행이 된다. 검사를 고치지 않고 코드에서 걸렀다.

`npm run measure:representation` 은 그대로다 — 노드 수·합류·되돌아감을 건드리지 않았다
(§7.10 · 논문 §3-2 의 값과 여전히 일치).

### 배수가 ×1.05 인 이유 — **한 편만 채웠다**

지시서 §5 가 「`MSN-260909-01` 한 편만」이라고 못박았고 그대로 했다. 그 한 편만 보면

```
MSN-260909-01 의 사건 54 → 69 (×1.28)
```

이고, 전편을 같은 밀도로 채우면 합계는 **약 358건**이 된다(추정 — 편마다 명령 수가 달라
그대로는 안 된다).

### 축 가를 쓸 수 있는가 — **아직 판정이 안 선다**

이것이 이 작업의 마지막 관문이었는데, **솔직한 답은 「이 숫자로는 모른다」**다.

- 분모가 노드 24개에서 **사건 295건**으로 옮겨 간 것 자체는 얻었다. 「600줄을 40줄로
  줄였다」를 말하려면 600이 실재해야 하는데, 지금 한 편에서 명령 4건이 응답 10줄을
  달고 왔다 — **명령 하나에 줄이 2~5개 붙는 비율**이 그 600의 뼈대다
- 그러나 295는 **여섯 편의 합**이고, 실험 한 건이 보는 것은 **한 편**이다. 한 편의
  69건으로 「격리가 줄였다」를 말하기에는 작다
- 남은 다섯 편을 채우면 편당 ~60건이 ~80건이 되고, 그것도 600에는 한참 못 미친다

**600줄에 닿는 길은 대본이 아니라 라이브다.** 실제 로봇 한 판에서 `scan_mission` 하나가
회전 8걸음 × (수락·진행·촬영대기·풀림·종료)를 흘리므로 줄이 수십이 된다. 이번에 라이브
경로도 같은 열에 들어오게 해 뒀으니, **다음 측정은 대본이 아니라 실제 한 판을 재야 한다.**
그 숫자가 나오기 전에는 축 가를 쓸 수 있는지 판정하지 않는 것이 맞다.

## 7. 손 확인

브라우저로 눌러 본 것이 아니라 **같은 경로를 프로그램으로 돌려** 확인했다. 그 사실을
적어 둔다 — 화면을 눈으로 본 것은 아니다.

| 확인 | 방법 | 결과 |
|---|---|---|
| 되감기에 명령 표가 따라오는가 | `foldActions(31, …)` vs `foldActions(48, …)` | T+31 에 2건(답1·답5) · 끝에 4건. **따라온다** |
| 목으로 한 바퀴 | 로컬 재생기로 `MSN-260909-01` 완주 | 열 69건 · 액션 15건 · 머리 48.0 에서 정지 |
| 통합으로 한 바퀴 | 게이트웨이 부팅 → 발화 → 승인 → 재생 | `trace_event` 69건 · 액션 15건 · `layer=action_item` |
| 라이브와 목이 같은 모양인가 | §4 | `payload` 키·`produced_by` 동일. 다른 셋은 위에 이유를 적었다 |
| `?lang=en` 에 한국어가 새는가 | `translateEvents` 를 두 언어로 | 목의 로봇 줄이 영어로 바뀐다. `verify:no-raw-korean` · `verify:i18n-no-frozen` · `verify:i18n-data` 전부 초록 |

**남은 손 확인 하나** — 실제 로봇을 붙인 라이브 한 판에서 되감기를 해 보는 것. 이 기계에
로봇이 없어 못 했다. 가짜 로봇으로 같은 경로를 태웠지만 그것이 실물을 대신하지는 않는다.

## 8. 안 한 것

지시서 §6 과 2부 그대로다.

- **현황판 값 이관** — 260828 판단 유지
- **격리 알고리즘** — 이 작업이 그 재료를 만들었다. 구현은 다음 지시다
- **대본 전편 액션 아이템** — 한 편만
- **2부 전체** — 정지 확인 관문 · 값 조정을 재시작에 잇는 것 · `currentMission().params`
  를 입력칸이 덮어쓰게 하는 것. 하나도 안 했다
- **긴급정지 경로의 동작** — `abort` 발행도, 잠금 순서도, 2·3·4가 1의 결과를 안 보는
  뼈대도 한 줄도 안 바꿨다. **일지에 남기는 것만 더했다**(일시정지 명령과 그 답·기한).
  `verify:emergency-stop` 이 그것을 확인한다

로봇에 나가는 바이트는 한 줄도 안 바뀌었다. 기록은 전부 **이미 나간 뒤에, 또는 이미 받은
뒤에** 적는다.
