## 배경

Phase 2가 저장 축을 세우면서 관측은 일부러 비워 두었다 — 채널 본문 규격 6종에 신호 종류 힌트(`$comment`)만 달고
계측하지 않았다. Phase 3은 그 힌트를 실제 계측으로 바꾸고, Phase 0이 남긴 서버 관측 스택의 gap 4건을 정리한다.

딛고 선 것: 가동 중인 관측 5개(Collector·Prometheus·Loki·Tempo·Grafana), Phase 1의 토픽 규약·3채널, Phase 2의 본문
규격 6종과 `$comment` 힌트, `telemetry.lag_s`, pytest 104건 기준선, 그리고 설계 세션(2026-09-14)이 닫은 **착수 결정
7개**(systemd·Collector 파이프라인/포트·수집 주기와 보존·이름과 라벨·C층 파생 지점과 범위·엣지 2계층·traceparent).

**착수 시 가장 중요한 실측(§6-2):** 관측 3종 중 둘이 비어 있었다 — Collector 10일간 OTLP 수신 0건, Tempo 이력 전체
trace 0건, Loki 7개월간 로그 0건. 살아 있는 것은 Prometheus 하나였고 그 데이터는 전부 다른 파트 것이었다. 그래서 이
Phase의 판정은 "떠 있다"가 아니라 **"흐른다"**로 했다.

### 확정한 것 — 이 Phase가 굳힌 구조 결정

**① 관측 어댑터가 유일한 문이다.** `backend/observability.py`만 `opentelemetry`를 import 한다. `bridge.py`·`consumer.py`·
`ws_echo.py`·`tsdb_writer.py`·`registry.py`·`derive.py`는 `count`·`updown`·`gauge`·`observe`·`log_handler` 목적 인터페이스만
부른다(원칙 1). SDK가 없거나 `MK2_OTEL_ENDPOINT`가 비면 **no-op**이고 업무 경로는 그대로 돈다(제약 20).

**② 라벨 가드는 `ValueError`다 — 조용히 버리지 않는다.** 금지 7종(`session_id`·`internal_seq`·`sequence_id`·`timestamp`·
`ts`·`frame_id`·`capture_timestamp`) + A층에 `source_id`·`zone_id`·`entity_type`. 어댑터가 활성이든 no-op이든 똑같이 난다.

**③ 두 층의 라벨 기준이 다르다.** A층(`component`·`channel`·`outcome`·`stage`, 장치 식별 없음)과 C층(`source_id`·`zone_id`·
`entity_type`·`channel`). `service.name`은 Prometheus에서 `exported_job`(`mk2/be-ingest`)으로 밀려나므로 **컴포넌트 구분은
`component` 라벨**로 한다.

**④ C층 대상은 규격에서 읽는다.** `contracts.observation_hints()`가 `$comment`를 `properties` 재귀로 훑어 27곳 → 22개.
계기 이름은 `be.telemetry.<경로>`이고 **`state.analysis` 규격의 항목만** `analysis.` 접두사. **counter 힌트 3개는 gauge 계기**
(절대 누적값). `null`·`{value:null}`·부재는 시계열을 만들지 않는다. 파생 지점은 저장 소비자, 저장 성공과 무관, 예외 삼킴.

**⑤ Collector가 분배하고 호스트 포트는 그대로다.** `traces`→`otlp_grpc` `tempo:4317`, `logs`→`otlp_http` `http://loki:3100/otlp`
(도커 망). `127.0.0.1:4316` 무변경. 이미지 digest 고정. 컴포넌트 유무는 **`validate`로** 판정.

**⑥ 집약 계층 경계 표기(BE-S-06) = `agg_layer="edge"`.** 엣지 `external_labels`가 붙이고 중앙 `honor_labels`가 보존한다.
**부재 = 중앙 원본.** 중앙 `global.external_labels`는 건드리지 않는다.

**⑦ 상주 3개는 systemd이고 소비자는 SIGTERM에 그룹을 떠난다.** `Restart=on-failure`·`StartLimitBurst=3/60s`·
`EnvironmentFile=/home/dg/capstone-db/.env`. `.env` 파서가 셋(셸·compose·systemd)이 됐다.

**⑧ `be.pipeline.lag`가 BE-S-07의 측정 수단이다.** 값의 출처는 `TelemetryRecord.lag_s`(새로 계산하지 않음), 버킷
`0.1…86400`. **음수는 절대값 + `outcome=clock_skew`**(사용자 결정 안 A — 아래 「발견한 것 ⑦」).

## 작업 중 발견한 것

### ① C층 counter 힌트 3개는 gauge 계기로 냈다 (`$comment`와 계기 종류가 다르다)

`buffer.dropped`·`buffer.thinned`·`publish_failures`는 말단이 보내는 **절대 누적값**이다. 델타를 만들려면 직전 값을
들고 있어야 하는데 그건 Phase 2의 무상태 원칙과 충돌한다. gauge로 절대값을 기록하고 `_total`을 붙이지 않았다 —
증가분은 조회에서 `delta()`/`deriv()`. `contracts/common/README.md` 표에 처리 열로 적었다.

### ② `components` 목록이 정식명+별칭 쌍 4개를 빠뜨린다 — 유무는 `validate`로

설계 세션 실측 그대로였다: `otlp`/`otlp_grpc`·`otlphttp`/`otlp_http`·`azureblob`/`azure_blob`·`googlecloudstorage`/
`google_cloud_storage`. 이번 Phase의 모든 Collector 설정은 적용 전 `validate`(exit=0)로 판정했고 README §5-0에 규칙으로 적었다.

### ③ 재기동마다 retained `status`가 A층 카운터에 잡힌다

ingest 재기동 직후 `be_ingest_received_total{channel="status"}`가 retained 건수만큼 튄다. 단계 1 시점 **3건**(wl-001,
reg-a zoneA, reg-a zoneB)이었고, 단계 7의 타입별 `status` 발행 뒤 **6건**(robot·actuator·analysis wl-001 추가)이 됐다.
정상이며 구분 라벨은 달지 않았다. `lag_s` ≈ 434,000초라 히스토그램 `+Inf` 버킷에 들어간다.

### ④ SIGTERM에 `consumer.close()`가 안 불려 재기동 후 45~78초 파티션 미할당 (고쳤다)

`systemctl restart`는 SIGTERM인데 `consumer.py`는 SIGINT만 잡았다 → 파이썬 즉시 종료 → LeaveGroup 없음 → 코디네이터가
죽은 멤버를 `session.timeout.ms`(45초)까지 유지 → 새 인스턴스가 파티션을 못 받는다. 실측: 재기동 5초 뒤 describe에
`CONSUMER-ID -`, 발행분은 78초 뒤 저장. 단계 6 DoD 6이 이 때문에 처음 `489 → 489`로 나왔다. SIGTERM/SIGINT 핸들러로
`_STOP` 이벤트를 세우고 `finally`에서 `close()` → 6초 만에 할당. `ws_echo.py`는 메인 태스크 취소로 같은 효과.
**`kill -9`·OOM에는 효과가 없다**(Kafka 설계상 정상).

### ⑤ 전달 콜백은 `poll()`에서만 처리된다 — `be.kafka.produce`가 1건 늦었다 (고쳤다)

`produce()` 직후 `poll(0)`은 아직 ack가 안 와 **직전 메시지**의 콜백만 처리한다. 실측 `received 28 / produce 27`. 조용한
파이프라인에서는 마지막 건(특히 실패)이 다음 메시지까지 무기한 미뤄진다. 1초 주기 `poll(1.0)` 데몬 스레드를 두어
해소(`received 2 == produce 2`).

### ⑥ 테스트가 counter 절대값을 읽어 재기동 직후 헛되이 실패했다 (고쳤다)

Collector exporter가 옛 프로세스의 마지막 값을 5분간 계속 내보내므로 재기동 직후 `before`는 옛 값, `after`는 새 값(작다).
지시서 6-4-a의 경고 그대로다. `counter_delta()`(after < before면 after 자체가 증가분 — `rate()` 규칙)로 바꿨다.

### ⑦ OTel 히스토그램은 음수를 받지 않는다 (규격)

SDK `Histogram.record()`가 `amount < 0`이면 경고 후 반환(소스 확인). 지시서 6-3의 "음수 그대로"는 이행 불가 → 표 제시 →
사용자 결정 안 A. 어댑터 `observe()`는 음수를 SDK에 넘기지 않고 한 번만 경고한다.

### ⑧ C층 계기 이름 버그 — `analysis.` 접두사를 타입만 보고 붙였다 (서버 실측으로 잡아 고쳤다)

첫 실발행에서 `be_telemetry_*`가 17종 — `be_telemetry_analysis_{uptime_s,buffer_*,publish_failures}` 5종이 잘못 생겼다.
`status`는 타입 공통 규격이라 이름에 타입이 들어가면 안 된다(타입은 라벨). `instrument_name(channel, entity_type, path)`로
고치고 회귀 테스트 2개(`status`는 타입 무관 이름·4타입×3채널 합집합 = 12)를 더했다. 잘못된 5종은 Prometheus에 stale
표본으로 보존 기간(15d)까지 남지만 갱신되지 않는다 — 판정은 이름 색인이 아니라 **살아 있는 시계열**(instant query)로.

### ⑨ Loki "흘리기 전에 걸어야 한다"는 틀렸다 (소급 정정)

retention은 compactor가 나이 기준으로 **소급 집행**한다. 정확한 서술은 "보존을 집행할 기능 세 줄이 함께 꺼져 있었다".
그리고 v11/boltdb-shipper는 네이티브 OTLP 수집을 지원하지 않아 Collector→Loki 경로가 애초에 성립하지 않았다(Phase 0
README의 "동작에 문제 없다"는 틀렸다). plan·README에 정정했다.

### ⑩ `LoggingHandler`가 SDK 1.44에서 deprecated다

pytest 경고 2건: *"Use the handler from `opentelemetry-instrumentation-logging` instead."* 동작엔 영향 없다. Phase 4 이월
(패키지 1개 교체). 로그 SDK 모듈 경로는 아직 `opentelemetry.sdk._logs`(밑줄)이고 `opentelemetry.sdk.logs`는 없다(1.44.0 실측).

### ⑪ C층 gauge는 값이 흐를 때만 존재한다

OTel SDK의 last-value 집계는 새 측정이 있을 때만 데이터 포인트를 내고, Collector exporter는 5분 갱신이 없으면 `/metrics`에서
내리며, Prometheus가 stale 처리한다. "장치가 안 보내면 시계열도 없다" — 대시보드에서 빈칸은 곧 침묵이다. 12종을 한 화면에
보려면 한 창(5분) 안에 전부 발행해야 했다.

### ⑫ 기타 (조치 불필요)

- 로컬 `infra/config/` 사본 3개의 md5가 서버와 바이트 단위로 같았다 — Phase 2 이후 서버 설정에 손댄 사람이 없었다.
- `.env` 159바이트 = `KEY=value\n` 3줄 정확히 — `export`·따옴표 없음. systemd `EnvironmentFile`이 그대로 읽는다.
- `docker compose up -d otel-collector`는 `depends_on: prometheus`가 있어도 prometheus를 **재생성하지 않는다**(`Running 0.0s`).
- Tempo·Loki의 `/ready`는 준비 뒤에도 15초를 더 기다린다(`min_ready_duration`) — 기동 직후 `not ready`는 정상.
- 컴퓨터(Python 3.12)와 서버(3.14)의 OTel 패키지 버전이 동일했다(1.44.0, grpcio 1.84.0).
- `tailscale ping`은 첫 시도 DERP(tok, 72ms)였다가 다음 시도에 직접 경로(3ms)가 잡혔다. Windows 방화벽 규칙 없이는 서버에서
  엣지 `/-/healthy`가 안 됐을 것이다(규칙을 먼저 만들어 확인 못 함 — 지시서 8-5-a 예방 순서대로).
- Phase 2 보고서의 "컴퓨터 28 skip"은 사용자 기억과 다르다(컴퓨터에서 pytest를 돌린 적이 없다고 함). 이번에 처음으로
  컴퓨터 venv에 pytest를 깔았다.

## 검증 범위의 한계 — "검증됨"으로 적지 않은 것

1. **엣지는 컴퓨터 대역이다.** 전용 엣지 장비·현장 회선·다구역은 검증되지 않았다. Tailscale 직접 경로가 잡혔지만 그것도
   연구실 공유기 뒤의 컴퓨터다. 엣지 OTLP 수신단(서버 4316 Tailscale 바인딩)에는 **인증·TLS가 없다**(BE-T-08, Phase 4).
2. **B층은 가짜 지표 발신이다.** 실 말단은 `HW_OTEL_ENDPOINT`가 꺼져 있다. `tests/edge_probe_publisher.py`가 HW `otel_metrics.py`의
   이름·resource를 흉내 냈을 뿐이고, HW의 실제 span은 한 건도 받지 못했다(스냅샷 `260909`에 `begin()` 호출부가 없다 — §7-3).
3. **`state.analysis` C층 3종은 생산자가 없어 실값이 없다.** 증강 분석이 돌지 않는다. 가짜 발행자 값(2.87 / 0.0412 / 3.2)으로만.
4. **백엔드 span은 가짜 1건이다**(pytest가 `be-test-span-*`로 Collector→Tempo 경로만). 실제 추적 생산은 Phase 6.
5. **Tailscale은 팀 공용 계정**이고 서버·컴퓨터 둘 다 그 계정으로 붙어 있다. 같은 tailnet에 팀 장비(pi1·pi7·다른 데스크톱)가
   있어, 되살릴 때 ufw는 반드시 엣지 IP `/32`로 제한한다.
