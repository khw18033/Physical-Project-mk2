## 이번 작업의 핵심 설계 판단 — 명령 출구를 어떻게 합쳤나

### 방향이 반대였다

반사적으로는 "포팅한 `commands.ts` 를 `issueCommand()` 로 바꾼다"가 떠오른다. 두 코드를 놓고 보면 반대다.

| | `shared/commandEgress.ts` (탭①) | `data/commands.ts` 의 `CommandTracker` (대시보드) |
|---|---|---|
| 크기 | 25줄 | 374줄 |
| 하는 일 | 요청 조립 + 발행 + 실패 알림 | **4단계 추적**(발행→ACK→진행→완료) · **상관 키 매핑** · **만료 처리** · 늦은 응답 무시 · 보류 이벤트 흡수 |
| 근거 | — | `VZ-O-01`·`O-02`·`O-03`·`O-05` |

**`CommandTracker` 가 본체가 되고 `issueCommand()` 가 그 위의 껍데기로 접혔다.**
반대로 했으면 `VZ-O-02`(4단계 추적)와 `VZ-O-03`(감사)이 통째로 사라진다.
탭①의 출구가 단순했던 것은 잘 설계돼서가 아니라 **받을 화면이 탭① 하나뿐이었기 때문**이다.

### 호출부는 정말 안 바뀌었는가 — 그렇다

`issueCommand()` 호출부는 네 곳이고 **한 줄도 바뀌지 않았다.**

| 파일 | 호출 | 바뀐 것 |
|---|---|---|
| `shell/AppShell.tsx` | `issueCommand({ action: 'mission_pause' })` 외 2건 | 없음 |
| `views/ActionModal.tsx` | `issueCommand({ action: kind, entity, params })` | 없음 |
| `views/UtterancePanel.tsx` | `issueCommand({ …, inputModality: 'voice', voice })` | 없음 |

반환 타입만 `CommandAck` → `TrackedCommand` 로 바뀌었는데, 세 곳 다 반환값의 필드를 읽지 않아
(`void issueCommand(...)` 또는 `await` 후 자체 문구 표시) 호출 코드가 그대로 성립했다.

`CommandTracker.issue()` 에서 고친 곳은 **두 줄**이다.

1. `params` — 원본은 `{ target_pct }` 만 보냈다(액추에이터 명령만 받으면 됐으므로).
   임무 제어와 발화 발행은 `target_pct` 가 없다. **주지 않으면 원본과 완전히 같은 본문**이
   되도록 `options.params ?? { target_pct: spec.targetPct }` 로 뒀다 — 탭③의 호출부도 안 바뀌었다.
2. `voice` — 음성 감사 필드를 `buildAuditPayload()` 로 넘긴다. 이름을 붙이는 일은 여전히
   `auditFieldMap` 안에서만 일어난다.

카탈로그에 없는 명령(임무 제어·발화)에는 `commandEgress.ts` 가 최소 `ActionSpec` 을 만들어
**같은 입구**로 보낸다. 추적기에 두 번째 입구를 내면 그 순간 출구가 둘이 된다.

### 음성 감사 필드가 `auditFieldMap` 에 어떻게 합류했는가

두 벌이었다.

| | 어휘 | 출처 |
|---|---|---|
| STT 이식 때 만든 것 | `produced_by` · `input_modality` · `voice{…}` | `shared/voiceAudit.ts` |
| 대시보드가 쓰던 것 | `input_mode` · `decision_source` | `data/auditFieldMap.ts` |

**`auditFieldMap` 쪽 어휘를 남겼다.** 이유는 셋이다.

1. 그 파일의 목적이 **"감사 필드 이름을 한 파일에 가둔다"** 이다. 음성만 다른 파일에서 이름을
   만들면 그 목적이 깨지고, 백엔드가 철자를 확정하는 날 두 곳을 고쳐야 한다.
2. `input_mode` × `decision_source` 는 **입력 수단과 판단 주체를 두 축으로 나눈 것**이라
   한 축짜리 `produced_by` 보다 담는 것이 많다. "음성으로 말했고 LLM이 해석했다"를
   `produced_by` 하나로는 표현할 수 없다 — 그 분리를 백엔드에 요청해 둔 상태이기도 하다.
3. `REQ-1305` 의 문구가 `voice.transcript` 이므로 **중첩 `voice` 객체는 그대로 남긴다.**

역할이 이렇게 갈렸다.

```
voiceAudit.ts      검사만 한다      — 발행 전에 막는 자리
auditFieldMap.ts   이름을 붙인다    — 감사 필드 이름을 가두는 자리
```

`voiceAudit.buildAudit()` 은 이제 이름 붙은 payload가 아니라 `{ inputMode, voice? }` 를 돌려주고,
`CommandTracker` 가 그것을 `buildAuditPayload()` 로 넘긴다. **가드는 그 자리에 그대로 있다.**

`verify:voice-audit` 도 두 단계를 다 본다 — 가드가 거부하는지(키 8개 각각을 뺀 대조군),
`buildAuditPayload` 를 거친 뒤에도 **세 수치가 각각 살아 있는지**, 화면 표시행이 그 이름을
실제로 읽는지(`전사(원문)`·`STT 엔진`·`녹음`), 그리고 가드를 지운 사본이 잡히는지까지.

## 두 상태 모델을 어떻게 공존시켰나

**합치지 않았다. 저장소만 둘이고 transport 는 하나다.**

| | `TraceStore` (탭①) | `DataStore` (탭②~⑥) |
|---|---|---|
| 담는 것 | **일어난 일의 열.** seq 순서로 덧붙이기만 | **채널별 최신값.** 같은 키가 오면 덮어씀 |
| 지우는가 | 안 지운다. 실패해도 남는다 | 덮어쓴다 |
| 왜 이 형태여야 하나 | 되감기는 "그 시점의 값"이 아니라 **"그때까지 일어난 일을 접은 결과"** 다 | 구역 현황판은 지금 값만 필요하고, 열을 매번 접으면 20 Hz 수신에서 렌더 예산을 넘긴다 |

착수 전 판단(기술스택 §3-2)은 **`store.ts` 를 기록 열로 개조해서 가져온다**였는데, 그게 틀렸다.
하나로 합치면 둘 중 하나가 반드시 손해를 본다.

`shared/stores/latestValueStore.ts` 스텁(탭이 없을 때 추측으로 만든 자리)은 **지웠다.**
실물인 `DataStore`(264줄)가 들어왔으므로 두 벌로 둘 이유가 없다. 그 자리의 설명은
`traceStore.ts` 의 주석으로 옮겼다 — 왜 둘인지가 코드 옆에 있어야 다음 사람이 합치지 않는다.

## 목 게이트웨이를 어떻게 합쳤나 — 가장 크고 가장 놓치기 쉬웠던 일

| | 통합 전 viz | web-dashboard |
|---|---|---|
| 크기 | **10줄** (`gateway/server.mjs`) | **4,757줄** (12파일) |
| 내보내는 것 | `trace_event` 하나 | 장치·제어·계획·영상·지표·파이프라인·레지스트리·시나리오 |
| 포트 | 8790 | 8787 |

**명령 출구와 같은 방향으로 합쳤다 — 큰 쪽이 본체, 작은 쪽이 접힌다.**
`mock-gateway/` 12파일을 `viz-debugger/gateway/` 로 옮기고, **10줄짜리 시나리오 재생을
그 안의 `trace_event` 채널 하나로 접었다**(`gateway/mission-trace.ts`).
반대로 했으면 4,757줄을 다시 짜게 된다.

### 시나리오 재생을 어느 채널로 접었나

`protocol.ts` 의 `Channel` 에 `trace_event` 를 더하고, `config.ts` 의 `CACHE_POLICY` 에
**캐시 금지**로 등록했다. 사유는 이렇게 적었다 — *"기록은 열이라 마지막 한 건만 재생하면
순서가 끊긴 조각이 된다. 되감기는 열 전체를 접어야 성립한다."*

접으면서 원본과 달라진 것 둘.

1. **엔벨로프를 직접 만들지 않고 `hub.publish()` 를 거친다.** seq·ts·quality·scope·
   coordinate_frame 을 붙이는 규칙이 허브 안에 하나 있는데, 밖에서 또 만들면 두 벌이 된다.
2. **`node` 축이 태스크 id 가 아니라 `mission-trace` 고정이다.** 옛 구현은 봉투의 `node` 에
   태스크 id 를 넣었는데, 허브의 node 축은 **레지스트리의 노드**를 가리키는 자리라 거기에
   태스크 id 를 넣으면 zone 매칭이 엉킨다. 태스크 id 는 payload 의 `node_id` 에 그대로 있고,
   그것이 `contracts/trace-event.schema.json` 의 필드 이름이기도 하다.

임무는 `hub.runtime` 에만 등록하고 **`/registry` 응답에는 넣지 않았다.** 넣으면 탭②의
구역 현황판에 임무가 장비처럼 한 칸 뜬다. 임무는 장비가 아니다.

### `registry.json` 은 정말 참조만 했는가 — 그렇다

`hub.ts` 와 `server.ts` 의 `join(HERE, 'registry.json')` 을 `join(REGISTRY_DIR, 'registry.json')` 으로
바꾸고, `REGISTRY_DIR` 을 `web-dashboard/mock-gateway/` 로 뒀다(`VIZ_REGISTRY_DIR` 로 변경 가능).
**복사본은 없다.** 이유가 하나 더 있다 — `stt/vocab.py` 가 같은 파일을 읽어 hotwords 를 만들므로
(`REQ-305`) 두 벌이 되면 **화면의 장치 목록과 음성 인식 어휘가 조용히 갈라진다.**

기동 로그의 `등록 대상 10개` 가 web-dashboard 의 registry.json 을 읽었다는 증거다.

### 확인 방법을 스크립트로 남겼다

`verify:one-gateway` 를 새로 만들었다. **"빌드가 된다"가 아니라 "데이터가 실제로 온다"** 를 본다.

```
✅ 게이트웨이 1개 · 연결 1개로 탭별 채널
   state · actuator_state · control_lock · telemetry · video_meta · trace_event 수신,
   파이프라인 카탈로그 동일 출처, 재연결 후 구독·스냅샷 복원, 미발행 채널 대조군 확인
```

대조군은 **`command_result`** 다. 명령을 내지 않았으므로 와서는 안 되는 채널이고
(캐시 금지 채널이기도 하다), 아무거나 통과시키는 검사라면 이것도 "봤다"로 잡힌다.

이 스크립트는 게이트웨이를 **직접 띄웠다가 끈다**(전용 포트 8795). 이미 떠 있는 것에 붙으면
남아 있던 프로세스가 다른 버전일 때 조용히 통과한다. 같은 이유로 `verify:transport` 도
전용 포트(8796)로 자기 게이트웨이를 띄우도록 고쳤다 — 개발 서버가 8790 을 잡고 있어도 성립해야 한다.

| 자체 관측 (`VZ-O-04`) | **공유 계층** | `startDataLayer()` 가 `selfObservability` 를 기동한다. 셸이 한 번만 부른다 |

AI 실패를 알림으로 올린 이유: 구 화면에서는 그 탭 안 상자에 쌓였는데, 통합 앱에서는
**탭을 보고 있지 않을 때도 알아야 하는 것**이다. 탭 여섯 중 하나에만 뜨면 다섯 번 중 다섯 번을 놓친다.

## 요구사항정의서 §3.1과 어긋난 지점 — 문서를 고쳤다

문서가 코드를 따라간다는 규칙대로 §3.1 을 고쳤다. 어긋난 곳은 둘이다.

### 1. 「노드 그래프 → 모드별 분할, 임무 관제 모드 → 탭①」

**하지 않았다.** 임무 관제 모드를 가져오면 탭①과 같은 화면이 둘이 된다.
지시서 제약 7도 같은 판단이고, 탭①이 이미 3계층 그래프·8상태·DAG를 갖고 있다.
→ §3.1 표를 "파이프라인 모드만 ⑥으로. 임무 관제 모드는 지웠다"로 고쳤다.

### 2. 「`VZ-U-03` 계층 뷰 → 탭①」

**탭②에 남겼다.** 탭①의 표시 깊이 설계는 **HCI 논의 미결**이다(전달본 논의 항목 5
「사용자 계층별 표시 깊이 — 비전문가에게 무엇을 감출 것인가」). 지금 옮기면 탭①의 화면이
바뀌고, 그건 지시서 제약 10(1단계 결과물을 깨지 않는다)에 걸린다.
→ §3.1 에 사유와 함께 적고, "다음 개정 때 배치표를 한 번 더 맞춰야 한다"고 남겼다.

## 막힌 것 — 임의로 정하지 않고 남긴다

### 레지스트리 원천이 둘이고, 두 목 데이터가 다른 세계다

지시서는 "탭①과 탭②가 같은 원천을 봐야 하므로 `shared/registry.ts` 를 실제로 배선한다"고 했다.
**배선은 했지만 합류는 못 했다.**

| | 탭① | 탭②~⑥ |
|---|---|---|
| 원천 | `scenarios/MSN-260826-01.json` (번들 내장) | 게이트웨이 `/registry` = `web-dashboard/mock-gateway/registry.json` |
| 담긴 것 | `go1-02`(Unitree Go1) · `arm-03`(매니퓰레이터) · `cam-4f` · `drone-01` … | `robot-01` · `sensor-04`(수위 센서) · `actuator-01`(수문) · `edge-node-a` … |
| 이야기 | 415동 → 503동 **건물 간 이동** | zone-503 **수문·수위 관제** |

**겹치는 대상이 하나도 없다.** 합치려면 임무 시나리오를 registry.json 위에 다시 쓰거나
그 반대인데, 둘 다 이식의 범위를 넘고 **탭①의 HCI 전달본을 바꾸는 일**이다.

이번에 한 것은 접근 지점을 하나로 모은 것까지다 — `main.tsx` 가 `scenario.hardware` 를
직접 읽던 세 곳을 `listRegisteredHardware()` 로 바꿨고, 화면에 원천 표시(`hardwareSourceLabel()`)를
붙였다. **합칠 때 고쳐야 할 곳이 이제 파일 하나다.**

정해야 하는 것: **목 데이터를 하나의 이야기로 통일할 것인가, 두 세계를 유지할 것인가.**
시연에서 탭①과 탭②의 장비 목록이 다르면 "이 둘이 같은 시스템이냐"는 질문이 다시 나온다.

### `utterance.confidence` 계약 (이월)

STT 보고서에 적은 그대로 미결이다. `VZ-G-01` 이 임무 객체를 만드는 순간 필요하다.
이번 작업은 그 결정과 무관해서 진행할 수 있었다.

## 46건 중 화면에 닿지 않는 것이 남았는가

이식의 목적이 "하나도 죽지 않는다"였으므로 확인했다.

| 배치 | 건수 | 상태 |
|---|---|---|
| 공유 계층 | 16 | **전부 살아 있다.** 전송·구독·레지스트리·명령 4단계·권한·표기·자체 관측·기동·상단 알림 |
| 탭② ~ ⑤ | 7 | **전부 화면에 있다** (`verify:one-gateway` 로 데이터 수신까지 확인) |
| 탭⑥ (동결) | 2 | **화면에 있다.** `동결 — 유지만 함` 표시를 붙였고 기능을 늘리지 않았다 |
| 탭① | 18 | 디버깅 8 · 음성 3 · `VZ-U-07` = **12건 동작.** 생성 `VZ-G-01`~`05` 5건은 로컬 LLM 미착수, `VZ-U-03` 은 탭②에 있음 |
| Unity 트윈 (`VZ-U-02`) | 1 | 별도 앱. 이번 범위 밖 |
| 탭①이 대체 (`VZ-U-05`) | 1 | **화면에 있다.** `PlanApproval` 의 구간 진행판을 버리지 않고 같이 들여왔다 |
| 보류 (`VZ-U-06`) | 1 | 미구현 (원래 보류) |

**화면에 닿지 않는 것은 `VZ-G-01`~`05`(로컬 LLM 미착수)와 `VZ-U-06`(보류)뿐**이고,
둘 다 이식이 아니라 신규 구현 대기다. 이식으로 죽은 요구사항은 없다.
