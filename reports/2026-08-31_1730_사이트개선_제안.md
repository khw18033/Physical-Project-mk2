## 0. 네 건이 사실은 한 문제다

지금 화면은 **모드가 세 군데에 흩어져 있고, 그 사실을 글로 설명하고 있다.**

- 목 렌더는 우상단 토글, 대본 진입은 승인 시 자동, 대본 이탈은 배너 안 「대본 닫기」 — 세 곳(요구 4).
- 어느 모드인지 화면만 봐서는 모르니 배너와 문단으로 적는다 — 글이 불어난다(요구 1).
- 모드가 바뀌어도 탭②~⑤가 안 변하니 "연결 예정"만 남는다(요구 2).
- 탭①은 마일스톤당 노드가 하나라 모드를 바꿔도 볼 것이 없다(요구 3).

그래서 **순서는 4 → 2 → 3 → 1**을 권한다. 스위치를 먼저 만들면 나머지 셋을 화면에서 바로 확인할 수 있다.

## 요구 4 — 우상단 모드 표시·전환

### 지금

| 모드 | 진입 | 이탈 | 표시 |
|---|---|---|---|
| `placeholder` (일반) | 기본값 | — | 없음 |
| `mock` | 우상단 토글 | 같은 토글 | 붉은 띠 + 자리마다 배지 |

`renderMode.ts`의 상태 자체는 이미 3종이다. **모자란 것은 상태가 아니라 하나의 조작 지점이다.**

### 제안 — 세그먼트 컨트롤 하나

```
모드  [ 일반 ] [ 시나리오 ▾ ] [ 목·개발 ]        ← global-bar 우측
```

- **일반** — 현행 `placeholder`. 기본값은 그대로 둔다(`verify:placeholder-default` 유지).
- **시나리오 ▾** — 대본 3편 드롭다운. 고르면 `enterScenarioRender()` + 임무 저장소에 대본을 **정지 상태로** 적재한다. **재생하지 않는다.**
- **목·개발** — 현행 `mock`. 붉은 배지는 그대로(끄는 경로 없음).
- 승인으로 재생이 시작되면 세그먼트가 `시나리오 · 재생 중 MSN-260831-01`로 바뀌고 옆에 「대본 닫기」가 붙는다.

**VZ-U-07 승인 선은 안 무너진다.** 수동 진입은 "그린다"까지고, "재생한다"는 여전히 승인 뒤다.
`renderMode.ts`에 `playing: boolean` 한 필드만 붙이면 되고 `DEFAULT_MODE`는 안 건드린다.

배너 3종은 세그먼트가 상태를 말해 주므로 **한 줄로 줄인다**(목 배너의 경고 문구만 남긴다).

## 요구 2 — 탭②~⑤ 시나리오 연계

### 왜 지금 "연결 예정"만 나오나 (코드 근거)

1. **`entity`가 없는 자리는 scenario 분기 자체가 없다.** `PendingSource`는 `entity === undefined`면 무조건 자리표시로 떨어진다. 해당: `zone-summary` · `risk-state` · `audit-history` · `registry` · `role-scope` · `mission-history` · `hardware-pool-status` · `device-cards`(전체 자리).
2. **탭④는 구조적으로 못 그린다.** `METRIC_ENTITY = 'edge-node-a'`인데 세 대본 cast 어디에도 `edge-node-a`가 없다. 기본 선택 지표도 `cpu_pct`(원천 `edge-node-a`) — 그래서 **시나리오로 들어가도 탭④ 첫 화면이 자리표시**다.
3. **탭③은 대상이 고정이다.** `TARGETS = ['actuator-01','actuator-02']` — 1편·2편에는 그 장비가 없다.
4. **셋째 상태가 없다.** 지금 화면 상태는 「연결 예정(못 받았다)」와 「값 있음」 둘뿐이다. 시나리오에 진짜 필요한 셋째는 **「이 대본에는 해당 없음」**이다. `ZoneMapMini`가 이미 이걸 손으로 하고 있다(「이 대본에는 맵이 없습니다」).

### 제안 A — 「임시 데이터」의 정체를 대본 t=0 스냅샷으로 정의한다

지어내지 않는다. 대본 `worldTimeline`에 이미 `atSec: 0` 프레임이 있다
(1편: `robot-01` position·speed_mps·is_moving, `camera-02` in_view). 수동 진입 시 그 프레임을 그린다.
승인·재생이 시작되면 그때부터 시간축이 움직인다 — **같은 데이터의 정지 화면과 동영상**이지 별개의 목이 아니다.

### 제안 B — `PendingSource`에 셋째 상태를 정식으로 추가

| 상황 | 표시 |
|---|---|
| 일반 모드 | `연결 예정` (현행 4행 → 요구 1에서 한 줄로) |
| 시나리오 · cast 안 | `대본 — 합성 데이터` (현행) |
| 시나리오 · cast 밖 장비 | `이 대본에 없는 장비` |
| **시나리오 · 대본에 그 축이 없음** | **`이 대본에는 해당 없음` + 어느 편에서 보이는지** |

넷째 줄이 새로 만드는 것이다. 1편·2편의 탭③(수문 없음), 3편의 탭⑤(영상 없음)가 여기 해당한다.
**이 구분이 있어야 시연 중 "왜 여긴 비었냐"가 안 나온다.**

### 제안 C — 탭별로 고칠 곳

| 탭 | 고칠 것 |
|---|---|
| ② 구역 현황판 | `zone-summary`를 cast 기준 집계로(카드 4장 중 2장이 대본 장비 → 「대본 2 · 자리표시 2」). `risk-state`에 scenario 분기 신설 — 3편은 위험 수위 근거가 대본에 있다 |
| ③ 제어 패널 | `TARGETS`를 시나리오에서 대본 cast로 좁힌다. cast에 액추에이터가 없으면 「해당 없음」. 3편은 현행대로 `commands`가 실제 CommandEngine을 통과한다 |
| ④ 지표 조회 | **시나리오 진입 시 기본 지표를 대본 지표로 자동 전환** — 1편 `robot_speed_mps` · 2편 `coverage_pct` · 3편 `water_level_m`. 대본과 무관한 지표는 목록에서 흐리게. `metrics-push`(edge-node-a)는 「해당 없음」 |
| ⑤ 영상 오버레이 | `CAMERA='camera-02'`는 1·2편 cast에 있으므로 현행 경로로 동작한다. 3편은 「해당 없음」 |

## 요구 3 — 노드 분화

### 지금

세 대본 모두 **마일스톤 1개 = 태스크 1개**다. 그래서 마일스톤을 눌러도 그래프에 노드가 하나뿐이고,
DAG·트리 전환도 실패 경로 강조도 볼 것이 없다.

| 편 | 마일스톤 | 태스크 |
|---|---|---|
| 1편 | 7 | 7 |
| 2편 | 6 | 7 |
| 3편 | 4 | 4 |

### 분할 원칙 — 임의로 쪼개지 않는다

**노드 문법 5종**을 정하고, 마일스톤을 이 문법의 작은 부분그래프로 편다.
"왜 이렇게 쪼갰나"에 답이 있어야 논문에서 방어된다.

| 종류 | 뜻 | 계약의 근거 |
|---|---|---|
| `sense` | 값을 받아 온다 | telemetry · coverage · vision 채널 |
| `decide` | 조건이 참인가 | `evaluation.judgedBy = backend` |
| `act` | 명령을 낸다 | `commands[]` · CommandEngine |
| `verify` | 구동 결과가 의도대로인가 | `evaluation.criteria` |
| `report` | 기록·발행 | trace_event · 감사 |

**사용자가 준 단계를 더하거나 빼지 않는다**(지시서 원칙 유지). 실패 분기도 지어 넣지 않는다.
분화는 **한 단계 안을 펴는 것**이지 단계를 늘리는 것이 아니다.

### 1편 MSN-260831-01 — 7 → 16 노드

| 마일스톤 | 현재 | 분화 |
|---|---|---|
| MS-A 출발점→문 앞 | T-11 | `T-11a` 경로 계획(decide) → `T-11b` 주행(act) → `T-11c` 문 앞 도착 판정(verify) |
| MS-B 문 열림 확인 | T-12 | `T-12a` 문 영역 관측(sense·camera-02) → `T-12b` 열림 판정(decide·ai) |
| MS-C 복도 진입 | T-13 | `T-13a` 진입 여유 확인(sense) → `T-13b` 진입 주행(act) |
| MS-D 엘리베이터까지 이동 | T-14 | `T-14a` 복도 경로 추종(act) → `T-14b` 위치 발행(sense) ∥ `T-14c` 카메라 시야 이탈 기록(sense·camera-02) |
| MS-E 3 m 이내 정지 | T-15 | `T-15a` 거리 계산(decide·backend) → `T-15b` 정지 구동(act) → `T-15c` 정지 확인(verify) |
| MS-F 도착 보고 | T-16 | `T-16a` 도착 스냅샷(sense) → `T-16b` 보고 발행(report) |
| MS-G 임무 종료 | T-17 | `T-17a` 자원 해제(act) → `T-17b` 요약 기록(report) |

MS-D의 `T-14c`가 이 편 유일한 병렬 가지다 — **지어낸 것이 아니라 `worldTimeline` 34s/44s의 `in_view` 변화가 근거다.**
`T-15a`가 `T-14b`·`T-14c`를 합류시킨다. 이걸로 이 편에도 분기·합류가 한 쌍 생긴다.

### 2편 MSN-260831-02 — 7 → 17 노드 (모양이 가장 풍부하다)

| 마일스톤 | 현재 | 분화 |
|---|---|---|
| MS-A 작동 확인 | T-21 | `T-21a` 하트비트·프레임 수신(sense) → `T-21b` 작동 판정(decide) |
| MS-B 사각지대 표시 | T-22 | `T-22a` FOV 투영(decide) → `T-22b` 미커버 칸 산출(decide) → `T-22c` 맵 칸 표시 발행(report) |
| MS-C 첫째 사각지대 | T-23 | `T-23a` 대상 칸 선택(decide) → `T-23b` 칸으로 이동(act) → `T-23c` 칸 스캔(sense) |
| MS-D 첫째 채움 | T-24 | `T-24a` 채움 판정(verify) → `T-24b` 커버리지 갱신(report) |
| MS-E 다음 사각지대 | T-25 | `T-25a` 남은 칸 확인(decide) → `T-25b` 이동(act) → `T-25c` 칸 스캔(sense) |

- **분기**: `T-22c` → `T-23a`(탐색 축) ∥ `T-27a`(감시 축).
- **합류**: `T-25a`가 `T-24b`와 `T-27c`를 함께 받는다 — "다음 칸" 후보가 *미탐색 칸*과 *경과 초과 칸* 둘이기 때문. **대본에 이미 있던 구조다.**
- ⚠️ `T-27c` → `T-23a` 되돌아가는 엣지는 **`deps`에 넣으면 안 된다.** `graph/layout.ts`의 `depths()`가 순환 보호 없이 재귀해 무한 루프에 빠진다. **점선 「참조 엣지」로 그리고 레이아웃·deps에서는 뺀다.**

### 3편 MSN-260831-03 — 4 → 15 노드 (가장 급하다)

| 마일스톤 | 현재 | 분화 |
|---|---|---|
| MS-A 대기 | T-41 | `T-41a` 수위 구독(sense) → `T-41b` 평시 판정(decide) |
| MS-B 30초 상승 → ON | T-42 | `T-42a` 상승 구간 누적(sense) → `T-42b` 30초 지속 판정(decide) → `T-42c` 프로세스 ON(act) |

이 편만 `commands[]`가 실제 CommandEngine을 통과한다. **명령 노드(`act`)와 검증 노드(`verify`)를 나눈 이유가 여기 있다** —
VZ-O-02 4단계 추적이 노드 사이 간격으로 화면에 드러난다.
지시서가 적어 둔 **배속(20×)과 실시간 개폐(6초)의 어긋남**도 `T-43c`↔`T-43e` 간격으로 눈에 보이게 된다 — 숨기지 않고 보이게 하는 쪽이 맞다.

`sensor-02`가 cast에 있는데 어느 태스크도 쓰지 않는다. 이중화 확인 노드를 넣을지는 **결정 필요**(지어내는 쪽에 가까워 넣지 않기를 권한다).

### 이벤트 재작성 규칙

`events[]`의 `nodeId`가 전부 바뀐다. **마일스톤의 시작·끝 시각은 보존한다** —
기존 이벤트의 첫 `started`와 마지막 `evaluated`를 각각 첫 노드·끝 노드에 그대로 주고,
사이 노드는 그 구간을 등분한다. 그러면 `statusesAt()`의 마일스톤 접기 결과가 안 바뀌고
**되감기 슬라이더 눈금과 탭②~⑤의 `worldTimeline` 정렬이 그대로다.**

`MSN-260826-01`(옛 편)은 **무수정** — HCI 전달본·논문용 예외.

## 요구 1 — 글이 너무 많음 / 설명서 탭

### 화면에 상주하는 글 목록

| 위치 | 양 | 처리 |
|---|---|---|
| `PendingSource` 4행(무엇/누가 보내나/우리 자리/경로) × 화면당 3~6곳 | **가장 크다** | 한 줄 칩으로 축약 + 팝오버 |
| `global-bar`의 안내 문단 2줄 | 상시 | 설명서 탭으로 |
| 탭별 부제 `board__sub` 5곳 | 상시 | 제목 옆 ⓘ 팝오버 |
| `note` / `note--dim` 문단 (현황판·지표·맵) | 상시 | 설명서 탭으로 |
| `devpanel` 개발 도구(시나리오 버튼·계약 확인·리렌더 카운터) | 상시 | 접이식, 기본 접힘 |
| 배너 3종 | 조건부 | 요구 4의 세그먼트가 대신한다 |

### 제안

**(a) `PendingSource` 기본형을 한 줄로.**
`연결 예정 · 구역 요약 ⓘ` — 4행은 hover 팝오버로 옮긴다.
`pendingSources.ts`(데이터)는 **한 글자도 안 건드린다.** 표현만 바꾼다.
`minHeight`는 유지 — "진짜 데이터가 오면 이 자리에 그대로 들어간다"는 원칙은 그대로다.

**(b) 탭 본문 = 제목 + 태그 + UI.** 설명 문단은 전부 ⓘ 뒤로.

**(c) 새 탭 「설명서」.** 내용 절반 이상을 **손으로 쓰지 않고 기존 데이터에서 생성**한다 — 그래야 문서가 코드와 어긋나지 않는다.

| 절 | 내용 | 출처 |
|---|---|---|
| §1 화면 5개가 무엇인가 | 탭당 1줄 | 손 |
| §2 모드 3종의 차이 | 일반/시나리오/목 | 손 |
| §3 **연결 예정 자리 전체 표** (15개 × 4행) | 자동 생성 | `pendingSources.ts` |
| §4 대본 3편 + 발화 문장 + cast | 자동 생성 | `scenarios/*.json` · `manifest.ts` |
| §5 요구사항 ID ↔ 화면 대응표 | 자동 생성 | 탭 `tag` + `pendingSources` |

**§3이 핵심이다.** 「못 만든 것이 아니라 못 받은 것」이라는 논거는 화면에서 걷어내는 것이 아니라
**한곳에 모으는 것**이다 — 오히려 15개가 한 표에 모이면 회의에서 "이건 누가 언제 주느냐"를 묻기 더 쉽다.

⚠️ 이 축약이 논문 측정축(자리표시 가시성)을 약화시키는지는 **지도교수 확인이 필요할 수 있다.** 결정 5 참고.
