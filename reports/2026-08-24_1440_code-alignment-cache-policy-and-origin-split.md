## 판단

### 1. 캐시 정책 — 타입 검사가 막게 만들었다

`hub.ts`의 `publish()`가 채널 구분 없이 `this.cache.set(key, env)` 했다. 고치는 방법은
여러 가지인데, **조건문 하나를 끼우는 것으로 끝내지 않았다.**

```ts
export const CACHE_POLICY: Record<Channel, CachePolicy> = { … };
```

`Record<Channel, …>`로 선언하면 **채널이 새로 생길 때 타입 검사가 막는다.** 조건문
방식이었다면 새 채널은 기본값(캐시함)으로 조용히 흘렀을 것이고, 그게 정확히 이번에
있었던 사고다. 같은 사고를 두 번 겪지 않는 방법은 "다음에 주의하기"가 아니라
**컴파일러가 물어보게 만드는 것**이다.

각 항목에 `why` 문자열을 함께 넣어 `/health`와 시나리오 출력에 그대로 실린다. 정책과
이유가 떨어져 있으면 반년 뒤에 "왜 이 채널은 캐시하지 않나"를 다시 논쟁한다.

### 2. 정책을 지키는지는 선언이 아니라 실물로 확인한다

`hub.cachedKeys()`를 열고 `/health`가 **정책 · 캐시 실물 · 위반 목록**을 함께 낸다.
`violations`가 비어 있지 않으면 그 자체가 버그라는 뜻이다.

그리고 `npm run verify:cache`(`scripts/verify-reconnect-cache.mjs`)를 새로 두었다.
**시나리오가 아니라 스크립트인 이유**가 있다 — 이 검증은 두 번 접속해야 성립한다.
첫 접속에서 영상 패널을 열어 `video_frame`·`detections`를 흘리고, 끊고 다시 붙었을 때
스냅샷에 그 채널이 섞이는지를 봐야 한다. **서버 안에서 도는 시나리오는 클라이언트
재접속을 재현할 수 없다.** 지금까지 이 버그를 못 본 이유가 정확히 여기에 있었다.

스냅샷과 실시간 발행을 **시간으로 가르면 안 된다** — 50ms 주기 로봇과 15fps 영상이
섞이면 어느 것이 캐시에서 온 것인지 알 수 없다. 서버가 캐시를 먼저 다 보내고 그
다음에 `subscribed`를 보내므로 경계는 **메시지 순서**다. 첫 판에서 시간으로 갈랐다가
40건이 20건으로 선언된 스냅샷에 섞여 들어와 오판했고, 순서 기준으로 고쳤다.

### 3. 검증 중 실제 버그를 하나 더 잡았다 — 영상 패널 누수

첫 검증에서 **접속 0인데 `vision.open`이 `true`** 였다. 브라우저가 탭을 닫을 때
`video:false`를 보낼 기회가 없고, `ws.on('close')`가 `openCount`를 되돌리지 않았다.
서버가 **아무도 안 보는 15fps를 영원히 발행하는 상태**로, `VZ-I-06`("열린 패널만
받는다")의 정반대다.

접속 스코프에 `openVideos` 집합을 두어 종료 시 회수하고, 같은 접속의 중복 `open`은
한 번만 센다 — 두 번 세면 close에서 다시 못 닫는다. 이 버그는 **캐시 검증을 하려다
발견됐다.** 재접속을 실제로 재현하지 않았으면 계속 못 봤을 것이다.

### 4. 인지 출처 — 필드를 나누는 것으로 끝나지 않는다

`HW-R-04`가 온디바이스를 최소 안전 판단으로 내리고 정밀 분류·추적을 엣지로 옮겼다.
`origin: { tier, kind, label, optional }`을 붙이는 것만으로는 부족하다 — **두 결과가
담을 수 있는 필드 자체가 다르다.**

| | 온디바이스 | 엣지 |
|---|---|---|
| `track_id` | **null** — 프레임 단위 판단이라 프레임을 넘어 대상을 잇지 못한다 | 있다 |
| `class_confidence` | **null** — 의미 분류를 하지 않는다 | 있다 |
| `approach` | `closing`/`steady`/`receding` — **거리가 아니라 방향** | null (궤적으로 표현) |
| `corridor` | 진행영역 | null |
| 지연 | 60ms — **엣지보다 빠르다** | 200ms |

`class_confidence`를 null로 둔 것이 핵심이다. 여기에 검출 신뢰도를 채워 넣으면 화면이
"분류를 안 하는 결과의 분류 신뢰도"를 그리게 되고, 그게 `HW-R-04`가 *"객체 의미 분류
하나에 안전 기능을 의존시키지 않는다"* 로 막으려는 것이다. 대신 화면은 분류 신뢰도가
없는 결과에 **검출 신뢰도로** 불확실 판정을 한다 — 분류 임계를 그대로 적용하면 온디바이스
결과가 전부 "불확실"이 된다.

온디바이스를 **엣지보다 빠르게**(60ms vs 200ms) 둔 것도 의도다. 안전 기능이 엣지 왕복을
기다리는 구조면 그건 이미 최소 안전 판단이 아니다.

### 5. 이름을 `origin`으로 하지 않았다 — `VZ-C-06`과 섞인다

`VZ-C-06`의 **원천 종류**(raw / simulated)와 이번 **인지 급**(device / edge)은 다른 축이다.
전자는 "실물인가 시뮬레이션인가", 후자는 "어느 급의 인지인가"다. 필드 이름을 `origin_kind`로
했으면 Unity 뷰어의 `OriginKindSpec`과 이름이 겹쳐 반년 뒤에 누군가 하나로 합친다.
`tier`·`kind`로 갈라 두고 두 파일 주석에 서로를 가리키게 적었다.

### 6. 연계 부재 — 두 가지 "없음"을 구분했다

`AI-S-02`가 선택 기능이 되면서 필요한 것은 필드 하나가 아니라 **구분**이다.

| | 뜻 | 화면 |
|---|---|---|
| `association: 'unavailable'` | 이 배치에 **연계 기능 자체가 없다** | "연계 없음 · 소스별 추적 유지" 안내 |
| `link: null` (기능은 있음) | 기능은 있으나 **이 대상을 못 묶었다** | 그 대상만 연계 신뢰도 없음 |

둘을 섞으면 화면이 "연계가 없는 배치"와 "연계에 실패한 대상"을 같게 그린다. 그리고
연계가 없을 때 **연계 신뢰도를 그리지 않는다** — 묶지 못했는데 신뢰도를 띄우면 없는
근거를 만드는 것이다. 추적 식별자에 소스를 붙이는 것(`camera-02:trk-01`)도 같은 이유로,
소스를 지우면 서로 다른 추적이 같은 id로 보인다.

### 7. 엣지가 없을 때 — 미결을 덮지 않고 화면에 남겼다

엣지 결과가 2초간 안 오면 화면이 "엣지 정밀 인지 결과 없음 · 온디바이스 최소 안전 판단만"을
띄운다. 값이 안 오는 것을 빈 화면으로 두면 관제사는 고장으로 읽는다.

**여기서 알 수 있는 것은 "안 온다"까지다.** 미배포(`AI-E-04` 선택 기능)인지 장애인지는
구분할 수 없다 — capability 상태(`DISABLED`/`DEGRADED`)를 가시화까지 전달하는 경로가
계약에 없다. 그럴듯한 추정으로 채우는 대신 **화면과 코드에 `[확인 요망]`으로 남겼다.**
없는 계약을 코드가 있는 것처럼 흉내 내면 회의에서 그 구멍이 안 보인다.

### 8. 왕복 지연 — 한 방향과 왕복을 갈랐다

`commandLatency.oneWayMs` 하나만 두고, **게이트웨이 ACK는 한 방향**(회신 한 겹),
**말단 응답은 두 방향**(하달 + 회신)을 겪게 했다. 두 값을 따로 두면 둘이 어긋나고,
하나만 두고 전부 같이 더하면 실제 경로 모양과 달라진다.

기본값은 0으로 뒀다 — 평소 시연 감각을 바꾸지 않고 시나리오로만 켠다.

### 클라이언트 정합 계산 — 브라우저 없이 확인

Node가 `.ts`를 그대로 읽으므로 `resolveAlignment`를 직접 호출해 잰 값이다.

```
정합 ON   출처 2개 · [device] maxLag 0.0px · [edge] maxLag 39.0px (박스 4개 · 소스 2개)
정합 OFF  출처 2개 · [device] maxLag 105.0px · [edge] maxLag 105.0px
```

- 정합 ON에서 엣지가 39px인 것은 **오차가 아니다** — 연계 OFF 상태의 두 번째 소스가
  26px 떨어져 보는 값이고 표시 배율 1.5를 곱하면 39px이다. 소스가 같은 대상을 다르게
  본다는 것이 숫자로 나온다.
- 정합 OFF의 105px = 7프레임 × 10px × 1.5. 계산과 일치한다.
- 온디바이스 박스는 `class_confidence` null 2건이고 **불확실 0건** — 분류 임계를 그대로
  적용하지 않고 검출 신뢰도로 판단한 결과다.
- 출처 표기 없는 결과를 투입하니 출처 2 → 2로 **변하지 않았다**. 조용히 device로
  취급하지 않는다.

### 신규

17. **`가시화_프로토타입_설명서.md`의 시나리오 목록이 낡았다.** 20건 기준으로 쓰여
    있는데 코드는 이제 31건이다(이번에 7건 추가, 그 전에도 늘어 있었다). `.md`와 `.pdf`가
    짝이라 재조판이 필요해 이번 코드 범위에서 손대지 않았다. **문서 정합 작업에 포함할 것.**

18. **엣지 부재 판정이 시간 기반 추정이다.** `EDGE_SILENCE_MS = 2000`으로 "안 온다"를
    판정하는데, 이 숫자는 계약이 아니라 내가 고른 값이다. capability 상태 전달 경로가
    생기면 서버 선언으로 대체해야 하고, 그때까지는 **추론 지연을 2초 이상으로 올리면
    정상 동작을 미배포로 오판한다.** 지금 시나리오 최대치가 500ms라 문제되지 않지만
    경계가 존재한다는 사실은 남는다.

19. **연계 부재 시 화면이 소스별 추적을 그리기는 하나, 두 추적이 같은 대상인지 사람이
    판단할 근거는 주지 않는다.** 지금은 26px 떨어진 박스 두 개가 나란히 뜬다. 관제사가
    "이게 둘인가 하나인가"를 물을 때 화면이 답할 것이 없다 — 연계가 없으면 원래 답이
    없는 것이 맞지만, **그 사실을 더 분명히 말할 표시**가 필요할 수 있다. 회의 안건 후보.

20. **온디바이스 진행영역이 고정 사각형이다.** 실제로는 로봇의 조향·속도에 따라 움직이는
    영역이다. 목 서버에 조향 상태가 없어 고정으로 뒀고, 정합 검증에는 영향이 없다.
    Unity 시뮬레이터 단계에서 실제 진행영역을 받으면 그때 맞춘다.
