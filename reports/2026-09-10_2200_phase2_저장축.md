## 배경

Phase 1이 얇은 파이프라인을 관통시키면서 **저장은 일부러 비워 두었다.**
`TelemetryWriter.write()`는 목적 인터페이스이고 구현은 JSONL placeholder였다. Phase 2는 **그
인터페이스 뒤를 갈아끼우는 것**이 본체다 — 그러라고 나눠 둔 지점이다.

딛고 선 것: Phase 1이 확정한 토픽 규약(`mk2.telemetry.<채널>`)·파티션 키·컨슈머 그룹,
공통 헤더 규격 v1.0, 가동 중인 Mosquitto·Kafka, 그리고 설계방이 2026-09-09에 확정한 **착수 결정
다섯**(TSDB 제품 · MySQL DB/계정/테이블 범위 · 적재 시각 기준 · `sequence_id` 의미 · 채널 본문 규격).

**이번에 저장하는 것은 넷이다** — 계측 추이(TimescaleDB) · 신원 대장(MySQL) · 사건 책임(MySQL) ·
임무 사건 열(MySQL). 감사와 실행 기록은 둘 다 사건이지만 **조회 패턴이 다르다**(검색 vs 복원)라
같은 MySQL의 다른 테이블로 나눴다.

### 확정한 것 — 이 Phase가 굳힌 구조 결정

**① 시간축은 발행 `timestamp`다.** 지연 도착 데이터가 **원래 측정 시각 자리에 꽂혀야** 되감기와
구간 조회가 성립한다. `received_at` 축으로는 원천적으로 불가능하다.

**② 유일 키는 스트림 좌표다** — `(ts, stream_topic, stream_partition, stream_offset)`.
저장 소비자는 `auto.offset.reset=earliest` + 자동 커밋이라 **구조적으로 재소비**한다. 업무 내용 키
(`sequence_id`)로는 막을 수 없다 — 로봇은 항상 0, `status`에는 없고, 증강 분석은 순번을 대상끼리
공유한다. **재소비는 도착 계층의 현상이므로 도착 좌표로 잡는다.**

**③ 검출은 저장이 아니라 조회에서 한다.** 적재 시점에 "유실"이라고 못 박으면 7분 뒤 도착해 갭을
메울 데이터와 정면 충돌한다. 원본만 넣고 갭은 `LAG()` 윈도우 함수로 계산한다. 적재 시 상태를
들고 있는 칼럼(`seq_epoch` 같은)을 두지 않았다 — 무상태 원칙과 충돌하고 재기동 시 소실된다.

**④ 갭이 곧 유실이 아니다.** 채널·타입마다 QoS와 spool 정책이 달라 갭의 의미가 다르다.
판정을 네 갈래로 나눴다: `gap`(→ `loss_candidate` / `loss_not_implied`) · `seq_stalled` ·
`seq_reset_without_boundary` · `segment_start`.

**⑤ append-only를 코드가 아니라 DB 권한이 지킨다.** `mk2_app`에는 `mission_event`·`audit_log`에
`SELECT, INSERT`만 있다. 코드 규율로 약속하면 언젠가 누군가 깬다.

**⑥ 원본은 `payload` JSONB, 칼럼은 추출이다.** 계측 행의 칼럼(`source_id`·`reason`·`device_status`
…)은 인덱스와 조회를 위한 **추출**이고, 공통 헤더를 포함한 **원본 메시지 전체가 `payload`에**
있다. 저장 시점에 없는 값을 채워 넣지 않는다 — 채우면 "생산자가 안 보낸 것"과 "백엔드가 채운 것"을
구분할 수 없다. 규격대로 키를 채우는 것은 **읽기 함수**(`normalize.py`)의 몫이다. JSONB는 키 순서를
잃지만 값은 보존하므로 이 손실은 수용했다(바이트 재현이 필요해지면 그때 `raw BYTEA` 재검토).

**⑦ 저장 제품이 드러나는 파일은 셋뿐이다** — `tsdb_writer.py`(psycopg) · `registry.py`(PyMySQL) ·
`mission.py`(PyMySQL). 그 위(`consumer.py`·`bridge.py`)는 목적 인터페이스만 안다. 제품을 바꾸면 이
셋만 바뀐다.

### ① 서버 왕복에서 걸린 사고 셋 — 전부 지시 방식의 문제였다

| 사고 | 원인 | 교훈 |
|---|---|---|
| TimescaleDB가 **36회 재시작** | `/docker-entrypoint-initdb.d`에 마운트한 디렉터리가 `700`(umask 077 잔존) → 컨테이너 안 postgres(**uid 70**, Alpine)가 못 읽어 `exit 1` | `.env` 때문에 건 `umask 077`을 **그 직후 되돌렸어야** 했다. 그리고 애초에 그 경로를 마운트한 것이 설계 결함이었다 |
| MySQL 권한 검증이 **하나도 실행되지 않음** | `mysql:8.0` 이미지에 **`hostname` 명령이 없다**(Oracle Linux 기반). `$(hostname -i)`가 빈 문자열 → 로컬 소켓 접속 → `mk2_app@localhost`로 거부 | `Access denied` 5줄은 **권한 검증 결과가 아니었다.** 검증 안 된 것을 검증됐다고 적지 않고 다시 했다 |
| pytest 2건 실패 | 상주 프로세스 3개를 **한 코드블록에 세 줄로** 적어서 첫 줄만 실행됨 | 터미널을 나눠 적어야 한다. 이후 모든 지시를 **터미널 1/2/3/4로 명시** |

### ② 설계 근거가 실물로 확인된 순간 둘

- **retained `status`가 47분 전 `ts`로 다시 흘렀다**(`lag_s = 2836.224`). 레지스트리 시각 가드가
  없었으면 재기동할 때마다 대장이 과거로 되돌아간다. **가드의 근거가 탁상이 아니라 실측이 됐다.**
- **소비자가 없는 동안 Kafka가 8건을 들고 있다가 넘겨줬다.** 소비자를 다시 띄우자 한꺼번에
  저장됐다 — Kafka를 고른 이유(단기 버퍼·독립 오프셋)가 그대로 동작한 장면이다.

### ③ `mission_event.seq`는 단조 증가하지만 **연속이 아니다**

실측: `2 → 4 → 5`. `1`은 자가시험 행이, **`3`은 실패한 INSERT가** 채번을 소비했다(InnoDB는 실패한
INSERT도 AUTO_INCREMENT를 쓴다). VZ-D-02의 「순번」 용도에는 단조성만 있으면 되지만, **가시화가
"연속"을 가정하면 이 구멍을 유실로 오해한다.** → §9-2 문의 [2-9](../docs/be/vz-mission-record-inquiry.md#q9)에 통지 항목으로 넣었다.

### ④ PyMySQL 자동 재접속이 **세션 타임존을 조용히 잃는다** (고쳤다)

`pytest`가 `DeprecationWarning` 8건을 냈다(`ping(reconnect=True)`). 소스를 직접 읽어 확인한 결과
**deprecation보다 중요한 것**이 있었다:

```python
def ping(self, reconnect=False):
    if reconnect: warnings.warn("The 'reconnect' argument is deprecated. ...")
    if self._sock is None:
        if reconnect: self.connect()      # ← 새 세션이다
```

`connect()`가 되살리는 것은 **자기가 아는 것**(charset·autocommit·init_command)뿐이다. 그 뒤에
우리가 실행한 `SET time_zone = '+00:00'`은 **복원되지 않는다.** 이 서버는 `system_tz=KST`다.

**지금 틀린 데이터는 없다** — 두 모듈이 쓰는 시각은 ① 파라미터로 넣는 naive UTC `datetime`
(`DATETIME(6)`에 리터럴로 저장, 변환 없음)과 ② `UTC_TIMESTAMP(6)`(타임존 무관 함수)뿐이라 세션
tz와 무관하다. **문제는 나중이다** — 조회 층이 `NOW()`나 `TIMESTAMP` 비교를 넣는 순간 9시간
어긋난다. 그래서 `ping(reconnect=False)` + **우리가 직접 `_connect()`** 로 바꿨다(두 파일 3줄씩).
재확인: `103 passed in 34.79s`, **warnings summary 통째로 사라짐**.

### ⑨ `.gitignore`의 `!.env.example`이 무효였다 (고쳤다)

`!.env.example            # 예제(placeholder만)는 올린다` — gitignore에서 `#`는 **줄 첫 글자일 때만**
주석이다. 줄 끝에 붙이면 패턴의 일부가 되어, 이 줄은 `.env.example`이 아니라 *"`!.env.example   # 예제…`"
라는 이름의 파일*을 되살리라는 규칙이 됐고 아무 일도 하지 않았다. 결과적으로 `.env.example`은 `.env.*`에
계속 걸렸다. **지금 피해는 없다**(그 파일이 없다) — "만들면 조용히 안 올라간다"는 함정이었다. 주석을
윗줄로 옮겨 고쳤고, 임시 파일로 `git status`에 뜨는 것을 확인한 뒤 지웠다.

> 같은 함정을 이번 Phase의 `.gitignore` 추가분(`_hwsrc/`·`infra/sql/mk2_grants_*.sql`)에는 만들지
> 않았다 — 줄 끝 주석 없음. 판정은 `git check-ignore`의 종료코드가 아니라 **`git status`로** 했다
> (부정 패턴이 매치돼도 check-ignore는 0을 돌려준다).

## 검증 범위의 한계 — **"검증됨"으로 적지 않은 것**

지시서 §7 각주가 미리 못 박은 한계이고, 전건 통과가 이것을 바꾸지 않는다.

1. **`session_id` 경로는 가짜 발행자로만 검증됐다.** HW가 아직 안 보낸다. 실노드는 `status`의
   `birth`를 경계로 쓰는 **폴백 경로**로 동작한다.
2. **로봇·액추에이터·증강 분석 본문도 가짜 발행자로만 검증됐다.** 세 실노드가 서버 브로커에 붙어
   있지 않다. 본문은 HW 소스를 그대로 베꼈고 **증강 분석은 결함까지 그대로 재현**했다 — 결함을
   고쳐서 흉내 내면 판정 17·22가 실제로는 아무것도 검증하지 못하기 때문이다.
3. **실노드 관통 검증은 §6-3의 편집 4개가 들어와야 가능하다.** 지금 붙이면 전량 격리된다.
   **TSDB에 실노드 데이터가 있긴 하다** — Phase 1 센서 구간(2026-09-07 12:16~12:32, heartbeat
   193건 등)이 Kafka 재소비로 적재됐다. 그러나 그것은 **Phase 1 ingest가 만든 메시지라 Kafka 헤더가
   없어** `ingest_at`·`entity_type`·`lag_s`가 전부 NULL이다. **새 ingest(2단 검증 + 헤더)를 거친
   실노드 데이터는 아직 한 건도 없다.**
4. **감사는 스키마와 음성 대조까지다.** 쓰기 경로·actor 토큰 주입은 Phase 6(인증이 선행조건).
5. **실행 기록의 실제 쓰기 배선이 없다.** 생산자는 가시화·엣지이고 Phase 6/7이다. 지금
   `append_mission_event()`를 부르는 것은 테스트뿐이다.
6. **되감기 질의·구체 필드·실패 단계 어휘·보존 기간은 미확정**이다 — BE-S-08 원문이 *"실제 소비
   시점에 구체화한다"* 이고, 가시화 회신(§9-2)을 기다린다.

## 3차 (2026-09-14) — DDL 정정 1건: `mission_event.actor_kind` NULL → NOT NULL

**2차 재검수 ④가 만든 §1 표(`actor_kind` ❌ 반드시)와 DDL(`NULL`)이 어긋났다.** 표의 주가
*"둘이 어긋나면 DDL을 이 표에 맞춘다"* 이므로 DDL을 맞췄다. 근거는 VZ-D-02 *"산출 주체(AI·백엔드·
사람)를 **반드시** 포함"* — 처음(9-10) `NULL`로 만든 것이 잘못 읽은 것이다.

**서버(사람이 root로 실행, 전부 로그로 확인):**

| 순서 | 한 것 | 결과 |
|---|---|---|
| 1 | NULL 행 세기 | `total_rows 3 · null_rows 2 · null_test_rows 2` — NULL 행은 전부 pytest 잔여(`m-test-*`, 키 없는 사건 2건) |
| 2 | 첫 ALTER 시도(NULL 행 둔 채) | **`ERROR 1138 Invalid use of NULL value`** — strict 모드는 NULL 행이 있으면 NOT NULL 전환을 거부한다 |
| 3 | `DELETE … WHERE actor_kind IS NULL AND mission_id LIKE 'm-test-%'` | `total_rows 1 · null_rows 0` |
| 4 | `ALTER TABLE mission_event MODIFY actor_kind VARCHAR(32) NOT NULL COMMENT '…'` | 성공. `SHOW CREATE TABLE`에 `actor_kind varchar(32) … NOT NULL COMMENT 'VZ-D-02 …'` 확인 |
| 5 | `pytest tests/test_mission_event.py tests/test_mysql_storage.py` | **`20 passed in 0.22s`** (단위 10 + MySQL 10), skip 0, warning 0 |

> ⚠ `MODIFY`는 칼럼을 통째로 다시 정의하므로 **`COMMENT`를 같이 적지 않으면 지워진다.** 그래서
> 한 줄짜리 ALTER를 그대로 치지 않고 COMMENT를 붙였다.

**컴퓨터(편집) — "한 줄"의 여파 4파일, 전부 이 칼럼 하나 얘기다:**

| 파일 | 변경 |
|---|---|
| `infra/sql/mk2_mysql_schema.sql` | `actor_kind` `NULL`→`NOT NULL` + COMMENT, 정정 이력 주석. `audit_log.actor_kind`(Phase 6 토큰 주입)는 **손대지 않았다** |
| `backend/storage/mission.py` | `build_params(actor_kind=None)` → **필수 인자**. 빈 문자열은 `ValueError` — DB NOT NULL이 `''`는 못 거르기 때문. 어휘(`ai\|backend\|human`)는 VZ 회신 전이라 강제하지 않는다 |
| `tests/test_mysql_storage.py` | `actor_kind` 없던 호출 3곳(`again`·`a`·`b`)에 추가 — 안 고치면 `test_mission_event_idempotent`가 1048로 깨진다 |
| `tests/test_mission_event.py` | "필수 넷"→"다섯"(산출 주체 포함), **음성 `test_build_params_requires_actor_kind` 신설**(빠지면 `TypeError`, 빈 값이면 `ValueError`) → 9건→**10건** |

**전체 회귀 건수는 103→104가 됐지만, 이 변경 뒤 전체 회귀(서비스 3개 기동 후 `pytest -q`)는
돌리지 않았다** — 위 2파일 20건만 돌렸다. 나머지 84건은 이 칼럼을 건드리지 않는다.

**서버와 파일이 다른 곳 1군데(무해):** `actor_id`의 COMMENT — 서버 `'위와 같음'`, 파일은 *"산출
주체의 개별 식별자. 종류만 필수이고 개별 식별자는 비워도 된다"*. 구조·제약은 같다. 맞추려면
`ALTER TABLE mission_event MODIFY actor_id VARCHAR(128) NULL COMMENT '…'` 한 줄(필수 아님).

**교훈 (경로):** 서버의 SQL 사본 경로는 **`~/capstone-db/mk2_sql/`** 이다(「서버에 남은 것」에
이미 적혀 있었다). 이번에 저장소 사본 경로를 잘못 안내해 사용자가 바로잡았다 — 서버 경로는
「서버에 남은 것」 표에서 찾아 쓴다.
